# GH100 — Renommer un type d'objet (nom / préfixe) migre les objets existants

## Contexte

Dans Modèle de données → Structure, l'éditeur de type enregistre aujourd'hui le schéma puis ne
migre que les **champs** renommés (GH77) et les **statuts / valeurs d'enum** renommés (GH82).
Changer le **nom** ou le **préfixe** d'un type qui a déjà des objets laisse ceux-ci orphelins :

- leur `objectTypeRef` vaut toujours `<nœud>::<ancien nom>` → ils disparaissent des listes ;
- leurs IDs gardent l'ancien préfixe ;
- les refs `<nœud>::<ancien nom>` des `linkTypes` ne visent plus rien ;
- le fichier d'ordre `.polenta/trees/<nœud>/<ancien nom>.yaml` n'est plus lu.

Cas réel (PH2) : `hmi-PH2`, type `HMI_PH2_REQ` (2 exigences) renommé en `VE22D_REQ` (nom + préfixe)
→ « Aucun élément ».

Décision utilisateur : au changement de préfixe, **les IDs des objets existants sont renommés**.

## Comportement attendu

Périmètre : un type `T` du nœud `N` du repo `R`, modifié dans l'éditeur de type (Structure).

### 1. Changement de nom (`old` → `new`)

| Donnée | Migration |
|---|---|
| `objectTypeRef` des exigences / tests / campagnes de `R` | `N::old` → `N::new` |
| `testSnapshot.objectTypeRef` des campagnes (tous les repos du workspace) | idem |
| `.polenta/trees/N/old.yaml` | renommé `new.yaml`, `typeId: new` |
| `linkTypes[].sourceRefs / targetRefs` du schéma de `R` | `N::old` → `N::new` |
| `linkTypes` des **autres** repos du workspace | idem, **sauf** si un autre repo déclare encore un type `N::old` (la ref lui appartient alors — collision possible, chaque repo ayant un nœud `root`) |

### 2. Changement de préfixe (`OLD` → `NEW`), types `requirement` et `test`

Chaque objet `OLD-NNNN` du type devient `NEW-NNNN` (**même numéro**).

| Donnée | Migration |
|---|---|
| Fichier `requirements/OLD-NNNN.yaml` / `tests/OLD-NNNN.yaml` de `R` | renommé `NEW-NNNN.yaml`, champ `id` mis à jour, `history` conservé tel quel |
| `test-runs/OLD-NNNN/` | dossier renommé, `testCaseId` / `runId` (`OLD-NNNN-run-…`) réécrits |
| Toutes les occurrences de l'ID entier dans les fichiers de données des **repos du workspace** : `links/links.yaml` (`sourceId`, `targetId`), `campaigns/*.yaml` (`testCaseIds`, `runs[]` / `removedRuns[]` : `testCaseId`, `requirementId`, `entryId`, `runId`, `testSnapshot.id`), `test-runs/**`, `reviews/*.yaml` (`objectId`), `impact-analyses/*`, `impact-acks/<id>/` (dossier + `triggerReqId`), arbres `.polenta/trees/**` (`objectId`), texte des champs (richtext compris) | réécriture par `renumberText` / `renumberPath` (`@polenta/merge-core`, GH37) : ID entier uniquement (`SYS-0043` ne touche ni `SYS-00431` ni `XSYS-0043`), suffixes `entryId` couverts |
| Pierres tombales | une `.polenta/tombstones/OLD-NNNN` par ID renommé dans `R` (GH20 : un ID n'est jamais réutilisé, même si `OLD` est un jour redéclaré) |

Les types `campaign` ne sont pas concernés par le préfixe : les IDs de campagne sont `CAMP-NNNN`
quel que soit le type (`campaigns.service.ts`) — leur préfixe n'est pas utilisé.

### 3. Pré-contrôles (aucune écriture si l'un échoue)

- `NEW-NNNN` existe déjà (fichier ou pierre tombale) dans `R` pour l'un des numéros → refus,
  message listant les IDs en collision.
- Un repo du workspace à réécrire n'est pas chargé / accessible → refus, repo nommé (sinon ses
  liens resteraient sur l'ancien ID sans que l'utilisateur le sache).
- Unicité du préfixe projet (règle 10) : inchangé, déjà contrôlé à l'enregistrement.

### 4. Interface

- À l'enregistrement d'un type dont le nom et/ou le préfixe a changé **et qui a des objets** :
  modale de confirmation (même principe que GH82) : « N objets renommés `OLD-…` → `NEW-…`,
  M fichiers réécrits dans K repos (liste) ; la date de création git des objets renommés sera
  celle du renommage ». Annuler = rien n'est enregistré, ni schéma ni objets.
- Type sans objet : enregistrement direct (comportement actuel), arbre et refs de liens migrés.
- Après migration : compte rendu (objets migrés, fichiers réécrits, échecs éventuels), comme GH77.
- Les caches (listes, détail, campagnes) sont invalidés.

### 5. Ordre et reprise

1. Pré-contrôles. 2. Écriture du schéma. 3. Migration des objets et références. Une erreur
d'écriture en cours de route n'interrompt pas les autres fichiers ; elle est listée dans le compte
rendu. Rien n'est commité : l'utilisateur relit le diff git (et peut `git checkout` pour annuler).

## Critères d'acceptation

1. Renommer `HMI_PH2_REQ` → `VE22D_REQ` (nom + préfixe) dans `hmi-PH2` avec 2 exigences : les
   fichiers deviennent `VE22D_REQ-0001/0002.yaml` (`id`, `objectTypeRef: root::VE22D_REQ`),
   apparaissent dans « HMI VE22D / Exigence » dans le même ordre / les mêmes dossiers, et
   `.polenta/tombstones/HMI_PH2_REQ-0001/0002` existent.
2. Un lien stocké dans `handstickProduct/links/links.yaml` vers `HMI_PH2_REQ-0001` vise
   `VE22D_REQ-0001` après migration ; la couverture / l'éditeur de liens le montrent.
3. Une campagne contenant un test renommé : `testCaseIds`, `entryId`, `runs[].testCaseId`,
   `testSnapshot.id`/`objectTypeRef` et le dossier `test-runs/` sont migrés ; la page d'exécution
   affiche les runs existants.
4. Renommer le seul nom (préfixe inchangé) : IDs inchangés, `objectTypeRef`, arbre et refs de
   liens migrés.
5. Collision `NEW-NNNN` déjà présente (fichier ou pierre tombale) : refus, aucun fichier modifié.
6. Annuler la confirmation : aucun fichier modifié.
7. `SYS-00431` et `XSYS-0043` ne sont pas touchés par le renommage de `SYS-0043`.
8. Tests unitaires couvrant 1–7 (fixture workspace multi-repos).

## Hors scope

- Scripts / requêtes / dashboards de la vue Suivi (code côté projet, GH79) : un ID ou un nom de
  type écrit en dur dans un script n'est pas réécrit — signalé dans la confirmation.
- Historique git : pas de suivi des renommages (`fileHistoryMap` ne suit pas les renames) —
  createdAt/createdBy des objets renommés = commit du renommage. Documenté, non corrigé ici.
- Tags git / baselines, exports déjà produits, `.<user>.pref`, brouillons de merge, `versions/`
  (lecture seule héritée).
- Réparation a posteriori d'un renommage déjà fait sans migration (cas PH2 actuel) : remettre
  l'ancien nom/préfixe dans l'outil, puis refaire le renommage une fois GH100 livré.
- Renommage depuis le serveur MCP (aucun tool de renommage de type aujourd'hui).
- Changement de nœud d'un type (`moveElementToNode`, déjà géré).

## À vérifier en Design

- `RequirementsService.retargetObjectTypeRef` / `rewriteObjects` appellent `persist(repoPath,
  repoPath, …)` sans résoudre le repo composant (`resolveComponentRepoPath`) : s'assurer que la
  migration écrit bien dans `R` (le repo du type), y compris quand l'éditeur est ouvert depuis le
  repo produit.
- Point d'entrée : nouveau handler IPC (ex. `schema:rename-object-type`) avec `dryRun` pour la
  modale de confirmation (comptes), puis exécution — sur le modèle de `previewValueRenames` /
  `renameValues` (GH82).
- Écriture sérialisée (`serialize-writes.util.ts`) et invalidation du graphe (`GRAPH_WRITE_CHANNELS`).
