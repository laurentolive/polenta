# GH103 — Gestion des repos depuis Polenta (GitHub, Forgejo)

Issue parapluie : #103. Lots livrables, chacun avec sa propre issue :

| Lot | Issue | Contenu | Spec |
|---|---|---|---|
| A | #106 | Branche d'intégration explicite (onglet Structure, désignation commitée) | §1 |
| B | #107 | Ajouter un repo : création ou adoption sur GitHub / Forgejo | §2 |
| C | #108 | Paramètres du repo : membres, visibilité, nouvelle branche d'intégration | §3 |

Ordre conseillé : A (débloque l'usage aujourd'hui), puis B, puis C. B et C partagent le provider
GitHub étendu (§4) : le lot qui arrive en premier le livre.

## Contexte

La gestion d'un repo oblige aujourd'hui à faire des allers-retours entre Polenta et l'interface
de GitHub ou de Forgejo. Objectif de l'issue : tout faire depuis Polenta, quelle que soit la forge.
Invariant posé par l'issue : **un repo ne doit jamais se retrouver sans branche d'intégration**.

### Constat (projet PH2, composant `hmi-PH2`, 2026-10-16)

`int-PH2` a été créée depuis le panneau Version. « Publier » reste bloqué avec « `int-PH2` n'est
pas la branche d'intégration configurée (`int-VE22D`) — publication impossible depuis ici ».

- `config/project.yaml` est **versionné dans la branche**. `int-PH2` a été créée depuis
  `int-VE22D` (même commit `c831de5`) : elle hérite de `integrationBranch: int-VE22D`.
- À la création d'une `int-*`, `useBranchCheckout.maybeSetIntegrationBranch` réécrit le fichier,
  mais **sans commit**. La valeur reste une modification en attente : elle peut être perdue (checkout,
  resynchronisation) ou, comme ici, n'apparaître nulle part. Rien ne la rend visible à l'utilisateur.
- Le message de blocage n'offre aucune action. Le widget `IntegrationBranchSelector` décrit par
  `SPEC-FORKS-BRANCHES-BASELINES.md` §2.2 n'existe plus (retiré au fil de T86/T87) : la seule façon
  de désigner une branche est un checkout ou une création de branche `int-*`, implicite.

### Existant réutilisé

- `ForgeService` / `forgejo.provider.ts` (GH45 §6) : liste des repos, organisations où créer,
  existence d'un nom, création d'un repo **privé** dans une organisation, droits, membres
  d'organisation. Création publiée sur `main`, pas sur une `int-*`.
- `github.provider.ts` : identité et Device Flow seulement (scope `repo user:email`).
- `CreateRepoOnServer` (dans `AddDependencyModal`) et la création « Sur le serveur » de l'accueil.
- `useBranchCheckout` (checkout, création de branche, propagation de pin), `RepoBranchSelector`
  (onglet Structure), `useModificationMode` / `ModificationControl` (état de « Publier »).

### Articulation avec les autres issues

- `ANALYSE-SERVEUR-AUTOHEBERGE.md` §4.4 et GH45 « Hors scope » excluaient l'administration des
  droits dans Polenta. **Décision du 2026-10-16 : amendement.** Polenta gère l'**accès à un repo**
  (collaborateurs, équipes de l'organisation attribuées au repo, visibilité). Les **comptes**, la
  **composition des équipes** et les **organisations** restent gérés dans la forge.
- #63 (administration du serveur) n'est pas touchée : elle porte sur l'hôte et les instances, pas
  sur les repos. Son import CSV d'utilisateurs reste de son ressort.
- #17 (même repo monté deux fois sur deux `int-*`) : compatible. Le modèle ci-dessous permet
  plusieurs `int-*` cohérentes dans un même repo, chacune se désignant elle-même.

## Décisions

1. **Source de vérité de la branche d'intégration : `config/project.yaml`, commité.** Désigner une
   branche produit toujours un commit (et un push) de ce fichier sur la branche désignée. Une
   désignation n'est jamais laissée en modification en attente.
   Rejeté : la branche par défaut de la forge comme source (hors ligne et git générique non
   couverts), un fichier local non versionné (non partagé entre utilisateurs).
2. **Invariant de cohérence** : sur une branche `int-X`, `config/project.yaml` contient
   `integrationBranch: int-X`. Une branche `dev-*` hérite de la valeur de l'`int-*` dont elle part.
3. **Convention `int-xxx` obligatoire** pour tout repo créé ou adopté (§2). Les repos existants dont
   l'intégration est `main` (fichier absent, repli actuel) continuent de fonctionner. Polenta propose
   de créer une `int-*`, sans l'imposer.
4. **Branche par défaut de la forge alignée** sur la branche d'intégration à chaque création ou
   désignation, quand le compte en a le droit. Effet utile : la forge refuse de supprimer sa branche
   par défaut, ce qui protège l'invariant côté serveur.
5. **Repo existant non vide** : on complète ce qui manque (§2.3), on ne redemande pas ce qui existe.

## 1. Branche d'intégration explicite (lot A, #106)

### 1.1 Où et comment elle s'affiche

Onglet **Structure** du Modèle de données, sur la ligne de **chaque repo** du workspace (root et
repos séparés ; pas les composants locaux, qui partagent le repo de leur parent) :

- Un seul contrôle : la combo de branche (`RepoBranchSelector`). Elle affiche la branche courante
  (en detached HEAD, composant épinglé : la baseline checkoutée, sinon le commit abrégé) ; dans sa liste, la branche d'intégration
  désignée porte la mention « intégration ». Y choisir une branche en fait le checkout (sous la
  garde des modifications en attente) ; y créer une `int-*` la désigne (§1.3).
- L'intégration n'est affichée à côté de la combo **que si elle diffère de la branche checkoutée**
  (sinon l'information serait répétée) :
  - **Incohérente** : la branche courante est une `int-*` dont le `project.yaml` désigne une autre
    branche (cas PH2) : action ⚠ « Désigner `int-PH2` comme intégration ».
  - Autre branche, ou detached HEAD : « Intégration : `int-X` », pour information.
  - Rien sur une branche `dev-*` (modification en cours, l'écart est normal).
- Le pin d'un composant n'est affiché (en avertissement) que s'il diffère de ce qui est checkouté ;
  pin et checkout sont identiques s'ils désignent la même version (même nom, ou même commit : SHA épinglé, tag ou branche qui pointe sur HEAD).
- Changer d'intégration : checkout de l'`int-*` voulue dans la combo, puis « Désigner » si elle
  n'est pas déjà désignée.

### 1.2 Désigner une branche existante `int-Y`

Depuis le menu (§1.1) ou depuis l'action du bandeau (§1.4). Séquence :

1. Si des modifications sont en attente : même garde de confirmation qu'un checkout ailleurs dans
   l'app. Les modifications suivent le checkout comme aujourd'hui (comportement isomorphic-git) et
   **ne sont pas embarquées** dans le commit de l'étape 3.
2. Checkout de `int-Y` (crée la branche locale de suivi si elle n'existe que sur `origin`).
3. Si `project.yaml` ne désigne pas déjà `int-Y` : écriture de `integrationBranch: int-Y` (les
   autres clés sont conservées) puis **commit de ce seul fichier**. Message de commit :
   `Branche d'intégration : int-Y`.
4. Push de `int-Y` vers `origin`. C'est un best-effort, comme dans « Publier » (§2.3 de
   SPEC-FORKS) : un échec est signalé par l'indicateur de synchronisation (§2.6) et relancé par
   l'auto-pull.
5. Branche par défaut de la forge réglée sur `int-Y` si le compte est admin du repo. Sinon, aucun
   message bloquant : une mention dans le résultat (« la branche par défaut sur <hôte> reste `X` »).
6. Propagation du pin vers les repos parents (mécanisme existant `propagatePinToDependents`).

### 1.3 Créer une nouvelle branche d'intégration

« Nouvelle branche… » de la combo, avec un nom `int-<nom>` : la branche est créée à la position
courante (checkouter d'abord une baseline pour partir d'elle), puis la séquence du §1.2 s'applique.
Mêmes caractères autorisés qu'un nom de branche `dev-*` ; un nom déjà pris (local ou `origin`) est
refusé avant toute écriture.

Créer une `int-*` depuis le panneau Version ou depuis le `RepoBranchSelector` revient à la même
chose : **la création désigne la branche, avec commit**. Cela remplace l'écriture non commitée de
`maybeSetIntegrationBranch`.

### 1.4 Checkout d'une `int-*` sans la désigner

Un simple **checkout** d'une `int-*` (panneau Version, `RepoBranchSelector`) ne commite rien : un
checkout ne doit pas créer de commit à l'insu de l'utilisateur.

- Si son `project.yaml` la désigne déjà, elle devient l'intégration du repo, sans autre action.
- Sinon (cas PH2), le blocage de « Publier » est remplacé par un bandeau avec action :
  « `int-PH2` n'est pas désignée comme branche d'intégration (le fichier indique `int-VE22D`).
  [Désigner `int-PH2`] ». Le bouton exécute le §1.2.
- Une branche courante qui ne commence pas par `int-` garde le comportement actuel de
  « Publier » (SPEC-FORKS §2.1).

### 1.5 Jamais sans branche d'intégration

- Supprimer la branche d'intégration désignée est refusé, dans le panneau Version comme ailleurs,
  avec le message « Branche d'intégration de <repo> : désignez-en une autre avant de la supprimer ».
- Supprimer la dernière branche `int-*` d'un repo qui en a une est refusé, même si elle n'est pas
  désignée.
- Côté forge, l'alignement de la branche par défaut (décision 4) empêche la suppression depuis
  l'interface web.

### 1.6 Critères d'acceptation (lot A)

1. Dans `hmi-PH2` (sur `int-PH2`, fichier à `int-VE22D`), l'onglet Structure affiche
   « Intégration : `int-VE22D` » avec la pastille « incohérente ». Un clic sur « Désigner
   `int-PH2` » produit un commit `Branche d'intégration : int-PH2` qui ne contient que
   `config/project.yaml`, pousse `int-PH2`, et « Publier » devient actif.
2. Le bandeau de « Publier » propose la même action (§1.4) et aboutit au même état.
3. Après une désignation, `git status` ne montre aucune modification de `config/project.yaml`.
   Les modifications en attente avant la désignation sont toujours présentes et ne figurent pas
   dans le commit.
4. Une `int-*` créée depuis le panneau Version, depuis le `RepoBranchSelector` ou depuis
   « Nouvelle branche d'intégration… » est désignée et commitée, sans autre action.
5. Un checkout d'une `int-*` ne crée jamais de commit.
6. La suppression de la branche désignée, ou de la dernière `int-*`, est refusée avec un message.
7. Un repo en `main` sans `project.yaml` fonctionne comme avant, avec la pastille « hors
   convention ».
8. Hors ligne : la désignation commite localement. Le push est signalé « à publier » et repart à
   la reconnexion.

## 2. Ajouter un repo : création ou adoption (lot B, #107)

### 2.1 Points d'entrée

Un même assistant « Ajouter un repo », ouvert depuis :

- l'accueil, « Créer » → « Sur le serveur » (remplace le flux GH45 §6.2) ;
- l'accueil, « Depuis un repo » (repo existant) ;
- l'onglet Structure, `AddDependencyModal` (composant en repo séparé ; remplace
  `CreateRepoOnServer`).

Première étape : **Nouveau repo** ou **Repo existant** (liste des repos du compte avec recherche,
ou saisie d'URL comme aujourd'hui).

### 2.2 Nouveau repo

| Champ | Règle |
|---|---|
| Service | Comptes connectés de type `github` ou `forgejo` (un compte `generic` n'est pas proposé). Avec un seul compte éligible, choix fait d'office. |
| Propriétaire | Le compte de l'utilisateur ou une organisation dans laquelle il peut créer un repo. Les autres ne sont pas proposées. |
| Nom | Caractères acceptés par la forge. **Disponibilité vérifiée pendant la saisie** (à la pause de frappe) et une dernière fois avant création. |
| Visibilité | Privé (par défaut) ou public. |
| Description | **Obligatoire**, non vide. Devient la description du repo sur la forge et le contenu du `README.md`. |
| Branche d'intégration | Obligatoire, préfixe `int-` imposé (comme au §1.3), pré-remplie avec `int-<nom>`. |
| Membres | Facultatif : collaborateurs et équipes, avec le même widget qu'au §3.2. |

Séquence, **après validation de tous les champs** (rien n'est écrit avant) :

1. Création du repo distant vide, avec la visibilité et la description choisies.
2. Préparation locale (contenu d'un nouveau projet Polenta, comme GH27 / `initProjectRepo`), plus :
   - `README.md` : titre = nom, paragraphe = description ;
   - `config/project.yaml` avec `integrationBranch: int-<x>`.
3. Premier commit **sur `int-<x>`**. Aucune branche `main` n'est créée.
4. Push de `int-<x>`, puis branche par défaut de la forge = `int-<x>`.
5. Ajout des membres choisis.
6. Fin selon le point d'entrée :
   - accueil : le projet s'ouvre ;
   - composant : l'URL et la branche `int-<x>` sont inscrites dans `polenta-repo.yaml`, puis le
     clone suit le flux habituel.

**Échec partiel** : Polenta ne supprime jamais un repo distant (règle GH45 inchangée). La fenêtre
affiche les étapes réussies et celles en échec. Les étapes restantes peuvent être reprises depuis
« Paramètres du repo » (§3), ou au §2.3 en adoptant le repo.

### 2.3 Repo existant

Polenta inspecte le repo choisi et affiche ce qu'il a trouvé avant toute action :

- **Vide** (aucun commit) : parcours complet du §2.2. La visibilité et la description sont
  pré-remplies depuis la forge et restent modifiables.
- **Non vide**, chaque élément est vérifié séparément et **seul ce qui manque est demandé** :

| Élément | Présent si… | Si absent, Polenta… |
|---|---|---|
| Branche d'intégration | La branche par défaut est une `int-*`, ou son `project.yaml` désigne une `int-*` existante. | Demande un nom `int-*`, la crée depuis la branche par défaut et la désigne (§1.2). |
| Description | Description de la forge non vide **et** `README.md` présent sur l'intégration. | Demande la description, la reporte sur la forge et/ou commite un `README.md` sur l'intégration. |
| Projet Polenta | `.polenta/` présent sur l'intégration. | Après confirmation explicite, commite l'initialisation Polenta sur l'intégration. Sans confirmation, l'ajout est abandonné. |
| Visibilité, membres | Toujours présents. | Affichés en lecture ; modifiables ensuite au §3. |

Selon les droits du compte :

- **Sans droit d'écriture** : rien n'est complété. Le repo est ajouté en lecture seule s'il est
  déjà complet. Sinon, l'ajout est refusé avec la liste de ce qui manque.
- **Écriture sans admin** : les éléments locaux (branche, `README.md`, `project.yaml`, init
  Polenta) sont complétés. Les éléments de la forge (description, branche par défaut) sont signalés
  « à faire par un administrateur du repo », sans bloquer l'ajout.

Le résultat attendu est le même que pour un repo neuf : une `int-*` désignée et commitée, un
`README.md` et une description, un projet Polenta, la branche par défaut alignée si les droits le
permettent.

### 2.4 Critères d'acceptation (lot B)

1. Création sur GitHub (compte personnel et organisation) et sur Forgejo : le repo existe avec la
   visibilité et la description choisies. Sa seule branche est `int-<x>`, qui est aussi la branche
   par défaut. Elle contient `README.md`, `config/project.yaml` (`integrationBranch: int-<x>`) et
   les fichiers Polenta. Les membres choisis ont accès au repo.
2. Un nom déjà pris est signalé pendant la saisie. Le bouton de création reste désactivé tant que
   la description est vide ou que la branche n'est pas une `int-*` valide.
3. Un repo existant vide aboutit au même état que le critère 1.
4. Un repo existant complet est ajouté sans aucune question.
5. Un repo existant sans `int-*` et sans `README.md` : seules ces deux questions sont posées,
   l'état final respecte le critère 1.
6. Échec du push après la création distante : le repo distant n'est pas supprimé, l'écran indique
   l'étape en échec, et la reprise par §3 ou §2.3 fonctionne.
7. Avec un compte sans droit de création dans une organisation, cette organisation n'est pas
   proposée.

## 3. Paramètres du repo (lot C, #108)

### 3.1 Accès

Dans l'onglet Structure, menu de la ligne d'un repo → **« Paramètres du repo… »**. La fenêtre
contient trois sections. Elle s'ouvre pour tout repo dont `origin` est sur une forge `github` ou
`forgejo` d'un compte connecté. Pour un repo `generic` ou sans compte : seule la section Branche
d'intégration est disponible, avec un lien vers l'interface web si l'URL est connue.

Les modifications de la forge exigent le droit **admin** du compte sur le repo. Sans ce droit, les
sections Général et Membres sont en lecture seule, avec la mention « Réservé aux administrateurs
du repo ».

### 3.2 Sections

**Général**
- Description, modifiable (non vide). Une modification met aussi à jour le `README.md`, après
  confirmation, par un commit sur l'intégration.
- Visibilité. Le passage en **public** demande une confirmation explicite qui rappelle que tout le
  contenu, historique compris, devient lisible.

**Branche d'intégration** : le contenu du §1 (choix, nouvelle branche), dans cette fenêtre.

**Membres**
- **Collaborateurs** : liste (login, nom, niveau). Ajout par login, avec autocomplétion sur les
  membres de l'organisation (mécanisme GH45 §7) et saisie libre acceptée. Retrait.
- **Équipes** (repo d'organisation uniquement) : les équipes de l'organisation ayant accès au repo,
  avec leur niveau. On peut attribuer une équipe existante au repo ou la retirer. Créer une équipe
  ou en changer la composition reste dans la forge (lien).
- **Niveaux proposés** : lecture, écriture, admin. Ils sont traduits vers les niveaux de la forge
  (GitHub `pull`/`push`/`admin`, Forgejo `read`/`write`/`admin`). Les niveaux propres à une forge
  (`triage`, `maintain`) sont affichés tels quels s'ils existent déjà, mais pas proposés.
- **Gardes** : le retrait de son propre accès admin demande une confirmation. Le retrait du dernier
  admin direct est refusé quand aucune équipe admin n'existe sur le repo.
- Les invitations en attente (GitHub) sont listées comme telles et peuvent être annulées.

### 3.3 Critères d'acceptation (lot C)

1. Sur GitHub et sur Forgejo, ajouter un collaborateur avec un niveau, le changer puis le retirer :
   l'état de la forge suit. Idem pour une équipe sur un repo d'organisation.
2. Le passage public ⇄ privé fonctionne et le passage en public exige la confirmation.
3. Un compte non admin voit les sections Général et Membres en lecture seule, sans erreur.
4. Une nouvelle branche d'intégration créée ici respecte le §1.6 et devient la branche par défaut
   de la forge.
5. Hors ligne ou forge injoignable : la fenêtre s'ouvre, les sections forge indiquent
   « indisponible hors ligne », la section Branche d'intégration reste utilisable.

## 4. Provider GitHub (commun aux lots B et C)

Parité avec `forgejo.provider.ts` pour les fonctions utilisées ci-dessus : liste des repos,
propriétaires où créer, existence d'un nom, création (compte ou organisation, visibilité,
description), droits, membres d'organisation, collaborateurs et équipes du repo, visibilité,
branche par défaut. `ForgeService` choisit le provider selon le compte au lieu d'utiliser
Forgejo d'office (`require()` refuse aujourd'hui tout compte non `forgejo`).

Scope OAuth : `repo user:email` couvre les repos et collaborateurs. Les équipes demandent
`read:org`. Un jeton sans ce scope ne bloque rien : la section Équipes propose de se reconnecter.
Le scope exact est à confirmer au design.

## Hors scope

- Création d'organisations, de comptes ou d'équipes, et changement de la composition d'une équipe :
  ils restent dans la forge (§4.4 de l'analyse, amendé).
- Suppression, renommage, transfert ou archivage d'un repo depuis Polenta.
- Règles de protection de branche autres que la branche par défaut (reviews obligatoires, statuts
  requis).
- GitLab, et toute forge sans API connue (`generic`).
- Migration automatique des repos existants de `main` vers une `int-*` : proposée, jamais imposée
  (décision 3).
- Import CSV d'utilisateurs, rapport d'accès croisé : #63.
- Même repo monté deux fois sur deux `int-*` : #17.

## Points ouverts pour le Design

1. Le commit de désignation (§1.2) quand `config/project.yaml` a lui-même une modification en
   attente : commiter la seule ligne `integrationBranch`, ou demander de publier d'abord.
2. Interaction avec l'auto-pull (§2.5 / §2.6 de SPEC-FORKS) quand deux postes désignent des
   branches différentes en même temps (conflit sur `project.yaml`).
3. Forgejo : niveau minimal requis pour attribuer une équipe à un repo (propriétaire de
   l'organisation ou admin du repo) et scope de jeton nécessaire.
4. Client web (GH44) : les trois lots doivent fonctionner dans l'espace serveur (channels à ajouter
   à la liste blanche).
5. Faut-il une vérification « repo conforme » à l'ouverture d'un workspace (pastilles du §1.1 sur
   tous les repos), ou seulement dans l'onglet Structure ?
