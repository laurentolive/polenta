# GH104 — Supprimer un composant local ou un type d'objet supprime ses objets, liens, arbres et refs de liens

## Contexte

Dans Modèle de données → Structure, la corbeille d'un **composant local** (`LocalNodeRow`) appelle
`handleDeleteLocalComponent` (`StructureTab.tsx`), qui ne fait que
`saveSchema(repo, { ...schema, nodes: removeSystemNode(schema.nodes, nodeName) })`. La suppression
d'un **type d'objet** (corbeille de `ElementLeaf`, bouton Supprimer de la modale de type) retire
de même le seul type de `objectTypes`. Restent sur disque :

- les refs `<nœud>::<type>` dans `linkTypes[].sourceRefs / targetRefs` : le type de lien continue
  de viser un composant qui n'existe plus ;
- les objets du type (`requirements/`, `tests/`, `campaigns/`), invisibles puisqu'aucun type ne
  les déclare ;
- leurs `ObjectLink` dans `links/links.yaml` ;
- les arbres `.polenta/trees/<nœud>/<type>.yaml` ;
- pour les tests, leurs exécutions `test-runs/<ID>/`.

La confirmation affichée aujourd'hui annonce pourtant que « le composant, ses sous-composants et
tous leurs éléments (exigences, tests, campagnes) seront supprimés »
(`schema.structureTab.deleteComponentCascadeBody`).

Cas réel (PH2, `handstickProduct`) : après suppression des composants locaux `VE12A` et `VE22D`
(+ `VE22D_SW`), `implements` cible toujours `VE12A::VE12A_REQ` et `VE22D::VE22D_REQ` ; 3
`VE12A_REQ`, 44 `VE22D_SW_REQ`, leurs liens et les arbres `.polenta/trees/VE12A|VE22D|VE22D_SW`
restent en place.

Décisions utilisateur :

- suppression **en cascade avec confirmation** (comptes affichés avant de valider) ;
- **exception à `SPEC-REQ` §9** (« pas de suppression physique d'une exigence ») : la suppression
  du composant ou du type qui porte des objets les supprime physiquement, avec pierre tombale ;
  l'historique reste dans git ;
- les restes déjà présents dans PH2 ne sont **pas** nettoyés par ce ticket.

## Comportement attendu

Périmètre : un composant local `N` (avec tout son sous-arbre `children`) ou un type `T` d'un nœud
`N`, dans le schéma du repo `R`, supprimé depuis l'onglet Structure. L'ensemble des types
supprimés est noté `S` (un seul type, ou tous les types de `N` et de ses descendants).

### 1. Données supprimées ou réécrites

| Donnée | Traitement |
|---|---|
| Schéma de `R` | nœud(s) ou type retirés (comportement actuel) |
| Objets de `R` dont `objectTypeRef ∈ S` (exigences, tests, campagnes) | fichier supprimé, **pierre tombale** `.polenta/tombstones/<ID>` écrite avant (`deleteWithTombstone`, GH20) |
| `test-runs/<ID>/` des tests supprimés | dossier supprimé |
| `ObjectLink` dont `sourceId` ou `targetId` est un objet supprimé, dans `links/links.yaml` de **tous les repos du workspace** | lien supprimé |
| `.polenta/trees/<nœud>/<type>.yaml` pour chaque type de `S` ; dossier `.polenta/trees/<nœud>/` d'un nœud supprimé | supprimé |
| Ref `<nœud>::<type>` (type de `S`) dans `linkTypes[].sourceRefs / targetRefs` du schéma de `R` | retirée |
| Même ref dans les `linkTypes` des **autres** repos du workspace | retirée, **sauf** si un autre repo déclare encore un type `<nœud>::<type>` (même règle de collision que GH100 : chaque repo a un nœud `root`) |

Un type de lien dont `sourceRefs` ou `targetRefs` devient vide n'est **pas** supprimé : il devient
invalide (`isLinkTypeValid` = faux, déjà masqué des éditeurs de liens) et la confirmation le
signale, l'utilisateur le corrige ou le supprime dans l'onglet Liens. Une liste vide n'est jamais
lue comme « accepte tout » ici.

Les campagnes d'un **autre** type qui contiennent un test supprimé ne sont pas modifiées : elles
affichent déjà l'entrée comme « Indisponible : test supprimé » (`SPEC-TESTS` §4.1).

### 2. Confirmation

- La corbeille ouvre la confirmation avec un aperçu calculé **sans écriture** : nombre d'objets
  supprimés par catégorie (exigences / tests / campagnes), nombre de liens supprimés et repos
  concernés, types de lien modifiés (et ceux qui deviennent invalides), sous-composants supprimés
  (texte actuel conservé).
- Composant ou type sans objet : même confirmation, sans les lignes vides (comportement actuel).
- Annuler = aucun fichier modifié, ni schéma ni données.

### 3. Pré-contrôles (aucune écriture si l'un échoue)

- Nœud `readonly` ou repo en lecture seule (pin tag / SHA) : suppression impossible (déjà le cas
  dans l'UI) — refus côté main également.
- Un repo du workspace à réécrire (liens, `linkTypes`) n'est pas chargé / accessible : refus, repo
  nommé (sinon des liens orphelins resteraient sans que l'utilisateur le sache).

### 4. Ordre, reprise et compte rendu

1. Pré-contrôles. 2. Pierres tombales puis suppression des objets. 3. Liens, arbres, `test-runs`.
4. Schéma de `R` (nœud / type et refs), puis `linkTypes` des autres repos. Une erreur d'écriture
en cours de route n'interrompt pas les autres fichiers ; elle est listée dans un compte rendu
(comme GH100). Rien n'est commité : l'utilisateur relit le diff git (et peut `git checkout`).
Les caches (listes, liens, graphe, matrice) sont invalidés.

### 5. Règle §9 amendée

`SPEC-REQ` §9 devient : pas de suppression physique d'une exigence **individuelle** ; seule la
suppression du composant ou du type qui la porte la supprime, avec pierre tombale (l'ID n'est
jamais réutilisé). Même règle pour les tests.

## Critères d'acceptation

1. Composant local `A` avec 2 exigences, 1 test (avec un run) et 1 campagne, liés à 3 objets de
   `root` : après suppression, les 4 fichiers, `test-runs/<test>/`, les 3 liens et
   `.polenta/trees/A/` n'existent plus ; 4 pierres tombales existent ; `implements` ne contient
   plus `A::A_REQ`.
2. Composant `A` avec un sous-composant `B` (objets dans les deux) : les objets, liens, arbres et
   refs de `A` et de `B` sont supprimés.
3. Suppression du seul type `A_TEST` : seuls les tests et leurs liens / runs / arbre / refs sont
   supprimés ; les exigences de `A` restent.
4. Lien vers un objet supprimé stocké dans `links.yaml` d'un **autre** repo du workspace :
   supprimé.
5. Ref `root::X` dans un autre repo qui déclare lui-même `root::X` : conservée.
6. Type de lien dont la seule `targetRef` était le type supprimé : conservé, `targetRefs: []`,
   signalé dans la confirmation et absent des éditeurs de liens.
7. La confirmation affiche les comptes exacts de 1 ; Annuler ne modifie aucun fichier.
8. Après suppression, recréer un type de même préfixe attribue un numéro supérieur aux IDs
   supprimés (pierres tombales).
9. Tests unitaires couvrant 1–8 (fixture workspace multi-repos) ; scénario e2e web de la
   confirmation et du résultat.

## Hors scope

- Nettoyage des restes déjà présents dans PH2 (`handstickProduct`) : laissés en l'état.
- Retrait d'un composant **en repo séparé** (`RemoveDependencyModal`) : ses objets vivent dans
  son propre repo et ne sont pas supprimés ; le nettoyage des liens / refs du produit vers ses
  types relève d'un ticket séparé si besoin.
- Suppression d'un type ou d'un composant depuis le serveur MCP (aucun tool de suppression de
  schéma aujourd'hui).
- Scripts / requêtes / dashboards de la vue Suivi qui citent un ID ou un type supprimé (code côté
  projet, GH79) ; tags git / baselines, exports déjà produits, `.<user>.pref`, brouillons de
  merge, `versions/`.
- Références textuelles `[[ID]]` dans les richtext d'autres objets : restent littérales.

## À vérifier en Design

- Réutiliser le moteur multi-repos de GH100 (`type-rename.service.ts` : aperçu sans écriture,
  pré-contrôles, compte rendu, collision de refs `root::`) — GH100 mergé (#102), GH104 rebasé
  sur `main`.
- Point d'entrée : handler IPC avec aperçu (`dryRun`) puis exécution, sur le modèle de
  `previewValueRenames` / `renameValues` (GH82) ; écriture sérialisée
  (`serialize-writes.util.ts`) et invalidation du graphe (`GRAPH_WRITE_CHANNELS`).
- Objets d'un type d'un composant en repo séparé supprimé depuis le repo produit : écrire dans le
  repo du type (`resolveComponentRepoPath`), pas dans le repo ouvert.
- `reviews/*.yaml` (`objectId`), `impact-analyses/*`, `impact-acks/<id>/` et
  `needsRevalidation` posé par un objet supprimé : supprimer ou laisser (à trancher, la vue
  d'impact doit rester lisible).
