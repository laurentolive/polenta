# GH105 — Liens : objets de tous les repos du workspace comme candidats, titre et navigation résolus

## Contexte

Un type de lien peut viser un type d'un composant en repo séparé. Cas réel (PH2) : dans
`handstickProduct`, `implements` va de `root::PRODUCT_REQ` vers `root::HMI_PH2_REQ`, un type du
repo composant `hmi-PH2`. Aucun objet `HMI_PH2_REQ` n'est pourtant proposé dans l'éditeur de
liens d'une `PRODUCT_REQ`.

Cause : les candidats du `LinkCombobox` (`SystemView.tsx` → `candidateObjects`, passés aux vues
Édition, Excel, Word et à `SearchEditPane`) viennent de `api.requirements.list(repoPath)` et
`api.tests.list(repoPath)` : l'index (`RequirementsIndexService.build`) ne lit que le repo
courant. C'était un hors scope explicite de T72 (« Autocomplete cross-repo dans
`LinkCombobox` … les candidats restent scopés au repo courant », avec l'affichage du titre d'un
objet lié d'un autre repo, « reste un ID brut »).

Le lien est pourtant valide et déjà géré ailleurs : l'outil MCP `create_links` résout les objets
sur tout le workspace (`links.tools.ts`, `resolveWorkspaceRepoPaths`), la matrice de traçabilité
et la revalidation (T172) agrègent déjà les liens de tous les repos.

Décisions utilisateur :

- on doit pouvoir lier des objets **dès que le composant est créé**, quel que soit le repo de
  l'objet ;
- périmètre **complet** : candidats, titre et navigation ;
- le lien est stocké **côté source** : dans le repo de l'objet `sourceId` (précision de la
  validation de spec, qui remplace « le repo courant ») ;
- un objet n'affiche que les liens stockés dans son propre repo (pas d'agrégation des liens des
  autres repos sur l'objet, refusée à la validation de spec).

## Comportement attendu

Notations : `W` = repos du workspace (repo racine ouvert + dépendances résolues de
`WorkspaceTree.nodes`, comme `resolveWorkspaceRepoPaths`) ; `S` = repo de l'objet source du lien.

### 1. Candidats

- Les candidats de l'éditeur de liens (vues Édition, Excel, Word, volet d'édition de la
  recherche) sont les exigences et tests de **tous les repos de `W`**, filtrés par les refs du
  type de lien comme aujourd'hui (`filterCandidatesByRefs`).
- Un composant ajouté (repo cloné, local ou créé sur le serveur) apporte ses objets aux candidats
  sans redémarrage, dès que l'arbre du workspace est reconstruit ; un objet créé dans un composant
  apparaît dès sa création (fichiers du working tree, pas besoin de commit).
- Composants épinglés (tag / SHA) ou `readonly` : leurs objets sont candidats **en cible** (le
  lien est écrit dans le repo de la source). Ils ne sont pas proposés quand le lien les mettrait en
  source (écriture impossible dans leur repo).
- Le combobox indique le composant de chaque candidat (libellé du repo / nœud, comme
  `groupLabel` de la combobox Composant) pour distinguer des titres identiques.

### 2. Stockage du lien

- Le lien est écrit dans `links/links.yaml` de `S`, le repo de l'objet **source** : celui qui
  correspond aux `sourceRefs` du type de lien, quel que soit l'objet depuis lequel l'utilisateur
  crée le lien (création possible depuis la source ou la cible, comme aujourd'hui). Le repo de la
  cible n'est jamais modifié. Cas PH2 : `implements` (`PRODUCT_REQ` → `HMI_PH2_REQ`) est écrit
  dans `handstickProduct`.
- `S` en lecture seule (pin tag / SHA, nœud `readonly`) : création refusée avec un message qui
  nomme le repo.
- Le type de lien peut être défini dans le schéma d'un autre repo que `S` (ex. type du produit dont
  la source est un objet d'un composant) : le lien porte le nom du type, résolu dans les schémas de
  `W`.
- Doublon : un lien du même type entre les deux mêmes objets, dans n'importe quel sens, déjà
  présent dans `S` → refus, comme `validateLinkEntries` (MCP).

### 3. Affichage d'un lien vers un objet d'un autre repo

- Titre, statut et catégorie de l'objet lié sont résolus quel que soit son repo (plus d'ID brut).
- Objet introuvable dans `W` (composant retiré, fichier supprimé) : ID affiché comme aujourd'hui,
  marqué « introuvable ».
- Un objet n'affiche que les liens stockés dans **son propre repo** (comportement actuel). Ouvrir
  `HMI_PH2_REQ-0001` dans `hmi-PH2` ne montre pas le lien `implements` stocké dans
  `handstickProduct`. Conséquence assumée : un lien inter-repos n'est visible que depuis sa
  source ; la matrice de traçabilité, qui agrège déjà tous les repos, reste la vue complète.

### 4. Navigation

- Clic sur un objet lié d'un autre repo : la Vue Système bascule sur son repo, son nœud et son
  type (sélection de repo de T72) et ouvre l'objet ; « ← Retour » revient à l'objet de départ, repo
  compris.
- Ctrl+clic / nouvel onglet : ouvre l'objet dans son repo (`/req/<id>` ou `/test/<id>` avec le
  repo de l'objet).

## Critères d'acceptation

1. PH2 : dans l'éditeur de liens d'une `PRODUCT_REQ`, `implements` propose `HMI_PH2_REQ-0001` et
   `-0002` (titres « bla bla », « bla bla bla ») avec le libellé du composant `HMI VE22D`, alors
   que ces fichiers ne sont pas commités dans `hmi-PH2`.
2. Le lien créé (source `PRODUCT_REQ`) est écrit dans `handstickProduct/links/links.yaml`, qu'il
   soit créé depuis la `PRODUCT_REQ` ou depuis la `HMI_PH2_REQ` ; `hmi-PH2` n'est pas modifié.
3. Le lien affiche le titre et le statut de `HMI_PH2_REQ-0001` ; un clic ouvre l'objet dans
   `hmi-PH2` ; « ← Retour » revient à la `PRODUCT_REQ`.
4. Type de lien dont la source est un objet d'un composant modifiable : le lien est écrit dans le
   `links.yaml` du composant ; source dans un composant épinglé : création refusée, repo nommé.
5. Nouveau composant ajouté au workspace puis nouvel objet créé dedans : candidat sans redémarrage.
6. Composant épinglé sur un SHA : ses objets sont candidats en cible, le lien se crée dans le
   produit.
7. Lien vers un ID absent de `W` : ID brut marqué « introuvable », pas d'erreur.
8. Les filtres de refs restent appliqués : un type de lien ciblant `root::PRODUCT_TEST` ne propose
   pas les `HMI_PH2_REQ`.
9. Tests unitaires (agrégation des candidats sur un workspace multi-repos, résolution des refs) et
   e2e web (création, affichage, navigation d'un lien inter-repos).

## Hors scope

- Liens vers les campagnes (non proposés comme candidats aujourd'hui, inchangé).
- Création d'un type de lien entre repos depuis l'onglet Liens (déjà possible) ; nettoyage des
  refs / liens à la suppression d'un composant (GH104).
- Affichage sur un objet des liens stockés dans d'autres repos (refusé à la validation de spec).
- Recherche plein texte globale sur tout le workspace (Vue Recherche) : inchangée.
- Résolution des références textuelles `[[ID]]` des richtext vers un autre repo.
- Performance : pas d'index global persistant ; l'agrégation réutilise les index par repo.

## À vérifier en Design

- **Collision de refs `root::`** : chaque repo a un nœud `root`. Une ref `root::HMI_PH2_REQ`
  écrite dans le schéma produit vise un type d'un autre repo. Le filtre par refs doit tenir compte
  du repo de l'objet (une ref résout vers le ou les repos de `W` qui déclarent `<nœud>::<type>`,
  repo qui définit le type de lien prioritaire) pour ne pas mélanger deux types homonymes de repos différents. Écart à
  noter avec `SPEC-ELECTRON-DESKTOP` §22.3 (qui décrit `<montage>::<type>`).
- Unicité des IDs dans `W` : garantie par l'unicité des préfixes projet (règle 10) ; à confirmer
  pour la résolution par ID seul (sinon clé `repo + id`).
- Point d'entrée : IPC d'agrégation (ex. `requirements:list-workspace` / `links:list-workspace`) à
  partir de `resolveWorkspaceRepoPaths`, plutôt que N requêtes du renderer ; invalidation à la
  création d'un objet dans un autre repo et à la reconstruction de l'arbre.
- Navigation : réutiliser la sélection de repo de `SystemViewContext` (T72) ; `backHistory` doit
  mémoriser le repo.
- Écriture côté source : `requirements:link-create` reçoit aujourd'hui le `repoPath` courant ;
  le main doit résoudre le repo de `sourceId`. Écart avec l'outil MCP `create_links`, qui écrit
  dans `container.repoPath` : aligner ou documenter. Les lecteurs d'un `links.yaml` qui
  cherchent le type de lien dans le schéma de leur propre repo (couverture, revalidation, matrice)
  doivent le chercher dans les schémas de `W`.
- Client web : mêmes channels (liste blanche `WEB_EXPOSED`).
