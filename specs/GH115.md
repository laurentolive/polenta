# GH115 — Renommer une dépendance échoue sous Windows (EPERM)

## Root cause
`WorkspaceTreeService.renameClonedRepo` renommait le dossier de la dépendance sans arrêter sa
surveillance : `RepoWatcherService` (chokidar) surveille chaque repo du workspace depuis
`openWorkspace` (`watchTree`) et garde des descripteurs ouverts sur le dossier. Sous Windows, un
dossier ouvert ne peut pas être renommé → `EPERM`. `unwatch` n'attendait pas non plus la fermeture
(`close()` est asynchrone).

## Correctif
- `RepoWatcherService.unwatchDir(dir)` : arrête la surveillance de ce repo (clé comparée sans
  casse ni séparateur final) et **attend** la fermeture des watchers ; retourne les clés arrêtées.
- `WorkspaceTreeService.renameClonedRepo` (watcher injecté, `container.ts`) : arrêt de la
  surveillance → renommage (jusqu'à 5 tentatives espacées sur EPERM / EBUSY / EACCES : antivirus,
  indexation) → surveillance du nouveau chemin. Échec : l'ancien chemin est de nouveau surveillé ;
  verrou persistant → message « Le dossier « X » est utilisé par un autre programme… ».
- Le conteneur MCP (sans surveillance) est inchangé (watcher optionnel).

## Vérification
1. Workspace PH2 → Structure → modifier `hmi-PH2` → nom `VE22D` → Enregistrer : le dossier
   `PH2/VE22D` existe, la dépendance est renommée, plus d'erreur.
2. Dossier ouvert dans un terminal (`cd PH2/hmi-PH2`) : message explicite, rien n'est modifié,
   l'application continue de voir les changements du repo.
