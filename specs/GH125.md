# GH125 — Suivi : paramètres choisis par widget (sélecteurs dans l'en-tête du widget, suppression de la barre globale)

Issue : #125 — type `feature`. Base : `origin/main` @ 7f2b454.

## 1. Contexte

GH93 a introduit les **paramètres choisis à l'affichage** (déclaration `parameters` d'une requête,
`polenta.params` dans le script). Sur un dashboard, ils sont regroupés dans une **barre globale**
(`ParamBar` + `useDashboardParams`) : un sélecteur par couple `name:kind`, partagé par tous les
widgets dont la requête le déclare (`dashboardSelectors`, `paramsForQuery` dans
`packages/types/src/suivi-params.ts`). La valeur choisie est mémorisée par utilisateur et par
dashboard dans le `.pref` (`suiviParamValues[dashboardId]["name:kind"]`).

Conséquence : impossible de montrer sur un même dashboard un widget sur **toutes** les campagnes et
un autre sur **une** campagne choisie, sans figer la valeur, renommer le paramètre à la main
(requête détachée de son modèle) ou faire un dashboard par vue. GH93 avait mis hors scope les
« paramètres déclarés par un widget seul » (SPEC-DASHBOARDS §10).

Les décisions listées dans l'issue (section « Décisions déjà prises », rédigée par l'humain à la
création de l'issue) sont reprises ci-dessous comme acquises.

## 2. Description fonctionnelle

### 2.1 Plus de barre de paramètres sur le dashboard

La barre globale du dashboard disparaît (écran, impression). Aucun mécanisme « appliquer à tous
les widgets » : recentrer tout un dashboard sur une campagne demande de changer chaque widget
(décision de l'issue).

La **vue `/query`** garde sa propre barre de paramètres (celle de la requête ouverte : défauts à
l'ouverture, non mémorisée) — elle ne relève pas du dashboard. *(dépend de Q4)*

### 2.2 Sélecteurs dans l'en-tête du widget

- Chaque widget dont la requête déclare des paramètres porte, dans l'en-tête de sa carte, **un
  sélecteur par paramètre déclaré**, dans l'ordre de la déclaration, affiché « Libellé : valeur ▾ »
  (ex. « Campagne : Toutes ▾ »). Libellé, types, options et contrôles identiques à ceux de GH93
  (`campaign`, `component`, `objectType`, `enum`, `text`, `period` ; `null` = « Tous / Toutes ») —
  seul l'emplacement change. Un widget sans paramètre n'a aucun sélecteur.
- Plus de regroupement entre widgets : deux widgets d'une même requête (ou de deux requêtes
  déclarant le même `name:kind`) ont chacun leur sélecteur et leur valeur. Pour un `enum`, les
  options sont celles de la déclaration de la requête du widget (plus d'union).
- Les sélecteurs restent utilisables quand le dashboard ou la branche est en lecture seule (la
  valeur n'est jamais écrite dans le dashboard — comme GH93).
- Les sélecteurs n'entrent pas en conflit avec les actions de la carte (glisser pour réordonner,
  modifier, supprimer) : ouvrir un sélecteur ne déclenche pas le glisser. Sur un widget étroit, les
  sélecteurs passent à la ligne dans l'en-tête plutôt que de masquer le titre (disposition exacte :
  design).
- **Retour au défaut** : un bouton « Réinitialiser » par widget, visible seulement quand une valeur
  du widget diffère du défaut de sa déclaration. *(dépend de Q1)*

### 2.3 Valeur propre au widget

- Valeur mémorisée **par utilisateur, par dashboard et par widget** dans le `.pref` (jamais
  commitée), au lieu de par dashboard. `paramsFor(widget)` renvoie les valeurs de ce widget seul ;
  plus de fusion `name:kind` entre widgets. Format de stockage : *(dépend de Q2)* — recommandation :
  nouvelle clé `suiviWidgetParamValues[dashboardId][widgetId]["name:kind"]`.
- **Défaut** : `default` de la déclaration, sinon `null` (« Toutes » / « Tous »). Pas de valeur par
  défaut configurable par widget, pas de sélecteur masqué ni de valeur figée dans la configuration
  du widget (décision de l'issue).
- Changer la valeur d'un widget ne relance **que ce widget** (le cache d'exécution distingue déjà
  les valeurs : rien à changer côté moteur de scripts).
- Paramètre `required` sans valeur → le widget affiche « Choisir <libellé> » (comme GH93), le
  sélecteur restant disponible dans son en-tête.
- Valeur devenue introuvable (campagne supprimée, composant / type retiré, valeur d'énumération
  retirée) → avertissement « Valeur introuvable : … » **sur le widget concerné**, défaut appliqué,
  valeur conservée dans le `.pref` (règle GH93, appliquée au widget).
- Une valeur mémorisée pour un `name:kind` que la requête du widget ne déclare plus (requête
  modifiée, widget repointé sur une autre requête) est ignorée à l'exécution et dans l'affichage ;
  elle reprend effet si la déclaration revient. Pas de purge à la modification du widget.
- **Cycle de vie** :
  - suppression d'un widget (app ou MCP `delete_widget`) → ses valeurs sont retirées du `.pref` de
    l'utilisateur courant ;
  - suppression d'un dashboard → toutes les valeurs de ses widgets retirées (comme GH93) ;
  - changement de portée du dashboard (privé ↔ partagé) : l'id du dashboard change, les ids des
    widgets sont conservés (`setScope` réécrit le même brouillon) → les valeurs **suivent** le
    nouvel id du dashboard, widget par widget ;
  - promotion d'une requête (remappage `queryId` des widgets, `remapWidgetQueryId`) : les valeurs
    sont attachées au widget, pas à la requête → conservées.
  - Les valeurs des autres utilisateurs restent dans leur `.pref`, ignorées si le widget n'existe
    plus (comme GH93).

### 2.4 Drill-down, widget agrandi, aperçu de configuration

- **Drill-down** : la relance du script avec `polenta.drill` utilise les valeurs du widget cliqué
  (déjà le cas en GH93 via `paramsFor(widget)` ; désormais ce sont ses valeurs propres).
- **Widget agrandi** : l'issue demande qu'il utilise les valeurs du widget. Aucun mode « widget
  agrandi » n'existe dans le code à 7f2b454 (vérifié : `DashboardGrid.tsx`, route `dashboard.tsx`) ;
  la règle vaut pour tout affichage d'un widget hors de sa carte : mêmes valeurs que la carte.
- **Aperçu de `WidgetConfigModal`** : modification d'un widget existant → aperçu avec les valeurs de
  ce widget (filtrées par la déclaration de la requête choisie dans la modale) ; nouveau widget →
  défauts des déclarations. Pas de sélecteur dans la modale.

### 2.5 Impression et export docx

- **Impression** (`print.dashboard.tsx`) : plus d'en-tête de paramètres du dashboard ; sous le
  titre de chaque widget paramétré, une ligne texte « Libellé : valeur » par paramètre (valeurs du
  widget, sans contrôle). Widget en attente d'un paramètre obligatoire : « Aucune donnée. »
  (inchangé).
- **Export docx direct** (`export/dashboard.docx.ts`) : plus de paragraphes de paramètres en tête ;
  sous le titre (Heading 2) de chaque widget paramétré, les paragraphes « **Libellé :** valeur » de
  ce widget, avant son tableau.
- **Export docx par gabarit** (`template-data-campaign.ts`) : chaque élément de `widgets` reçoit
  `parameters: [{ label, value }]` (`{#widgets}…{#parameters}{label} : {value}{/parameters}…{/widgets}`).
  La liste `parameters` de premier niveau : *(dépend de Q3)* — recommandation : conservée **vide**
  pour qu'un gabarit existant qui l'utilise ne casse pas (il n'affiche plus rien), documentée comme
  dépréciée.
- `DashboardExportPayload.parameters` (niveau dashboard) est remplacé par des valeurs par widget
  (forme exacte : design).

### 2.6 Migration

Les choix enregistrés au niveau du dashboard (`suiviParamValues`, GH93) sont **abandonnés** :
chaque widget repart de son défaut, aucune recopie sur les widgets (décision de l'issue).
Nettoyage de l'ancienne clé : *(dépend de Q2)* — recommandation : retirée du `.pref` à la première
écriture de valeurs de widget, jamais lue.

### 2.7 MCP et documentation

- MCP : aucun tool ne lit ni n'écrit les valeurs choisies d'un dashboard (`run_query` /
  `test_script` reçoivent `params` explicitement) → pas de changement de comportement. Seule la
  description du schéma `parameters` (`mcp-server/tools/suivi-common.ts`, « barre du dashboard »)
  est reformulée (« sélecteurs du widget »). `delete_widget` retire les valeurs du widget via le
  service (§2.3).
- `SPEC-DASHBOARDS.md` §5.1, §6, §7.0, §7.1 (seed Campagnes : « un sélecteur Campagne commun »
  devient un sélecteur par widget), §10 (le hors-scope « paramètres déclarés par un widget » tombe)
  et `SPEC-MCP-SERVER.md` (mention de la barre) mis à jour au dernier sprint.
- Tutoriel Suivi fr / en (`docs/tutoriels/07-suivi.md`, `docs/tutorials/07-tracking.md` — l'issue cite
  « 06-suivi », le fichier actuel est le 07) : paragraphe « Paramètres choisis à l'affichage »
  réécrit (le sélecteur est dans chaque widget ; « une campagne choisie recentre tous ses widgets »
  et « les widgets qui partagent un même paramètre partagent le même sélecteur » deviennent faux).

## 3. Cas d'usage

| # | Situation | Comportement attendu |
|---|-----------|----------------------|
| U1 | Dashboard *Campagnes* (6 widgets, campagne choisie à l'affichage) | Chaque widget montre « Campagne : Toutes ▾ » dans son en-tête ; pas de barre en tête du dashboard |
| U2 | L'utilisateur choisit CAMP-0003 sur « Avancement dans le temps » | Seul ce widget se relance et se recentre ; « Avancement par campagne » reste sur Toutes |
| U3 | Deux widgets de la même requête paramétrée sur un dashboard | Valeurs indépendantes, deux exécutions distinctes |
| U4 | Rechargement de l'app / réouverture du dashboard | Chaque widget retrouve sa valeur (par utilisateur) |
| U5 | Autre utilisateur sur le même dashboard partagé | Voit ses propres valeurs (défaut s'il n'a rien choisi) |
| U6 | Widget avec paramètre `required` sans défaut | « Choisir <libellé> » dans la carte, sélecteur dans l'en-tête ; choisir une valeur l'exécute |
| U7 | Campagne choisie puis supprimée | Avertissement sur ce widget seul, défaut appliqué, valeur gardée dans le `.pref` |
| U8 | Clic sur une barre d'un widget recentré sur CAMP-0003 | Détail calculé avec CAMP-0003 |
| U9 | Dashboard privé passé en partagé (ou l'inverse) | Valeurs de chaque widget conservées |
| U10 | Suppression d'un widget, puis d'un dashboard | Valeurs correspondantes retirées du `.pref` |
| U11 | Impression / export docx (direct et gabarit) | Valeurs de chaque widget sous son titre ; rien en tête du document |
| U12 | Premier lancement après mise à jour avec des choix GH93 enregistrés | Tous les widgets au défaut ; ancienne clé ignorée (puis retirée, Q2) |
| U13 | Dashboard en lecture seule / branche en lecture seule | Sélecteurs utilisables, valeur mémorisée, aucune écriture dans le dashboard |

## 4. Critères d'acceptation

1. Aucun dashboard n'affiche de barre de paramètres (écran ni impression) ; la vue `/query` garde la
   sienne (Q4).
2. Un widget dont la requête déclare N paramètres affiche exactement N sélecteurs dans son en-tête,
   dans l'ordre de la déclaration ; un widget sans paramètre n'en affiche aucun.
3. Changer la valeur d'un widget ne relance que ce widget (aucune autre exécution observée) et
   n'affecte pas un autre widget de la même requête.
4. La valeur est relue après rechargement, par utilisateur, et stockée dans le `.pref` sous la clé
   dashboard + widget ; rien n'est écrit dans `dashboards/` ni commité.
5. Paramètre obligatoire, valeur introuvable : mêmes comportements que GH93, limités au widget.
6. Drill-down et aperçu de modification d'un widget utilisent les valeurs de ce widget.
7. `setScope` (dans les deux sens) conserve les valeurs de chaque widget ; `deleteWidget` (app et
   MCP) et `delete` retirent les valeurs concernées.
8. Impression, docx direct et docx par gabarit placent les valeurs de chaque widget sous son titre ;
   un gabarit existant utilisant `{#parameters}` de premier niveau s'exporte sans erreur (Q3).
9. Les choix GH93 existants ne sont pas recopiés sur les widgets.
10. `SPEC-DASHBOARDS.md`, `SPEC-MCP-SERVER.md`, description MCP et tutoriels fr / en à jour ;
    `e2e-web/gh93-params.spec.ts` adapté (il vérifie aujourd'hui la barre et
    `suiviParamValues`) et scénarios GH125 ajoutés en e2e (`e2e-web/gh125-*.spec.ts`).

## 5. Indicateur

Aucun nouvel indicateur : le ticket déplace un mécanisme de sélection de valeurs (affichage), sans
calcul nouveau. Principe GH79 non concerné.

## 6. Interaction avec #67 (spécifié en parallèle)

#67 — « partager un dashboard privé avec ses requêtes en une seule action » — touche le même
service (`DashboardsService.setScope`, `remapWidgetQueryId`, `renameInOrder`) et la même spec
(SPEC-DASHBOARDS §7.0b).

- **Fonctionnellement compatibles** : la promotion d'un dashboard change son id (valeurs déplacées
  vers le nouvel id, §2.3) et la promotion de ses requêtes change les `queryId` des widgets sans
  changer leurs ids ni les déclarations copiées → les valeurs par widget de GH125 survivent à
  l'action de #67, **à condition** que la clé reste `dashboardId` + `widgetId` (jamais `queryId`).
  À rappeler dans le design de #67 : sa séquence (promotion des requêtes puis du dashboard) doit
  passer par le déplacement des valeurs de `setScope` / `renameInOrder`, qui sous GH125 déplace le
  bloc par widget.
- **Conflits de fichiers probables** : `dashboards.service.ts` (`setScope`, `renameInOrder`),
  `SPEC-DASHBOARDS.md` §7.0b / §7.0 / §10, `SPEC-INDEX.md`, éventuellement `dashboard.tsx`. Le
  second ticket mergé rebase sur le premier ; aucun ordre imposé.
- La confirmation de #67 ne doit pas mentionner de « barre de paramètres » (supprimée ici).

## 7. Hors scope

- Mécanisme « appliquer à tous les widgets » / sélecteur commun optionnel au dashboard.
- Valeur par défaut configurable par widget, sélecteur masqué, valeur figée dans la configuration
  du widget.
- Recopie des choix GH93 existants sur les widgets.
- Sélecteurs dans `WidgetConfigModal` (l'aperçu prend les valeurs du widget ou les défauts).
- Lecture / écriture des valeurs choisies d'un widget via le MCP.
- Restent hors scope (GH93 §10) : sélection multiple, valeurs dépendantes entre sélecteurs,
  paramètres dans l'URL, intégration d'un widget dans la page d'une campagne, comparaison de
  campagnes sur un même graphique.
- Création d'un mode « widget agrandi » (inexistant à ce jour).
- Changement du format de `query.yaml`, `dashboard.yaml` ou du moteur de scripts.

## 8. Questions ouvertes

La spec est rédigée sur la base des recommandations ; les passages concernés portent
« *(dépend de Qn)* ».

- **Q1 — Réinitialiser par widget.** GH93 avait un bouton « Réinitialiser » dans la barre.
  *Recommandation* : une petite icône « Réinitialiser » dans l'en-tête du widget, visible seulement
  quand une de ses valeurs diffère du défaut. *Alternative* : aucun bouton — l'utilisateur revient
  au défaut en le choisissant dans le sélecteur (« Toutes »), plus simple mais moins direct quand le
  défaut n'est pas `null`.
- **Q2 — Stockage dans le `.pref`.** *Recommandation* : nouvelle clé
  `suiviWidgetParamValues[dashboardId][widgetId]["name:kind"]`, l'ancienne `suiviParamValues`
  jamais lue et retirée à la première écriture (abandon explicite, aucune ambiguïté de format).
  *Alternative* : réutiliser `suiviParamValues` avec un niveau widget en plus — oblige à
  distinguer l'ancien format du nouveau à la lecture (une valeur `period` est déjà un objet), source
  d'erreurs.
- **Q3 — Gabarit docx, `{#parameters}` de premier niveau.** *Recommandation* : conservé en liste
  vide (un gabarit existant s'exporte toujours, sans rien afficher à cet endroit), déprécié dans la
  référence des balises ; valeurs exposées par widget. *Alternative* : le retirer (un gabarit qui
  l'utilise afficherait une section vide ou, selon le réglage docxtemplater, une valeur
  « undefined »).
- **Q4 — Vue `/query`.** L'issue dit « la barre globale disparaît » pour le dashboard.
  *Recommandation* : la vue `/query` garde sa barre des paramètres de la requête (non mémorisée,
  défauts à l'ouverture), inchangée. *Alternative* : la retirer aussi — mais la vue n'aurait alors
  plus de moyen d'essayer la requête avec d'autres valeurs.
