# GH126 — Vues : une requête-colonne peut produire plusieurs colonnes (ex. une colonne de résultat par campagne)

> Issue : #126 — suite de #70 (colonnes calculées définies par le projet, fermé).

## 1. Besoin

Dans PH2, les utilisateurs veulent voir dans la Vue Système des tests **une colonne par campagne**
(RE2, RP1, RP2…) portant le résultat de chaque test dans cette campagne.

Avec GH70, une requête partagée déclarée en `column` produit **une** colonne. Contournement actuel
dans PH2 : une requête par campagne (QUERY-0004/5/6), à dupliquer à chaque nouvelle campagne.

Évolution : une requête-colonne peut **éclater** son résultat en **plusieurs sous-colonnes**, une par
valeur distincte d'une colonne du résultat (ex. `campaignId`). Une nouvelle campagne fait apparaître
une nouvelle sous-colonne sans créer ni modifier de requête.

## 2. Décision indicateur (principe GH79, SPEC-TECH-stack §1.1)

*« Résultat d'un test par campagne » sert-il à une fonction de Polenta ?* **Non** : indicateur de
suivi. Polenta livre uniquement le **mécanisme générique** d'éclatement d'une colonne calculée (il
ne sait pas qu'il s'agit de campagnes). Le calcul est côté projet : fonction de la bibliothèque de
départ (`dashboards/lib/campaign.js`) et modèle de requête, modifiables par le projet — comme
« Dernier résultat » (GH70 §5).

## 3. Déclaration

Deux propriétés optionnelles s'ajoutent à la déclaration `column` de `query.yaml` (GH70 §3,
SPEC-DASHBOARDS §5.2) :

```yaml
column:
  label: Résultat par campagne      # libellé du groupe (panneau ⚙️, infobulle d'en-tête)
  appliesTo: { categories: [test], objectTypes: [] }
  type: enum
  values: [PASS, FAIL, BLOCKED, INCOMPLETE, pending]
  idColumn: id                      # inchangé (défaut id)
  valueColumn: value                # inchangé (défaut value)
  tooltipColumn: tooltip            # inchangé (défaut tooltip)
  splitColumn: campaignId           # NOUVEAU : une sous-colonne par valeur distincte de cette colonne
  splitLabelColumn: campaignTitle   # NOUVEAU, optionnel : libellé de la sous-colonne (défaut : la valeur de splitColumn)
```

Règles :

- **Sans `splitColumn`** : comportement GH70 strictement inchangé (une colonne, clé `query::<ID>`).
- **Avec `splitColumn`** : la requête est une **colonne éclatée**. Chaque valeur distincte (non vide)
  de `splitColumn` dans le résultat définit une sous-colonne de clé
  `query::<ID>::<valeur>` (ex. `query::QUERY-0007::CAMP-0005`).
- `splitLabelColumn` : libellé de la sous-colonne = valeur de cette colonne sur la **première** ligne
  de la sous-colonne ; absente, vide ou non textuelle → la valeur de `splitColumn`.
- Type, valeurs d'enum, rendu, infobulle, cible `_ids` : ceux de la déclaration, communs à toutes les
  sous-colonnes.
- Validation (`validateColumnDecl`) : `splitColumn` / `splitLabelColumn` = nom de colonne non vide
  si fourni ; `splitLabelColumn` sans `splitColumn` → erreur (`column.splitLabelColumn : réservé
  aux colonnes éclatées`). Erreurs traitées comme GH70 (`columnError`, `[COLUMN_INVALID]`).
- Indépendance du modèle (GH70 §9 A) : ces propriétés n'entrent pas dans l'empreinte.

## 4. Contrat de ligne

Comme GH70 §4, avec en plus la colonne `splitColumn` :

- une ligne par **(élément, sous-colonne)** ; plusieurs lignes pour le même couple → la première
  est retenue (la règle reste celle du script) ;
- ligne sans valeur de `splitColumn` (absente, `null`, chaîne vide) → erreur de la colonne
  (« Ligne N (ID) : colonne « campaignId » manquante. ») — même traitement que `idColumn` absente ;
- valeur non textuelle (nombre) → convertie en texte pour la clé et le libellé ;
- **ordre des sous-colonnes = ordre de première apparition** de leur valeur dans le résultat (le
  script décide : ex. campagnes par date de création) ;
- **limite : 50 sous-colonnes** par requête ; au-delà → erreur de la colonne (« 50 sous-colonnes au
  maximum (N trouvées) »), aucune sous-colonne rendue.

## 5. Comportement dans les vues

### 5.1 Panneau ⚙️ (Configuration des champs)

- Dans la section « Colonnes calculées », une colonne éclatée apparaît comme un **groupe** :
  libellé du groupe + badge `(calc)` (non cochable), puis **une case par sous-colonne**, dans l'ordre
  du script, libellé = libellé de la sous-colonne ; infobulle = ID et titre de la requête + valeur
  de `splitColumn`.
- Chaque sous-colonne est un champ indépendant : cochée / décochée séparément, onglets Tableau et
  Document indépendants, **décochée par défaut**. Une nouvelle valeur (nouvelle campagne) apparaît
  **décochée**.
- Pour lister les sous-colonnes, le script d'une colonne éclatée applicable est exécuté **à
  l'ouverture du panneau ⚙️** (s'il ne l'a pas déjà été) ; pendant l'exécution, le groupe affiche un
  indicateur de chargement ; en erreur, le groupe affiche ⚠ avec le message (aucune case).
- Sous-colonne disparue du résultat (campagne supprimée) ou requête qui n'est plus éclatée → clé
  ignorée à l'affichage, jamais réécrite dans les préférences (règle GH70 §6.1).

### 5.2 Vue Excel (Tableau), Vue Word (Document), impression, exports

Chaque sous-colonne visible se comporte **exactement comme une colonne calculée GH70** : colonne à
part entière positionnée selon l'ordre des colonnes (glisser-déposer compris), lecture seule,
infobulle de cellule, double-clic → cible `_ids`, filtre par colonne (T51) propre à la sous-colonne,
hauteur max des lignes, mode sélection GH33, champ de la carte en Vue Word, exports Excel / Word /
PDF et impression.

- **En-tête** : libellé de la sous-colonne (ex. « RP1 ») ; infobulle d'en-tête = « libellé du groupe
  — libellé de la sous-colonne » (ex. « Résultat par campagne — RP1 »).
- **Exports** : en-tête = libellé de la sous-colonne.
- **Exécution** : une seule exécution du script par requête pour toute la vue, partagée par toutes
  ses sous-colonnes, dès qu'au moins une est visible (ou panneau ⚙️ ouvert). Rafraîchissement et
  cache : ceux de GH70 §6.4 (un résultat saisi en campagne met à jour les cellules sans recharger ;
  une nouvelle campagne apparaît dans ⚙️ sans recharger).
- **Erreur** du script : ⚠ dans l'en-tête de chaque sous-colonne visible, cellules vides.

## 6. Bibliothèque et modèle livrés

### 6.1 `dashboards/lib/campaign.js`

Nouvelle fonction `entryResultsByCampaign(data)` (fonctions existantes inchangées ; version de la
bibliothèque incrémentée, proposée par le bandeau des mises à jour) :

- parcourt **toutes les campagnes, abandonnées comprises**, dans l'ordre de création
  (`createdAt`, puis ID) ;
- pour chaque campagne, chaque test ayant au moins une **entrée active** ;
- statut = **pire statut** des entrées du test dans la campagne (`worst` de `lib/status.js` :
  test itérant ; `pending` si au moins une instance n'est pas exécutée et aucune n'est en échec,
  bloquée ou incomplète) ;
- renvoie, par couple (campagne, test) : `{ campaignId, campaignTitle, testId, status, executedAt,
  executedBy, entryId, statuses }` — `executedAt` / `executedBy` / `entryId` de l'entrée exécutée la
  plus récente (à défaut, première entrée), `statuses` = statuts de toutes les instances.

### 6.2 Modèle de requête « Résultat par campagne (colonnes) »

Nouveau modèle `campaign-results` (`suivi-templates.ts`), sans paramètre :

- une ligne par (campagne, test) : `id` = test, `value` = statut, `campaignId`, `campaignTitle`,
  `tooltip` = « `CAMP-xxxx` — titre · date locale · exécutant » (« · non exécuté » si aucune
  instance exécutée ; « · PASS, FAIL » si plusieurs instances), `_ids` = `[CAMP-xxxx/<entryId>]` ;
- déclaration proposée : libellé « Résultat par campagne » / « Result by campaign »,
  `categories: [test]`, `type: enum`, `values: [PASS, FAIL, BLOCKED, INCOMPLETE, pending]`,
  `splitColumn: campaignId`, `splitLabelColumn: campaignTitle`.

Le projet de démonstration (`scripts/demo-lave-linge/generate.mjs`) contient cette requête.

Remarque : la requête existante « Entrées de campagne » (modèle `campaign-entries`) déclarée avec
`idColumn: testCaseId`, `valueColumn: status`, `splitColumn: campaignId`,
`splitLabelColumn: campaignTitle` fonctionne aussi sans code (première instance retenue pour un test
itérant, au lieu du pire statut).

### 6.3 Saisie et MCP

- Vue `/query`, section « Utiliser comme colonne dans la Vue Système » (`ColumnDeclEditor`) : case
  « Une colonne par valeur de » + liste déroulante (colonnes du dernier résultat), et liste « Libellé
  des colonnes » (optionnelle), alimentées comme `idColumn` / `valueColumn`.
- MCP : `create_query` / `update_query` acceptent `splitColumn` / `splitLabelColumn` dans `column`
  (même validation) ; `list_queries` les renvoie.

## 7. Critères d'acceptation

1. Sans `splitColumn`, toute colonne GH70 existante se comporte exactement comme avant (clé
   `query::<ID>`, préférences existantes conservées).
2. Une requête « Résultat par campagne » (modèle) sur un projet à 3 campagnes propose dans ⚙️ un
   groupe « Résultat par campagne » avec 3 cases RE2, RP1, RP2 dans l'ordre de création des
   campagnes, toutes décochées par défaut.
3. Cocher RP1 et RP2 en Tableau affiche deux colonnes « RP1 » et « RP2 » ; le réglage est persisté
   sous `query::<ID>::CAMP-0005` et `query::<ID>::CAMP-0006`, par type et par utilisateur.
4. Un test présent dans RP1 mais pas encore exécuté affiche `pending` dans « RP1 » ; un test absent
   de RP2 a une cellule vide dans « RP2 ».
5. Un test itérant avec une instance `PASS` et une `FAIL` dans la même campagne affiche `FAIL` ;
   l'infobulle liste les deux statuts.
6. Créer une nouvelle campagne fait apparaître une nouvelle case (décochée) dans ⚙️ sans recharger
   ni modifier la requête ; supprimer une campagne fait disparaître sa colonne sans erreur.
7. Saisir un résultat dans une campagne met à jour la cellule de la sous-colonne sans recharger.
8. Double-clic sur une cellule → page de la campagne sur l'entrée ; infobulle d'en-tête « Résultat
   par campagne — RP1 ».
9. Le filtre de colonne sur « RP1 » = `FAIL` ne garde que les tests en échec dans RP1.
10. Les sous-colonnes cochées dans l'onglet Document apparaissent dans la carte en Vue Word ;
    l'export Excel contient une colonne par sous-colonne visible, en-tête « RP1 »…
11. Une ligne sans valeur de `splitColumn` → ⚠ « colonne « campaignId » manquante » ; plus de 50
    valeurs → ⚠ limite, la vue reste utilisable.
12. `splitLabelColumn` sans `splitColumn` est refusé (UI, service, MCP `[COLUMN_INVALID]`).
13. `create_query` (MCP) avec `splitColumn` crée une colonne éclatée proposée dans ⚙️.
14. Polenta ne contient aucun code propre aux campagnes pour ce mécanisme.

## 8. Hors scope

- Case de groupe « tout cocher » / visibilité automatique des nouvelles sous-colonnes (choix
  utilisateur 2026-10-20 : une case par sous-colonne, nouvelle sous-colonne décochée).
- Tri des sous-colonnes dans Polenta (l'ordre est celui du script).
- Type ou valeurs d'enum différents par sous-colonne.
- Tri par colonne dans la Vue Excel (hors scope GH70, inchangé).
- Vue Édition et autres vues (cf. GH70 §8).
- Migration automatique des requêtes par campagne de PH2 (QUERY-0004/5/6) : le projet crée la
  requête depuis le modèle et supprime les anciennes.
