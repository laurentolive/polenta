# GH129 — Import des résultats JUnit sans interface (CLI et outil MCP)

> Issue #129, milestone v0.4.0. Origine : boucler la CI de `laurentolive/fan-demo` (résultats e2Unit,
> e2Sim, e2HIL → Polenta, `docs/PLAN.md` §5 « Retour des résultats », `docs/MATRIX.md` ligne
> « Import des résultats en CI »).
>
> **Statut : validée par l'humain le 2026-11-07** (« proposition ok, même Q7 ok aussi ») : les
> recommandations Q1 à Q10 sont toutes retenues (§ Décisions). Les marques **[Q n]** renvoient à la
> décision correspondante.

## But

Importer dans un projet Polenta les résultats d'un ou plusieurs rapports **JUnit XML**, sans ouvrir
l'application : depuis une ligne de commande (un job de CI, un script) ou depuis un agent IA (serveur
MCP). Chaque résultat reconnu devient un **TestRun** du cas de test correspondant, écrit dans l'arbre
de travail du repo, **sans commit** — comme toute écriture du serveur MCP (SPEC-MCP-SERVER §1). Ce qui
est fait de l'arbre de travail ensuite (commit, artefact, rien) appartient à l'appelant.

## Constat de départ (corrige l'énoncé de l'issue)

L'issue écrit « aujourd'hui l'import JUnit / JSON se fait dans l'application ». **Ce n'est pas le cas** :
SPEC-TESTS §3.5 décrit un import JUnit XML / JSON Polenta, mais il n'a jamais été implémenté
(`specs/SPEC-AUDIT.md` §3.5, généré le 2026-06-24, re-confirmé par T130 le 2026-07-21 : « [ABSENT]
Aucun handler IPC `tests:import`, aucun service d'import ») ; vérifié le 2026-11-07 : aucune occurrence
de `junit` ni d'`automationId` dans le code (`apps/`, `packages/`, `templates/`). Le champ
`automationId` n'existe que dans la spec (SPEC-TESTS §2.5, champ configurable d'exemple) : aucun type
de test livré ne le déclare.

GH129 livre donc le **premier** import de résultats automatisés. Il n'ajoute pas d'import dans
l'interface (hors scope, voir plus bas) ; le service d'import est écrit pour pouvoir y être branché
plus tard.

## Décision voisine à prendre en compte — #130 « Ne pas mélanger la CI à Polenta »

L'issue sœur #130 (« Contrôle de traçabilité en CI », `polenta check … code retour`) a été **fermée par
l'humain le 2026-11-06** avec le commentaire « Ne pas melanger la CI a polenta ». #129 est restée
ouverte (milestone v0.4.0). La spec lit cette décision ainsi **[Q1]** : Polenta ne contient **aucune
logique propre à la CI** (pas de seuils, pas de fournisseur de CI, pas de sortie dédiée à un tableau de
bord de CI, pas de commit/push) ; il offre une commande générique d'import, que la CI — ou n'importe
quel script — appelle. Si l'humain entend au contraire « pas de commande pour la CI du tout », le
périmètre se réduit à l'outil MCP (§3) et au service d'import (§1–§2).

## 1. Lecture d'un rapport JUnit XML

### 1.1 Fichiers acceptés

- Un ou plusieurs fichiers ; motifs glob développés **par Polenta** (`out/junit/*.xml`), pour que la
  commande se comporte de même sous bash, PowerShell et cmd. Un motif qui ne désigne aucun fichier est
  une **erreur globale** (code 2) : un rapport manquant en CI ne doit pas passer pour « rien à
  importer ».
- Racine `<testsuites>` (une ou plusieurs `<testsuite>`, imbrications comprises) ou `<testsuite>`
  seule. Variantes visées : pytest (`--junitxml`, e2Sim), JUnit/Jest/Maven Surefire, e2Unit
  (`eunit/report.py`), e2HIL quand il existera.
- Fichier illisible, XML mal formé, racine autre que `testsuites` / `testsuite` : **erreur globale**,
  rien n'est écrit (aucun fichier importé, même les autres).

### 1.2 Un résultat = un `<testcase>`

Pour chaque `<testcase>` :

| Donnée | Lue dans |
|---|---|
| Clés de correspondance | `classname` et `name` (§2.1) |
| Verdict | enfants `<failure>`, `<error>`, `<skipped>` (§1.3) |
| Message | attribut `message` et texte de `<failure>` / `<error>`, tronqués à 2 000 caractères |
| Durée | attribut `time` (secondes, décimal) ; absent ou illisible → 0 |
| Date d'exécution | `timestamp` de la `<testsuite>` englobante la plus proche (ISO 8601, sans fuseau = UTC) ; absent ou illisible → instant de l'import, avertissement `no_timestamp` |
| Exigences déclarées | `<properties><property name="requirement" value="…"/>` **du testcase** (une ou plusieurs) — c'est ce qu'émet le plugin pytest d'e2Sim (`e2sim/pytest_plugin.py`, `item.user_properties.append(("requirement", req))`) |

Les propriétés de la `<testsuite>` (e2Unit y met `runner`, `hash`, `license`) sont recopiées dans les
notes du run en texte brut, pas interprétées.

### 1.3 Verdicts

| JUnit | Verdict Polenta (SPEC-TESTS §3.3) |
|---|---|
| ni `failure`, ni `error`, ni `skipped` | `PASS` |
| `<failure>` | `FAIL` |
| `<error>` | `BLOCKED` **[Q5]** — le test n'a pas pu s'exécuter (fixture, setup, crash du banc) |
| `<skipped>` | **non importé**, compté « ignorés » dans le résumé **[Q5]** |

## 2. Correspondance résultat → cas de test

### 2.1 Par `automationId` (règle de SPEC-TESTS §3.5)

- Le champ s'appelle **`automationId`**, champ de `fields` d'un type de catégorie `test`, de type
  `text` **[Q4]**. Valeur vide ou absente : le test n'est pas automatisé.
- Un résultat JUnit est comparé, **à l'identique** (casse et espaces compris), à
  `<classname>.<name>` puis à `<name>` seul. La première forme qui trouve un cas de test gagne.
  Exemples : pytest `classname="tests.test_system" name="test_t09_two_firmwares"` → `automationId`
  `tests.test_system.test_t09_two_firmwares` ou `test_t09_two_firmwares`.
- Tests recherchés : tous les types `test` des nœuds accessibles (repo ouvert, composants locaux,
  submodules avec `--workspace`, comme le serveur MCP — SPEC-MCP-SERVER §2.3). Tests à statut
  terminal (`isTerminal`, ex. obsolète) exclus.
- **Ambiguïté** : deux cas de test portent la même valeur → le résultat n'est pas importé (raison
  `ambiguous`, IDs listés). Polenta ne choisit jamais à la place de l'utilisateur.
- Aucun type de test du projet ne déclare `automationId` : chaque résultat est non mappé, et le résumé
  le dit une fois en tête (« aucun type de test ne déclare le champ automationId »).

### 2.2 Secours par la propriété `requirement`

Seulement si §2.1 ne trouve **aucun** cas de test, et si le testcase porte au moins une propriété
`requirement` :

- Chaque valeur est un **ID Polenta d'exigence** (ex. `SYS-0012`). Une valeur qui n'est pas l'ID d'une
  exigence existante est ignorée (avertissement `unknown_requirement`).
- Candidats : les cas de test liés à ces exigences par un lien de **couverture** (paire test ↔
  exigence, quel que soit le sens du lien — `matchCoverageLink`, `CLAUDE.md` § Sens d'un lien) **et
  dont `automationId` est vide** — un test qui a un `automationId` différent est un autre test
  automatisé **[Q3]**.
- **Exactement un candidat** → correspondance, avertissement `mapped_by_requirement` (le résumé
  propose de renseigner son `automationId`). Zéro → non mappé ; plusieurs → `ambiguous`.

> Constat sur les outils de fan-demo (lu le 2026-11-07 sur les branches par défaut) : seul **e2Sim**
> émet la propriété `requirement` par testcase. **e2Unit** ne la met que dans son JSON et son Excel
> (`eunit/report.py` : `write_junit` n'écrit que des propriétés de suite) et nomme ses testcases
> `"<id> <titre>"`. **e2HIL** n'a pas encore de code. Les identifiants actuels des tests e2Sim
> (`FAN-SYS-01`, `FAN-MOT-01`) ne sont pas des IDs Polenta : le projet `polenta/` de fan-demo est
> « à venir » (`docs/PLAN.md`). Voir [Q6].

### 2.3 Avec une campagne (`--campaign CAMP-xxxx`)

Sans campagne : **TestRun isolés**, conformément à la décision arrêtée de SPEC-TESTS §7 (« Import JUnit
XML : TestRun isolés — pas de rattachement automatique »). Avec `--campaign`, le rattachement est
**explicite**, donc compatible avec cette décision :

- Campagne inconnue, `completed` ou `abandoned` : **erreur globale** (code 2), rien n'est écrit — même
  refus que l'import du classeur d'exécution (SPEC-TESTS §4.5).
- Campagne d'un autre repo que celui dont relève le test : impossible par construction (GH255,
  `TEST_OTHER_REPO`) ; le test est alors « absent de la campagne ».
- Le cas de test trouvé (§2.1 / §2.2) doit avoir **une** entrée dans `runs[]` de la campagne :
  - aucune entrée → non importé, raison `not_in_campaign` ;
  - plusieurs entrées (test paramétré, instances T179) → départagées par les propriétés `requirement`
    du testcase contre `requirementId` de l'entrée ; une seule retenue → importée, sinon `ambiguous`.
- Le run porte `campaignEntry` (GH73) ; l'entrée prend `status`, `runId`, `executedAt`, `executedBy` ;
  campagne `planned` → `in_progress` — exactement comme l'import du classeur (SPEC-TESTS §4.5,
  « Toute instance remplie écrase »).
- Version testée (GH202) : obligatoire dès que le repo de la campagne a une version sélectionnable
  (décision GH202 Q2, validée le 2026-11-03, `specs/GH202.md`). Option `--tested-version <ID|label|texte>`
  : ID ou label reconnu → version ; autre texte → écart non documenté (avertissement
  `tested_version_undocumented`). Absente alors qu'une version est sélectionnable : **erreur globale**
  (code 2) **[Q7]**. Le commit retenu est `HEAD` du repo au moment de l'import.
- Test dont la version effective n'est pas approuvée : avertissement `test_not_approved`, pas de refus
  (comme GH68).

### 2.4 Plusieurs résultats pour un même cas de test

Un même test exécuté plusieurs fois dans une invocation (ex. fan-demo : `sim32.xml` et `sim64.xml`,
deux toolchains) donne **un seul TestRun** par cas de test (et par entrée de campagne) et par
invocation **[Q2]** :

- verdict = le plus défavorable (`FAIL` > `BLOCKED` > `PASS`) ;
- date = la plus récente des dates des résultats ; durée = somme ;
- notes = une ligne par résultat source : fichier, suite, `classname.name`, verdict, message.

### 2.5 Nœuds en lecture seule, composants

Le run est écrit dans le repo du test (composant compris), comme `TestsService.execute` aujourd'hui.
Test d'un nœud `readonly: true` : non importé, raison `readonly_node` (règle d'écriture du serveur MCP,
SPEC-MCP-SERVER §1).

## 3. Le TestRun écrit

Même service et même fichier que l'exécution dans l'outil et l'import du classeur
(`TestsService.execute`, `test-runs/<TEST>/<TEST>-run-NNNN.yaml`). Valeurs :

| Champ | Valeur |
|---|---|
| `origin` | **`junit-import`** (nouvelle valeur de l'énumération, à côté de `excel-import` — SPEC-TESTS §3.2) |
| `result` | verdict (§1.3, §2.4), toujours explicite |
| `executedAt` | date du résultat (§1.2, §2.4) |
| `executedBy` | `--executed-by <nom>`, sinon `user.name` de la config git du repo, sinon vide |
| `duration` | durée JUnit (§1.2, §2.4), arrondie à la seconde |
| `stepResults` | **vide** : un rapport JUnit ne dit rien des étapes du cas de test **[Q8]** |
| `notes` | lignes de §2.4 et propriétés de suite, texte brut échappé (Markdown, une ligne = un paragraphe, comme l'import du classeur) |
| `campaignEntry`, `requirementId`, `testedConfig` | avec `--campaign` seulement (§2.3) |

Champs d'exécution (GH196) : aucun n'est fourni. Un champ `required` ou `requiredWhen` satisfait par
le verdict fait refuser **ce** résultat (raison `required_field_missing`, nom du champ), les autres sont
importés.

Relecture d'un run importé dans l'application : badge « Importé depuis JUnit », comme « Importé depuis
Excel » (SPEC-TESTS §4.5).

### 3.1 Réimport (idempotence)

SPEC-TESTS §3.5 promet un import idempotent sur la clé `automationId` + `productVersion` +
`executedAt` ; `productVersion` n'existe pas dans le modèle (SPEC-AUDIT §4.1). Clé retenue : un run
**n'est pas recréé** si le même cas de test a déjà un run `origin: junit-import` avec la même
`executedAt` et la même `campaignEntry` (ou aucune des deux). Résultat « déjà importé », compté à part,
ni erreur ni code ≠ 0. *(Implémentation, sprint 2)* Limite : un run agrégé (§2.4) porte la date du plus
récent de ses résultats ; réimporter un sous-ensemble des mêmes fichiers donne une autre date, donc un
nouveau run. Sans `timestamp` dans le fichier (§1.2) l'idempotence ne peut pas être garantie :
l'avertissement `no_timestamp` le dit.

## 4. Commande `polenta import-results`

```
polenta import-results --repo <dir> --junit <fichier|motif> [--junit …]
                       [--campaign CAMP-xxxx] [--tested-version <ID|label|texte>]
                       [--executed-by <nom>] [--workspace <dir>] [--dry-run] [--json]
```

- `--repo` obligatoire (racine du projet Polenta : dossier portant `.polenta/schema.yaml`) ; dossier
  absent ou non Polenta → code 2. `--workspace` : même rôle que pour le serveur MCP (§2.3 de
  SPEC-MCP-SERVER).
- `--dry-run` : tout est lu, apparié et contrôlé, **rien n'est écrit** ; même résumé, mêmes codes
  retour. Défaut de la commande : écriture (c'est son usage en CI) ; défaut inverse pour l'outil MCP
  (§5).
- Écriture : arbre de travail uniquement, jamais de commit, de push ni de pull. L'écriture des runs est
  séquentielle ; une erreur inattendue en cours d'écriture arrête l'import (ce qui est écrit reste),
  code 2, comme l'import du classeur.
- **Sortie** : résumé texte sur stdout — compteurs (importés, déjà importés, ignorés, non mappés,
  ambigus, refusés), puis une ligne par résultat non importé (fichier, `classname.name`, raison) et
  une par avertissement. `--json` : le même contenu en un objet JSON (contrat commun avec l'outil MCP,
  §5). Messages d'erreur globale sur stderr. Langue : anglais (outil sans interface, lu dans des logs
  de CI) **[Q9]**.
- **Code retour** :

| Code | Signification |
|---|---|
| 0 | tous les résultats non ignorés sont importés ou déjà importés |
| 1 | au moins un résultat non importé : non mappé, ambigu, absent de la campagne, refusé (§2–§3) — les autres sont importés |
| 2 | erreur globale : arguments, repo, fichier, campagne, version testée manquante, erreur d'écriture — rien n'est écrit (sauf interruption en cours d'écriture, ci-dessus) |

### 4.1 Distribution **[Q10]**

La commande doit tourner sur un runner de CI qui n'a ni l'application installée, ni Electron, ni
`keytar`, ni écran : Node.js ≥ 20 seul.

- Un bundle autonome `polenta-cli.cjs` (même principe que `out/mcp-server/index.cjs`, SPEC-TECH-stack §9),
  `node polenta-cli.cjs import-results …` ; commande racine `polenta <sous-commande>` pour accueillir
  d'autres sous-commandes génériques plus tard (aucune n'est prévue ici).
- Publié en asset de chaque release GitHub (`release.yml`, tag `vX.Y.Z`), à côté de l'installeur et de
  l'image `polenta-web` (GH305). Marque : celle de la release (GH49). Également présent dans les
  ressources de l'application installée (lançable comme le serveur MCP, `ELECTRON_RUN_AS_NODE=1`).
- Aucun accès réseau, aucun compte, aucun jeton : le bundle échoue explicitement s'il en a besoin
  (même garde-fou que `mcpHostContext`, SPEC-MCP-SERVER §3).

## 5. Outil MCP `import_test_results`

Même service, même contrat que la commande (fichier `tools/…`, à côté des autres outils d'écriture) :

- Entrée : `files` (liste de chemins ou motifs, absolus ou relatifs au repo du serveur), `campaignId?`,
  `testedVersion?`, `executedBy?`, **`dryRun` (défaut `true`)** — règle des écritures massives du
  serveur (SPEC-MCP-SERVER §1).
- Sortie : l'objet JSON du `--json` de la commande, avec en plus `dryRun`. Les cas du code 1 sont un
  **succès** (le détail est dans l'objet) ; ceux du code 2 reviennent en `isError: true` avec le message
  (convention d'erreur, SPEC-MCP-SERVER §6).
- `executedBy` absent : `--user` du serveur (GH18), sinon `user.name` git, sinon vide.
- `AGENTS.md` généré : une ligne sur l'outil (dry run d'abord, puis `dryRun: false`).

## 6. Cas d'usage

1. **CI fan-demo, sans campagne** : `node polenta-cli.cjs import-results --repo polenta --junit
   "out/junit/*.xml"` → un run isolé par test automatisé ; code 1 si un test pytest n'a pas de cas de
   test Polenta ; le job commite ensuite (ou non) — décision du dépôt, pas de Polenta.
2. **CI sur une campagne de release** : `--campaign CAMP-0007 --tested-version 1.2.0` → les entrées
   de la campagne prennent les verdicts, la campagne passe `in_progress`.
3. **Agent IA** : `import_test_results` en dry run, lecture des non mappés, proposition de renseigner
   les `automationId`, puis `dryRun: false`.
4. **Réimport du même fichier** : « N déjà importés », aucun run nouveau, code 0.
5. **Rapport absent** (`out/junit/*.xml` vide) : code 2, rien écrit.

## 7. Critères d'acceptation

1. Un fichier pytest et un fichier e2Unit réels (fixtures tirées de fan-demo / e2Unit) sont lus ; chaque
   `<testcase>` donne un résultat avec verdict, durée, date et propriétés `requirement`.
2. `automationId` égal à `<classname>.<name>` ou à `<name>` → run écrit dans
   `test-runs/<TEST>/`, `origin: junit-import`, verdict selon §1.3 ; `<skipped>` → aucun run.
3. Deux tests avec le même `automationId` → aucun run, raison `ambiguous`, code 1.
4. Sans correspondance `automationId`, une propriété `requirement` désignant une exigence couverte
   par un seul test sans `automationId` → run écrit, avertissement `mapped_by_requirement` ; deux tests
   candidats → `ambiguous`.
5. Deux fichiers contenant le même test → un seul run, verdict le plus défavorable, une ligne de notes
   par source.
6. `--campaign` : entrée mise à jour (`status`, `runId`, `executedAt`, `executedBy`), run avec
   `campaignEntry`, campagne `planned` → `in_progress` ; test hors campagne → `not_in_campaign` ;
   campagne clôturée → code 2 et aucun fichier modifié (vérifié par `git status`).
7. Campagne d'un repo avec version sélectionnable, sans `--tested-version` → code 2 ; avec → run
   portant `testedConfig`.
8. `--dry-run` / `dryRun: true` : mêmes compteurs et mêmes codes qu'une exécution réelle, `git status`
   inchangé.
9. Réimport du même fichier (avec `timestamp`) → 0 run nouveau, code 0.
10. Codes retour 0 / 1 / 2 conformes au tableau du §4 ; erreurs globales sur stderr.
11. Aucune écriture hors `test-runs/` et `campaigns/` ; aucun commit (`git log` inchangé).
12. Le bundle `polenta-cli.cjs` s'exécute avec un Node.js système, sans Electron ni `keytar`
    installés, sur Linux (runner de CI) et Windows.
13. L'outil MCP renvoie le même objet que `--json` et n'écrit rien sans `dryRun: false`.
14. Un run importé s'affiche dans l'application (section « Exécutions » de l'éditeur, page de
    campagne) avec le badge « Importé depuis JUnit ».

## 8. Indicateurs (principe GH79)

Aucun indicateur de suivi n'est introduit. Les compteurs du résumé et l'agrégation des verdicts (§2.4)
servent la fonction d'import elle-même (écrire un run, dire ce qui n'a pas été importé) : ils relèvent
de Polenta (SPEC-TECH-stack §1.1). Taux de réussite, tendance par build, etc. restent côté projet
(scripts de la vue Suivi sur les runs bruts).

## Hors scope

- Import depuis l'interface (bouton, aperçu) — le service est réutilisable, à faire dans une autre
  issue si besoin.
- Le format **JSON Polenta** de SPEC-TESTS §3.5 (jamais défini) et le JSON d'e2Unit **[Q6]**.
- Toute logique propre à la CI : seuils, échec de build selon la couverture, sortie JUnit, intégration
  GitHub Actions, commit / push des résultats (#130 fermée le 2026-11-06).
- Création automatique des cas de test manquants ou de leur `automationId` ; rattachement a posteriori
  d'un run isolé à une campagne (SPEC-TESTS §3.5 : « manuel depuis l'UI » — non implémenté non plus).
- Proposition d'issue sur échec (GH244) : l'outil la fait à l'écran et dans le bilan du classeur, pas ici
  (le résumé liste les échecs).
- Resynchronisation de la copie `testSnapshot` des entrées de campagne (GH81) : pas de version
  exportée à comparer.
- Résultats par étape (voir [Q8]), pièces jointes / `system-out` complets (le message tronqué suffit,
  les logs restent dans les artefacts de CI).
- Modification d'e2Unit / e2Sim / e2HIL (à demander dans leurs dépôts, [Q6]).

## Décisions

Validées par l'humain le 2026-11-07 : chaque question ci-dessous est tranchée **selon la
recommandation** ; l'alternative est conservée pour mémoire. Q6 : issue ouverte dans `laurentolive/e2Unit`
— laurentolive/e2Unit#4, ouverte le 2026-11-07.

### Questions (texte d'origine)

1. **Portée après #130 (« Ne pas mélanger la CI à Polenta », humain, 2026-11-06).** Recommandation :
   garder la commande, générique, sans logique de CI (§ Décision voisine). Alternative : pas de
   commande, seulement l'outil MCP et le service (§4 retiré).
2. **Plusieurs résultats d'un même test dans une invocation.** Recommandation : un run agrégé, verdict
   le plus défavorable (§2.4). Alternative : un run par `<testcase>` (traçabilité fichier par fichier,
   mais un test e2Sim joué sur deux toolchains donne deux runs et l'entrée de campagne ne garde que le
   dernier).
3. **Secours par `requirement`.** Recommandation : candidat unique parmi les tests couvrant l'exigence
   et **sans** `automationId` (§2.2). Alternatives : tous les tests couvrant l'exigence ; ou créer un
   run pour chacun d'eux.
4. **Nom du champ de correspondance.** Recommandation : `automationId` fixe, type `text` (SPEC-TESTS
   §2.5 / §3.5). Alternative : nom configurable (option `--key-field`, ou propriété du type de test).
5. **`<error>` et `<skipped>`.** Recommandation : `error` → `BLOCKED`, `skipped` → non importé.
   Alternatives : `error` → `FAIL` ; `skipped` → run `BLOCKED` (ou `INCOMPLETE`).
6. **Outils de fan-demo.** e2Unit n'émet pas `requirement` par testcase en JUnit et nomme ses tests
   `"<id> <titre>"` ; e2HIL n'existe pas encore ; les exigences d'e2Sim ne sont pas des IDs Polenta.
   Recommandation : ne rien adapter dans Polenta ; ouvrir une issue dans e2Unit (propriété
   `requirement` et `name` = id stable) et utiliser des IDs Polenta dans les `@requirement` de
   fan-demo. Alternative : lire aussi le JSON d'e2Unit, ou faire correspondre le premier mot du `name`.
7. **Version testée absente avec `--campaign`.** Recommandation : erreur globale (code 2), cohérente
   avec GH202 Q2 (saisie obligatoire, validée le 2026-11-03). Alternative : avertissement et run sans
   `testedConfig`, comme les classeurs antérieurs à v4 (contrôle non bloquant par défaut, décision #206
   Q1 notée en mémoire de l'agent — à confirmer).
8. **Étapes du run.** Recommandation : `stepResults` vide, verdict global explicite. Alternative : toutes
   les étapes du cas de test au verdict global (affichage complet, mais résultat d'étape inventé).
9. **Langue de la sortie.** Recommandation : anglais. Alternative : langue de la locale système, ou
   français.
10. **Distribution.** Recommandation : bundle `polenta-cli.cjs` en asset de release + dans l'application
    installée (§4.1). Alternatives : paquet npm publié ; commande intégrée à l'image Docker
    `polenta-web` (`docker run … polenta import-results`).
