# GH133 — Publier hors de la branche d'intégration : avertir et proposer de fusionner ou non

> Phase Spec (WORKFLOW.md). Q1–Q3 tranchées par Benoit le 23/10 (case cochée par défaut, choix
> mémorisé par branche, une seule case). **[Q4]** en attente : la recommandation s'applique.

## Contexte

`SPEC-FORKS-BRANCHES-BASELINES.md` §2.1 : depuis une branche libre ou `dev-*` (≠ intégration, hors
`int-*`), « Publier » commite sur la branche courante, **fusionne dans la branche d'intégration** et
**pousse l'intégration** (`publishRepo` dans `lib/publishWorkspace.ts`, push dans
`ModificationControl.tsx`/`pushPublished`). C'est voulu pour le cas nominal, mais rien ne le dit à
l'utilisateur : le popup « Publier » ne montre pas la cible. Un utilisateur qui a créé `toolTest` pour
isoler des essais a vu ses exigences de test arriver sur `origin/main`.

## Description fonctionnelle

### Qui est concerné

Un repo est **« hors intégration »** quand sa branche courante n'est ni la branche d'intégration
configurée, ni une `int-*` (déjà bloquées, GH106), ni la `dev-<slug>` éphémère d'une publication
nominale interrompue (`continuingEphemeral`), ni une branche `dev-resync*` (GH39, flux de
resynchronisation qui doit fusionner). Le calcul se fait par repo, comme Publier (GH38).

### Cas nominal (aucun repo à publier hors intégration)

Inchangé : ni avertissement, ni case à cocher.

### Popup « Publier » quand au moins un repo à publier est hors intégration

- **Avertissement** au-dessus du champ titre, par repo concerné :
  « Vous êtes sur `toolTest`. Publier fusionnera cette branche dans `main` puis poussera `main`. »
  (en multi-repo : une ligne par repo, préfixée du nom du repo).
- **Case à cocher « Fusionner dans `<intégration>` »** (en multi-repo, intégrations différentes :
  « Fusionner dans la branche d'intégration »). Le texte de l'avertissement suit l'état de la case :
  - **cochée** : comportement actuel — commit sur la branche, fusion dans l'intégration, push de
    l'intégration, épinglage (T82) du SHA de fusion dans les parents ;
  - **décochée** : commit sur la branche courante puis push de **cette branche seulement**
    (`origin/<branche>`, créée si absente). La branche d'intégration n'est ni avancée, ni fusionnée,
    ni poussée. Texte : « Publier commitera sur `toolTest` et poussera `toolTest`. `main` ne sera pas
    modifiée. »
- **Valeur par défaut : cochée** (décidé par Benoit le 23/10, **[Q1]**) : par défaut, Publier se
  comporte comme aujourd'hui (fusion dans l'intégration) ; décocher permet de ne pas fusionner.
- **Choix mémorisé par branche** (décidé, **[Q2]**) : l'état de la case est enregistré dans la
  préférence personnelle (`.{compte}.pref`, clé `publishMerge`, par repo puis par branche) à chaque
  publication, et repris à la publication suivante depuis la même branche. Sans choix mémorisé pour
  la branche : cochée. Rien n'est mémorisé pour une branche d'intégration (pas de case).
- **Une seule case pour toute la publication** (décidé, **[Q3]**). Les repos sur leur intégration
  sont publiés normalement quel que soit l'état de la case. Le choix mémorisé est écrit pour chaque
  repo hors intégration de la publication ; à l'ouverture, si ces repos ont des choix différents, la
  case reprend cochée.

### Publication sans fusion — détails

- Le fetch préalable (T154) est conservé ; la vérification de divergence de l'intégration (GH39,
  `PublishDivergedError`) **ne s'applique pas** au repo publié sans fusion (l'intégration n'est pas
  touchée).
- Push de la branche courante : l'échec (refus, réseau) est signalé comme aujourd'hui pour le push de
  l'intégration (`pushError`, nom du repo + branche). Une branche distante qui a avancé
  (non fast-forward) n'est jamais forcée : erreur explicite, « Rafraîchir » pour récupérer.
- **Épinglage (T82)** **[Q4]** : publier sans fusion **n'épingle pas** le commit dans les manifestes
  des parents (il n'est pas sur l'intégration). Recommandation retenue ; alternative : épingler la
  branche (`pin: toolTest`).
- Après publication, le repo reste checkouté sur sa branche (comme aujourd'hui).
- Le message de succès dit ce qui a été fait : « Publié sur `toolTest` (non fusionné dans `main`) ».

## Critères d'acceptation

1. Sur `main` = intégration : le popup Publier est identique à aujourd'hui (aucun avertissement,
   aucune case).
2. Sur `toolTest` créée depuis le panneau Version, une exigence modifiée : le popup affiche
   l'avertissement et la case « Fusionner dans `main` », **cochée** (aucun choix mémorisé).
3. Case décochée, Publier : `origin/toolTest` contient le commit ; `main` et `origin/main` sont à
   leur SHA d'avant ; le repo reste sur `toolTest`.
4. Case cochée, Publier : comportement actuel (commit sur `toolTest`, fusion dans `main`, push de
   `main`), conforme à §2.1.
5. Sur `int-B` non désignée : toujours bloqué (GH106), pas de case.
6. Publication nominale interrompue puis reprise (`dev-<slug>` éphémère) et branche `dev-resync` :
   aucune case, fusion comme aujourd'hui.
7. Multi-repo : enfant sur `toolTest`, parent sur son intégration, case décochée : l'enfant pousse
   `toolTest` seul, le parent est publié normalement et son manifeste n'est pas ré-épinglé sur le
   commit de l'enfant.
8. Case décochée puis Publier sur `toolTest` : au Publier suivant depuis `toolTest`, la case est
   décochée ; depuis une autre branche hors intégration jamais publiée, elle est cochée.
