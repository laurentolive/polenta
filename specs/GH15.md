# GH15 — Réseau : délais d'attente réglables (accès à GitHub depuis la Chine)

## Contexte

Un collaborateur en Chine ne peut pas utiliser Polenta avec un projet hébergé sur GitHub : les
opérations échouent sur un **délai d'attente dépassé**. Le filtrage du trafic sortant ralentit
fortement l'établissement des connexions vers github.com, au-delà des délais codés en dur.

Délais actuels (tous codés en dur, desktop) :

| Appel | Fichier | Délai actuel |
|---|---|---|
| Établissement de connexion (TCP + TLS), direct ou via proxy, pour tout appel undici | défaut undici (`net-proxy.ts`, `git-http.ts`) | 10 s |
| API de la forge (en-têtes / corps) | `forge/forge-http.ts` | 20 s |
| Sondes rapides de l'API de la forge (`repoInfo`, `repoPermissions`, `probeAccess`, projets d'équipe) | `forgejo.provider.ts` l. 79, 106, 265 ; `github.provider.ts` l. 50 ; `forge-config.service.ts` l. 137 | 10 s |
| Opérations git HTTPS (clone, fetch, pull, push) — en-têtes / corps | `git-http.ts` (défaut undici) | 300 s |
| Images distantes des gabarits d'export | `export/template/image-source.ts` | 10 s |

Le délai de connexion de 10 s est le suspect principal : il s'applique à **toutes** les requêtes
(forge et git) et n'est pas réglable.

## Décisions de cadrage (2026-10-27)

| Question | Décision |
|---|---|
| Où vit le réglage | **Préférences de l'application seulement** (`userData/app-settings.json`, `AppSettingsService`). Pas de clé dans la configuration machine (`machine-config.ts`). |
| Granularité | **Un seul délai en secondes** : le « délai de connexion réseau ». Les autres délais en dérivent proportionnellement. |
| Valeurs par défaut | **Inchangées** : sans réglage, le comportement est exactement celui d'aujourd'hui. |
| Accès au réglage | **Panneau compte seulement** (à côté de la mise à jour automatique et du dossier des gabarits), donc après connexion. |

## Description fonctionnelle

### 1. Le réglage

- Nouvelle préférence d'application `networkTimeoutSeconds` : « Délai de connexion réseau (s) ».
- Valeur entière, **défaut 10**, **bornes 10 à 120**. Une valeur absente, non entière ou hors bornes
  dans `app-settings.json` est ramenée au défaut (lecture) ; l'UI n'accepte que les valeurs valides.
  Abaisser sous le défaut n'est pas proposé (aucun cas d'usage, risque d'échecs sur réseau normal).
- Affichée dans le panneau compte (`AccountPanel.tsx`), section des préférences de l'application,
  avec une aide : « À augmenter si les opérations échouent sur un délai dépassé (réseau lent ou
  filtré, ex. accès à GitHub depuis la Chine). »
- Stockée comme les autres préférences app-level ; écrite seulement si elle diffère du défaut
  (comme `exportTemplatesDir`, le fichier reste inchangé pour qui ne touche à rien).

### 2. Application aux délais

Soit `f = networkTimeoutSeconds / 10` (facteur ≥ 1). Chaque délai réseau du desktop devient
`délai de base × f` :

| Appel | Délai de base | Avec 30 s (f = 3) |
|---|---|---|
| Établissement de connexion (direct **et** via proxy), forge et git | 10 s | 30 s |
| API de la forge (en-têtes / corps) | 20 s | 60 s |
| Sondes rapides de l'API de la forge | 10 s | 30 s |
| Opérations git HTTPS — en-têtes / corps | 300 s | 900 s |
| Images distantes des gabarits d'export | 10 s | 30 s |

- Le délai de connexion est passé **explicitement** au dispatcher undici, pour les connexions
  directes comme pour celles via proxy (`ProxyAgent`) — aujourd'hui il n'est jamais fixé.
- Un changement du réglage s'applique **aux requêtes suivantes, sans redémarrage**. Une requête
  en cours garde le délai avec lequel elle a démarré.
- Avec la valeur par défaut (10), tous les délais sont identiques à ceux d'aujourd'hui.

### 3. Message d'erreur

Quand une opération échoue sur un **délai dépassé** (connexion, en-têtes ou corps —
`UND_ERR_CONNECT_TIMEOUT`, `ETIMEDOUT`, `UND_ERR_HEADERS_TIMEOUT`, `UND_ERR_BODY_TIMEOUT`, ou
abandon sur délai pour les images), le message présenté à l'utilisateur :

- dit que le délai est dépassé et rappelle la valeur courante (« délai de connexion : 10 s ») ;
- **cite le réglage** à modifier : « Compte → Délai de connexion réseau » ;
- garde la piste actuelle proxy/pare-feu.

Cela vaut pour les appels de l'API de la forge (déjà traduits par `describeFetchError`) **et** pour
les opérations git (clone, fetch, pull, push), qui aujourd'hui remontent l'erreur brute.

Le classement « réseau injoignable » (`isNetworkUnreachable`, GH43 : auto-pull silencieux hors
ligne, échec réseau explicite de Publier) reste inchangé et inclut les nouveaux codes de délai
d'en-têtes/corps seulement si le Design le juge nécessaire pour la cohérence de ces écrans.

## Cas d'usage

1. **Collaborateur en Chine, déjà connecté** : le clone d'un projet GitHub échoue avec « Délai de
   connexion dépassé (10 s) … Compte → Délai de connexion réseau ». Il règle 40 s dans le panneau
   compte, relance le clone sans redémarrer : il aboutit. Fetch, Publier et l'auto-pull utilisent
   ensuite le même délai.
2. **Utilisateur sur réseau normal** : ne touche à rien, aucun changement de comportement ni de
   fichier.
3. **Réglage puis retour au défaut** : remettre 10 restaure exactement les délais d'origine.
4. **Poste hors ligne avec un délai élevé** : les échecs DNS / réseau injoignable restent
   immédiats (ils ne dépendent pas du délai) ; seul un serveur qui ne répond pas fait attendre
   jusqu'au délai réglé.

## Critères d'acceptation

- [ ] CA1 — Le panneau compte affiche « Délai de connexion réseau (s) », valeur 10 par défaut,
      bornée à 10–120 ; la valeur est persistée dans `app-settings.json` et relue au redémarrage.
- [ ] CA2 — Valeur invalide dans `app-settings.json` (texte, 5, 500, 12.5) → défaut 10, sans erreur.
- [ ] CA3 — Avec la valeur par défaut, les délais effectifs sont ceux du tableau « Délai de base »
      (test unitaire sur la fonction de calcul des délais).
- [ ] CA4 — Un délai réglé à la main est appliqué aux appels de l'API de la forge et aux opérations
      git HTTPS, connexion directe **et** via proxy (test unitaire : options passées à undici /
      au dispatcher pour 10 et pour 30).
- [ ] CA5 — Le changement s'applique sans redémarrage à la requête suivante.
- [ ] CA6 — Simulation d'un lien lent (proxy de test qui retarde l'établissement de la connexion
      de plus de 10 s) : le clone et le fetch **échouent** avec le délai par défaut et **aboutissent**
      avec un délai augmenté (ex. 30 s).
- [ ] CA7 — En cas d'échec sur délai dépassé (API forge et git), le message cite le réglage
      « Compte → Délai de connexion réseau » et sa valeur courante.
- [ ] CA8 — Les images distantes des gabarits d'export suivent le facteur.
- [ ] CA9 — À confirmer avec le collaborateur en Chine sur un vrai projet GitHub (validation
      manuelle, hors CI).

## Hors scope

- **Configuration machine** (clé DSI dans `config.json`) : non retenue (décision du 2026-10-27).
- **Accès avant connexion** : le réglage n'est pas proposé sur l'écran de connexion. Conséquence
  assumée : si la connexion elle-même (Device Flow GitHub, API `/user`) échoue sur délai dépassé,
  l'utilisateur doit d'abord se connecter (ex. par jeton, ou via un proxy). Le collaborateur
  concerné étant déjà connecté, ce cas est à rouvrir en nouvelle issue si besoin.
- **Valeurs par défaut** : non relevées (décision du 2026-10-27).
- **Valeurs séparées** par type d'appel (connexion / API / git) : non retenues.
- **Client web** (GH44) : le serveur web n'expose pas ce réglage et garde les délais par défaut
  (y compris `oidc.ts`). Le panneau compte du client web ne l'affiche pas.
- **Nouvelles tentatives automatiques** (retry) sur délai dépassé.
- **Passer par un proxy** (déjà supporté) ou **héberger la forge en Chine** (jalon B).
- Délais non réseau (bac à sable des scripts de suivi, impression headless…).
