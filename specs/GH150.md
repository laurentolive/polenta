# GH150 — MCP : modifier des exigences/tests existants et gérer les paramètres

Statut : spec en attente de validation (questions en fin de document).

## Contexte

Le serveur MCP crée des exigences, tests, campagnes et liens (`bulk_import_*`, `create_links`) et
modifie le schéma (`add_*`), mais ne sait ni **modifier un objet existant** ni **gérer la base de
paramètres** (T171, `parameters/parameters.yaml`). Un agent écrit alors les YAML à la main
(repli prévu par `AGENTS.md`), ce qui contourne les règles de l'appli : formatage différent de
`git.writeYaml` (diff sur tout le fichier), `history` réécrit au `sed`, pas de `needsRevalidation`,
pas de marquage des éléments approuvés qui utilisent un paramètre modifié.

## Fonctionnement attendu

### 1. `update_requirements` / `update_tests`

Entrée : `{ entries: [{ id, title?, status?, fields? }], dryRun?: boolean = true }`.
Pour un test, en plus : `preconditions?`, `postconditions?`, `steps?` (remplacement complet),
`equipment?` (remplacement complet).

- `fields` : **fusion partielle** ; une clé à `null` **retire** le champ du fichier.
- Validation par entrée (même style que `validateBulkEntries`, première règle en échec) :
  1. l'objet existe (dans le repo ouvert ou un composant du workspace, comme `list_requirements`) ;
  2. son nœud n'est pas `readonly` (`READONLY_REPO` si le repo est en lecture seule) ;
  3. `status` fait partie des statuts du type (`isUnknownStatus`, GH149) ;
  4. chaque clé de `fields` est un champ déclaré du type ; valeur d'`enum` / `multi_enum` dans
     `values` ;
  5. après fusion : champs `required` non vides, champs `validator: EARS` conformes.
- `dryRun: true` : renvoie, par entrée, l'aperçu `{ id, changes: { <champ>: { before, after } } }`
  et les erreurs, sans écrire.
- `dryRun: false` : écriture **en série, best-effort** (comme `bulk_import_*`), par les services
  de l'appli :
  - `title` / `fields` → `RequirementsService.update` / `TestsService.update` ;
  - `status` → `transition()` (version incrémentée en sortie d'un statut `isApproval`,
    `needsRevalidation` posé sur les éléments liés, T172) ;
  - `history` alimenté avec `source: mcp` (déjà le cas via `HistoryService` du conteneur MCP).
- Résultat : `{ dryRun, summary: { total, ok, failed }, updated: [{ index, id, version }], preview, errors }`.

### 2. Paramètres

- `list_parameters({ repo? })` : paramètres de chaque repo visible (`ParametersService.list`),
  avec `usageCounts` et `readonly`.
- `set_parameters({ repo?, entries: [{ name, value, unit?, description? }], dryRun = true })` :
  création si absent, modification sinon ; `dryRun` liste `{ name, action: create|update, before, after }`
  et les éléments approuvés qui seraient marqués. Écriture par `ParametersService.create/update`
  (clés triées, format identique à l'appli, revalidation T171 §9).
- `delete_parameter({ repo?, name })` : **refusé** tant qu'un élément non terminal l'utilise
  (comportement actuel de `ParametersService.delete`) ; renvoie alors la liste des utilisations.
- `repo` : nom de montage du repo cible ; absent = repo ouvert.
- Le conteneur MCP instancie `ParametersService` (aujourd'hui absent de `mcp-server/container.ts`).

### 3. `AGENTS.md`

Gabarit `agents-md.template.ts` : lister les nouveaux outils, retirer le repli « écrire le YAML à
la main » pour la modification d'objets et de paramètres (version du gabarit incrémentée).

## Critères d'acceptation

1. `update_requirements` en `dryRun` ne modifie aucun fichier et renvoie avant/après par champ.
2. Un `status` inconnu, un champ non déclaré ou une valeur d'enum hors liste → erreur sur l'entrée,
   les autres entrées passent.
3. `fields: { x: null }` retire `x` du YAML ; les autres champs sont conservés.
4. Une exigence `approved` passée en `draft` par l'outil : version +1, `needsRevalidation: true`
   sur les éléments liés, entrée `history.status` avec `source: mcp`.
5. Fichiers réécrits au même format que l'appli : relire puis réécrire depuis l'appli ne produit
   aucun diff.
6. `set_parameters` crée/modifie, `parameters.yaml` reste trié ; un paramètre utilisé par un
   élément approuvé dont la valeur change marque cet élément.
7. `delete_parameter` d'un paramètre utilisé par un élément non terminal → refus + utilisations.
8. `AGENTS.md` régénéré à l'ouverture d'un projet existant (nouvelle version du gabarit).

## Hors scope

- Suppression d'exigences / tests (pierres tombales GH20) : autre ticket si besoin.
- Changement d'`objectTypeRef` (déplacement de type) : reste réservé à la cascade de
  l'onglet Structure (T135).
- Modification de campagnes.
- Renommage de paramètre (et réécriture des références `{nom}`).

## Questions

1. **Statut et contenu dans le même appel** : si une entrée change `status` et `fields`, on écrit
   les champs puis la transition (deux écritures, deux entrées d'historique au même instant).
   Recommandation : oui, dans cet ordre.
2. **Commentaire de modification** : `UpdateRequirementSchema` a un `modificationComment` ; l'exposer
   dans `update_*` ? Recommandation : oui, facultatif.
3. **`delete_parameter` avec utilisations** : refus strict (comportement de l'appli) ou option
   `force` ? Recommandation : refus strict, comme l'appli.
4. **Un outil ou deux pour les tests** : `update_tests` séparé de `update_requirements` (comme
   `bulk_import_*`). Recommandation : deux outils.
