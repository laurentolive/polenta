# GH154 — Notes de version générées depuis les issues GitHub fermées (release 0.1.3)

Issue : #154 — type `feature`.

## Besoin

`scripts/release-notes.mjs` lisait `TICKETS.md` / `tickets_archive.md`, abandonnés depuis la
migration des tickets vers les issues GitHub : la release suivante aurait affiché « Aucun ticket
traité ». Les notes doivent lister, automatiquement au moment où le workflow génère la release, les
issues fermées depuis la dernière release.

## Comportement

`node scripts/release-notes.mjs <tag>` (appelé par `release.yml` au push d'un tag `v*.*.*`) :

- **Dernière release** : la plus récente des releases GitHub publiées (ni brouillon, ni préversion)
  dont le tag diffère de `<tag>` — une relance du workflow après publication retombe donc sur la
  précédente. Aucune release → toutes les issues fermées.
- **Issues retenues** : fermées **comme terminées** (`reason:completed`) après la date de publication
  de cette release. Les doublons et « not planned » sont exclus. Recherche GitHub paginée.
- **Rendu** : sections « Nouveautés » (`type:feature`), « Corrections » (`type:bug`), « Autres »
  (sans label de type), issues par numéro décroissant, `- #N — titre` (lien auto GitHub) ; lien
  « Changelog complet » `compare/<release précédente>...<tag>`.
- Échec de `gh` (jeton, réseau) → l'étape échoue, la release n'est pas publiée.

## Workflow

`release.yml` : `GH_TOKEN: ${{ github.token }}` sur l'étape de génération, permission `issues: read`.

## Release

`apps/desktop/package.json` : 0.1.2 → 0.1.3. Tag parasite `v1.2.0` (15/10, build en échec, sans
release) supprimé.

## Vérification

Exécution locale `node scripts/release-notes.mjs v0.1.3` : 17 issues depuis v0.1.2 (7 nouveautés,
10 corrections), #128 (doublon, « not planned ») exclue, comparaison `v0.1.2...v0.1.3`.
