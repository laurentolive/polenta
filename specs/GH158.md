# GH158 — Release : version déduite du tag git, build dev en `<dernière release>-alpha.<n>`

Ticket court : spec, design et résumé de sprint réunis ici, sur demande de l'humain.

## Besoin

Publier une release = poser un tag `vX.Y.Z` et le pousser. Plus de modification de
`apps/desktop/package.json` à chaque release : c'était une étape manuelle de plus, et un tag
désaccordé avec `package.json` faisait échouer le workflow.

## Comportement

| Build | Version |
|-------|---------|
| Commit portant le tag `vX.Y.Z` (release CI, ou build locale sur ce commit) | `X.Y.Z` |
| Tout autre commit (dev, build de marque hors tag) | `<dernière release>-alpha.<commits depuis ce tag>`, ex. `0.1.3-alpha.5` |
| `POLENTA_VERSION` défini (image Docker : pas de `.git` dans le contexte) | sa valeur (`v` initial retiré) |
| Ni git ni tag atteignable | `version` de `package.json`, figée à `0.0.0-dev` |

Cette version est celle de la barre de titre (`app:get-version`), de l'état de mise à jour, du nom
de l'installeur, de `latest.yml` et du client web.

**Limite semver** : `0.1.3-alpha.5` < `0.1.3`. Une build `-alpha` packagée qui vérifie les mises à
jour se voit donc proposer `0.1.3`. C'est sans effet sur les releases (toujours sur un tag) ; une
build de marque client (`workflow_dispatch`) doit être lancée sur un tag pour porter une version
de release.

## Critères d'acceptation

1. `pnpm package` sur un commit non tagué produit `Polenta-Setup-<tag>-alpha.<n>.exe`, avec
   `latest.yml` et le `package.json` de l'asar à cette version.
2. Sur un commit tagué `vX.Y.Z`, la version déduite est `X.Y.Z`.
3. `release.yml` sur un tag ne lit plus `package.json`. Il échoue si le tag n'est pas `vX.Y.Z`, ou
   si la version déduite diffère du tag.
4. En dev (`pnpm dev`), la barre de titre affiche `<tag>-alpha.<n>`.
5. Le client web affiche la version déduite (ou `POLENTA_VERSION` dans l'image Docker).

## Hors scope

- Pré-releases publiées (`vX.Y.Z-beta.N`) : le workflow n'accepte que `vX.Y.Z`.
- Publication automatique de l'image Docker depuis le tag.

## Design

- `apps/desktop/scripts/app-version.ts` (nouveau) : `appVersion()`, `git describe --tags --long
  --match 'v[0-9]*.[0-9]*.[0-9]*'`. Seul point de calcul, appelé au build.
- `scripts/print-version.ts` (nouveau) : l'affiche, pour `release.yml`. Le fichier est séparé, car
  `electron.vite.config.ts` est chargé en ESM, où `require.main` n'existe pas.
- `scripts/package.ts` : `extraMetadata.version` ajouté à la configuration electron-builder (le
  `package.json` packagé alimente `app.getVersion()`, `${version}` et `latest.yml`).
  `builderConfig()` n'est pas modifié : `check-gh49.ts` reste valable.
- `electron.vite.config.ts` : `define __POLENTA_VERSION__` dans le bundle main.
- `src/main/app-version.ts` (nouveau) : build packagée → `app.getVersion()` (la même valeur que
  celle comparée par electron-updater) ; dev → la constante injectée. Utilisé par `app:get-version`
  et `UpdateService`.
- Serveur web : `define __POLENTA_VERSION__` (`scripts/build-web-server.ts`). `index.ts` revient à
  `package.json` sous `tsx`. `Dockerfile.web` : `--build-arg POLENTA_VERSION`.
- `release.yml` : l'étape « Check tag matches package.json version » est remplacée par
  « Check version from tag », placée après l'installation des dépendances (elle a besoin de `tsx`).
- `apps/desktop/package.json` : `version` → `0.0.0-dev`.

Alternative rejetée : écrire la version dans `package.json` en CI (`npm pkg set`). Le dev
afficherait alors `0.0.0-dev` au lieu de `<release>-alpha.<n>`, et les builds locales packagées
n'auraient pas de version significative.
