# GH16 — Serveur MCP : tools de gestion des liens (create / list / delete)

> Issue : [#16](https://github.com/laurentolive/polenta/issues/16) — type `feature`

## Contexte

Le serveur MCP (`apps/desktop/src/mcp-server/`) permet à un agent IA de lire le schéma,
de lister et de créer en masse des exigences, tests et campagnes (`bulk_import_*`), et de
modifier le schéma (`add_*`). Il **n'a aucun tool pour les liens** (`ObjectLink`, stockés
dans `links/links.yaml` du repo produit). Un agent peut donc créer des exigences et des
tests, mais pas les relier : la traçabilité (couverture, implémentation) doit ensuite être
faite à la main dans l'UI.

Côté app, la création passe par l'IPC `requirements:link-create` →
`RequirementsService.createLink` → `RequirementsIndexService.createLink`, qui **ne valide
rien** (type, existence des objets, compatibilité `sourceRefs`/`targetRefs`, doublons).
L'UI filtre en amont les candidats (`renderer/components/system/linkUtils.ts`). Le serveur
MCP est une surface externe sans ce filtrage : la validation doit être faite côté serveur.

## Description fonctionnelle

Trois nouveaux tools MCP, dans un nouveau fichier `tools/links.tools.ts`, enregistrés dans
`mcp-server/index.ts`.

### 1. `list_links` (lecture)

Entrée :
```ts
{ objectId?: string; type?: string }
```
- Sans filtre : tous les liens de `links/links.yaml` du repo ciblé.
- `objectId` : uniquement les liens dont `sourceId` **ou** `targetId` vaut cet ID.
- `type` : uniquement les liens de ce type (`linkTypes[].name`).
- Les deux filtres se cumulent (ET).

Sortie : `{ links: ObjectLink[] }` — champs tels que stockés (`id`, `type`, `sourceId`,
`targetId`, `createdAt`, `createdBy`, et les champs optionnels présents).

Toujours relu depuis le disque (pas de cache périmé, cf. §4).

### 2. `create_links` (écriture, par lot)

Entrée :
```ts
{ entries: Array<{ type: string; sourceId: string; targetId: string }>; dryRun?: boolean }  // dryRun par défaut true
```

Même garde-fou que `bulk_import_*` : `dryRun: true` par défaut.

**Validation stricte**, par entrée, dans l'ordre ; la première règle en échec arrête la
validation de CETTE entrée seulement (les autres entrées sont validées normalement) :

1. `type` existe dans `schema.linkTypes` → sinon `LINK_TYPE_NOT_FOUND`.
2. `sourceId !== targetId` → sinon `SELF_LINK`.
3. `sourceId` et `targetId` désignent chacun un objet existant (exigence, test ou
   campagne) → sinon `OBJECT_NOT_FOUND` (en précisant lequel).
   - Recherche dans le repo ciblé ; si `--workspace` est fourni, aussi dans les repos
     composants du workspace (mécanisme à arrêter au design).
4. Compatibilité avec le type de lien : on résout pour chaque objet son `objectTypeRef`
   et la `category` de son type. L'entrée est valide si **l'un des deux sens** est
   compatible :
   - (source ∈ `sourceRefs` ET cible ∈ `targetRefs`), OU
   - (cible ∈ `sourceRefs` ET source ∈ `targetRefs`).

   Une ref contenant `::` est comparée à `objectTypeRef`, sinon à la `category` — même
   règle que `linkUtils.ts::matchesRefs`. Une liste de refs vide ou absente accepte tout.
   Sinon → `LINK_TYPE_INCOMPATIBLE`.
   Le sens fourni est **conservé tel quel** à l'écriture (pas de normalisation) :
   conformément à CLAUDE.md, le moteur de traçabilité apparie un lien de couverture
   quel que soit son sens.
5. Pas de doublon : aucun lien existant (ni aucune entrée valide **précédente du même
   lot**) avec le même `type` et la même paire d'objets, **quel que soit le sens** →
   sinon `DUPLICATE_LINK` (en citant l'`id` du lien existant s'il y en a un).

Sortie (même forme que `bulk_import_*`) :
```ts
{ dryRun: boolean,
  summary: { total, ok, failed },
  wouldCreate: Array<{ index, type, sourceId, targetId }>,   // dryRun: true uniquement
  created:     Array<{ index, id }>,                          // dryRun: false uniquement
  errors:      Array<{ index, code, reason }> }
```

- `dryRun: true` : aucune écriture disque.
- `dryRun: false` : les entrées valides sont écrites ; best-effort (une entrée en erreur
  n'empêche pas l'écriture des autres). Le fichier `links/links.yaml` est réécrit **une
  seule fois** pour tout le lot (pas un write par lien).
- Les liens créés ont `createdBy: 'mcp'` (au lieu de `'user'` côté UI) pour qu'on puisse
  les distinguer. `createdAt` = date ISO de création, `id` au format existant
  `lnk_<timestamp>_<aléa>`, unique au sein du lot.
- Création d'un lien **ne pose pas** `needsRevalidation` (comportement identique à l'UI).

### 3. `delete_links` (écriture, par lot)

Entrée :
```ts
{ ids: string[]; dryRun?: boolean }  // dryRun par défaut true
```

- Chaque `id` inexistant → erreur `LINK_NOT_FOUND` pour cet index ; les autres sont traités.
- `dryRun: true` : retourne les liens qui **seraient** supprimés (objets complets), sans
  écrire.
- `dryRun: false` : supprime les liens trouvés, une seule réécriture de
  `links/links.yaml`.

Sortie :
```ts
{ dryRun: boolean,
  summary: { total, ok, failed },
  wouldDelete: ObjectLink[],          // dryRun: true uniquement
  deleted: string[],                  // ids — dryRun: false uniquement
  errors: Array<{ index, code, reason }> }
```

### 4. Cohérence avec l'app ouverte en parallèle

Le process MCP a son propre index en mémoire (`RequirementsIndexService`). Si l'app crée
un lien après que le serveur MCP a construit son index, une écriture MCP basée sur l'index
en cache **écraserait** ce lien (réécriture complète du fichier). Les tools
`create_links` et `delete_links` doivent donc **relire `links/links.yaml` depuis le disque
juste avant de valider et d'écrire** (et `list_links` aussi, pour ne pas lister un état
périmé). L'app, elle, voit déjà les écritures MCP : son `RepoWatcherService` invalide
l'index sur tout changement sous `links/`.

### Convention d'erreur

Conforme à SPEC-MCP-SERVER §6 : les erreurs de validation par entrée sont dans `errors[]`
du résultat (pas d'exception). Un résultat où **toutes** les entrées échouent reste un
résultat normal (pas `isError`), comme `bulk_import_*`. Une erreur inattendue (FS, YAML
corrompu) remonte telle quelle.

## Critères d'acceptation

1. `list_links` sans filtre renvoie exactement le contenu de `links/links.yaml`.
2. `list_links { objectId: "SYS-0001" }` renvoie les liens où SYS-0001 est source ou cible,
   et seulement ceux-là.
3. `create_links` sans `dryRun` n'écrit rien sur disque (`links/links.yaml` inchangé,
   octet pour octet).
4. `create_links` avec un `type` absent de `linkTypes` → `LINK_TYPE_NOT_FOUND` sur
   l'entrée.
5. `create_links` avec un ID inexistant → `OBJECT_NOT_FOUND`.
6. Lien `verification` test → exigence **et** exigence → test : tous deux acceptés ; lien
   `verification` exigence → exigence : `LINK_TYPE_INCOMPATIBLE`.
7. Lien identique à un lien existant, dans le même sens ou le sens inverse :
   `DUPLICATE_LINK`. Deux entrées identiques dans un même lot : la 2ᵉ en
   `DUPLICATE_LINK`, la 1ʳᵉ acceptée.
8. `create_links { dryRun: false }` : les liens valides apparaissent dans
   `links/links.yaml` avec `createdBy: mcp`, et dans l'app ouverte (vue édition de
   l'exigence) sans redémarrage.
9. Un lien créé dans l'app **après** le démarrage du serveur MCP est toujours présent
   après un `create_links` ou `delete_links { dryRun: false }` via MCP.
10. `delete_links` avec un id inexistant → `LINK_NOT_FOUND` pour cet index, les autres
    ids sont supprimés.
11. AGENTS.md régénéré mentionne les trois tools.

## Hors scope

- Modifier un lien existant (changer son type ou ses extrémités) : supprimer + recréer.
- Ajouter la validation stricte au chemin IPC de l'UI (`requirements:link-create`) :
  l'UI garde son comportement actuel (constat préexistant, cf. SPEC-MCP-SERVER §7).
- Champs optionnels `coverageType` / `targetCommitHash` à la création.
- Liens vers des objets autres qu'exigences, tests, campagnes.
- Commit git automatique (comme les autres tools MCP, rien n'est commité).
