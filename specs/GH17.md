# GH17 — Workspace : même repo monté deux fois sur des branches d'intégration différentes

Issue : #17 (type:feature, ouverte le 2026-09-30). Spec rédigée le 2026-11-07 sur `origin/main`
`7f2b454`.

> **Statut de la spec** : rédigée sans échange direct avec l'humain. Les choix marqués
> **[Q1]…[Q6]** reposent sur les recommandations de la section « Questions ouvertes » ; si une
> recommandation est refusée, les paragraphes marqués sont à reprendre.

## 1. Besoin

Monter dans un même workspace Polenta **deux montages du même dépôt** (même URL git) épinglés sur
des versions différentes — typiquement deux branches d'intégration (`component-x@int-A` et
`component-x@int-B`) — et travailler avec les deux : ouvrir le workspace, voir et éditer les deux
copies, tracer les liens, lire la couverture, sans que les objets d'une copie écrasent ceux de
l'autre.

Deux formes d'arrivée du cas :

- **Déclaration directe** : un même `polenta-repo.yaml` déclare deux dépendances de même `url`,
  de `name` différents, de `pin` différents.
- **Diamant** : deux repos du workspace déclarent chacun la même `url` avec des `pin` différents
  (avec des `name` identiques ou différents).

Autres constats utiles relevés en lisant le code :

- `mountOverrides` est stocké dans `<workspace>/.polenta/workspace.yaml`, **non versionné**
  (`polenta-workspace.ts`) : un nom de montage choisi dans la modale est propre à la machine.
- Un `MountOverride` est indexé par `(url, pin)` : un pin SHA mis à jour (propagation T82) ne
  correspond plus à l'override, le conflit réapparaît.
- Un composant épinglé sur une **branche** n'est pas en lecture seule (HEAD non détaché) : les deux
  copies du cas d'usage sont éditables et publiables.
- La désignation d'intégration (GH106) vit dans `config/project.yaml` **de chaque branche** : deux
  `int-*` désignées chacune dans leur propre `project.yaml` sont publiables l'une et l'autre ; la
  « branche par défaut de la forge » suit la dernière désignée.
- Décision antérieure (source : `SPEC-TEMPLATES.md` §3b, T71, non datée dans le fichier) : « deux
  composants implémentant des versions différentes de la même interface passent par le mécanisme
  de diamond-conflict + `MountOverride` (chaque version montée sous un nom distinct) ». Ce mécanisme
  n'a jamais fonctionné (constat 1b) ; la présente spec le rend opérant, sans revenir sur la
  décision.

## 3. Description fonctionnelle

### 3.1 Identité d'un montage et d'un objet

- Un **montage** est identifié par son **nom de montage** (nom de dossier dans le workspace), jamais
  par son URL. Deux montages de même URL sont deux repos distincts du workspace.
- Un objet du workspace (exigence, test, campagne, issue, version, validation) est identifié par le
  couple **(montage, ID)**. L'ID seul ne suffit plus dès que deux montages contiennent le même ID.
- Hors workspace multi-montage (cas d'aujourd'hui sans doublon d'ID), rien ne change : un ID présent
  dans un seul repo se résout comme avant, aucun fichier n'est réécrit.

### 3.2 Ouverture du workspace — règle de conflit **[Q2]**

Le conflit en diamant est redéfini : il y a conflit quand **plusieurs déclarations aboutissent au
même nom de montage** (même dossier) avec un couple `(url, pin)` différent. Concrètement :

| Déclarations | Comportement |
|---|---|
| Même `url`, `name` différents (pins égaux ou non) | **Pas de conflit** : deux montages, deux dossiers clonés. C'est le cas d'usage. |
| Même `name`, même `url`, même `pin` (diamant classique partagé) | Pas de conflit : un seul montage partagé (inchangé). |
| Même `name`, même `url`, `pin` différents | **Conflit** affiché dans `DiamondConflictModal` (plus d'écrasement silencieux). |
| Même `name`, `url` différentes | **Conflit** affiché (plus d'écrasement silencieux). |

- La résolution par la modale (un nom de montage par couple `(url, pin)`) **aboutit** : après
  « Appliquer et relancer », les déclarations reçoivent des noms distincts, le workspace s'ouvre
  avec les deux montages, sans réafficher la modale.
- La modale affiche, pour chaque variante, l'URL, le pin, les repos qui la requièrent ; un nom
  vide, en double, déjà pris par un autre montage ou invalide (`isSafeMountName`) est refusé avec
  un message sous le champ.
- Le cycle de dépendance reste détecté (la détection actuelle par URL sur la chaîne d'ancêtres est
  conservée : un repo ne peut pas dépendre de lui-même, même via une autre branche).

### 3.3 Affichage des deux montages

Partout où un repo du workspace est listé ou nommé (onglet Structure, combobox Composant/Élément de
la Vue Système, panneau Version, libellé de repo des candidats de lien, pastilles de liens,
recherche, colonne ou libellé « repo » des vues transverses), deux montages de même URL sont
**distinguables** : libellé du repo suivi du nom de montage — par ex. « Contrôle moteur
(component-x-int-A) » — dès que deux montages portent le même libellé. Un repo sans homonyme garde
son libellé actuel.

### 3.4 Résolution d'un ID référencé (liens, couverture, revalidation) **[Q3]**

Un lien est stocké dans `links.yaml` d'un repo R (règle GH105, côté source inchangée). Ses
`sourceId` / `targetId` nus sont résolus **relativement à R** :

1. l'objet existe dans R → c'est lui ;
2. sinon, parmi les montages du **sous-arbre de dépendances de R** (dépendances déclarées par R,
   récursivement) contenant l'ID : un seul → c'est lui ; plusieurs → **ambigu** (§3.5) sauf
   qualificatif ;
3. sinon, parmi les autres montages du workspace : un seul → c'est lui ; plusieurs → **ambigu** ;
4. aucun → « introuvable » (pastille existante, inchangée).

Conséquence attendue : un repo intermédiaire A qui dépend de `component-x@int-A` et un repo B qui
dépend de `component-x@int-B` voient chacun leurs liens résolus sur leur propre copie, sans
qualificatif.

Cette résolution s'applique à tous les consommateurs du graphe de liens agrégé :
`WorkspaceLinksService` (onglet Liens, candidats, `DUPLICATE_LINK`), matrice de traçabilité et
couverture (`hasCoverage`, contrôle `hasCoverageLink` des transitions), revalidation T172
(propagation de `needsRevalidation` aux seuls éléments liés résolus), analyse d'impact, graphe de
données de la vue Suivi (`graph.service.ts`), navigation par lien vers un autre repo.

Les runs et campagnes restent rattachés au repo qui les stocke : le dernier run d'un test est celui
de **son** montage (plus de fusion `latestRunMap` par ID entre repos).

### 3.5 Lien ambigu et qualificatif de montage **[Q4]**

- **Création** : si l'objet choisi comme pair d'un lien a un ID présent dans plusieurs montages et
  que la règle §3.4 ne le désigne pas seul depuis le repo de stockage, Polenta enregistre dans le
  lien un **qualificatif** désignant le montage visé. Le qualificatif est exprimé **par le chemin des
  noms de dépendance déclarés dans les `polenta-repo.yaml`** à partir du repo de stockage (ex.
  `component-x-int-A`, ou `sub-a/component-x` à travers un repo intermédiaire) — jamais par un nom de
  montage choisi dans la modale, qui n'est pas versionné. Le champ n'est écrit que lorsqu'il est
  nécessaire (lien non ambigu : `links.yaml` identique à aujourd'hui). Son nom exact relève du
  design.
- **Candidats** : la liste des candidats propose les deux objets, chacun avec le libellé distinctif
  de son montage (§3.3) ; le doublon `DUPLICATE_LINK` se juge sur le couple (montage, ID).
- **Lecture d'un lien ambigu sans qualificatif** (lien antérieur, YAML écrit à la main, montage
  ajouté après coup) : le lien est affiché avec une pastille « ambigu » listant les montages
  candidats, sur l'objet qui le stocke ; il **n'est compté dans aucune couverture** et ne propage pas
  de revalidation ; il reste supprimable. Pas de réécriture automatique.
- **Qualificatif invalide** (dépendance renommée ou retirée) : traité comme « introuvable ».

### 3.6 Écriture

- Une écriture (édition, création, suppression, statut) vise toujours le repo du montage
  sélectionné : modifier `SW-0001` dans `component-x-int-A` ne touche pas le fichier de
  `component-x-int-B`.
- L'allocation d'un nouvel ID reste calculée par repo (fichiers + pierres tombales) : les deux
  copies peuvent allouer le même nouvel ID — comportement inhérent aux branches git, hors scope
  (§5).
- Publication multi-repo (GH38) : chaque montage est publié sur sa propre branche et propage son pin
  à ses propres parents ; deux montages de même URL ne sont jamais fusionnés entre eux par Polenta.

### 3.7 Serveur MCP et graphe de données **[Q5]**

- Graphe de données (vue Suivi, contrat v1) : chaque objet porte déjà `repo` ; les liens gagnent le
  repo résolu de leur source et de leur cible (ajout de champs, contrat v1 compatible), et la
  couverture est calculée par (montage, ID). Un lien ambigu y figure avec un repo résolu absent.
- Tools MCP qui reçoivent un ID sur le périmètre workspace (lecture et écriture d'objets, liens) :
  un ID présent dans plusieurs montages sans précision du repo est refusé avec un code d'erreur
  explicite listant les montages ; le tool accepte la précision du repo / montage. Les tools qui
  listent des liens renvoient le repo résolu de chaque pair.

## 4. Critères d'acceptation

Ouverture (sprint « bug » autonome) :

1. Un `polenta-repo.yaml` déclarant deux dépendances de même `url`, `name` différents, `pin`
   `int-A` et `int-B` : le workspace s'ouvre **sans modale**, deux dossiers sont clonés, chacun
   checkouté sur sa branche ; l'onglet Structure montre deux lignes distinguables (§3.3).
2. Diamant avec même `name` et pins différents : la modale s'affiche ; après saisie de deux noms
   distincts et « Appliquer et relancer », le workspace s'ouvre avec les deux montages, la modale
   ne réapparaît pas, y compris à la réouverture du workspace.
3. Même `name`, pins différents (ou URL différentes) : plus aucun cas où une déclaration est ignorée
   sans conflit affiché.
4. Diamant même `name`, même `url`, même `pin` : un seul montage, aucune modale (non-régression).
5. Tests unitaires de `buildTree` couvrant : même URL / noms différents, même nom / pins
   différents sans puis avec override, même nom / URL différentes, diamant partagé, cycle.

Agrégation (fixture : `component-x` monté deux fois, `SW-0001` dans les deux, un test `TC-0001`
couvrant `SW-0001` dans `int-A` seulement) :

6. La matrice de traçabilité affiche deux lignes `SW-0001`, chacune avec son montage ; celle de
   `int-A` est couverte par `TC-0001` (avec le dernier run de `int-A`), celle de `int-B` est
   `not_covered`.
7. L'onglet Liens de `SW-0001` dans `int-B` n'affiche pas le lien de `TC-0001` ; celui de `int-A`
   l'affiche.
8. Faire quitter l'approbation à `SW-0001@int-A` pose `needsRevalidation` sur `TC-0001@int-A` et
   sur aucun objet de `int-B`.
9. Vue Suivi : le graphe contient deux objets `SW-0001` (repos distincts), la couverture de chacun
   conforme au critère 6, chaque lien porte le repo résolu de ses deux extrémités.
10. Plus aucun avertissement « ID … présent dans plusieurs repos — … ignoré » : aucun objet n'est
    écarté de l'agrégation.

Liens ambigus (depuis le repo produit qui déclare les deux montages) :

11. Créer un lien `SYS-0001` → `SW-0001` : les deux candidats sont proposés, distingués ; le lien
    créé vers `int-B` ne couvre / n'affecte que `SW-0001@int-B` après rechargement.
12. Lier `SYS-0001` aux deux `SW-0001` (un lien par montage) n'est pas refusé en `DUPLICATE_LINK`.
13. Un lien sans qualificatif vers `SW-0001` écrit à la main dans le `links.yaml` du produit
    s'affiche « ambigu » avec les deux montages, n'entre dans aucune couverture et se supprime.
14. Un workspace sans ID dupliqué : `links.yaml` produits octet pour octet identiques à aujourd'hui
    pour les mêmes actions (pas de qualificatif écrit) ; la suite existante reste verte.

MCP :

15. Un tool de lecture d'objet sur `SW-0001` sans repo précisé renvoie l'erreur d'ambiguïté listant
    les deux montages ; avec le montage précisé, il renvoie l'objet de ce montage.

## 5. Hors scope

- **Allocation d'IDs coordonnée entre les deux copies** (constat 3) : deux branches d'un même dépôt
  peuvent allouer le même ID à des objets différents ; c'est inhérent à git et se règle au merge
  entre ces branches, comme aujourd'hui entre deux branches `dev-*`. **[Q6]**
- **Merge / comparaison entre les deux montages** (diff `int-A` ↔ `int-B`, report d'un objet d'une
  copie vers l'autre) : ticket à part si besoin.
- **Dédoublonnage** de deux montages de même `url` et même `pin` sous des noms différents : ils
  restent deux montages (comportement actuel), traités par cette spec comme tout autre double
  montage.
- **Clé des `MountOverride`** : reste `(url, pin)` ; un pin SHA mis à jour fait réapparaître la
  modale (cas des branches d'intégration non concerné : leur pin est le nom de branche).
- Versionner les `mountOverrides` (`workspace.yaml` reste local à la machine).
- Unicité des `prefix` entre repos différents du workspace (règle 10 inchangée : par schéma).
- Matrice de conformité des interfaces (`InterfaceComplianceService`, recherche du nœud
  d'interface « par nom ») quand l'interface est elle-même montée deux fois : vérifier au design
  qu'elle ne mélange pas les deux montages ; une évolution fonctionnelle de la matrice serait un
  ticket à part.
- Versions / validations (milestone D) dont le périmètre référencerait un composant monté deux
  fois : vérifier au design qu'aucune ne s'appuie sur l'URL comme identité ; pas de nouveau
  comportement.
- Client web : même comportement attendu que le desktop (mêmes services main) ; pas d'écran
  spécifique.

## 6. Indicateurs

Aucun nouvel indicateur. La couverture et `needsRevalidation` sont des indicateurs déjà calculés par
Polenta pour ses propres fonctions (GH79) ; seule leur clé change (montage, ID).

## 7. Questions ouvertes

Chaque question porte la recommandation retenue pour rédiger la spec, et l'alternative.

1. **[Q1] Périmètre du ticket.** Recommandation : un seul ticket GH17, livré en sprints ordonnés —
   S1 ouverture (critères 1-5, livrable seul, corrige le bug de l'issue) ; S2 identité (montage, ID)
   dans l'agrégation (6-10) ; S3 liens ambigus et qualificatif (11-14) ; S4 MCP (15).
   Alternative : sortir le point 1 (bug de résolution `mountAs`) dans une issue `type:bug` à part,
   livrable rapidement, et garder GH17 pour l'agrégation.
2. **[Q2] Deux `name` différents sur la même URL = pas de conflit.** Recommandation : considérer
   des noms différents comme un choix explicite de double montage, sans modale ; conflit seulement
   quand deux déclarations visent le même nom de montage. Alternative : garder une modale (ou un
   bandeau de confirmation) dès que la même URL apparaît avec deux pins, même sous des noms
   différents, en corrigeant seulement la prise en compte des overrides.
3. **[Q3] Résolution d'un ID nu relative au repo de stockage** (repo → ses dépendances → reste du
   workspace). Recommandation : oui, elle résout sans qualificatif le cas diamant (chaque parent
   voit sa copie). Alternative : toute référence à un ID présent dans plusieurs montages est
   ambiguë et exige un qualificatif, quel que soit le repo de stockage (plus simple à expliquer,
   mais les liens existants des repos intermédiaires deviennent ambigus).
4. **[Q4] Lien depuis le produit vers un objet présent dans les deux montages.** Recommandation :
   qualificatif optionnel dans le lien, exprimé en noms de dépendance des `polenta-repo.yaml`
   (versionnés), écrit seulement si nécessaire ; lien ambigu existant affiché « ambigu », hors
   couverture. Alternative : refuser la création d'un lien ambigu (`AMBIGUOUS_TARGET`) sans
   changer le format de `links.yaml` — le produit ne peut alors pas lier une exigence aux deux
   copies.
5. **[Q5] MCP dans ce ticket.** Recommandation : oui (sprint S4), refus explicite des IDs ambigus et
   précision du repo, pour qu'un agent IA ne modifie pas la mauvaise copie. Alternative : MCP hors
   scope, ticket de suivi ; le MCP garde le comportement « premier repo gagnant » d'ici là.
6. **[Q6] Allocation d'IDs entre les deux copies.** Recommandation : hors scope (inhérent aux
   branches). Alternative : calculer le prochain ID sur le maximum des montages de même URL présents
   dans le workspace, pour réduire les collisions au merge (ne protège que la machine locale).
