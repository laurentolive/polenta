# GH170 — Page blanche quelques secondes au retour sur un onglet (page Tests)

Type : bug — correctif « option B » (atténuation, sans garder les onglets inactifs montés).

## Constat

Client, PC bas de gamme, app desktop, projet `PH2`, page **Tests** (Vue Système,
`/product?category=test`) : après avoir ouvert un lien dans un nouvel onglet puis être revenu
sur l'onglet de départ, la page reste blanche quelques secondes puis se réaffiche — à chaque retour.

## Root cause

Les onglets ne gardent pas les vues montées : activer un onglet = `navigate()` vers son URL
(`TabsContext.activateTab`), la route `/product` est remontée, `SystemView` repart de son état
initial. Trois états étaient re-synchronisés **dans des `useEffect`**, donc après un premier rendu
committé et peint :

1. **Arbre du type** (`SystemViewContext`, `rootKey`) — l'onglet ouvert sur une fiche `/req/…`
   fait basculer le contexte (qui survit au changement de route) sur un type d'exigence ; au
   retour, le type redevient « test » mais `rootKey` n'était réaligné que dans un effet.
2. **Préférences de colonnes** (`SystemView`, `prefsAppliedKey`) — repart à `null` au remontage,
   appliqué dans un effet même quand les prefs sont en cache.
3. **Mode de vue** (`viewMode`) — repart à `'excel'` ; le mode stocké (localStorage) et la Vue
   Édition encore ouverte (`editingNodeId`, dans le contexte) n'étaient restaurés que dans des effets.

Tant que (1) ou (2) n'est pas aligné, `viewReady` est faux → `ViewLoading` (zone vide) est peinte,
puis le rendu complet du tableau suit ; sur un PC lent ce second rendu prend plusieurs secondes,
d'où le blanc. En Vue Édition, la fiche (`['object', …]`, `gcTime: 0`) était en plus relue à
chaque remontage (« Chargement… »). Enfin, une vue quittée plus de 5 min (gcTime par défaut)
perdait tout son cache.

## Correctif

- `SystemViewContext` : synchronisation arbre/`rootKey` faite **pendant le rendu** (mise à jour
  d'état en rendu, rejouée par React avant tout commit) au lieu d'un effet.
- `SystemView` : prefs de colonnes appliquées pendant le rendu (`appliedPrefs` remplace
  `prefsAppliedKey`) ; `viewMode` initialisé dès le premier rendu (`'edit'` si `editingNodeId`,
  sinon mode stocké, sinon `'excel'`).
- Fiche en Vue Édition : `gcTime: 0` → cache conservé + `refetchOnMount: 'always'` (affichage
  immédiat, relue en arrière-plan ; EditView adopte le refetch sans écraser une saisie).
- `QueryClient` : `gcTime` 30 min (au lieu de 5).

### Itération 2 — lag au changement d'onglet (retour de validation)

Retour humain sur la 1re version : plus de blanc, mais un gel net au changement d'onglet, même
sur PC puissant. Mesuré (Playwright + Electron sur une copie de PH2, 233 tests dans le type,
onglet Tests ↔ onglet Exigences, profil CPU via CDP) :

| Build | Retour sur l'onglet Tests |
|---|---|
| `main` | 220–270 ms (dont la zone vide) |
| GH170 v1 | 425–600 ms, sans zone vide |
| GH170 v2 | 220–305 ms, sans zone vide |

Cause de la régression v1 : Tests ↔ Exigences reste sur la même route `/product`, la vue n'est
pas remontée. Sur `main` le tableau était démonté (zone vide) puis remonté une fois l'état
stabilisé ; en v1 il restait monté, d'où (a) une réconciliation lignes d'exigences → lignes de
tests et (b) 3 re-rendus complets juste après, déclenchés par les refetchs en arrière-plan : les
callbacks passés au tableau (dépendants d'un `useMutation`, ou inline) changeaient à chaque rendu
et invalidaient la mémoïsation de toutes les cellules (`InlineCell`, `NameCell`…).

Correctifs v2 :
- `key={typeKey}` sur `ExcelView` / `WordView` : un changement de type remonte proprement le tableau.
- `useStableCallback` (nouveau, `hooks/useStableCallback.ts`) pour tous les callbacks passés aux
  deux vues ; `ExcelView` et `WordView` mémoïsés → un re-rendu de `SystemView` sans changement de
  données ne refait plus le tableau (vérifié : un seul rendu du tableau par retour).
- `setBackHistory([])` au montage ne crée plus de nouvel état s'il est déjà vide.

Coût restant (~250 ms ici, plusieurs fois plus sur un PC bas de gamme) : un rendu complet du
tableau (React ≈ moitié, mise en page du navigateur ≈ moitié). Le supprimer demande soit de garder
les onglets inactifs montés (option A), soit un rendu progressif / virtualisé des lignes.

Hors périmètre : garder les onglets inactifs montés (option A) — à envisager si les plaintes
persistent (perte du défilement / sélection au changement d'onglet notamment).

## Comment vérifier

Idéalement sur un PC lent (ou DevTools → Performance → CPU throttling 6×), projet avec beaucoup de tests :

1. Page Tests en Vue Tableau : ouvrir un lien d'un test dans un nouvel onglet (fiche exigence),
   revenir sur l'onglet Tests → pas de zone blanche : l'ancien onglet reste affiché le temps du
   rendu puis le tableau apparaît directement, avec les bonnes colonnes.
2. Idem en Vue Document.
3. Vue Édition d'un test, lien « ouvrir dans un nouvel onglet », retour → la fiche du test
   réapparaît directement en Vue Édition, sans passage par le tableau ni « Chargement… ».
4. Dans l'autre onglet, modifier ce même test (`/test/…`), revenir → la Vue Édition affiche la
   valeur modifiée (refetch au montage).
5. Non-régression : changer de type dans la combobox, modifier les colonnes visibles puis changer
   de vue et revenir (prefs conservées), undo/redo de l'arbre après sauvegarde.

Vérifs automatiques : `pnpm typecheck` OK, `pnpm test` (desktop) 779/779.
