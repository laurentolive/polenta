# GH18 — Serveur MCP : tools de gestion des indicateurs (dashboards et requêtes de la vue Suivi)

> Issue : [#18](https://github.com/laurentolive/polenta/issues/18) — type `feature`

## Contexte

Le serveur MCP (`apps/desktop/src/mcp-server/`) permet à un agent IA de lire le schéma, de
créer exigences/tests/campagnes (`bulk_import_*`), de modifier le schéma (`add_*`) et de gérer
les liens (`*_links`, GH16). Il **n'a aucun tool pour la vue Suivi** : un agent ne peut ni
lire les données du projet par requête, ni créer une requête sauvegardée, ni ajouter un
indicateur (widget) à un dashboard.

Côté app, la vue Suivi repose sur (cf. `SPEC-DASHBOARDS.md`) :
- `QueryEngineService` — AlaSQL sur un dataset en mémoire (`requirements`, `tests`, `links`),
  mode builder (allowlist de champs) ou SQL (garde-fou lecture seule) ;
- `SavedQueriesService` — requêtes partagées `queries/QUERY-xxxx.yaml` ou privées
  (`savedQueries` dans `.{username}.pref`) ;
- `DashboardsService` — dashboards partagés `dashboards/DASHBOARD-xxxx.yaml` (widgets
  embarqués) ou privés (`dashboards` dans `.{username}.pref`), règles de dépendance
  widget ↔ requête (§3.1).

Aucun de ces services n'est construit dans le container MCP aujourd'hui
(`SPEC-MCP-SERVER.md` §3). Le serveur MCP n'a pas non plus de notion d'utilisateur, alors que
le scope privé est rangé par utilisateur.

## Description fonctionnelle

### 1. Nouvel argument `--user` (scope privé)

| Paramètre | CLI | Variable d'env | Obligatoire |
|---|---|---|---|
| Utilisateur Polenta | `--user <username>` | `POLENTA_USER` | Non |

- Même `username` que celui de l'app (celui qui nomme le fichier `.{username}.pref`).
- Valeur invalide (vide, contient `/`, `\`, `..` ou un caractère interdit dans un nom de
  fichier) → `process.exit(1)`, message sur stderr (même règle que `--repo`).
- **Sans `--user`** : seuls les objets **partagés** sont visibles et modifiables. Toute
  écriture en `scope: private` ou sur un objet privé → erreur `PRIVATE_SCOPE_UNAVAILABLE`.
  Les listes ne renvoient que le partagé.
- **Avec `--user`** : partagé + privé de cet utilisateur, comme dans l'app.
- `.mcp.json` généré par l'app **n'est pas modifié** : l'argument se pose à la main (ou par
  variable d'env) dans la configuration du client MCP.

### 2. Tools de lecture

#### `list_queries`
Entrée : `{ scope?: 'shared' | 'private' }`.
Sortie : `{ queries: SavedQuery[] }` — tous les champs stockés (`id`, `title`, `mode`,
`builderConfig` | `sqlText`, `scope`, `createdBy`, `createdAt`), triés par `createdAt`
(ordre de `SavedQueriesService.list`). L'historique de requêtes n'est jamais exposé.

#### `list_dashboards`
Entrée : `{ scope?: 'shared' | 'private' }`.
Sortie : `{ dashboards: Dashboard[] }` — dashboards complets, widgets **dans l'ordre
`widgetOrder`**. Pour chaque widget, le titre de sa requête est ajouté (`queryTitle`, ou
`null` si la requête est introuvable).
**Ne déclenche pas** le seed des dashboards pré-configurés (`DashboardSeedService`) — ce
seed reste propre à l'app.

#### `run_query`
Entrée :
```ts
{ queryId?: string
  definition?: { mode: 'builder' | 'sql'; sqlText?: string; builderConfig?: BuilderConfig }
  offset?: number; limit?: number }
```
- Exactement un de `queryId` / `definition` → sinon `INVALID_INPUT`.
- `queryId` inconnu (ou privé sans `--user`) → `QUERY_NOT_FOUND`.
- Exécute via `QueryEngineService.execute` (mêmes garde-fous que l'app : lecture seule,
  allowlist builder), sur le périmètre workspace si `--workspace` est fourni.
- Sortie : `{ sql, columns, rows, total, offset, limit }` — `sql` = SQL finale exécutée
  (utile pour un builder), `rows` paginées avec `paginate()` / `LIST_RESULT_LIMIT`
  (`SPEC-MCP-SERVER.md` §8).
- N'écrit rien, pas même l'historique de requêtes.

### 3. Tools d'écriture

Règles communes à tous les tools d'écriture :
- `dryRun` **par défaut `true`** (même garde-fou que `bulk_import_*` / `create_links`) :
  validation complète (exécution de la requête comprise) et aperçu de l'objet résultant,
  sans écriture disque.
- **Un objet par appel** (pas de lot).
- **Branche en lecture seule** (branche courante `''` ou `prj-*`, même règle que
  `DashboardSeedService`) → `READONLY_BRANCH`, y compris en `dryRun`.
- Relecture disque à chaque appel (les services lisent déjà YAML/`.pref` à chaque appel —
  aucun cache à invalider).
- `createdBy: 'mcp'` sur les requêtes et dashboards créés.
- IDs : ceux des services existants (`QUERY-xxxx`/`DASHBOARD-xxxx` via
  `config/counters.yaml` pour le partagé, `local-<ts>-<rand>` pour le privé, id de widget
  généré par `DashboardsService`). En `dryRun`, l'id partagé est prévisualisé sans
  consommer le compteur (`peekNextCounterId`).
- Erreur de validation → `errorToolResult` avec un message préfixé par le code :
  `[CODE] raison` (convention `SPEC-MCP-SERVER.md` §6). Erreur inattendue → remonte telle
  quelle.

#### Validation d'une définition de requête (`create_query`, `update_query`)
Dans l'ordre, la première règle en échec arrête :
1. `mode: 'sql'` ⇒ `sqlText` non vide et pas de `builderConfig` ; `mode: 'builder'` ⇒
   `builderConfig` présent et pas de `sqlText` → sinon `INVALID_QUERY_DEFINITION`.
2. SQL : garde-fou lecture seule de `query-engine.service.ts` (`FORBIDDEN_SQL`) →
   `FORBIDDEN_SQL`.
3. Builder : `objectTypeRef` (+ `component`) résolvable dans le schéma du composant ;
   chaque `condition.field` dans l'allowlist du type ; `operator` parmi les valeurs de
   `BuilderCondition` ; `groupBy` dans l'allowlist → sinon `INVALID_BUILDER_CONFIG` (en
   citant le champ fautif).
4. **Exécution** de la requête → une erreur AlaSQL donne `QUERY_EXECUTION_ERROR` (message
   AlaSQL cité). Le résultat (colonnes, nombre de lignes, 5 premières lignes) est renvoyé
   dans la sortie, en `dryRun` comme en écriture.

#### `create_query`
Entrée : `{ title, mode, sqlText?, builderConfig?, scope?: 'shared' | 'private' (défaut 'shared'), dryRun? }`
- Validation de la définition (ci-dessus).
- `title` non vide ; pas d'autre requête **du même scope visible** avec le même titre
  (comparaison insensible à la casse, espaces de bord ignorés) → `DUPLICATE_TITLE` (en
  citant l'id existant).
- Sortie : `{ dryRun, query, preview: { columns, total, sample } }`.

#### `update_query`
Entrée : `{ id, title?, mode?, sqlText?, builderConfig?, dryRun? }`
- `id` introuvable → `QUERY_NOT_FOUND`.
- La définition résultante (existant + champs fournis ; changer `mode` exige de fournir la
  nouvelle définition complète) est revalidée et réexécutée.
- Titre modifié → contrôle `DUPLICATE_TITLE` (hors la requête elle-même).
- Les widgets qui utilisent la requête sont revérifiés : si une colonne de leur
  `fieldMapping` disparaît du nouveau résultat, la mise à jour **n'est pas bloquée** mais
  la sortie liste ces widgets dans `warnings` (`WIDGET_MAPPING_BROKEN`).
- Le scope ne se change **pas** par ce tool (hors scope, cf. plus bas).
- Sortie : `{ dryRun, query, preview, warnings }`.

#### `delete_query`
Entrée : `{ id, dryRun? }`
- `id` introuvable → `QUERY_NOT_FOUND`.
- Utilisée par au moins un widget visible → `QUERY_IN_USE`, avec la liste des widgets
  (`dashboardId`, `dashboardTitle`, `widgetId`, `widgetTitle`) —
  `DashboardsService.findDependentWidgets`, même règle que l'app (§3.1 de
  `SPEC-DASHBOARDS.md`, y compris sa limite connue sur les dashboards privés d'un autre
  utilisateur).
- Sortie : `{ dryRun, deleted: SavedQuery }` (en `dryRun`, la requête qui serait supprimée).

#### `create_dashboard`
Entrée : `{ title, scope?: 'shared' | 'private' (défaut 'shared'), dryRun? }`
- `title` non vide, `DUPLICATE_TITLE` (même règle que les requêtes, entre dashboards).
- Créé vide (widgets ajoutés ensuite par `add_widget`).
- Sortie : `{ dryRun, dashboard }`.

#### `update_dashboard`
Entrée : `{ id, title, dryRun? }` — renommage uniquement.
`DASHBOARD_NOT_FOUND`, `DUPLICATE_TITLE`. Sortie : `{ dryRun, dashboard }`.

#### `delete_dashboard`
Entrée : `{ id, dryRun? }` — `DASHBOARD_NOT_FOUND`. Supprime le dashboard et ses widgets
embarqués (les requêtes restent). Sortie : `{ dryRun, deleted: Dashboard }`.

#### `add_widget`
Entrée :
```ts
{ dashboardId: string; title: string; queryId: string
  type: 'bar' | 'pie' | 'line' | 'kpi' | 'table'
  fieldMapping: WidgetFieldMapping
  size?: 'sm' | 'md' | 'lg'        // défaut 'md'
  position?: number                 // index dans widgetOrder, défaut = à la fin
  dryRun?: boolean }
```
Validation, dans l'ordre :
1. `dashboardId` introuvable → `DASHBOARD_NOT_FOUND`.
2. `queryId` introuvable → `QUERY_NOT_FOUND`.
3. Dashboard partagé + requête privée → `PRIVATE_QUERY_IN_SHARED_DASHBOARD` (règle §3.1).
4. `type` / `size` hors valeurs → `INVALID_INPUT`.
5. Mapping requis selon le type → sinon `MISSING_MAPPING` :
   - `bar`, `line`, `pie` : `category` et `measure` ;
   - `kpi` : `measure` ;
   - `table` : `columns` optionnel (absent = toutes les colonnes).
   `series` n'est accepté que pour `bar`/`line`, `stacked` que pour `bar` avec `series`,
   `columns` que pour `table` → sinon `INVALID_MAPPING`.
6. La requête est exécutée ; chaque colonne citée dans `fieldMapping` (`category`,
   `measure`, `series`, `columns[]`) doit exister dans les colonnes du résultat →
   `UNKNOWN_COLUMN` (en citant les colonnes disponibles). **Exception** : résultat vide
   (0 ligne ⇒ colonnes non déterminables, `inferColumns`) → contrôle sauté, `warnings`
   contient `COLUMNS_UNVERIFIED`.
7. Même `queryId` + même `type` + même `fieldMapping` qu'un widget existant du dashboard →
   `DUPLICATE_WIDGET` (en citant son id).

La cohérence type ↔ forme du résultat n'est **pas** contrôlée au-delà de l'existence des
colonnes (`SPEC-DASHBOARDS.md` §4 : le type n'est jamais contraint par le résultat).
Sortie : `{ dryRun, dashboard, widget, preview: { columns, total }, warnings }`.

#### `update_widget`
Entrée : `{ dashboardId, widgetId, title?, queryId?, type?, fieldMapping?, size?, dryRun? }`
- `DASHBOARD_NOT_FOUND`, `WIDGET_NOT_FOUND`.
- Le widget résultant (existant + champs fournis ; `fieldMapping` fourni **remplace**
  l'ancien) repasse les règles 2 à 7 d'`add_widget` (la règle 7 hors le widget lui-même).
- Sortie : `{ dryRun, dashboard, widget, preview, warnings }`.

#### `delete_widget`
Entrée : `{ dashboardId, widgetId, dryRun? }` — `DASHBOARD_NOT_FOUND`, `WIDGET_NOT_FOUND`.
Retire aussi l'id de `widgetOrder`. Sortie : `{ dryRun, dashboard }`.

#### `reorder_widgets`
Entrée : `{ dashboardId, order: string[], dryRun? }`
- `order` doit être une permutation exacte des ids de widgets du dashboard (ni manquant,
  ni inconnu, ni doublon) → sinon `INVALID_ORDER`.
- Sortie : `{ dryRun, dashboard }`.

### 4. Rafraîchissement de l'app ouverte en parallèle

Aujourd'hui, `useLiveFileSync` (renderer) n'invalide rien pour `queries/`, `dashboards/`
ni `.{username}.pref` : une écriture MCP n'apparaîtrait qu'au prochain rechargement.
À ajouter :
- changement sous `queries/` → invalider `['queries', repoPath, *]` ;
- changement sous `dashboards/` → invalider `['dashboards', repoPath, *]` ;
- changement de `.{username}.pref` → invalider `['queries', …]`, `['dashboards', …]`,
  `['queries-order', …]`, `['dashboards-order', …]` du repo.

Ordre du panneau latéral : un objet créé via MCP n'est pas ajouté à
`queriesOrder`/`dashboardsOrder` ; il apparaît en fin de section (comportement existant de
`ReorderableSidebarSection` pour un id inconnu).

### 5. Container MCP

`createMcpContainer` construit en plus `TraceabilityService`, `QueryEngineService`,
`SavedQueriesService`, `DashboardsService` (mêmes classes que `main/container.ts`) —
`DashboardSeedService` reste exclu. Le détail des dépendances est à arrêter au design.

## Critères d'acceptation

1. `list_queries` / `list_dashboards` sans `--user` ne renvoient que les objets partagés ;
   avec `--user alice`, ils renvoient aussi le privé de `.alice.pref`, et rien d'un autre
   utilisateur.
2. `create_query { scope: 'private' }` sans `--user` → `PRIVATE_SCOPE_UNAVAILABLE`.
3. `run_query { definition: { mode: 'sql', sqlText: 'SELECT status, COUNT(*) AS n FROM requirements GROUP BY status' } }`
   renvoie les mêmes lignes que la vue Requêtes de l'app sur le même projet.
4. `run_query` / `create_query` avec `DELETE FROM requirements` → `FORBIDDEN_SQL` ; aucune
   écriture disque.
5. `create_query` avec une SQL invalide (`SELECT FROM`) → `QUERY_EXECUTION_ERROR`.
6. Tout tool d'écriture sans `dryRun` : aucun fichier modifié (`queries/`, `dashboards/`,
   `.{user}.pref`, `config/counters.yaml` inchangés octet pour octet).
7. `create_query { dryRun: false }` crée `queries/QUERY-xxxx.yaml` avec `createdBy: mcp` ;
   une 2ᵉ création avec le même titre (casse différente) → `DUPLICATE_TITLE`.
8. `delete_query` d'une requête utilisée par un widget → `QUERY_IN_USE` avec la liste des
   widgets ; la requête n'est pas supprimée.
9. `add_widget` sur un dashboard partagé avec une requête privée →
   `PRIVATE_QUERY_IN_SHARED_DASHBOARD`.
10. `add_widget { type: 'bar', fieldMapping: { category: 'inexistant', measure: 'n' } }` →
    `UNKNOWN_COLUMN` avec la liste des colonnes disponibles ; sur une requête au résultat
    vide, le widget est accepté avec l'avertissement `COLUMNS_UNVERIFIED`.
11. `add_widget` identique à un widget existant (même requête, type, mapping) →
    `DUPLICATE_WIDGET`.
12. `reorder_widgets` avec un id manquant ou inconnu → `INVALID_ORDER`.
13. Sur une branche `prj-*`, tout tool d'écriture → `READONLY_BRANCH`.
14. App ouverte sur la vue Suivi : une requête, un dashboard ou un widget créé, modifié ou
    supprimé via MCP apparaît dans le panneau latéral et dans la vue Dashboard **sans
    rechargement manuel** (≤ 2 s).
15. `list_dashboards` sur un projet sans aucun dashboard ne crée pas le dashboard **Status**
    (pas de seed).
16. AGENTS.md régénéré mentionne les nouveaux tools et l'argument `--user`.

## Hors scope

- Changement de scope (privé ↔ partagé) d'une requête ou d'un dashboard via MCP :
  reste dans l'UI (changement d'id, remappage des widgets, `renameInOrder`).
- Réordonner les sections du panneau latéral (`queriesOrder` / `dashboardsOrder`).
- Historique de requêtes (lecture comme écriture).
- Export Excel d'un résultat.
- Seed des dashboards pré-configurés.
- Injection automatique de `--user` dans `.mcp.json` par l'app.
- Opérations par lot.
- Commit git automatique (comme les autres tools MCP).
