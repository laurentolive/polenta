# GH191 — Conformité : revue de conformité aux jalons, champs d'exécution et vue Conformité (spec globale)

> **Spec globale (épique).** Ce ticket cadre l'ensemble et le découpe en tickets
> d'implémentation (§10). Il n'implémente rien. Chaque ticket de lot aura sa propre spec
> `specs/GH{N}.md`, qui détaille et peut amender ce cadrage.

## Contexte

La qualité suit aujourd'hui la conformité dans la **vue Tests**. Pour gérer le retour des
campagnes, on y a ajouté des colonnes, et l'idée d'ajouter des statuts qualité (approbation /
dérogation / rejet) sur le test est à l'étude. Cela mélange trois choses qui n'ont ni le même
cycle de vie, ni la même cardinalité :

| Quoi | Cycle de vie | Cardinalité | Où aujourd'hui |
|---|---|---|---|
| La **procédure** de test | brouillon → review → approuvé | 1 par test | `tests/<ID>.yaml` |
| Les **exécutions** | `pending` → PASS / FAIL / BLOCKED / INCOMPLETE | N par test : instances (T179) × campagnes × reports (GH64) | `campaigns/`, `test-runs/<TEST>/<RUN>.yaml` |
| La **décision qualité** | ébauche → signée | 1 par **objet × jalon** | inexistant |

Une décision qualité ne qualifie pas la procédure. Elle dit : « au jalon DVT, l'exigence SYS-0012
est acceptée par dérogation malgré le FAIL de TEST-0042, à condition que… ». Mise sur le test,
elle :
- ne distingue pas les instances ni les exécutions ;
- n'est pas rattachée au jalon et « fuit » d'un jalon au suivant ;
- est mal ancrée : un test qui couvre quatre exigences peut être dérogé pour l'une et rejeté pour
  une autre ;
- transforme la vue des procédures en tableau de bord qualité.

La qualité veut en outre voir la décision **jusqu'au niveau des exigences**.

### État du code (vérifié sur `origin/main` @ 6998973)

- `TestRun` (`packages/types/src/test.ts`) n'a que des champs fixes : `result`, `executedAt`,
  `executedBy`, `duration`, `equipmentUsed`, `stepResults[] {order, result, comment, executedAt}`,
  `notes`, `origin`, `campaignEntry`, `requirementId`. Un run est **immuable** : un nouvel essai ou
  un réimport crée un nouveau run (SPEC-TESTS §3.1, §4.5).
- Pièces jointes : décision existante (SPEC-TESTS §7). Pas de stockage dans Polenta : on colle des
  liens (OneDrive) dans les `richtext` `comment` / `notes`. Ces liens ne sont **pas structurés** :
  impossible d'en faire une colonne, un champ obligatoire ou un export.
- `ObjectCategory = 'requirement' | 'test' | 'campaign'` (`packages/types/src/schema.ts`).
- `SchemaFieldType` : `text`, `textarea`, `number`, `enum`, `multi_enum`, `boolean`, `date`,
  `datetime`, `richtext`, `user`, `drawio`. Pas de type lien, pas d'obligation conditionnelle.
- Baselines = tags git `baseline/<nom>` posés « à un jalon » (SPEC-FORKS-BRANCHES-BASELINES §5).
  Aucun objet ne porte la notion de jalon. `Review.milestoneTag` est prévu mais **non implémenté**
  (SPEC-REVIEWS §2.6).
- Graphe de données (#74) : `runs: GraphTestRun[]` expose `result`, `executedAt`, `executedBy`,
  `duration`, `origin`, `campaignEntry`, `requirementId`, mais ni `notes` ni `stepResults`.
- Panneau ⚙️ (`FieldConfigModal`) : **un** réglage par vue × type × utilisateur (`.pref`), avec le
  défaut d'équipe `polenta-config` (GH45) fusionné en dessous (SPEC-SYSTEM-VIEW §Configuration des
  champs). Pas de configurations nommées.

## Décisions de cadrage (échanges du 2026-10-28)

1. Le statut qualité **n'est pas un champ** de l'exigence ni du test. C'est une **décision humaine,
   datée, propre à un jalon**, enregistrée dans un objet dédié : la **revue de conformité**.
2. La qualité statue sur des **exigences et/ou des tests**, avec cinq décisions : Conforme / Non
   conforme / Dérogation / Non vérifié / Obsolète (liste configurable, §3.3).
3. Pour statuer, elle consulte **l'historique de toutes les exécutions**, avec leurs champs : verdicts,
   commentaires du technicien, rapports…
4. **Ce qu'on affiche pour décider est configurable comme le ⚙️ de la vue Excel**, pour
   l'exigence, le test et les exécutions, et dépend du cas. On réutilise donc le mécanisme ⚙️ et on
   lui ajoute des **vues enregistrées nommées**. Pas de mise en page figée dans le schéma.
5. Les exécutions reçoivent des **champs personnalisés**, définis par le type de test.
6. **Pas de pièces jointes.** Un nouveau type de champ générique **`link`** `{label, url}` les
   remplace.
7. Une **vue Conformité** dédiée porte le processus. Les vues Exigences et Tests n'en montrent que le
   reflet, en lecture seule.

## 1. Le processus : revue de conformité au jalon

### 1.1 Entrants

| # | Entrant | Source |
|---|---|---|
| E1 | Périmètre du jalon : exigences et/ou tests concernés, sur une baseline | sélection à la création de la revue (§3.4) |
| E2 | Couverture exigence ↔ test, instances par exigence (T179) | liens de couverture |
| E3 | **Toutes les exécutions** de chaque test et instance : verdict global et d'étape, testeur, date, durée, équipement, notes, commentaires, champs d'exécution (§2), campagne, paramètres, version du test exécutée (`testSnapshot`), reports (GH64), entrées retirées (GH73) | `test-runs/`, `campaigns/` |
| E4 | Rapports et preuves externes | champs `link` (§2.2) |
| E5 | Décisions du jalon précédent, surtout les dérogations et leurs conditions | revue de conformité précédente (§3.6) |
| E6 | Changements depuis le jalon précédent : objets modifiés, `needsRevalidation` (T172) | existant |

### 1.2 Activité

Pour chaque objet du périmètre, la qualité consulte l'historique des exécutions (E3, E4), désigne
celles qui **font foi** (preuves), puis saisit une décision avec sa justification. Pour une
dérogation, elle saisit aussi les conditions et l'échéance.

### 1.3 Sortants

| # | Sortant | Consommé par |
|---|---|---|
| S1 | **Registre de conformité du jalon** : décision, justification et preuves par objet, auteur, date | audit, dossier de jalon |
| S2 | Dérogations ouvertes avec conditions et échéance | **E5 du jalon suivant** |
| S3 | Non-conformités | développement, campagnes suivantes |
| S4 | Revue **signée** (figée) et registre exporté | direction de projet, client, audit |

La décision de passage du jalon (go / go conditionnel / no-go) est un **champ de la revue**,
configuré par le projet (§3.3). Polenta ne la calcule pas.

## 2. Champs personnalisés des exécutions

### 2.1 Trois niveaux de saisie

| Niveau | Défini sur | Exemple | Saisi |
|---|---|---|---|
| Campagne | type de campagne, `fields` (**existe**) | banc d'essai, lot de cellules, version firmware | une fois par campagne |
| Exécution | **type de test**, nouveau `runFields: SchemaField[]` | n° de rapport, température ambiante, lien vers le rapport | à chaque exécution |
| Étape | **type de test**, nouveau `stepFields: SchemaField[]` | valeur mesurée, lien vers une capture | à chaque étape exécutée |

**Règle de conception** (à reprendre dans l'aide du schéma) : une information commune à toute la
campagne est un champ de campagne ; une information propre à chaque passage est un champ
d'exécution.

```yaml
objectTypes:
  - name: essai-normatif
    category: test
    prefix: TN
    fields: [...]                       # la procédure (inchangé)
    runFields:
      - name: reportNumber
        label: N° de rapport
        type: text
        requiredWhen: { result: [PASS, FAIL] }
      - name: ambientTemp
        label: Température ambiante (°C)
        type: number
      - name: report
        label: Rapport d'essai
        type: link
        multiple: true
        requiredWhen: { result: [FAIL] }
    stepFields:
      - name: measured
        label: Valeur mesurée
        type: number
```

Stockage : un bloc `fields: {}` sur le run et sur chaque `StepResult`. Ce bloc est absent tant
qu'il est vide, et les runs existants ne sont pas migrés.

```yaml
# test-runs/TN-0004/RUN-20261028-001.yaml
id: RUN-20261028-001
testCaseId: TN-0004
campaignEntry: { campaignId: CAMP-0005, entryId: TN-0004-1 }
result: FAIL
fields:
  reportNumber: RE-2026-118
  ambientTemp: 23.5
  report:
    - { label: RE-2026-118, url: "https://ged.example.com/docs/RE-2026-118" }
stepResults:
  - order: 3
    result: FAIL
    comment: <p>coupure tardive</p>
    fields: { measured: 13.1 }
```

### 2.2 Nouveau type de champ `link` (générique)

- Valeur : `{ label?, url }`. Si `label` est vide, on affiche l'URL. Le nouvel attribut
  `multiple: true` permet une liste.
- **Disponible pour tous les champs** : exigence, test, campagne, `runFields`, `stepFields`, champs
  de la revue et des décisions (§3.3).
- Schémas d'URL acceptés : `http://`, `https://`, `file://`, chemin réseau `\\serveur\partage\…`.
  Tout autre schéma est refusé à la saisie.
- Ouverture : l'application par défaut du poste (`shell.openExternal`). Hors `http(s)`, on demande
  une confirmation. Client web : seuls les liens `http(s)` sont cliquables, les autres proposent
  « Copier ». Polenta **ne vérifie pas** que le lien répond.
- Affichage : libellé cliquable avec l'URL en infobulle (vues Excel / Word / Édition, grille
  d'exécutions). Export xlsx : hyperlien natif.
- Classeur d'exécution (GH36) : une cellule contient `libellé | URL`, un lien par ligne.
- Pérennité : la preuve dépend du système externe. Le client doit garantir des URL stables dans sa
  GED. À écrire dans la doc utilisateur.
- SPEC-TESTS §7 (« Pièces jointes ») est amendée : le champ `link` devient la voie **structurée**.
  Coller un lien dans un `richtext` reste possible.

### 2.3 Obligation conditionnelle — `requiredWhen` (générique)

Nouvel attribut de `SchemaField` : `requiredWhen: { <champ>: [valeurs…] }`. Le champ est
obligatoire quand le champ nommé a une des valeurs listées.

- Sur `runFields`, le champ de référence est le pseudo-champ `result` (verdict global). Sur
  `stepFields`, c'est `result` de l'étape.
- Sur les champs de décision (§3.3), c'est un autre champ de décision (ex. `decision`).
- Contrôle : à l'enregistrement de l'exécution (page d'exécution, import Excel) et de la décision.
  Un champ manquant **bloque l'enregistrement**, avec un message qui nomme le champ.
- `required: true` reste l'obligation inconditionnelle. Les deux attributs peuvent coexister.

### 2.4 Règles

1. **Immuabilité** inchangée : les champs d'exécution sont écrits à la création du run. Pour
   corriger, on crée un nouveau run (SPEC-TESTS §3.1). Pas d'historique GH77 sur les runs.
2. **Évolution du schéma** :
   - si un champ est retiré, ses valeurs restent dans les runs et s'affichent en lecture seule,
     marquées « hors schéma » ;
   - si une valeur d'enum disparaît, on affiche la valeur brute avec un ⚠ ;
   - un champ ajouté ne concerne que les exécutions suivantes ;
   - **on ne réécrit jamais un run**, même pour les renommages de champ (GH82) : à documenter comme
     limite.
3. **Repo** : les `runFields` d'un test de composant sont ceux du schéma du composant (le run vit
   dans le repo du test).
4. **Saisie** : page d'exécution d'une entrée de campagne, champs d'exécution sous le verdict
   global, champs d'étape sur chaque ligne d'étape.
5. **Classeur Excel (GH36)** :
   - une colonne jaune par `runField` sur les lignes d'instance, et par `stepField` sur les lignes
     d'étape ;
   - si la campagne mélange plusieurs types de test, on prend l'**union** des colonnes, et les
     cellules sans objet sont grisées et verrouillées ;
   - la validation à l'import applique `requiredWhen` et le format `link`.
6. **Graphe de données (#74)** : `GraphTestRun` gagne `fields`, `notes` et `stepResults` (avec
   leurs `fields`). C'est une évolution mineure du contrat, documentée dans `polenta.d.ts`. Les
   colonnes calculées du projet (« température max », « FAIL sans n° de rapport »…) s'appuient
   dessus.

## 3. La revue de conformité

### 3.1 Nouvelle catégorie d'objet `conformity`

`ObjectCategory` gagne `conformity`. Un type de cette catégorie a un `prefix` (ex. `CONF`), des
`fields` (niveau revue), des `statuses`, et un nouveau `entryFields` (niveau décision, §3.3).
Comme pour les campagnes, les objets de cette catégorie **ne participent pas à la couverture**.

Stockage : `conformity/<ID>.yaml`, IDs déduits du disque et des pierres tombales (GH20), comme les
autres objets.

```yaml
# conformity/CONF-0002.yaml
id: CONF-0002
objectTypeRef: root::revue-conformite
title: Revue de conformité DVT
status: open                        # statuts du type ; le statut isApproval = signé
baselineRef: baseline/v0.9-dvt      # état évalué (§3.5)
fields:
  jalon: DVT                        # champ du type (enum déclaré par le projet)
  gate: go_conditionnel
entries:
  - objectId: SYS-0012              # exigence ou test
    requirementId: ~                # si entrée par instance (question Q2)
    evidence:                       # exécutions qui font foi
      - RUN-20261014-003
    fields:                         # entryFields
      decision: derogation
      justification: <p>…</p>
      conditions: <p>re-test après révision C du driver</p>
      dueJalon: PVT
      proof: [{ label: Note de dérogation ND-12, url: "https://…" }]
    carriedFrom: { conformityId: CONF-0001, objectId: SYS-0012 }
    decidedBy: jdupont              # posé par l'application
    decidedAt: 2026-10-28T10:12:00Z
history: …                          # GH77 : statut et champs suivis de la revue
```

### 3.2 Pourquoi pas un champ sur l'exigence ou le test

Une décision dépend du jalon. Un champ unique sur l'objet serait écrasé à chaque jalon, et on
perdrait la réponse à « qu'avait-on décidé en DVT ? ». Le reflet sur l'objet est une **lecture**
des revues (§6).

### 3.3 Configuration du type de revue

```yaml
  - name: revue-conformite
    label: Revue de conformité
    category: conformity
    prefix: CONF
    appliesTo: [requirement, test]          # catégories ou types précis acceptés au périmètre
    terminalDecision: obsolete              # valeur pré-remplie pour un objet en statut isTerminal
    fields:
      - { name: jalon, label: Jalon, type: enum, values: [EVT, DVT, PVT, MP], required: true }
      - { name: gate, label: Décision de passage, type: enum, values: [go, go_conditionnel, no_go] }
    entryFields:
      - name: decision
        label: Décision
        type: enum
        values: [conforme, non_conforme, derogation, non_verifie, obsolete]
        required: true
      - name: justification
        type: richtext
        requiredWhen: { decision: [non_conforme, derogation] }
      - name: conditions
        type: richtext
        requiredWhen: { decision: [derogation] }
      - name: dueJalon
        type: enum
        values: [EVT, DVT, PVT, MP]
        requiredWhen: { decision: [derogation] }
    statuses:
      - { name: open, label: Ouverte }
      - { name: signed, label: Signée, isApproval: true }
      - { name: cancelled, label: Annulée, isTerminal: true }
```

- **Les valeurs de décision sont configurables.** Polenta ne leur prête aucune sémantique, sauf
  `terminalDecision` (pré-remplissage) et le dialogue de reprise (§3.6), où l'utilisateur choisit
  quelles valeurs reprendre.
- **Le jalon est un simple champ de la revue** : pas de nouveau référentiel. Voir la question Q1.
- La configuration se fait dans l'éditeur `/schema`, avec la même UI que les `fields`, pour
  `entryFields`, `runFields` et `stepFields`.

### 3.4 Création et périmètre

- On crée la revue depuis la vue Conformité : titre, champs de la revue, baseline évaluée, puis
  périmètre.
- Le périmètre se choisit avec un sélecteur sur le modèle de celui des campagnes (GH176) :
  composant, type, filtres, arbre, limité aux `appliesTo`.
- On peut ajouter ou retirer des objets tant que la revue n'est pas signée. Un objet retiré qui avait
  une décision est conservé à part, avec `removedAt`, comme les `removedRuns` de GH73.
- Un objet du périmètre en statut `isTerminal` est pré-rempli avec `terminalDecision`. La qualité
  peut changer cette décision.

### 3.5 Baseline évaluée et exécutions

- `baselineRef` fixe **l'état évalué** des définitions : contenu des exigences et tests et liens
  de couverture, lus au tag. Ce tag est facultatif. Sans tag, on lit l'état courant, et l'écran le
  signale par un bandeau.
- Les **exécutions** sont des faits immuables : elles sont lues **à l'état courant**, toutes
  campagnes confondues. Celles postérieures à la baseline sont signalées par un badge, sans être
  filtrées. Voir la question Q3.

### 3.6 Reprise du jalon précédent

« Reprendre une revue… » : on choisit une revue signée, puis les valeurs de décision à reprendre
(par défaut : `derogation`, `non_conforme`). Les entrées correspondantes sont ajoutées au périmètre
avec `carriedFrom`, et l'ancienne décision et ses conditions s'affichent dans le panneau
(« Décision J-1 »). La nouvelle décision **reste à saisir** : elle n'est pas recopiée.

### 3.7 Décider, signer, figer

- Saisir ou modifier une décision écrit `decidedBy` / `decidedAt` : identité courante, comme
  `executedBy`.
- **Signature** : passage au statut `isApproval`.
  - Refusée si une entrée du périmètre n'a pas de décision, ou si un champ obligatoire
    (`required` / `requiredWhen`) manque. Le message liste les objets concernés.
  - Qui a signé et quand : historique GH77 du statut.
- Une revue signée est **figée** : plus de décision, de périmètre ni de preuve modifiable. Pour
  corriger, on crée une nouvelle revue (éventuellement reprise de celle-ci).
- La signature à plusieurs (quorum, via les reviews existantes) est **hors socle** : voir Q4.

## 4. Grille d'historique des exécutions (composant réutilisable)

Une grille, avec une ligne par exécution, utilisée à trois endroits :
- l'onglet « Exécutions » de l'éditeur de test ;
- l'onglet « Exécutions » de l'éditeur d'exigence ;
- le panneau de la vue Conformité (§5).

**Lignes**

- **Pour un test** : tous ses runs (`test-runs/<TEST>/`), campagne ou non, plus les entrées de
  campagne `pending` sans run (verdict « en attente »).
- **Pour une exigence** : les runs des tests qui la couvrent, avec la règle de T179 (un run avec
  `requirementId` ne compte que pour cette exigence ; sans `requirementId`, il compte pour toutes
  les exigences liées).
- Une ligne dont l'entrée de campagne a été retirée (GH73) est marquée « entrée retirée ». Elle
  n'est pas masquée.
- Ordre par défaut : `executedAt` décroissant. Tri par colonne.

**Colonnes, au choix dans ⚙️**

- **Exécution** : verdict, date, testeur, durée, origine, notes, équipement utilisé, `runFields`
  (union des types présents).
- **Campagne** : ID, titre, statut, baseline, champs de la campagne.
- **Entrée** : `entryId`, exigence de l'instance, paramètres saisis et résolus, version du test
  exécutée (`testSnapshot.version`), report (`carriedFrom`).
- **Étapes** : une sous-ligne dépliable par étape, avec verdict, commentaire et `stepFields`.

Le défaut d'équipe vient de `polenta-config`, comme les vues. Clé `fieldVisibility` dédiée à la
grille, par type de test.

## 5. La vue Conformité

Nouvel espace, au même niveau qu'Exigences, Tests et Campagnes.

1. **Liste des revues** : titre, jalon, baseline, statut, avancement (N décidés / M), nombre de
   décisions par valeur. Avancement et comptes servent à l'écran de saisie, donc ils sont calculés
   dans Polenta (§8).
2. **Revue ouverte**, en trois zones :
   - **Périmètre** : grille de type vue Excel, une ligne par entrée. Le ⚙️ propose :
     - les champs de l'objet (selon son type) ;
     - les colonnes calculées du projet (GH70 / GH126) ;
     - les `entryFields`, **éditables dans la grille**, ce qui permet de statuer en masse sur les
       cas simples.

     Filtres par décision : « à statuer », chaque valeur, « reprise J-1 ».
   - **Exécutions** de l'objet sélectionné : la grille du §4, avec une case « preuve » par ligne
     (`evidence`).
   - **Détail** de l'objet : son ⚙️ comme l'onglet Édition, la décision J-1 si l'objet a été repris,
     le formulaire des `entryFields`. Pour un test : version exécutée ou version courante, au choix
     (question Q5).
3. **Barre d'actions** : Reprendre une revue…, Ajouter / retirer au périmètre, Signer, Exporter.
4. **Export du registre** (xlsx et impression) : une ligne par entrée, avec les colonnes visibles,
   les preuves (ID de run, verdict, date) et l'en-tête de la revue (champs, statut, signataire et
   date de signature).

### 5.1 Vues enregistrées nommées du ⚙️ (évolution générique)

Le ⚙️ garde aujourd'hui **un** réglage par vue et par type. On ajoute des **vues enregistrées
nommées** (ex. « Revue sécurité batterie », « Analyse d'un FAIL ») :

- elles mémorisent les réglages ⚙️ de l'écran courant. Pour la vue Conformité, ce sont les trois
  zones à la fois ;
- elles sont **personnelles** (`.pref`) ou **d'équipe** (`polenta-config`, GH45) ;
- elles se choisissent dans une liste déroulante près du ⚙️ (Enregistrer sous…, Renommer,
  Supprimer) ;
- elles sont disponibles aussi dans la vue Excel / Word des exigences et des tests : le mécanisme
  n'est pas propre à la conformité ;
- elles dépendent de #139 (« Réinitialiser » vers le défaut d'équipe), à traiter avant ou avec.

## 6. Reflet dans les vues Exigences et Tests

- **Onglet « Décisions qualité »** dans l'éditeur, en lecture seule : une ligne par revue qui
  contient l'objet, avec revue, jalon, statut de la revue, décision, justification, preuves et lien
  vers la revue. Ce sont des données brutes, affichées par Polenta.
- **Colonne « Décision au jalon »** dans les vues Excel / Word : c'est une **colonne calculée du
  projet** (GH70), pas du code Polenta (§8). Elle est livrée comme modèle de requête de départ, avec
  un paramètre « revue choisie à l'affichage » (GH93) ou « dernière revue signée ». Le graphe expose
  les revues pour cela (§7).

## 7. Graphe de données et MCP

- Graphe (#74) : nouvelle collection `conformity` (revues, entrées, `fields`, preuves,

- MCP : lecture des revues et des runs avec leurs `fields`. Pas d'écriture de décision par le MCP
  dans le socle : une décision qualité est une décision humaine. Voir Q6.

## 8. Indicateurs : décision Polenta / côté projet (GH79)

| Indicateur | Sert une fonction de Polenta ? | Décision |
|---|---|---|
| Avancement d'une revue (N décidés / M), comptes par décision | oui : liste des revues, contrôle de signature | **Polenta** |

## 9. Cas limites

- Un objet du périmètre est supprimé physiquement (pierre tombale) : l'entrée reste, et son ID
  s'affiche « supprimé ».
- Un objet change de type ou de composant : l'entrée suit son ID.
- Un test d'un composant est évalué dans une revue du repo produit : les runs sont lus dans le repo
  du composant, comme dans la traçabilité.
- Un run de preuve n'existe plus (repo réécrit, « Garder les deux » GH37) : la preuve s'affiche
  « introuvable » et n'est pas retirée.
- Une revue reprise d'une revue non signée est **refusée** : on ne reprend qu'une revue signée.
- Plusieurs revues ouvertes pour le même jalon : c'est autorisé (revues par domaine, par exemple).
  La colonne projet choisit la revue à lire.
- Conflit de merge sur `conformity/<ID>.yaml` : fusion par entrée, sur le modèle des campagnes
  (GH37). À détailler dans le ticket de lot.
- Le ⚙️ d'une grille d'exécutions mélange plusieurs types de test : on prend l'union des
  `runFields`, et les cellules sans objet restent vides.
