# GH193 — Gestion du changement : objet change, analyse d'impact intégrée, versions de composant (spec globale)

> **Spec globale (épique, milestone « D — Gestion du changement »).** Ce ticket cadre l'ensemble et
> le découpe en tickets d'implémentation (§12). Il n'implémente rien. Chaque lot aura sa propre spec
> `specs/GH{N}.md`, qui détaille et peut amender ce cadrage.

## Contexte

Un composant du produit passe à une nouvelle version pour **deux raisons** :

| Cause | Spec modifiée ? | Exemple |
|---|---|---|
| **Évolution** | oui : des exigences et/ou des tests changent | nouveau mode Turbo |
| **Non-conformité** | souvent non (correction de bug), parfois le test (test faux) | surcharge de courant au démarrage corrigée en FW 1.2.4 |

Dans les deux cas, la modification a des **impacts que l'outil doit lister** : exigences et tests
touchés, tests à rejouer, preuves obtenues sur l'ancienne version, campagnes, autres composants. Un
correctif sans changement de spec a quand même des impacts. Il faut aussi suivre le changement
jusqu'à sa clôture.

### État du code (vérifié sur `origin/main` @ 0b1b824)

- **Trois flux d'analyse d'impact** existent (SPEC-TRACEABILITY §4) :
  - §4.1–4.5 : `getImpactReport`, sur un élément unique à l'édition, avec `ImpactAcknowledgement` ;
  - §4.6 : **entre deux baselines**, persisté dans `impact-analyses/<id>.yaml`, figé à la création ;
    statut par élément impacté (8 valeurs, dont `impact_a_tester`, `modification_verifiee`…),
    indicateur de complétude, génération de campagne. Les bornes sont **uniquement des
    baselines** ;
  - §4.7 : **modifications locales vs HEAD**, live, jamais persisté.

  Aucun de ces flux n'est rattaché à un **objet qu'on pilote** : il n'y a ni cause, ni description, ni
  cycle de vie, ni lien vers ce qui a déclenché le changement ou vers la version qui le livre.
- `needsRevalidation` (T172) est posé sur les éléments liés quand un élément quitte l'approbation,
  et levé depuis l'analyse d'impact (T173).
- « A déjà été approuvé » se déduit de l'historique du statut (`history.status`, GH77). Repli :
  `version > 1`, puisque la version s'incrémente quand un élément quitte l'approbation
  (`requirements.service.ts`, GH164 pour les tests).
- Le cycle de vie des objets se configure par `statuses` (`isApproval`, `isTerminal`). Il n'y a
  **aucune contrainte de transition** : tout passage d'un statut à un autre est permis.
- Les composants Polenta (nœuds, repos de composant) n'ont pas de notion de **version produit**.

## Décisions de cadrage (échanges du 2026-10-28)

1. Un nouvel objet **change**, avec sa vue et sa liste dans le panneau latéral. **L'analyse
   d'impact se fait dans le change.**
2. Les **types** de change (ex. évolution, non-conformité) sont **définis dans le schéma** par
   l'utilisateur. On ne crée pas d'objet « FIX » dédié.
3. Un change porte une description, la liste des **éléments à modifier** (exigences **et tests** ;
   aucune exigence pour une non-conformité produit) et la liste des **éléments impactés**. Ces deux
   listes pilotent l'analyse d'impact comme aujourd'hui.
4. Un change de non-conformité pointe vers son **origine** : exécutions en échec, décision de
   conformité (#191).
5. On crée un change **sur de l'existant** (entre deux baselines **ou deux commits**) ou comme
   **demande de changement**.
6. **Rattachement des modifications** : rien n'est exigé tant que l'élément n'a jamais été approuvé,
   pour ne pas alourdir les débuts de projet. Dès qu'un élément **déjà approuvé** est modifié, le
   rattachement est rigoureux : change actif, sinon **change implicite** créé sans nom.
7. Le change est **stocké dans le repo qu'il change**. S'il touche plusieurs repos, on crée un
   change par repo, reliés entre eux, et **une campagne par repo**.
8. Le change **crée et alimente une campagne** avec les tests identifiés à exécuter.
9. Le change porte la **version de composant** dans laquelle il est intégré.
10. **Cycle de vie** par défaut proposé, modifiable. **Contraintes de transition configurables
    dans le schéma, toujours facultatives et retirables** : elles sont souvent mal comprises et
    frustrantes. C'est un mécanisme générique.
11. Une contrainte possible pour clore un change : **les éléments modifiés et impactés doivent être
    de nouveau approuvés**.

## 1. L'objet change

### 1.1 Catégorie et types

`ObjectCategory` gagne `change`. Le projet déclare un ou plusieurs types dans cette catégorie, avec
son préfixe, ses `fields` et ses `statuses` : par exemple `evolution` (EVO) et `non-conformite`
(NC), ou un seul type `changement` (CHG) avec un champ « cause ». Polenta ne prête **aucune
sémantique** aux types : la mécanique (listes, analyse, campagne, version) est la même pour tous.

Stockage : `changes/<ID>.yaml` dans le repo changé. IDs déduits du disque et des pierres tombales
(GH20). Les objets de cette catégorie ne participent pas à la couverture.

```yaml
# changes/NC-0004.yaml   (repo du composant motor-control)
id: NC-0004
objectTypeRef: motor-control::non-conformite
title: Surcharge courant au démarrage
status: analyse
fields:                              # définis par le projet
  description: <p>Pic à 13,1 A au démarrage à froid…</p>
  bug: { label: BUG-482, url: "https://jira.example.com/BUG-482" }   # type link (#191)
component: motor-control            # composant concerné (§1.2)
mode: request                        # request (demande) | range (sur l'existant)
range: ~                             # { from, to } pour mode range (§2.1)
toModify: []                         # éléments à modifier : aucun ici (correctif produit)
impacted:                            # éléments impactés, avec statut d'impact (§3.3)
  - { id: SW-0042, status: impact_a_tester, comment: ~ , source: declared }
  - { id: TEST-0007, status: impact_a_tester, source: computed }
origin:                              # §1.3
  runs: [RUN-20261014-003]
  decisions: [{ conformityId: CONF-0002, objectId: SYS-0012 }]   # identité d'une décision (#191 §0)
integratedIn: MC-1.2.4               # version de composant (§6)
campaigns: [CAMP-0009]               # campagnes créées / alimentées (§5)
history: …                           # GH77
```

Les liens vers les changes des autres repos (§4) passent par `links/links.yaml`.

### 1.2 Composant concerné et les deux listes

**Composant concerné** (`component`) : le nœud du schéma que le change fait évoluer.
- Il est **déduit du repo** quand le repo ne porte qu'un composant.
- Il est **obligatoire** quand le repo porte plusieurs composants locaux (nœuds sans `url`, T129) :
  le repo seul ne dit pas lequel est concerné.
- Il désigne la version de composant que le change produira (§6), et donne le **périmètre
  d'impact par défaut**. Si les deux listes sont vides (correctif produit non encore précisé),
  l'analyse part de **toutes les exigences du composant**. C'est large mais sûr. Les listes
  resserrent ensuite le périmètre.

- **Éléments à modifier** (`toModify`) : exigences et tests qu'on **prévoit** de changer.
  - Vide pour une non-conformité purement produit.
  - Un test faux est une non-conformité avec le test dans cette liste.
  - Les éléments **réellement** modifiés et rattachés au change (§2) s'y ajoutent automatiquement,
    marqués « modifié ».
- **Éléments impactés** (`impacted`) :
  - éléments **déclarés** par l'utilisateur : touchés sans être modifiés. Pour un correctif, ce sont
    les exigences que le bug concerne ;
  - plus les éléments **calculés** par l'analyse d'impact (§3).

  Chaque élément porte un statut d'impact.

### 1.3 Origine

`origin.runs` et `origin.decisions`. Un change créé depuis un run en échec ou depuis une décision
de conformité (§2.1) les pré-remplit. En retour, le run et la décision affichent « traité par
NC-0004 » avec le statut du change. La revue de conformité suivante (#191) voit qu'une dérogation
est **levée** quand son change est clos.

## 2. Création et rattachement des modifications

### 2.1 Créer un change

Depuis le panneau latéral de la vue Changements (« Nouveau change ») :

| Mode | Usage | Contenu initial |
|---|---|---|
| **Demande de changement** (`request`) | prospectif : on va modifier | type, titre, champs ; listes vides ou pré-remplies |
| **Sur l'existant** (`range`) | rétrospectif : documenter ce qui a déjà été modifié | bornes `from` / `to` = **baselines ou commits** (extension de §4.6, limité aujourd'hui aux baselines) ; éléments modifiés de la plage → `toModify` |

Raccourcis pré-remplis :
- depuis une **exécution en échec** (page d'exécution, grille d'historique #191) ;
- depuis une **sélection de FAIL** ;
- depuis une **décision de conformité** Non conforme ou Dérogation (#191) ;
- depuis l'**éditeur d'une exigence ou d'un test** (« Créer un change »).

Le pré-remplissage porte le type proposé, `origin`, et les exigences de l'instance ou les exigences
couvertes dans `impacted` (source `declared`).

### 2.2 Qui doit être rattaché

Un élément est **officiel** s'il a déjà été approuvé une fois (§État du code). La règle :

| Élément modifié | Rattachement à un change |
|---|---|
| jamais approuvé (brouillon de début de projet) | **non requis**, publication libre |
| officiel (approuvé, ou repassé en brouillon après approbation) | **requis** |

La règle se règle par la préférence projet `preferences.changeTracking` :
- `officialOnly` (défaut) ;
- `always` ;
- `off` (aucun rattachement, aucun change implicite).

### 2.3 Change actif et attribution des commits

- Un **change actif** se choisit dans la barre d'état ou le panneau Version, par repo. C'est le
  contexte de travail.
- À **Publier**, si le commit contient des modifications d'éléments officiels :
  - **avec un change actif** : le commit porte la ligne finale `Change: <ID>` et les éléments
    modifiés rejoignent `toModify` (« modifié ») ;
  - **sans change actif** : Polenta propose de choisir un change, d'en créer un, ou de continuer
    sans choisir. Dans ce dernier cas, la modification va au **change implicite** du repo (§2.4).
- Les modifications d'éléments non officiels ne sont pas attribuées. Une ligne `Change:` est quand
  même écrite s'il y a un change actif : elle ne coûte rien.
- L'attribution repose sur la ligne finale du commit : lisible dans `git log`, et elle survit au
  merge.
- **Régularisation** : depuis un change, « Rattacher des commits… » attribue après coup des commits
  sans ligne `Change:`. L'attribution est enregistrée dans le change, car l'historique git n'est
  jamais réécrit.

### 2.4 Change implicite

- Il est **créé automatiquement** à la première publication non rattachée d'éléments officiels.
  Un seul change implicite est ouvert par repo, et les publications suivantes non rattachées s'y
  ajoutent.
- Il **n'a pas de nom donné par l'utilisateur** : `implicit: true`, titre généré « Modifications
  non rattachées — depuis le <date> ». Il a le premier type déclaré, ou un type désigné par
  `preferences.implicitChangeType`.
- Il est mis en évidence dans la liste (« à qualifier »). Actions possibles :
  - **Nommer**, ce qui le convertit en change ordinaire (titre, type, champs) ;
  - ou **Répartir** : rattacher ses commits à d'autres changes, puis le supprimer s'il est vide.
- Il a la même analyse d'impact que les autres changes (§3).
- L'analyse des **modifications locales non publiées** (§4.7) reste telle quelle. Elle affiche en
  plus le change actif qui recevra ces modifications.

## 3. L'analyse d'impact dans le change

### 3.1 Calcul

- **Point de départ** : éléments à modifier (prévus et modifiés) + éléments impactés déclarés. Si
  les deux sont vides : toutes les exigences du composant concerné (§1.2).
- **Arbres** : mêmes arbres qu'en §4.6 (`buildImpactTreesFromSnapshot`), montant et descendant,
  graphe complet, couverture dans les deux sens. Les nœuds atteints s'ajoutent à `impacted` avec
  la source `computed`.
- **Impacts supplémentaires** listés :
  - **campagnes** en cours qui incluent les tests impactés ;
  - **exécutions** des tests impactés obtenues sur une version antérieure du composant, quand la
    configuration testée est connue (#191, `testedConfig`) ;
  - **décisions de conformité** de revues ouvertes qui s'appuient sur ces exécutions ;
  - **dérogations** ouvertes sur les exigences impactées ;
  - **changes liés** des autres repos (§4).

### 3.2 Live tant que le change est ouvert, figé à la clôture

- Contrairement à §4.6 (figé à la création), l'analyse d'un change est **recalculée tant que le
  change n'est pas dans un statut terminal**, car les listes évoluent. Un élément calculé qui sort
  de l'analyse **garde sa ligne** s'il a un statut autre que `impact_non_verifie`, marquée « n'est
  plus atteint ».
- Au passage dans un statut `isTerminal`, l'analyse est **figée** et enregistrée dans le change :
  c'est un instantané reproductible, comme en §4.6.

### 3.3 Statuts d'impact

On réutilise les 8 valeurs de §4.6 (`impact_non_verifie`, `pas_d_impact_reel`, `impact_a_tester`,
`impact_teste`, `modification_a_faire`, `modification_faite`, `modification_a_tester`,
`modification_verifiee`), avec commentaire, la même règle de complétude, et la levée de
`needsRevalidation` depuis l'arbre (§4.8).

### 3.4 Devenir des flux existants

- **§4.6 (entre baselines)** : remplacé par un change `range`. Les fichiers `impact-analyses/`
  existants restent **lisibles** en lecture seule dans la vue Changements (« analyses
  antérieures »), et peuvent être convertis en change sur action de l'utilisateur. Pas de migration
  automatique.
- **§4.7 (local)** et **liste « Impact à vérifier » (§4.8)** : inchangés.
- **§4.1–4.5 (élément unique)** : inchangé. Le lot L3 précisera s'il doit rejoindre le change.

## 4. Changes sur plusieurs repos

- On crée **un change par composant touché**, dans le repo de ce composant, avec le préfixe du type
  de ce repo (préfixes uniques sur le projet). Pour des repos séparés (submodules), c'est un change
  par repo. Plusieurs composants locaux d'un même repo ont chacun leur change, puisque `component`
  est unique (§1.2).
- Ils sont reliés par un type de lien dédié, `change-coordination`, déclaré par défaut dans
  `linkTypes` et inter-repos (GH105). L'un d'eux, en général celui du repo produit, est le
  **change pilote**.
- **Création** : depuis le change pilote, « Étendre au composant… » crée le change du composant
  pré-rempli (type équivalent s'il existe, titre, champs communs, origine) et le lien.
- **Vue d'ensemble** : la vue Changements affiche le dossier complet (pilote et changes liés, statut
  de chacun).
- **Campagnes** : **une campagne par repo**, créée et alimentée par le change de ce repo (§5).
- **Analyse** : chaque change calcule l'analyse de son repo. Les arbres traversent les repos comme
  en §4.7, et un élément d'un autre repo est attribué au change de ce repo s'il existe, sinon il est
  signalé « repo sans change ».

## 5. Campagnes issues d'un change

- **Créer la campagne** : on collecte les tests des éléments en `impact_a_tester` /
  `modification_a_tester`, on résout les exigences vers les tests qui les couvrent
  (`generateTestPlan`, SPEC-TRACEABILITY §5), et on pré-remplit `/campaign/new` comme aujourd'hui.
  La campagne créée est **liée au change** (`campaigns`) et porte la référence du change.
- **Alimenter** : quand de nouveaux tests passent « à tester », le change **propose** de les ajouter
  à sa campagne ouverte (bandeau « N tests à ajouter »). Il ne les ajoute jamais seul.
- La campagne est créée dans le **repo du change** (§4), avec composant et `objectTypeRef` complets
  (leçon de #146).

## 6. Versions de composant

### 6.1 Version produit d'un composant

Le composant Polenta est l'**élément de configuration** du produit. Une version produit est un
objet du repo du composant. Il suit le composant quand celui-ci est réutilisé dans un autre produit.

```yaml
# versions/MC-1.2.4.yaml   (repo motor-control)
id: MC-1.2.4
title: Firmware moteur 1.2.4
component: motor-control           # nœud du schéma (obligatoire si le repo porte plusieurs composants)
source: { label: fw-motor@v1.2.4, url: "https://git.example.com/fw-motor/-/tags/v1.2.4" }
implements: baseline/mc-2.1        # tag du repo du composant (voir ci-dessous)
basedOn: MC-1.2.3
status: released                   # figée
```

- **Composant local** (nœud sans `url`, T129) : ses versions vivent dans le repo qui le porte,
  distinguées par `component`.
- **`implements`** désigne un tag **du repo du composant**, lu directement dans git. Ce n'est pas
  forcément une baseline du workspace. Aujourd'hui, `BaselineService.list` ne retient comme
  baseline un tag du repo racine que s'il existe sur **tous** les composants. Un tag posé sur le
  seul repo du composant n'apparaît donc que quand ce repo est ouvert seul. Faut-il afficher les
  baselines propres à un composant dans le workspace produit ? Voir Q7.
- `integrates` n'est **pas stocké** sur la version : c'est la liste des changes dont `integratedIn`
  vaut cette version. La source de vérité est unique.
- La version produit est **distincte** de la baseline documentaire. Un correctif crée une version
  produit sans nouvelle baseline documentaire (`implements` inchangé).

### 6.2 Configuration produit (batch)

Une **configuration produit** (FOT, SOT, PR1, PR2, PRV, MP) est une nomenclature de versions de
composants, dans le repo produit, plus des éléments libres (pack, visserie) et un `link` vers le
PLM.

```yaml
# configurations/CFG-0003.yaml   (repo produit)
id: CFG-0003
title: PR1
status: released
basedOn: CFG-0002                  # SOT
versions:                          # une version par composant (clé = nœud du schéma)
  motor-control: MC-1.2.3
  bms: BMS-0.9
items:                             # éléments non modélisés comme composants
  pack: PK-21700-4S / L32
fields:
  docBaseline: baseline/PR1        # baseline documentaire visée (correspondance souhaitée, non imposée)
  plm: { label: Nomenclature PR1, url: "https://plm.example.com/bom/PR1" }
```

Les clés de `versions` et `items` sont celles de `testedConfig` (#191 §2.5) : un run se compare à
sa configuration de référence clé par clé.

La configuration testée d'une exécution (`testedConfig`) et la configuration de référence
d'une campagne ou d'une revue sont spécifiées dans **#191**, qui consomme cet objet.

> Catégories techniques pour ces deux objets : à trancher au lot L5. Soit des catégories dédiées
> (`version`, `configuration`), soit un type système non configurable. Voir Q5.

## 7. Cycle de vie et contraintes de transition (générique)

### 7.1 Cycle de vie par défaut d'un change

Il est fourni à la création du type et entièrement modifiable :

```
ouvert → analysé → implémenté → vérifié → clos
   └──────────┴──────────┴──→ rejeté (isTerminal)
```

### 7.2 Contraintes de transition

Nouveau bloc **facultatif** `transitions` sur un type d'objet, **toutes catégories**. Sans bloc, on
garde le comportement actuel : tout passage est libre.

```yaml
    statuses: [...]
    transitions:
      - from: analyse
        to: implemente
        requires: [impactsClosed]
      - from: verifie
        to: clos
        requires: [modifiedApproved, impactedApproved, linkedCampaignsPassed]
```

- `requires` puise dans une **liste fermée de conditions** fournies par Polenta. Pas de script :
  une condition doit être explicable en une phrase.

  | Condition | Sens | Catégories |
  |---|---|---|
  | `fieldsFilled` | champs `required` / `requiredWhen` remplis | toutes |
  | `impactsClosed` | aucun élément impacté « ouvert » (règle de complétude §3.3) | change |
  | `modifiedApproved` | éléments modifiés de nouveau dans un statut `isApproval` | change |
  | `impactedApproved` | éléments impactés de nouveau dans un statut `isApproval` | change |
  | `linkedCampaignsPassed` | campagnes liées closes, toutes entrées PASS | change |
  | `linkedChangesAt: <statut>` | changes liés (§4) au moins à ce statut | change |
  | `hasCoverageLink` | au moins un lien vers un test (règle 3 de CLAUDE.md) | exigence |
  | `allDecided` | toutes les entrées ont une décision (signature, #191) | conformity |

- **Toujours facultatives et retirables** : chaque transition et chaque condition se retirent en un
  clic dans l'éditeur de schéma. Le cycle de vie par défut d'un change est livré **avec**
  `impactsClosed` et `modifiedApproved` pour la clôture uniquement. Le projet les garde ou les
  retire.
- **Lisibilité, contre la frustration** : on montre toujours une transition refusée, jamais on ne la
  masque. Le menu de statut indique pourquoi elle n'est pas disponible et ce qu'il faut faire
  (« 2 éléments impactés non approuvés : SW-0042, TEST-0007 », chaque ID cliquable).
- Une transition **absente** de `transitions` (alors que d'autres sont déclarées) reste-t-elle libre
  (liste noire) ou interdite (liste blanche) ? Voir Q3. Proposition : **libre**, les contraintes
  s'ajoutent au cas par cas.
- Ces contraintes s'appliquent aux écritures de l'application **et du serveur MCP**. Le YAML
  modifié à la main n'est pas contrôlé (comme les autres règles).

## 8. Vue Changements

- **Panneau latéral** : liste des changes du workspace, regroupés par dossier multi-repo, avec ID,
  type, titre, statut et compteur d'impacts ouverts. Le change implicite apparaît en tête, marqué
  « à qualifier ». Filtres : type, statut, repo, « mes changes », « actif ». Bouton « Nouveau
  change » (§2.1). En bas, les « analyses antérieures » (§3.4).
- **Zone principale** d'un change :
  - en-tête : type, statut avec ses transitions, champs, origine, version intégrée, changes liés ;
  - **Éléments à modifier** : grille ⚙️, avec « prévu / modifié » et les commits attribués ;
  - **Éléments impactés** : arbres et grille, avec statut d'impact, commentaire et levée du flag ;
  - **Campagnes** : liées, avec « Créer » et « Ajouter N tests » ;
  - **Historique** : GH77, plus les commits attribués.
- **Reflets** :
  - éditeur d'exigence ou de test : onglet « Changes » (changes qui l'ont modifié ou impacté) ;
  - run et décision de conformité : « traité par… » ;
  - version de composant : liste des changes intégrés.

## 10. Graphe de données et MCP

- Graphe (#74) : collections `changes` (champs, listes, statuts d'impact, origine, version,
  campagnes, commits attribués) et `versions`. Évolution mineure du contrat.
- MCP : lecture des changes, création d'une demande de changement, mise à jour des listes et des
  statuts d'impact. Les contraintes de transition s'appliquent (§7.2).

## 11. Cas limites

- Un commit modifie des éléments officiels de deux repos avec un change actif dans un seul : la
  partie de l'autre repo va au change implicite de ce repo, et Polenta propose « Étendre au
  composant… ».
- Un change actif est clos ou rejeté : il cesse d'être actif, et les publications suivantes
  appliquent la règle sans change actif.
- Un élément est modifié par deux changes (deux commits) : il figure dans les deux. Les deux
  analyses sont indépendantes.
- Merge de branches (GH37) : les lignes `Change:` survivent. Conflit sur `changes/<ID>.yaml` :
  fusion par champ ou par liste, comme les autres objets.
- Change `range` dont une borne (commit) n'existe plus (historique réécrit) : erreur explicite, et
  le change reste lisible avec sa dernière analyse enregistrée.
- Suppression physique d'un change : seulement s'il n'a pas eu de vie officielle (#184), sinon
  statut terminal.
- `preferences.changeTracking: off` : pas de change implicite ni de proposition à Publier. Les
  changes manuels restent possibles.
- Change implicite dans un repo qui porte plusieurs composants locaux : `component` n'est pas
  déductible. Le change implicite reste sans composant tant qu'il n'est pas nommé, et le nommer
  exige de choisir le composant (ou de le répartir, §2.4).
