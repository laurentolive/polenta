# GH196 — Champs personnalisés des exécutions (`runFields` / `stepFields`) et classeur Excel

> Lot **2/16** du milestone « D — Conformité et gestion du changement », épique #191
> (`specs/GH191.md` §2.1, §2.4, lot L2). Dépend de #195 (type `link`, `requiredWhen`), intégré dans
> `milestone-D`. Cette spec détaille et peut amender la spec globale.

## Contexte

Un run (`test-runs/<TEST>/<RUN>.yaml`) n'a que des champs fixes : verdict, testeur, date, durée,
équipement, `stepResults[] {order, result, comment, executedAt}`, `notes`. Le technicien ne peut pas
saisir d'information **structurée** propre à chaque passage (n° de rapport, température, lien vers le
rapport, valeur mesurée) : tout part dans les `richtext` `comment` / `notes`.

État du code (`milestone-D` @ b9ba81f) :

- Toutes les écritures de run passent par `TestsService.execute` (page d'exécution d'une entrée de
  campagne, import du classeur GH36 via `CampaignExecutionService.apply`). Aucun outil MCP n'écrit de
  run.
- Le classeur d'exécution (GH36, format **v2**) est lu **par position de colonne** (12 colonnes fixes
  A…L, `EXECUTION_SHEET_COLUMNS`) et par clé technique masquée ; la feuille `_polenta` porte
  l'identité du fichier et l'empreinte des tests exportés (GH81).
- `GraphTestRun` (graphe #74) n'expose ni `notes` ni `stepResults`.
- #195 fournit le type `link` (et `readLinkCell` pour les cellules Excel) et le moteur
  `requiredWhen`, au lecteur de valeurs paramétrable.

## 1. Déclaration (schéma)

```yaml
objectTypes:
  - name: essai-normatif
    category: test
    prefix: TN
    fields: [...]                    # la procédure (inchangé)
    runFields:                       # saisis à chaque exécution
      - name: reportNumber
        label: N° de rapport
        type: text
        requiredWhen: { result: [PASS, FAIL] }
      - name: ambientTemp
        label: Température ambiante (°C)
        type: number
      - name: report
        label: Rapport d'essai
        type: link
        multiple: true
        requiredWhen: { result: [FAIL] }
    stepFields:                      # saisis à chaque étape exécutée
      - name: measured
        label: Valeur mesurée
        type: number
        requiredWhen: { result: [PASS, FAIL] }
```

- `runFields?: SchemaField[]` et `stepFields?: SchemaField[]`, **sur les types de catégorie `test`
  seulement** ; ignorés (et signalés par l'éditeur) sur un autre type. Absents tant qu'ils sont vides.
- Types de champ admis : tous sauf `drawio` (Q2). `richtext` est saisi en Markdown, comme `comment`.
- **Unicité du nom (Q6)** : un nom de champ d'exécution ou d'étape désigne **un seul champ dans tout
  le projet**. Deux types de test peuvent déclarer le même nom (même colonne dans le classeur) à
  condition de le déclarer avec le **même type de champ** et dans la **même liste** ; un nom ne peut
  pas servir à la fois dans `runFields` et dans `stepFields`. Refusé à l'enregistrement du schéma
  (`schema:save`, MCP) sinon. `fields` (la procédure) reste un espace de noms distinct.
- `trackHistory` sans objet (un run est immuable, pas d'historique GH77) : non proposé, ignoré.
- `required: true` : obligatoire à chaque exécution, quel que soit le verdict.
- `requiredWhen` (#195) — références admises (Q4) :

| Liste | Pseudo-champ | Autres références |
|---|---|---|
| `runFields` | `result` : verdict global (`PASS`, `FAIL`, `BLOCKED`, `INCOMPLETE`) | champ `enum` / `multi_enum` / `boolean` de `runFields` |
| `stepFields` | `result` : verdict de l'étape (`PASS`, `FAIL`, `BLOCKED`, `SKIP`, `NOT_EXECUTED`) | champ `enum` / `multi_enum` / `boolean` de `stepFields` |

  Même contrôle de cohérence que #195 (erreurs refusées à la sauvegarde, références ou valeurs
  inconnues signalées ⚠).

**Règle de conception** (aide de l'éditeur de schéma) : une information commune à toute la campagne
est un champ de **campagne** ; une information propre à chaque passage est un champ **d'exécution** ;
une mesure par étape est un champ **d'étape**.

### 1.1 Éditeur de schéma

Sur un type de test, deux tableaux supplémentaires « Champs d'exécution » et « Champs d'étape », sous
« Champs », avec les mêmes colonnes que le tableau des champs (sans « Hist. ») : nom, libellé, type,
valeurs / Multiple, obligatoire, obligatoire si, défaut. Le texte d'aide reprend la règle de
conception. Le MCP `add_field` gagne un paramètre `list: 'fields' | 'runFields' | 'stepFields'`
(défaut `fields`), refusé hors catégorie `test`.

## 2. Stockage

```yaml
# test-runs/TN-0004/RUN-20261028-001.yaml
id: RUN-20261028-001
testCaseId: TN-0004
campaignEntry: { campaignId: CAMP-0005, entryId: TN-0004-1 }
result: FAIL
fields:
  reportNumber: RE-2026-118
  ambientTemp: 23.5
  report:
    - { label: RE-2026-118, url: "https://ged.example.com/docs/RE-2026-118" }
stepResults:
  - order: 3
    result: FAIL
    comment: coupure tardive
    fields: { measured: 13.1 }
```

- Bloc `fields: {}` sur le run et sur chaque `StepResult`, **absent tant qu'il est vide**. Les runs
  existants ne sont pas migrés.
- Valeurs typées comme les champs d'objet : `number` en nombre, `boolean` en booléen, `link` en objet
  / liste (#195), `multi_enum` en chaîne CSV, dates en chaîne ISO.
- **Immuabilité inchangée** (SPEC-TESTS §3.1) : les champs sont écrits à la création du run, jamais
  modifiés. Corriger = nouveau run.
- Repo : les `runFields` / `stepFields` d'un test de composant sont ceux du **schéma du composant**
  (le run vit dans le repo du test).

## 3. Contrôle à l'écriture du run

Dans `TestsService.execute` (point d'écriture unique), avec le type du test :

1. clés inconnues de `runFields` / `stepFields` refusées ;
2. valeurs converties au type du champ (le classeur et les formulaires envoient des chaînes) ; `link`
   normalisé et contrôlé (#195) ; `enum` dans `values` ;
3. `required` et `requiredWhen` évalués avec le verdict global (run) ou d'étape (étape) final —
   le verdict calculé depuis les étapes quand il n'est pas forcé ;
4. champs d'étape : seulement sur les étapes **exécutées** (`result` ≠ `NOT_EXECUTED`) ; une étape
   non exécutée n'a pas d'obligation de champ d'étape.

Refus : rien n'est écrit, le message nomme le champ, l'étape le cas échéant, et la condition
(« « N° de rapport » est obligatoire quand Verdict = Échoué », « Étape 3 : « Valeur mesurée » est
obligatoire… »).

## 4. Saisie sur la page d'exécution

Page d'exécution d'une entrée de campagne (`campaign.$campaignId_.execute.$testId`) :

- **champs d'exécution** sous le verdict global, avec les widgets des formulaires (`DynamicField`,
  `link` compris), valeur par défaut (`default`) pré-remplie ;
- **champs d'étape** sur chaque ligne d'étape, sous le commentaire, affichés quand l'étape a un
  verdict autre que « Non exécuté » ;
- astérisque dynamique (`required`, `requiredWhen` selon le verdict sélectionné) ; le bouton
  d'enregistrement reste actif, le refus du main s'affiche (même règle que #195) ;
- consultation d'un run (`campaign.$campaignId_.run.$testId`) : champs d'exécution et d'étape en
  lecture seule, liens cliquables (`LinkList`).

## 5. Classeur Excel d'exécution (GH36)

### 5.1 Format v3

- Nouvelles colonnes **jaunes de saisie** insérées **après « Commentaire »**, avant les colonnes
  d'information (Exigence, Paramètres, Statut actuel) — visibles sans défilement :
  1. une colonne par `runField` (renseignée sur la ligne d'instance) ;
  2. une colonne par `stepField` (renseignée sur les lignes d'étape).
- Campagne qui mélange plusieurs types de test : **union** des colonnes, dans l'ordre de première
  apparition (types dans l'ordre des entrées, champs dans l'ordre du schéma). Un même nom = une seule
  colonne (unicité, §1) ; libellé et valeurs d'enum du premier type rencontré.
- Cellule sans objet (champ non déclaré par le type de l'instance, champ d'étape sur une ligne
  d'instance et inversement) : **grisée et verrouillée** (protection de feuille sans mot de passe,
  comme les colonnes non jaunes).
- En-tête : libellé du champ, `*` pour un champ `required` ; commentaire de cellule : type, valeurs,
  condition `requiredWhen` en clair.
- `enum` : liste déroulante (validation de données Excel) ; `boolean` : liste Oui / Non ; `link` :
  forme `libellé | URL` ou lien hypertexte (#195 §1.10).
- La feuille `_polenta` enregistre la **carte des colonnes** (lettre → liste + nom de champ + type de
  test) : la lecture d'un v3 se fait par cette carte, jamais par libellé.
- `EXECUTION_SHEET_FORMAT_VERSION` = 3 ; v1 et v2 restent lus (sans champs).
- Campagne sans aucun `runField` / `stepField` : colonnes absentes, fichier identique au v2 hormis le
  numéro de version.

### 5.2 Import

- Lecture des cellules par type : `number` (nombre ou texte numérique, virgule décimale acceptée),
  `boolean` (Oui / Non / Yes / No / true / false / 1 / 0), `enum` (valeur ou libellé), `date`,
  `link` (`readLinkCell`), texte sinon.
- Erreurs **par instance** (l'instance est refusée, les autres sont importées, comme aujourd'hui) :
  - valeur illisible (`invalid_field_value` : ligne, champ, valeur) ;
  - champ obligatoire manquant (`required_field_missing` : ligne, champ, condition).
- L'aperçu d'import (GH36) liste ces erreurs avec le libellé du champ.

## 6. Évolution du schéma (lecture)

- Champ retiré : ses valeurs restent dans les runs et s'affichent en lecture seule, marquées
  « hors schéma ».
- Valeur d'enum disparue : valeur brute affichée avec ⚠.
- Champ ajouté : ne concerne que les exécutions suivantes ; les runs antérieurs n'ont pas la valeur.
- **On ne réécrit jamais un run**, y compris au renommage d'un champ (GH82) : limite documentée
  (le renommage n'atteint pas les runs).

## 7. Graphe de données (#74)

`GraphTestRun` gagne (ajout, contrat v1) :

```ts
fields: Record<string, unknown>          // {} si aucun
notes: string                             // Markdown, '' si vide
stepResults: { order: number; result: GraphStepResult; comment: string; fields: Record<string, unknown> }[]
```

`GraphObjectType` (types de test) expose `runFields` / `stepFields` (`GraphFieldDef[]`).
`polenta.d.ts` régénéré, manifeste incrémenté. Les colonnes calculées du projet (« température
max », « FAIL sans n° de rapport ») s'appuient dessus — aucune n'est livrée par ce lot (GH79).

## 8. Cas d'usage

| # | Situation | Résultat attendu |
|---|---|---|
| U1 | Déclarer 3 `runFields` et 1 `stepField` sur un type de test dans l'éditeur | schéma sauvé avec `runFields` / `stepFields` |
| U2 | Exécuter une entrée : verdict FAIL, n° de rapport vide | refus nommant « N° de rapport » ; rien n'est écrit |
| U3 | Même exécution, champs remplis | run écrit avec `fields`, étape 3 avec `fields.measured` |
| U4 | Étape non exécutée, champ d'étape vide | accepté |
| U5 | Exporter le classeur d'une campagne à deux types de test | colonnes union ; cellules sans objet grisées / verrouillées |
| U6 | Réimporter avec un lien hypertexte dans « Rapport d'essai » et `23,5` dans la température | `{label, url}` et `23.5` dans le run |
| U7 | Réimporter une instance FAIL sans n° de rapport | instance en erreur `required_field_missing`, les autres importées |
| U8 | Réimporter un classeur v2 | importé comme aujourd'hui, sans champs |
| U9 | Retirer `ambientTemp` du schéma, ouvrir un ancien run | valeur affichée « hors schéma » |
| U10 | Script Suivi : max de `ambientTemp` des runs FAIL | lit `runs[].fields.ambientTemp` |

## 9. Critères d'acceptation

- [ ] `runFields` / `stepFields` déclarables (éditeur de schéma, MCP `add_field` avec `list`), refusés
      hors type de test ; `requiredWhen` sur `result` contrôlé en cohérence.
- [ ] `TestsService.execute` convertit, contrôle (`required`, `requiredWhen` sur verdict final, liens,
      enums, clés inconnues) et écrit `fields` sur le run et les étapes exécutées ; refus sans écriture,
      message nommant champ, étape et condition.
- [ ] Page d'exécution : saisie des champs d'exécution et d'étape, défauts, astérisque dynamique ;
      consultation d'un run en lecture seule (liens cliquables, « hors schéma »).
- [ ] Classeur v3 : colonnes jaunes après Commentaire, union multi-types, cellules sans objet
      verrouillées, listes déroulantes, carte des colonnes dans `_polenta` ; v1 / v2 toujours lus.
- [ ] Import : conversion par type (lien hypertexte compris), erreurs par instance
      `invalid_field_value` / `required_field_missing` dans l'aperçu.
- [ ] Graphe : `GraphTestRun.fields`, `notes`, `stepResults` ; `runFields` / `stepFields` sur les types ;
      `polenta.d.ts` régénéré.
- [ ] Tests unitaires (contrôle à l'écriture, aller-retour du classeur v3, lecture v2) et e2e (saisie
      sur la page d'exécution, refus `requiredWhen`).
- [ ] SPEC-TESTS §3 (TestRun, StepResult), §4.5 (classeur), SPEC-DASHBOARDS (contrat graphe),
      SPEC-REQ §3 (listes de champs) mis à jour.

## 10. Indicateurs (GH79)

Aucun indicateur. `required` / `requiredWhen` des champs d'exécution servent une fonction de Polenta
(contrôle à l'écriture) ; tout agrégat sur les valeurs (température max, FAIL sans rapport) est une
colonne calculée **côté projet**.
