# GH198 — Objet change : catégorie, types, vue Changements, création, listes, composant concerné

> Lot **4/16** du milestone « D — Conformité et gestion du changement », épique #193
> (`specs/GH193.md` §1, §2.1, §8, lot L2). Modèle d'ensemble : `specs/MODELE-OBJETS.md`.
> Ce lot pose l'**objet** et sa **vue**. L'analyse d'impact calculée (L3, #199), le rattachement des
> commits (L4, #200), les versions (L5, #201), les campagnes (L6, #207), le multi-repo (L7, #208) et
> l'intégration conformité (L8, #209) viennent ensuite et s'appuient sur ce qui est posé ici.

## Contexte

Aucun objet ne porte aujourd'hui une **modification qu'on pilote** : cause, description, éléments à
modifier et impactés, cycle de vie, version qui la livre. Les trois flux d'analyse d'impact
(SPEC-TRACEABILITY §4) ne sont rattachés à rien.

État du code (`milestone-D` @ 3e6bcd9) :

- `ObjectCategory = 'requirement' | 'test' | 'campaign'` (`packages/types/src/schema.ts`), utilisée
  par l'éditeur de schéma (`StructureTab`, `objectTypeEditor`), `NoTypeForCategory`, les couleurs de
  catégorie, la suppression de type (`schema-delete`), les références de schéma, le graphe.
- Les campagnes ont leur service (`CampaignsService`, `campaigns/<ID>.yaml`, historique GH77 via
  `persist`), leur vue (entrée « Campagnes » de la barre d'activité, liste par composant, page
  `campaign.$campaignId`).
- IDs : préfixe du type, numéro déduit du disque et des pierres tombales (GH20).
- Statuts : `statuses` du type (`isApproval`, `isTerminal`), historique GH77 ; **aucune contrainte de
  transition** (elles arrivent avec L1, #206).
- Champs : `fields` du type, dont `link` et `requiredWhen` (#195).

---

## 1. Catégorie et types

- `ObjectCategory` gagne **`change`**. Le projet déclare un ou plusieurs types de cette catégorie dans
  l'éditeur de schéma (préfixe, libellé, `fields`, `statuses`) : par exemple `evolution` (EVO) et
  `non-conformite` (NC), ou un seul `changement` (CHG) avec un champ « cause ». Polenta ne prête
  **aucune sémantique** aux types.
- **Cycle de vie par défaut** proposé à la création d'un type `change` (modifiable) :

  ```
  ouvert → analyse → implemente → verifie → clos
     └────────┴──────────┴──→ rejete (isTerminal)
  ```

  `clos` et `rejete` sont `isTerminal`. Aucun statut `isApproval` par défaut. Les contraintes de
  transition (ex. « impacts clos » pour clore) viendront avec L1 / L6 : en L2, tout passage est libre.
- Les changes **ne participent pas à la couverture** ni à la maturité.
- Sans type `change` dans le schéma : la vue Changements affiche le message existant « aucun type de
  cette catégorie » avec le lien vers le modèle de données (`NoTypeForCategory`).

## 2. Stockage

```yaml
# changes/NC-0004.yaml   (repo du composant concerné)
id: NC-0004
objectTypeRef: motor-control::non-conformite
title: Surcharge courant au démarrage
status: ouvert
version: 1
fields:                         # définis par le type
  description: Pic à 13,1 A au démarrage à froid…
  bug: { label: BUG-482, url: "https://jira.example.com/BUG-482" }
component: motor-control        # composant concerné (§3)
mode: request                   # request (demande) — `range` : L3
toModify:                       # éléments à modifier
  - { id: SW-0042, state: planned }
impacted:                       # éléments impactés déclarés
  - { id: SYS-0012, status: impact_a_tester, comment: "", source: declared }
origin: { runs: [], decisions: [] }   # rempli par L8 (affiché en L2)
integratedIn: ~                 # version de composant : L5
campaigns: []                   # campagnes : L6
history: …                      # GH77 (statut)
```

- Fichier `changes/<ID>.yaml` **dans le repo du composant concerné** (repo du nœud ; repo du
  composant pour un nœud submodule, comme les objets d'un composant). IDs : préfixe du type, déduits
  du disque et des pierres tombales (GH20).
- Champs système fixes : `id`, `objectTypeRef`, `title`, `status`, `version`, `component`, `mode`,
  `toModify`, `impacted`, `origin`, `integratedIn`, `campaigns`, `history`. Champs du projet :
  `fields`. Les champs encore sans fonction en L2 (`origin`, `integratedIn`, `campaigns`) sont écrits
  vides et affichés en lecture seule.
- Écritures par un `ChangesService` sur le modèle des campagnes (`persist` + historique GH77,
  `requiredWhen` / liens contrôlés comme les autres objets, #195).

## 3. Composant concerné

- `component` : nom du nœud du schéma que le change fait évoluer.
- **Déduit** quand le repo ne porte qu'un composant local ; **obligatoire** (sélection) quand il en
  porte plusieurs (nœuds sans `url`, T129). Seuls les **composants locaux** du repo sont proposés en
  L2 : un change sur un composant externe (stocké dans son repo, type résolu dans son schéma) relève
  du multi-repo, L7 (#208) — décision de revue de code.
- Modifiable tant que le change est au statut initial ; ensuite figé (il désigne le repo de stockage).

## 4. Les deux listes (manuelles en L2)

- **Éléments à modifier** (`toModify`) : exigences et tests qu'on prévoit de modifier, `state:
  planned`. Deux façons de les ajouter :
  - **à la main** (sélecteur d'éléments) ;
  - **depuis les éléments repassés en brouillon** : l'action « Ajouter les éléments repassés en
    brouillon » liste les exigences et tests du repo **déjà approuvés une fois** (un statut
    `isApproval` dans leur historique GH77, repli `version > 1`) et **qui ne sont plus dans un statut
    d'approbation** ; l'utilisateur coche ceux à ajouter. Les éléments déjà listés ne sont pas proposés.

  (L4 ajoutera automatiquement les éléments réellement modifiés et rattachés, `state: modified`.)
- **Éléments impactés** (`impacted`) : éléments **déclarés** (`source: declared`), avec un **statut
  d'impact** parmi les 8 valeurs existantes (SPEC-TRACEABILITY §4.6 : `impact_non_verifie`,
  `pas_d_impact_reel`, `impact_a_tester`, `impact_teste`, `modification_a_faire`,
  `modification_faite`, `modification_a_tester`, `modification_verifiee`) et un commentaire. Défaut :
  `impact_non_verifie`. (L3 ajoutera les éléments calculés, `source: computed`, et la complétude.)
- Ajout par un sélecteur d'éléments (ID, titre, type) **du repo du change** (Q3) ; un élément ne
  figure qu'une fois par liste ; retrait en un clic. Un ID dont l'élément n'existe plus s'affiche
  « supprimé » et reste dans la liste.

## 5. Vue Changements

- **Barre d'activité** : nouvelle entrée « Changements » (Q1).
- **Panneau latéral** : liste des changes du **workspace**, regroupés par repo, triés par ID
  décroissant ; chaque ligne : ID, type (couleur du type), titre, statut. Filtres : type, statut,
  repo, « mes changes » (Q9), « masquer les terminés » (coché par défaut). Bouton **« Nouveau
  change »**.
- **Zone principale** (page `change.$changeId`) :
  - en-tête : ID, type, titre éditable, statut (menu des statuts du type), composant ;
  - champs du type (même édition que les autres objets : `DynamicField`, liens, `requiredWhen`) ;
  - **Éléments à modifier** : liste (ID cliquable, titre, statut de l'élément), ajout / retrait ;
  - **Éléments impactés** : liste avec statut d'impact (menu) et commentaire, ajout / retrait ;
  - origine, version intégrée, campagnes : affichées (vides en L2) ;
  - **Historique** (GH77).
- **Création** (« Nouveau change », mode `request`) : type (pré-sélectionné s'il est seul), titre,
  composant (§3), champs `required` ; le change créé s'ouvre dans la zone principale.
- **Depuis l'éditeur d'un élément** : action **« Créer un change »** dans la vue Édition et les pages
  de détail d'une exigence ou d'un test → formulaire de création avec l'élément dans `toModify`
  (`planned`) et le composant de l'élément (Q4).
- **Suppression** (Q6) : possible **tant que le fichier du change n'a jamais été commité** (aucun
  commit git ne le touche), quel que soit son statut ; ensuite, passer par un statut terminal. Pierre
  tombale (GH20).

## 6. Graphe de données et MCP

- Graphe (#74) : nouvelle collection **`changes`** (champs système et `fields`, listes, statut,
  historique), types de catégorie `change` dans `objectTypes`. Ajout au contrat v1, `polenta.d.ts`
  régénéré (Q7).
- MCP (Q8) : lecture des changes (`list_changes`, `get_change`) et création d'une demande
  (`create_change`), avec les mêmes contrôles que l'application.

## 7. Cas d'usage

| # | Situation | Résultat attendu |
|---|---|---|
| U1 | Créer un type `non-conformite` (NC) dans le modèle de données | cycle de vie par défaut pré-rempli |
| U2 | « Nouveau change » dans un repo à un composant | composant déduit ; `changes/NC-0001.yaml` créé, statut `ouvert` |
| U3 | Repo produit avec deux composants locaux | composant obligatoire dans le formulaire |
| U4 | « Créer un change » depuis l'éditeur de SW-0042 | formulaire avec SW-0042 dans « à modifier » |
| U5 | Ajouter SYS-0012 aux impactés, statut « impact à tester », commentaire | enregistré dans `impacted` |
| U6 | Passer le change à `analyse` | statut changé, historique GH77 |
| U7 | Supprimer un change jamais commité | supprimé, pierre tombale ; change déjà commité (publié) : suppression refusée, statut terminal proposé |
| U7b | « Ajouter les éléments repassés en brouillon » | SW-0042 (approuvé puis rouvert) proposé ; SW-0050 (jamais approuvé) non proposé |
| U8 | Liste du panneau : filtre type NC, masquer les terminés | liste filtrée, regroupée par repo |
| U9 | Script Suivi | `data.changes` disponible |

## 8. Critères d'acceptation

- [ ] Catégorie `change` déclarable dans le modèle de données, cycle de vie par défaut.
- [ ] `ChangesService` : création (`request`), lecture, mise à jour (titre, statut, champs, listes,
      composant au statut initial), suppression tant que jamais commité ; candidats « repassés en
      brouillon » ; historique GH77 ; contrôles #195.
- [ ] Vue Changements : entrée de barre d'activité, panneau (liste workspace par repo, filtres,
      nouveau), page d'un change (en-tête, champs, deux listes, historique).
- [ ] « Créer un change » depuis l'éditeur d'une exigence ou d'un test.
- [ ] Graphe `changes` + `polenta.d.ts` ; MCP `list_changes`, `get_change`, `create_change`.
- [ ] Tests unitaires (service, IDs, suppression, composant) et e2e (création, listes, statut).
- [ ] SPEC : nouvelle section changes (SPEC-REQ / SPEC-TRACEABILITY), SPEC-DASHBOARDS, SPEC-MCP-SERVER.
