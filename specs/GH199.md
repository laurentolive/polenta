# GH199 — Analyse d'impact dans le change (bornes baselines et commits)

> Lot **5/16** du milestone « D — Conformité et gestion du changement », épique #193
> (`specs/GH193.md` §3, lot L3). S'appuie sur l'objet change de #198 (`specs/GH198.md`).
> Hors périmètre : rattachement des commits et change actif (L4, #200), versions (L5, #201),
> campagnes du change (L6, #207), multi-repo (L7, #208), origine / conformité (L8, #209).

## Contexte

État du code (`milestone-D` @ 03e6dcb) :

- Un change (#198) porte deux listes **manuelles** : `toModify` (`planned`) et `impacted`
  (`declared`, statut d'impact parmi 8 valeurs, commentaire). Aucune analyse n'est calculée.
- Trois flux d'analyse d'impact coexistent (SPEC-TRACEABILITY §4) :
  - **§4.1–4.5, élément unique** : `TraceabilityService.getImpactReport` (profondeur 1 par
    défaut) et `acknowledgeImpact` (`impact-acks/<reqId>/<ackId>.yaml`), IPC
    `traceability:impact` / `traceability:acknowledge`. **Aucun écran ne les appelle plus**
    (vérifié : pas d'usage dans le renderer ni le MCP) ; restent le main, l'api-client, les types.
  - **§4.6, entre deux baselines** (T46) : `impact-analyses/<id>.yaml`, figée à la création,
    arbres montant / descendant (`buildImpactTreesFromSnapshot` sur `loadSnapshotAtRef`), statut
    par nœud d'arbre, complétude, génération de campagne, levée de `needsRevalidation` (§4.8).
    Création depuis le panneau Version (« Analyser l'impact »), lecture dans `/impact-analysis`.
  - **§4.7, modifications locales** (T175) et **§4.8, « Impact à vérifier »** : live, non
    persistés.

## 1. Point de départ et arbres

- **Racines** de l'analyse d'un change : éléments de `toModify` + éléments `impacted` **déclarés**.
  Listes vides : **toutes les exigences du composant concerné** (`objectTypeRef` dont le nœud est
  `component`).
- **Arbres** : ceux de §4.6 (`buildImpactTreesFromSnapshot`) pour chaque racine — montant et
  descendant, graphe complet, couverture test ↔ exigence dans les deux sens ; pour un test racine,
  arbre montant (exigences couvertes et leurs ascendants), comme en §4.7.
- **Snapshot** des arbres :
  - change **demande** (`request`) : état courant **sur disque** du repo du change (exigences,
    tests, liens ; lecture disque comme §4.7, pas l'index vivant) ;
  - change **sur l'existant** (`range`, §3) : snapshot à la borne **`to`**.
- Chaque élément atteint (hors racines) devient un **élément impacté calculé**
  (`source: computed`) ; un élément atteint depuis plusieurs racines n'a **qu'une ligne** (Q1).

## 2. Statuts, persistance, live / figé

- **Un statut par élément** (Q1) : la liste `impacted` reste plate (une ligne par élément, déclaré
  ou calculé), avec les 8 statuts et un commentaire. Les arbres servent à comprendre **pourquoi**
  un élément est atteint : chaque nœud affiche le statut de sa ligne et permet de le modifier.
- **Persistance** (Q2) : le fichier ne garde que ce qui porte une saisie :
  - éléments déclarés (comme en #198) ;
  - éléments calculés dont le statut ≠ `impact_non_verifie` ou avec commentaire.

  Les éléments calculés au statut par défaut sont **recalculés à l'affichage**, pas écrits : pas
  d'écriture du change à chaque modification d'un lien du projet.
- **Live tant que le change n'est pas terminal** : recalcul à l'ouverture de la page, sur
  changement de fichier (`requirements/`, `tests/`, `links/`, `changes/`) et par « Rafraîchir ».
  Un élément calculé **qui n'est plus atteint** garde sa ligne s'il est persisté, marquée
  « n'est plus atteint » ; sinon il disparaît.
- **Figé au statut terminal** (`isTerminal`) : l'analyse (racines, arbres, lignes calculées) est
  enregistrée dans le change (`analysis`, Q11) ; la page l'affiche telle quelle, plus de recalcul.
  Repasser le change dans un statut non terminal **efface l'instantané** et revient au live ; les
  statuts saisis sont conservés (Q12).
- **Complétude** (§4.6) : `pas_d_impact_reel`, `impact_teste`, `modification_verifiee` = clos ;
  bandeau « N ouverts / M » et « Analyse complète » quand rien n'est ouvert. Informatif.
- **`needsRevalidation`** (§4.8) : ⚠, case et « Lever le flag » sur les nœuds marqués, comme dans
  les arbres §4.6 / §4.7 (flag lu en direct).

## 3. Change « sur l'existant » (`range`)

- Création : « Nouveau change » propose **Demande** ou **Sur l'existant**. Sur l'existant : deux
  bornes **`from` / `to`**, chacune une **baseline** ou un **commit** du repo du change (Q3 :
  baselines + 50 derniers commits de la branche, ou SHA saisi). Stocké :
  `mode: range`, `range: { from: { ref, sha }, to: { ref, sha } }` (`ref` = tag ou SHA court).
- Éléments changés entre les bornes (diff de §4.6 étendu aux **tests**, comme §4.7) : ajoutés à
  `toModify` avec `state: modified` à la création ; ils sont les racines (§1). La liste reste
  modifiable.
- Multi-repo (une borne par repo) : L7.

## 4. Impacts supplémentaires

- **Campagnes en cours** (statut non clos) qui incluent un test impacté (racine ou calculé) :
  listées sous l'analyse (ID, titre, tests concernés), lien vers la campagne.
- Exécutions sur une version antérieure (`testedConfig`, #191), décisions de conformité,
  dérogations : avec leurs lots (L8). Changes liés : L7. (Q6)

## 5. Devenir des flux existants (GH193 §3.4)

- **§4.1–4.5 élément unique — retiré** : `getImpactReport`, `acknowledgeImpact`, IPC
  `traceability:impact` / `traceability:acknowledge`, api-client et types `ImpactReport`,
  `ImpactAcknowledgement`, `AcknowledgeImpactDto`. Les fichiers `impact-acks/` existants restent
  **lisibles** : section repliée « Acquittements d'impact (anciens) » dans l'historique de
  l'élément, affichée seulement s'il en existe (Q8). Pas de migration.
- **« Analyser l'impact » sur un élément** (fiche, vue Édition) : aujourd'hui absent. Le bouton
  « Créer un change » de #198 devient **« Analyser l'impact »** : s'il existe des changes **non
  terminaux** du repo qui listent l'élément (à modifier ou impacté), menu « Ouvrir NC-0004… /
  Créer un change » ; sinon formulaire de création avec l'élément dans `toModify`. (Le change
  **actif** arrive avec L4.)
- **§4.6 entre baselines — retiré, remplacé par le change `range`** : service, IPC, api-client,
  types et écrans des analyses enregistrées supprimés. Les fichiers `impact-analyses/` existants
  sont **ignorés** (décision 2026-10-29 : fonction pas encore utilisée par le client, analyses
  antérieures perdues, pas de lecture ni de conversion).
- `preferences.changeTracking: off` : L4.

### 5.1 La vue Analyse d'impact disparaît (Q9, décision)

Toutes ses fonctions passent dans la **vue Changements** :

| Fonction (vue Analyse d'impact) | Devient |
|---|---|
| Entrée de barre d'activité « Analyse d'impact » | **retirée** (préférence d'ordre / masquage GH56 : entrée inconnue ignorée) |
| « Impact à vérifier » (§4.8, `RevalidationList`) | entrée en tête du panneau Changements (compteur, affichée s'il y a des éléments marqués) ; contenu inchangé, dans la zone principale |
| « Modifications locales (vs HEAD) » (§4.7) | entrée du panneau Changements sous la précédente (compteur, affichée s'il y a des modifications) ; contenu inchangé ; **plus de sélection automatique** à l'ouverture de la vue |
| Création d'une analyse entre baselines | **retirée** : « Nouveau change › Sur l'existant » (§3) |
| Analyses enregistrées (§4.6) | **supprimées** (fichiers ignorés) |
| Arbres, statuts, commentaires, complétude, levée du flag, popups d'édition | dans la section Analyse d'impact de la page d'un change (§6) |
| Export de l'analyse (xlsx / docx / pdf) | export de l'analyse d'un change (même format : racines, arbres, statuts) |
| Génération de campagne | L6 (#207), depuis le change (Q7) |
| Constellation (GH183) | bouton dans l'en-tête du panneau Changements ; route `/constellation` inchangée, rattachée au panneau Changements |

La route `/impact-analysis` est remplacée par `/changes/local` et `/changes/revalidation` ;
`/print/impact-analysis` imprime l'analyse d'un change.

## 6. Page d'un change

Section **« Analyse d'impact »** sous les deux listes :

- en-tête : mode (demande / sur l'existant + bornes), « calculée à <heure> » ou « figée le … »,
  complétude, « Rafraîchir » ;
- par racine : ID, titre, statut de l'élément, arbres descendant et montant dépliables (rendu de
  `/impact-analysis` réutilisé : nœuds avec statut d'impact, commentaire, ⚠ needsRevalidation,
  popup d'édition de l'élément) ;
- la liste « Éléments impactés » montre déclarés **et** calculés (badge « calculé », « n'est plus
  atteint ») ; filtre « ouverts seulement » ;
- campagnes en cours concernées (§4) ;
- « Exporter » l'analyse (§5.1).

## 7. Graphe, MCP

- Graphe (#74) : `GraphChange.impacted` contient les lignes **persistées** ; `range`, `analysis`
  (instantané figé) exposés. Pas de calcul d'analyse dans le graphe (GH79 : données brutes).
- MCP : `get_change` renvoie en plus l'analyse **calculée** (`computeChangeAnalysis`) — même
  résultat que la page. Pas d'outil d'écriture des statuts dans ce lot (Q10).

## 9. Critères d'acceptation

- [ ] Analyse calculée d'un change (racines, arbres, lignes calculées dédupliquées), live / figée.
- [ ] Persistance des seules lignes saisies ; « n'est plus atteint » ; complétude ; levée du flag.
- [ ] Change `range` : bornes baseline ou commit, diff exigences + tests, snapshot à `to`.
- [ ] Campagnes en cours concernées.
- [ ] Flux élément unique retiré ; `impact-acks/` lisibles ; « Analyser l'impact » sur un élément.
- [ ] Analyses entre baselines retirées (code et écrans) ; `impact-analyses/` ignoré.
- [ ] Vue Analyse d'impact retirée : « Impact à vérifier », « Modifications locales » et Constellation dans la vue Changements ; export de l'analyse d'un change.
- [ ] Graphe (`range`, `analysis`) + `polenta.d.ts` ; MCP `get_change` avec l'analyse.
- [ ] Tests unitaires (calcul, persistance, figé, range, conversion) et e2e (U1–U3, U5, U11).
- [ ] SPEC-TRACEABILITY §4 réécrit (élément unique retiré, §4.6 remplacé), SPEC-REQ §10.

## 10. Indicateurs (GH79)

La complétude et l'analyse servent une fonction de Polenta (piloter le change) : calculées dans
Polenta. Aucun indicateur de suivi (délais, volumes…) : côté projet via le graphe.
