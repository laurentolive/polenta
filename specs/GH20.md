# GH20 — IDs : remplacer `counters.yaml` par parsing + pierres tombales

Issue : https://github.com/laurentolive/polenta/issues/20

## 1. Contexte

L'attribution des IDs séquentiels (`<PREFIX>-NNNN`) s'appuie aujourd'hui sur
`config/counters.yaml`, réécrit à **chaque création** d'objet. Conséquences :

- conflit de merge quasi systématique entre deux branches qui créent des objets ;
- trois implémentations divergentes du même mécanisme :
  - `id-counter.util.ts` `nextCounterId` / `peekNextCounterId` — exigences, tests, campagnes
    (sérialisé par repo, recalé sur `max(compteur, max ID sur disque) + 1`, T118) ;
  - `GitService.nextCounterId` — dashboards, requêtes partagées (ni sérialisé, ni recalé sur le disque) ;
  - `ReviewsService.nextReviewId` — revues (copie locale, ni sérialisée, ni recalée).

Le compteur ne sert qu'à calculer le prochain ID. Son seul apport par rapport au parsing
du disque est la **mémoire des IDs supprimés physiquement** (campagnes, dashboards,
requêtes). Ce ticket remplace cette mémoire par des **pierres tombales** et supprime
`counters.yaml`.

**Règle conservée, étendue à tous les types séquentiels** : un ID n'est **jamais réutilisé**.

## 2. Périmètre

Types d'objets à ID séquentiel concernés (desktop + serveur MCP) :

| Type | Dossier | Prefix | Suppression physique aujourd'hui |
|---|---|---|---|
| Exigence | `requirements/` | prefix du type (schema) | non (statut terminal) |
| Cas de test | `tests/` | prefix du type (schema) | non (statut terminal) |
| Campagne | `campaigns/` | `CAMP` | oui (`CampaignsService.delete`) |
| Revue | `reviews/` | `REVIEW` | non |
| Dashboard partagé | `dashboards/` | `DASHBOARD` | oui (`delete`, passage partagé → privé) |
| Requête partagée | `queries/` | `QUERY` | oui (`delete`, passage partagé → privé) |

## 3. Comportement attendu

### 3.1 Pierre tombale

- Emplacement : `.polenta/tombstones/<ID>` dans le repo qui possédait l'objet
  (ex. `.polenta/tombstones/CAMP-0012`).
- Un fichier par ID, **contenu vide**. Auteur et date se lisent dans `git log`.
- Écrite par l'application **à chaque suppression physique** d'un objet à ID séquentiel
  (§2), **avant** la suppression du fichier de l'objet. Si la suppression échoue, la
  pierre tombale reste : c'est sans danger, l'ID ne sera simplement pas réutilisé.
- Versionnée comme n'importe quel fichier : elle part dans le même commit que la
  suppression (« Publier » fait déjà `git add .` et stage les suppressions).
- Une pierre tombale n'est jamais supprimée par l'application.

### 3.2 Attribution d'un ID

Pour un repo et un prefix `P` :

```
next(P) = max( N de tout <dossier du type>/P-N.yaml,
               N de tout .polenta/tombstones/P-N,
               valeur de P dans config/counters.yaml s'il existe encore ) + 1
```

- Un **seul** module d'attribution, utilisé par tous les types du §2 (remplace les trois
  implémentations actuelles).
- Sérialisé par `repoPath` (même file de promesses que T118) : deux créations
  concurrentes dans le même process obtiennent des IDs distincts.
- Aucune écriture de fichier n'est faite pour réserver un ID : c'est la création du
  fichier de l'objet qui le « consomme ». L'écriture de l'objet doit donc rester dans la
  même section sérialisée que le calcul, ou le calcul doit tenir compte des IDs déjà
  attribués et pas encore écrits (choix d'implémentation laissé au design).
- Format inchangé : `<PREFIX>-` + numéro sur 4 chiffres minimum (`formatCounterId`).
- `peekNextCounterId` (aperçu `bulk_import_*` en `dryRun`) utilise exactement le même
  calcul, en lecture seule.

### 3.3 Migration des repos existants

Déclenchée paresseusement par le module d'attribution (UI **et** serveur MCP), dans la
section sérialisée, dès qu'une attribution a lieu dans un repo qui a encore
`config/counters.yaml` :

1. Pour chaque clé numérique `K: v` du fichier (les clés héritées `nextId`, `prefixes`
   sont ignorées) : `v` est le **dernier numéro attribué** pour `K`. Si aucun fichier
   `K-v.yaml` n'existe dans les dossiers du §2, créer la pierre tombale `K-v` (l'ID a
   été attribué puis supprimé).
2. Supprimer `config/counters.yaml`.

La migration est idempotente : relancée après une interruption, elle ne crée pas de
doublon et aboutit au même état. Après migration, le prochain ID de chaque prefix est
identique à celui qu'aurait donné l'ancien mécanisme.

`peekNextCounterId` ne migre pas (lecture seule), mais tient compte de `counters.yaml`
s'il est encore présent (§3.2).

### 3.4 Cas d'usage

- **UC-1** Suppression de la dernière campagne `CAMP-0012`, puis création d'une
  campagne → `CAMP-0013` ; `.polenta/tombstones/CAMP-0012` existe.
- **UC-2** Passage d'une requête partagée `QUERY-0005` en privé, puis création d'une
  requête partagée → `QUERY-0006`.
- **UC-3** Repo existant avec `counters.yaml` `{ SW: 42, CAMP: 7 }`, `SW-0042.yaml`
  présent, `CAMP-0007.yaml` absent. Première création → pierre tombale `CAMP-0007`
  seulement, `counters.yaml` supprimé, prochain `SW` = `SW-0043`, prochain `CAMP` = `CAMP-0008`.
- **UC-4** Deux branches créent chacune une exigence : plus aucun conflit sur un fichier
  partagé. Les deux obtiennent le même ID : limite connue (§5).
- **UC-5** `bulk_import_*` en `dryRun` sur un repo non migré → IDs prévus identiques à ceux
  que l'import réel attribuera, sans écrire ni migrer.

## 4. Critères d'acceptation

1. Plus aucun code du desktop ni du serveur MCP n'écrit `config/counters.yaml` (hors
   suppression lors de la migration).
2. Un seul module d'attribution d'ID ; `GitService.nextCounterId` et
   `ReviewsService.nextReviewId` sont supprimés ou délèguent à ce module.
3. Toute suppression physique d'un objet du §2 crée `.polenta/tombstones/<ID>`.
4. Après suppression de l'objet au plus grand numéro d'un prefix, la création suivante
   n'obtient jamais cet ID (tous les types du §2).
5. La migration donne, pour chaque prefix, le même prochain ID que l'ancien mécanisme, et
   est idempotente.
6. Créations concurrentes dans le même process → IDs distincts (non-régression T118),
   y compris pour dashboards, requêtes et revues, qui n'étaient pas sérialisés.
7. `dryRun` de `bulk_import_*` : IDs prévus = IDs réellement attribués ensuite, sans
   écriture sur le disque.
8. Typecheck, lint et tests existants au vert ; nouveaux tests unitaires couvrant
   UC-1, UC-2, UC-3, UC-5 et la concurrence.
9. Documentation à jour : SPEC-TECH-stack §4.1/§4.4, SPEC-REQ-requirements §6.1/§9,
   SPEC-DASHBOARDS (tableau stockage), SPEC-FORKS-BRANCHES-BASELINES (arborescence),
   SPEC-MCP-SERVER (aperçu `dryRun`, sérialisation), CLAUDE.md (arborescence
   `.polenta/tombstones/`, interdiction de supprimer une pierre tombale) et gabarit
   `AGENTS.md` si nécessaire.

## 5. Hors périmètre

- **Collisions entre branches** : deux branches qui partent du même état attribuent le
  même prochain ID. Non résolu ici (cf. #17, point 3). Le §4.4 de SPEC-TECH-stack
  (résolution par renommage) reste la règle.
- **Suppression hors application** (explorateur, `git rm`) : pas de pierre tombale, l'ID
  peut être réutilisé s'il était le plus grand. Accepté.
- **`apps/api`** (backend NestJS inactif, ancien format `nextId`/`prefixes`) : non modifié.
- **Analyses d'impact** (`impact-<timestamp>`) et **IDs privés** (`local-<ts>-<rand>`) :
  non séquentiels, jamais réutilisés en pratique, non concernés.
- Collision entre un prefix de type (schema) et un prefix réservé (`CAMP`, `REVIEW`,
  `DASHBOARD`, `QUERY`) : problème existant, inchangé.
