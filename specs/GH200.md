# GH200 — Rattachement des modifications : change actif, ligne `Change:`, change implicite

> Lot **6/16** du milestone « D — Conformité et gestion du changement », épique #193
> (`specs/GH193.md` §2.2–§2.4, §11, lot L4). S'appuie sur l'objet change de #198 et sur l'analyse
> et le backlog de #199 (`specs/GH199.md` §8bis). Modèle d'ensemble : `specs/MODELE-OBJETS.md`.
> Depuis GH199 §8ter, « change » désigne un **changeset** (catégorie `changeset`, dossier
> `changesets/`, vue « Changesets ») ; les identifiants internes du code restent `Change*`.

## Contexte

État du code (`milestone-D` @ 98c3423) :

- **Publier** (`publishWorkspace` / `publishRepo`, `ModificationControl`) : un titre saisi, un commit
  par repo qui a du travail (enfants avant parents), sur une branche éphémère `dev-<slug>` puis merge
  dans l'intégration. Le message de commit est le titre seul.
- Un change porte `toModify` (`planned` | `modified`) — `modified` n'est jamais posé aujourd'hui —
  et `impacted`. Le **backlog** (#199 §8bis) recueille les éléments à traiter non assignés ; à
  l'approbation d'un élément non assigné, un dialogue propose de l'assigner.
- « Déjà approuvé » : déductible de `history.status` (GH77), repli `version > 1`.
- Le **serveur MCP n'effectue aucun commit** (écritures de fichiers seulement) : ses modifications
  sont publiées ensuite par l'interface, et passent donc par la règle de Publier. Les commits
  **hors interface** sont ceux faits en dehors de Polenta (git en ligne de commande, autre outil,
  forge).
- « Analyser l'impact » sur un élément (#199 §5) propose les changes ouverts qui le listent ; le
  change **actif** était renvoyé à ce lot.

## 1. Élément officiel et préférence `changeTracking`

- Un élément (exigence ou test) est **officiel** s'il a été approuvé au moins une fois **avant la
  modification** : son fichier à `HEAD` a une entrée `isApproval` dans `history.status` (repli :
  `version > 1`). Un élément créé dans la modification, ou jamais approuvé, ne l'est pas. Approuver
  pour la première fois un brouillon n'est donc pas une modification d'élément officiel (cette
  approbation passe par le dialogue d'assignation de #199 §8bis).
- Seuls les fichiers d'**exigences et de tests** comptent. Liens (`links/links.yaml`), paramètres,
  schéma, arbres, campagnes, changes, pins : jamais soumis à la règle (Q1).
- Préférence projet `preferences.changeTracking` (schéma du **repo racine**, onglet Préférences du
  modèle de données) :

  | Valeur | Choix exigé à Publier quand… | Change implicite |
  |---|---|---|
  | `officialOnly` (défaut, absent) | le commit modifie un élément officiel | oui |
  | `always` | le commit modifie une exigence ou un test, quel qu'il soit | oui |
  | `off` | jamais | non |

- `preferences.implicitChangeType` (facultatif) : type du change implicite, sinon le premier type de
  la catégorie déclaré dans le schéma du repo.
- Sans type de catégorie changeset dans le schéma d'un repo, ce repo n'est soumis à aucune règle
  (rien à quoi rattacher), quelle que soit la préférence.

## 2. Change actif

- Un **change actif par repo**, choisi :
  - dans la **barre d'état** : indicateur « Change : NC-0004 » (ou « aucun change actif »), menu
    listant les changes **ouverts** (non terminaux) de chaque repo, regroupés par repo, plus
    « Aucun » ;
  - dans le **panneau Version**, sur le dossier de chaque repo (même menu, limité au repo) ;
  - depuis la page d'un change : bouton **« Rendre actif »** / « Actif ✓ ».
- **Portée** : préférence **locale à l'utilisateur** (application desktop : réglages locaux par
  chemin de repo ; client web : par utilisateur et par repo), **non versionnée** — c'est le contexte
  de travail de chacun, pas une donnée du projet (Q2).
- Un change actif qui passe dans un statut terminal, est supprimé ou introuvable **cesse d'être
  actif** (GH193 §11) ; l'indicateur revient à « aucun ».
- L'analyse des **modifications locales** (`/changesets/local`, §4.7) affiche en tête, par repo, le
  change actif qui recevra ces modifications (ou « aucun : choix exigé à Publier » si la règle
  l'exige).
- **« Analyser l'impact »** sur un élément (#199 §5) : s'il y a un change actif dans le repo de
  l'élément, il est proposé **en premier** (« Ajouter à NC-0004 (actif) » : élément ajouté à
  `toModify` `planned` s'il n'y est pas, puis ouverture du change), suivi des autres entrées
  existantes (changes qui listent l'élément, « Créer un change »).

## 3. Publier

### 3.1 Rattachement d'un commit

- Pour chaque repo à publier, Polenta détermine les **éléments modifiés** (fichiers d'exigences et de
  tests créés, modifiés ou supprimés dans la modification, vs `HEAD`) et ceux d'entre eux qui sont
  **officiels** (§1).
- Le commit du repo est **rattaché** à un change :
  - **le change choisi** dans le popup pour ce repo (§3.2), sinon
  - **le change actif** du repo, s'il y en a un.
- Un commit rattaché porte une **ligne finale** `Change: <ID>` (après une ligne vide sous le titre) :

  ```
  Ajustement du seuil de surintensité

  Change: NC-0004
  ```

  La ligne est écrite **même si aucun élément officiel n'est modifié** (GH193 §2.3 : elle ne coûte
  rien), y compris avec `changeTracking: off`.
- **Éléments ajoutés à `toModify`** : tous les éléments modifiés du commit (officiels ou non) sont
  ajoutés au change rattaché avec `state: modified` (un élément déjà `planned` passe `modified`) —
  Q3. Le fichier du change est écrit **avant** le commit et part dans le même commit (le change est
  dans le repo qu'il change).
- Un commit non rattaché n'a pas de ligne `Change:` et ne touche aucun change.

### 3.2 Choix exigé

- À l'ouverture du popup Publier, pour chaque repo à publier : si la règle (§1) exige un choix et
  qu'il n'y a **pas de change actif** dans ce repo, le popup affiche une section **« Rattacher à un
  change »** par repo concerné :
  - la liste des éléments officiels modifiés (ID, titre ; `always` : tous les éléments modifiés) ;
  - un choix obligatoire parmi :
    1. **un change ouvert existant** du repo (menu) ;
    2. **un nouveau change** : type (pré-sélectionné s'il est seul) et titre saisis dans le popup,
       composant déduit ou à choisir comme à la création (#198 §3) ; créé au moment de la
       publication, dans le même commit ;
    3. **le change implicite** du repo (§4), libellé « Modifications non rattachées (à qualifier) » ;
  - une case **« En faire le change actif »** (cochée par défaut pour les choix 1 et 2, décochée
    pour le change implicite).
- **« Publier » est désactivé** tant qu'un repo concerné n'a pas de choix ; un message en indique
  la raison (« Choisissez un change pour motor-control »). Rien n'est publié tant que tous les repos
  concernés n'ont pas leur choix (le choix est vérifié avant tout fetch, comme les branches
  bloquées).
- Avec un change actif dans le repo, le popup affiche simplement « Rattaché à NC-0004 (actif) » avec
  un lien **« Changer »** qui ouvre la même section de choix (choix pour ce commit seulement).
- Les repos qui ne publient qu'une mise à jour de pin, ou sans élément soumis à la règle, n'ont pas
  de section (mais reçoivent la ligne `Change:` s'ils ont un change actif).
- Si le contenu à publier change pendant que le popup est ouvert (popup « périmé » existant), les
  sections sont recalculées.
- Cas GH193 §11 : modifications officielles dans deux repos, change actif dans un seul → la section
  n'apparaît que pour l'autre. (« Étendre au composant… » proposé en premier : L7, #208.)

### 3.3 Reprise après conflit et branches hors intégration

- Le rattachement est décidé une fois, à la soumission ; la reprise après résolution d'un conflit
  (GH37) et le « Publier sans fusionner » (GH133) gardent le même titre **et les mêmes lignes
  `Change:`** par repo.

## 4. Change implicite

### 4.1 Création et contenu

- **Un seul change implicite ouvert par repo** (GH193 Q1). Fichier `changesets/<ID>.yaml` ordinaire
  avec `implicit: true`, ID au préfixe de son type (§1), titre généré « Modifications non
  rattachées — depuis le <date> », statut initial du type, `component` déduit si le repo n'a qu'un
  composant local, **vide** sinon (GH193 §11).
- **Créé** la première fois qu'il est choisi à Publier (§3.2, choix 3) ; ensuite, les publications
  qui le choisissent s'y rattachent (ligne `Change: <ID>`).
- **Commits hors interface** (§5) : ils lui sont **attribués** sans qu'aucun fichier soit écrit
  tant que personne n'agit (Q4) : la liste du panneau affiche alors une entrée
  **« Modifications non rattachées (à qualifier) »** même si le fichier n'existe pas encore. Le
  fichier est créé à la première action (Nommer, Répartir, Rendre actif, choix à Publier).
- Dans le panneau Changesets : **en tête de la liste du repo**, badge « à qualifier », compteur de
  commits. Il a la même page et la même analyse d'impact qu'un autre change.

### 4.2 Nommer

- **« Nommer »** (page du change implicite) : titre, champs du type, composant (obligatoire s'il
  était vide) → `implicit` retiré, c'est un change ordinaire. L'ID et le type sont **conservés**
  (les lignes `Change: <ID>` déjà écrites restent valides).
- Pour lui donner **un autre type**, « Nommer » propose « Nouveau change d'un autre type » : crée le
  change choisi, y **répartit tous les commits** (§4.3), puis supprime le change implicite vide
  (Q5).

### 4.3 Répartir

- **« Répartir… »** : sélection multiple de commits du change implicite → « Attribuer à… » un change
  ouvert du repo, ou « Nouveau change » (pré-rempli). Les éléments modifiés par ces commits sont
  ajoutés à `toModify` (`modified`) du change cible ; ils restent dans `toModify` du change implicite
  s'ils sont aussi modifiés par un commit qui y reste, sinon ils en sont retirés.
- Quand le change implicite n'a plus aucun commit, il est **supprimé** (pierre tombale GH20), même
  s'il a déjà été publié — exception à la règle de suppression de #198 §5 (Q5) : il n'a jamais eu de
  contenu propre.

## 5. Attribution des commits

### 5.1 Règle

Le change d'un commit se lit, par ordre de priorité :

1. une **attribution enregistrée** dans un change (`commits`, §5.2 : régularisation, répartition) ;
2. la **ligne finale** `Change: <ID>` du message ;
3. sinon, si le commit est **hors interface et soumis à la règle** : le **change implicite** du
   repo, signalé « hors interface ».

Un commit est attribué à **un seul** change. Les commits de merge (deux parents) ne sont jamais
attribués : seuls les commits qui portent la modification le sont (la ligne survit au merge, GH193
§2.3).

- **Soumis à la règle** = commit non-merge qui modifie un élément officiel **au commit parent**
  (`officialOnly`) ou une exigence / un test (`always`). Avec `off` : pas d'étape 3.
- **Point de départ** : seuls les commits **postérieurs à l'activation** du suivi sont examinés
  (Q6) : le premier commit du repo dont le schéma déclare un type de catégorie changeset. Avant, il
  n'y avait rien à quoi rattacher.
- **Périmètre lu** : historique de la branche courante (`HEAD`). Lecture paresseuse, à l'ouverture
  de la vue Changesets et d'une page de change, puis sur changement de `HEAD` (publication, pull,
  checkout) — mise en cache par SHA.

### 5.2 Stockage

```yaml
# changesets/NC-0004.yaml — ajouts de ce lot
implicit: true                 # change implicite (absent sinon)
commits:                       # attributions enregistrées (§5.1, priorité 1) — absent si vide
  - { sha: 9f3c2a1, by: lolive, at: 2026-10-30T14:02:11Z, source: attached }
```

- `commits` ne contient **que** les attributions enregistrées : régularisation (`source: attached`)
  et répartition depuis le change implicite (`source: distributed`). Les commits à ligne `Change:`
  et les commits hors interface sont **lus dans git**, jamais recopiés (pas d'écriture à chaque
  publication, pas de divergence avec l'historique).
- `toModify` reçoit les éléments `modified` (§3.1, §4.3, §5.3).

### 5.3 Rattacher des commits… (régularisation)

- Depuis la page d'un change ouvert : **« Rattacher des commits… »** liste les commits récents du
  repo (50 derniers de la branche, comme les bornes de #199 §3, + SHA saisi), avec pour chacun son
  change actuel (« aucun », « NC-0007 (implicite) », « EVO-0002 »…). Sélection → attribution
  enregistrée dans `commits` du change ; les éléments modifiés rejoignent `toModify` (`modified`).
- Un commit déjà attribué à un **autre change non implicite** demande confirmation (« Réattribuer de
  EVO-0002 à NC-0004 ? ») ; l'attribution enregistrée la plus récente l'emporte, l'ancienne est
  retirée du change d'origine.
- « Détacher » sur un commit enregistré le retire de `commits` (il revient à sa ligne `Change:` ou
  au change implicite).

## 6. Page d'un change

- Nouvelle section **« Commits »** : SHA court, date, auteur, titre, origine (`Change:` / rattaché /
  réparti / hors interface), éléments modifiés ; actions « Rattacher des commits… », « Détacher »,
  et pour le change implicite « Répartir… ».
- Liste **Éléments à modifier** : badge `prévu` / `modifié` (déjà en place), et pour un élément
  `modified` les commits qui l'ont modifié (infobulle).
- En-tête : « Rendre actif » / « Actif ✓ » (§2) ; pour le change implicite, bandeau « À qualifier »
  avec « Nommer » et « Répartir… ».
- Historique (GH77) : inchangé.

## 7. Graphe de données et MCP

- Graphe (#74) : `GraphChange` gagne `implicit` et `commits` = **tous** les commits attribués
  (enregistrés + lignes `Change:` + hors interface), `{ sha, at, by, title, source:
  'line' | 'attached' | 'distributed' | 'outside' }` — donnée brute lue dans git. Contrat v1 étendu,
  `polenta.d.ts` régénéré.
- MCP : `get_change` / `list_changes` renvoient `implicit` et `commits`. Pas d'outil de change actif
  ni de régularisation dans ce lot. Le MCP ne commite pas : rien à exiger de lui.

## 9. Critères d'acceptation

- [ ] Élément officiel (§1), préférences `changeTracking` et `implicitChangeType` (lecture, édition
      dans les préférences du modèle de données).
- [ ] Change actif par repo : barre d'état, panneau Version, page du change ; local à l'utilisateur ;
      désactivé au statut terminal / à la suppression.
- [ ] Publier : section de choix par repo, Publier bloqué sans choix, ligne `Change:`, `toModify`
      `modified` dans le même commit, nouveau change et change implicite créés dans le commit,
      reprise GH37 / GH133 avec les mêmes lignes.
- [ ] Change implicite : unique par repo, entrée calculée pour les commits hors interface, Nommer,
      Répartir, suppression quand vide.
- [ ] Attribution des commits (§5.1) : priorité, merge ignorés, point de départ, cache par SHA.
- [ ] « Rattacher des commits… », « Détacher », section Commits de la page d'un change.
- [ ] « Analyser l'impact » propose le change actif ; modifications locales affichent le change actif.
- [ ] Graphe (`implicit`, `commits`) + `polenta.d.ts` ; MCP.
- [ ] Tests unitaires (officiel, règle, attribution, message de commit, implicite) et e2e (A1–A6,
      A8–A13).

## 10. Indicateurs (GH79)

« Élément officiel » et l'attribution des commits servent une fonction de Polenta (règle de
Publier, contenu d'un change) : calculés dans Polenta. Aucun indicateur de suivi (commits par
change, délais, part de hors interface…) : côté projet, via `commits` du graphe.

## 11. Hors périmètre

- « Étendre au composant… », changes liés multi-repo : L7 (#208).
- Contraintes de transition (dont `assignedToChange`) : L1 (#206).
- Campagnes du change : L6 (#207). Versions de composant (`integratedIn`) : L5 (#201).
- Réécriture de l'historique git : jamais (les attributions a posteriori sont enregistrées).
- Contrôle des écritures MCP (elles sont publiées par l'interface) et hooks git côté forge.

## 12. Questions

| # | Question | Proposition |
|---|---|---|
| Q1 | Quels fichiers déclenchent la règle ? | exigences et tests seulement ; un lien modifié sur un élément officiel ne l'exige pas (le lien est stocké à part) |
| Q2 | Où vit le change actif ? | préférence locale à l'utilisateur, par repo, non versionnée |
| Q3 | Avec un change rattaché, quels éléments rejoignent `toModify` ? | **tous** les éléments modifiés du commit (les brouillons sont ainsi assignés et quittent le backlog) ; la règle « officiel » ne décide que si le choix est exigé |
| Q4 | Commits hors interface : écrire le change implicite à la détection ? | non : attribution calculée, entrée affichée sans fichier ; fichier créé à la première action (évite des écritures que personne n'a demandées, à chaque lecture, chez chaque utilisateur) |
| Q5 | Nommer avec un autre type / supprimer l'implicite vide déjà publié | autre type = nouveau change + répartition de tous les commits ; implicite vide supprimé (pierre tombale) même publié |
| Q6 | Point de départ de l'examen des commits hors interface | premier commit où le schéma du repo déclare un type changeset ; avant, aucun commit n'est attribué |
| Q7 | Commit modifiant des éléments de deux composants locaux d'un même repo | un seul change par commit (celui choisi ou actif) ; pas de découpage du commit — le multi-composant relève de L7 |
