## Contexte

État du code (`milestone-D` @ c2c4f99) :

- Changeset (#198, #199) : `toModify: [{ id, state: planned | modified }]`, `impacted`, analyse
  live / figée au statut terminal, **backlog** calculé par composant, dialogue « Assigner à un
  change » à l'approbation d'un élément non assigné (`ApprovalGateContext`,
  `ChangesService.approvalCheck`).
- Écritures d'éléments : `RequirementsService` / `TestsService` — `create`, `update`,
  `openDraft` (réouverture, version + 1), `transition` (exigences) ; MCP `bulk_import_requirements`,
  `bulk_import_tests`, `update_requirements`, `update_tests`.
- **Verrou de l'approuvé non uniforme** : la vue Word verrouille l'édition d'un élément au statut
  `isApproval` (« Rouvrir en brouillon ») ; la vue Excel (`canEdit`), les éditeurs et les services
  ne le font pas — un élément approuvé peut être modifié sans réouverture.

## 1. Principe et préférence

- **Toute modification d'une exigence ou d'un test se fait dans un changeset** : création,
  travail sur un brouillon, réouverture, passage à un statut terminal depuis l'approuvé.
- Préférence `preferences.changeTracking: on | off` dans le schéma de **chaque repo** (onglet
  Préférences du modèle de données). Absente : `on` si le schéma du repo déclare au moins un type de
  catégorie changeset, sinon `off`. Avec `off`, rien n'est exigé (changesets manuels possibles).
  La règle d'un élément est celle du repo qui le stocke.

## 2. Verrou de l'approuvé

- Un élément au statut `isApproval` **n'est pas modifiable** (titre, champs, étapes, objet type,
  préconditions…) : vues Word, Excel, éditeurs (exigence, test), tableaux, édition groupée, MCP.
  Seules restent possibles les transitions de statut (dont « Rouvrir en brouillon ») et les
  écritures qui ne modifient pas le contenu (liens, `needsRevalidation`, historique, renommages du
  schéma, rangement des arbres).
- Dans l'interface : cellules et champs en lecture seule avec l'action **« Rouvrir en brouillon »**
  (existante en vue Word) disponible partout. Dans les services : écriture refusée (erreur
  explicite « SYS-0002 est approuvée : rouvrez-la pour la modifier »), ce qui couvre le MCP.
- Le verrou s'applique quelle que soit `changeTracking` : c'est le sens d'« approuvé ».

## 3. Assignation quand l'élément devient modifiable

### 3.1 Moments

| Action | Élément concerné |
|---|---|
| **Créer** (formulaire, vue Excel / Word, duplication, import) | le nouvel élément |
| **Rouvrir** (approuvé → non approuvé, `openDraft` / transition / colonne Statut) | l'élément |
| **Passer à un statut terminal** depuis l'approuvé (ex. obsolète, P5) | l'élément |

Un élément **déjà** dans `toModify` d'un changeset **non clos** (statut non terminal) du repo y
reste : pas de question (P4). Sinon (aucun, ou seulement des changesets clos) : assignation.

### 3.2 Choix du changeset

Changesets **éligibles** : ouverts (non terminaux) du repo de l'élément (même règle que
l'assignation de #199 §8bis).

- **Un seul** éligible → assignation **automatique**, signalée par un toast « Ajouté à NC-0004 ».
- **Plusieurs** → dialogue **« Dans quel changeset ? »** : liste (ID, type, titre, statut), dernier
  utilisé pré-sélectionné ; « Nouveau changeset… ».
- **Aucun** → formulaire de création de changeset (type, titre, composant de l'élément), avec
  l'élément dans `toModify`.
- **Annuler** annule l'action (pas de création, pas de réouverture, statut inchangé).
- Création **en masse** (import, duplication de plusieurs éléments, P2) : **un** choix pour tout le
  lot.

L'élément est ajouté à `toModify` avec `state: planned` et sa **version de départ** (§4) ; le fichier
du changeset est écrit en même temps que l'élément (publiés ensemble).

### 3.3 MCP

- `bulk_import_requirements` / `bulk_import_tests` et les mises à jour de statut de
  `update_requirements` / `update_tests` acceptent un paramètre facultatif `changesetId` (changeset
  ouvert du repo) pour les éléments créés ou rouverts.
- Sans `changesetId` (règle `on`) : un seul éligible → assignation automatique ; sinon l'élément
  est créé / rouvert **sans assignation** et rejoint le **backlog** ; la réponse le signale
  (`unassigned: [ids]`). Le MCP n'échoue pas pour autant (P2).
- Modifier le contenu d'un élément approuvé via le MCP : refusé (§2).

## 4. Trace par élément : départ, approbation, diff

```yaml
# changesets/NC-0004.yaml — toModify enrichi
toModify:
  - id: SYS-0002
    state: modified
    base: { sha: 4be1f09, version: 3 }   # état approuvé avant réouverture ; absent = création
    approved: { sha: a91c3d2, version: 4 }   # écrit au gel (statut terminal du changeset)
  - id: SYS-0031
    state: modified                      # créé dans ce changeset : pas de `base`
```

- **`base`** (version de départ) : enregistrée à l'assignation par réouverture = dernier commit qui
  touche le fichier de l'élément à `HEAD` (l'état approuvé) et sa `version`. **Absente** pour une
  création. Un élément planifié à la main (`planned`, sélecteur #198) reçoit sa `base` à la
  réouverture si elle survient dans ce changeset.
- **`approved`** (commit d'approbation) : **calculé** tant que le changeset est ouvert = dernier
  commit, postérieur à `base`, où le fichier de l'élément est à un statut `isApproval` ; plusieurs
  cycles rouvrir / approuver dans le même changeset → une seule ligne, départ = premier état,
  approbation = dernière (P3). **Figé** dans le fichier au passage du changeset à un statut terminal
  (avec l'analyse, GH199 §2) ; effacé s'il est rouvert. Non approuvé à la clôture : `approved`
  absent, ligne marquée « non approuvé à la clôture ».
- **`state: modified`** : posé dès qu'un commit postérieur à `base` (ou la création) touche
  l'élément ; `planned` sinon.
- **Diff** : depuis la ligne, **« Voir les modifications »** ouvre la vue de diff existante (rendu
  générique GH222, `/diff`) entre `base` et `approved` — ou entre `base` et l'état courant s'il n'est
  pas encore approuvé ; création : contenu complet face à « vide ».
- Élément supprimé physiquement (jamais approuvé, #184) : la ligne reste, « supprimé » (#198 §4).

## 5. Modifications hors interface

- Un élément **au statut `isApproval`** dont le contenu diffère de son état d'approbation (commit où
  il est passé approuvé, ou fichier sur disque non publié) a été modifié **hors interface** (git
  direct, éditeur de texte, autre outil) : le verrou de l'application l'empêche autrement.
- Il apparaît dans le **backlog** de son composant, marqué **« modifié hors interface »**, avec
  « Voir les modifications » (diff état d'approbation → état actuel) et l'action **« Rouvrir et
  assigner… »** (réouverture + §3.2, `base` = commit d'approbation). Rien n'est écrit tant que
  personne n'agit.
- Détection au calcul du backlog, mise en cache par `HEAD` (et invalidée sur changement de
  fichier) ; uniquement si `changeTracking: on`.

## 6. Backlog et dialogue d'approbation (#199 §8bis)

- Le backlog reste et devient un **filet** : éléments à traiter non assignés (créés avant
  l'activation de la règle, créés / rouverts par le MCP sans changeset, retirés d'un changeset,
  changeset clos avant approbation) et éléments modifiés hors interface (§5).
- Le dialogue « Assigner à un change » à l'approbation reste, pour ces mêmes cas.

## 7. Page d'un changeset

- Liste **Éléments à modifier** : colonnes **Départ** (version + commit court, ou « création »),
  **Approbation** (version + commit court, « en cours », ou « non approuvé à la clôture »), état
  `prévu` / `modifié`, action « Voir les modifications ».
- Rien d'autre ne change (analyse, listes, historique).

## 8. Graphe de données et MCP

- Graphe (#74) : `GraphChange.toModify[]` gagne `base` et `approved` (`approved` calculé pour un
  changeset ouvert, lu dans le fichier sinon) — donnée brute utilisée par #207
  (`modifiedApproved`). `polenta.d.ts` régénéré.
- MCP : `get_changeset` renvoie `base` / `approved` ; paramètre `changesetId` (§3.3).
