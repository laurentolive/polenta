# GH201 — Version de composant / produit : changements, backlog, tag au passage released

> Spec validée le 2026-11-02 (P1–P3 acceptés tels que proposés).
>
> **Retours de validation (2026-11-02, projet PH2)** — remplacent ce qui suit là où ils divergent :
> - **Plusieurs versions en cours** par repo (P3 abandonné) : « Nouvelle version » n'est plus désactivée ;
>   le backlog propose la **liste des versions en cours** comme cible ; un élément inclus dans l'une
>   d'elles sort du backlog. L'ordre des livraisons est la date de gel (`freeze.at`), plus l'ordre des ID.
> - **Panneau Produit** : composant choisi en liste déroulante, case « abandonnées » dessous, backlog
>   des changements, puis versions du composant seulement, dépliables sur la structure des composants
>   (cube, label, version à droite).
> - **Sous-composant sans type version** : visible dans la structure (« Pas de type version ») ; le choisir
>   affiche un message qui renvoie au modèle de données.
> - **Clic droit sur une version** : Copier, Coller (nouvelle version en cours dans le même composant,
>   mêmes changements, sans gel), Supprimer (pierre tombale ; refusé pour une version figée, released
>   ou abandonnée après l'avoir été). Pas de notion de version par défaut.
>

## Contexte

État du code (`milestone-D` @ 09dad90, après #243) :

- Catégories d'objet : `requirement | test | campaign` (`packages/types/src/schema.ts`).
- Le changeset est retiré ; restent le verrou de l'approuvé (`approved-lock.util`), `versionBump`,
  le diff par élément (`sync:diff-element`, route `/diff?element&baseSha&toSha`) et le moteur
  d'arbres d'impact.
- Code de référence retiré par #243, au commit `4e06052` : backlog (`ChangesService.backlog`,
  `useBacklog`, `changesets_.backlog`), détection hors interface (`ChangeTrackingService` :
  `outsideModifications`, `fileCommits`, `baseOf`), sélecteur d'éléments (`ChangeElementPicker`).
  L'ancien backlog listait les éléments « à traiter » (ni approuvés ni terminaux) non assignés à
  un changeset ouvert : la règle change (§4).
- Baselines : tags git posés par `baseline:create` (`SyncService.createTag` /
  `createAnnotatedTag`), **locaux** — aucun push de tag aujourd'hui.
- Multi-repo : composants en repo séparé déclarés dans `polenta-repo.yaml` (`dependencies[]`,
  `pin` = commit ou tag) ; composants locaux = nœuds enfants du schéma d'un repo (T123).

## Décisions (questions tranchées le 2026-10-31)

| # | Question | Décision |
|---|---|---|
| Q1 | Backlog de la première version (sans `basedOn`) | **tout le composant** : même règle que pour les suivantes (tous les éléments, jamais inclus, sont au backlog) ; bouton « Tout inclure » |
| Q2 | Statuts d'une version | **configurables** comme les autres types ; Polenta ne lit que les marques `isApproval` (= released : gel, tag, verrou) et `isTerminal` (= abandonnée) ; tout autre statut = « en cours » |
| Q3 | Tag | convention **`<projet>-<version>`** (pré-rempli, modifiable) ; tag existant → refus du passage |
| Q4 | Composant local (nœud enfant sans repo propre) | **pas de versions propres : une version par repo**. Les éléments des nœuds locaux appartiennent à la version de leur repo |

« Composant » désigne donc, dans tout ce lot, **un repo** du workspace (racine ou dépendance de
`polenta-repo.yaml`).

## 1. Type et objet version

### 1.1 Type

- Nouvelle catégorie **`version`** (`ObjectCategory`). Un type de cette catégorie se déclare sur le
  **nœud `root`** du schéma du repo (onglet Structure), avec `prefix` (unique sur le projet),
  `fields` du projet, `statuses`.
- **Au plus un type `version` par repo** ; refusé sur un nœud enfant local (validation du schéma,
  message explicite).
- À la création du type dans l'éditeur de schéma, statuts pré-remplis : `en_cours` (En cours),
  `released` (Released, `isApproval`), `abandonnee` (Abandonnée, `isTerminal`) ; champ par défaut
  `description` (richtext). Le projet peut les renommer / en ajouter (GH82 s'applique).
- Un repo sans type `version` n'a pas de versions : il n'apparaît dans le sous-panneau Produit
  qu'avec la mention « pas de type version » et n'est pas proposé dans `components`.

### 1.2 Fichier

`versions/<ID>.yaml` dans le repo du composant ; IDs séquentiels déduits du disque + pierres
tombales (GH20) ; `history` (GH77, statut historisé par défaut).

```yaml
# versions/MCV-0004.yaml   (repo motor-control)
id: MCV-0004
objectTypeRef: root::version
title: "1.2.4"                     # label
status: en_cours
version: 1
basedOn: MCV-0003                  # version précédente du même repo ; absent pour la première
components:                        # versions des dépendances (polenta-repo.yaml), par nom de montage
  bms: BMSV-0002
changes:                           # éléments inclus (exigences, tests — issues : #244)
  - id: SW-0042
    base: { sha: 4be1f09, version: 3 }   # état dans la dernière version released qui l'incluait
  - id: SW-0051                          # sans base : jamais inclus dans une version released
freeze: { tag: motor-control-1.2.4, sha: a91c3d2 }   # posé au passage released seulement
fields:
  description: <p>…</p>
history: …
```

- Champs système nouveaux : `basedOn`, `components`, `changes`, `freeze`. Les champs `campaigns`,
  `impacted`, `analysis` de MILESTONE-D §3.1 sont posés par #245 ; `changes[]` accepte d'avance des
  entrées d'issues (#244) sans qu'aucune ne soit créée ici.
- Label = `title` ; non vide, **unique parmi les versions non abandonnées du repo**.

## 2. Cycle de vie

- **Une seule version en cours par repo** à la fois (« Nouvelle version » est désactivée tant
  qu'il en existe une, avec l'ID de celle-ci en infobulle). L'historique des versions d'un repo est
  donc une chaîne `basedOn`.
- **Création** (« Nouvelle version ») : label saisi ; `basedOn` pré-rempli avec la dernière version
  released du repo (modifiable parmi les released, ou vide) ; `components` pré-remplis avec la
  dernière version released de chaque dépendance qui a un type version (modifiables : n'importe
  quelle version de la dépendance, ou vide). `changes` vide.
- **En cours** : `title`, `basedOn`, `components`, `changes`, `fields` modifiables ; les
  changements sont lus à l'état courant (HEAD + disque) du repo.
- **Abandon** (statut `isTerminal`) : la version sort des listes par défaut ; ses `changes` ne
  comptent plus pour le backlog (§4) ; son label redevient disponible.
- **Composant en lecture seule** : aucune création ni écriture de version depuis le produit
  (`READONLY_REPO`, comme pour les autres objets) ; consultation possible.

## 3. Passage released

Déclenché par le passage au statut `isApproval` (sélecteur de statut de la page), avec un dialogue
de confirmation :

1. **Tag** pré-rempli **`<projet>-<label>`**, modifiable, où `<projet>` est le nom du repo dans le
   workspace (nom de montage pour une dépendance, nom du dossier pour le repo racine). Caractères
   interdits par git remplacés par `-` dans la proposition ; nom saisi invalide → erreur en ligne.
2. **Contrôles** (refus avec la liste des causes, rien n'est écrit) :
   - le tag existe déjà dans le repo ;
   - une version de `components` n'est pas released ;
   - un élément de `changes` a des modifications non commitées (le gel porte sur un commit) ;
   - le repo est en lecture seule.
3. **Écriture** : `freeze.sha` = HEAD du repo (état figé des éléments inclus), `freeze.tag`,
   statut released (historique GH77) ; **commit** du seul fichier de la version
   (`[version] <ID> <label> released`) ; **tag annoté** sur ce commit (message = label + ID). Le
   contenu des éléments au tag est identique à celui de `freeze.sha` (seul le fichier de version
   diffère).
4. **Push du tag** : le tag est poussé au prochain push du repo (Publier / push de l'intégration)
   — *voir point ouvert P1*.

Une version released est **verrouillée** comme un élément approuvé : ni ses champs, ni `changes`,
ni `components` ne sont modifiables (UI, IPC, MCP) ; elle ne peut **pas** revenir à un statut en
cours (on crée une nouvelle version) — seul le passage à `isTerminal` reste possible, sans effet
sur le tag.

## 4. Backlog d'un composant

Calculé (non stocké), par repo, sur les **exigences et tests** du repo (tous nœuds locaux confondus).

Un élément est **au backlog** s'il n'est pas dans les `changes` de la version en cours **et** :

- **jamais inclus** dans une version released (non abandonnée) du repo — sauf s'il est dans un
  statut terminal (élément créé puis rendu obsolète sans avoir jamais été livré : ignoré) ; ou
- **modifié depuis** la dernière version released qui l'incluait : son contenu courant (disque)
  diffère de son contenu à `freeze.sha` de cette version. Comparaison sur le YAML lu, **hors**
  `history` et `needsRevalidation` (posés par l'application, ce ne sont pas des changements).

Chaque ligne affiche : ID (lien), titre, type, statut, nature (« nouveau » / « modifié »), et le
signal **« modifié hors interface »** (#200 §5 : approuvé dont le contenu a changé sans
réouverture) repris de `outsideModifications`.

Actions : **« Inclure dans <version en cours> »** (une ou plusieurs lignes cochées, « Tout
inclure ») ; **« Voir les modifications »** (diff de l'élément entre `base` et l'état courant,
contenu complet face à « vide » si nouveau). Sans version en cours : inclusion désactivée,
« Nouvelle version » proposée.

**`base` à l'inclusion** (backlog ou « Ajouter ») : `{ sha: freeze.sha, version }` de l'élément
dans la dernière version released qui l'incluait ; absent sinon.

## 5. Page d'une version

- **En-tête** : ID, label (éditable si en cours), statut, version précédente (`basedOn`, lien),
  `fields` du type (description), tag et commit si released.
- **Composants** : une ligne par dépendance du repo (`polenta-repo.yaml`) ayant un type version :
  nom du composant, ID + label de la version retenue (lien), statut ; sélecteur si en cours.
- **Changements** : les `changes` de cette version **et** ceux des versions de chaque dépendance
  postérieures à celle retenue par `basedOn` (chaîne `basedOn` de la dépendance, de
  `components[dep]` exclue… à `components[dep]` de cette version incluse ; récursivement pour les
  dépendances des dépendances). Une ligne par élément :

  | Composant | Version | Type | ID (lien) | Label | Diff |
  |---|---|---|---|---|---|

  Diff « Voir les modifications » : `base` → `freeze.sha` de la version qui porte la ligne (ou
  état courant si elle est en cours) ; sans `base` : contenu complet face à « vide ». Si `basedOn`
  est vide, toutes les versions de la dépendance jusqu'à celle retenue sont prises.
- **Version en cours** : sur les lignes de **ce** composant, **Retirer** (l'élément retourne au
  backlog) ; bouton **« Ajouter »** : sélecteur d'éléments (`ChangeElementPicker` réintroduit) sur
  toutes les exigences et tous les tests du repo, même inchangés ; un élément déjà inclus n'est
  pas proposé.
- Élément de `changes` introuvable (supprimé depuis) : ligne affichée « supprimé », diff vers
  « vide ».

## 6. Sous-panneau « Produit » (panneau Version)

Nouvelle entrée du panneau **Version** :

- **Arbre des composants** : repo racine puis ses dépendances (récursivement, comme la structure
  `polenta-repo.yaml`). Sous chacun : **versions** (label, statut, du plus récent au plus ancien,
  abandonnées masquées par défaut), **Backlog (n)**, bouton **« Nouvelle version »** (absent en
  lecture seule ou sans type version).
- Clic sur une version → page de la version ; clic sur Backlog → vue du backlog du composant.
- Rafraîchi par `useLiveFileSync` comme les autres listes.

## 7. Statut de design (MILESTONE-D §2)

Hors périmètre d'affichage (vues exigence : #210 ; vue Validation : #204/#205), mais ce lot fournit
la donnée : pour une exigence, **première version released de son repo dont l'état figé
(`freeze.sha`) contient l'exigence dans sa `version` courante** — exposée par le main (graphe,
MCP), « — » si aucune. *Corrigé par GH204 §3 (P1) : la version doit inclure l'exigence dans `changes`, et
l'état figé être identique.*

## 8. Graphe et MCP

- Graphe : collection **`versions`** (`id`, `title`, `status`, `component` (repo), `basedOn`,
  `components`, `changes`, `freeze`, `fields`) ; manifeste du graphe incrémenté ; `polenta.d.ts`
  à jour. Statut de design exposé sur les exigences (`designVersion`).
- MCP (lecture seule) : lister les versions d'un composant, lire une version (composants,
  changements avec base), lire le backlog. Le MCP ne crée pas, ne modifie pas et ne passe pas une
  version released.

## Critères d'acceptation

1. Un type `version` se déclare sur le `root` d'un repo (statuts et champ par défaut pré-remplis) ;
   un second type version, ou un type version sur un nœud enfant, est refusé à l'enregistrement.
2. « Nouvelle version » crée `versions/<PREFIX>-NNNN.yaml` (ID GH20), pré-remplit `basedOn` et
   `components` ; elle est désactivée en lecture seule ou sans type (plusieurs versions en cours permises, retours PH2).
3. Premier composant sans version : le backlog liste toutes les exigences et tous les tests non
   terminaux ; « Tout inclure » les met dans `changes` sans `base`.
4. Après passage released d'une version incluant SW-0042, puis modification de SW-0042 (contenu,
   hors `history`) : SW-0042 réapparaît au backlog « modifié » ; inclus dans la version suivante,
   il porte `base: { sha: <freeze.sha>, version }`. Un élément non modifié n'y réapparaît pas.
5. Un élément approuvé modifié sans réouverture apparaît au backlog avec le signal « modifié hors
   interface ».
6. « Retirer » remet l'élément au backlog ; « Ajouter » permet d'inclure un élément inchangé.
7. « Voir les modifications » ouvre le diff générique (GH222) `base` → état courant (en cours) ou
   `freeze.sha` (released) ; nouveau : face à « vide ».
8. Page d'une version produit : les changements des dépendances postérieurs à `basedOn` sont
   listés avec composant et version d'origine.
9. Passage released : refusé (rien d'écrit) si le tag existe, si une version de `components`
   n'est pas released, ou si un élément inclus a des modifications non commitées ; sinon commit
   du fichier de version, tag annoté `<projet>-<label>` (ou saisi) sur ce commit, `freeze` renseigné.
10. Une version released n'est plus modifiable (UI, IPC, MCP) et ne peut pas revenir en cours.
11. Composant en lecture seule : création et écriture de version refusées (`READONLY_REPO`).
12. Graphe `versions` et outils MCP de lecture disponibles ; scripts Suivi et `polenta.d.ts` à jour.

## Points ouverts (à confirmer à la validation de la spec)

- **P1 — Push du tag** : proposé « poussé au prochain push du repo ». Alternative : tag local
  comme les baselines actuelles (les autres postes ne verraient pas le tag de la version).
- **P2 — `<projet>`** : proposé = nom du repo dans le workspace. Alternative : nom du produit
  (label du `root` du repo racine) pour tous les composants.
- **P3 — Une seule version en cours par repo** (§2) : simplifie l'inclusion depuis le backlog.
