# GH202 — Version testée de l'exécution : copie de la structure testée dans le run

> Lot **5/9** du milestone « D — Conformité et gestion du changement ». Spec globale :
> `specs/MILESTONE-D.md` §6, qui fait foi. Remplace `specs/GH191.md` §2.5 (`configurationRef`, version prévue).

## But

Tracer **sur quelle version** chaque test a été exécuté, pour que la qualité puisse juger une preuve
au moment de la validation (#204, #205). Une version en cours peut évoluer après l'exécution : le run
garde donc une **copie figée** de ce qui a été testé, comparable à l'état courant de la version.

## Décisions à valider

| # | Question | Proposition | Alternative |
|---|---|---|---|
| Q1 | **Quelle version choisir ?** | Une version du **repo de la campagne** : version produit pour une campagne du repo produit, version du composant pour une campagne du repo du composant. Un test de composant exécuté depuis une campagne produit référence donc la version produit | Toujours la version produit, même depuis le repo d'un composant |
| Q2 | **Saisie obligatoire ?** | **Oui** dès que le repo de la campagne a au moins une version sélectionnable : une version, ou un texte libre (écart non documenté). Refus à l'enregistrement sinon | Facultative : une exécution peut rester sans version, et la qualité le voit à la validation |
| Q3 | **Copier la liste des changements ?** | **Oui pour une version en cours** : c'est ce qui peut évoluer après l'exécution. Pas pour une version released, figée par nature | Structure seule (version, composants, commit) : run plus léger, mais un changement ajouté à la version après l'exécution passe inaperçu |

La suite est écrite avec ces propositions.

## 1. Champ `testedConfig` du run

Champ système, écrit une seule fois comme le reste du run (immuable). Toutes les données sont copiées :
la preuve reste lisible si la version change ou disparaît.

```yaml
# test-runs/TST-0012/TST-0012-run-0004.yaml
testedConfig:
  component: aspirateur-v1    # repo de la version testée (nom de montage, ou dossier du repo racine)
  ref: PRDV-0003              # version testée
  label: "1.2.0"
  state: in_progress          # in_progress | released, au moment de l'exécution
  commit: a91c3d2…            # HEAD du repo à l'enregistrement
  changes: [SYS-0042, ISS-0007]   # version en cours seulement (Q3)
  components:                 # récursif, comme la structure de la version
    motor-control:
      ref: MCV-0004
      label: "1.2.4"
      state: released
      commit: 4be1f09…
      expected: MCV-0003      # écart : la version testée prévoyait MCV-0003
    turbine:
      undocumented: "TRB-200 ind. C-bis"   # écart non documenté : valeur libre
      expected: TRBV-0001
```

- **Écart** : un composant porte `expected` quand la valeur saisie diffère de la composition de la version
  testée. Il porte `undocumented` quand la valeur ne correspond à aucune version déclarée.
- **Racine sans version déclarée** : `{ component, undocumented, commit }`, sans `ref`.
- **Composant sans valeur** : clé absente. C'est le cas d'un composant que la version ne renseigne pas, ou
  d'un repo sans type version où rien n'a été saisi ; ce n'est pas un écart.
- **Commit** : `HEAD` de chaque repo à l'enregistrement. Pour un import Excel, c'est donc le moment de
  l'import, pas celui du test.
- **Absent** : run antérieur à ce ticket, ou repo de la campagne sans version sélectionnable. Affiché « — ».
  Aucune reprise des anciens runs.
- **Écriture** : l'appelant n'envoie que le choix (`ref` ou texte libre, et les écarts par composant). Le main
  construit la copie dans `TestsService.execute`, point unique de la page d'exécution et de l'import.

## 2. Saisie à l'écran d'exécution

- Bloc **« Version testée »** en tête de page : liste des versions du repo de la campagne, en cours et
  released, abandonnées exclues, plus la saisie libre.
- **Structure repliable** sous la liste : une ligne par composant, avec sa version dans la composition.
  On ne touche que ce qui diffère : autre version du composant, ou texte libre. Une ligne modifiée est surlignée.
- **Pré-remplissage** : version et écarts de la **dernière exécution de la campagne**, sans rien stocker sur la
  campagne. Sans exécution précédente, ou si cette version est abandonnée ou supprimée : champ vide, pour
  ne jamais attribuer un résultat à une version par défaut.
- **Enregistrement** : refus en ligne si la saisie obligatoire manque (Q2). La proposition d'issue après un
  échec (#244) reste inchangée.

## 3. Classeur Excel (format v4)

- Colonnes **« Version testée »** et une colonne par composant (chemin `motor-control/bms` pour un composant
  imbriqué), sur la première ligne de chaque instance, après les champs d'exécution.
- **Export** : version pré-remplie comme à l'écran (§2) ; colonnes de composant vides, ce qui signifie
  « la composition de la version ». Une valeur saisie y est un écart, ce qui évite un faux écart quand le
  testeur change seulement la version.
- **Import** : ID ou label de version reconnu ; toute autre valeur est un **écart non documenté**, signalé dans
  l'aperçu pour repérer une faute de frappe. Version manquante : erreur par instance `tested_version_missing`.
- **Classeurs v1 à v3** : toujours acceptés, sans `testedConfig` (pas de colonne à lire).

## 4. Consultation

- **Grille d'exécutions** (onglets du test et de l'exigence) : colonnes « Version testée » (visible par
  défaut), « Structure testée », « Commit », « Écarts ». Les écarts sont surlignés, les non documentés en
  priorité. Lien vers la page de la version.
- **Consultation d'un run** : bloc en lecture seule avec la copie complète.
- **Évolution depuis l'exécution** : mention « a évolué » sur la ligne et détail dans le run, par comparaison à
  l'état courant : composant passé à une autre version, changement ajouté ou retiré, version supprimée ou
  abandonnée. Pour un composant en écart, la comparaison porte sur `expected`. Calcul fourni par le main et
  réutilisé par la vue Validation (#205).

**Indicateur (GH79)** : l'écart et l'évolution sont calculés dans Polenta, car ils servent une fonction de Polenta :
le jugement de la preuve dans la vue Validation.

## 5. Graphe et MCP

- Graphe : `GraphTestRun.testedConfig` (`null` si absent) ; manifeste + 1 et `polenta.d.ts` régénéré.
- MCP : aucun outil n'écrit d'exécution aujourd'hui, rien à ajouter. La donnée se lit par le graphe.

## Critères d'acceptation

1. Une exécution enregistrée sur une version en cours écrit `testedConfig` avec version, label, état, commit,
   changements et composants récursifs.
2. Sur une version released, `changes` est absent de la copie.
3. Modifier ensuite la composition ou les changements de la version ne modifie pas le run, et la grille
   affiche « a évolué » avec le détail.
4. Un composant passé à une autre version porte `expected` et apparaît en écart ; un texte libre porte
   `undocumented` et apparaît en écart prioritaire.
5. La deuxième exécution d'une campagne est pré-remplie avec la version et les écarts de la précédente ; la
   première exécution est vide ; une version abandonnée ou supprimée n'est pas reprise.
6. Enregistrer sans version ni texte libre est refusé si le repo a une version sélectionnable, et accepté sinon.
7. Un test de composant exécuté depuis une campagne produit référence la version produit, et son run reste
   stocké dans le repo du composant.
8. La campagne ne porte aucun champ de version, avant comme après une exécution.
9. Un classeur v4 importé écrit la même copie ; une version inconnue est signalée en écart dans l'aperçu ; une
   version manquante donne `tested_version_missing` ; un classeur v3 s'importe sans `testedConfig`.
10. Un ancien run s'affiche « — » sans erreur.
11. Le graphe expose `testedConfig` et `polenta.d.ts` le décrit.
