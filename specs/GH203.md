# GH203 — Vues enregistrées nommées du panneau ⚙️

> Lot **6/9** du milestone « D — Conformité et gestion du changement ». Spec globale :
> `specs/MILESTONE-D.md` (lot inchangé) et `specs/GH191.md` §5.1. **S'écarte de §5.1 sur le stockage
> des vues d'équipe** (Q1). Statut : **validée le 2026-11-03**, Q1 à Q3 retenues telles que proposées.

## But

Le ⚙️ garde un seul réglage par vue et par type. Selon le travail (revue sécurité, analyse d'un
échec), l'utilisateur recoche chaque fois les mêmes colonnes. Il peut désormais enregistrer ces
réglages sous un nom, les retrouver dans une liste et les partager avec l'équipe.

## Constat

- Réglages actuels : `fieldVisibility["<nœud>::<type>"]` dans `.{user}.pref`, non versionné, écrit
  par `pref:set-field-visibility` (écriture partielle, GH176).
- `polenta-config/config.yaml` : un fichier **par organisation**, modifiable par ses seuls
  propriétaires, que l'application lit sans jamais l'écrire (SPEC-ACCOUNTS-AUTH §7).
- GH139 (2026-10-29, décision avec l'humain) a retiré `fieldVisibility` de `polenta-config` : le
  défaut d'équipe des colonnes vit dans `schema.yaml`.
- Les vues Tableau et Document des issues (#244) passent par `SystemView` : elles reçoivent la
  fonction sans code dédié.
- La vue Validation n'existe pas encore (#204).

## Décisions

### Q1 — Où vivent les vues d'équipe ? *(écart à §5.1)*

**Dans le repo du projet**, `.polenta/views/<nœud>/<type>.yaml`, sur le modèle des
requêtes Suivi (partagé : repo ; privé : `.pref`, SPEC-DASHBOARDS §7.0).

| | Repo du projet (retenu) | `polenta-config` (§5.1) |
|---|---|---|
| « Enregistrer sous… » depuis l'écran | oui, puis Publier | non pour un membre : seuls les propriétaires de l'organisation peuvent écrire, et l'application n'écrit pas ce fichier |
| Portée | le projet, dont les types sont propres | l'organisation, à laquelle il faudrait ajouter une clé par projet |
| Sans forge d'organisation (GitHub personnel, autre serveur) | fonctionne | pas de vues d'équipe |
| Historique, revue, branches | ceux de git | hors du projet |
| Réservé à un responsable | non : qui peut publier sur le repo (Publier, droits de la forge) | oui |

L'alternative n'avait qu'un avantage, réserver la modification aux propriétaires : il n'a pas été
retenu, toute personne qui peut publier sur le repo peut modifier une vue d'équipe.

### Q2 — Que mémorise une vue ?

**Les réglages de mise en page du type, tous onglets confondus** : `excel`, `word`,
`popup`, `showFoldersExcel`, `showFoldersWord`, `freezeColCountExcel`.

Ne sont **pas** mémorisés :

- **les filtres de colonnes**, qui ne sont aujourd'hui persistés nulle part (état local de la vue
  Excel). Une vue « Revue sécurité batterie » n'affichera donc pas d'elle-même les seules exigences
  de sécurité. Si besoin, nouvelle issue ;
- les dossiers repliés (état de navigation) ;
- la hauteur des lignes (réglage global de l'application, T168) ;
- les colonnes du sélecteur de tests et de l'historique des exécutions (hors périmètre).

### Q3 — Que devient une vue quand on change une colonne ?

**Appliquer une vue copie ses réglages dans le réglage courant**, sans lien vivant.

- La vue reste indiquée comme active, avec la mention « modifiée » si les réglages courants en
  diffèrent. Rien n'est réécrit tant que l'utilisateur ne choisit pas « Enregistrer ».
- Une vue d'équipe changée par un collègue n'écrase donc jamais l'écran : après un pull, elle
  apparaît « modifiée », et la resélectionner applique la nouvelle version.

Alternative rejetée : chaque case cochée met à jour la vue active. Pour une vue d'équipe, un simple
essai de colonne modifierait un fichier versionné.

## 1. Stockage

Vue d'équipe :

```yaml
# .polenta/views/root/exigence-systeme.yaml
version: 1
views:
  - name: Revue sécurité batterie
    settings:
      excel: [section, name, id, status, priority, query::QUERY-0003]
      word: [section, name, id, status, statement]
      popup: [statement]
      showFoldersExcel: true
      showFoldersWord: true
      freezeColCountExcel: 3
```

Vue personnelle, même forme, dans l'entrée du type du `.pref` :

```json
"fieldVisibility": { "root::exigence-systeme": {
  "excel": ["…"],
  "savedViews": [{ "name": "Analyse d'un FAIL", "settings": { "…": "…" } }],
  "activeView": { "scope": "team", "name": "Revue sécurité batterie" }
} }
```

- `settings` reste un objet libre pour le stockage : #204 y rangera les réglages de ses zones.
- Vue complète et figée : elle ne suit pas les `defaultVisible` du schéma, même si elle a été
  enregistrée depuis le défaut.
- Le fichier d'équipe n'existe qu'à partir de la première vue et disparaît avec la dernière.
- Il est écrit dans le repo de l'élément, sans commit automatique : il suit le flux de toute
  modification (Publier).

## 2. Liste près du ⚙️

Liste déroulante juste à côté du bouton ⚙️, dans la barre d'outils des vues Tableau et Document.
Elle est masquée quand le ⚙️ l'est (types campagne).

- **Libellé** : nom de la vue active, suivi de « modifiée » s'il y a lieu ; « Vues » sans vue active.
- **Contenu** : groupes « Mes vues » et « Équipe », triés par nom, puis les actions.
- **Choisir une vue** : applique ses réglages à toutes les vues du type, sans recharger les données.
- **Enregistrer** : remplace le contenu de la vue active ; proposé si elle est modifiée.
- **Enregistrer sous…** : nom et portée (Personnelle, par défaut, ou Équipe).
- **Renommer**, **Supprimer** (avec confirmation) : portent sur la vue active.
- **Colonnes par défaut** : retire le choix personnel de tous les onglets (même effet que
  « Réinitialiser » du ⚙️, GH139) et quitte la vue active.

« Réinitialiser » dans le ⚙️ ne change pas : il agit sur l'onglet courant, et la vue active apparaît
« modifiée » si le résultat en diffère.

## 3. Règles

- **Nom** : 1 à 80 caractères, espaces de bord retirés ; unique par portée et par type, sans tenir
  compte de la casse. Doublon : refus avec message. Le même nom peut exister en personnel et en
  équipe : le groupe de la liste les distingue.
- **Colonne devenue invalide** (champ supprimé, requête retirée ou rendue privée) : ignorée à
  l'affichage et dans les exports, jamais réécrite d'office, comme aujourd'hui (GH70).
- **Renommage** de champ ou de type : migré dans les vues d'équipe, données versionnées du repo, par
  les services de renommage existants. Non migré dans le `.pref`, comme les réglages actuels.
- **Vue active disparue** (supprimée, renommée par un collègue, absente de la branche) : la vue
  active est oubliée sans message et les réglages courants restent.
- **Composant en lecture seule** : les vues d'équipe se lisent et s'appliquent ; toute écriture
  d'équipe est refusée (`READONLY_REPO`), les actions sont désactivées avec une infobulle. Les vues
  personnelles restent disponibles.
- **Fichier d'équipe illisible ou version inconnue** : groupe « Équipe » vide avec un avertissement ;
  le fichier n'est jamais réécrit, et les écritures d'équipe sont refusées tant qu'il n'est pas corrigé.
- **Desktop et web** : même comportement (canaux autorisés dans `channel-policy`).

Sans objet : aucun indicateur de suivi. La mention « modifiée » est une comparaison propre à l'écran.

## Critères d'acceptation

1. Sur une exigence, « Enregistrer sous… » en Personnelle crée la vue dans le `.pref`, sans fichier
   créé ni modifié dans le suivi git.
2. Choisir une autre vue, puis la première, restitue à l'identique les colonnes et leur ordre (Tableau,
   Document, Popup), les titres de dossiers et les colonnes figées.
3. Cocher une colonne affiche « modifiée » sans écrire la vue ; « Enregistrer » la met à jour et
   retire la mention ; revenir manuellement à l'état de la vue la retire aussi.
4. « Enregistrer sous… » en Équipe crée `.polenta/views/<nœud>/<type>.yaml`, visible dans Publier ;
   après publication et pull, un autre utilisateur voit la vue dans « Équipe » et peut l'appliquer.
5. Une vue d'équipe modifiée par un pull ne change pas l'écran de qui l'a active : mention
   « modifiée », puis nouvelle version au moment de la resélectionner.
6. Renommer et Supprimer fonctionnent dans les deux portées ; supprimer la dernière vue d'équipe
   retire le fichier ; un doublon de nom est refusé avec un message.
7. « Colonnes par défaut » ramène aux colonnes du schéma (GH139), sans vue active, les vues
   enregistrées restant dans la liste.
8. Le « Réinitialiser » du ⚙️ et les réglages `picker`, `executions`, dossiers repliés ne sont pas
   affectés par l'application d'une vue, et l'écriture d'une vue ne les efface pas.
9. Une colonne invalide d'une vue est ignorée sans erreur et reste dans le fichier.
10. Composant en lecture seule : vues d'équipe lisibles et applicables, écriture refusée, vues
    personnelles utilisables.
11. Un fichier d'équipe illisible ne bloque pas la vue, affiche un avertissement et n'est pas réécrit.
12. Un renommage de champ, puis de type, est répercuté dans les vues d'équipe.
13. Scénarios 1 à 4 passants sur un type issue et sur le client web.
14. Les types campagne n'affichent pas la liste.

## Hors périmètre

- Mémorisation des filtres et du tri (Q2).
- Vue d'équipe imposée, ou vue appliquée par défaut à l'ouverture d'un projet : le défaut reste celui
  du schéma (GH139).
- Vues enregistrées du sélecteur de tests et de l'historique des exécutions.
- Vue Validation elle-même et réglages de ses zones (#204).
- Accès MCP et graphe de données : pas de besoin identifié.
