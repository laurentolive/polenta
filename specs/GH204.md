# GH204 — Validation d'une version : objet, vue, décisions, reprise, signature (#204 + #205)

> Lot **7/9** du milestone « D — Conformité et gestion du changement ». Couvre #204 et #205, fusionnés.
> Spec globale : `specs/MILESTONE-D.md` §2, §5, §8 et §11 (P1 à P3), qui fait foi. Remplace `specs/GH191.md`
> §3 et §5, sauf §5.1 (livré par #203). Statut : **validée le 2026-11-03**, Q1 à Q6 retenues telles que proposées.
> Amendé par GH267 : pour une validation signée, liens, tests et exécutions sont figés (`specs/GH267.md`), à la place de Q1.

## But

La qualité statue, exigence par exigence, sur la conformité d'une version d'un composant, au vu des tests
exécutés. La signature de la validation d'une version released est le feu vert ; sur la version produit, elle
vaut go production série.

## Constat

- Ni `validation` ni `conformity` n'existent dans le code ; `/compliance` est la matrice d'interfaces, sans
  rapport. `IssueOrigin.decisions` existe, lu par le graphe et jamais écrit.
- `designVersions` compare le seul numéro `version` (P1). Aucun écran ne lit encore `designVersion`.
- `objectVersion` (GH191 §3.5) ne détecte pas une modification : `version` ne monte qu'en quittant
  l'approbation, donc un brouillon modifié garde son numéro. Même défaut que P1 (Q3).
- Les channels `versions:*`, `issues:*` et `tested-config:*` sont masqués sur le client web (SPEC-WEB §11, #256).

## 1. Objet

Catégorie `validation`, stockée dans le repo du composant, comme la version validée.

```yaml
# validations/VAL-0002.yaml
id: VAL-0002
objectTypeRef: root::validation
title: Validation 1.2.4
status: en_cours                  # statuts du type ; isApproval = signée
versionId: MCV-0004               # obligatoire, non modifiable après création
fields: { jalon: DVT }            # champs du projet (dont description)
entries:                          # exigence absente = décision isPending
  - requirementId: SYS-0012
    decision: derogation
    comment: <p>…</p>
    fields: { dueJalon: PVT }     # entryFields du projet
    contentHash: 8f3a1c           # contenu de l'exigence dans la version au moment de la décision (Q3)
    decidedBy: jdupont            # posés par l'application
    decidedAt: 2026-11-04T10:12:00Z
    carriedFrom: VAL-0001         # si reprise (§5)
    # proposed: true, proposedBy, proposedAt : décision proposée par le MCP (§8)
history: …                        # GH77 : statut et champs suivis
```

- **`versionId` et non `version`** (écart à MILESTONE-D §5.1) : `version` est déjà l'entier système des objets.
- **Une validation signée contient toutes ses décisions** : aucune décision en attente n'étant admise à la
  signature, le fichier signé est le registre complet. Les entrées d'exigences sorties du périmètre en sont
  retirées à la signature ; git les conserve.
- Fusion git par entrée (clé `requirementId`), comme les runs d'une campagne.
- Pas de `baselineRef`, de reprise par sélection manuelle, ni de `removedAt` (P2, P3).

## 2. Configuration du type

```yaml
- name: validation
  label: Validation
  category: validation
  prefix: VAL
  fields: […]
  decisions:
    - { name: en_attente, label: En attente, isPending: true }
    - { name: conforme, label: Conforme }
    - { name: non_conforme, label: Non conforme, proposesIssue: true }
    - { name: hors_scope, label: Hors scope }
    - { name: derogation, label: Dérogation, proposesIssue: true }
  entryFields: […]                # mêmes types et requiredWhen que fields
  statuses:
    - { name: en_cours, label: En cours }
    - { name: signee, label: Signée, isApproval: true }
    - { name: annulee, label: Annulée, isTerminal: true }
```

- Un seul type par repo, déclaré sur `root`, comme la version. Le jeu ci-dessus pré-remplit le type créé dans
  l'éditeur `/schema`, qui gère aussi `decisions` et `entryFields`.
- Contrôle à l'enregistrement du schéma : exactement une décision `isPending`, un statut `isApproval`, un
  statut `isTerminal`.
- Le commentaire est un champ fixe, facultatif ; un justificatif obligatoire se configure avec un `entryField`
  et `requiredWhen`.
- Décision utilisée non retirable ni renommable (`DECISION_IN_USE`). Champs de `fields` et statuts renommés avec
  migration, comme tout type. `entryFields` sans migration (`specs/GH204-design.md`).
- Tant qu'une validation existe, le préfixe des types d'exigence du repo est figé (`HAS_VALIDATIONS`) : l'état figé
  d'une version garde les anciens IDs, et une décision ne retrouverait plus son exigence.
- Premier statut non marqué, historique du statut obligatoire : refus à l'enregistrement du schéma.

## 3. Périmètre et lecture des données

Une ligne par exigence **du composant** (type déclaré par le schéma du repo), hors statut terminal (P2). Pas de
sélecteur : `hors_scope` joue ce rôle.

| Donnée | Version released | Version en cours |
|---|---|---|
| Liste des exigences, titre, contenu, statut de rédaction, statut de design | état figé (`freeze.sha`) (Q1) | `HEAD` + disque |
| Signal d'impact | analyse figée | analyse vivante |
| Liens, tests, exécutions, statut de vérification | état courant (MILESTONE-D §2) | état courant |

- Une exigence qui apparaît dans le périmètre arrive sans entrée : décision `isPending`. Une exigence qui en
  sort disparaît de la grille.
- La lecture n'écrit jamais dans le fichier de la validation.

### Statut de design (P1)

Première version released, dans l'ordre des livraisons, qui **inclut** l'exigence dans `changes` et dont l'état
figé est **identique** à l'état lu, selon la clé du backlog (`ElementState.key`). « — » sinon. Corrige
`designVersions` ; le graphe en hérite.

## 4. Cycle de vie

- **Création** : depuis la vue, sur une version en cours ou released, pas abandonnée. **Une seule validation
  non annulée par version** (Q5).
- **Version en cours** : décisions possibles, signature refusée (P3).
- **Signature** : action dédiée, confirmée par l'utilisateur ; le statut ne se change pas librement vers
  `isApproval`. Le fichier est commité ; ni tag ni baseline. Signataire et date : historique GH77. Le commit part
  au prochain push.
- **Refus de signature**, avec la liste de tous les motifs : version non released ; décision `isPending` ;
  décision proposée ; décision « à revoir » (§6) ; champ obligatoire manquant (validation ou entrée).
- **Validation signée** : verrouillée. Seule sortie : `annulee` (Q5).
- **Annulation** : possible à tout moment, tracée par GH77. Permet d'en créer une nouvelle pour la même version.
- **Suppression** : validation en cours seulement, avec pierre tombale. Une version non figée référencée par une
  validation ne se supprime pas (`VERSION_HAS_VALIDATION`).
- **Version abandonnée** : une validation en cours ne peut plus être signée ; une validation signée reste, avec
  la mention « version abandonnée ».
- **Composant en lecture seule** : validations visibles, aucune écriture (`READONLY_REPO`), message renvoyant au
  repo du composant (Q4).
- **Sous-composants** : voir Q6.

## 5. Reprise

À la création, si la version `basedOn` a une validation signée, sa décision est reprise pour chaque exigence :

- absente des `changes` de la version ;
- non impactée dans l'analyse (`pas_d_impact_reel` ne compte pas) ;
- de contenu identique à celui de la décision reprise (`contentHash`). Ce dernier critère complète MILESTONE-D
  §5.4 : une exigence modifiée sans être incluse dans la version ne doit pas garder sa décision.

La reprise copie décision, commentaire, `fields`, `decidedBy` et `decidedAt`, et pose `carriedFrom`. Aucune mention
à l'écran (§5.4). Toutes les valeurs sont reprises, `non_conforme` et `derogation` comprises. Les autres exigences
partent en `isPending`.

## 6. Signal d'impact et décision « à revoir »

- **Impactée** (lecture seule) : l'exigence est dans `changes`, ou dans les lignes de l'analyse hors
  `pas_d_impact_reel`. La source (racine et chemin) s'affiche sur la ligne.
- **À revoir** : décision prise ou reprise, alors que :
  - le contenu de l'exigence dans la version diffère de `contentHash` ;
  - ou, pour une décision reprise, l'exigence est devenue changée ou impactée (version en cours : l'analyse vit,
    P3).
- « À revoir » conserve la décision et bloque la signature. **Confirmer** réécrit `contentHash`, `decidedBy`,
  `decidedAt` et retire `carriedFrom` ; changer la décision fait de même.
- Sur une version released, le contenu ne bouge plus : ce qui est confirmé le reste.

## 7. Vue Validation

**Entrée de la barre d'activité**, au même niveau qu'Issues.

**Panneau latéral** : liste déroulante du composant (version produit = nœud racine), puis versions du composant,
avec l'état de leur validation. Une version sans validation propose « Créer la validation » (titre pré-rempli,
champs du type).

**Page** :

- En-tête : ID, titre, statut, version (lien, label, état), champs, **reste à décider : N**, actions Signer et
  Annuler.
- Grille d'une ligne par exigence :
  - **en écriture** : décision, commentaire, `entryFields` ;
  - **en lecture seule** : ID (lien), titre, champs de l'exigence, statuts de rédaction, de design (lien vers la
    version), de vérification (libellés de SPEC-TRACEABILITY §2.2), signal d'impact, mention « à revoir » ou
    « proposée » avec leurs actions.
- Dépliée, l'exigence montre **ses tests** et leur dernière exécution ; dépliée, un test montre **ses exécutions** :
  version testée, structure figée, résultat, commentaire, lien vers le run.
- Mentions sur une exécution :
  - **autre version** : la version validée n'est ni la version testée ni dans sa structure figée (une exécution
    sur le produit contenant cette version de composant ne la déclenche donc pas) ;
  - **a évolué** : calcul de #202, avec le détail ;
  - **version non renseignée** : run sans `testedConfig` ;
  - **après la signature** : run postérieur à la signature (Q2).
- ⚙️ et vues enregistrées (#203) pour les colonnes. Filtres : à décider, valeur de décision, proposée, à revoir,
  impactée.
- Validation signée ou annulée, composant en lecture seule : grille entièrement en lecture.

**Proposition d'issue** : au choix d'une décision `proposesIssue` (ou à la confirmation d'une telle proposition),
si le composant a un type issue, le dialogue de #244 s'ouvre : créer (`origin.decisions: ["VAL-0002/SYS-0012"]`,
lien d'impact vers l'exigence pré-rempli), lier à une issue existante, ignorer. Jamais sur une reprise, ni sur une
proposition du MCP. Rien n'est écrit sans action de l'utilisateur.

## 8. Graphe et MCP

- **Graphe** : collection `validations` (`versionId`, statut, champs, entrées, signature) ; manifeste + 1 et
  `polenta.d.ts` régénéré. `designVersion` corrigé (§3).
- **MCP** : `list_validations`, `get_validation`, `propose_validation_decision` (GH191 Q6). Une proposition n'écrit
  que sur une exigence sans décision confirmée d'une validation en cours. Le MCP ne confirme, ne rejette et ne signe
  pas.
- **Dans la vue** : Confirmer (tel quel ou modifié ; écrit `decidedBy` / `decidedAt`, retire `proposed`) ou Rejeter
  (retire l'entrée).
- **Client web** : channels `validations:*` masqués et limite ajoutée à SPEC-WEB §11, car la vue dépend de
  `versions:*`, lui-même masqué. Une ouverture éventuelle se traite pour l'ensemble, à la suite de #256.

## 9. Critères d'acceptation

1. Un type `validation` se crée dans `/schema`, avec le jeu par défaut ; un schéma sans décision `isPending`, ou
   avec deux, est refusé.
2. La vue liste une ligne par exigence non terminale du composant, sans celles des sous-composants.
3. Sur une version released, une exigence modifiée après le gel s'affiche avec son contenu et ses statuts figés ;
   une exigence créée après le gel n'apparaît pas.
4. Statut de design : « — » pour une exigence jamais incluse, ou modifiée depuis son inclusion ; sinon la première
   version qui l'inclut à l'identique.
5. Une décision écrit `decidedBy`, `decidedAt`, `contentHash` ; revenir à `isPending` retire l'entrée.
6. À la création sur une version dont `basedOn` a une validation signée : seules les exigences ni changées, ni
   impactées, ni modifiées reprennent leur décision. Un élément marqué « pas d'impact réel » est repris.
7. Une exigence changée ou impactée affiche sa source ; une décision devenue « à revoir » bloque la signature
   jusqu'à sa confirmation.
8. La signature est refusée avec tous ses motifs dans chaque cas du §4 ; acceptée, elle commite le fichier, sans
   tag ; la validation devient non modifiable, sauf annulation.
9. Une seconde validation non annulée sur la même version est refusée ; après annulation, elle est acceptée.
10. Sous une exigence, ses tests et exécutions s'affichent avec les mentions du §7, dont le cas de l'exécution sur
    le produit qui contient la version validée.
11. Une décision `proposesIssue` ouvre le dialogue ; une issue créée porte `origin.decisions` et le lien d'impact.
12. Le MCP propose une décision, ne peut ni écraser une décision confirmée, ni signer ; une proposition bloque la
    signature ; Confirmer et Rejeter fonctionnent.
13. Conflit git sur deux décisions d'exigences différentes : fusion automatique.
14. Le graphe expose `validations` et `polenta.d.ts` les décrit.
15. Une vue enregistrée restitue les colonnes de la grille.
16. Composant en lecture seule : aucune écriture possible.

## 10. Questions tranchées (2026-11-03)

| # | Question | Proposition | Pourquoi |
|---|---|---|---|
| **Q1** | La grille d'une version released lit-elle l'exigence figée ou courante ? | **Figée** (§3) ; liens, tests et exécutions courants | Si l'équipe prépare déjà la version suivante, la qualité ne doit pas statuer sur un texte qui n'est pas celui de la version. Coût : lecture git par exigence |
| **Q2** | Garde-t-on `evidence` (exécutions qui font foi, cochées) ? | **Non** : toutes les exécutions s'affichent, celles d'après la signature sont signalées, le commentaire porte le jugement | Moins de saisie ; ce qui était connu à la signature reste lisible. Ajout possible plus tard sans migration. Inconvénient : Polenta ne dit pas quelle exécution a emporté la décision |
| **Q3** | Comment détecter « modifié depuis la décision » ? | **`contentHash`** au lieu d'`objectVersion` | `version` ne monte pas sur un brouillon modifié (cf. P1) ; même comparaison que le contenu GH200 |
| **Q4** | Validation d'un composant en lecture seule depuis le produit ? | **Refusée**, à faire dans le repo du composant | Même règle que les versions (MILESTONE-D §3.1). Conséquence : une qualité sans droit d'écriture sur ce repo ne peut pas y statuer |
| **Q5** | Combien de validations par version, et comment corriger après signature ? | **Une seule non annulée** ; une signée peut être annulée, puis refaite | Évite deux avis contradictoires sur un même feu vert. GH191 §3.7 interdisait toute sortie, mais une signature par erreur doit se corriger avec une trace |
| **Q6** | Signer une version produit exige-t-il des validations signées sur ses composants ? | **Non bloquant** : l'en-tête affiche l'état de la validation de chaque composant | MILESTONE-D ne l'impose pas, et le blocage se heurterait aux composants externes. Si c'est une règle de votre processus qualité, il faut plutôt bloquer : c'est le choix le plus lourd de conséquences |
