# GH206 — Contraintes de transition : facultatives, à niveaux, expliquées

> Lot **8/9** du milestone D. Spec globale : `specs/MILESTONE-D.md` §9, §11 (P5, P6). Origine : GH193 §7.2, dont
> les conditions propres au changeset sont retirées (#243) et `allDecided` aussi (P5). Préparation du 2026-11-04 :
> commentaire de l'issue. **Validée le 2026-11-05**, avec la décision Q1 ci-dessous.

## Contexte

Aujourd'hui, tout passage de statut est libre (SPEC-REQ §4.3). Les seuls contrôles au changement de statut sont
`requiredWhen: { status: … }` (GH195) et le verrou de l'approuvé (GH200). Une équipe ne peut donc pas demander,
par exemple, « pas d'approbation sans lien vers un test » (règle 3 de `CLAUDE.md`), sauf par discipline.

Ce lot ajoute des **contraintes déclarées par le projet**, toujours facultatives. Chaque condition a un **niveau** :
pas de contrôle, notification ou blocage. Sans contrainte déclarée, rien ne change.

**Décision Q1 (humain, 2026-11-05)** : un contrôle bloquant freine le déploiement de l'outil et crée de la
frustration. Les contrôles sont donc **configurables par niveau**, et le niveau par défaut est la **notification** :
le blocage est un choix explicite du projet. La condition `validatorsPass` est ajoutée.

## 1. Déclaration (`schema.yaml`)

Bloc facultatif `transitions` sur un type d'objet :

```yaml
    statuses: [...]
    transitions:
      - to: approved                 # obligatoire : statut d'arrivée
        from: review                 # facultatif : absent = depuis n'importe quel statut
        requires:                    # condition → niveau
          fieldsFilled: block
          hasCoverageLink: warn
          validatorsPass: off
```

- **Niveaux** :

  | Niveau | Effet |
  |---|---|
  | `off` | pas de contrôle ; la condition reste déclarée, pour la réactiver sans la ressaisir |
  | `warn` | **notification** : le passage se fait, l'utilisateur voit ce qui manque. Niveau par défaut |
  | `block` | **blocage** : le passage est refusé tant que la condition n'est pas remplie |

  Le niveau est toujours écrit, `warn` compris, pour qu'un fichier se lise sans connaître le défaut. Une valeur
  absente ou inconnue est refusée à l'enregistrement.
- **Catégories** : exigence, test, issue (D1). Un bloc `transitions` sur une autre catégorie est refusé à
  l'enregistrement du schéma : la version a son passage released (`RELEASE_REQUIRED`), la validation sa signature, la
  campagne un cycle figé.
- **Liste fermée de conditions** (D2) :

  | Condition | Sens | Catégories |
  |---|---|---|
  | `fieldsFilled` | dans l'état d'arrivée, tous les champs `required` sont remplis, ainsi que les `requiredWhen` actifs au statut d'arrivée (D6) | exigence, test, issue |
  | `validatorsPass` | dans l'état d'arrivée, chaque champ rempli qui porte un `validator` (EARS, `regex:`) est valide (Q1) | exigence, test, issue |
  | `hasCoverageLink` | l'exigence a au moins un test qui la couvre, au sens de la matrice de traçabilité : son statut de couverture n'est pas `not_covered` (D7) | exigence |

- **Cohérence contrôlée à l'enregistrement du schéma** : `from` et `to` désignent des statuts du type ; `from ≠ to` ;
  `requires` non vide, avec des conditions admises par la catégorie et des niveaux connus ; pas deux règles de même
  `from` / `to`. Message qui nomme le type et la règle.
- **Renommage** d'un statut : `from` et `to` suivent, comme `requiredWhen` (#214). Retrait d'un statut cité :
  refusé, avec le nom de la règle, tant qu'elle existe.

## 2. Évaluation

- Un passage du statut S au statut T (S ≠ T) est soumis à **toutes les règles** dont `to = T` et dont `from` est
  absent ou vaut S. Une condition citée par plusieurs de ces règles prend le **niveau le plus fort**
  (`block` > `warn` > `off`).
- Un passage **sans règle** reste libre (Q3 de GH193) : ce n'est pas une machine à états stricte.
- **Création avec un statut** T (formulaire, import, MCP) : toutes les règles dont `to = T` s'appliquent, quel que
  soit leur `from` (D3). Sinon, créer directement en `approved` contournerait tout.
- **Écriture sans changement de statut** : aucune contrainte de transition, même si l'écriture passe le statut
  inchangé (D4).
- **Résultat** :
  - une condition `block` non remplie : **refus**, rien n'est écrit. Code `TRANSITION_BLOCKED`, avec **tous** les
    motifs, bloquants et notifiés ;
  - seulement des conditions `warn` non remplies : **écriture faite**, et la réponse porte la liste des
    notifications (`transitionWarnings`) ;
  - chaque motif tient en une phrase, avec ce qu'il faut faire (« Champs obligatoires vides : Justification » ;
    « Aucun test ne couvre SYS-0012 : liez un test à cette exigence » ; « Énoncé : syntaxe EARS non respectée »).
- **Retour arrière** : libre, sauf règle explicite. Une condition `block` qui peut s'appliquer en **quittant** un
  statut `isApproval` (sa réouverture, seule façon d'éditer un élément approuvé, GH200) est acceptée avec un
  **avertissement** dans l'éditeur de schéma (D5).
- Le YAML modifié à la main n'est pas contrôlé, comme les autres règles. La fusion GH37 non plus (avertissement
  `requiredEmpty` inchangé).

## 3. Écrans

- **Éditeur de schéma** (onglet du type) : section « Transitions » listant les règles. Ajout d'une règle (statut
  d'arrivée, statut de départ facultatif, conditions) ; chaque condition a un sélecteur à trois positions
  **Aucun contrôle / Notification / Blocage**, Notification par défaut ; retrait d'une règle **en un clic** ;
  avertissement D5 sur la condition concernée.
- **Menu de statut**, partout où l'on change un statut (éditeur, vue Tableau, vue Document, liste, menu
  contextuel) :
  - transition **bloquée** : visible, désactivée, avec son motif (infobulle, ou libellé de l'option dans les listes
    natives). Rien n'est masqué ;
  - transition **notifiée** : active, marquée d'une icône d'avertissement, motif en infobulle.
- **Après un passage notifié** : une notification non bloquante liste ce qui manque, avec les ID cliquables. Elle
  ne demande aucune confirmation.
- **Refus après coup** (écriture concurrente, contrôle serveur) : le message s'affiche et la saisie optimiste est
  annulée, la valeur affichée revient au statut réel.
- **Client web** : mêmes écrans ; tout canal de pré-contrôle est exposé au web.

## 4. MCP

- Les écritures du MCP (`bulk_import_*`, `update_requirements`, `update_tests`, `create_issue`, `update_issue`)
  appliquent les mêmes contraintes : refus `TRANSITION_BLOCKED` avec les motifs, ou succès avec
  `transitionWarnings`.
- `dryRun` donne le même résultat que l'écriture réelle, conditions de lien comprises.
- L'outil de mutation de schéma accepte `transitions`, avec les mêmes contrôles de cohérence.

## 5. Cas d'usage

| # | Situation | Résultat attendu |
|---|---|---|
| U1 | Type sans `transitions` | tout passage libre, comme aujourd'hui |
| U2 | Règle `to: approved`, `hasCoverageLink: block` ; exigence sans test lié, passage review → approved | refus, motif « aucun test ne couvre … » ; statut inchangé |
| U3 | Même exigence après liaison d'un test (lien créé depuis l'exigence ou le test) | passage accepté, sans notification |
| U4 | Test lié dans un autre repo du workspace (composant) | la condition est remplie (D7) |
| U5 | Même règle avec `hasCoverageLink: warn` | passage fait ; notification « aucun test ne couvre … » |
| U6 | Même règle avec `hasCoverageLink: off` | passage fait, aucune notification |
| U7 | Règle `from: review, to: approved, fieldsFilled: block` ; passage draft → approved | accepté : la règle ne vise que review → approved |
| U8 | Même règle ; création d'une exigence directement en `approved` avec un champ `required` vide | refus (D3) |
| U9 | `validatorsPass: block` vers `review` ; énoncé non EARS | refus, motif nommant le champ |
| U10 | Une condition `block` et une `warn` non remplies | refus listant les deux motifs |
| U11 | Modification du titre d'une exigence rouverte, statut inchangé | aucune contrainte de transition |
| U12 | Menu de statut d'une exigence non couverte | « Approuvé » désactivé avec motif (`block`), ou actif avec icône (`warn`) |
| U13 | MCP `update_requirements` avec `status: approved`, `dryRun` puis réel | même résultat dans les deux cas (refus ou `transitionWarnings`) |
| U14 | `transitions` sur un type `version` ou `campaign` | refus à l'enregistrement du schéma |
| U15 | Renommer le statut `approved` en `valide` | la règle suit (`to: valide`) |
| U16 | Retirer la règle depuis l'éditeur de schéma | un clic ; le passage redevient libre |

## 6. Décisions

| # | Question | Décision | Pourquoi |
|---|---|---|---|
| D1 | Catégories visées | exigence, test, issue | version et validation ont leur propre circuit ; la campagne a un cycle figé (`campaign.ts`) |
| D2 | Conditions | `fieldsFilled`, `validatorsPass`, `hasCoverageLink` | celles qui restent de GH193 §7.2, plus `validatorsPass` (Q1) |
| D3 | Création avec statut | toutes les règles vers ce statut s'appliquent | sinon la création directe contourne les règles (MCP, import) |
| D4 | Écriture avec statut inchangé | pas de contrôle | certains écrans renvoient le statut à chaque enregistrement |
| D5 | Blocage sur une sortie d'approbation | permis, avec avertissement | la réouverture est le seul moyen d'éditer : la bloquer peut figer un élément |
| D6 | `fieldsFilled` | `required` + `requiredWhen` actifs au statut d'arrivée ; les validateurs relèvent de `validatorsPass` | une condition = une phrase |
| D7 | `hasCoverageLink` | même règle que la matrice (`not_covered` ou non), liens de tout le workspace | un seul sens de « couvert » dans Polenta |
| D8 | Niveaux (Q1) | `off`, `warn`, `block` par condition ; `warn` par défaut dans l'éditeur ; toujours écrit | le blocage freine l'adoption : il reste un choix explicite |

## Critères d'acceptation

1. Sans bloc `transitions`, aucun comportement ne change (suites existantes vertes).
2. Les cas U1 à U16 se vérifient, en desktop et sur le client web pour U2, U5, U12.
3. Un refus nomme toutes les conditions non remplies, chacune avec l'action à faire ; un passage notifié les nomme
   sans demander de confirmation.
4. Les mêmes résultats s'obtiennent depuis le MCP, `dryRun` compris.
5. L'éditeur de schéma ajoute et retire une règle en un clic, règle le niveau de chaque condition, refuse une règle
   incohérente et avertit en cas D5.
6. Le renommage d'un statut migre les règles ; son retrait est refusé tant qu'une règle le cite.
7. SPEC-REQ §4.3 (« toutes les transitions sont autorisées ») est réécrit ; SPEC-MCP-SERVER, SPEC-TEMPLATES à jour.

## Indicateur (GH79)

Pas d'indicateur de suivi : les trois conditions servent une fonction de Polenta (contrôler une transition) et
réutilisent ce que Polenta calcule déjà (champs obligatoires, validateurs, couverture). Rien n'est stocké.

## Hors périmètre

- Conditions propres au changeset et `allDecided` (retirées, MILESTONE-D §9).
- Contraintes sur le passage released d'une version et sur la signature d'une validation.
- Trace d'un passage notifié (qui est passé outre, quand) : la notification n'écrit rien.
- Niveaux pour les contrôles existants hors transitions (`required`, `requiredWhen`, verrou de l'approuvé) : à
  traiter dans un ticket à part, si l'humain le souhaite.
- Rôles ou droits par utilisateur (qui peut approuver).
- Script ou condition libre : la liste reste fermée.
- Contrôle du YAML modifié à la main et de la fusion GH37.
- Migration : aucun fichier existant n'est réécrit.
