# GH207 — Campagnes issues d'un changeset

> Lot **13/16** du milestone « D — Conformité et gestion du changement », traité juste après #200
> (point global `specs/GH193-point.md`, P6). Épique #193 (`specs/GH193.md` §5, §7.2, lot L6).
> S'appuie sur l'analyse d'impact (#199) et la trace par élément (#200).
> « Change » désigne un **changeset** (GH199 §8ter).

## Contexte

État du code (`milestone-D` @ 53b0608) :

- Un changeset porte `campaigns: []`, affiché « — » ; rien ne l'alimente.
- Analyse d'impact (#199) : racines = `toModify` + impactés déclarés ; lignes `impacted` avec 8
  statuts, dont `impact_a_tester` et `modification_a_tester` ; campagnes **en cours** concernées
  listées sous l'analyse.
- Trace (#200) : chaque élément de `toModify` a sa version de départ et son commit d'approbation.
- Campagnes : `CampaignsService.create` (`testCaseIds`, `reqInstances` T179, `baselineRef`),
  `addTests` ; formulaire `/campaign/new` pré-remplissable (`testCaseIds`, `title`, héritage T46) ;
  statuts `planned | in_progress | completed | abandoned`.
- `generateTestPlan` (SPEC-TRACEABILITY §5) : exigences → tests qui les couvrent (et instances).
- Les contraintes de transition (#206) **n'existent pas encore**.

## 1. Tests « à exécuter » d'un changeset

Calculés (pas stockés), à partir de l'analyse courante (ou figée) :

| Source | Contribue |
|---|---|
| ligne impactée au statut `impact_a_tester` ou `modification_a_tester` | si test : lui-même ; si exigence : les tests qui la couvrent |
| élément de `toModify` (Q1) | si test : lui-même ; si exigence : les tests qui la couvrent |

- Une exigence → ses tests par la couverture (sens indifférent), comme `generateTestPlan` ; pour un
  test itérant (T179), l'instance de **cette** exigence (`reqInstances`).
- Exigence sans test : listée « non couverte » (rien à exécuter, signalé).
- Un test déjà **inclus dans une campagne liée** au changeset (entrée active, quel que soit son
  verdict) n'est plus « à ajouter ».

## 2. Créer la campagne

- Page du changeset, section **« Campagnes »** (remplace la ligne « Campagnes : — ») : bouton
  **« Créer la campagne »**, actif s'il y a des tests à exécuter.
- Ouvre `/campaign/new` pré-rempli : titre `<ID> — <titre du changeset>`, tests et instances du §1,
  **repo du changeset**, composant du changeset ; l'utilisateur ajuste (type, champs, paramètres)
  et crée comme d'habitude.
- À la création : la campagne porte **`changeset: <ID>`** (champ système, lecture seule, affiché
  dans son en-tête avec lien) et le changeset reçoit l'ID dans **`campaigns`** — les deux écrits en
  même temps (Q2).
- Plusieurs campagnes par changeset sont permises (ex. une par jalon) ; « Créer la campagne » reste
  disponible.

## 3. Alimenter (jamais automatique)

- Quand des tests « à exécuter » ne sont dans **aucune** campagne liée **ouverte** (`planned` ou
  `in_progress`), la section Campagnes affiche **« N tests à ajouter »** avec **« Ajouter à
  CAMP-0009 »** (une seule campagne liée ouverte) ou un menu (plusieurs). L'ajout passe par le
  sélecteur de tests existant (GH33) pré-coché, paramètres compris ; rien n'est ajouté sans
  validation.
- Aucune campagne liée ouverte : seul « Créer la campagne » est proposé.

## 4. Section « Campagnes » du changeset

Une ligne par campagne liée : ID (lien), titre, statut, avancement (entrées PASS / total, calculé
pour l'écran), et une colonne « tests du changeset » (nombre d'entrées de la campagne qui
correspondent aux tests à exécuter). Une campagne liée supprimée s'affiche « supprimée ».

Les **campagnes en cours concernées** de l'analyse (#199 §4) restent listées sous l'analyse : ce
sont les campagnes non liées qui contiennent des tests impactés.

## 5. Conditions de transition — reportées à #206 (Q3)

Les conditions `linkedCampaignsPassed`, `impactsClosed`, `modifiedApproved`, `impactedApproved`
exigent le mécanisme générique de contraintes de transition (#206), qui vient après. Elles sont
**retirées de ce lot** et rejoignent #206, qui les livre avec le mécanisme. Ce lot expose
seulement les données qu'elles liront : campagnes liées et leurs verdicts (§4), complétude
(#199), trace d'approbation (#200).

## 6. Graphe et MCP

- Graphe : `GraphChangeset.campaigns` (déjà présent) alimenté ; `GraphCampaign.changeset`
  (`string | null`). `polenta.d.ts` régénéré.
- MCP : `get_changeset` renvoie en plus `testsToRun` (§1 : tests, instances, exigences non
  couvertes) ; `bulk_import_campaigns` accepte `changeset` (lien écrit des deux côtés). Pas d'ajout
  automatique.

## 9. Indicateurs (GH79)

« Tests à exécuter » et l'avancement de la section servent l'écran du changeset (fonction de
Polenta) : calculés. Aucun indicateur de suivi (délais, taux d'échec par changeset…) : côté projet.
