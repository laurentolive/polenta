# GH21 — Pin sur tag annoté jamais reconnu comme déjà checkouté

Issue : #21.

## Root cause

`git.resolveRef` s'arrête à l'objet d'un tag annoté, sans aller jusqu'au commit.
`WorkspaceTreeService.repoExistsAtPin` comparait donc HEAD à l'objet tag : un repo épinglé sur une
baseline (tag annoté, créée par Polenta) était jugé désynchronisé à chaque ouverture, d'où un fetch
réseau et un checkout. Hors ligne ou sans remote, l'ouverture échouait (`HTTP Error: 404`, arbre en
`parse-error`).

Après un checkout du tag lui-même, HEAD contient aussi l'objet tag : les deux côtés doivent être
déréférencés.

## Correctif

- `workspace-tree.service.ts` : `repoExistsAtPin` compare des commits des deux côtés (`peelToCommit`,
  qui s'appuie sur `git.readCommit`).
- `sync.service.ts` : `resolveTag` renvoie le commit, y compris pour un tag annoté. Même défaut, et son
  commentaire supposait des tags légers seulement. Il alimente `resolveCommitish` (GH199) et
  `createAndDesignate` depuis une baseline, qui aurait créé une branche sur un objet tag.

### Recensement du même motif

Appels de `resolveRef` sur un tag ou un pin dans `main/services` :

| Emplacement | État |
|---|---|
| `git.service.ts` `resolveTagOid`, `sync.service.ts` `resolveRefs`, `baseline.service.ts` | Déjà corrects |
| `baseline.service.ts:36` | Test d'existence seulement |
| `sync.service.ts` `tagsForCommit` | Même défaut, mais aucun appelant : non modifié |

## Comment vérifier

Tests : `workspace-tree.annotated-tag.gh21.test.ts`, sur de vrais repos git et avec un fetch qui échoue
comme hors ligne. HEAD sur le commit du tag, HEAD posé par un checkout du tag, tag léger, HEAD sur un
autre commit, `resolveTag`. Vus en échec sans le correctif : le premier cas et le `resolveTag` annoté.

À la main : `demo-lave-linge`, dans `ll800-produit/polenta-repo.yaml`, remplacer le pin de
`comp-pompe-vidange` (`v2.0`) par une baseline annotée sur le même commit, couper le réseau et rouvrir :
le workspace s'ouvre sans erreur.
