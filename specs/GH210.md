# GH210 — Reflets : statuts de design et de validation dans les vues exigence

> Lot **9/9** du milestone D. Spec globale : `specs/MILESTONE-D.md` §2, §11 (P1, P4). Préparation du 2026-11-04 :
> commentaire de l'issue.

## Contexte

Une exigence a quatre statuts (MILESTONE-D §2) :

| Statut | Aujourd'hui dans les vues exigence |
|---|---|
| Rédaction (`status`) | affiché partout |
| Vérification (couverture : `not_covered`, `covered`, `validated` « Vérifié », `failing`, `needs_revalidation`) | colonne facultative `coverageStatus`, libellée « Couverture » |
| **Design** | calculé (`designVersion` du graphe, vue Validation) mais **affiché nulle part** dans les vues exigence |
| **Validation** | affiché seulement dans la vue Validation, version par version |

Ce lot affiche les deux reflets manquants là où l'on travaille sur les exigences. Le périmètre d'origine (onglet
« Décisions qualité », modèle de colonne « Décision au jalon ») est remplacé (MILESTONE-D §9).

## 1. Les deux reflets

| Reflet | Valeur affichée | Sinon |
|---|---|---|
| **Design** | label de la **première version released** du composant qui inclut l'exigence dans `changes` et dont l'état figé est identique à son contenu courant (P1, règle de GH204 §3, déjà calculée) | « — » |
| **Validation** | **décision** (libellé du type de validation) de la **dernière validation signée** du composant, suivie du label de sa version : « Conforme (1.2.4) » (P4) | « — » |

- **Dernière validation signée** (D1) : parmi les validations signées du repo de l'exigence, celle dont la version est la
  plus récente dans l'**ordre des livraisons** (`freeze.at`, comme le statut de design), pas l'ordre des signatures.
- **Annulation** (D2) : calcul vivant. Une validation annulée ne compte plus ; le reflet retombe sur la signée
  précédente.
- **Exigence sans entrée** dans cette validation (créée après, ou hors périmètre à la signature) : « — » (D3).
- **Exigence modifiée depuis la décision** (D4) : la décision et le label restent affichés. Le reflet Design, qui passe
  à « — » tant qu'aucune version ne contient le nouvel état, signale déjà l'écart ; pas de mention supplémentaire.
- **Sous-composant** : les deux reflets se lisent dans le repo **propriétaire** de l'exigence (ses versions, ses
  validations).
- Exigences seulement : pas de reflet pour les tests et les issues.

## 2. Écrans

- **Colonnes facultatives** `designStatus` et `validationStatus`, comme `coverageStatus` : décochées par défaut, cochées
  dans ⚙️ (« Champs visibles »), dans les vues **Tableau** et **Document**, et affichées dans la vue **Édition** comme
  les champs système en lecture seule.
- Dans le Tableau : triables et filtrables sur le texte affiché, comme la couverture (GH224) ; exportées en xlsx avec
  le texte affiché.
- Le label de version du reflet Design et du reflet Validation ouvre la page de la version (desktop). Sur le web, tant
  que les vues Versions n'y sont pas (#252), le label s'affiche sans lien.
- **Vocabulaire** (D5) : le libellé de la colonne `coverageStatus` devient « Vérification » (la clé ne change pas, les
  vues enregistrées restent valables). Les trois colonnes s'appellent donc Vérification, Design, Validation.
- Les vues enregistrées (GH203) mémorisent les nouvelles colonnes comme les autres.

## 3. Données (GH79)

Les deux reflets servent une fonction de Polenta (les quatre statuts d'une exigence, MILESTONE-D §2) : calculés dans
Polenta, **rien n'est stocké**. Calcul à la demande, par repo, seulement quand une des deux colonnes est visible ;
invalidé quand une version, une validation, une exigence ou le schéma change.

Le graphe expose déjà `designVersion` (ID) et les validations avec leurs entrées : un script projet peut recomposer le
reflet Validation, aucun ajout n'est nécessaire au contrat.

## 4. Cas d'usage

| # | Situation | Résultat attendu |
|---|---|---|
| U1 | Exigence jamais livrée | Design « — », Validation « — » |
| U2 | Exigence incluse dans la version 1.0, released, contenu inchangé | Design « 1.0 » |
| U3 | Même exigence modifiée après la release | Design « — » ; Validation inchangée si une décision existe |
| U4 | Validation de 1.0 signée, décision Conforme | Validation « Conforme (1.0) » |
| U5 | Validation de 1.1 signée ensuite, décision Dérogation | Validation « Dérogation (1.1) » |
| U6 | Validation de 1.1 annulée | Validation « Conforme (1.0) » |
| U7 | Exigence créée après la signature de 1.1 | Validation « — » |
| U8 | Exigence d'un sous-composant, vue depuis le produit | reflets lus dans le repo du composant |
| U9 | Colonnes non cochées | aucun calcul |
| U10 | Vue enregistrée avec la colonne Design | colonne restaurée |
| U11 | Client web | reflets affichés, labels sans lien |

## 5. Décisions proposées

| # | Question | Recommandation | Pourquoi |
|---|---|---|---|
| D1 | « Dernière signée » | ordre des livraisons des versions (`freeze.at`) | même ordre que le statut de design ; l'historique du statut peut être désactivé (`trackStatusHistory`) |
| D2 | Validation annulée | calcul vivant, retombe sur la précédente signée | une annulation corrige une signature par erreur (GH204 Q5) |
| D3 | Exigence absente des entrées | « — » | pas de décision prise sur cette exigence |
| D4 | Exigence modifiée depuis la décision | garder la décision, pas de mention | le reflet Design signale déjà l'écart ; une seule information par colonne |
| D5 | Libellé « Couverture » | renommé « Vérification », clé `coverageStatus` gardée | vocabulaire des quatre statuts, sans casser les vues enregistrées |
| D6 | Web | reflets exposés, labels sans lien jusqu'à #252 | pas de page Version sur le web aujourd'hui |

## Critères d'acceptation

1. Les cas U1 à U11 se vérifient (U11 sur le client web).
2. Sans colonne cochée, aucun calcul de reflet n'est lancé.
3. Les colonnes se trient, se filtrent et s'exportent sur le texte affiché.
4. Une signature, une annulation ou une release met les reflets à jour sans recharger l'application.
5. SPEC-REQ §13 (reflets), SPEC-SYSTEM-VIEW (colonnes), SPEC-WEB §11 à jour.

## Hors périmètre

- Reflets sur les tests et les issues.
- Mention « modifiée depuis la décision » dans le reflet Validation (D4).
- Ajout au contrat du graphe (§3).
- Lien vers la version sur le web (#252).
- Onglet « Décisions qualité » et modèle « Décision au jalon » (remplacés).
