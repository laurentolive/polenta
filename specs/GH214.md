# GH214 — `requiredWhen` : migrer les références au renommage

Bug trouvé en revue de #195. Traité à part du milestone D (`specs/MILESTONE-D.md` §11, P6).

## Root cause

`saveAndMigrate` (`StructureTab.tsx`) réécrit `default` (GH82) et `displayIdField` (GH229) au
renommage, mais rien ne réécrit les `requiredWhen` des autres champs. La référence devient inconnue,
ce qui n'est qu'un ⚠ orange (GH195 §2.3) : le schéma s'enregistre et la condition ne se déclenche
plus jamais. Exemple : `rationale.requiredWhen = { status: [approved] }`, statut renommé `validated`
→ `rationale` n'est plus obligatoire à l'approbation.

## Correctif

`withRenamedRequiredWhen` (`objectTypeEditor.tsx`), appliqué dans la même sauvegarde que le schéma,
sur le moteur pur `renameRequiredWhenRefs` (`packages/types/src/required-when.ts`) :

| Renommage | Effet sur `requiredWhen` |
|-----------|--------------------------|
| Champ | la clé suit |
| Statut retenu dans la confirmation | valeur réécrite sous la clé `status` |
| Valeur d'enum retenue | valeur réécrite sous la clé de ce champ uniquement |
| Champ et valeur dans la même édition | les deux |

Décisions :

- **Ligne décochée dans la confirmation GH82** : ce n'est pas un renommage, comme pour `default`. La
  condition garde l'ancienne valeur, et son ⚠ le signale.
- **`runFields` / `stepFields`** : même symptôme, donc même correctif, chaque liste ne référençant
  que ses propres champs. Les valeurs détectées s'appliquent sans confirmation : les runs ne sont
  jamais migrés (GH196), il n'y a donc pas de confirmation à laquelle se raccrocher.
- **Pseudo-champs** : la clé `status` (`result` pour les listes d'exécution) désigne toujours le
  pseudo-champ. Un vrai champ de ce nom, renommé dans un sens ou dans l'autre, ne la change pas.
- **Échange de noms** : les renommages s'appliquent d'un seul tenant, deux champs peuvent échanger
  leur nom. Deux clés qui se rejoignent fusionnent leurs valeurs, sans doublon.

## Écarts avec l'issue

**MCP** : l'issue demande « éditeur de schéma et MCP ». Le MCP n'a aucun outil de renommage
(`add_component`, `add_object_type`, `add_field`, `add_status`, `add_link_type` seulement) : il n'y
a rien à y corriger.

## Limite connue

Pendant l'édition, avant d'enregistrer, le ⚠ apparaît sur la condition dès qu'on renomme sa
référence : l'éditeur contrôle la saisie telle quelle. Il disparaît à l'enregistrement. Le masquer
demanderait de rejouer dans `FieldsTable` la détection des renommages, y compris la décision de la
confirmation, qui n'est pas encore connue à ce stade.

## Comment vérifier

Onglet Structure, sur un type dont un champ porte `status = approved` en condition :

1. Renommer le statut `approved`, enregistrer et confirmer.
2. Rouvrir le type : la condition cite le nouveau nom, sans ⚠.
3. Passer un objet dans ce statut avec le champ vide : refus « est obligatoire quand ».

Tests : `objectTypeEditor.gh214.test.ts`, `e2e-web/gh214-required-when-rename.spec.ts`.
