# GH222 — Diff / merge : moteur et vue YAML génériques, mise en évidence type VS Code

Issue : #222 · Type : feature

## 1. Contexte et retours utilisateurs

Polenta a deux familles d'écrans de comparaison :

- **Résolution de conflits** (`/merge-resolve`, GH37) : 3 panneaux (mes modifications |
  destination, sortie en dessous, ancêtre en option), bascule Raw / Rendu.
- **Vues de diff** (`/version-diff`, `/diff`, `/diff?commitSha`, GH178) : bascule Raw / Rendu sur
  deux colonnes Avant | Après.

Retours des utilisateurs :

1. **Tout ne peut pas être fusionné visuellement.** Le mode Rendu n'existe que pour les exigences et
   les tests (et pour les `.drawio`, mais en diff seulement). Campagnes, `links.yaml`, paramètres,
   schéma, arbres d'affichage, requêtes, dashboards et `polenta-repo.yaml` restent en YAML brut, en
   diff comme en merge.
2. **Les différences se voient mal.**
   - Le diff Raw (`LineDiffView`) colore seulement des lignes entières, avec un fond très pâle (en
     thème sombre, le fond est à 15 % d'opacité). Il n'y a pas de surlignage des caractères modifiés.
   - On ne peut pas aller d'un changement à l'autre et rien ne montre où sont les changements dans
     un long fichier.
   - En merge, les actions « Prendre gauche / droite » n'apparaissent que dans la sortie, et les
     blocs repris automatiquement passent inaperçus.
3. **Le code est éclaté selon le type de fichier** :
   - fusion par unité pour les objets (`object.ts`, `units.ts`) ;
   - fusion par clé pour les liens et les paramètres (`keyed.ts`) ;
   - hunks `diff3` pour le reste ;
   - en diff : `lineDiff.ts`, `objectUnits.ts`, `align.ts` et `mediaDiff.ts`.

   Chaque type est traité à part, d'où les trous de couverture.

## 2. Principe : un moteur, une vue

```
            ┌──────────────────────────────────────────────┐
 fichiers → │ Moteur YAML générique (diff 2 voies, merge 3) │ → arbre de différences
            └──────────────────────────────────────────────┘        (nœuds annotés)
                                │
                 ┌──────────────┴───────────────┐
                 ▼                              ▼
     Vue YAML générique (tout fichier YAML)   Vue Raw (tout fichier texte)
       └ rendu d'objet selon son type (exigence, test, campagne)
```

- **Un seul moteur** compare des documents YAML **structurellement** (et non ligne à ligne).
  - Il produit un **arbre de différences** commun au diff (2 versions) et au merge (3 versions).
  - Le moteur ne connaît pas les types d'objets métier. Il reçoit une **description de structure**
    pour chaque type de fichier : clés d'identité des listes, granularité des blocs, champs ignorés.
- **Une seule vue de diff / merge, la vue YAML générique**, dessine cet arbre pour **tous** les
  fichiers YAML. Disposition, mise en évidence (§5), navigation et actions de merge (§6) sont les
  mêmes quel que soit le fichier. **Aucun fichier YAML n'est donc plus limité au Raw.**
  - Seul le **contenu** d'un objet typé (exigence, test, campagne) dépend de son type : ses
    valeurs sont rendues avec les libellés et les widgets du schéma (§4.2). Le cadre reste celui de
    la vue générique.
  - Pas de vue dédiée aux autres fichiers (liens, paramètres, schéma, arbres, requêtes…) : ils
    s'affichent dans la vue générique.
- Le **Raw** reste disponible partout, en diff comme en merge, avec la même mise en évidence.

## 3. Moteur YAML générique

### 3.1 Arbre de différences

Le moteur lit chaque version et aligne les nœuds par **chemin** :

| Nœud | Alignement |
|---|---|
| Mapping | par clé |
| Liste d'éléments identifiables | par **clé d'identité** déclarée pour ce chemin (`id`, `name`, `key`, `order`…) |
| Autre liste | par plus longue sous-séquence commune (LCS) sur l'égalité profonde, puis appariement par position entre deux ancres, comme `alignSteps` aujourd'hui |
| Scalaire court | égalité de valeur |
| Chaîne multiligne (richtext, description…) | égalité de valeur ; le détail est fourni par le diff de texte (§5.2) |

Chaque nœud reçoit un **état** :

- en diff : `inchangé`, `ajouté`, `supprimé`, `modifié` ou `déplacé` (élément identifié dont la
  position change dans une liste ordonnée) ;
- en merge, en plus : `repris de gauche`, `repris de droite`, `identique des deux côtés`, `conflit`
  ou `résolu` (avec le choix fait : gauche, droite, les deux, édité).

Un nœud parent est `modifié` dès qu'un de ses descendants l'est. C'est ce qui donne les compteurs
et la navigation (§5.4).

### 3.2 Merge 3 voies

Le merge suit la règle actuelle, appliquée récursivement :

- un nœud modifié d'un seul côté, ou à l'identique des deux côtés, est repris sans conflit ;
- un nœud modifié différemment des deux côtés est un conflit **au niveau du bloc** défini par la
  description de structure (§3.3) ;
- en dessous de ce niveau, aucune fusion automatique : une chaîne multiligne modifiée des deux
  côtés reste **un seul conflit**, même si les changements portent sur des lignes différentes. Les
  surlignages (§5) montrent ce que chaque côté a changé par rapport à l'ancêtre ;
- listes identifiées : union des ajouts. Un élément supprimé d'un côté et modifié de l'autre donne
  un conflit « supprimé / modifié ». Deux ordres différents donnent un conflit d'**ordre** sur la
  liste, avec un choix gauche / droite ;
- les règles spéciales restent : `history` (union triée, GH77), `version` (max),
  `needsRevalidation` (OU logique), pierres tombales et « Garder les deux » (GH20, GH37 §7).

### 3.3 Descriptions de structure

Chaque type de fichier a une description déclarative, interne à Polenta (pas un réglage
utilisateur). Elle indique :

- le motif de chemin qui reconnaît ce type de fichier ;
- les clés d'identité des listes, par chemin ;
- la granularité des blocs de conflit ;
- les nœuds masqués en Rendu.

| Fichier | Clés d'identité | Bloc de conflit |
|---|---|---|
| Exigence, test (`objectTypeRef` résolu) | `steps` : LCS (comme aujourd'hui) | clé racine, `fields.<nom>`, une étape |
| Campagne `campaigns/**` | entrées : `entryId` ; runs : id du run | champ, entrée, run |
| `test-runs/**` | selon la structure du run | champ |
| `links/links.yaml` | `id` | un lien |
| `parameters/parameters.yaml` | clé | un paramètre |
| `.polenta/schema.yaml` | nodes, objectTypes, fields, statuses, linkTypes : `name` | une propriété d'un élément nommé |
| `.polenta/trees/**` | éléments : ID d'objet | position d'un objet (parent, rang) |
| `polenta-repo.yaml`, `.polenta/workspace.yaml` | composants : `name` | une propriété |
| `queries/**`, `dashboards/**` | widgets : `id` | un widget, une propriété |
| Tout autre YAML | aucune (LCS) | une clé de mapping ou un élément de liste |

Résultat attendu : **un merge est au moins aussi fin qu'aujourd'hui** pour les objets, les liens et
les paramètres, et devient structurel pour le schéma, les arbres, les campagnes et les autres YAML.
Ceux-ci passent aujourd'hui par `diff3` ligne à ligne.

### 3.4 Hors YAML

- `.drawio` : le diff et le merge se font **par page**. La page est alignée par nom, puis par id si
  deux pages ont le même nom.
- Texte non YAML (Markdown, scripts `.js` de la bibliothèque, CSV…) : `diff3` ligne à ligne, comme
  aujourd'hui, avec la même mise en évidence en Raw.
- Binaires : choix d'un côté (inchangé).
- YAML illisible d'un côté : repli sur le diff texte, avec le message « Rendu indisponible — voir
  Raw » (comme GH178 §2.1).

## 4. Vue de diff / merge générique

### 4.1 Vue YAML générique

Une seule vue, utilisée pour **tout fichier YAML**, en **diff** (2 colonnes Avant | Après) comme en
**merge** (disposition GH37 : gauche | [ancêtre] | droite en haut, sortie en bas).

#### Disposition : la structure à gauche, les valeurs alignées à droite

```
Diff
┌─────────────────┬─────────────────────────┬─────────────────────────┐
│ Structure       │ Avant · a1b2c3d         │ Après · working tree    │
├─────────────────┼─────────────────────────┼─────────────────────────┤
│ Titre           │ Démarrage rapide        │ Démarrage rapide Eco    │
│ Statut        ● │ Brouillon               │ En review               │
│ ▾ Champs      ● │                         │                         │
│ │ Priorité      │ Haute                   │ Haute                   │
│ │ Énoncé      ● │ WHEN the user presses … │ WHEN the user presses … │
│ │             │ │ … within 500 ms         │ … within 300 ms         │
│ ▸ Étapes (4)  ● │ 1 modifiée              │ 1 modifiée              │
└─────────────────┴─────────────────────────┴─────────────────────────┘

Merge
┌─────────────────┬───────────────┬───────────────┬───────────────┐
│ Structure       │ Mes modifs    │ [Ancêtre]     │ Destination   │
│ …               │ …             │ …             │ …             │
├─────────────────┼───────────────┴───────────────┴───────────────┤
│ Structure       │ Sortie du merge                                 │
│ …               │ …                                               │
└─────────────────┴─────────────────────────────────────────────────┘
```

- **Colonne « Structure » à gauche** : l'arbre repliable des nœuds, dans l'ordre du document. C'est
  **la seule à porter la profondeur** (indentation, chevrons, filets de niveau) et les clés.
  - Libellé d'un nœud : sa clé ; pour un élément de liste identifié, sa clé d'identité (`id`,
    `name`…) ; pour un objet typé, le libellé du schéma (§4.2). Le **chemin complet** s'affiche au
    survol.
  - Les nœuds sans changement sont repliés par défaut ; les nœuds modifiés et leurs parents sont
    dépliés.
  - Chaque nœud porte une **marque d'état** (§5.1). Un nœud replié porte la marque agrégée de ses
    descendants.
  - Un clic sur un nœud sélectionne la rangée et la fait défiler dans tous les panneaux.
- **Panneaux de comparaison à droite** : **une rangée par nœud visible de l'arbre**, à la même
  hauteur que lui.
  - Les panneaux **n'affichent que les valeurs**, sans clé ni indentation : toutes les valeurs
    commencent **à la même position X**, quelle que soit la profondeur du nœud. Leur largeur ne
    dépend pas de la profondeur.
  - Rangée d'un nœud parent déplié : bande vide et fine.
  - Rangée d'un nœud parent replié : résumé (« 4 éléments, 1 modifié »).
  - La hauteur d'une rangée est celle de la plus haute de ses cellules (texte multiligne, richtext,
    diagramme). Le libellé dans l'arbre est aligné en haut.
- **Merge** : la rangée du haut (gauche | [ancêtre] | droite) et la sortie ont chacune leur colonne
  Structure, de même largeur. Les deux arbres montrent les mêmes nœuds, se replient et se déplient
  ensemble et défilent de façon synchronisée.

#### Arbre compact en largeur

- Indentation de **12 px par niveau**, chevrons et marques d'état sur une seule ligne.
- Au-delà de **6 niveaux**, l'indentation n'augmente plus. Le niveau réel est indiqué par le
  filet et par le chemin au survol.
- Libellés tronqués avec points de suspension, texte complet au survol.
- Largeur par défaut **180 px**, redimensionnable (glisser la séparation, minimum 120 px). La
  largeur est mémorisée par poste avec les autres préférences de diff.

#### Contenu des rangées

- Nœuds **alignés** entre les panneaux : même nœud sur la même rangée, zone hachurée quand il
  manque d'un côté (§5.5).
- Tous les états du §3.1 sont dessinés de la même façon (§5.1), y compris `déplacé`.
- Valeurs : scalaire sur une ligne ; chaîne multiligne en bloc de texte avec diff mot à mot
  (§5.2).
- En merge, sur la **sortie** : choix par bloc (§6), **valeur scalaire éditable en place**,
  édition libre complète en Raw.

C'est la même vue pour `links.yaml`, `parameters.yaml`, le schéma, les arbres d'affichage, les
requêtes, les dashboards, `polenta-repo.yaml` et tout autre YAML. Seule la description de structure
(§3.3) change d'un fichier à l'autre.

### 4.2 Rendu des objets typés

Pour un objet dont l'`objectTypeRef` se résout dans le schéma (exigence, test, campagne), la vue
reste la vue générique (même arbre, mêmes marques, mêmes actions), mais les **valeurs** sont
rendues selon le type :

- libellés du schéma pour les clés (champ `statement` → « Énoncé ») et pour les valeurs de statut,
  d'`enum` et de `multi_enum` ;
- `richtext` rendu (paragraphes, listes, tableaux, diagrammes draw.io et images lus à la version de
  leur colonne, GH178 §2.4) ;
- étapes d'un test : un nœud par étape (« Étape 2 »), alignées étape par étape (LCS, comme
  aujourd'hui), avec pour enfants Action, Résultat attendu et Notes ;
- en merge, édition de la sortie avec les widgets de l'éditeur (comme aujourd'hui, GH37 §5) ;
- nœuds masqués comme aujourd'hui (`id`, `projectId`, `branchId`, `objectTypeRef`, `history`).

Ce rendu remplace `RenderedObjectPane` et `ObjectDiffView`. Les valeurs gardent le même rendu ; la
disposition devient celle du §4.1 (libellés dans la colonne Structure, valeurs alignées). Une
campagne reçoit le même traitement : c'est nouveau, puisqu'elle était en Raw seul.

### 4.3 Fichiers non YAML

- `.drawio` : pages rendues à leur version (GH178 §2.8), avec les mêmes marques, la même
  navigation et, **nouveau en merge**, un choix gauche / droite par page.
- Image : les deux images côte à côte, choix d'un côté (inchangé).
- Autre texte : Raw seul.

### 4.4 Règles communes

- La bascule **Raw / Rendu** est affichée pour tout fichier YAML ou `.drawio`. Seuls le texte non
  YAML et les binaires n'ont pas de bascule.
- Raw et Rendu agissent sur **la même sortie**. Un choix ou une édition fait dans l'un se retrouve
  dans l'autre (règle GH37 §5). Le texte de la sortie reste la source de vérité (marqueurs nommés,
  SPEC-TECH §6.1).
- Les préférences restent celles de GH178 et GH37 : mode mémorisé par poste, « Masquer les
  inchangés ».

## 5. Mise en évidence des différences (à la manière de VS Code)

Ces règles valent pour **toutes** les vues, Raw et Rendu, en diff et en merge.

### 5.1 Couleurs et sémantique

| Sens | Où | Rendu |
|---|---|---|
| Supprimé | côté Avant / gauche | fond rouge de ligne ou de bloc + caractères supprimés en **rouge plus soutenu** |
| Ajouté | côté Après / droite | fond vert + caractères ajoutés en **vert plus soutenu** |
| Modifié (bloc) | des deux côtés | fond de bloc + **barre verticale colorée** à gauche du bloc |
| Conflit non résolu | merge | bordure et fond **orange**, icône ⚠, libellé « Conflit » |
| Résolu | merge | barre latérale discrète + pastille « gauche / droite / les deux / édité » |
| Repris automatiquement | merge | barre latérale fine (couleur du côté d'origine) + info-bulle « repris de … » |
| Déplacé | listes, arbres | icône ⇅ + lien « déplacé de / vers » |

- Les fonds de ligne doivent **rester visibles en thème sombre**. Les jetons de thème actuels
  (`status-*-bg` en mode sombre à 15 %) seront complétés par des jetons dédiés `diff-*` :
  ligne ajoutée / supprimée, caractères ajoutés / supprimés, conflit, résolu. Contraste vérifié dans
  les deux thèmes (SPEC-THEMING).
- La couleur n'est jamais le seul indice : signes `+` / `−` dans la gouttière, barre latérale,
  icône de conflit, texte barré pour les caractères supprimés.

### 5.2 Surlignage au caractère

- **Raw** : en plus du fond de ligne, les **caractères** qui diffèrent entre une ligne supprimée et
  la ligne ajoutée qui lui correspond sont surlignés. L'appariement des lignes reprend celui du diff
  ligne à ligne ; le diff intra-ligne se fait au niveau du mot, puis du caractère.
- **Rendu** : diff mot à mot pour le texte et le richtext (GH178 §2.4), étendu à **toute valeur
  textuelle** de toutes les vues (cellules de tableau, valeurs YAML génériques, titres).
- **Merge** : chaque panneau du haut surligne ce que **son côté a changé par rapport à l'ancêtre
  commun**, que l'ancêtre soit affiché ou non. On voit ainsi ce que chacun a modifié, et pas
  seulement ce qui diffère entre les deux.

### 5.3 Gouttière et règle de vue d'ensemble

- **Gouttière** (Raw, et bord gauche des blocs en Rendu) : numéros de ligne Avant / Après, signes
  `+` / `−`, marque de conflit.
- **Règle de vue d'ensemble** : une bande verticale le long de la barre de défilement de chaque
  panneau marque la position de chaque changement (rouge, vert, orange pour un conflit). Un clic sur
  une marque fait défiler jusqu'au changement.

### 5.4 Navigation

- Boutons **« Changement précédent / suivant »** et compteur **« 3 / 12 »** dans le sous-en-tête.
  En merge : **« Conflit précédent / suivant »** et compteur des conflits non résolus.
- Raccourcis : `F7` / `Maj+F7` (changement suivant / précédent, comme le diff de VS Code) et
  `Alt+↓` / `Alt+↑` en équivalent. Au dernier conflit résolu d'un fichier, `F7` propose le fichier
  suivant à résoudre.
- Le bloc courant est **mis en relief** (contour plus épais) et centré dans tous les panneaux grâce
  au défilement synchronisé.

### 5.5 Alignement et régions inchangées

- **Côte à côte** : les blocs qui se correspondent sont à la même hauteur dans tous les panneaux.
  Une absence d'un côté est remplie par une **zone hachurée** (et non un simple vide), y compris en
  Raw.
- **Régions inchangées repliées** : en Raw, les plages de plus de N lignes inchangées (N = 3 lignes
  de contexte de chaque côté) sont repliées en « ⋯ n lignes inchangées » (cliquable). En Rendu, la
  case « Masquer les inchangés » existante (GH178) s'applique.
- **Diff en ligne** (une colonne, suppressions au-dessus des ajouts) : bascule **Côte à côte / En
  ligne** dans les vues de diff seulement (Raw et Rendu), mémorisée avec le mode.

### 5.6 Liste des fichiers

Dans le panneau Version (diff) comme dans la liste de résolution (merge), chaque fichier affiche :

- une lettre d'état colorée (`A` / `M` / `D` / `R` pour renommé ou renuméroté) ;
- les compteurs `+n −m` (en Rendu : nombre de blocs modifiés) ;
- en merge, le nombre de conflits restants ;
- l'ID et le titre de l'objet s'il y a lieu (comme aujourd'hui en merge).

## 6. Actions de merge

- Au-dessus de **chaque bloc en conflit**, dans **chaque panneau** (et pas seulement dans la
  sortie), des actions en ligne comme les « CodeLens » de VS Code :
  - panneau gauche : **Prendre gauche** ;
  - panneau droit : **Prendre droite** ;
  - sortie : **Prendre gauche | Prendre droite | Prendre les deux | Réinitialiser**.
- **Prendre les deux** n'est proposé que quand le résultat a un sens :
  - listes : union, éléments de gauche puis de droite ;
  - texte et richtext : concaténation, gauche puis droite, à retoucher ;
  - liens et paramètres : seulement s'ils ont des clés différentes, ce qui n'est pas un conflit par
    construction.

  Il n'est pas proposé pour un scalaire.
- **Réinitialiser** remet le bloc dans son état de conflit initial.
- Actions globales par fichier, inchangées : Tout prendre à gauche, Tout prendre à droite.
- Un bloc **repris automatiquement** peut être consulté et **forcé** vers l'autre côté. Il devient
  alors « résolu (édité) ».
- « Merger », la validation, la finalisation, l'abandon et les brouillons ne changent pas (GH37
  §8–10).

## 7. Cas d'usage

1. **Conflit sur `links.yaml`** : Alice et Bob modifient chacun la cible du même lien `LNK-0042`.
   En Rendu, la vue générique montre le nœud `LNK-0042` déplié des deux côtés, avec la valeur
   `targetId` surlignée. Alice clique « Prendre droite » dans le panneau de droite.
2. **Conflit sur `schema.yaml`** : l'un ajoute le statut `obsolete` au type `exigence-systeme`,
   l'autre renomme le libellé du champ `priority`. Il n'y a **pas de conflit** : ce sont deux
   éléments nommés différents. Aujourd'hui, `diff3` signale un conflit si les lignes sont proches.
   Les deux changements sont visibles en Rendu (vue générique) comme « repris ».
3. **Campagne** : deux testeurs ajoutent chacun un run à des entrées différentes. Pas de conflit,
   union des runs. Un même run modifié des deux côtés donne un conflit sur ce run seul, montré sous
   son entrée avec les libellés de statut du schéma.
4. **Diff d'un dashboard** (YAML générique) entre deux baselines : arbre repliable, seul le widget
   modifié est déplié, la valeur `title` surlignée au mot.
5. **Long `links.yaml`** (2 000 lignes, 5 changements) en Raw : la règle de vue d'ensemble montre
   5 marques, les régions inchangées sont repliées, `F7` passe d'un changement au suivant.
6. **Exigence en thème sombre** : dans le diff Raw, une valeur `priority: high` → `low` montre une
   ligne rouge et une ligne verte bien visibles, et seuls `high` / `low` sont surlignés en soutenu.
7. **Arbre d'affichage** : Alice déplace `SYS-0005` sous `SYS-0001`, Bob le déplace sous `SYS-0003`.
   Il y a conflit de position sur le nœud `SYS-0005`, montré dans la vue générique, et
   l'utilisateur choisit l'une ou l'autre.
8. **Diagramme modifié des deux côtés** sur des pages différentes : pas de conflit. Sur la même page,
   conflit sur cette page, avec un choix gauche / droite.

## 8. Critères d'acceptation

1. Tout fichier YAML du repo s'affiche en Rendu, en diff comme en merge, dans la vue YAML
   générique ; exigences, tests et campagnes y ont leurs valeurs rendues selon le type (§4.2). Le
   Raw reste disponible pour tout fichier texte.
2. Le diff et le merge de tous les fichiers YAML passent par le même moteur. Pour les exigences,
   tests, liens et paramètres, les blocs de conflit sont au moins aussi fins qu'avant (les tests de
   `merge-core` restent verts).
3. Deux modifications de **nœuds différents** du schéma, d'un arbre, d'une campagne ou d'un YAML
   générique ne produisent pas de conflit.
4. Raw : chaque paire de lignes modifiées montre les caractères différents surlignés. En thème clair
   comme sombre, le contraste des fonds de ligne et des surlignages respecte le minimum fixé au
   design (jetons `diff-*`).
5. Chaque panneau a une règle de vue d'ensemble qui marque tous les changements et conflits ; un
   clic fait défiler jusqu'au changement.
6. « Précédent / Suivant », le compteur et `F7` / `Maj+F7` parcourent tous les changements (diff) ou
   les conflits non résolus (merge), dans toutes les vues.
7. En merge, chaque bloc en conflit offre ses actions dans les panneaux gauche, droit et sortie.
   « Prendre les deux » n'apparaît que dans les cas prévus au §6.
8. En merge, chaque panneau du haut surligne les changements de son côté par rapport à l'ancêtre.
9. Les absences sont matérialisées par une zone hachurée alignée, en Raw comme en Rendu.
10. En Rendu, la profondeur n'est portée que par la colonne Structure : dans les panneaux de

## 9. Hors scope

- Diff graphique **à l'intérieur** d'une page draw.io (formes ajoutées / déplacées) : le niveau
  reste la page.
- Fusion automatique **à l'intérieur** d'une chaîne multiligne (deux paragraphes d'un même
  `statement`) : le conflit reste au niveau du champ, l'ajustement se fait par édition.
- Action « Prendre l'ancêtre » (l'ancêtre reste consultatif, GH37).
- Descriptions de structure fournies par le projet (configurables dans `schema.yaml`) : elles
  restent internes à Polenta.
- Résolution d'un rebase en conflit.
- Diff entre deux repos différents.
- Minimap de contenu (aperçu miniature du texte) : seule la règle de vue d'ensemble est demandée.
- Vues dédiées aux fichiers non objets (tableau des liens, des paramètres, arbre du schéma…) : ils
  utilisent la vue générique.

## 12. Édition depuis la vue de diff (ajout du 2026-10-29, ex-#232)

Retour utilisateur pendant la validation : quand un côté du diff est **modifiable**, pouvoir
déplacer une modification d'un côté à l'autre, ajouter du contenu ou le modifier, sans quitter le
diff.

### 12.1 Quand un côté est modifiable

- Seul le côté **Après** d'une **modification locale** (`/diff` sans `commitSha` : Avant = `HEAD`,
  Après = working tree) est modifiable. Les diffs entre deux commits (`/version-diff`, `/diff` d'un
  commit du graphe) restent en lecture seule : le passé ne se modifie pas.
- Ne sont pas modifiables : un fichier supprimé du working tree, un binaire, un repo en lecture
  seule (composant `readonly`), un fichier en cours de résolution de conflit.
- Un bandeau discret « Modifiable — working tree » signale le côté éditable.

### 12.2 Actions

| Action | Raw | Rendu (vue générique) |
|---|---|---|
| **Reprendre la version d'Avant** (annuler un changement local, « déplacer » le bloc d'Avant vers Après) | bouton « ← Rétablir » au-dessus de chaque bloc changé, comme « revert » dans VS Code | « ← Rétablir » sur la rangée d'un nœud modifié, retiré ou ajouté (un nœud ajouté est retiré) |
| **Modifier** | éditeur texte du côté Après | édition en place, comme la sortie du merge : scalaires, statut, widgets du schéma |
| **Ajouter** | saisie libre | « + Ajouter » sous une liste (élément vide, ou copie du dernier élément) et sous un mapping (clé + valeur) |

Les surlignages, la navigation et la règle de vue d'ensemble suivent les modifications (le diff est
recalculé contre `HEAD` à chaque changement).

### 12.3 Enregistrement (décidé le 2026-10-29)

- **Explicite** : bouton « Enregistrer » (et `Ctrl+S`) ; tant que rien n'est enregistré, l'onglet
  est marqué modifié et sa fermeture demande confirmation (comme l'éditeur d'objet).
- **Exigence / test** : enregistré par le service de l'objet, comme l'éditeur (`version`,
  `history` GH77, validations). Une sortie invalide (YAML, `id`, type, statut) n'est pas
  enregistrée ; un énoncé non EARS ou un champ obligatoire vide est un avertissement.
- **Autre fichier** : écriture du texte dans le working tree (YAML invalide refusé pour un fichier
  `.yaml`).
- **Modification extérieure** pendant l'édition (autre onglet, autre outil) : l'enregistrement est
  refusé avec un message ; « Recharger » reprend la version du disque.

### 12.4 Critères d'acceptation

15. Sur `/diff` d'une modification locale, « ← Rétablir » sur un bloc (Raw) ou une rangée (Rendu)
    remet la version de `HEAD` pour ce bloc seulement ; le diff se met à jour.
16. Le côté Après se modifie en Raw (texte) et en Rendu (édition en place) ; « Enregistrer » écrit le
    fichier ; le panneau Version reflète le nouvel état.
17. Une exigence ou un test modifié depuis le diff garde un `history` cohérent (GH77) : même
    résultat qu'une modification depuis l'éditeur.
18. Aucune action d'édition sur un diff entre commits, un fichier supprimé ou binaire, ni pendant
    une résolution de conflit.
19. Une modification non enregistrée est signalée et la fermeture de l'onglet demande confirmation.

### 12.5 Hors scope

- Modifier le côté Avant (`HEAD`) ou un commit.
- Indexer (`stage`) un bloc seulement : le panneau Version continue d'indexer le fichier entier.
