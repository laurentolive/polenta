# GH238 — Console git dans la vue Version

Issue : #238 — « Ajout Terminal dans la vue version » (milestone C).

## Besoin

Pouvoir taper des commandes git « en cas de galère » avec l'interface de version (état bloqué,
rebase/merge à annuler, reflog, reset…), sans quitter Polenta, via un panneau bas ouvert par
`Ctrl+ù` comme le terminal de VS Code.

## Décisions de cadrage (échange du 2026-10-30)

| Question | Décision |
|---|---|
| Forme | **Console git**, pas un terminal shell : ligne de saisie + sortie ; seules des commandes git sont exécutées |
| Moteur | **git système** (`git` du PATH, Git for Windows), pas isomorphic-git — voir § Alternatives rejetées |
| Portée | Vues **Version** seulement : `/graph`, `/diff`, `/version-diff`, `/baseline` |
| Sessions | **Une** console ; répertoire de travail = repo sélectionné du panneau Version |
| Préfixe | `git status` et `status` sont équivalents |
| Client web | **Absent** (desktop seulement) |

## Description fonctionnelle

### 1. Panneau

- Panneau horizontal **en bas de la zone principale** (sous la vue courante, au-dessus de rien
  d'autre ; l'ActivityBar et le panneau latéral ne sont pas réduits).
- Disponible uniquement quand la route active est une vue Version (`/graph`, `/diff`,
  `/version-diff`, `/baseline`). Sur toute autre route le panneau n'est pas rendu et `Ctrl+ù` est
  sans effet.
- Ouverture / fermeture :
  - `Ctrl+ù` (bascule) — également `Ctrl+`` ` pour un clavier QWERTY (même touche physique que
    VS Code). Actif même quand le focus est dans la vue ; à l'ouverture, le focus va dans la ligne
    de saisie ; à la fermeture, il revient à la vue.
  - Bouton **Console git** (icône terminal) dans le header du panneau latéral Version.
  - Bouton × dans l'en-tête de la console.
- Hauteur réglable par une poignée de redimensionnement sur le bord haut (min 80 px, max 70 % de
  la zone principale). Hauteur et état ouvert/fermé mémorisés pour la session de l'application :
  quitter une vue Version masque la console, y revenir la réaffiche si elle était ouverte.
- **Fermer n'efface rien** : la sortie, l'historique de saisie et une commande éventuellement en
  cours sont conservés jusqu'à la fermeture de l'application ou au changement de projet.

### 2. En-tête de la console

- Libellé du repo courant (nom du repo comme dans l'arbre Version) + chemin absolu en infobulle.
- Bouton **Effacer** (vide la sortie, garde l'historique), bouton **Interrompre** (visible
  pendant une exécution), bouton ×.

### 3. Répertoire de travail

- Chaque commande s'exécute à la racine du **repo sélectionné** dans le panneau Version
  (`SelectedRepoContext` : root par défaut, ou le repo composant/interface cliqué).
- Changer de repo sélectionné : la sortie affiche une ligne séparatrice `── <nom du repo> ──` et
  les commandes suivantes s'exécutent dans le nouveau repo. Une commande en cours continue dans
  son repo d'origine.

### 4. Saisie

- Invite fixe `git ›` devant la ligne de saisie : ce qu'on tape est lu comme des arguments de
  git. Un premier mot `git` est retiré s'il est saisi (`git status` ≡ `status`).
- Découpage des arguments façon shell **sans aucune interprétation** : espaces séparateurs,
  guillemets `"…"` et `'…'` pour un argument contenant des espaces, `\` d'échappement dans les
  guillemets doubles. Pas de variables, de jokers, de redirection, de pipe ni d'enchaînement.
- Une ligne contenant hors guillemets `|`, `>`, `<`, `&&`, `||` ou `;` est **refusée** avec le
  message « Opérateurs shell non pris en charge : une seule commande git par ligne ».
- Guillemet non fermé → refus « Guillemet non fermé ».
- Mots réservés à la console (non envoyés à git) : `clear` / `cls` → Effacer.
- `Entrée` exécute ; `↑` / `↓` parcourent l'historique des lignes exécutées (100 dernières,
  dédupliquées consécutivement, gardées en mémoire pour la session) ; `Échap` vide la ligne.
- Une seule commande à la fois : pendant une exécution, la ligne reste éditable mais `Entrée` est
  sans effet.
- La ligne exécutée est recopiée dans la sortie précédée de l'invite (`git › log --oneline -5`).

### 5. Exécution

- Processus `git` lancé par le main process **sans shell** (`execFile`/`spawn` avec tableau
  d'arguments), `cwd` = repo courant, entrée standard fermée.
- Environnement forcé, pour qu'aucune commande ne reste bloquée en attente d'une saisie :
  `GIT_PAGER=cat`, `PAGER=cat`, `GIT_TERMINAL_PROMPT=0`, éditeur (`GIT_EDITOR`,
  `GIT_SEQUENCE_EDITOR`) qui échoue immédiatement ; couleurs activées (`-c color.ui=always`).
- Commandes interactives **refusées avant exécution** avec un message qui indique l'alternative
  non interactive :
  - `-i` / `--interactive` / `-p` / `--patch` sur `add`, `rebase`, `checkout`, `reset`,
    `restore`, `stash`, `clean`, `commit` ;
  - `gui`, `citool`, `difftool`, `mergetool`, `gitk`.
  - Toute autre commande demandant un éditeur (ex. `commit` sans `-m`, `merge --continue`
    sans `--no-edit`) échoue par git lui-même ; son message d'erreur s'affiche normalement.
- Sortie **en continu** (stdout et stderr entrelacés dans l'ordre d'arrivée, stderr dans une
  couleur distincte). Couleurs ANSI de base (16 couleurs, gras) rendues ; autres séquences
  d'échappement retirées.
- Fin de commande : code de sortie ≠ 0 → ligne `✗ code <n>` ; 0 → rien.
- **Interrompre** (bouton ou `Ctrl+C` dans la ligne de saisie quand aucun texte n'est sélectionné
  et qu'une commande tourne) : tue le processus et ses descendants (ex. `git-remote-https`) ;
  ligne `✗ interrompu`.
- Tampon de sortie limité à 5 000 lignes ; au-delà, les plus anciennes sont supprimées.
- Identifiants distants : ceux du git système (Git Credential Manager…), **pas** le jeton PAT /
  OAuth de Polenta. Une demande d'identifiants échoue sans bloquer (`GIT_TERMINAL_PROMPT=0`).

### 6. Git introuvable

- À l'ouverture de la console, détection de `git` : PATH, puis emplacements standards de Git for
  Windows (`%ProgramFiles%\Git\cmd\git.exe`, `%LocalAppData%\Programs\Git\cmd\git.exe`).
- Absent : la console affiche « git introuvable — installez Git (https://git-scm.com) puis
  rouvrez la console » ; la ligne de saisie est désactivée. Nouvelle détection à chaque ouverture.
- Ligne d'accueil quand git est trouvé : `git version x.y.z — <chemin du binaire>`.

### 7. Synchronisation avec l'interface

- À la fin de chaque commande (succès, échec ou interruption), l'interface est rafraîchie pour le
  repo concerné comme après une opération Polenta : statut (Stagés / Modifications), graphe,
  branches et combobox de branche, tags, état d'intégration, et index des exigences/tests
  (invalidation « tout le repo », équivalente à un changement de ref du watcher).
- Les opérations Polenta et la console ne sont pas sérialisées : si les deux écrivent en même
  temps, git signale l'erreur (`index.lock`…) dans la console ; aucun mécanisme de verrou ajouté.

### 8. Client web

- Pas de console : bouton masqué, `Ctrl+ù` sans effet, canal IPC absent de la liste blanche du
  serveur web. Motif : même limitée à `git`, la console permet l'exécution de code arbitraire
  sur l'hôte (`-c core.sshCommand=…`, alias `!…`, hooks) — inacceptable sur le serveur
  multi-clients.

## Cas d'usage

| # | Situation | Comportement attendu |
|---|---|---|
| U1 | Sur `/graph`, `Ctrl+ù` | La console s'ouvre, focus dans la saisie, ligne d'accueil `git version …` |
| U2 | Saisie `status` | Sortie de `git status` du repo sélectionné, en couleurs |
| U3 | Saisie `git log --oneline -3` | Identique à `log --oneline -3` |
| U4 | Rebase bloqué → `rebase --abort` | Exécuté ; le graphe et le statut du panneau se mettent à jour |
| U5 | Saisie `add -p` | Refus avant exécution, message d'alternative |
| U6 | Saisie `log | head` | Refus « Opérateurs shell non pris en charge… » |
| U7 | `fetch` long → `Ctrl+C` | Processus tué, `✗ interrompu`, saisie à nouveau possible |
| U8 | Clic sur un repo composant dans l'arbre | Séparateur `── <composant> ──`, commandes suivantes dans ce repo |
| U9 | Console ouverte, navigation vers `/requirements` puis retour `/graph` | Masquée puis réaffichée avec sa sortie |
| U10 | Git non installé | Message d'installation, saisie désactivée |
| U11 | Sur `/requirements`, `Ctrl+ù` | Rien |
| U12 | Client web | Aucune trace de la console |
| U13 | `commit` sans `-m` | Échec git (éditeur indisponible) affiché, aucun blocage |
| U14 | `push` sans identifiants dans le git système | Échec git affiché, aucun blocage |

## Critères d'acceptation

1. `Ctrl+ù` (et `Ctrl+`` `) bascule la console sur les 4 routes Version, et n'a aucun effet ailleurs.
2. Une commande valide s'exécute dans le repo sélectionné ; sa sortie apparaît en continu.
3. Aucune ligne ne peut lancer autre chose que le binaire `git` (pas de shell, opérateurs refusés).
4. Les commandes interactives listées au § 5 sont refusées avant exécution ; aucune commande ne
   laisse la console bloquée en attente de saisie (éditeur, pager, identifiants).
5. Interrompre tue le processus et ses descendants en moins de 2 s ; la saisie redevient active.
6. Après chaque commande, statut, graphe et branches du panneau Version reflètent l'état du repo
   sans action manuelle.
7. Fermer / rouvrir la console, ou naviguer hors des vues Version et revenir, conserve sortie et
   historique.
8. Git absent : message explicite, pas d'erreur non gérée.
9. Client web : bouton, raccourci et canal absents.
10. Aucune nouvelle dépendance native (pas de `node-pty`).

## Hors scope

- Terminal shell complet (Git Bash, PowerShell, xterm.js + node-pty), commandes interactives.
- Plusieurs consoles / onglets, split.
- Console dans le client web (nouvelle issue si besoin, avec sandbox serveur).
- Complétion (`Tab`) des sous-commandes, branches ou chemins.
- Utilisation des identifiants Polenta (PAT / OAuth) par le git système.
- Persistance de la sortie ou de l'historique entre deux lancements de l'application.
- Verrou entre opérations Polenta et commandes de la console.

## Alternatives rejetées

- **Console sur isomorphic-git** (aurait fonctionné sans git installé et en web) : isomorphic-git
  est une bibliothèque, pas une CLI — chaque commande serait à réimplémenter, et les commandes de
  dépannage utiles « en cas de galère » y sont absentes ou partielles (`rebase` / `--abort`,
  `reflog`, `cherry-pick`, `reset --hard`, `stash`, `fsck`). Un outil de secours ne doit pas non
  plus dépendre du moteur qui a pu créer l'état bloqué.
- **Vrai terminal Git Bash** (xterm.js + node-pty) : interactif, mais module natif à packager
  (mêmes difficultés que keytar, cf. `electron-builder.config.ts`) et shell arbitraire ; le
  besoin est couvert par la console git.
