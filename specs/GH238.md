# GH238 — Terminal Git Bash dans la vue Version

Issue : #238 — « Ajout Terminal dans la vue version » (milestone C).

## Besoin

Pouvoir taper des commandes « en cas de galère » avec l'interface de version — git (état bloqué,
rebase/merge à annuler, reflog, reset…) mais aussi `cd`, `rm`, `ls`… — sans quitter Polenta, via
un panneau bas ouvert par `Ctrl+ù` comme le terminal de VS Code.

## Décisions de cadrage (échange du 2026-10-30)

| Question | Décision |
|---|---|
| Forme | **Vrai terminal** (pseudo-terminal) exécutant **Git Bash** — révise une première version « console git seule », abandonnée pour avoir `cd`, `rm`… |
| Moteur git / shell | Ceux **du PC** (Git for Windows) ; rien d'embarqué ; installation proposée si absents |
| Portée | Vues **Version** seulement : `/graph`, `/diff`, `/version-diff`, `/baseline` |
| Sessions | **Une** session ; ouverte dans le repo sélectionné du panneau Version |
| Client web | **Absent** (desktop seulement) |

## Description fonctionnelle

### 1. Panneau

- Panneau horizontal **en bas de la zone principale** (sous la vue courante ; l'ActivityBar et le
  panneau latéral ne sont pas réduits).
- Disponible uniquement quand la route active est une vue Version (`/graph`, `/diff`,
  `/version-diff`, `/baseline`). Sur toute autre route le panneau n'est pas rendu et `Ctrl+ù` est
  sans effet.
- Ouverture / fermeture :
  - `Ctrl+ù` (bascule) — également `Ctrl+`` ` pour un clavier QWERTY (même touche physique que
    VS Code). Fonctionne aussi quand le focus est dans le terminal. À l'ouverture, le focus va
    dans le terminal ; à la fermeture, il revient à la vue.
  - Bouton **Terminal** (icône terminal) dans le header du panneau latéral Version.
  - Bouton × dans l'en-tête du terminal.
- Hauteur réglable par une poignée sur le bord haut (min 80 px, max 70 % de la zone principale) ;
  le terminal se redimensionne (colonnes/lignes) avec le panneau.
- Hauteur et état ouvert/fermé mémorisés pour la session de l'application : quitter une vue
  Version masque le terminal, y revenir le réaffiche s'il était ouvert.
- **Fermer / masquer ne tue pas le shell** : le processus, son contenu affiché et son historique
  continuent jusqu'à la fermeture de l'application, au changement de projet ou à un clic sur
  **Tuer**.

### 2. En-tête du terminal

- Nom du shell (`Git Bash`, ou celui de §5) + nom du repo dans lequel la session a été ouverte
  (chemin absolu en infobulle).
- Bouton **Aller au repo sélectionné** : visible seulement quand le repo sélectionné dans le
  panneau Version diffère du repo d'ouverture de la session ; il tape dans le shell
  `cd '<chemin du repo au format du shell>'` suivi d'Entrée. (Il le fait aussi si un programme
  tourne au premier plan : à l'utilisateur de choisir le bon moment.)
- Bouton **Effacer** (efface l'affichage, équivalent `clear`), bouton **Tuer** (termine le shell
  et ses descendants ; le panneau affiche alors l'état « terminé » de §4), bouton ×.

### 3. Terminal

- Émulateur de terminal complet dans le renderer, connecté à un pseudo-terminal du main process :
  couleurs, édition de ligne, complétion `Tab`, programmes interactifs (`less`, `vim`,
  `git rebase -i`, `git add -p`, invites d'identifiants…) fonctionnent comme dans Git Bash.
- Thème clair / sombre suivant celui de Polenta ; police à chasse fixe ; défilement arrière de
  5 000 lignes.
- Clavier : toutes les touches vont au shell, sauf :
  - `Ctrl+ù` / `Ctrl+`` ` → bascule du panneau ;
  - `Ctrl+C` **avec une sélection** → copie (sans sélection → envoyé au shell, interrompt) ;
  - `Ctrl+V` et `Ctrl+Maj+V` → colle ; `Ctrl+Maj+C` → copie.
  Les autres raccourcis de Polenta (`Ctrl+B`, `Ctrl+T`, `Ctrl+W`…) ne s'appliquent **pas** quand
  le focus est dans le terminal (ex. `Ctrl+W` efface un mot dans bash).
- Clic droit : menu Copier / Coller / Effacer.

### 4. Cycle de vie de la session

- Créée à la **première ouverture** du panneau (pas au lancement de Polenta), dans le repo
  sélectionné à ce moment (`SelectedRepoContext`).
- Le shell se termine (`exit`, Tuer, plantage) → le terminal affiche
  `[processus terminé — code <n>] Appuyez sur Entrée pour relancer` ; Entrée relance un shell
  dans le repo **sélectionné à ce moment**.
- Changement de projet : la session est tuée ; la prochaine ouverture en crée une nouvelle.
- Fermeture de l'application : tous les shells et leurs descendants sont tués.
- Environnement du shell : celui de l'utilisateur, **sans** les variables propres à
  Electron/Polenta (`ELECTRON_*`, notamment `ELECTRON_RUN_AS_NODE`), avec `TERM=xterm-256color`.

### 5. Shell lancé et Git absent

- **Windows** : Git Bash = `bin\bash.exe` de l'installation Git for Windows, lancé en shell de
  login interactif. Installation localisée par : `git.exe` trouvé dans le PATH (racine = parent
  de son dossier `cmd`/`bin`), puis emplacements standards (`%ProgramFiles%\Git`,
  `%LocalAppData%\Programs\Git`). Le PATH du processus Polenta n'étant pas mis à jour par une
  installation faite pendant qu'il tourne, les emplacements standards sont toujours consultés :
  Git installé devient utilisable **sans redémarrer** Polenta.
- **macOS / Linux** : `$SHELL` de l'utilisateur (repli `/bin/bash`), en shell de login. Pas
  d'installation pilotée (git y est généralement présent ou installé par le système).
- **Git Bash introuvable (Windows)** : le panneau affiche « Git Bash introuvable sur ce poste »
  avec deux boutons :
  - **Installer Git** — si `winget` répond : lance
    `winget install --id Git.Git -e --source winget --accept-package-agreements
    --accept-source-agreements`, sortie affichée en continu dans le panneau, interruptible ;
    l'élévation éventuelle (UAC) est demandée par l'installeur lui-même ; à la fin, détection
    relancée et, si trouvé, ouverture du shell. Échec ou winget absent → ouvre
    https://git-scm.com/downloads dans le navigateur par défaut.
  - **Revérifier** — relance la détection (aussi relancée à chaque ouverture du panneau).
- Polenta **n'embarque pas** git/bash (GPLv2, cf. modèle de licences) et n'en télécharge pas
  pour son propre usage.

### 6. Synchronisation avec l'interface

- Les modifications de fichiers du working tree et les changements de HEAD/refs sont déjà vus par
  le watcher des repos (exigences, tests, index) — inchangé.
- En plus, pour l'index git et les états de merge/rebase qu'il ne voit pas : après chaque `Entrée`
  tapée dans le terminal, **dès que la sortie est restée silencieuse 500 ms**, l'interface est
  rafraîchie pour le repo d'ouverture de la session **et** le repo sélectionné : statut (Stagés /
  Modifications), graphe, branches et combobox de branche, tags, état d'intégration. Même
  rafraîchissement à la fermeture du panneau et à la fin du shell.
- Les opérations Polenta et le terminal ne sont pas sérialisés : si les deux écrivent en même
  temps, git signale l'erreur (`index.lock`…) ; aucun verrou ajouté.

### 7. Client web

- Pas de terminal : bouton masqué, `Ctrl+ù` sans effet, canaux IPC absents de la liste blanche du
  serveur web. Motif : un shell sur l'hôte multi-clients = exécution de commandes arbitraires.

### 8. Avertissements (documentés, pas de garde-fou)

- Le terminal agit sur les fichiers **sans passer par Polenta** : supprimer à la main le fichier
  d'un objet (`rm requirements/SYS-0001.yaml`) ne pose pas de pierre tombale (GH20), éditer un
  YAML peut contourner l'historique (GH77) ou les arbres maintenus par l'app. Ces écarts sont
  ceux d'une édition hors application, déjà traités par Polenta à la lecture ; aucune
  confirmation n'est ajoutée.
- Les identifiants distants sont ceux du git du PC (Git Credential Manager…), pas le jeton
  PAT / OAuth de Polenta.

## Cas d'usage

| # | Situation | Comportement attendu |
|---|---|---|
| U1 | Sur `/graph`, `Ctrl+ù` | Panneau ouvert, Git Bash démarré dans le repo sélectionné, focus dans le terminal |
| U2 | `git status`, `ls`, `cd ..`, `rm fichier` | Exécutés comme dans Git Bash, couleurs incluses |
| U3 | `git log` long | Pager `less` utilisable (`q` pour sortir) |
| U4 | `git rebase -i HEAD~3` | Éditeur de Git Bash ouvert dans le terminal, rebase mené à terme |
| U5 | Rebase bloqué → `git rebase --abort` | Graphe et statut du panneau Version à jour ≤ 1 s après la fin de la sortie |
| U6 | `git add fichier` | Fichier passé dans Stagés du panneau sans action manuelle |
| U7 | `Ctrl+C` sans sélection pendant `git fetch` | Commande interrompue |
| U8 | Sélection de texte + `Ctrl+C` | Texte copié, rien envoyé au shell |
| U9 | `Ctrl+ù` dans le terminal | Panneau masqué, focus rendu à la vue, shell toujours vivant |
| U10 | Ouvert sur `/graph`, navigation `/requirements` puis retour | Masqué puis réaffiché, contenu et processus intacts |
| U11 | Clic sur un repo composant dans l'arbre | Bouton « Aller au repo sélectionné » apparaît ; clic → `cd` dans ce repo |
| U12 | `exit` | `[processus terminé — code 0] …` ; Entrée relance un shell |
| U13 | Changement de projet | Session tuée ; réouverture → nouveau shell dans le nouveau projet |
| U14 | Windows, Git absent | « Git Bash introuvable », Installer Git / Revérifier |
| U15 | Installer Git via winget | Sortie winget affichée ; à la fin, shell ouvert sans redémarrer Polenta |
| U16 | Git absent, pas de winget | Installer Git ouvre git-scm.com/downloads |
| U17 | Sur `/requirements`, `Ctrl+ù` | Rien |
| U18 | Client web | Aucune trace du terminal |
| U19 | Fermeture de Polenta avec un `git fetch` en cours | Shell et `git` tués, aucun processus orphelin |

## Critères d'acceptation

1. `Ctrl+ù` (et `Ctrl+`` `) bascule le panneau sur les 4 routes Version, y compris focus dans le
   terminal, et n'a aucun effet ailleurs.
2. Windows : Git Bash démarre dans le repo sélectionné ; commandes shell et git, `Tab`, pager,
   éditeur et programmes interactifs fonctionnent comme dans Git Bash hors Polenta.
3. Le redimensionnement du panneau ajuste les colonnes/lignes du shell (pas de retour à la ligne
   cassé dans `git log --oneline --graph`).
4. Masquer / naviguer hors des vues Version et revenir conserve processus et contenu.
5. Copier / coller selon §3 ; `Ctrl+C` sans sélection interrompt.
6. Après une commande git modifiant index, HEAD ou refs, le panneau Version reflète l'état du repo
   en ≤ 1 s après la fin de la sortie, sans action manuelle.
7. Aucun processus shell/git orphelin après Tuer, changement de projet ou fermeture de Polenta.
8. Git absent : message explicite, Installer Git (winget, sinon page de téléchargement),
   Revérifier ; Git installé utilisable sans redémarrer Polenta.
9. Client web : bouton, raccourci et canaux absents.
10. Le module de pseudo-terminal est livré **prébuilt** dans l'installeur (pas de compilation
    C++ à l'installation ni au build, cf. `npmRebuild: false`) et chargé hors de l'asar.

## Hors scope

- Plusieurs terminaux / onglets, split, choix du shell (PowerShell, cmd, WSL…) ou préférence de
  chemin du shell.
- Terminal ailleurs que dans les vues Version ; terminal dans le client web.
- Git ou bash embarqués dans Polenta ; installation hors winget (téléchargement direct,
  installation silencieuse).
- Utilisation des identifiants Polenta (PAT / OAuth) par le git du PC.
- Persistance du contenu du terminal entre deux lancements de l'application.
- Liens cliquables, recherche dans la sortie, garde-fous sur `rm` & co, verrou entre opérations
  Polenta et terminal.

## Alternatives rejetées

- **Console git seule** (première version de cette spec : ligne de saisie, `git` lancé sans
  shell, pas de module natif) : abandonnée par l'humain — pas de `cd`, `rm`, ni de commandes
  interactives.
- **Console sur isomorphic-git** : bibliothèque, pas une CLI ; commandes de dépannage
  (`rebase --abort`, `reflog`, `cherry-pick`, `reset --hard`, `stash`) absentes ou partielles.
- **Git embarqué** (MinGit / dugite-native) : binaire GPLv2 distribué avec Polenta, +quelques
  dizaines de Mo ; refusé au profit du git du PC avec installation proposée.
- **bash lancé sans pseudo-terminal** (simples pipes) : pas d'édition de ligne, de pager ni de
  programme interactif, couleurs désactivées par git — ne répond pas au besoin.
