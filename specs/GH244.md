# GH244 — Issue : objet, vue Issues, impacts, proposition de création

Lot 4/9 du milestone D. Spec globale : `specs/MILESTONE-D.md` §4, qui fait foi.

## But

Tracer le « pourquoi » d'une modification du produit que les exigences ne décrivent pas (correction de
bug, non-conformité, évolution), et la faire entrer dans une version au même titre qu'une exigence ou
un test, avec son impact et ses tests à exécuter.

## 1. Objet

Nouvelle catégorie d'objet **`issue`**, stockée dans `issues/<ID>.yaml` du repo de son composant.

```yaml
# issues/ISS-0007.yaml
id: ISS-0007
objectTypeRef: root::issue
title: Coupure intempestive à -10 °C
status: corrigee
version: 1
origin:                     # absent si créée à la main
  runs: [RUN-20261030-004]
fields:
  description: <p>…</p>
history: …                  # GH77
```

- **Types configurables** : plusieurs types par nœud (bug, non-conformité, demande d'évolution…), préfixe
  unique, `fields`, `statuses`. Bouton « + Issue » dans la structure du modèle de données, comme « + Version ».
  Déclarable sur tout nœud local, comme une exigence.
- **Statuts par défaut** : `ouverte` → `en_cours` → `corrigee` ; `rejetee` (`isTerminal`). `corrigee` n'est
  volontairement pas terminal : un terminal sort du backlog, et une correction doit pouvoir entrer dans une
  version.
- **Pas de verrou d'approbation** : aucun statut `isApproval` attendu, et un statut ainsi marqué sur une
  issue n'a pas d'effet de verrou. `version` reste un champ système, sans incrément automatique.
- **`origin`** : `runs` seulement dans ce lot. `decisions` arrive avec la validation (#204).
- **Pas de suppression individuelle** : on passe au statut terminal (SPEC-REQ §9). Les IDs suivent GH20.
- **Modèle de données** : un type issue compte dans les gardes de suppression et le renommage de type.

## 2. Exigences impactées

- Liens `links/links.yaml` de type **`issue-impact`** : source = issue, cible = exigence.
- Le type de lien est **ajouté au schéma à la création du premier type issue** du repo (« impacte » /
  « est impactée par »), modifiable ensuite. Rien n'est ajouté aux schémas sans type issue.
- **Exigences du composant de l'issue seulement** : la cible doit appartenir au même repo et son type être
  déclaré par son schéma (règle de GH201). Refus à la création du lien, dans l'interface et par le MCP
  (`NOT_OWN_ELEMENT`).

## 3. Issue dans une version

Une issue suit les règles d'un changement (SPEC-REQ §11.3) :

- **Backlog** : jamais incluse, ou modifiée depuis la dernière version released qui l'incluait, hors statut
  terminal. Un simple changement de statut la fait donc revenir au backlog, comme une exigence.
- **« Ajouter »** : ses types sont proposés dans le sélecteur.
- **Page d'une version** : ligne de type « Issue », lien vers sa page, diff générique.
- **Passage released** : une issue incluse non commitée bloque comme les autres (`DIRTY_CHANGES`).
- **Analyse d'impact** : l'issue elle-même n'est pas une racine. Ses exigences impactées le sont, avec
  l'issue en source. Sans exigence impactée, elle reste une simple ligne de changement.
- **Tests à exécuter** : ces exigences amènent leurs tests, selon la règle existante.
- **Statut de design** : une issue n'en a pas ; il reste calculé sur les exigences.

## 4. Vue Issues

- Entrée de la barre d'activité : panneau latéral avec liste déroulante de composant (comme Exigences et
  Tests), filtre texte et statut, statuts terminaux masqués par défaut, bouton « Nouvelle issue ».
- Page de création et de modification : ID, titre, statut, champs du type, exigences impactées (lecture et
  édition des liens), origine (liens vers les exécutions), historique.
- Composant en lecture seule : consultation seulement (`READONLY_REPO`).

## 5. Proposition de création

Popup **jamais automatique dans ses effets** : rien n'est créé sans action de l'utilisateur.

- **Déclencheur** : enregistrement d'une exécution `FAIL` ou `BLOCKED` depuis l'écran d'exécution d'une
  campagne, sur un test d'un composant qui a un type issue. Pas de popup sinon.
- **« Créer une issue »** : ouvre la page de création pré-remplie : `origin.runs`, titre « Échec de
  `<ID du test>` — `<titre>` », liens d'impact vers les exigences du test (celle de l'instance si
  l'exécution en porte une), limités au composant. Rien n'est écrit avant l'enregistrement.
- **« Lier à une issue existante »** : ajoute l'exécution à `origin.runs` de l'issue choisie et les
  exigences manquantes à ses impacts.
- **« Ignorer »** : ferme, sans trace. La popup n'est pas reproposée pour cette exécution.
- **Import Excel** : voir Q1. **MCP** : pas de popup.

## 6. Graphe et MCP

- Graphe : collection `issues` (`origin`, champs, statut, historique), impacts dans `links` ; manifeste + 1
  et `polenta.d.ts` régénéré.
- MCP : `list_issues`, `get_issue`, `create_issue`, `update_issue`, liens par les outils existants.
  `get_version_*` inclut les issues.

## 8. Critères d'acceptation

1. Créer un type issue ajoute `issue-impact` au schéma ; un second type ne le duplique pas.
2. Une issue créée a un ID séquentiel, un fichier `issues/<ID>.yaml` et son historique de statut.
3. Un lien d'impact vers une exigence d'un autre composant est refusé (`NOT_OWN_ELEMENT`).
4. Une issue non terminale apparaît au backlog, s'inclut, et y revient si elle est modifiée après un
   passage released. Une issue `rejetee` jamais incluse n'y apparaît pas.
5. Une issue incluse, avec exigence impactée liée à d'autres éléments : l'exigence est racine de l'analyse
   et ses tests sont proposés.
6. Une issue incluse sans exigence impactée : ligne de changement, aucune racine, passage released possible.
7. Une issue incluse non commitée bloque le passage released (`DIRTY_CHANGES`).
8. Une exécution FAIL ou BLOCKED déclenche la popup ; PASS ne la déclenche pas ; un composant sans type issue
   non plus.
9. « Créer » pré-remplit sans rien écrire avant l'enregistrement ; « Lier » met à jour `origin.runs` et les
   impacts ; « Ignorer » n'écrit rien.
10. Une issue d'un composant en lecture seule est consultable, pas modifiable.
11. Le graphe expose `issues`, et les outils MCP créent et modifient une issue.
