## Contexte

État du code (`milestone-D` @ `e6beee9`, après #201) :

- Version : `versions/<ID>.yaml`, `changes` avec `base`, page (`version.$versionId.tsx`) listant les
  changements de la version et ceux des versions des composants postérieures à `basedOn`
  (`VersionsService.page` → `rows`) ; plusieurs versions en cours par repo ; `freeze.at`.
- Moteur conservé : `TraceabilityService.buildImpactTreesFromSnapshot`, `loadWorkingTreeSnapshot`,
  composant `ImpactTrees`, 8 statuts d'impact (`ImpactAnalysisStatus`).
- Retirés par #243, à réintroduire : `computeChangeAnalysis`, `computeTestsToRun`,
  `ChangeAnalysisSection`, `ChangeCampaignsSection`.

## 1. Analyse d'impact d'une version

- **Racines** : les éléments changés que liste la page de la version — ses propres `changes` **et**
  ceux des versions de ses composants postérieures à `basedOn` (même ensemble que `rows`, éléments
  introuvables exclus). Les exigences impactées par les issues incluses s'y ajouteront avec #244.
- **Arbres** : `buildImpactTreesFromSnapshot` sur l'état courant du workspace (disque), montants et
  descendants, libellé du lien vu du parent (GH207 §10bis).
- **Lignes** : éléments atteints par les arbres (hors racines), **du repo de la version seulement**
  (un composant a sa propre analyse) ; une ligne par élément :

  | ID (lien) | Type | Label | Statut d'impact | Commentaire | Source |
  |---|---|---|---|---|---|

  **Source** : la racine qui l'amène et le chemin (racine → … → élément, libellés de lien) ; plusieurs
  racines possibles : la première affichée, les autres au survol (« +2 »).
- **Statuts d'impact** (8 valeurs GH199, défaut `impact_non_verifie`) et commentaire saisis sur la
  ligne ou sur le nœud de l'arbre ; enregistrés dans la version : champ système **`impacted`**
  (`[{ id, status, comment? }]`), version en cours seulement. Une ligne enregistrée qui n'est plus
  atteinte reste affichée « n'est plus atteint » (statut conservé).
- **Live** tant que la version est en cours (recalcul à l'ouverture et aux changements de fichiers).
- **Figée au passage released** : l'analyse (lignes, statuts, sources, `computedAt`) est écrite dans
  le champ système **`analysis`** de la version, dans le commit du passage released (GH201 §3) ;
  la page d'une version released affiche l'analyse figée. Pas d'autre condition au passage released
  (contraintes de transition : #206).
- **Signal d'impact** (pour la vue Validation, #204) : pour une version, l'ensemble des éléments
  **changés ou impactés** avec leur source — fourni par le main (même calcul : figé si released).

## 2. Tests à exécuter

Calcul de #207 §10bis, appliqué à la version :

- **Sources** : les racines (§1) et toutes les lignes de l'analyse, **sauf** celles au statut
  `pas_d_impact_reel` (un test ainsi marqué n'est jamais proposé).
- Un test se propose lui-même ; une exigence amène les tests qui la couvrent (lien de couverture, sens
  indifférent), avec l'instance de cette exigence pour un test itérant (T179). Exigence sans test :
  listée « non couverte ».
- **Liste cochable** : test, élément(s) qui l'amènent, **« Déjà dans »** = campagnes **ouvertes**
  (`planned` / `in_progress`) du repo qui le contiennent déjà (information calculée, aucun lien).
  Coché par défaut : ce qui n'est dans aucune campagne ouverte.
- **Raccourcis** (Q2), à partir des seuls tests cochés :
  - **« Créer une campagne »** : `/campaign/new` pré-rempli (titre `<ID> — <label>`, tests et instances,
    repo de la version) ; l'utilisateur ajuste et crée comme d'habitude.
  - **« Ajouter à … »** : menu des campagnes ouvertes du repo ; sélecteur de tests de la campagne
    (GH33) pré-coché, paramètres compris ; rien n'est ajouté sans validation.
- Disponibles pour une version en cours **et** released (on teste aussi après livraison) ; pas pour
  une abandonnée.

## 3. Page d'une version

Sous « Changements », deux sections repliables : **« Analyse d'impact »** (lignes, puis arbres par
racine — `ImpactTrees`) et **« Tests à exécuter »** (liste cochable, non couvertes, raccourcis). État
replié mémorisé par poste.

## 4. Graphe et MCP

- Graphe : `GraphVersion.impacted` (statuts saisis) et `GraphVersion.analysis` (analyse figée, `null`
  tant que la version est en cours) — données brutes stockées, pas de calcul live dans le graphe ;
  manifeste incrémenté.
- MCP (lecture) : `get_version_impact` (analyse live ou figée, avec sources) et
  `get_version_tests` (tests à exécuter, non couvertes, « déjà dans »).

## Critères d'acceptation

1. Version en cours incluant SYS-0001 : l'analyse liste les éléments du repo atteints depuis SYS-0001,
   avec leur source (SYS-0001 → … → élément) ; un élément d'un autre repo n'y figure pas.
2. Version produit : les changements des versions des composants postérieures à `basedOn` sont des
   racines ; leurs impacts dans le repo produit sont listés.
3. Statut et commentaire saisis → `impacted` dans le fichier ; élément plus atteint : ligne « n'est plus
   atteint », statut conservé.
4. Passage released : `analysis` écrite dans le commit ; page released = analyse figée, non éditable.
5. Tests à exécuter : racines + lignes hors `pas_d_impact_reel` ; exigence non couverte signalée ;
   « Déjà dans » d'après les campagnes ouvertes du repo.
6. « Créer une campagne » : création pré-remplie avec les tests cochés ; ni la campagne ni la version
   ne portent de lien.
7. « Ajouter à … » : sélecteur de la campagne pré-coché ; rien sans validation.
8. Graphe (`impacted`, `analysis`) et outils MCP `get_version_impact`, `get_version_tests` disponibles.

## Hors périmètre

- Issues et leurs exigences impactées comme racines (#244).
- Version prévue / testée d'une exécution (#202) — la référence à la version vit côté exécution (Q1).
- Vue Validation et usage du signal d'impact (#204 / #205) ; conditions de transition (#206).
- Impactés **déclarés** à la main (sans changement) : non repris — on inclut l'élément dans la version
  (« Ajouter ») pour en faire une racine.
