# GH252 — Client web : versions, analyse d'impact et validation

> Le client web est maintenu (humain, 2026-11-03). Après #256 (`tested-config:*`, `issues:*`), il manque les vues des
> versions et de la validation, livrées pour le desktop seul.

## Constat

- **27 canaux masqués** dans `WEB_HIDDEN` : 16 `versions:*`, 10 `validations:*`, `issues:add-decision`.
- **Panneau Version** : visible sur le web, mais ses appels `versions:*` répondent 404. Le sous-panneau Produit, le
  backlog et la page d'une version ne fonctionnent pas. Les e2e web tolèrent ces 404 (`gh243`).
- **Vue Validation** : entrée masquée (`capabilities.productValidation`).
- **Reflets (#210)** : affichés sur le web, label de version sans lien.
- **Audit des autres écarts** : comparaison des canaux appelés par `api-client` et des canaux exposés. Hors des 27, il reste :
  - propres au desktop : dialogues de fichiers, mise à jour, ouverture externe, `app:zoom`, fenêtre d'export ;
  - terminal, hors périmètre (décision du 2026-11-03) ;
  - `web:*`, `export:*` et classeur d'exécution : couverts par `WEB_ONLY` ou le pont web.

  Cet audit porte sur les canaux, **pas écran par écran**.

## 1. Comportement

Mêmes écrans et mêmes règles que sur le desktop, dans le navigateur :

- **Versions** : sous-panneau Produit, backlog, inclusion, page, copie, suppression, abandon, passage released avec tag,
  analyse d'impact, statuts d'impact, tests à exécuter.
- **Validation** : entrée de la barre d'activité, liste, création, décisions, confirmation, rejet, signature, annulation,
  suppression, popup d'issue sur une décision.
- **Reflets** : le label de version devient un lien.
- **Tag** : posé dans le clone de l'utilisateur sur le serveur, poussé à son prochain push, avec son accès à la forge.
- **Auteur** des commits de release et de signature : le compte de la session.
- **Droits** : aucun rôle ajouté. Les refus existants s'appliquent (`READONLY_REPO`, verrous, motifs de signature).

## 2. Garde de chemins

Chaque canal exposé déclare dans `ROOT_ARGS` la position du repo **et** du `workspaceDir`. Un chemin hors de l'espace de
l'utilisateur est refusé, comme pour les autres canaux. Un test le vérifie sur les 27 canaux.

## 3. Décisions proposées

| # | Question | Recommandation | Pourquoi |
|---|---|---|---|
| D1 | Zoom de l'interface (GH237) | **Laisser le zoom du navigateur** ; écart assumé dans SPEC-WEB §11 | Le navigateur l'offre déjà ; un second zoom se cumulerait |
| D2 | Release et signature depuis le navigateur | **Permises**, comme sur le desktop | Sans elles, la vue serait incomplète ; l'historique et l'auteur tracent déjà qui a signé |
| D3 | `capabilities.productValidation` | **Retirée** | Plus aucune différence à porter |
| D4 | Tolérance des 404 dans les e2e web | **Retirée de `gh243`** | Elle masquerait une régression sur ces canaux |

## 4. Cas d'usage

| # | Situation | Résultat attendu |
|---|---|---|
| U1 | Web, panneau Version, repo avec un type version | sous-panneau Produit et backlog chargés, aucun 404 |
| U2 | Créer une version, inclure un élément, voir la page | changements et diff affichés |
| U3 | Analyse d'impact, statut saisi sur un nœud | statut enregistré |
| U4 | Passage released | commit et tag dans le clone ; « Tag … pas encore poussé » affiché |
| U5 | Push du repo | tag présent sur la forge, mention retirée |
| U6 | Créer une validation, décider, signer | signature enregistrée, auteur = compte de la session |
| U7 | Décision « non conforme » | popup d'issue, issue liée à la décision |
| U8 | Label de version dans la colonne Design | ouvre la page de la version |
| U9 | Chemin d'un autre utilisateur passé à `versions:get` ou `validations:page` | refusé |

## Critères d'acceptation

1. Les cas U1 à U9 sont couverts par des scénarios `e2e-web`, ou unitaires pour U9.
2. Plus aucun canal `versions:*`, `validations:*` ni `issues:add-decision` dans `WEB_HIDDEN`.
3. SPEC-WEB §11 ne garde que les écarts assumés : terminal, zoom (si D1), et ceux déjà listés sans lien avec ce ticket.
4. Les e2e desktop `gh204` et `gh210` restent verts.
