# GH254 — Renommer le préfixe d'un type ne met pas à jour les changements des versions

Trouvé pendant #202 à la lecture du code. Confirmé et traité à la suite de la revue du milestone D.

## Root cause

`TypeRenameService` réécrit les ID dans les dossiers de données, dont `versions/` ne fait pas partie. Après un renommage de préfixe, une version
cite des ID qui n'existent plus : lignes « supprimé », éléments de retour au backlog, analyse sans racine.

Réécrire ces fichiers ne suffit pas : l'état figé d'une version et son tag gardent les anciens ID, dans l'historique git.

Une cause voisine a été trouvée : la clé de comparaison d'un élément contenait `objectTypeRef`. Renommer le **nom** d'un type, sans toucher au
préfixe, faisait revenir tous ses éléments livrés au backlog, et leur retirait leur statut de design.

## Correctif

- **Préfixe :** refus avec `HAS_VERSIONS`, en nommant les versions, tant qu'une version d'un repo du workspace cite un objet du type, quel que soit le champ
  ou le statut de la version. C'est la seconde option de l'issue, et elle suit la règle des validations.
- **Nom seul :** `objectTypeRef` sort de la clé de comparaison. Le renommage reste permis.

## Conséquence

Le préfixe d'un type dont un objet a été livré ne se modifie plus. Pour une version encore en cours, retirer l'élément de ses changements lève le refus. Le nom du type et ses libellés restent modifiables.

## Comment vérifier

- Tests : `npx vitest run src/main/services/type-rename.service src/main/services/versions.gh201`.
- Manuel : éditeur de schéma, sur un type dont un élément est dans une version. Changer le préfixe : refus nommant la version. Changer seulement le nom : accepté, et le backlog ne bouge pas.

## Non couvert

Les tests de campagne et les runs qui citent une version sont hors de ce ticket : ils référencent l'ID de la version, jamais renommé.
