# GH26 — Desktop : mise à jour automatique de l'application

Issue : [#26](https://github.com/laurentolive/polenta/issues/26) — type:feature

## 1. Contexte

- `electron-updater` est en dépendance de `apps/desktop` mais n'est branché nulle part ;
  SPEC-TECH-stack §9 annonce déjà « vérification au démarrage, téléchargement en arrière-plan ».
- La cible Windows actuelle est `portable` (`Polenta-X.Y.Z.exe`), **non supportée** par
  `electron-updater` (qui ne sait mettre à jour qu'une installation NSIS).
- Les releases sont publiées par `.github/workflows/release.yml` sur `laurentolive/polenta`
  (repo **public**) à chaque tag `vX.Y.Z` ; seul `apps/desktop/dist/*.exe` est publié aujourd'hui.
- La version courante est exposée au renderer via `app:get-version` (`app.getVersion()`) et
  affichée dans la barre de titre (`Polenta vX.Y.Z — …`, `ProjectPanel.tsx`).

## 2. Description fonctionnelle

L'application vérifie au démarrage, silencieusement, si une version plus récente est publiée.
Si oui, elle la télécharge en arrière-plan puis le signale par un **badge discret**. L'utilisateur
installe quand il le souhaite (bouton « Redémarrer pour installer »), ou la mise à jour s'installe
d'elle-même à la prochaine fermeture de l'application. Aucune popup, aucune interruption.

### 2.1 Packaging Windows : passage du portable à NSIS par utilisateur

- Cible Windows : `nsis` à la place de `portable`.
- Installation **par utilisateur** (`perMachine: false`) dans `%LOCALAPPDATA%\Programs\Polenta` :
  **aucun droit administrateur** requis, ni à l'installation ni lors des mises à jour.
- Installeur « one-click » (pas d'assistant), raccourcis bureau + menu Démarrer.
- Nom d'artefact conservé : `Polenta-Setup-${version}.exe` (le suffixe distingue l'installeur
  de l'ancien exe portable).
- `publish` configuré sur le provider GitHub `laurentolive/polenta`, pour que le build génère
  `latest.yml` (+ `.blockmap`).
- `userData` (auth.json, workspace.json, keytar) est inchangé : un utilisateur qui passe du
  portable à la version installée retrouve ses comptes et projets.

### 2.2 Publication

- `release.yml` publie, en plus de l'installeur : `latest.yml` et
  `Polenta-Setup-${version}.exe.blockmap`. Sans `latest.yml`, aucune détection n'est possible.
- Les releases GitHub marquées **pré-release** ou **draft** ne sont pas proposées
  (`allowPrerelease: false`).

### 2.3 Cycle de mise à jour

| Étape | Comportement |
|-------|--------------|
| Démarrage | Si la préférence est active et que l'app est **packagée**, vérification ~10 s après l'ouverture de la fenêtre (ne ralentit pas le démarrage). |
| Pas de nouvelle version | Rien n'est affiché. |
| Hors ligne / erreur réseau / GitHub indisponible / `latest.yml` absent | Rien n'est affiché ; l'erreur est seulement journalisée (log main). |
| Nouvelle version trouvée | Téléchargement automatique en arrière-plan (`autoDownload: true`), sans indicateur bloquant. |
| Téléchargement terminé | Le badge apparaît (§2.4). |
| Fermeture normale de l'app | Si une mise à jour est téléchargée, elle s'installe silencieusement à la fermeture (`autoInstallOnAppQuit: true`) ; le lancement suivant est sur la nouvelle version. |
| Clic « Redémarrer pour installer » | L'app se ferme, installe et se relance (`quitAndInstall`). |

Une seule vérification par session (pas de vérification périodique).
En mode développement (`pnpm dev`, app non packagée), aucune vérification.

### 2.4 Badge

- Indicateur discret (petite pastille / icône) dans la barre latérale, visible quelle que soit
  la vue ; apparaît **uniquement** quand une mise à jour est téléchargée et prête.
- Au survol : info-bulle « Polenta vX.Y.Z est disponible ».
- Au clic : petit panneau/popover avec la version disponible, un lien « Voir les nouveautés »
  (page de la release GitHub, ouverte dans le navigateur) et le bouton
  « Redémarrer pour installer ».
- Si des modifications non commitées existent dans le projet ouvert, le bouton reste utilisable
  (les fichiers sont déjà sur disque — rien n'est perdu au redémarrage) ; aucune confirmation
  supplémentaire n'est exigée.
- Fermer le popover ne masque pas le badge ; il reste présent jusqu'à l'installation.

### 2.5 Préférence on/off

- Case à cocher « Rechercher automatiquement les mises à jour au démarrage », **activée par
  défaut**.
- Préférence **de l'application** (par machine/utilisateur OS), stockée dans `userData` —
  **pas** dans `schema.yaml`/`preferences` qui sont des préférences de projet versionnées.
- Désactivée : aucune vérification ni téléchargement au démarrage. Prise en compte au prochain
  lancement.
- Emplacement UI : à trancher en Design (section « Application » de la page Préférences, ou
  panneau Compte), accessible même sans projet ouvert de préférence.

## 3. Critères d'acceptation

1. `pnpm package` produit `Polenta-Setup-X.Y.Z.exe`, `latest.yml` et le `.blockmap` dans
   `apps/desktop/dist/`.
2. L'installeur s'exécute sans élévation UAC et installe dans `%LOCALAPPDATA%\Programs\Polenta`.
3. Une release `vX.Y.Z` publiée par la CI contient les trois fichiers du critère 1.
4. Version installée N, release N+1 publiée : au lancement, le badge apparaît en moins de 2 min
   (connexion normale) sans aucune popup ni dialogue.
5. Clic « Redémarrer pour installer » : l'app se relance en N+1 (titre `Polenta vN+1`), comptes
   et projets récents conservés.
6. Sans cliquer : fermer l'app puis la relancer → elle démarre en N+1.
7. Version installée = dernière release : aucun badge, aucun message.
8. Réseau coupé au lancement : aucun badge, aucun message, aucune erreur visible.
9. Préférence désactivée : aucune requête vers GitHub au lancement (vérifiable dans les logs).
10. Une release marquée pré-release n'est jamais proposée.
11. `pnpm dev` : aucune vérification déclenchée.
12. Libellés UI en i18n (fr + en).

## 4. Hors scope

- Signature de code (certificat Authenticode) — SmartScreen avertira à la 1re installation
  d'un binaire non signé ; à traiter dans une issue dédiée si besoin.
- Builds macOS / Linux et leur mise à jour.
- Vérification manuelle depuis un menu, vérification périodique, « Ignorer cette version ».
- Canal pré-release / bêta.
- Migration automatique des utilisateurs du `.exe` portable : ils installent une fois
  l'installeur NSIS à la main (aucun mécanisme dans le portable ne peut le faire). La release
  qui introduit l'installeur le mentionnera dans ses notes.
- Installation pour tous les utilisateurs du poste (`perMachine: true`, qui exigerait l'admin).

## 5. Points d'attention pour le Design

- `autoUpdater` doit être instancié côté main, son état (`idle | downloading | ready`, version,
  URL des notes) exposé au renderer via IPC + événement push (le renderer peut monter après
  l'événement `update-downloaded` : prévoir un `get-state`).
- `electron-builder` 24 + `electron-updater` 6 : vérifier la compatibilité du format
  `latest.yml` et du nom d'artefact (le `path` de `latest.yml` doit pointer vers le nom publié).
- La CI tourne avec `GITHUB_TOKEN` : `electron-builder` ne doit pas tenter de publier lui-même
  (`--publish never`) — c'est `softprops/action-gh-release` qui téléverse.
- Les chemins packagés du serveur MCP (`process.resourcesPath`, T122) changent de dossier
  (portable temporaire → installation) ; les `.mcp.json`/`AGENTS.md` générés pointent vers
  `resources/mcp-server` : vérifier qu'ils restent valides après une mise à jour (même dossier
  d'installation → oui a priori).
