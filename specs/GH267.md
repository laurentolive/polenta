# GH267 — Validation signée : figer à la signature ce que le signataire a vu

> Décision de l'humain du 2026-11-04 : **figer** (option 1 de l'issue). Amende GH204 §3 et Q1 : liens, tests et
> exécutions n'y sont plus lus en direct pour une validation signée. Statut : **validée le 2026-11-04**, Q1 à Q5 retenues telles que proposées.

## 1. But

Une validation signée est un registre, et sur la version produit le go production série. Elle doit montrer durablement
ce que le signataire a vu, même si des liens, des exécutions ou la traçabilité changent ensuite.

Aujourd'hui, seules les décisions et l'exigence (lue au commit du gel) sont stables. Le statut de vérification, les tests
liés et leurs exécutions sont lus en direct : retirer un lien après la signature fait disparaître le test de la grille.

## 2. Ce qui est figé

À la signature, chaque entrée reçoit une copie `atSignature`, écrite dans le commit de signature :

```yaml
entries:
  - requirementId: SYS-0012
    decision: conforme
    contentHash: …
    atSignature:
      status: approved                     # statut de rédaction
      designVersion: { id: PRV-0001, title: "1.0" }   # absent si aucune
      coverageStatus: validated
      impact: { kind: impacted, sources: [ { rootId: ISS-0007, path: [] } ] }   # absent si aucun
      tests:
        - id: TST-0004
          title: Mesure du courant
          local: true
          lastRun:                         # absent si jamais exécuté, ou test d'un autre repo
            id: TST-0004-run-0002
            result: PASS
            executedAt: 2026-11-02T10:00:00.000Z
            executedBy: Alice
            notes: …
            testedConfig: { ref: PRV-0001, … }   # copie du run, absente si non renseignée
            testedDrift: […]                     # évolution constatée à la signature, absente si aucune
```

- **Source :** les lignes déjà calculées pour le contrôle de signature, plus la dernière exécution de chaque test, c'est-à-dire
  la même que celle affichée dans la grille.
- **Pas de copie des exécutions plus anciennes :** elles restent dans leurs fichiers de run.
- **Échec de lecture :** si la matrice ou l'historique des exécutions ne se lit pas, la signature est refusée. Une copie
  partielle serait une fausse preuve.
- **Champ système :** posé par l'application, jamais par le MCP ni à la main. Une proposition MCP ne le lit ni ne l'écrit.

## 3. Comportements

| Cas | Comportement |
|---|---|
| Validation signée, ou signée puis annulée | Rédaction, design, vérification, impact, et tests avec leur dernière exécution : **lus dans la copie** |
| Validation en cours | Inchangé, lecture en direct |
| Lien retiré, nouveau run, exigence ou test supprimé, après la signature | La grille reste identique |
| Déplier un test d'une validation signée | Ligne figée, puis exécutions actuelles sous le chevron, avec les mentions existantes dont « après la signature » (GH204 Q2) ; rien si le lien n'existe plus |
| Reprise vers la version suivante | `atSignature` n'est **jamais reprise** : la nouvelle validation repart en direct |
| Page d'une validation signée | Ne dépend plus de la matrice : une erreur de traçabilité n'empêche ni de l'ouvrir ni de l'annuler |
| Annulation | Les copies restent dans le fichier, l'annulation ne réécrit pas la preuve |

La mention **« À la signature »** en tête de la colonne ou du détail indique d'où viennent les valeurs.

## 4. Fusion git (doute repris de #266)

Fusion d'un fichier signé avec une décision prise sur une autre branche : l'entrée ajoutée n'a pas de copie. Une ligne
d'un fichier signé dont l'entrée n'a pas d'`atSignature`, alors que d'autres en ont une, porte la mention
**« hors signature »**, et un bandeau le signale en haut de la page. Rien n'est réécrit : la correction consiste à annuler
puis à refaire la validation (GH204 Q5). La fusion n'est pas bloquée.

Une décision **modifiée** sur l'autre branche n'est pas détectée par ce contrôle. Pour la détecter, il faudrait figer une
empreinte de la décision, ce que je ne propose pas tant que le cas n'a pas été constaté (Q4).

## 5. Validations déjà signées

Pas de migration : sans aucune copie dans le fichier, la page reste en lecture directe, et affiche la mention
« signée avant le figeage ». Les données actuelles sont des données de test (Q3).

## 6. Graphe et MCP

- `GraphValidationEntry.atSignature` : donnée brute exposée telle quelle (GH79), pour les scripts d'audit côté projet.
  Manifeste du graphe +1, `polenta.d.ts` régénéré (Q2).
- MCP : lecture seule via les outils de validation existants, sans nouvel outil.
- Web : `validations:*` reste masqué (#252).

Ce n'est pas un nouvel indicateur : la copie conserve des valeurs déjà calculées par Polenta pour ses propres fonctions.

## 7. Critères d'acceptation

1. Une signature écrit `atSignature` sur chaque entrée, dans le commit de signature.
2. Après signature, retirer un lien, ajouter un run, ou supprimer le test : grille et détail figé identiques.
3. La page d'une validation signée s'ouvre et s'annule même si la matrice échoue.
4. Si la matrice ou l'historique échoue à la signature : refus, fichier inchangé.
5. La validation de la version suivante reprend les décisions sans `atSignature`.
6. Une entrée sans copie dans un fichier signé qui en contient : mention « hors signature » et bandeau.
7. Une validation signée sans aucune copie : lecture directe et mention « signée avant le figeage ».
8. `atSignature` est dans le graphe, jamais dans `history`.
9. Le MCP ne peut pas écrire `atSignature`.
10. Une validation en cours se comporte comme avant.

## 8. Hors périmètre

- Export ou impression du registre (GH204, script côté projet).
- Copie des tests et des exécutions d'un autre repo : `local: false` reste affiché « autre composant » (#255, #269).
- Empreinte ou signature cryptographique du fichier.
- Annuler automatiquement une validation hors signature.
