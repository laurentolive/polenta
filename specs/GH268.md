# GH268 — Versions : tag traité comme baseline, backlog sans fin, sous-composant retiré, tags en HTTPS

Trouvé à la revue du milestone D du 2026-11-04, à la lecture du code.

## Root cause et correctif

| Point | Root cause | Correctif |
|---|---|---|
| Tag vu comme une baseline | Sans composants, tout tag est une baseline, et rien ne protège un `freeze.tag` | `version-tags.util` : les tags des versions figées sortent de la liste et refusent la suppression, depuis les baselines comme depuis le graphe de commits (`sync:delete-tag`) |
| Élément livré qui revient au backlog | La boucle `outsideModifications` ignorait la livraison | Pas de ligne si le contenu est identique au gel de la dernière version qui l'inclut. Le signal revient dès que le contenu diffère |
| Sous-composant retiré, release bloquée | La page ne listait que les dépendances courantes | La page affiche les entrées orphelines, avec une action « Retirer » |
| Tags absents en HTTPS | isomorphic-git ne suit pas les tags par défaut | `tags: true` au fetch, et fetch après `git.pull`, qui n'a pas cette option. Un tag local n'est pas écrasé |
| Tag en échec invisible | Un simple `console.warn` | La page affiche « Tag … pas encore poussé » tant qu'il est en attente |
| Tag orphelin | Branche avancée pendant le commit, tag déjà posé | Tag retiré à l'échec, et le nouvel essai passe |
| `base` périmée | Calculée à l'inclusion seulement | Recalculée au gel |
| Tri sans garde | `localeCompare` sur `freeze.at` absent ou date YAML | Tri numérique, tolérant |
| Version abandonnée | Sa chaîne listait encore ses changements | Ses changements ne sont plus attribués au produit, et son état s'affiche à côté du composant |
| Graphe | `freeze.at` perdu | Exposé, manifeste +1 |
| Schéma illisible | Sans statuts, une version figée paraissait en cours et perdait son verrou | `update` refuse (`NO_VERSION_TYPE`) |

## Écartés, avec motif

- **Interdire d'abandonner une version référencée par un produit released** : le produit peut être dans un autre repo, inaccessible ici. L'état « abandonnée » s'affiche sur la page du produit.
- **Produit released sans version de composant** : conforme à GH201 §2. À revoir seulement si Q5 doit le couvrir.
- **Release sur une branche d'intégration abandonnée** : la spec ne restreint pas les branches, et aucun garde-fou fiable ne distingue une branche abandonnée. Question ouverte, à poser à l'humain.
- **Rafraîchir `base` sur une version encore en cours** : le diff d'une version en cours peut rester celui d'avant la livraison voisine jusqu'au gel, c'est-à-dire tant que cette base n'est pas figée.

## Comment vérifier

- Tests : `npx vitest run src/main/services/versions.gh201`.
- Manuel, sur le desktop :
  1. Sur un mono-repo, une version released : son tag n'est plus dans les baselines, et le graphe de commits refuse de le supprimer.
  2. Sur un produit avec composants, retirer un montage cité par une version en cours : l'entrée s'affiche avec « Retirer », et la release passe après son retrait.
  3. Version released, avant tout push : « Tag … pas encore poussé » sur sa page, qui disparaît après le push.

## Non couvert par un test automatique

Le fetch des tags en HTTPS demande un vrai serveur : à vérifier sur la forge de test ou PH2, depuis un second clone. L'affichage des entrées orphelines et du tag en attente est aussi à vérifier à la main.
