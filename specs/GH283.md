# GH283 — Tests unitaires : un processus de test perdu, son fichier disparaît du total sans échec

## Root cause

Sous Windows, avec le pool `forks` de vitest (un processus Node par fichier de tests), un processus meurt de temps en temps, environ une fois sur trois à cinq : `Worker exited unexpectedly`. Son fichier disparaît alors du total. Le code de sortie vaut 1, mais aucun test n'est en échec.

- **Pas un test fautif** : le fichier perdu change d'un passage à l'autre (`history.test.ts`, du code pur ; `forge/forge.service.test.ts`). Lancé seul, `history.test.ts` passe 8 fois sur 8.
- **Origine probable**, non démontrée : la fin d'un processus enfant sous Windows (libuv). Une assertion libuv a été vue une fois dans la journée, `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c`.
- **Code de sortie non capturé** : instrumenter le pool rendait le crash beaucoup plus rare. Il n'est apparu qu'une fois sur environ 45 passages instrumentés, sans être enregistré.

Un second défaut intermittent est apparu pendant les mesures, dans `integration-branch.service.test.ts` :

- nettoyage refusé (`ENOTEMPTY` sur `.git`, git qui vient de se terminer) ;
- hook dépassant 10 s (push par la CLI git vers un repo nu).

## Correctif

- `vitest.config.ts` : `pool: 'threads'`, et `hookTimeout: 20_000`, aligné sur `testTimeout`.
- `integration-branch.service.test.ts` : suppression du dossier temporaire avec `maxRetries`.

Tests seuls, application inchangée.

## Mesures

| Configuration | Passages | Worker perdu | Autre échec |
|---|---|---|---|
| `forks` (avant), sans instrumentation | 5 + 3 | 1 + 1 | — |
| `threads`, en ligne de commande | 12 | 0 | 1 (hook > 10 s) |
| `threads` + correctifs, configuration du dépôt | 14 | 0 | 0 |

Durée : environ 33 s en `threads`, contre 40 s en `forks`.

## Limites

- Cause du crash non démontrée. Les threads l'évitent, et la mesure le montre, mais rien ne prouve qu'il ne reviendra pas.
- Rien n'est mesuré sur `main`, ni sous Linux. Dans le cas où le crash reviendrait, le code de sortie 1 reste la seule alerte : il faut le lire, et pas seulement le total affiché.

## Comment vérifier

Depuis `apps/desktop`, en boucle : `npx vitest run > sortie.txt 2>&1`. Vérifier le code de sortie et `Tests 1403 passed (1403)`.
