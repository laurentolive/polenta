# GH288 — Vue Tableau : les largeurs de colonnes redimensionnées ne sont pas mémorisées

Type : bug — issue #288

## Symptôme

Une colonne redimensionnée à la souris dans la vue Tableau reprend sa largeur automatique dès
qu'on quitte la vue (vue Document, autre type, autre écran) puis qu'on y revient, et au
rechargement.

## Root cause

`ExcelView` tenait les largeurs dans un `useState` local (`colWidths`), perdu au démontage du
composant. Le nombre de colonnes figées (GH24), lui, est détenu par `SystemView` et écrit dans la
pref du type ; les largeurs n'avaient jamais été raccordées à ce mécanisme.

## Correctif

- `FieldVisibilityPref.colWidthsExcel?: Record<string, number>` (api-client) : largeurs en px par
  colonne, dans la pref par (type, utilisateur). Absent ⇒ largeurs automatiques. Le main fusionne
  les patchs de pref sans liste de clés : aucun changement côté main ni serveur web.
- `ExcelView` : props contrôlées `colWidths` / `onColWidthsChange`. Pendant le glissé, la largeur
  reste locale (`dragWidth`) ; seule la valeur finale est remontée au relâchement (pas d'écriture
  de pref à chaque pixel, rien si la poignée est cliquée sans déplacement).
- `SystemView` : lit `colWidthsExcel` au chargement des prefs du type, l'enregistre via
  `persistPrefs`.
- `TestPickerGrid` (sélecteur de tests d'une campagne) : reprend les largeurs de la vue Tableau du
  type sans les réenregistrer, comme il le fait pour les colonnes figées.
- Les largeurs ne font pas partie des vues enregistrées (GH203) : redimensionner une colonne ne
  marque pas la vue active « modifiée ».

## Comment vérifier

- Automatique : `e2e-web/gh288-col-widths.spec.ts` — redimensionne la colonne ID, passe en vue
  Document, revient en vue Tableau, puis recharge la page : la largeur est conservée.
- Manuel (desktop) : redimensionner une colonne, changer de type puis revenir ; fermer et rouvrir
  l'application ; ouvrir le sélecteur de tests d'une campagne et constater les mêmes largeurs que
  dans la vue Tableau des tests.
