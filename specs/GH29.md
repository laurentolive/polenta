# GH29 — Identité toujours `local` dans la vue Suivi et SystemView

Type : bug · Issue #29

## Root cause

Les écrans qui lisent/écrivent les préférences par utilisateur (`.{username}.pref`) —
`DashboardPanel`, routes `query` et `dashboard`, `SystemView` — appelaient
`api.auth.resolveIdentity(repoPath)` avec le **chemin local** du repo. `resolveIdentity`
attend une URL de remote : `new URL("C:\…").hostname` vaut `""`, keytar lève « Account is
required », la requête échoue et le repli `identity?.login ?? 'local'` s'applique toujours.
Tout était donc rangé dans `.local.pref`, quel que soit le compte connecté (d'où, au scénario
L2 de GH18, la requête privée écrite par le MCP dans `.laurentolive.pref` jamais affichée).

## Correctif

- **Nouveau canal `auth:project-username(repoPath) → string`**
  (`AuthService.projectUsername`, `api.auth.projectUsername`) : lit l'URL `origin` du repo,
  essaie son hôte puis `github.com` / `gitlab.com` (les hôtes sondés par le menu compte).
  Un hôte est « connecté » s'il a un jeton nu dans le trousseau (celui que la déconnexion
  supprime) ; le login vient de `auth.json` (compte actif d'abord), sans appel réseau — à
  défaut d'entrée dans `auth.json`, repli sur `resolveIdentity`. `local` si aucun compte.
- **Migration `.local.pref` (décision : fusion au premier accès)** — `migrateLocalPref`
  (`pref-store.util.ts`), appelée par `projectUsername` dès qu'un vrai login est résolu :
  fusion clé par clé dans `.{login}.pref`, le contenu existant de `.{login}.pref` l'emporte ;
  tableaux réunis (par `id` pour les objets : requêtes, dashboards, historique ; par valeur pour
  les ordres) ; objets fusionnés clé par clé (`fieldVisibility`). `.local.pref` est ensuite
  renommé `.local.migrated.pref` (toujours couvert par le `.gitignore` `*.pref`) → pas de
  double fusion, données d'origine conservées.
- **Renderer** : les 4 appelants utilisent `projectUsername` ; `username` reste vide tant que
  l'identité n'est pas résolue (les lectures, gardées par `!!username`, attendent — rien n'est
  lu ni écrit sous `local` par erreur pendant ce court instant ; `SystemView` le faisait déjà
  via `identityPending`). Les routes d'impression reçoivent `username` de ces écrans : corrigées
  par ricochet.
- `SPEC-ELECTRON-DESKTOP.md` (table Auth) : ajout du canal.

## Vérification

1. Connecté à un compte GitHub, ouvrir un projet ayant un `.local.pref` (requêtes / dashboards
   privés, colonnes masquées) : ils restent visibles ; sur disque, `.{login}.pref` les contient
   et `.local.pref` est devenu `.local.migrated.pref`.
2. Scénario L2 de `specs/GH18-tests.md` : requête privée créée via MCP avec `--user <login>` →
   visible en direct dans l'app.
3. Se déconnecter puis rouvrir la vue Suivi : identité `local` (nouveau `.local.pref`).
4. Projet sans remote (démo) : identité = login du compte connecté.

Vérifs automatiques : `tsc --noEmit` (apps/desktop) OK ; fusion testée par script
(valeurs utilisateur prioritaires, union par id, renommage, 2ᵉ appel sans effet). Pas de
suite de tests unitaires dans le repo.
