# GH293 — Mise à jour Windows bloquée par un serveur MCP encore lancé

## Symptôme

Mise à jour 0.2.0 → 0.3.0 depuis l'application : « Échec de désinstallation des anciens fichiers
d'application. Veuillez réessayer d'exécuter l'installeur. : 2 ».

## Root cause

Un client MCP lance le serveur MCP avec l'exécutable installé (`.mcp.json` → `process.execPath`
`resources\mcp-server\index.cjs`, `ELECTRON_RUN_AS_NODE=1`, cf. `host/mcp-launch.ts`). Ce processus
n'est pas un enfant de l'application : il survit à sa fermeture et reste dans le dossier d'installation.

Observé sur le poste au moment de l'échec : deux `Polenta.exe` de ce type, enfants de Claude Desktop,
lancés deux jours plus tôt, encore vivants alors que l'installeur affichait l'erreur.

Le code 2 vient du désinstalleur de l'ancienne version. Il sort avec ce code s'il abandonne, soit après
n'avoir pas pu fermer l'application (`appCannotBeClosed`, réponse par défaut Annuler en silencieux),
soit s'il n'a pas pu déplacer les fichiers (`Can't rename "$INSTDIR"`).

**Non expliqué** : le contrôle d'electron-builder (`_CHECK_APP_RUNNING`) lance `taskkill /f` sur l'image
`Polenta.exe`, et il voit bien ces processus (`tasklist` testé avec les mêmes filtres). Ils auraient donc
dû être tués, or leur date de création prouve qu'ils ne l'ont pas été. Le poste a bien le droit
`PROCESS_TERMINATE` sur eux (`OpenProcess` testé). Le `taskkill` n'a pas pu être rejoué sur ces processus.

## Correctif

`services/mcp-server-processes.ts` détecte, par `Get-CimInstance Win32_Process`, les processus de notre
exécutable dont la ligne de commande contient le chemin complet du bundle MCP de cette installation.
Ce filtre écarte les processus auxiliaires d'Electron et les serveurs d'une autre installation. Windows
uniquement. Une détection impossible n'empêche pas la mise à jour.

`UpdateService` :

- `install()` (bouton de mise à jour) : si des serveurs sont détectés, un dialogue prévient qu'ils seront
  arrêtés et qu'il faudra redémarrer le client MCP. « Annuler » ne change rien et la mise à jour reste
  proposée. Sinon, arrêt puis `quitAndInstall`.
- `will-quit` (`autoInstallOnAppQuit`, l'installeur part sur `quit`) : arrêt sans dialogue, seulement si
  une mise à jour est prête.

L'action de l'utilisateur étant déjà une demande explicite d'installation, le dialogue prévient sans
ajouter de réglage. L'option d'un `installer.nsh` qui tue les processus n'a pas été retenue : elle
reprendrait le mécanisme `taskkill` dont l'échec reste inexpliqué.

## Limites

- **Le correctif s'applique à la version installée au moment de la mise à jour** : il agit à partir de la
  mise à jour suivant la première version qui le contient. Depuis une version antérieure (dont 0.2.0),
  quitter le client MCP avant d'installer.
- `process.kill` passe par `TerminateProcess`, comme `taskkill /f`. Si la cause du refus de `taskkill`
  s'applique aussi à lui, l'arrêt échoue, et l'installeur affiche la même erreur.
- Un client MCP qui relance son serveur entre l'arrêt et le désinstalleur rebloquerait l'installation.

## Vérification

Automatique : `mcp-server-processes.gh293.test.ts` (dont de vrais processus Windows, chemin accentué, voisin
épargné) et `update.service.gh293.test.ts` (dialogue, annulation, ordre arrêt puis installation, fermeture).

À la main, non couvert par les tests (installation packagée, aucune n'a été construite pour ce ticket) :

1. Installer une version contenant ce correctif, publier ou servir une version supérieure.
2. Lancer un client MCP sur un projet dont le `.mcp.json` pointe vers cette installation.
3. Attendre que la mise à jour soit prête, cliquer sur le bouton : le dialogue annonce le serveur MCP.
4. « Annuler » : le serveur tourne toujours, le bouton reste proposé.
5. Recommencer, « Arrêter et installer » : la mise à jour aboutit, sans erreur 2. Redémarrer le client MCP.
6. Même préparation, sans cliquer : fermer l'application, la mise à jour doit aboutir au prochain lancement.
