# GH296 — Panneau Version : faux fichiers modifiés quand `core.autocrlf` est hors de `.git/config`

## Root cause

Le statut de Polenta vient de `git.statusMatrix` (isomorphic-git), qui ne lit que `.git/config`. Or
`core.autocrlf=true` est le plus souvent dans la config système de Git (défaut de Git for Windows).
Après un checkout ou un reset en git natif, un fichier suivi en LF est en CRLF sur le disque.
isomorphic-git le hache tel quel dès que le cache d'index ne s'applique plus, et le voit modifié ;
git natif convertit avant de comparer et le voit inchangé.

Constaté sur un vrai repo (PH2, `handstickProduct`) : `git status` donne 1 fichier, le panneau 171, et
417 sur une copie du repo, où le cache d'index ne sert plus.

Effets au-delà de l'affichage : le statut sert de garde au pull, au merge et à `settleAutoBranch`
(une `dev-auto` ne revient pas sur l'intégration, et l'intégration part à tort sur une `dev-auto`), et
le stage écrivait le contenu CRLF brut dans git, d'où un diff sur le fichier entier.

## Correctif appliqué

`apps/desktop/src/main/services/eol-status.util.ts`, indépendant de la config de git, pour que le
résultat ne dépende ni de la machine ni de l'emplacement du réglage :

- `eolAwareStatusMatrix` : un fichier non stagé qui ne diffère de HEAD que par ses fins de ligne compte
  comme inchangé. Utilisé par `status`, `stageAll`, `discardAll` et `workdirChangesVsHead`. Les binaires
  (NUL dans les 8000 premiers octets, même règle que git) restent comparés à l'octet près.
- `addKeepingEol` : si HEAD est en LF et le disque en CRLF, le fichier repasse en LF avant `git.add`.
  Utilisé par `stage` et `stageAll`. Un fichier déjà en CRLF dans git garde son style.

`stageAll` ne fait plus `git.add('.')`, qui stagerait les faux changements : il parcourt la matrice.

`unstageAll` et `discard` gardent `git.statusMatrix` : ils ne dépendent que des colonnes `stage` et
`head`, que la correction ne change pas.

Non traité :

- Un fichier **nouveau** en CRLF est stagé tel quel : il n'existe pas dans HEAD, et Polenta ne connaît
  pas le réglage de git. Pas de faux changement ensuite, git natif le voit inchangé.
- Le merge et le checkout d'isomorphic-git comparent toujours par hash. Ils n'ont pas été testés avec un
  disque en CRLF **quand l'arbre cible change des fichiers**. Seul le retour d'une `dev-auto` sur le même
  commit est couvert.

Coût : une lecture du fichier et du blob HEAD par fichier concerné, à chaque calcul du statut (toutes les
3 s par repo affiché). Mesuré : environ 0,6 s avec 417 fichiers en CRLF. Rien de plus pour un repo
sans fichier concerné.

## Comment vérifier

Automatique : `apps/desktop/src/main/services/sync.service.gh296.test.ts` (statut, modifications locales,
stage, « Tout stager », « Tout annuler », `settleAutoBranch`). Sans le correctif, 9 des 11 premiers tests
échouaient.

À la main, sous Windows avec `core.autocrlf=true` en config système :

1. Dans un repo du projet : `git checkout <autre-branche>`, puis retour, pour sortir les fichiers en CRLF.
2. Dans le panneau Version, la liste « Modifications » correspond à `git status`.
3. Modifier une exigence depuis Polenta, stager, committer : `git show --stat` n'affiche que les lignes
   réellement changées.

## Repo déjà touché

Rien à faire : les fichiers en CRLF sur le disque ne ressortent plus. Pour les remettre en LF, il suffit
de les stager après une vraie modification, ou de laisser git natif les gérer.
