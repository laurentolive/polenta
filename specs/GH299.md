# GH299 — Richtext : couleur du texte et couleur de surlignage

Issue : #299 — type feature.

## 1. Besoin

Dans un champ `richtext`, l'utilisateur doit pouvoir colorer une portion de texte (**couleur du
texte**) et la surligner (**couleur de fond**), comme dans un traitement de texte, pour faire
ressortir une valeur, un seuil, une remarque de revue.

## 2. Décisions (humain, 2026-11-06)

| # | Question | Décision |
|---|----------|----------|
| D1 | Encodage dans le YAML (le richtext est du Markdown, sans syntaxe couleur) | **Classes nommées** dans du HTML inline restreint : `<span class="pl-c-<nom>">…</span>` (texte) et `<mark class="pl-hl-<nom>">…</mark>` (surlignage). La couleur réelle vient du thème de l'application — pas de code couleur dans le fichier. Hors Polenta (GitHub, éditeur texte) le texte reste lisible, sans couleur |
| D2 | Choix des couleurs | **Palette fixe**, pas de couleur libre |

## 3. Palette

Noms stables (ils sont écrits dans les fichiers, ne jamais les renommer) ; libellés traduits
(fr/en). Chaque couleur a une valeur en thème clair et une en thème sombre, choisies pour rester
lisibles sur le fond de l'application (contraste texte ≥ 4.5:1 visé).

| Couleur du texte (`pl-c-…`) | Surlignage (`pl-hl-…`) |
|---|---|
| `red` — Rouge | `yellow` — Jaune |
| `orange` — Orange | `green` — Vert |
| `green` — Vert | `blue` — Bleu |
| `blue` — Bleu | `pink` — Rose |
| `purple` — Violet | `orange` — Orange |
| `gray` — Gris | |

Le texte surligné garde la couleur d'encre normale du thème (sauf couleur de texte explicite) :
en thème sombre, les fonds de surlignage sont assombris pour que l'encre claire reste lisible.

## 4. Format de stockage

```yaml
statement: |
  WHEN the pack temperature exceeds <span class="pl-c-red">60 °C</span>
  THE BMS SHALL <mark class="pl-hl-yellow">cut the charge within 1 s</mark>
```

- Couleur et surlignage combinés : imbrication `<mark class="pl-hl-yellow"><span class="pl-c-red">…</span></mark>`
  (ordre d'imbrication fixé par la sérialisation, stable d'une sauvegarde à l'autre).
- Les balises encadrent du texte d'une même ligne/paragraphe ; elles peuvent contenir les autres
  marques inline (gras, italique, barré, code, lien, ID d'élément `[[…]]`, paramètre `{…}`) et
  vivre dans une liste, une citation, un titre ou une cellule de tableau.
- **Liste blanche stricte** : seules ces deux formes exactes (balise `span`/`mark`, attribut
  `class` unique, nom de la palette) sont interprétées. Tout autre HTML — autre balise, attribut
  `style`, classe inconnue, balise mal fermée — reste du **texte littéral** affiché tel quel, comme
  aujourd'hui (`html: false` conservé pour le reste ; aucune injection HTML possible).
- Un champ sans couleur est écrit exactement comme aujourd'hui : aucun changement de format pour
  les fichiers existants, aucune réécriture à l'ouverture.

## 5. Comportements attendus

### 5.1 Édition (éditeur TipTap)

- Deux boutons dans la barre d'outils richtext — **barre partagée** (`RichTextToolbar`) et
  **barre inline** de `RichTextField` : « Couleur du texte » (A souligné de la couleur courante)
  et « Surlignage » (marqueur). Chacun ouvre un petit menu : les pastilles de la palette, plus
  « Aucune couleur » / « Aucun surlignage ».
- Appliqué à la sélection ; sans sélection, s'applique au texte saisi ensuite (comme le gras).
- Le bouton reflète l'état de la sélection (couleur active indiquée dans le menu).
- Boutons désactivés en mode Raw et masqués en lecture seule (même règle que les autres boutons).
- Mode **Raw** : les balises apparaissent en clair et sont éditables ; repasser en mode riche
  les réinterprète.
- **Collage** : la couleur d'un texte collé depuis Word / une page web n'est pas reprise (le
  texte arrive sans couleur, comme aujourd'hui). Collage interne Polenta → Polenta : couleurs
  conservées.
- Annuler / rétablir (GH152) couvre l'application et le retrait d'une couleur.

### 5.2 Lecture

Couleurs rendues partout où un richtext est affiché, dans les deux thèmes :
`RichTextViewer`, `StaticRichTextViewer` (Vue Document, cellules Vue Excel, Vue Recherche,
popup d'aperçu d'un lien d'élément, campagnes/exécution, copies `testSnapshot`), desktop et
client web.

- Surbrillance de recherche (`highlightRegex`, T167) et diff de versions (`diffAgainst`, GH178) :
  continuent de fonctionner sur un texte coloré (la correspondance porte sur le texte, pas sur
  les balises). Un changement **de couleur seule** n'est pas signalé comme différence de texte
  dans le diff visuel (le diff YAML/brut, lui, le montre).

### 5.3 Texte « nu » et contrôles

Les balises de couleur sont retirées (le texte encadré est gardé) partout où le richtext est
réduit à du texte :

- validation **EARS** (`isEarsCompliant`) : `<span class="pl-c-red">WHEN</span> … SHALL …` est conforme ;
- filtre global et Vue Recherche : une recherche `span`, `mark` ou `pl-hl` ne trouve pas un objet
  du seul fait de sa couleur ; le texte coloré, lui, est trouvé ;
- `markdownToPlainText` (gabarit `{{champ}}`, export xlsx d'exécution, toute colonne texte).

### 5.4 Exports

- **Word gabarit** (`{{@rich.x}}`, `markdown-to-ooxml`) : couleur de texte → `w:color`,
  surlignage → `w:shd` (fond de run) avec les valeurs du **thème clair**.
- **Export Standard** (docx, xlsx) et impression : ils écrivent aujourd'hui le Markdown brut, sans
  mise en forme (ni gras ni listes) — les balises de couleur y sont **retirées** (texte seul).
  *(Précision du design, 2026-11-06 : la spec citait l'export Standard docx parmi les exports
  colorés.)*
- **xlsx** (Standard, gabarit, exécution) : texte sans couleur.
- Impression / PDF depuis l'app : couleurs du thème clair.

### 5.5 Autres

- **MCP** : un agent peut écrire ces balises dans une valeur richtext ; la description des outils
  d'écriture documente la palette. Aucune validation bloquante d'une classe inconnue (elle reste
  littérale, cf. §4).
- `contentHash` (validations GH204) et `needsRevalidation` : un changement de couleur est un
  changement de contenu, comme un passage en gras aujourd'hui — pas de règle spéciale.
- Historique GH77 : sans objet (un richtext suivi enregistre sa valeur brute).

## 6. Critères d'acceptation

1. Sélectionner un mot, choisir « Rouge » : le mot s'affiche en rouge ; le YAML contient
   `<span class="pl-c-red">mot</span>` ; rechargement → toujours rouge.
2. Idem surlignage « Jaune » → `<mark class="pl-hl-yellow">…</mark>`.
3. Couleur + surlignage sur le même mot : les deux visibles ; sauvegarder deux fois sans
   modification ne change pas le fichier.
4. « Aucune couleur » / « Aucun surlignage » retire la balise ; le fichier redevient identique à
   l'original si c'était la seule couleur.
5. Gras + couleur, couleur dans une puce, un titre, une cellule de tableau, autour d'un `[[ID]]`
   ou d'un `{param}` : rendu correct, aller-retour fichier sans perte.
6. Couleurs visibles et lisibles en thème clair et sombre, dans l'éditeur, la Vue Document, une
   cellule Vue Excel et la Vue Recherche (desktop et web).
7. `<span style="color:red">x</span>`, `<span class="pl-c-fuchsia">x</span>`, `<script>…</script>`
   saisis en Raw : affichés en texte littéral, aucune couleur, aucun HTML interprété.
8. Un `statement` EARS dont le mot-clé est coloré reste conforme EARS.
9. Filtre `pl-hl` sur un projet avec du surlignage : aucun résultat ; filtre sur le mot surligné :
   trouvé et mis en surbrillance.
10. Export Word gabarit : couleur et surlignage présents dans le `.docx` ; export Standard (docx, xlsx) et xlsx : texte sans balise.
11. Projet existant sans couleur ouvert puis enregistré : aucun diff de fichier.
12. Boutons désactivés en Raw, absents en lecture seule.

## 7. Hors scope

- Couleur libre (`#rrggbb`), palette configurable par projet dans `schema.yaml`.
- Reprise des couleurs au collage depuis Word / le web.
- Couleur de fond d'une cellule de tableau, d'un paragraphe entier ; taille / police de caractères.
- Couleurs dans les champs `text` / `textarea`.
- Signalement d'un changement de couleur seule dans le diff visuel.
- Couleurs dans l'export xlsx.
