# GH30 — Un 401/403/404 au clone d'une dépendance s'affiche « Erreur de parsing »

## Symptôme
À l'ouverture du workspace `handstickProduct` (cloné par un collègue), l'application affiche :
`Erreur de parsing dans "hmi-PH2" : HTTP Error: 404 Not Found`.

## Root cause
`WorkspaceTreeService.buildTree` (`apps/desktop/src/main/services/workspace-tree.service.ts`) clone
ou fetch chaque dépendance déclarée dans `polenta-repo.yaml`. Tout échec est renvoyé en
`status: 'parse-error'` avec le message brut de l'exception, que le renderer préfixe de
« Erreur de parsing dans … ». Or GitHub répond **404** (et non 401/403) pour un dépôt privé quand la
requête n'a pas d'identifiants valides ou que le compte n'a pas accès : le problème réel (accès au
dépôt `SEB-lolive/ver-hmi`) est masqué derrière un faux diagnostic de parsing.

## Correctif
- `packages/types` : `WorkspaceOpenResult` `parse-error` gagne `remoteAccess?: boolean` — quand vrai,
  `error` est un message complet destiné à l'utilisateur.
- `workspace-tree.service.ts` : dans le catch du clone/fetch, une `HttpError` isomorphic-git (détection
  sur `code === 'HttpError'`) de statut 401/403/404 produit
  `Dépôt introuvable ou accès refusé pour "<dep>" (<url>, HTTP <code>) : …` avec une consigne qui
  dépend de la présence d'un compte pour l'hôte :
  - compte configuré → vérifier l'accès du compte au dépôt et la portée du token ;
  - aucun compte → ajouter dans Polenta un compte ayant accès au dépôt.
- `sync.service.ts` : `hasHttpsCredentials(url)`.
- Renderer (`useWorkspaceStructure.ts`, 6 sites de `StructureTab.tsx`) : si `remoteAccess`, affiche
  `error` tel quel au lieu du gabarit « Erreur de parsing ».

Les autres erreurs (YAML invalide, réseau, branche introuvable, cycle) sont inchangées.

## Comment vérifier
1. Workspace dont une dépendance pointe vers un dépôt GitHub privé inaccessible au compte actif
   (ou une URL inexistante, ex. `https://github.com/<vous>/n-existe-pas.git`), dossier de la dépendance
   absent.
2. Ouvrir le workspace : le message « Dépôt introuvable ou accès refusé pour "<dep>" (…, HTTP 404) : … »
   s'affiche, sans « Erreur de parsing ».
3. Supprimer le compte GitHub dans Polenta et rouvrir : la consigne indique qu'aucun compte n'est configuré.
4. Rendre un `polenta-repo.yaml` invalide : « Erreur de parsing dans … » s'affiche toujours.

Vérifié : `pnpm typecheck` (apps/desktop) sans erreur. Non reproduit en direct (pas de réseau Node
dans la session de dev).
