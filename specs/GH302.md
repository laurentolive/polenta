# GH302 — Mise à jour de l'application : bouton dès la détection, téléchargement et installation visibles

Issue : #302. Remplace le comportement de GH26 (détection), GH293 (arrêt des serveurs MCP) et la
portée du verrou GH45 (§7) sur la vérification.

## Constat (code au 2026-11-06)

- `UpdateService` (`apps/desktop/src/main/services/update.service.ts`) : **une seule vérification par
  session**, 10 s après le démarrage. Une app restée ouverte plusieurs jours ne voit jamais la nouvelle
  version.
- `UpdateBadge` n'apparaît qu'à l'état `ready` (mise à jour téléchargée). L'état `downloading` existe
  côté main mais n'est pas affiché ; les erreurs sont seulement journalisées.
- `quitAndInstall(true, true)` : installeur NSIS **silencieux**. L'app se ferme, rien ne s'affiche
  pendant l'installation, puis elle se relance.
- La préférence « Mises à jour auto. » (`autoCheckUpdates`) commande la **vérification** elle-même :
  décochée, l'app ne sait pas qu'une version existe.
- Verrou GH45 (`autoUpdate: false` dans la configuration DSI, `updates: managed` dans celle de la
  forge) : aucune requête vers github.com.
- Client web : le pont (`renderer/web/bridge.ts`) répond `{ status: 'idle' }` ; un onglet ouvert ne
  sait jamais que le serveur a été redéployé.

## Décisions de l'humain (2026-11-06)

- D1 — La vérification se fait **toujours** (« pas de raison de ne jamais contacter GitHub »). La
  préférence ne commande plus que le téléchargement.
- D2 — Verrou DSI / forge : la vérification a lieu ; l'utilisateur est **informé** qu'une version
  existe, sans téléchargement ni installation (« mises à jour gérées par votre service
  informatique »). Ce point **modifie GH45 §7** et SPEC-ACCOUNTS-AUTH §6 (« aucune requête vers
  github.com » ne vaut plus).
- D3 — Client web : seul l'**administrateur** peut mettre à jour (c'est le serveur qui change de
  version, pas le navigateur).

## Comportement — desktop

### États du bouton de mise à jour (bas de l'ActivityBar)

| État | Quand | Bouton | Popover |
|------|-------|--------|---------|
| aucun | pas de nouvelle version, vérification en cours ou échouée sans version connue | absent | — |
| **disponible** | nouvelle version détectée, pas (encore) téléchargée | icône de mise à jour + point | « vX disponible », notes de version ; bouton **Télécharger** si téléchargement auto désactivé ; si verrou : « Mises à jour gérées par votre service informatique », sans bouton d'action |
| **téléchargement** | téléchargement en cours | icône animée + pourcentage dans l'infobulle | « Téléchargement de vX… NN % », barre de progression |
| **prête** | téléchargée | icône distincte (couleur d'accent) | comme aujourd'hui : « Redémarrer pour installer », « Plus tard » |
| **erreur** | échec du téléchargement (ou de la vérification alors qu'une version est connue) | icône d'avertissement | message court + **Réessayer** |

- Le bouton apparaît **dès la détection** (événement `update-available`), avant le téléchargement.
- Une vérification qui échoue sans version connue (hors ligne, réseau qui bloque github.com) reste
  silencieuse (journal `[update]`) : pas de bouton d'erreur pour un réseau d'entreprise fermé.

### Vérification

- Au démarrage (après ~10 s) puis **toutes les 4 h** tant que l'app est ouverte, et dans tous les cas
  (préférence et verrou n'empêchent plus la vérification, D1/D2).
- Uniquement en build packagé (inchangé) ; `POLENTA_FORCE_DEV_UPDATE=1` reste le moyen de test en dev.
- Marque sans source de mise à jour (GH49) : aucune vérification, aucun bouton (inchangé).
- Une vérification n'en relance pas une autre pendant un téléchargement ou quand la mise à jour est prête.

### Préférence

- Libellé : **« Téléchargement automatique des nouvelles versions »** (EN : « Download new versions
  automatically »). Infobulle : la vérification a lieu de toute façon ; décochée, le bouton propose
  « Télécharger ».
- Défaut : cochée. Effet **immédiat** (plus « au prochain lancement »).
- La valeur actuelle de `autoCheckUpdates` dans `app-settings.json` est reprise (pas de perte du choix
  existant).
- Verrou DSI / forge : case grisée et décochée, infobulle actuelle (« Mises à jour gérées par votre
  service informatique »).

### Installation

1. « Redémarrer pour installer » ouvre une **confirmation** (fenêtre de l'app, pas boîte native) qui
   annonce tout ce qui va être fermé :
   - les onglets non enregistrés (avertissement actuel, conservé) ;
   - les autres fenêtres de Polenta (nombre) ;
   - les serveurs MCP lancés depuis cette installation (nombre ; Windows) avec la consigne actuelle
     (redémarrer le client MCP ensuite).
   Boutons : « Fermer et installer » / « Annuler ».
2. Après confirmation : un écran « Installation de vX — Polenta va se fermer et redémarrer » s'affiche
   dans toutes les fenêtres, les serveurs MCP sont arrêtés, les fenêtres fermées.
3. L'installeur s'exécute **visiblement** (fenêtre de progression de l'installeur NSIS en un clic,
   sans question posée à l'utilisateur).
4. Polenta est relancé à la fin de l'installation.

- Fermer l'app normalement alors qu'une mise à jour est prête : installation à la fermeture,
  serveurs MCP arrêtés (comportement GH293 inchangé).
- Plusieurs fenêtres : l'état est le même partout ; la confirmation s'affiche dans la fenêtre d'où
  elle est demandée, un second clic ailleurs pendant la confirmation est ignoré.

## Comportement — client web

### W1 — Nouvelle version servie (tous les utilisateurs)

- L'onglet compare périodiquement (toutes les 5 min, et à chaque reconnexion du canal d'événements)
  la version du serveur à celle chargée au démarrage de la page.
- Différente → même bouton, état « nouvelle version » : « Polenta vX est en service — Recharger la
  page », avec l'avertissement des onglets non enregistrés. Pas de rechargement automatique.

### W2 — Nouvelle release disponible (administrateur seulement)

- Le serveur web vérifie la dernière release Polenta (même source et même cadence que le desktop :
  démarrage puis 4 h).
- L'utilisateur **administrateur de l'instance** (celui qui voit l'administration) voit le bouton à
  l'état « disponible » : « Polenta vX disponible (instance en vY) », notes de version, et la marche à
  suivre pour mettre à jour le client web.
- Les autres utilisateurs ne voient rien de W2.

### Hors périmètre de ce ticket (à ouvrir en issue séparée)

- **Mise à jour du client web en un clic depuis l'administration** (job `web.update` du service
  d'administration, `instance web enable --version` du kit) : demande d'abord que la CI publie l'image
  `polenta-web` de chaque release (aujourd'hui `release.yml` ne publie pas d'image ; elle est
  construite sur l'hôte). D3 est respecté par W2 en attendant : l'administrateur est informé, la mise
  à jour reste faite par lui.
- Mises à jour servies par le serveur du client (#52).
- macOS / Linux : comportement d'electron-updater inchangé, non testé ici.

## Critères d'acceptation

- CA1 — Desktop, nouvelle release publiée : le bouton apparaît à l'état « disponible » dès
  `update-available`, avant la fin du téléchargement.
- CA2 — Une app ouverte depuis plus de 4 h détecte une release publiée après son démarrage.
- CA3 — Pendant le téléchargement, le popover affiche le pourcentage, mis à jour au moins à chaque
  événement de progression.
- CA4 — À la fin du téléchargement, l'icône change (état « prête »).
- CA5 — Échec du téléchargement : état « erreur » visible, « Réessayer » relance le téléchargement.
  Échec de la vérification sans version connue : aucun bouton.
- CA6 — Préférence décochée : vérification faite, bouton « disponible » avec « Télécharger » ; aucun
  téléchargement sans clic.
- CA7 — Verrou DSI ou forge : vérification faite, bouton « disponible » informatif, aucun
  téléchargement possible, case de préférence grisée.
- CA8 — « Redémarrer pour installer » : confirmation listant onglets non enregistrés, autres fenêtres
  et serveurs MCP ; « Annuler » ne ferme rien.
- CA9 — Après confirmation : écran d'installation dans toutes les fenêtres, serveurs MCP arrêtés,
  fenêtre de progression de l'installeur visible, Polenta relancé sur la nouvelle version.
- CA10 — Web : après redéploiement du serveur, un onglet ouvert affiche « Recharger » en 5 min au plus,
  ou dès la reconnexion du canal d'événements.
- CA11 — Web : l'administrateur voit la release disponible ; un utilisateur non administrateur ne la
  voit pas.
- CA12 — Marque sans source de mise à jour : aucun bouton, aucune requête (desktop et W2).

## Vérification prévue

- Unitaires : transitions d'état du `UpdateService` (electron-updater simulé : disponible,
  progression, téléchargé, erreur, verrou, préférence, minuterie 4 h) ; rendu du bouton par état ;
  comparaison de version web ; filtrage administrateur de W2.
- e2e web : W1 (version du serveur simulée qui change) et W2 (admin / non-admin).
- Manuel (non automatisable) : CA9 de bout en bout, qui demande deux versions empaquetées publiées
  (installeur visible, relance) ; CA2 en accéléré si possible.
