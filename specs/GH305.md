# GH305 — Administration web : mettre à jour le client web en un clic (image `polenta-web` publiée par la CI)

Issue : #305. Suite de #302 (W2, hors périmètre de `specs/GH302.md`).

## Constat (code au 2026-11-06, `main` 1b190b1)

- **Image** : `release.yml` (tag `vX.Y.Z`, runner Windows) ne publie que l'installeur desktop. L'image
  du client web se construit à la main sur l'hôte (`docker build -f apps/desktop/Dockerfile.web …`,
  RUNBOOK A15). Sur le VPS de test, seule une image locale `polenta-web:gh44-s4` existe.
- **Kit** : `polenta-host instance web enable <nom> --version <v> [--image <i>]` sert déjà à mettre à
  jour (« même commande », RUNBOOK). Il garde domaine et image de l'instance (`instance.env`), fait
  `docker pull` si l'image n'est pas locale, refuse « image introuvable » sans rien modifier, puis
  redémarre le conteneur `polenta-web-<instance>`. L'image de l'instance l'emporte sur l'image par
  défaut de l'hôte (`POLENTA_WEB_IMAGE` de `host.env`).
- **Service d'administration** : le catalogue (`apps/admin-service/src/jobs/registry.ts`) contient
  `web.enable` (paramètres `domain`, `version` facultatifs) et `forge.update` (version obligatoire,
  formulaire « version + Mettre à jour » par ligne dans `InstancesPanel`). Aucune interface n'appelle
  `web.enable`.
- **W2 (#302)** : le serveur web vérifie la dernière release (démarrage puis 4 h). L'administrateur de
  l'instance voit « Polenta vX disponible (instance en vY) », les notes de version et la commande à
  lancer sur l'hôte (`update.popover.releaseAdmin`).

## Description fonctionnelle

### 1. Image publiée par la CI

- À chaque tag `vX.Y.Z` poussé (release publique, marque `polenta`), la CI construit
  `apps/desktop/Dockerfile.web` (`POLENTA_BRAND=polenta`, `POLENTA_VERSION=X.Y.Z`) et publie
  **`ghcr.io/laurentolive/polenta-web:X.Y.Z`**, paquet **public**, plateforme `linux/amd64`.
- Tag de version exact uniquement, **pas de `latest`** (même règle que la forge, GH63 §3.2 : versions
  épinglées).
- Le job d'image s'exécute sur un runner Linux, à côté du job Windows existant. Son échec fait échouer
  le workflow mais ne retire pas la release desktop déjà publiée (jobs indépendants).
- Build d'une marque client (`workflow_dispatch`, GH49) : aucune image publiée (le nom des clients
  n'apparaît pas sur le registre public, même règle que pour l'installeur).
- Image par défaut du kit : `POLENTA_WEB_IMAGE_DEFAULT` vaut `ghcr.io/laurentolive/polenta-web` quand
  `host.env` ne fixe rien (aujourd'hui : `polenta-web`, image locale).

### 2. Opération `web.update` du service d'administration

| Propriété | Valeur |
|-----------|--------|
| Niveau | instance (la sienne) ou hôte (toute instance) — comme `forge.update` |
| Paramètre | `version` obligatoire (`v.version`) |
| Commande | `instance web enable <instance> --version <v>` : domaine et image de l'instance conservés |
| Verrou | mutante (verrou de l'hôte, refus 409 si un travail est en cours) |
| Confirmation | simple ; non annulable |
| Audit | `version` |
| Étapes affichées | image, redémarrage, contrôle |
| Instance sans client web | refus explicite (« client web non activé sur cette instance ») |

- **Mise à jour de sa propre instance autorisée** : c'est le cas nominal (pas de `selfGuard`, à la
  différence de `web.disable`). Le travail s'exécute dans `polenta-admin`, indépendant du conteneur
  redémarré.
- Pas de sauvegarde préalable : `web-data` (sessions, clones de travail) n'est pas modifié par un
  changement d'image ; il reste couvert par les sauvegardes de l'instance.
- Échec (`image introuvable`, santé) : travail `failed`, message du kit affiché. Retour arrière
  automatique vers l'image précédente : **hors périmètre** (voir Hors scope).

### 3. Interface

**a) Popover de mise à jour (W2), administrateur de l'instance, client web.**
Le texte « Pour mettre à jour le client web de cette instance, sur l'hôte : <commande> » est remplacé
par un bouton **« Mettre à jour vers vX »** (vX = release détectée par W2).

1. Clic → confirmation dans l'app : « Le client web de <instance> passe de vY à vX. Polenta sera
   indisponible quelques secondes pour tous les utilisateurs de l'instance ; les onglets non
   enregistrés de chacun risquent d'être perdus. » + avertissement des onglets non enregistrés de
   l'utilisateur courant. Boutons « Mettre à jour » / « Annuler ».
2. Confirmation → travail `web.update` lancé ; le popover affiche « Mise à jour en cours… » et la
   progression du travail (étapes), comme le suivi des travaux de l'administration.
3. Le serveur redémarre : coupure du canal d'événements, puis reconnexion. À la reconnexion, W1
   (#302) détecte la nouvelle version et propose « Recharger la page ». Le suivi du travail reprend
   après rechargement (bandeau « opération en cours » / journal des travaux).
4. Échec : message du travail dans le popover + lien vers le journal des travaux ; l'instance reste
   sur vY.

Visible seulement si l'administration est disponible pour l'utilisateur (même condition que W2) et si
la marque a une source de release (CA12 de #302). Autres utilisateurs : rien (inchangé).

**b) Administration › Instances.** Pour chaque instance qui a un client web, en dessous du formulaire
de la forge : formulaire **« Client web : version + Mettre à jour »**, sur le modèle de
`forge.update`. Champ prérempli avec la dernière release connue du serveur (W2) quand elle est plus
récente ; saisie libre (autre version, retour à une version antérieure). Colonne Version : la version
du client web est affichée sous celle de la forge.
Cas de sa propre instance : même avertissement de coupure qu'au a).

### 4. Migration des instances existantes

Une instance activée avant ce ticket garde l'image inscrite dans son `instance.env` (ex. image locale
`polenta-web`) : `web.update` vers `0.4.0` échouerait (« image introuvable »). Le RUNBOOK (A15)
documente le passage unique à l'image publiée :
`polenta-host instance web enable <nom> --image ghcr.io/laurentolive/polenta-web --version X.Y.Z`.
**À trancher (Q1)** : migration documentée seulement, ou bascule automatique par `web.update`.

## Cas d'usage

- U1 — Release v0.4.0 publiée : l'image `ghcr.io/laurentolive/polenta-web:0.4.0` est disponible
  (`docker pull` sans authentification) quelques minutes après le tag.
- U2 — L'administrateur d'`acme` (instance en 0.3.2) ouvre le client web : bouton de mise à jour
  « disponible » → « Mettre à jour vers v0.4.0 » → confirmation → coupure courte → « Recharger » →
  page en 0.4.0.
- U3 — L'exploitant (niveau hôte) met à jour le client web de `gitea-test` depuis Administration ›
  Instances, sans toucher à son instance d'exploitation.
- U4 — Version saisie inexistante : travail `failed`, « image introuvable », instance inchangée.
- U5 — Une sauvegarde est en cours sur l'hôte : refus 409 « opération en cours », rien n'est lancé.
- U6 — Utilisateur non administrateur : aucun bouton, aucune route accessible (refus du service).

## Critères d'acceptation

- CA1 — Un tag `vX.Y.Z` publie `ghcr.io/laurentolive/polenta-web:X.Y.Z` (public, `linux/amd64`) ;
  l'image démarrée répond `/healthz` avec la version `X.Y.Z`.
- CA2 — Un build `workflow_dispatch` de marque ne publie aucune image.
- CA3 — `web.update` : version obligatoire et validée ; commande exacte
  `instance web enable <instance> --version <v>` ; mutante ; audit `version` ; refus si l'instance
  n'a pas de client web.
- CA4 — Niveau instance : mise à jour de sa propre instance acceptée ; d'une autre instance refusée.
  Niveau hôte : toute instance.
- CA5 — Popover W2 de l'administrateur : bouton « Mettre à jour vers vX », confirmation qui annonce la
  coupure pour tous les utilisateurs ; « Annuler » ne lance rien.
- CA6 — Après confirmation : travail lancé et suivi ; après redémarrage du serveur, « Recharger la
  page » apparaît (W1) sans action de l'administrateur autre que le clic.
- CA7 — Échec du travail : message visible dans le popover et dans le journal ; version inchangée.
- CA8 — Administration › Instances : formulaire « Client web » pour les instances avec client web
  uniquement, prérempli avec la release W2 plus récente, saisie libre acceptée.
- CA9 — Non-administrateur : aucun élément de W2 ni du formulaire ; appel direct de `web.update`
  refusé par le service.
- CA10 — `POLENTA_WEB_IMAGE_DEFAULT` du kit : `ghcr.io/laurentolive/polenta-web` sans valeur dans
  `host.env` ; RUNBOOK A15 à jour (image publiée, migration, mise à jour depuis l'interface).

## Hors scope

- Retour arrière automatique de l'image en cas d'échec de santé (le kit ne le fait pas pour le client
  web ; à ouvrir en issue si voulu).
- Mise à jour de toutes les instances en une fois.
- Images de marques client (registre privé du client, #52).
- Plateformes autres que `linux/amd64` (arm64).
- Mise à jour du desktop (#302) et de la forge (`forge.update`, inchangée).
