# GH308 — admin-service : tests unitaires en échec sous Windows (chemin du kit passé à bash)

## Root cause

`JobRunner` lançait les scripts du kit avec `spawn('bash', …)` : sous Windows, lancé depuis
PowerShell ou cmd, `bash` nu se résout en premier sur le lanceur WSL
(`%LOCALAPPDATA%\Microsoft\WindowsApps\bash.exe`), qui exécute `/bin/bash` de la distribution
Linux : le chemin Windows du kit (`C:\Users\…\kit\polenta-admin.sh`) y perd ses `\` et n'existe
pas, d'où `kit-error`, des 502 et des travaux `interrupted`. Depuis Git Bash, le PATH place le bash
MSYS en tête et la suite passe — c'est pourquoi le défaut dépend du terminal.

Bug de code (résolution de l'interpréteur), pas de test : la production (Linux) n'était pas touchée.

## Correctif appliqué

`apps/admin-service/src/jobs/runner.ts` : nouvelle fonction `resolveBash()` (résultat mémorisé),
utilisée par les deux `spawn` (travail détaché et lecture en direct) :

- `POLENTA_BASH` défini → cet interpréteur ;
- Linux / macOS → `bash` (comportement inchangé en production) ;
- Windows → premier `bash.exe` du PATH hors lanceurs WSL (`WindowsApps`, `System32`), sinon
  `<Git>\bin\bash.exe` déduit de `git.exe` au PATH, sinon `bash`.

Test : `apps/admin-service/test/runner-bash.test.ts` (Linux inchangé, `POLENTA_BASH`, lanceur WSL
écarté, repli via `git.exe`, repli final).

## Comment vérifier

Depuis **PowerShell** (pas Git Bash), dans le worktree :

```
pnpm --filter @polenta/admin-service test
```

→ 9 fichiers, 124 tests passés, 3 ignorés sous Windows (annulation SIGTERM et descripteur 4,
vérifiés sous Linux seulement). Avant le correctif : 13 tests en échec dans `app.test.ts` et
`sensitive.test.ts`.
