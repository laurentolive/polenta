# GH31 — tree.cache.yaml : chemins absolus, workspace copié/déplacé pointant vers les dépôts d'origine

Type : bug — issue #31

## Root cause

`WorkspaceTreeService.writeCache` (et le repli `WorkspaceService.writeCacheTree`) sérialisaient
l'arbre tel quel (`yaml.dump(tree)`), donc avec les `repoPath` **absolus** de la machine et de
l'emplacement d'origine. `readCache` / `readCacheTree` les relisaient sans aucun contrôle. Après une
copie ou un déplacement du dossier workspace, le cache restait valide côté app (même HEAD du repo
racine → `isCacheValid` vrai) et tous les consommateurs (`RepoWatcherService`,
`resolveWorkspaceRepoPaths`, traçabilité, revalidation, moteur de requête, `SchemaService`,
`InterfaceComplianceService`, `ParametersService`, IPC, et surtout le serveur MCP qui ne reconstruit
jamais le cache) visaient les dépôts d'origine — en lecture comme en écriture.

## Correctif

Nouveau module `apps/desktop/src/main/services/tree-cache.util.ts` :

- `serializeTreeCache(workspaceDir, tree)` : écrit chaque `repoPath` **relatif à `workspaceDir`**
  (`.` pour le workspace lui-même, séparateur `/`). Travaille sur un `structuredClone` : l'arbre en
  mémoire reste en chemins absolus (contrat de `WorkspaceTreeNode.repoPath` inchangé) et les
  références partagées `nodes` / `logicalTree` (ancres YAML) sont conservées.
- `parseTreeCache(workspaceDir, raw)` : résout les chemins relatifs contre le `workspaceDir`
  courant. Retourne `null` (cache invalide) si un chemin résolu sort de `workspaceDir`.
- Compatibilité caches existants (absolus) : acceptés s'ils sont sous `workspaceDir` (workspace non
  déplacé → comportement inchangé, réécrits en relatif à la prochaine reconstruction), rejetés
  sinon.

Branchement : `WorkspaceTreeService.readCache/writeCache` et `WorkspaceService.readCacheTree/
writeCacheTree` utilisent ces deux fonctions. Aucun consommateur modifié : un `null` déclenche
déjà la reconstruction dans `openWorkspace` (`isCacheValid` faux) et le repli mono-repo partout
ailleurs (`resolveWorkspaceRepoPaths`, serveur MCP, etc.).

Commentaire de `WorkspaceTreeNode.repoPath` (`packages/types`) précisé (stockage relatif).

## Comment vérifier

Vérifié par script (helper isolé) : aller-retour même workspace ; cache relatif relu depuis une
copie → chemins de la copie ; cache absolu legacy dans le même workspace → accepté ; cache absolu
legacy relu depuis une copie → `null` ; chemin relatif `../…` → `null` ; workspace self-contained
→ `repoPath: .`. `npm run typecheck` (apps/desktop) : 0 erreur.

Manuel :
1. Ouvrir un workspace multi-repo dans l'app (le cache est réécrit) ; `.polenta/tree.cache.yaml`
   contient des `repoPath` relatifs (`prod`, `bms`…).
2. Copier le dossier workspace ailleurs, ouvrir la copie : les dépôts affichés/surveillés sont ceux
   de la copie (modifier un objet dans la copie ne touche pas l'original).
3. Avec un ancien cache absolu (ou copie faite avant le correctif) : l'ouverture de la copie
   reconstruit l'arbre ; serveur MCP `--workspace <copie>` → repli mono-repo, aucune lecture /
   écriture dans les dépôts d'origine.
4. Workspace non déplacé : ouverture identique à avant.
