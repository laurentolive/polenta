# GH314 — Suite e2e web : 5 scénarios en échec sur main (gh105, gh106, gh126, gh222, gh70)

Origine commune des échecs côté test : la démo `demo-ll800-produit` refaite par GH278 et republiée
le 2026-11-05 (la suite la clone depuis GitHub à chaque exécution). Deux échecs révèlent des bugs de
l'app : gh106 (corrigé ici) et gh222 (#326, contourné dans le test).

## gh106 S2-5 / S2-6 — composant épinglé sur un tag annoté (bug de l'app, corrigé)

### Root cause

isomorphic-git `checkout({ ref: <tag annoté> })` écrit dans HEAD l'id de l'**objet tag**, pas celui
du commit (`resolveRef` s'arrête à l'objet tag). Le composant `comp-pompe-vidange`, épinglé sur
`v2.0` (tag annoté), était donc positionné sur 8721ac3 (objet tag) : `RepoBranchSelector` cherche
`integration.state().headOid` parmi les tags résolus **en commit** (`sync:resolve-refs`), ne le trouve
pas et affiche le sha abrégé au lieu de `v2.0` (S2-5). Une branche créée depuis ce HEAD (désignation,
S2-6) pointait elle aussi sur l'objet tag.

Même défaut dans `SyncService.checkoutBranch`, appelé quand l'utilisateur choisit un **tag** dans le
sélecteur de branche (`BranchCombobox` → `onCheckout`).

### Correctif

- `workspace-tree.service.ts` : `pinCheckoutRef` — un pin qui n'est pas une branche locale et qui est
  un tag est checkouté par son commit (`peelToCommit`), HEAD détaché sur le commit. Branche, SHA et
  branche distante : inchangés.
- `sync.service.ts` : `checkoutBranch` fait de même pour un tag (via `resolveTag`) ; `createBranch`
  part du commit de HEAD (un dossier positionné sur un objet tag avant le correctif ne crée plus de
  branche pointant sur cet objet).
- `integration-branch.service.ts` : `state().headOid` est ramené au commit, pour qu'un dossier déjà
  positionné sur l'objet tag avant le correctif affiche son tag (le pin y est jugé satisfait —
  `repoExistsAtPin` compare des commits depuis GH21 — donc il n'est pas re-checkouté).

Les autres `git.checkout` de l'app portent sur des branches ou des SHA de commit (`sync:checkout-commit`).

### Test

`apps/desktop/src/main/services/workspace-tree.annotated-tag.gh314.test.ts` : checkout du pin
annoté par `buildTree` (HEAD = commit, contenu du tag), pin de branche (HEAD attaché),
`checkoutBranch` d'un tag annoté et d'une branche, `createBranch` et `state().headOid` sur un HEAD
laissé sur l'objet tag. Les 4 cas de bug échouaient avant le correctif.

## gh105 GH105-1 — type de lien masqué par défaut (test)

La démo déclare `defaultVisible` sur ses types de lien (GH139) : la vue document n'affiche par défaut
que ceux-là, donc pas `gh105-implements` créé par le test. Le type du test est créé avec
`defaultVisible: true`.

## gh126 T21 — deux colonnes éclatées dans le ⚙️ (test)

La démo a sa propre colonne éclatée (QUERY-0011 « Résultat par campagne »). Le groupe est ciblé par
`[data-testid="field-config-computed-group"][data-query-id="${queryId}"]`.

## gh70 N4–N7 — deux colonnes « Dernier résultat » (test)

QUERY-0010 de la démo porte le même libellé que la requête du test. Les cases du ⚙️ sont ciblées par
leur requête (`label[title^="<id requête> — "]`, en plus du libellé), dans N4 et dans
`toggleColumn` ; la cellule calculée par `data-computed-cell="query::<id requête>"`.

## gh222 R1/R4 — modification non commitée (bug de l'app, #326, contourné dans le test)

### Root cause (confirmée)

isomorphic-git (`compareStats`) compare les dates de l'index **à la seconde** et ne traite pas le
cas « racy git » : la modification gauche de `gh222m/links/links.yaml` (`SYS-0002` → `SYS-0008`,
même taille), écrite dans la seconde du commit de base, est vue `[1,1,1]` par `statusMatrix` ;
`stageAll` ne la stage pas, le commit « GH222 merge gauche » part sans elle, et le fichier n'est pas
en conflit. Reproduit en test unitaire (écriture au début d'une seconde, commit, réécriture à taille
égale 66 ms plus tard → `[["links.yaml",1,1,1]]`, `stageAll` sans effet).

Bug de l'app : une modification peut ne pas être publiée. Correctif non trivial (chemin de tous les
statuts, à mesurer) : issue #326 avec les pistes.

### Contournement

`gh222-tree-merge.spec.ts` : chaque écriture de la fixture reçoit une date de modification
distincte (`utimes`), ce qui ne change rien à ce que vérifient R1–R8.
