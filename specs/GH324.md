# GH324 — Workspace : la résolution d'un conflit en diamant (mountAs) ne peut jamais aboutir

Issue : #324 (type:bug). Constat issu de la spec abandonnée de #17 (branche `GH17`,
`specs/GH17.md` §2, points 1a–1d). #17 (support complet de deux copies d'un même repo) reste hors
scope.

## Root cause

`WorkspaceTreeService.detectDiamondConflicts` regroupait les nœuds du graphe **par URL** et levait
un conflit dès que deux nœuds de même URL avaient des pins différents, alors que le graphe est indexé
par **nom de montage** :

- après « Appliquer et relancer » dans `DiamondConflictModal`, `dfsCollect` monte bien chaque
  version sous le nom choisi (`mountOverrides`), mais les deux nœuds gardent la même URL et des pins
  différents ⇒ même conflit, la modale revient à chaque ouverture ;
- deux déclarations du **même** nom avec un pin (ou une URL) différent aboutissaient à un seul
  nœud (`if (!graph.has(mountName))`, la 2ᵉ déclaration n'était pas retenue) ⇒ une seule version
  montée, sans conflit ni message ;
- par le même regroupement, une déclaration directe (même URL sous deux noms dans un même
  `polenta-repo.yaml`) était bloquée.

## Correctif

- `GraphNode.declarations` : chaque déclaration qui aboutit à un nom de montage est retenue
  (`url`, `pin`, repo déclarant), y compris quand le nom existe déjà dans le graphe.
- `detectDiamondConflicts` : conflit = plusieurs couples `(url, pin)` distincts pour un **même nom
  de montage**. Deux montages de même URL sous des noms distincts ne sont plus un conflit ; le
  diamant partagé (même nom, même url, même pin) reste un seul montage.
- `DiamondConflict` (types) : `mountName?` et `pins[].url?` (une variante peut avoir sa propre URL
  quand le même nom est déclaré pour deux repos différents). Champs optionnels, forme existante
  conservée.
- `DiamondConflictModal` : brouillons dédupliqués par `(url, pin)`, URL propre à chaque variante
  utilisée pour l'override, nom de montage affiché en tête du conflit.
- Inchangés : détection de cycle (par URL sur la chaîne d'ancêtres), clé `(url, pin)` des
  `MountOverride`, stockage dans `.polenta/workspace.yaml`.

Un nom choisi dans la modale qui est déjà celui d'un autre montage donne un nouveau conflit sur ce
nom (signalé, plus d'écrasement).

## Hors scope — objets de même ID dans les deux montages

Une fois le workspace ouvert avec deux versions d'un même repo, les IDs se recouvrent. Constat
(lecture du code, non modifié) : l'agrégation multi-repo garde le premier repo rencontré —
`workspace-links.service.ts` `collectObjects` (avertissement console seulement), `revalidation.service.ts`
(`byId`), `Map` par ID dans `traceability.service.ts` et `graph.service.ts`. Chaque repo reste listé
et éditable séparément. Le traitement (signalement, résolution des liens) relève de #17.

## Tests

`apps/desktop/src/main/services/workspace-tree.diamond.gh324.test.ts` (repos git réels sur disque,
aucun accès réseau) : diamant partagé, même nom + pins différents, même nom + URL différentes,
résolution complète puis partielle par override, nom choisi déjà pris, déclaration directe.

## Comment vérifier

1. Workspace plat avec un repo racine `root` déclarant deux composants `A` et `B`
   (`polenta-repo.yaml`) ; `A` et `B` déclarent chacun `comp` (même `url`), avec `pin: int-A`
   pour `A` et `pin: int-B` pour `B` (deux branches du repo `comp`).
2. Ouvrir le workspace, onglet Structure : la modale « Conflit de dépendances » liste `comp` avec
   les deux pins (requis par A / requis par B).
3. Saisir `comp-a` et `comp-b`, « Appliquer et relancer » : le workspace s'ouvre, l'arbre montre
   `comp-a` sous A et `comp-b` sous B ; rouvrir le workspace ne réaffiche pas la modale.
4. Non-régression : remettre le même pin dans A et B (supprimer les `mountOverrides` de
   `.polenta/workspace.yaml`) : un seul `comp`, pas de modale.
