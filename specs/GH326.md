# GH326 — Modification non vue : fichier réécrit à taille égale dans la seconde de son indexation

## Symptôme

Un fichier suivi, réécrit **à taille égale** dans **la même seconde** que son dernier ajout à l'index
(commit, `stage`, checkout), passe pour inchangé : `SyncService.stageAll` ne le stage pas, le commit /
la publication part sans cette modification, sans erreur. Découvert par #314 (e2e `gh222-tree-merge`).

## Root cause

`git.statusMatrix` d'isomorphic-git (1.38.4) passe par le walker `WORKDIR`, qui reprend l'oid de
l'entrée d'index sans relire le fichier si `compareStats` ne voit pas de différence. Or `compareStats`
compare `mtimeSeconds`, `ctimeSeconds`, `size`, `mode` (et `ino` hors Windows)… **à la seconde**. Git
natif traite ce cas (« racy git », `Documentation/technical/racy-git.txt`) en comparant les fractions
de seconde et en relisant les entrées « racy » (datées au même instant ou après l'écriture de
l'index) ; isomorphic-git ne le fait pas. `git.status` (fichier seul) a le même défaut.

## Inventaire des décisions « fichier modifié ? »

| Appelant | Passait par | Dépend de la colonne workdir ? |
|---|---|---|
| `SyncService.status` (panneau Version, publication, `sync:status`, serveur web) | `eolAwareStatusMatrix` | oui |
| `SyncService.stageAll` (publication, commit) | `eolAwareStatusMatrix` | oui |
| `SyncService.discardAll` | `eolAwareStatusMatrix` | oui |
| `SyncService.workdirChangesVsHead` (T175, analyse des changements) | `eolAwareStatusMatrix` | oui |
| `RepoSettingsService.syncReadme` (GH108 : README en attente ?) | `git.status` | oui — risque d'écraser une modification du README |
| `SyncService.unstageAll` | `git.statusMatrix` | non (colonne stage ≠ 1 : comparaison index / HEAD seulement) |
| `SyncService.discard` | `git.statusMatrix` | non (colonne head seulement) |

## Correctif

Point central : **`racySafeStatusMatrix`** (`apps/desktop/src/main/services/racy-status.util.ts`), qui
rejoue le walk de `statusMatrix` (`TREE(HEAD)`, `WORKDIR`, `STAGE`, mêmes règles d'ignorés, de filtre
et de calcul des colonnes) et, pour un fichier qu'isomorphic-git croirait inchangé, **hache son
contenu** quand `needsContentCheck` le demande :

1. la taille et les secondes concordent (sinon isomorphic-git relit déjà le fichier et rafraîchit
   l'index — on le laisse faire) ;
2. et **soit** la fraction de seconde du mtime diffère de celle de l'entrée (tolérance 1 µs : `mtimeMs`
   est un double précis à ~250 ns) — entrée sans nanosecondes (`ns = 0`, index écrit par un git sans
   `USE_NSEC`) : pas de comparaison sous la seconde ;
3. **soit** l'entrée est « racy » au sens de git : son mtime est ≥ la date d'écriture de `.git/index`
   (à la seconde si l'entrée n'a pas de nanosecondes ; index illisible → suspecte).

Le ctime n'est comparé qu'à la seconde (comme avant) : sous Windows, git natif indexe en ctime la date
de **création**, Node la date de **changement** ; comparer leurs fractions aurait fait relire tout fichier
indexé par git (mesuré : 924 fichiers sur 3 000 après un clone natif).

`eolAwareStatusMatrix` (déjà le passage obligé des décisions, GH296) s'appuie dessus ; `syncReadme`
aussi (à la place de `git.status`). L'index n'est jamais modifié par ce contrôle.

### Alternatives écartées

- **Post-traiter le résultat de `git.statusMatrix`** (lire l'index et `stat` chaque fichier une seconde
  fois) : double `lstat` de tout le repo à chaque statut, sans gain de sûreté.
- **« Salir » les entrées racy à chaque écriture d'index** (comme git) : les points d'écriture sont
  nombreux (add, remove, commit, checkout, merge, resetIndex…) et internes à isomorphic-git.
- **Patcher isomorphic-git** (`compareStats`) : dépendance patchée à maintenir ; le walk rejoué tient
  en une quarantaine de lignes et un test vérifie qu'il rend la même matrice que `git.statusMatrix` hors cas racy.
- **Déléguer à git natif** : dépendance à un binaire absent du serveur web et du poste client.

### Risque résiduel

isomorphic-git ne « salit » pas les entrées racy quand il réécrit l'index : un fichier réécrit dans le
**même tic d'horloge** (≈ 1 ms sous NTFS) que son indexation, puis l'index réécrit par une autre
opération avant tout statut, redevient invisible. La fenêtre est de l'ordre de la milliseconde (contre
une seconde avant le correctif).

## Coût mesuré

Moyenne de 10 statuts complets, repo chaud, Windows 11 / NTFS (bruit de mesure ≈ ±10 %) :

| Repo | Fichiers | `git.statusMatrix` | `racySafeStatusMatrix` | Fichiers relus en plus |
|---|---|---|---|---|
| Démo LL800 (`demo-ll800-produit`) | 185 | 28,4 ms | 30,3 ms | 0 |
| LL800 cloné par git natif | 176 | 38,0 ms | 45,1 ms | 0 |
| Synthétique cloné par git natif | 3 000 | 838 ms | 834 ms | 0 |
| Synthétique indexé par git natif | 3 000 | 672 ms | 736 ms | 0 |
| Synthétique, checkout isomorphic-git | 3 000 | 866 ms | 899 ms | 0 |

Surcoût fixe : un `stat` de `.git/index` par statut ; seuls les fichiers suspects sont relus.

## Comment vérifier

- `npx vitest run src/main/services/racy-status.gh326.test.ts` (dans `apps/desktop`) : réécriture à taille
  égale dans la seconde du commit → affichée, stagée, commitée ; fichier stagé puis réécrit → `[1,2,3]` ;
  réécriture à l'identique → inchangé ; même matrice que `git.statusMatrix` hors cas racy ;
  `needsContentCheck` (fraction de seconde, arrondi, ctime de git natif, entrée racy, index sans
  nanosecondes, index illisible). Les deux premiers échouent sans le correctif.
- e2e : `gh222-tree-merge` (n'a plus besoin des dates distinctes posées par #314, gardées), `gh108-repo-settings`,
  `s2-core`, `gh276-integration-gaps`, `gh252-versions`.
