# GH332 — MergeNotSupportedError sur une histoire croisée (Rafraîchir / Fusionner / Publier)

## Symptôme

Deux clients bloqués : « Rafraîchir » sur une branche (`int-PH2`) divergée de son origin affiche
`Error invoking remote method 'sync:pull': MergeNotSupportedError: Merges with conflicts are not
supported yet.` Même blocage pour un autre client, sur une autre branche divergée.

## Root cause

Toutes les fusions de Polenta passent par `git.merge` d'isomorphic-git (1.38.4). Quand les deux
commits ont **plusieurs ancêtres communs** (fusion croisée : les branches se sont fusionnées
mutuellement depuis leur dernier point commun — ex. `Merge branch 'dev-auto' into int-PH2` alors
que `dev-auto` contenait déjà de l'`int-PH2`), isomorphic-git n'a pas de stratégie récursive et lève
`MergeNotSupportedError` avant toute fusion (`TODO: Recursive Merge strategy` dans `_merge`).
L'erreur n'est ni un `MergeConflictError` ni traitée : elle remonte brute à l'écran.
L'éditeur de fusion (GH37) refusait lui aussi ce cas (`Cannot resolve this merge: 2 merge bases`).

Pas de git CLI sur les postes clients : le correctif reste dans isomorphic-git.

## Correctif

`apps/desktop/src/main/services/recursive-merge.util.ts` — stratégie récursive au-dessus
d'isomorphic-git :

- **`mergeRecursive`** remplace `git.merge` dans `SyncService` (`pull`, `mergeBranch` — Fusionner /
  Publier —, `canMergeRemoteIntoIntegration`, `resyncIntegration`). Un seul ancêtre commun →
  `git.merge` inchangé. Plusieurs → base virtuelle, fusion sur cette base, commit à deux parents
  (vrais parents), référence avancée ; un conflit lève le `MergeConflictError` habituel, donc le
  flux de conflit existant (éditeur de fusion, mise de côté GH39) s'applique sans changement.
- **Base virtuelle** (`singleMergeBase`) : les ancêtres communs sont fusionnés deux à deux
  (récursivement) en un commit non référencé. Un fichier en conflit *entre ancêtres* y garde la
  version de leur propre ancêtre commun : la fusion finale voit alors les deux côtés modifiés et
  présente le conflit à l'utilisateur au lieu de trancher. Conflit non exprimable (suppression /
  modification) → retombe sur cet ancêtre plus ancien (toujours un ancêtre commun valide).
- **Fusion sur une base choisie** : `git.merge` ne prend pas de base ; on lui passe deux commits
  temporaires (arbre de chaque côté, seul parent : la base voulue). Objets non référencés, sans effet
  sur les branches, l'index ou le working directory.
- **Éditeur de fusion** : `MergeResolutionService.open` prend la base via `singleMergeBase`.

## Comment vérifier

- Tests : `apps/desktop/src/main/services/recursive-merge.gh332.test.ts` (histoire croisée réelle :
  blocage reproduit avec isomorphic-git seul ; Fusionner, Rafraîchir, fusion dans une branche non
  checkoutée, simulation ; vrai conflit → conflit ordinaire ; ancêtres en conflit entre eux ;
  éditeur de fusion ouvert puis finalisé).
- Manuel : dans un repo, créer `dev` depuis `main`, un commit de chaque côté ; fusionner `dev` dans
  `main` puis le premier commit de `main` dans `dev` (vue graphe) ; un nouveau commit de chaque côté ;
  « Fusionner » `dev` dans `main` → aboutit (avant : MergeNotSupportedError). Pour Rafraîchir : même
  histoire entre la branche locale et son origin.
- Chez les clients : « Rafraîchir » sur `int-PH2` doit aboutir, ou ouvrir l'éditeur de fusion s'il y
  a de vrais conflits.
