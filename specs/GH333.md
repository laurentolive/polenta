# GH333 — Doc : les sous-repos ne sont pas des submodules git

## Constat

`CLAUDE.md` et plusieurs specs vivantes décrivaient les composants comme des **submodules git** :
`.gitmodules` « généré par Polenta depuis `schema.nodes` (nœuds avec `url`) », dossier `components/`,
nœud de schéma avec `url` / `branch`, règles « Ne pas éditer `.gitmodules` » et « pas de `url` dans un
repo composant ». Ce modèle a été abandonné en T69 ; un agent qui s'y fiait bâtissait des diagnostics
faux (leçon du 2026-11-09, GH332).

## Architecture réelle (vérifiée dans le code et sur le projet de démo)

- **Workspace plat** : un dossier (marqueur `.polenta/workspace.yaml` : `rootRepo`, noms de montage ;
  `.polenta/tree.cache.yaml`) où Polenta clone lui-même chaque repo côte à côte
  (`WorkspaceService`, `WorkspaceTreeService`). Pas de `.gitmodules`, pas de `git submodule`, pas de git
  CLI requis chez le client.
- **Dépendances** : `polenta-repo.yaml` à la racine de chaque repo qui en a — `name`, `url`, `pin`
  (branche, tag ou commit), `localParent` facultatif (`PolentaRepoManifest`). Un repo ne connaît que ses
  dépendances directes.
- **Schéma** : `SystemNode` n'a ni `url` ni `branch`. Un nœud peut porter le **nom de montage** d'une
  dépendance : `readonly: true` rend ce composant en lecture seule depuis le repo ouvert
  (`RevalidationService.readonlyRepoPathsFor`), et `<nom de montage>::<type>` route un objet vers le repo
  du composant (`SchemaService.resolveComponentRepoPath`). Les composants locaux (T123) vivent dans
  `children[]`.
- Un repo adopté sur place (ouvert directement) garde son `workspace.yaml` dans son propre `.polenta/`.
