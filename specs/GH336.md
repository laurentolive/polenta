# GH336 — Cohérence working directory / git

## 1. Contexte

Constaté chez des clients et reproduit sur `PH2/handstickProduct` (GH332, GH335) :

- Polenta affiche « Rien à committer », puis un changement de branche est refusé (« Your local
  changes … would be overwritten by checkout »). En cause, des fichiers que Polenta ne montre pas :
  - `.local.migrated.pref` est ignoré (`*.pref`) sur une branche mais commité sur une autre ;
  - des fichiers sont en CRLF sur le disque (`core.autocrlf=true` dans la config système de Git for
    Windows) alors qu'ils sont en LF dans git.
- L'application écrit d'elle-même des fichiers versionnés (liste au §6). Ils restent en
  modifications locales, ou divergent d'une branche à l'autre.

Cause de fond : le working directory sert à la fois aux données versionnées et à de l'état local.
Polenta le manipule avec isomorphic-git, qui ne se comporte pas comme le git CLI utilisé sur les
mêmes repos : il ignore `core.autocrlf` et `.gitattributes`, et refuse d'écraser un fichier
ignoré. Chaque écran et chaque opération décidait en outre seul de ce qui est « modifié ».

## 2. Décisions de l'humain (2026-11-09)

| | Décision |
|---|---|
| A | `.gitignore` reste le mécanisme qui protège les prefs. Il doit exister **dès la création** du repo. En cas de blocage, l'utilisateur **voit** le fichier en cause. |
| B | `.gitattributes` **propre à chaque repo Polenta**. Rien n'est écrit dans la config git globale ou système : d'autres projets du poste sont en CRLF. |
| C | **Une seule définition de « modification locale »**, partagée par le statut, le checkout, le merge, le pull et Publier. Règle : **si Polenta n'affiche aucune modification locale, l'utilisateur peut changer de branche.** |
| D | L'application n'écrit un fichier versionné **qu'après validation de l'utilisateur**, puis **commite et pousse aussitôt**. Rien ne reste en modification locale. |

## 3. A — `.gitignore` dès le départ, et blocages visibles

### 3.1 Contenu de référence

Tout repo Polenta (produit ou composant) porte un `.gitignore` versionné qui contient au moins :

```
*.pref
.polenta/tree.cache.yaml
```

Ce fichier est écrit et commité :
- à la création d'un projet (déjà fait par `initProjectRepo`) ;
- à la création d'un dépôt composant (`schema.service` écrit aujourd'hui `*.pref` seul) ;
- à l'adoption d'un repo existant.

### 3.2 Repo existant non conforme

Le `.gitignore` est absent ou incomplet, ou des fichiers locaux (`*.pref`, `tree.cache.yaml`) sont
suivis par git (« commités par erreur »). Polenta le signale. Le correctif passe par le flux D
(§6) : compléter `.gitignore` et retirer ces fichiers de l'index sans les supprimer du disque.

Les ajouts silencieux à `.gitignore` disparaissent (aujourd'hui `ensurePrefIgnored` et
`ensureCacheIgnored`, à chaque écriture d'une pref ou du cache).

### 3.3 Blocage visible

Toute opération refusée à cause de fichiers locaux (changement de branche, checkout d'un commit,
merge, Rafraîchir, Publier, resynchronisation) :

- liste **chaque fichier en cause**, avec son état et la raison en clair. Exemples :
  - « modifié » ;
  - « non suivi, existe sur `<branche>` » ;
  - « ignoré ici, versionné sur `<branche>` » ;
- propose l'action adaptée quand elle est sans risque (§5.2) ;
- n'affiche plus jamais le message brut d'isomorphic-git.

## 4. B — `.gitattributes` propre au repo

Tout repo Polenta porte un `.gitattributes` versionné :

```
* text=auto eol=lf
```

Le git CLI (y compris avec `core.autocrlf=true` système) sort alors les fichiers texte en LF, comme
Polenta les écrit et comme git les stocke : le disque est identique au contenu versionné. Les
fichiers binaires sont détectés par `text=auto` et restent intacts.

- **Création** : à la création du projet ou du composant, dans le commit initial.
- **Repo existant** : proposé par le flux D (§6). Les fichiers du disque qui ne diffèrent du contenu
  versionné **que par leurs fins de ligne** sont repassés en LF. Ce n'est pas une modification de
  contenu : ils n'apparaissent nulle part comme modifiés.
- Aucune écriture dans la config git (`core.autocrlf`, `core.eol`) du repo, de l'utilisateur ou du
  système.
- Le traitement des fins de ligne déjà en place (GH296 pour le statut et la mise en stage, GH335
  pour le checkout) reste, pour les repos non encore conformes.

## 5. C — une seule notion de « modification locale »

### 5.1 Définition

Un seul module calcule l'état de chaque fichier du working directory. Tout ce qui affiche ou garde
une opération l'utilise : panneau Version (Stagés / Modifications), Checkout branche, checkout d'un
commit, merge, Rafraîchir, Publier, auto-sync, resynchronisation, épinglage des sous-repos.

| État | Compte comme modification locale ? | Affiché dans Version |
|---|---|---|
| Suivi, contenu identique (fins de ligne comprises ou non) | Non | Non |
| Suivi, contenu modifié | Oui | Modifications |
| Stagé | Oui | Stagés |
| Non suivi, non ignoré | Oui | Modifications (nouveau) |
| Ignoré, non suivi | Non | Non |

### 5.2 Règle de changement de branche

**Si le panneau Version n'affiche aucune modification pour un repo, le changement de branche de ce
repo aboutit.**

Conséquences pour les cas qu'isomorphic-git refuse aujourd'hui :

- **Fichier ne différant que par les fins de ligne** : réécrit tel que dans git, puis checkout
  (déjà fait par GH335).
- **Fichier ignoré, non suivi, que la branche cible versionne** (cas `.local.migrated.pref`) : voir
  la question Q1 au §9.

### 5.3 Atomicité

Un checkout interrompu laisse aujourd'hui l'index et les fichiers sur la branche cible et HEAD sur
la branche d'origine (vu avec GH335 : 453 fichiers « stagés »). Le checkout est **tout ou rien** du
point de vue de l'utilisateur. Toute vérification bloquante passe avant la première écriture. Une
erreur après le début de l'écriture est détectée et réparée : on termine le checkout ou on revient à
l'état de départ. Elle n'est jamais laissée en l'état.

## 6. D — écritures de l'application : validées, puis commitées et poussées

### 6.1 Écritures concernées

Inventaire du code au 2026-11-09 : écritures de fichiers **versionnés** sans action explicite de
l'utilisateur.

| Fichiers | Déclencheur aujourd'hui |
|---|---|
| `AGENTS.md`, `.mcp.json` (régénérés si absents ou périmés) | chaque ouverture de workspace |
| `.gitignore` (ajout de `*.pref` / `.polenta/tree.cache.yaml`) | écriture d'une pref, du cache, création d'un dépôt composant |
| `dashboards/.seeded.yaml`, dashboard et requêtes Status partagés, `dashboards/lib/*` | ouverture du panneau Dashboards (`dashboards:list`) |
| Mise à niveau des anciennes requêtes partagées (`upgradeLegacySeeds`) | chaque `dashboards:list` |
| `.gitattributes` (nouveau, §4), mise en conformité `.gitignore` et retrait de l'index (§3.2) | — |

Écritures **hors périmètre**, déjà correctes : celles qui font partie d'une action de l'utilisateur
et de son commit (migration des compteurs GH20 à la création d'un objet), et l'état local ignoré
(`*.pref`, `tree.cache.yaml`, `.git/…`).

### 6.2 Comportement

1. Polenta détecte qu'une mise à jour est nécessaire. Il **n'écrit rien**.
2. Il le signale par repo : une ligne dans le panneau Version, avec un message qui dit quoi et
   pourquoi. Exemple : « Polenta doit ajouter `.gitattributes` et compléter `.gitignore`
   (fins de ligne, fichiers locaux) ». Le détail des fichiers est disponible.
3. **Valider** → écriture, commit (message préfixé `[polenta]`, explicite) et **push immédiat**, par
   les règles de Publier (fast-forward préalable de l'intégration, contrôle de divergence GH39,
   `dev-auto` GH173 si l'intégration n'est pas directement modifiable). Le repo revient
   « Rien à committer ».
4. **Plus tard** → rien n'est écrit. La fonction qui en dépend reste indisponible avec une
   explication (ex. seed des dashboards), et la proposition revient à la prochaine ouverture.
5. Repo en lecture seule (sous-repo épinglé, pas de droit d'écriture) : pas de proposition, rien
   n'est écrit.
6. Le commit ne contient que les fichiers de la mise à jour, jamais d'autres modifications locales
   de l'utilisateur. S'il y en a, la mise à jour est faite à part ou attend.

## 7. Critères d'acceptation

1. Un projet ou un composant créé par Polenta contient dans son premier commit un `.gitignore`
   (`*.pref`, `.polenta/tree.cache.yaml`) et un `.gitattributes` (`* text=auto eol=lf`).
2. Repo cloné par le git CLI avec `core.autocrlf=true` système puis ouvert dans Polenta, après
   validation de la mise en conformité : `git status` (CLI) et le panneau Version sont vides, et
   changer de branche dans Polenta aboutit.
3. Sur un repo qui contient `*.pref` suivis sur une branche et ignorés sur une autre : le panneau
   Version le signale. Si le changement de branche est refusé, le message nomme le fichier et la
   raison. Une fois la correction proposée validée, le changement de branche aboutit dans les deux
   sens.
4. Pour chaque opération du §5.1 : si le panneau Version est vide, l'opération n'est jamais refusée
   pour cause de modification locale. Test par opération.
5. Ouvrir un workspace et le panneau Dashboards sur un repo propre ne laisse **aucune**
   modification locale tant que l'utilisateur n'a rien validé. Après validation : un commit
   `[polenta]` poussé, et le repo propre.
6. Plus aucun ajout silencieux dans `.gitignore`.
7. Un checkout qui échoue après le début de l'écriture ne laisse ni HEAD ni l'index dans un état
   intermédiaire (test par injection d'erreur).
8. Aucune écriture dans une config git.

## 8. Hors scope

- Sortir les prefs du working directory (écarté par la décision A).
- Toute modification de la config git (`core.autocrlf`…) du poste.
- La fusion récursive (GH332) et le statut sous rafales de fichiers (GH335), déjà livrés.
- Les sous-repos ne sont pas des submodules git : la doc est traitée par #333.

## 9. Décisions sur les questions (humain, 2026-11-09)

- **Q1 — fichier ignoré localement que la branche cible versionne** : pour un `*.pref`, la copie
  locale est mise de côté, le checkout fait, puis la copie locale restaurée ; le panneau Version
  signale « fichier local commité sur cette branche » avec la correction D (retrait de l'index). Un
  autre fichier ignoré est listé dans le blocage.
- **Q2** : `* text=auto eol=lf` pour **tout le repo**.
- **Q3** : « Plus tard » → la proposition revient **à chaque ouverture**.
