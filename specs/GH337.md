# GH337 — Git natif embarqué (Git Bash portable), suppression d'isomorphic-git

Issue : #337 — milestone v0.6.0. Mesures préliminaires et confirmation de l'abandon d'isomorphic-git :
commentaires de l'issue (2026-11-10).

## 1. Contexte

isomorphic-git (pur JS) est à l'origine d'une série de bugs dus à ses écarts avec le vrai git : #296,
#326, #332, #335, #336. Il est aussi très lent sur les gros dépôts : 451 s pour l'historique par fichier
de `polenta-official`, contre 148 ms en natif. Polenta tourne en plus avec **deux moteurs** :
isomorphic-git pour HTTPS, et le `git` du PC pour les remotes SSH ou locaux (`sync.service.ts`, T154).
Le terminal GH238 utilise lui aussi le Git Bash du PC. Plusieurs bugs viennent du désaccord entre ces
moteurs, notamment `core.autocrlf=true` dans la config système de Git for Windows.

Inventaire au 2026-11-16 :
- 21 fichiers de production importent isomorphic-git, tous dans `apps/desktop/src/main`, plus le
  script `scripts/forge-smoke.ts` ;
- 34 tests unitaires et 1 spec e2e (`e2e-web/gh222-tree-merge.spec.ts`) créent leurs dépôts avec
  isomorphic-git ;
- `sync.service.ts` (8 commandes) et `results-import.service.ts` (`git config user.name`) appellent
  le binaire `git` du PC ;
- il n'existe pas de couche d'abstraction : `GitService` (`git.service.ts`) est une enveloppe
  partielle, et de nombreux services appellent isomorphic-git directement ;
- l'image Docker du serveur web (`Dockerfile.web`, `node:20-bookworm-slim`) **ne contient pas git**.

## 2. Décisions

### Humain, 2026-11-09/10 (issue)

1. Polenta embarque un git natif. Cela annule le refus de GH238 : depuis le passage en AGPL,
   distribuer git (GPLv2) comme exécutable séparé est acceptable.
2. isomorphic-git est supprimé **entièrement** : production, tests, fixtures et dépendance. Un seul
   moteur subsiste.
3. Les postes clients n'ont pas de git CLI : Polenta ne compte jamais sur le git du PC.

### Humain, 2026-11-16 (phase Spec)

| Question | Décision |
|---|---|
| Binaire embarqué | **Git for Windows portable (PortableGit) élagué**, et non MinGit/dugite : un seul git sert au moteur de Polenta **et** au terminal GH238 (bash, ssh, coreutils). |
| Livraison | **Un seul merge sur `main`**, une fois isomorphic-git entièrement retiré. Les deux moteurs ne coexistent jamais sur `main`. |
| Spike | Pas d'arrêt si les seuils du §8 sont tenus ; les mesures vont dans le résumé de sprint. Arrêt et présentation à l'humain sinon. |
| Plateformes | **Windows** (installeur) et **Docker** (serveur web : git de l'image, installé par apt). La résolution du binaire est générique (macOS et Linux possibles), mais le build, la signature et la notarisation macOS sont hors périmètre. |

## 3. Comportement attendu (utilisateur)

Aucune fonction n'est ajoutée ni retirée. L'utilisateur constate seulement les points suivants :

1. **Mêmes résultats que le git en ligne de commande.** Statut, checkout, fusion, pull et Publier
   donnent sur un dépôt le même résultat que `git` lancé dans le terminal de Polenta. Il n'y a plus de
   faux fichiers modifiés liés aux fins de ligne, ni de checkout refusé à tort.
2. **Rapidité.** Le statut, l'historique par fichier et l'ouverture du workspace sont au moins aussi
   rapides qu'aujourd'hui (seuils §8).
3. **Remotes SSH sans git installé.** Le binaire `ssh` embarqué utilise les clés de l'utilisateur
   (`~/.ssh`, `HOME` inchangé). Les remotes HTTPS passent par le PAT du compte, comme aujourd'hui.
4. **Terminal GH238 sans installation.** Le terminal lance le Git Bash **embarqué**. La proposition
   d'installation par winget disparaît. Le terminal partage avec Polenta le même `git` (en tête du
   `PATH`), la même configuration isolée (§4.2) et le même `GIT_ASKPASS`, si bien que `git push`
   fonctionne depuis le terminal avec le compte connecté.
5. **Sans Git for Windows sur le poste.** Toutes les fonctions git marchent sur un poste où Git for
   Windows n'est pas installé.
6. **Avec un Git for Windows quelconque sur le poste.** Une config système ou globale exotique
   (`core.autocrlf`, hooks, `commit.gpgsign`, credential helper, `core.editor`…) ne change rien au
   comportement de Polenta ni à celui de son terminal.

## 4. Principes techniques

### 4.1 Une seule couche `GitBackend`

Tous les services passent par une couche unique, `GitBackend` (main process). En dehors d'elle, aucun
fichier n'importe de moteur git ni ne lance `git`. Cela vaut pour le serveur MCP, le CLI et le serveur
web, qui réutilisent les services. Un lint (ou un test) le vérifie : pas d'`isomorphic-git` ni
d'`execFile('git'…)` hors de `GitBackend`.

### 4.2 Configuration isolée

Chaque processus git reçoit :
- `GIT_CONFIG_NOSYSTEM=1` ;
- `GIT_CONFIG_GLOBAL=<userData>/git/config`, une config propre à Polenta : identité du compte
  actif, `core.autocrlf=false`, `core.longpaths=true` sous Windows, aucun credential helper ;
- `GIT_TERMINAL_PROMPT=0` pour Polenta (dans le terminal, il reste à sa valeur par défaut) ;
- aucun hook (`core.hooksPath` pointant vers un dossier vide) et aucune signature.

La config locale d'un dépôt (`.git/config`) n'est ni lue pour modifier le comportement attendu, ni
réécrite, sauf pour ce que Polenta y écrit déjà : remotes et suivi de branches.

### 4.3 Fins de ligne

La règle est fixée par le `.gitattributes` de chaque repo (#336, décision B). Les clones existants
dont des fichiers sont en CRLF sur disque alors qu'ils sont en LF dans git sont normalisés une fois.
Cette normalisation ne crée ni commit ni modification affichée.

### 4.4 Identifiants

Le PAT reste dans keytar. git le reçoit par un script `GIT_ASKPASS` fourni avec Polenta, qui le
demande au main process. Il n'apparaît jamais en ligne de commande, dans `http.extraHeader`, dans
l'URL du remote ni dans un fichier. Le proxy (`HTTPS_PROXY`/`NO_PROXY`, GH347) et les délais réseau
(GH15) sont transmis à git par l'environnement et par `-c http.*`. Le garde de remote du serveur web
(`checkRemote`, GIT_HOSTS) est appliqué avant tout `fetch`, `push` ou `clone`.

### 4.5 Fusion

La fusion se calcule avec `git merge-tree --write-tree`, qui ne touche pas au working directory. Cela
reproduit le comportement actuel `abortOnConflict` : un conflit lève `MergeConflictError`, avec les
chemins en conflit et les deux refs, comme aujourd'hui. La fusion structurelle `@polenta/merge-core`
(GH37/GH222), la résolution dans l'outil et la fusion récursive (`recursive-merge.util.ts`) gardent le
même comportement.

### 4.6 Processus

| Processus persistant, un par dépôt | Usage |
|---|---|
| `cat-file --batch-command` | lecture d'objets, résolution de refs et de révisions |
| `update-ref --stdin` | écriture et suppression de refs, en transactions |
| `check-ignore --stdin`, `check-attr --stdin` | ignorés, attributs (eol) |
| `hash-object --stdin-paths` | hash de fichiers |

Les autres opérations passent par des processus ponctuels, regroupés : `status --porcelain=v2 -z`,
`for-each-ref`, un seul `log --name-status` pour l'historique par fichier, `merge-tree`, `checkout`,
`commit`, `fetch`, `push`, `clone`.

Exigences :
- les écritures sont mises en file **par dépôt** (`index.lock`), ce qui remplace `git-lock-limits` ;
- un processus persistant traite ses requêtes une à une ;
- un processus persistant mort est relancé de manière transparente, et la requête en cours est
  rejouée une fois ;
- les processus sont arrêtés à la fermeture du dépôt ou de l'application, et aucun ne reste orphelin
  sous Windows ;
- aucune fenêtre console ne s'ouvre (`windowsHide`).

### 4.7 Binaire et packaging

- **Windows** : PortableGit d'une version fixée (≥ 2.38), téléchargé au build par un script qui
  vérifie son SHA-256. Il est élagué (gitk, tcl/tk, git-gui, docs, locales inutiles…) puis placé
  hors de l'archive asar (`extraResources`). La version et le hash sont fixés dans le dépôt, et la
  mise à jour est manuelle.
- **Résolution du chemin**, identique en dev, en app packagée, pour le serveur MCP, le CLI et le
  serveur web : `POLENTA_GIT_DIR` s'il est défini, sinon le binaire embarqué (`resources/git`), sinon
  (Linux et macOS uniquement, donc Docker et CI) le `git` du `PATH`. Sous Windows, il n'y a **jamais**
  de repli sur le git du PC.
- **En dev**, `pnpm install` (ou un script dédié) installe le même PortableGit dans un dossier ignoré
  par git. Les tests utilisent cette résolution.
- **Version minimale** : git ≥ 2.38 (pour `merge-tree --write-tree`), vérifiée au démarrage. Si elle
  n'est pas atteinte, une erreur explicite est journalisée et les opérations git échouent avec un
  message clair.
- **Docker** : `Dockerfile.web` installe `git` et `openssh-client` par apt (bookworm : 2.39).
- **Licences** : `THIRD-PARTY-NOTICES.txt` cite Git for Windows et ses composants (GPLv2 et autres),
  avec le lien vers les sources.

## 5. Critères d'acceptation

1. `isomorphic-git` est absent de tout `package.json`, de `pnpm-lock.yaml` et de tout import
   (production, tests, e2e, scripts). Il en va de même pour `async-lock`, s'il n'a plus d'usage.
2. Hors de `GitBackend`, aucun fichier ne lance `git` ni n'importe un moteur git, et un test le vérifie.
3. `pnpm typecheck`, `pnpm lint` et `pnpm test` sont verts. La suite e2e web complète est verte au
   merge (niveau 3). Les specs desktop `gh238` et `gh342` sont vertes en ciblé.
4. Les tests de régression des bugs #296, #326, #332, #335 et #336 restent verts, réécrits sur le
   backend natif. Au moins un test les rejoue avec une config système hostile (`core.autocrlf=true`,
   hook `pre-commit` qui échoue, `commit.gpgsign=true`) : comportement identique.
5. Sur un poste Windows **sans Git for Windows** (ou avec un `PATH` qui en est expurgé), l'installeur
   donne une application où clone HTTPS, Publier, pull, checkout, merge avec conflit puis résolution,
   tag, baseline et terminal fonctionnent.
6. Remote SSH : fetch, pull et push fonctionnent avec le `ssh` embarqué (test automatisé sur un remote
   local `file://`, plus un test manuel en SSH).
7. Aucun processus `git.exe` ne reste après la fermeture de l'application (vérifié en e2e desktop).
8. Le PAT n'apparaît ni dans la ligne de commande des processus git, ni dans `.git/config`, ni dans
   les logs (test).
9. Mesures sur `PH2/handstickProduct` et `polenta-official` dans le résumé du dernier sprint, comparées
   à `main` : statut, checkout, historique par fichier, ouverture du workspace, taille de l'installeur.
10. Les specs (§9) sont à jour et ne mentionnent plus isomorphic-git comme moteur.

## 6. Découpage

Il y a un seul ticket et une seule PR. Les sprints sont détaillés dans `GH337-design.md` :

0. **Spike** : script d'embarquement de PortableGit et élagage, première version de `GitBackend`
   (résolution du binaire, config isolée, `cat-file` persistant), mesures (§8).
1. **Lectures** : statut, log, historique par fichier, lecture à une révision, refs, ignorés et
   attributs.
2. **Écritures locales** : commit, branche, tag, checkout (safe-checkout), reset, `update-ref`, init.
3. **Réseau et fusion** : clone, fetch, push, pull, `merge-tree`, fusion récursive, résolution GH37,
   `GIT_ASKPASS`, proxy et délais, suppression du double chemin SSH, terminal GH238 sur le Git Bash
   embarqué, Docker.
4. **Suppression d'isomorphic-git** : dépendance, code, 34 tests et la spec e2e réécrits avec le
   binaire, `forge-smoke.ts`, specs.

## 7. Hors périmètre

- Build, signature et notarisation macOS, et paquet Linux de bureau (la résolution du chemin reste
  générique).
- Git LFS, les sous-modules (abandonnés, #333), toute nouvelle fonction git dans l'interface.
- La mise à jour automatique de la version de PortableGit (elle se fait à la main, dans le dépôt).
- La modification de la config git globale ou système du poste (#336, décision B).
- Les dates de création et de modification (#340, déjà traité).

## 8. Seuils du spike

Le spike se poursuit sans arrêt si les trois seuils suivants sont tenus :
- l'installeur grossit de **120 Mo au plus** ;
- aucune des opérations mesurées (statut, checkout, historique par fichier, ouverture du workspace,
  sur `PH2/handstickProduct` et `polenta-official`) n'est **plus lente de plus de 10 %** que sur
  `main` ;
- `ssh` et `bash` démarrent depuis le binaire élagué.

Sinon, le spike s'arrête et les mesures sont présentées à l'humain.
