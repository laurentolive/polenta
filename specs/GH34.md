# GH34 — Export Word/Excel basé sur un gabarit fourni par le client

Issue : [#34](https://github.com/laurentolive/polenta/issues/34) — type:feature

## 1. Contexte

- Les exports Word sont construits de toutes pièces par code (lib `docx`,
  `apps/desktop/src/main/services/export/*.docx.ts`) avec les styles par défaut : pas de logo, pas
  d'en-tête/pied de page, pas de page de garde, pas de cartouche. Le rendu ne correspond pas aux
  documents qu'attendent les clients (charte graphique, référence documentaire, historique…).
- Les exports Excel sont construits par code (`exceljs`, `*.xlsx.ts`).
- Tous les exports passent par un point d'entrée unique : canal IPC `export:save` →
  `ExportService.run(kind, format, payload, …)`, table `GENERATORS` `kind:format`. Le renderer
  envoie un `payload` déjà filtré (colonnes/lignes visibles de la vue, cf. `buildExportRows`).
- Les champs `richtext` sont stockés en **Markdown** (GFM : listes, tableaux, gras/italique,
  images `![](images/…)` stockées dans le repo, blocs fenced draw.io `{"path","nodeId"}`, liens
  internes `[[SW-0042]]`). L'export docx actuel les écrit en texte brut ligne à ligne.
- Le dossier `templates/` du repo et SPEC-TEMPLATES désignent des **modèles de schéma projet** —
  sans rapport avec cette fonctionnalité. Pour éviter la confusion, on parle ici de **gabarits
  d'export**.

## 2. Description fonctionnelle

Le client fournit ses propres gabarits Word (puis Excel), réalisés avec Word/Excel : page de
garde, logo, en-têtes/pieds de page, cartouche, styles de titres, de tableaux et de listes. Il y
place des **balises** qui désignent les données Polenta (titre du projet, date, boucle sur les
exigences, champs…). À l'export, Polenta remplit le gabarit et produit le document final. Le
rendu standard actuel reste disponible.

### 2.1 Bibliothèque de gabarits (préférence application)

- Nouvelle préférence application (`app-settings.json`, `AppSettingsService`, GH26) :
  **dossier de la bibliothèque de gabarits d'export** (chemin absolu, vide par défaut).
- Ce dossier peut être un dossier local, un partage réseau ou un repo git cloné : Polenta ne
  fait que le **lire** (pas de commit, pas de synchro, pas d'écriture).
- Contenu : fichiers `*.docx` (et `*.xlsx` en phase 2), éventuellement rangés en
  sous-dossiers (ex. un sous-dossier par client). Un gabarit est identifié par son **chemin
  relatif** à la bibliothèque, séparateurs `/` (ex. `ACME/cahier-exigences.docx`).
- Fichiers ignorés : fichiers temporaires Office (`~$*`), fichiers cachés, autres extensions.
- Réglage dans l'écran des préférences de l'application : sélecteur de dossier natif +
  affichage du chemin courant + bouton pour le vider.
- La liste des gabarits est relue à chaque ouverture du popover Exporter (pas de cache à
  invalider) : un gabarit ajouté au dossier est visible immédiatement.

### 2.2 Gabarit par défaut du projet (préférence projet)

- Dans `.polenta/schema.yaml`, `preferences:` (préférences projet, partagées par l'équipe via
  git) : nouvelle entrée `exportTemplates`, table `<kind>:<format>` → chemin relatif dans la
  bibliothèque.

  ```yaml
  preferences:
    exportTemplates:
      requirements:docx: ACME/cahier-exigences.docx
      tests:docx: ACME/cahier-tests.docx
      campaign-report:docx: ACME/rapport-campagne.docx
  ```

- Le chemin est **relatif** : chaque membre de l'équipe peut avoir la bibliothèque à un endroit
  différent sur sa machine ; seul le contenu relatif doit être identique.
- Kind sans entrée → le défaut est le rendu standard.
- Éditable depuis l'UI des préférences projet (là où se règle `autoPropagatePin`) : un sélecteur
  par kind/format supporté, listant « Standard » + les gabarits de l'extension correspondante.

### 2.3 Choix à l'export

- Le popover `ExportButton` affiche, pour les formats qui supportent les gabarits (docx en
  phase 1, xlsx en phase 2), une liste déroulante **Gabarit** : « Standard » + gabarits de la
  bibliothèque ayant la bonne extension. Présélection = défaut du projet pour ce kind/format.
- Le choix fait à l'export ne modifie pas le défaut du projet.
- Pas de bibliothèque configurée → la liste ne propose que « Standard » et un lien/indication
  vers la préférence application.
- Défaut du projet introuvable dans la bibliothèque (non configurée, fichier absent ou renommé)
  → l'option est affichée comme **indisponible** avec son chemin, « Standard » est présélectionné
  et un message l'explique. Pas d'export silencieux avec un autre gabarit que celui attendu.
- PDF : inchangé (impression de la route `/print/<kind>`), pas de gabarit.

### 2.4 Données disponibles dans un gabarit

Chaque kind expose un modèle de données documenté (référence utilisateur, §2.6). Communes à
tous les kinds :

| Donnée | Contenu |
|--------|---------|
| `project` | nom/label du projet, composant exporté (`componentLabel`) |
| `export.date` / `export.datetime` | date de génération, format local |
| `export.user` | nom de l'utilisateur git courant |
| `git.branch`, `git.commit` (SHA court), `git.tag` (si HEAD est tagué) | référence de la révision exportée |
| `export.kind`, `export.templateName` | traçabilité du document généré |

Par kind :

- **requirements / tests** : liste `items` dans l'ordre de l'arbre (comme aujourd'hui). Chaque
  élément expose les colonnes visibles de la vue (`id`, `name`, `section`, `status`, `version`,
  champs personnalisés par **nom** de champ), plus un accès générique `fields` (liste
  `{key, label, value}`) pour les gabarits qui veulent boucler sur les colonnes sans les
  connaître. Les dossiers (titres de section) sont exposés comme éléments de type `folder` avec
  leur niveau, pour permettre des titres hiérarchiques. Tests : `steps` détaillés
  (`order`, `action`, `expectedResult`, `notes`), `preconditions`, `postconditions`,
  `equipment`.
- **campaign-plan / campaign-report** : `campaign` (id, titre, statut, champs), `entries`
  (test + run : statut d'exécution, résultats par étape, commentaires, exigence de l'instance
  pour les instances générées), et pour le rapport une synthèse `summary` (nombre par statut).
- **dashboard** : `dashboard` (titre), `widgets` (titre, type, résultat tabulaire
  colonnes/lignes).

Les valeurs de **paramètres** `{nom}` sont résolues comme dans l'export actuel (SPEC-REQ §3.2f).

### 2.5 Rendu des champs richtext

Un champ richtext inséré par une balise dédiée (ex. balise « bloc riche ») est converti en
contenu Word **mis en forme, avec les styles du gabarit** :

- titres, paragraphes, gras/italique/souligné/barré, code inline ;
- listes à puces et numérotées (imbriquées), cases à cocher (`- [ ]`) ;
- tableaux GFM → tableaux Word (style de tableau du gabarit s'il en définit un) ;
- images du repo et URL externes → images embarquées, largeur limitée à la largeur utile de la
  page ;
- diagrammes draw.io → image du diagramme (même rendu que la Vue Word / le PDF) ; si le rendu
  échoue, un paragraphe de remplacement explicite (`[Diagramme : <path>#<nodeId>]`) ;
- liens internes `[[SW-0042]]` → texte de l'ID (pas de lien hypertexte en v1).

Les styles Word utilisés (Titre 1…n, Paragraphe de liste, style de tableau…) sont ceux du
gabarit, pour que le résultat respecte la charte. Si le gabarit ne définit pas un style
attendu, Word applique son style par défaut (pas d'erreur).

Un champ richtext inséré avec une balise **texte simple** donne le texte brut (sans syntaxe
Markdown), pour les cartouches/cellules.

### 2.6 Documentation et gabarits d'exemple

- Une page de référence utilisateur liste la syntaxe des balises et le modèle de données de
  chaque kind (§2.4), avec des exemples.
- Un gabarit d'exemple par kind docx est livré avec l'application (copiable dans la
  bibliothèque) ; il sert aussi de fixture de test.

### 2.7 Erreurs

| Situation | Comportement |
|-----------|--------------|
| Gabarit syntaxiquement invalide (balise non fermée, boucle mal imbriquée…) | Export interrompu, message d'erreur dans le popover d'export indiquant le gabarit et la balise/l'emplacement fautif. Aucun fichier partiel écrit. |
| Balise désignant une donnée inexistante (ex. champ renommé) | Pas d'échec : valeur vide. (Le gabarit doit rester utilisable si un champ est masqué dans la vue.) |
| Fichier gabarit illisible/corrompu, ouvert verrouillé | Message d'erreur explicite, pas de fichier écrit. |
| Image/diagramme introuvable | Paragraphe de remplacement, l'export continue. |

**Sécurité** : un gabarit est un fichier externe ; son évaluation ne doit **pas permettre
l'exécution de code arbitraire** (pas d'expressions JavaScript libres évaluées dans le main
process). Seules des balises d'accès aux données, des boucles et des conditions simples sont
autorisées.

### 2.8 Phase 2 — Excel

- Même bibliothèque, même préférence projet (`requirements:xlsx`, `tests:xlsx`,
  `campaign-plan:xlsx`, `query-result:xlsx`, `impact-analysis:xlsx`), même sélecteur au moment
  de l'export.
- Le gabarit est un classeur du client (logo, cartouche, mise en forme, largeurs de colonnes,
  formats, en-têtes fixes, impression). Des balises dans les cellules donnent les valeurs
  uniques (projet, date, révision…) ; une **ligne modèle** marquée par une balise de boucle est
  répétée pour chaque élément, en conservant sa mise en forme (bordures, polices, formats,
  hauteur), les formules et la mise en forme conditionnelle s'étendant aux lignes générées.
- Richtext en Excel : texte brut (une cellule n'a pas la mise en forme riche) ; images et
  diagrammes ignorés.
- Le reste du classeur (autres feuilles, formules de synthèse) est conservé tel quel.

## 3. Cas d'usage

1. **Configuration initiale** — L'utilisateur clone le repo « charte ACME » contenant
   `ACME/cahier-exigences.docx`, renseigne son chemin dans les préférences de l'application.
   L'intégrateur du projet choisit `ACME/cahier-exigences.docx` comme défaut `requirements:docx`
   dans les préférences projet et publie le `schema.yaml`.
2. **Export courant** — Un autre membre de l'équipe (bibliothèque clonée ailleurs sur son disque)
   ouvre la vue système, Exporter → Word : le gabarit ACME est présélectionné, le document
   produit a la page de garde ACME, la référence git, la liste des exigences avec énoncés mis en
   forme, tableaux et diagrammes.
3. **Export ponctuel standard** — Il choisit « Standard » dans la liste : rendu actuel, défaut du
   projet inchangé.
4. **Bibliothèque absente** — Un utilisateur sans bibliothèque configurée exporte : le défaut est
   indiqué indisponible, « Standard » est présélectionné, un message indique comment configurer
   la bibliothèque.
5. **Gabarit cassé** — Le client a laissé une boucle non fermée : l'export échoue avec un message
   nommant le gabarit et la balise ; aucun fichier n'est créé.
6. **Plusieurs clients** — La bibliothèque contient `ACME/…` et `Globex/…` ; chaque projet pointe
   vers les gabarits de son client.

## 4. Critères d'acceptation

**Phase 1 — Word**

1. La préférence application « bibliothèque de gabarits d'export » est réglable (choisir, vider)
   et persistée dans `app-settings.json`.
2. Le popover Exporter liste, pour docx, « Standard » + tous les `*.docx` de la bibliothèque
   (sous-dossiers compris, `~$*` et fichiers cachés exclus), identifiés par chemin relatif.
3. `preferences.exportTemplates` est lu/écrit dans `.polenta/schema.yaml` et éditable depuis
   les préférences projet ; le défaut est présélectionné à l'export.
4. Défaut introuvable → affiché indisponible, « Standard » présélectionné, message explicite ;
   jamais d'export avec un gabarit non choisi.
5. Les 5 kinds docx (`requirements`, `tests`, `campaign-plan`, `campaign-report`, `dashboard`)
   produisent un document à partir d'un gabarit ; en-têtes, pieds de page, page de garde,
   styles et images du gabarit sont conservés dans le résultat.
6. Les données communes (§2.4) et propres à chaque kind sont accessibles par balises ; les
   éléments sont dans l'ordre de l'arbre et respectent le filtre/la configuration de colonnes
   de la vue, comme l'export standard.
7. Un champ richtext contenant titre, gras, liste imbriquée, case à cocher, tableau GFM, image du
   repo et diagramme draw.io est rendu mis en forme dans le docx (Word l'ouvre sans message de
   réparation) ; le même champ en balise texte simple donne le texte sans syntaxe Markdown.
8. Gabarit invalide → message nommant le gabarit et la balise, aucun fichier écrit à la
   destination.
9. Une balise de donnée inexistante donne une valeur vide, sans erreur.
10. Aucune balise ne permet d'exécuter du code arbitraire.
11. Le rendu « Standard » est strictement inchangé (non-régression des exports actuels).
12. Les gabarits d'exemple et la page de référence des balises sont livrés.

**Phase 2 — Excel**

13. Même sélection/défaut pour les kinds xlsx ; la ligne modèle est répétée par élément avec sa
    mise en forme ; cellules uniques remplies ; autres feuilles/formules conservées ; richtext en
    texte brut.

## 5. Hors scope

- PDF à partir d'un gabarit (conversion docx → PDF) — ticket ultérieur si besoin.
- Édition des gabarits dans Polenta, éditeur visuel de balises.
- Versionnement/synchronisation de la bibliothèque par Polenta (pull, commit) : c'est un dossier
  lu tel quel.
- Graphiques du dashboard dans le docx gabarité : tableaux de résultats uniquement, comme l'export
  docx actuel.
- Liens hypertexte internes entre éléments (`[[ID]]` → signet) dans le docx.
- Gabarits PowerPoint.
- Colonnes de relations `link::*` (déjà exclues de l'export standard, T43).

## 6. Découpage indicatif

- Phase 1 (Word) : bibliothèque + préférences + sélecteur ; moteur de gabarit et modèles de
  données ; rendu richtext → Word ; gabarits d'exemple et doc. Probablement plusieurs sprints
  (à évaluer en Design).
- Phase 2 (Excel) : sprint(s) dédié(s) une fois la phase 1 validée.
