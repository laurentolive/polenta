# GH340 — Dates de création / modification stockées dans le YAML, posées par l'application

Issue : #340 (type:feature). Lié à #337 (passage au git natif), indépendant.

## 1. Contexte

Depuis T112, `createdAt`, `createdBy`, `updatedAt` et `updatedBy` (« champs d'audit ») ne sont plus
stockés dans les objets. Ils sont **dérivés de git** par `GitService.fileHistoryMap`, qui parcourt
tout l'historique du dépôt à chaque construction d'index (exigences, tests, issues). La lecture d'une
exigence à un tag de baseline (T179) fait de même.

Mesuré sur une copie de handstickProduct (34 commits) : 552 ms pour les exigences, 402 ms pour les
tests, 315 ms pour les issues, refaits **à chaque changement de branche** (les index sont invalidés).
Le coût croît avec le nombre de commits : 451 s pour 786 commits, mesuré sans filtre de dossier
(#337). Il se multiplie aussi par le nombre de dépôts du workspace.

La dérivation a aussi trois défauts de sens :
- **Auteur faussé par les fusions** : la comparaison au premier parent attribue à la personne qui
  fusionne, sur la branche d'intégration, des modifications qu'elle n'a pas faites.
- **Dates perdues** quand un élément est déplacé entre dépôts, renommé (préfixe, GH100), ou que
  l'historique est réécrit (squash, rebase, import).
- **Dates absentes des fichiers** : les scripts projet (vue Suivi, GH79) ne les trouvent pas dans
  le YAML.

T112 avait retiré ces champs du YAML pour une raison : n'importe quelle écriture accidentelle les
modifiait (T104). Depuis, GH77 a mis en place ce qu'il faut pour l'éviter : un point d'écriture
unique par service (`persist` → `HistoryService.stamp`), qui ne pose une entrée que si la valeur
change vraiment, et un test garde-fou sur les chemins d'écriture.

## 2. Décisions de l'humain (2026-11-10)

1. Les quatre champs reviennent dans le YAML des exigences, des tests et des issues. Ils sont
   **posés par l'application**, comme `history`. Cela annule T112.
2. **Seules les actions de l'utilisateur** font avancer `updatedAt` / `updatedBy`, et seulement si
   le contenu change. Les écritures automatiques de l'application n'y touchent pas.
3. **Reprise des objets existants par la mise en conformité** de GH336 (§6) : validée par
   l'utilisateur, commitée et poussée.
4. **Plus aucune lecture de git** pour ces champs. Un objet sans dates (pas encore repris, ou lu à
   un tag antérieur à la reprise) affiche « — ».

## 3. Stockage

Champs système à la racine de l'objet, à côté de `history` :

```yaml
id: SYS-0001
title: Démarrage rapide en mode Eco
status: review
version: 3
createdAt: '2026-09-02T08:10:00Z'
createdBy: lolive
updatedAt: '2026-10-14T16:42:05Z'
updatedBy: sdupont
fields: { … }
history: { … }
```

- **Format de date** : celui des entrées de `history` (`at`, UTC, à la seconde).
- **Identité** (`createdBy`, `updatedBy`) : la même que le `by` de `history` (SPEC-REQ §4.4) :
  - desktop : login du compte du projet ;
  - client web : login de la session ;
  - MCP : `--user`, sinon `local`.
- **Objets concernés** : exigences, tests, issues, soit tous les objets dont l'index dérive ces
  champs aujourd'hui.
- **Valeurs absentes** : un champ absent est lu `null` et affiché « — ». Les quatre champs sont
  écrits ensemble ; un objet ne garde jamais une partie seulement.

## 4. Écriture

### 4.1 Création

Les quatre champs sont posés : `createdAt` = `updatedAt` = maintenant, `createdBy` = `updatedBy` =
l'auteur. Cela vaut aussi pour une **copie** d'objet (nouvel ID, donc nouvel objet) et pour l'import
en masse (MCP `bulk_import`).

`createdAt` et `createdBy` ne changent plus jamais ensuite, quelle que soit l'écriture.

### 4.2 Actions qui font avancer `updatedAt` / `updatedBy`

Toujours **à condition que le contenu de l'objet change**.

| Action | Origine |
|---|---|
| Modification d'un objet (titre, champs, étapes d'un test, liens Jira…) | UI, client web, MCP |
| Changement de statut (transition) | UI, client web, MCP |
| Enregistrement d'un objet depuis une vue de diff (GH222) | UI |
| Ajout d'un run ou d'une décision à une issue | UI, MCP |

**Contenu de l'objet** : tout le fichier, sauf les clés posées par l'application, c'est-à-dire
`history`, `needsRevalidation`, `version`, les quatre champs d'audit, `projectId`, `branchId` et
`objectTypeRef`. Si une écriture ne change que ces clés, ou ne change rien (autosave, ouverture
d'un éditeur, commentaire GH163 sans changement de champ), les champs d'audit restent tels quels.
Si rien d'autre ne change, le fichier ne change pas non plus.

### 4.3 Écritures automatiques : les champs restent tels quels

| Écriture | Ticket |
|---|---|
| Pose ou retrait de `needsRevalidation` (un élément lié quitte l'approbation) | T172 |
| Renommage d'un champ, d'une valeur d'enum, d'un statut | GH77, GH82 |
| Renommage d'un type (nom ou préfixe, y compris le changement de chemin du fichier) | GH100 |
| Déplacement d'un élément vers un autre type ou un autre dépôt | element-move |
| Adoption dans l'arbre d'affichage | tree |
| Reprise de l'historique depuis git (`history:backfill`) | GH77 |
| Résultat d'une fusion ou d'une résolution de conflits (§5) | GH37, GH222 |

Conséquence voulue : un élément déplacé ou renommé garde sa date et son auteur de création.

### 4.4 Modifications hors de Polenta

Une édition à la main, un script ou un agent IA qui écrit directement le fichier ne met pas les
dates à jour : c'est le compromis accepté (même règle que `history`). La documentation des agents
(`AGENTS.md`, CLAUDE.md) indique que ces champs sont posés par l'application et ne s'écrivent
jamais à la main. L'historique git reste la référence d'audit.

## 5. Fusion

Fusion structurelle (`@polenta/merge-core`, GH222), sur le modèle des règles existantes de
`history`, `version` et `needsRevalidation` :

- **`updatedAt` / `updatedBy`** : on garde **la paire** du côté dont `updatedAt` est le plus récent.
  Un seul côté renseigné → ce côté.
- **`createdAt` / `createdBy`** : on garde **la paire** du côté dont `createdAt` est le plus ancien.
  Un seul côté renseigné → ce côté.
- Ces champs ne produisent **jamais de conflit** et n'apparaissent pas dans l'éditeur de résolution
  (GH37).

Une fusion faite avec git hors de Polenta peut produire un conflit ligne à ligne sur ces champs.
C'est hors de la responsabilité de Polenta, sans autre traitement.

## 6. Reprise des objets existants (mise en conformité)

Nouvel élément de la mise en conformité de GH336 (§6.2), avec ses règles inchangées :
détection sans écriture, ligne dans le panneau Version, puis **Valider** ou **Plus tard**. Le
commit est préfixé `[polenta]` et poussé immédiatement. Rien n'est proposé sur un dépôt en lecture
seule.

- **Détection** : au moins une exigence, un test ou une issue du dépôt sans ses quatre champs.
  Message, par exemple : « Polenta doit compléter les dates de création et de modification de
  128 objets ». Le détail liste les fichiers.
- **Valeurs écrites**, tirées de l'historique git du chemin du fichier sur la branche courante, en
  ignorant les commits de fusion (pour avoir l'auteur réel) :
  - `createdAt` / `createdBy` : date d'auteur et auteur du **plus ancien** commit qui touche le
    fichier ;
  - `updatedAt` / `updatedBy` : date d'auteur et auteur du **plus récent** commit hors fusion qui
    le touche.

  Ce sont les valeurs que l'utilisateur voit aujourd'hui, hors le défaut de fusion.
- **Seuls les champs absents sont écrits** : jamais une valeur déjà présente. Ni `history`, ni
  `version`, ni le reste du fichier ne change.
- **Autres branches** : elles reçoivent les dates à la fusion de l'intégration (§5, sans conflit).
  Un objet créé sur une branche avant la reprise garde « — » jusqu'à sa prochaine modification, ou
  jusqu'à la reprise suivante sur l'intégration, une fois la branche fusionnée.
- **Dépôt en lecture seule** (composant épinglé) : pas de reprise. Ses objets affichent « — »
  jusqu'à ce que l'équipe propriétaire fasse la mise en conformité dans son propre dépôt. Il n'y a
  pas de repli sur git (validé par l'humain le 2026-11-10).
- **Plus tard** : rien n'est écrit, les objets non repris affichent « — ». La proposition revient à
  la prochaine ouverture.
- **Durée** : la reprise affiche sa progression. Repère de GH77 : 2 000 objets × 200 commits, environ
  1 min.

## 7. Lecture

- **Index** (exigences, tests, issues) : les champs sont lus dans le YAML. La construction d'un index
  **ne lit plus jamais l'historique git**.
- **Lecture à un tag** (`req-refs`, T179) : les champs sont lus dans le fichier au tag. Un fichier
  antérieur à la reprise n'en a pas et affiche « — ».
- **Graphe** : le repli sur les dates de l'objet (`graph.service`, pour une entrée d'historique
  manquante) utilise les valeurs du YAML.
- **Inchangé** : tout ce qui consomme ces champs (vue Excel, éditeur, aperçu, vue Word, requêtes,
  vue Suivi, exports, `{req.<champ>}` de T179, outils MCP) les reçoit sous la même forme. La seule
  différence est qu'ils peuvent valoir `null` sur un objet non repris.
- **Copies** : les copies `testSnapshot` des campagnes **ne contiennent pas** ces champs (comme
  `history`). L'empreinte `testFingerprint` les ignore déjà.
- **Diffs** : ces champs restent classés parmi les clés posées par l'application (`APP_KEYS` de
  `version-tracking`, `MANAGED` de `diff-edit`). Les vues de diff ne les proposent pas à l'édition.

## 8. Critères d'acceptation

1. **Création** : créer une exigence, un test ou une issue (UI, client web, MCP) écrit les quatre
   champs, avec `createdAt` = `updatedAt` et l'auteur attendu (§3).
2. **Modification** : modifier un champ puis enregistrer fait avancer `updatedAt` / `updatedBy`.
   `createdAt` / `createdBy` restent identiques.
3. **Écriture sans changement** (autosave, réenregistrement à l'identique) : le fichier reste
   identique à l'octet près.
4. **Écritures automatiques** : après chacune des écritures du §4.3, les quatre champs de chaque
   fichier touché sont inchangés.
5. **MCP** : une modification par `update_requirements` pose `updatedBy` = l'utilisateur MCP, ou
   `local`.
6. **Fusion** : deux branches modifient le même objet, sur des champs différents, à des dates
   différentes. La fusion dans Polenta aboutit sans conflit. Le résultat porte l'`updatedAt` le plus
   récent avec son auteur, et le `createdAt` le plus ancien avec son auteur.
7. **Sans git** : construire les index et lire une exigence à un tag n'appelle aucune lecture de
   l'historique git (vérifié par test). `fileHistoryMap` est supprimé s'il ne reste aucun appelant.
   Le temps de reconstruction des index de handstickProduct après un changement de branche est
   mesuré avant et après, et noté dans le résumé de sprint.
8. **Reprise** : un dépôt dont des objets n'ont pas les champs affiche la proposition de mise en
   conformité.
   - **Valider** : un commit `[polenta]` qui ne contient que ces fichiers, poussé immédiatement.
     Les valeurs suivent le §6, l'auteur d'une modification arrivée par une fusion est l'auteur
     réel, et aucune valeur existante n'est réécrite.
   - **Plus tard** : rien n'est écrit, et les objets non repris affichent « — ».
9. **Baseline ancienne** : une exigence lue à un tag antérieur à la reprise affiche « — » pour les
   quatre champs.
10. **Copies de campagne** : un `testSnapshot` créé après ce ticket ne contient pas les quatre champs.
11. **Garde-fou** : le test des chemins d'écriture (`history.write-paths.test.ts`) couvre aussi la
    pose des champs d'audit. Aucune écriture d'objet ne les contourne.

## 9. Hors scope

- Passage au git natif et retrait d'isomorphic-git (#337).
- Dates propres aux autres objets (campagnes, versions, validations, baselines, dashboards, liens
  `ObjectLink.createdAt`), déjà stockées ou sans rapport.
- `version-tracking` (`commitChanges`, recherche de la version approuvée) et la reprise d'historique
  GH77 : ils lisent git pour d'autres besoins et ne changent pas.
- Détection d'une modification faite hors de Polenta (§4.4).
- Ancien contenu des copies `testSnapshot` déjà écrites : pas de migration rétroactive (même règle
  que SPEC-TESTS §4.1).
