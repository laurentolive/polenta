# GH342 — Multi-fenêtres : le même projet dans deux fenêtres (deux écrans)

## Besoin

Demande client : afficher **le même projet** dans deux fenêtres Polenta, une par écran, pour
consulter et éditer **en parallèle les exigences de composants différents** (ex. composant A sur
l'écran 1, composant B sur l'écran 2).

Suite prévue dans #343 (glisser un onglet hors de la fenêtre, deux projets différents) — hors
périmètre ici.

## Décisions (Laurent, 2026-11-12)

| # | Question | Décision |
|---|----------|----------|
| D1 | « Ouvrir dans une nouvelle fenêtre » depuis un onglet | **Copie** : la nouvelle fenêtre ouvre la même page, l'onglet d'origine reste. Pas de transfert d'état non sauvegardé (le déplacement viendra avec #343). |
| D2 | Même élément édité dans les deux fenêtres | Les éditeurs **n'envoient que les champs modifiés**, et un **bandeau prévient** quand un champ en cours de saisie a été modifié ailleurs (« Recharger » / « Garder ma saisie »). |
| D3 | Redémarrage | Chaque fenêtre rouvre **à sa position, sur son écran, sur la page de son onglet actif** à la fermeture. Les autres onglets ne sont pas restaurés (ils ne le sont pas non plus aujourd'hui). |
| D4 | Client web | « Ouvrir dans une nouvelle fenêtre » ouvre la page dans un **nouvel onglet du navigateur**. Pas de raccourci (Ctrl+Shift+N appartient au navigateur). Le lien direct vers une page doit y mener (il retombe aujourd'hui sur l'accueil). |

## Constat (code au 2026-11-12, `565e946`)

- Le main process ne porte pas d'état « projet courant » par fenêtre : les handlers IPC reçoivent
  `repoPath` / `workspaceDir`. Un container de services unique sert toutes les fenêtres.
- `repo:file-changed` est diffusé à toutes les fenêtres → les caches de l'autre fenêtre sont
  invalidés (`useLiveFileSync`).
- Une URL de page identifie entièrement ce qui est affiché (`projectId`, `repoPath`/`repo`,
  `node`, `type`, `view`, `item`…).
- Manques : instance unique et une seule fenêtre créée au démarrage ; au boot le renderer force
  `/` puis l'accueil redirige vers le dernier projet (pas d'ouverture directe sur une page) ;
  aucun menu contextuel d'onglet ; onglets non persistés ; aucune garde « non sauvegardé » à la
  fermeture de fenêtre ; pull automatique lancé par chaque fenêtre ; sortie du terminal et lien
  d'invitation diffusés à toutes les fenêtres ; dialogues natifs sans fenêtre parente ; la page
  d'édition d'une exigence / d'un test renvoie tous les champs à l'enregistrement.

## Comportement attendu

### 1. Ouvrir une nouvelle fenêtre (desktop)

- **Ctrl+Shift+N** (Cmd+Shift+N sur macOS) : nouvelle fenêtre sur la **page de l'onglet actif**
  (même projet, même composant, même vue, même élément). Sans projet ouvert : nouvelle fenêtre sur
  l'accueil.
- **Menu contextuel d'un onglet** (clic droit sur l'onglet, nouveau) :
  - « Ouvrir dans une nouvelle fenêtre » — nouvelle fenêtre sur la page de cet onglet (D1 : copie) ;
  - « Fermer l'onglet » — même chemin que la croix (garde « non sauvegardé » comprise).
- La nouvelle fenêtre s'ouvre décalée par rapport à la fenêtre d'origine (pas exactement
  par-dessus), à la même taille.
- Chaque fenêtre a ses propres onglets, son historique Précédent / Suivant, son panneau latéral
  actif et son titre. Naviguer dans une fenêtre ne change rien dans l'autre.
- Relancer l'exécutable (raccourci bureau) alors que Polenta est ouvert met la fenêtre existante au
  premier plan (comportement actuel, instance unique conservée) — il n'ouvre pas de fenêtre.

### 2. Données partagées entre fenêtres

- Une modification enregistrée dans une fenêtre (champ, statut, lien, déplacement dans l'arbre,
  schéma) apparaît dans l'autre sans action manuelle.
- Un changement de branche, un pull ou une publication dans une fenêtre se répercute dans l'autre
  (même dossier sur disque).
- Le **pull automatique** tourne une seule fois par projet, quel que soit le nombre de fenêtres.

### 3. Même élément édité dans les deux fenêtres (D2)

Éditeurs concernés : page d'une exigence (`/req/…`), page d'un test (`/test/…`), vue Édition de la
vue système (`EditView`).

- À l'enregistrement, seuls les champs modifiés dans cet éditeur (titre compris) sont envoyés : une
  modification faite ailleurs sur un **autre** champ n'est plus écrasée.
- Si un champ que l'utilisateur est en train de modifier (saisie non encore enregistrée) change
  ailleurs — autre fenêtre, pull, modification hors de l'application, MCP — un bandeau s'affiche
  dans l'éditeur : « Cet élément a été modifié ailleurs pendant votre saisie (<champs>). »
  - « Recharger » : abandonne la saisie de ces champs et affiche la nouvelle valeur ;
  - « Garder ma saisie » : ferme le bandeau ; l'enregistrement écrasera la valeur extérieure.
- Les champs qui ne sont pas en cours de saisie se mettent à jour sans bandeau.
- Hors périmètre : l'édition en place dans les cellules des vues Tableau / Document (saisie courte,
  enregistrée 800 ms après) et l'éditeur d'étapes d'un test (liste enregistrée en bloc) — la
  dernière écriture y gagne, comme aujourd'hui.

### 4. Fermeture

- Fermer une fenêtre alors qu'il en reste une autre ne quitte pas l'application.
- Fermer une fenêtre (ou quitter) alors qu'un de ses onglets a des modifications non sauvegardées
  demande confirmation (« Fermer quand même » / « Annuler »), comme la fermeture d'un onglet. Les
  saisies en attente d'enregistrement automatique sont enregistrées avant la fermeture.
- Fermer le projet dans une fenêtre (panneau Projet) ne ferme pas le projet dans l'autre.

### 5. Événements propres à une fenêtre

- **Terminal** (vue Version) : sa sortie n'est envoyée qu'à la fenêtre qui l'a ouvert.
- **Dialogues natifs** (ouvrir / enregistrer un fichier, choisir un dossier ou une image, export,
  feuille d'exécution) : rattachés à la fenêtre qui les demande (modaux sur elle, sur son écran).
- **Lien d'invitation `polenta://`** : traité par une seule fenêtre — la dernière fenêtre active —
  mise au premier plan.
- La mise à jour de l'application, le zoom et le thème restent communs à toutes les fenêtres
  (comportement actuel). L'installation d'une mise à jour signale déjà les autres fenêtres ouvertes.

### 6. Redémarrage (D3)

- À la fermeture de l'application, Polenta mémorise pour chaque fenêtre ouverte : position, taille,
  état maximisé / plein écran, et la page de son onglet actif.
- Au lancement suivant, il rouvre autant de fenêtres, chacune à sa place et sur sa page.
- Si l'écran d'une fenêtre n'existe plus (écran débranché, résolution changée), la fenêtre est
  replacée sur l'écran principal, entièrement visible.
- Si la page mémorisée n'est plus valide (projet fermé ou déplacé), la fenêtre suit le démarrage
  habituel (dernier projet ouvert ou accueil).
- Fermer une fenêtre secondaire en cours de session la retire de ce qui sera rouvert ; la
  disposition mémorisée est celle des fenêtres ouvertes au moment où l'application se ferme.
- Une seule fenêtre : la position et la taille sont désormais aussi mémorisées (aujourd'hui
  1280×800 à chaque lancement).

### 7. Client web (D4)

- Le menu contextuel d'onglet propose « Ouvrir dans une nouvelle fenêtre » : la page s'ouvre dans
  un nouvel onglet du navigateur (que l'utilisateur peut détacher sur l'autre écran). Pas de
  raccourci clavier.
- Une URL de page Polenta ouverte directement (nouvel onglet, favori, lien copié) affiche cette
  page, et non plus l'accueil puis le dernier projet.
- Deux onglets navigateur sur le même projet fonctionnent comme deux fenêtres desktop (§2, §3).
- Pas de garde à la fermeture d'un onglet navigateur au-delà de ce que le navigateur permet
  (`beforeunload` : message générique du navigateur) — appliquée si un onglet Polenta est non
  sauvegardé.

## Critères d'acceptation

- [ ] CA1 — Ctrl+Shift+N ouvre une seconde fenêtre sur la page de l'onglet actif (même composant,
      même vue, même élément).
- [ ] CA2 — Clic droit sur un onglet → « Ouvrir dans une nouvelle fenêtre » ouvre cette page dans
      une nouvelle fenêtre ; l'onglet reste dans la fenêtre d'origine.
- [ ] CA3 — Fenêtre 1 sur les exigences du composant A, fenêtre 2 sur celles du composant B :
      naviguer, changer de vue, ouvrir / fermer des onglets dans l'une ne change rien dans l'autre.
- [ ] CA4 — Une modification enregistrée dans une fenêtre apparaît dans l'autre en moins de
      3 s, sans action manuelle.
- [ ] CA5 — Exigence ouverte dans les deux fenêtres, champ X modifié et enregistré dans la fenêtre 1,
      champ Y modifié et enregistré dans la fenêtre 2 : les deux modifications sont conservées.
- [ ] CA6 — Même champ en cours de saisie dans la fenêtre 2 et enregistré dans la fenêtre 1 : le
      bandeau apparaît dans la fenêtre 2 ; « Recharger » affiche la valeur de la fenêtre 1,
      « Garder ma saisie » conserve la saisie et l'enregistre.
- [ ] CA7 — Fermer une fenêtre dont un onglet est non sauvegardé demande confirmation ; « Annuler »
      la garde ouverte.
- [ ] CA8 — La sortie d'un terminal n'arrive qu'à sa fenêtre ; un dialogue d'ouverture de fichier
      s'affiche devant la fenêtre qui l'a demandé.
- [ ] CA9 — Avec deux fenêtres ouvertes, un seul pull automatique par repo et par intervalle.
- [ ] CA10 — Deux fenêtres sur deux écrans, application fermée puis relancée : les deux fenêtres
      rouvrent sur leur écran, à leur taille, sur leur page.
- [ ] CA11 — Écran de la fenêtre 2 débranché entre deux lancements : la fenêtre 2 rouvre entièrement
      visible sur l'écran principal.
- [ ] CA12 — Web : « Ouvrir dans une nouvelle fenêtre » ouvre un nouvel onglet navigateur sur la
      même page ; coller l'URL d'une page dans un nouvel onglet affiche cette page.

## Hors périmètre

- Glisser un onglet hors de la fenêtre / entre fenêtres, déplacer un onglet (#343).
- Deux projets différents dans deux fenêtres (#343). Ouvrir un autre projet dans une fenêtre reste
  possible techniquement mais n'est ni testé ni garanti dans ce ticket.
- Restauration de tous les onglets au redémarrage (seule la page de l'onglet actif est rouverte).
- Conflits dans l'édition en place Tableau / Document, l'éditeur d'étapes d'un test et le
  rangement de l'arbre (fichier écrit en entier) : dernière écriture gagnante, comme aujourd'hui.
- Préférences d'affichage en `localStorage` (largeur du panneau, mode Tableau / Document par repo,
  dernière sélection…) : communes aux fenêtres, la dernière modifiée s'applique.
