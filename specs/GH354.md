# GH354 — Créer un repo sur le serveur : repo créé malgré l'échec d'ajout d'un membre, fenêtre bloquée

Type : bug. Issue #354.

## Constat

Assistant « Créer le repo sur le serveur » (projet ou composant) : l'ajout d'un membre échoue après
la création du repo. Le repo existe sur la forge, mais l'écran s'intitule « Création incomplète » :
l'utilisateur comprend que rien n'a été créé, ferme la fenêtre, et le repo reste orphelin (non
inscrit dans `polenta-repo.yaml` pour un composant).

Cas mesuré (commentaire de l'issue) : `SEB-lolive` ajouté avec le niveau Admin à un repo
**personnel** GitHub → 422. Ce refus-là est corrigé par GH356 (pas de niveau sur un repo personnel,
détail de `errors[]` affiché). Restait le reste du bug.

## Root cause

1. `RepoProvisioningService.create` ne validait que nom, description, branche et dossier avant
   `createRemote` : les membres n'étaient éprouvés qu'**après** création et push. Un login inconnu
   (ou une équipe absente, ou une équipe sur un repo personnel) produisait donc toujours un repo créé
   avec une étape `members` en échec.
2. `ProvisionResult` affichait « Création incomplète » dès qu'une étape était en échec, même quand
   le repo était publié et que « Continuer » était possible : l'écran présentait la création comme
   ratée.
3. `ForgeService.guard` marquait le compte « accès révoqué » sur tout 403 « not allowed », y compris
   le refus d'ajouter **un membre** — un refus qui ne dit rien du jeton.

## Correctif

- `ForgeProvider.userExists` (Forgejo `GET /api/v1/users/{login}`, GitHub `GET /users/{login}` ;
  404 → non ; GitHub : une organisation → non).
- `ForgeService.checkMembers(accountKey, owner, ownerKind, members)` : comptes existants, équipes
  présentes dans l'organisation (non vérifiées si la liste est illisible, ex. jeton GitHub sans
  `read:org`), ni équipe ni propriétaire sur un repo personnel. Tous les problèmes sont nommés dans
  une seule erreur « Membres à corriger (rien n'a été créé) : … ».
- `RepoProvisioningService.create` l'appelle avant `createRemote` ; `adoptEmpty` avant toute écriture.
- `guard(…, { revokeOnForbidden: false })` pour `grantMember` et `checkMembers` : un 403 donne un
  message lisible, sans marquer le compte révoqué (un 401 reste traité comme avant).
- `ProvisionResult` : repo publié et échec ensuite → titre « Repo créé, points à traiter », renvoi
  aux paramètres du repo, et en mode composant une ligne qui dit que « Continuer » inscrit le
  composant et que « Fermer » le laisse sur le serveur sans l'inscrire.

Hors périmètre : le principe « Polenta ne supprime jamais un repo distant » est inchangé.

Spec mise à jour : `SPEC-PROJECT-MANAGEMENT.md` §9.1 (MAJ GH354 dans `SPEC-INDEX.md`).

  illisibles ; 403 sur un membre sans révocation), `forge-repo-api.gh107.test.ts` (userExists

  refusé → aucun repo créé, rien d'écrit).
- e2e : `e2e-web/gh354-create-members.spec.ts` — compte inconnu refusé dans l'assistant sans repo
  créé, puis création après correction ; refus 403 après création → « Repo créé, points à
  traiter », « Continuer » ouvre le projet, le compte reste utilisable. API Forgejo simulée étendue
  (`GET /users/{login}`, logins `inconnu…` / `refuse…`).

## Comment vérifier à la main

1. Accueil → Créer un nouveau projet → Sur le serveur. Ajouter un membre au login inexistant →
   « Créer » : message rouge « Membres à corriger (rien n'a été créé) », aucun repo sur la forge.
   Retirer le membre → la création passe.
2. Structure → + Composant → « Créer le repo sur le serveur » sur GitHub, repo personnel, avec un
   membre existant : l'ajout réussit (GH356). Pour provoquer un refus après création (ex. compte
   qui a bloqué l'utilisateur, ou réseau coupé au bon moment), l'écran doit dire « Repo créé, points
   à traiter », expliquer « Continuer » / « Fermer », et « Continuer » remplit l'URL et la branche.
3. Après un tel refus, le compte n'apparaît pas déconnecté (pas de bannière de reconnexion).
