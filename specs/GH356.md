# GH356 — Membres : ajout refusé (HTTP 422) sur un repo personnel GitHub

## Constat

Assistant de création, compte GitHub `SEB-vpelissier`, repo **personnel** `SEB-vpelissier/Head`,
membre `SEB-lolive` au niveau **Administration** : étape « Ajout des membres » en échec,
« Le serveur github.com a refusé l'opération (HTTP 422 : Validation Failed) ». Le même ajout fait
sur github.com fonctionne (l'interface GitHub ne demande aucun niveau pour un repo personnel).

## Root cause

1. Sur un repo **personnel** GitHub, un collaborateur a toujours l'écriture : il n'y a pas de
   niveau. Le paramètre `permission` de `PUT /repos/{owner}/{repo}/collaborators/{login}` ne vaut
   que pour un repo d'organisation ; GitHub refuse `permission: admin` en 422 (constaté). Polenta
   proposait Lecture / Écriture / Administration et envoyait toujours `permission`.
2. Le message affiché ne donnait pas la raison : sur un 422, GitHub met `Validation Failed` dans
   `message` et le détail dans `errors[]`, que `extractMessage` (`forge-http.ts`) ignorait.

## Correctif

- `github.provider.ts` :
  - `repoDetails` rend `ownerKind` (`owner.type` : `User` → `user`, `Organization` → `org`) ;
  - `setCollaborator` lit le propriétaire du repo : repo personnel → `PUT` sans `permission`, et
    une invitation en attente n'est pas modifiée (pas de `PATCH` de niveau) ; propriétaire inconnu
    ou organisation → comportement inchangé ;
  - `listOwners` : le compte (repo personnel) porte `fixedCollaboratorLevel: 'write'`.
- `forge.service.ts` (`repoSettings`) : `fixedCollaboratorLevel: 'write'` pour un repo GitHub
  dont le propriétaire est un compte.
- Types : `ForgeOwner.fixedCollaboratorLevel`, `ForgeRepoDetails.ownerKind`,
  `RepoSettings.fixedCollaboratorLevel` (facultatifs).
- Interface — assistant (`RepoMembersEditor`, `AddRepoWizard`) et Paramètres du repo
  (`RepoSettingsModal`) : niveau imposé → aucun sélecteur de niveau (ajout ni ligne), niveau
  affiché en texte, mention « Écriture pour tout membre : seul niveau possible sur un repo
  personnel GitHub. » ; l'assistant ramène à ce niveau les membres ajoutés avant un changement
  de propriétaire.
- `forge-http.ts` : `forgeMessage` = `message` suivi du détail de `errors[]` (`message`, sinon
  `resource.field : code`), pour toutes les forges et tous les appels. Les tests sur
  `forgeMessage` (regex) restent valides.

Forgejo inchangé (les niveaux y sont acceptés sur un repo personnel).

## Tests

- `forge-repo-api.gh107.test.ts` : repo personnel → `PUT` avec corps `{}` même pour `admin`,
  invitation en attente sans `PATCH` ; organisation → `permission` envoyé ; 422 avec `errors[]`
  → détail dans le message ; `listOwners` porte le niveau imposé du compte.
- `repo-settings.gh108.test.ts` : `fixedCollaboratorLevel` présent pour un repo GitHub personnel,
  absent pour une organisation.
- `e2e-web/gh108-repo-settings.spec.ts` (GH356) : réponse `forge:repo-settings` simulée avec le
  niveau imposé → pas de sélecteur, mention affichée, ajout envoyé en `write`, ligne en
  « Écriture » sans sélecteur.

## Comment vérifier

1. Compte GitHub connecté, assistant « Créer un repo » avec le compte comme propriétaire : la
   section Membres n'a pas de sélecteur de niveau et affiche la mention. Ajouter un compte,
   créer : l'étape « Ajout des membres » réussit (invitation envoyée).
2. Paramètres du repo d'un repo personnel GitHub : mêmes constats ; l'ajout aboutit à une
   invitation.
3. Organisation GitHub ou Forgejo : sélecteur de niveau toujours présent, comportement inchangé.
