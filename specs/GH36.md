# GH36 — Campagnes : exécution hors outil via export Excel puis réimport des résultats

Issue : #36 — type : feature

## 1. Contexte et besoin

Certaines équipes ne veulent pas exécuter les campagnes de test dans Polenta. Le cycle visé :

1. **Exporter** une campagne dans un classeur Excel « à remplir » ;
2. les testeurs **remplissent** le classeur hors outil (verdicts, commentaires, testeur, date) ;
3. **importer** le classeur rempli : Polenta crée les `TestRun` correspondants et met à jour les
   instances de la campagne, **exactement comme une exécution saisie dans l'outil**
   (`tests.execute()` puis `campaigns.updateRun()`, cf. `campaign.$campaignId_.execute.$testId.tsx`).

Le classeur est au **format natif Polenta, fixe**, conçu pour le réimport. Il est indépendant du
moteur de gabarits client de #34. L'export xlsx existant (« cahier de campagne »,
`export/campaign.xlsx.ts`) n'est pas modifié.

## 2. Décisions de cadrage (validées avec l'humain)

| Sujet | Décision |
|-------|----------|
| Granularité | **Une ligne par étape**, précédée d'une ligne d'en-tête par instance (`entryId`) |
| Format | **Format natif fixe** — pas de gabarit client (#34) |
| Instance déjà exécutée | **Toujours écraser** : toute instance remplie dans le fichier produit un nouveau `TestRun` et remplace le statut de l'instance (comme une ré-exécution dans l'outil) |
| Testeur / date | **Colonnes dans l'Excel** (par instance) ; vides → utilisateur qui importe / date-heure de l'import |

## 3. Export « Exécution hors outil (Excel) »

### 3.1 Point d'entrée

Page campagne (`/campaign/$campaignId`) : nouvelle entrée dans les actions d'export
« Classeur d'exécution (Excel)… ». Nom de fichier proposé : `<CAMP-ID>_execution_<AAAA-MM-JJ>.xlsx`
(dialogue natif d'enregistrement, comme les autres exports).

Disponible quel que soit le statut de la campagne, sauf `completed` / `abandoned` (l'import y serait
refusé, cf. §4.4). L'export porte sur **toutes les instances** de la campagne (exécutées ou non).

### 3.2 Feuille « Exécution » (visible)

En-tête du classeur (lignes 1–3, non éditables) : ID et titre de la campagne, baseline éventuelle,
date d'export, rappel « Ne pas modifier les colonnes grisées ni la feuille _polenta ».

Puis un tableau, **un bloc par instance** dans l'ordre de `runs[]` :

**Ligne d'instance** (mise en forme distincte, fond coloré) :

| Colonne | Contenu | Éditable |
|---------|---------|----------|
| Instance | `entryId` (ex. `TEST-0042-2`) | non |
| Test | `testCaseId` — titre (du `testSnapshot`, sinon live) | non |
| Exigence | `requirementId` (instance T179), sinon vide | non |
| Paramètres | valeurs figées de l'instance `réf = valeur` (`resolvedParams` + `paramValues`), une par ligne | non |
| Statut actuel | statut de l'instance au moment de l'export (libellé) | non |
| Verdict global | liste déroulante `PASS / FAIL / BLOCKED / INCOMPLETE` — vide à l'export | **oui** |
| Testeur | texte libre — vide à l'export | **oui** |
| Date d'exécution | date (format date Excel) — vide à l'export | **oui** |
| Commentaire | notes globales du run — vide à l'export | **oui** |

**Lignes d'étape** (une par étape du test, ordre `order`) :

| Colonne | Contenu | Éditable |
|---------|---------|----------|
| N° | `order` | non |
| Action | texte de l'étape, paramètres substitués par les valeurs figées (§4.4 SPEC-TESTS) | non |
| Résultat attendu | idem | non |
| Verdict | liste déroulante `PASS / FAIL / BLOCKED / SKIP / NOT_EXECUTED` — vide à l'export | **oui** |
| Commentaire | commentaire d'étape — vide à l'export | **oui** |

Les préconditions et postconditions du test figurent en lecture seule sur la ligne d'instance
(colonne « Préconditions / Postconditions » ou commentaire de cellule — choix au design).

Le texte richtext (Markdown/HTML) est exporté **en texte brut** (mise en forme perdue, sauts de
ligne conservés, images/diagrammes remplacés par un repère `[image]` / `[diagramme]`).

Les listes déroulantes affichent les **libellés dans la langue de l'UI** (ex. « Passé », « Échoué »).

### 3.3 Protection et identification

- La feuille est **protégée sans mot de passe** : seules les cellules éditables (§3.2) sont
  déverrouillées. Filtrer reste autorisé ; trier suppose d'ôter la protection (Excel refuse le tri
  d'une plage contenant des cellules verrouillées) — sans effet sur l'import.
- Chaque ligne porte, dans une **colonne masquée**, sa clé technique : `entryId` (ligne d'instance)
  ou `entryId#order` (ligne d'étape). L'import identifie les lignes par cette clé, **jamais par leur
  position** — un tri ou un filtre fait par le testeur ne casse pas le réimport.
- Feuille **`_polenta` masquée** : version du format, `campaignId`, date d'export, et pour chaque
  instance `entryId`, `testCaseId`, nombre d'étapes et liste des `order`.

## 4. Import « Résultats d'exécution (Excel) »

### 4.1 Point d'entrée

Page campagne : action « Importer des résultats (Excel)… » → sélecteur natif de fichier `.xlsx`
→ **aperçu** (§4.3) → confirmation → écriture.

### 4.2 Lecture et validation

Une instance du fichier est **remplie** si son verdict global, ou au moins un verdict d'étape, est
renseigné. Une instance non remplie est **ignorée** (son état dans la campagne ne change pas) —
cela permet l'import partiel et l'import successif de plusieurs fichiers (un par testeur).

Pour une instance remplie :

- **Verdicts d'étape** : vide → `NOT_EXECUTED`.
- **Verdict global** : renseigné → utilisé tel quel (équivalent du forçage manuel dans l'outil) ;
  vide → calculé par la règle §3.3 SPEC-TESTS (FAIL > BLOCKED > INCOMPLETE > PASS).
- **Testeur** : renseigné → `executedBy` ; vide → identité git de l'utilisateur qui importe.
- **Date d'exécution** : cellule date Excel, ou texte `AAAA-MM-JJ` / `JJ/MM/AAAA` (heure optionnelle)
  → `executedAt` du run, de ses `stepResults` et de l'instance ; vide → date-heure de l'import.
- **Commentaires** : texte brut converti en richtext (un paragraphe par ligne, échappement HTML).
- Valeurs de verdict acceptées : codes (`PASS`, `FAIL`…) et libellés FR et EN, sans tenir compte de la
  casse ni des espaces en bord.

**Erreurs bloquantes pour tout le fichier** (rien n'est importé, message explicite) :

- fichier illisible, pas de feuille `_polenta`, version de format inconnue ;
- `campaignId` du fichier ≠ campagne ouverte ;
- campagne `completed` / `abandoned`.

**Erreurs propres à une instance** (l'instance est exclue, les autres restent importables) :

- `entryId` absent de la campagne (instance retirée depuis l'export) ;
- étapes du fichier ne correspondant pas à la liste des `order` attendus (ligne ajoutée, supprimée,
  clé masquée altérée) ;
- verdict non reconnu ; date illisible.

Les lignes sans clé technique (ajoutées par le testeur) sont ignorées et signalées en avertissement.

### 4.3 Aperçu avant écriture

Modale listant :

- les instances **qui seront importées** : `entryId`, test, verdict global résultant, testeur, date,
  avec la mention « remplace le résultat existant (<statut>) » quand l'instance n'est plus
  `pending` (décision « toujours écraser » : information, pas de case à décocher) ;
- les instances **en erreur** avec la raison ;
- les **avertissements** (lignes ignorées) ;
- le nombre d'instances non remplies (ignorées).

Boutons « Importer N résultats » (désactivé si N = 0) et « Annuler ».

### 4.4 Écriture

Pour chaque instance importée, dans l'ordre du fichier :

1. création d'un `TestRun` (même service que l'exécution dans l'outil) avec `stepResults`, `notes`,
   `result`, `executedBy`, `executedAt` issus du fichier, `requirementId` de l'instance (T179) ;
2. mise à jour de l'instance de campagne : `status` (mapping résultat → statut identique à l'UI),
   `runId`, `executedAt`, `executedBy` ;
3. la campagne passe `planned` → `in_progress` si besoin (règle existante).

Le `TestRun` porte en plus `origin: 'excel-import'` (nouveau champ optionnel ; absent = saisie dans
l'outil) pour distinguer l'origine d'un résultat. La relecture d'un run (`/campaign/…/run/…`)
affiche « Importé depuis Excel » quand ce champ est présent.

Comme une saisie dans l'outil, les fichiers sont modifiés dans le repo de travail et publiés par le
workflow habituel (« Publier ») — pas de commit automatique spécifique.

Une erreur d'écriture en cours de route arrête l'import ; le message indique les instances déjà
importées (les écritures précédentes ne sont pas annulées).

Après l'import : rafraîchissement de la page campagne, de la liste des campagnes et de la matrice
de traçabilité ; toast « N résultats importés ».

## 5. Critères d'acceptation

1. L'export d'une campagne de 3 instances (dont une paramétrée et une générée pour une exigence)
   produit un `.xlsx` qui s'ouvre sans réparation dans Excel, avec 3 lignes d'instance, une ligne par
   étape, les paramètres figés substitués et l'ID d'exigence affiché.
2. Seules les cellules Verdict global / Testeur / Date / Commentaire (instance) et Verdict /
   Commentaire (étape) sont modifiables ; les verdicts proposent une liste déroulante.
3. Fichier rempli pour 2 instances sur 3, réimporté : aperçu = 2 importées, 1 non remplie ; après
   confirmation, 2 `TestRun` créés dans `test-runs/<TEST-ID>/`, instances mises à jour, la 3ᵉ reste
   `pending`, la campagne passe `in_progress`.
4. Lignes triées / filtrées dans Excel avant réimport : même résultat qu'en 3.
5. Verdict global vide, étapes PASS / FAIL → run `FAIL`. Verdict global `PASS` forcé avec une étape
   FAIL → run `PASS`.
6. Testeur et date vides → `executedBy` = utilisateur git, `executedAt` = date de l'import. Renseignés
   → valeurs du fichier.
7. Réimporter le même fichier → mêmes instances signalées « remplace le résultat existant », un
   nouveau run est créé pour chacune.
8. Fichier d'une autre campagne → refus global, rien n'est écrit. Campagne clôturée → refus global.
9. Instance retirée de la campagne après l'export → listée en erreur, les autres sont importées.
10. Verdict « foo » sur une étape → instance en erreur avec la raison, les autres importées.
11. La couverture (matrice de traçabilité) reflète les runs importés, y compris la restriction à
    l'exigence pour une instance T179.
12. Libellés FR et EN de l'UI : un fichier exporté en FR se réimporte avec l'UI en EN, et inversement.

## 6. Hors scope

- Gabarit client pour ce classeur (#34) ; modification de l'export « cahier de campagne » existant.
- Saisie du **matériel utilisé** (`equipmentUsed`) — absente aussi de l'exécution dans l'outil.
- Modification des **valeurs de paramètres** (`paramValues`) via le fichier.
- Ajout d'instances ou de tests depuis le fichier.
- Export d'un sous-ensemble d'instances (le testeur filtre dans Excel ; l'import partiel couvre la
  répartition entre testeurs).
- Pièces jointes / images dans les commentaires (texte seul ; liens OneDrive collés en texte).
- Outil MCP d'import/export.
- Correction de `executedBy: 'TODO:current-user'` pour l'exécution dans l'outil (ticket séparé à
  ouvrir si souhaité).
- Durée d'exécution (`duration` reste 0).
