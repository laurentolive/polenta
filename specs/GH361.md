# GH361 — Serveur MCP : créer des dossiers dans les exigences et les tests

Issue : #361 — `type:feature`

## Contexte

Dans l'application, l'utilisateur range les exigences et les tests d'un type dans des dossiers
(arbre de la Vue Système, `.polenta/trees/<nœud>/<type>.yaml`). Le rangement est curaté (GH180) :
le fichier ne contient que les dossiers et les objets rangés, tout objet absent est affiché
« non classé » en fin de liste.

Le serveur MCP ne construit plus de `TreeService` depuis GH180 (`mcp-server/container.ts`) : un
agent peut créer des centaines d'exigences (`bulk_import_*`), elles arrivent toutes non classées,
et aucun outil ne permet de les ranger ni même de voir le rangement existant.

## Objectif

Un agent connecté au serveur MCP peut :

1. **lire** le rangement d'un type d'exigence ou de test ;
2. **créer des dossiers**, imbriqués, désignés par leur chemin ;
3. **ranger** des objets existants dans un dossier (ou les remettre en « non classé ») ;
4. **ranger dès la création** les objets d'un `bulk_import_requirements` / `bulk_import_tests`.

Décisions de l'humain (2026-11-16) : périmètre « créer + ranger », adressage par chemin,
nouvel outil de lecture dédié.

## Désignation d'un dossier : le chemin

- Un chemin est une chaîne de noms de dossiers séparés par `/`, de la racine du type vers le
  dossier : `"Sécurité/Batterie"`.
- Chaque segment est comparé après suppression des espaces de début et de fin ; la comparaison
  est exacte (sensible à la casse et aux accents), comme ce que l'utilisateur voit dans l'arbre.
- Chemin refusé (`FOLDER_PATH_INVALID`) : chaîne vide, segment vide (`"A//B"`, `"/A"`, `"A/"`).
- Seuls les dossiers comptent dans un chemin : un élément (objet) n'est jamais un segment, même
  si des objets ont des enfants dans l'arbre.
- Deux dossiers frères de même nom rendent le chemin ambigu : `FOLDER_AMBIGUOUS` (l'agent doit
  demander à l'utilisateur de lever le doublon dans l'application). Aucun dossier n'est choisi
  au hasard.
- Limite connue : un dossier dont le nom contient `/` n'est pas désignable par chemin (il est
  lisible par `get_tree`, mais ni créable ni utilisable comme cible).

## Outils

Les trois outils et le champ `folder` ne valent que pour les types de catégorie `requirement`
et `test`. Un autre type (campagne, issue, version, validation) → `TYPE_NOT_SUPPORTED`. Un
`objectTypeRef` inconnu → `TYPE_NOT_FOUND` (même convention que les autres outils).

L'arbre visé est **celui que l'application affiche pour ce type** : pour un type d'un
composant en repo séparé (mode workspace), le fichier d'arbre du repo de ce composant, comme
pour ses objets (`SchemaService.resolveComponentRepoPath`).

### `get_tree` (lecture)

Entrée : `{ objectTypeRef: string }`.

Sortie :

```ts
{
  objectTypeRef: string,
  root: TreeEntry[],            // rangement curaté, dans l'ordre de l'arbre
  unclassified: Array<{ id: string; title: string }>,   // objets non rangés, triés par ID
}
type TreeEntry =
  | { kind: 'folder'; name: string; path: string; children: TreeEntry[] }
  | { kind: 'item'; id: string; title: string; children: TreeEntry[] }
```

- `title` est le titre courant de l'objet (comme l'affichage, GH180/GH261).
- Un élément rangé dont l'objet n'existe plus apparaît avec son ID comme titre (même repli que
  l'application) ; il n'est pas retiré par la lecture.
- `path` d'un dossier dont le nom contient `/` : `null` (cf. limite ci-dessus).

### `create_folders`

Entrée : `{ objectTypeRef: string; paths: string[]; dryRun?: boolean }` — `dryRun` vaut `true`
par défaut, comme les autres outils d'écriture.

- Chaque chemin est créé de la racine vers la feuille : les dossiers intermédiaires manquants
  sont créés, ceux qui existent déjà sont réutilisés.
- Un chemin qui existe déjà entièrement n'est pas une erreur (opération idempotente).
- Un dossier créé est ajouté **à la fin** des enfants de son parent (à la racine : après le
  rangement existant, avant les objets non classés, qui ne sont pas stockés).
- Les chemins sont traités dans l'ordre ; un chemin en erreur n'empêche pas les autres.
  Toutes les créations valides donnent **une seule écriture** du fichier d'arbre.
- Sortie :
  ```ts
  { dryRun, created: string[] /* chemins créés, y compris intermédiaires */,
    existing: string[], errors: Array<{ index: number; path: string; reason: string }> }
  ```
  En `dryRun`, `created` liste ce qui serait créé, sans aucune écriture disque.

### `move_to_folder`

Entrée :
`{ objectTypeRef: string; moves: Array<{ id: string; folder: string | null }>; createMissing?: boolean; dryRun?: boolean }`

- `folder` : chemin du dossier cible ; `null` → l'objet est retiré du rangement et redevient
  « non classé ». Pour ranger un objet à la racine, `folder: ""` n'est **pas** accepté : un
  objet non classé est déjà affiché à la racine.
- `createMissing` (défaut `true`) : crée le dossier cible et ses parents s'ils manquent, comme
  `create_folders` ; `false` → `FOLDER_NOT_FOUND`.
- L'objet doit exister et être du type `objectTypeRef` (`OBJECT_NOT_FOUND` sinon).
- Objet déjà rangé une seule fois : son élément est déplacé **avec ses enfants** (sous-éléments
  rangés sous lui dans l'arbre), ajouté à la fin du dossier cible. Objet non classé : un élément
  est créé à la fin du dossier cible.
- Objet présent plusieurs fois dans l'arbre (copies) : `OBJECT_AMBIGUOUS`, rien n'est déplacé
  pour cet objet.
- Déplacer un objet dans le dossier où il est déjà : sans effet, pas d'erreur (`unchanged`).
- Mêmes règles de traitement que `create_folders` : dans l'ordre, best-effort par entrée, une
  seule écriture.
- Sortie :
  `{ dryRun, moved: Array<{ id; folder: string | null }>, unchanged: string[], createdFolders: string[], errors: Array<{ index; id; reason }> }`

### `bulk_import_requirements` / `bulk_import_tests` : champ `folder`

- Chaque entrée accepte un champ facultatif `folder?: string` (chemin), hors DTO de création :
  il ne s'écrit jamais dans le YAML de l'objet.
- `dryRun: true` : le chemin est validé (`FOLDER_PATH_INVALID`, `FOLDER_AMBIGUOUS`) comme une
  règle de plus de l'entrée ; la sortie indique en plus les dossiers qui seraient créés.
- `dryRun: false` : après la création de tous les objets, les objets créés avec un `folder`
  sont rangés en **une** écriture par fichier d'arbre (dossiers manquants créés), dans l'ordre
  des entrées. Un échec de rangement (arbre illisible, etc.) n'annule pas la création : l'objet
  reste non classé et l'erreur est reportée pour cette entrée (`FOLDER_PLACEMENT_FAILED`).
- Entrée sans `folder` : comportement actuel, l'objet reste non classé.

## Règles communes d'écriture

- Écriture refusée, sans rien écrire : branche en lecture seule (`READONLY_BRANCH`), repo en
  lecture seule ou nœud `readonly: true` (`READONLY_REPO`), comme les autres outils d'écriture.
- Le fichier d'arbre est écrit **par le `TreeService` de l'application** (même stockage
  curaté GH180 : pas de `name` sur les éléments, queue non classée non écrite). Le container
  MCP reconstruit donc un `TreeService` branché sur les index exigences/tests.
- Le serveur MCP ne commite rien (comme les autres outils) : les changements apparaissent dans
  l'application comme modifications locales.
- L'application ouverte sur le même repo recharge l'arbre modifié de l'extérieur
  (`useLiveFileSync`, fichiers `.polenta/trees/…`) : le rangement fait par l'agent s'y affiche
  sans réouverture.
- L'ID d'un dossier créé est un UUID (`TreeService.generateId`), comme dans l'application.
- `AGENTS.md` (gabarit `agents-md.template.ts`) présente les nouveaux outils et le champ
  `folder`, et rappelle de ne jamais éditer `.polenta/trees/` à la main.

## Critères d'acceptation

1. `get_tree` sur un type rangé dans l'application renvoie les mêmes dossiers, dans le même
   ordre, que l'arbre de la Vue Système, avec les objets non rangés dans `unclassified`.
2. `create_folders` avec `["Sécurité/Batterie", "Sécurité/Moteur"]` sur un type sans
   rangement crée 3 dossiers (`Sécurité`, `Sécurité/Batterie`, `Sécurité/Moteur`) en une écriture ;
   relancé à l'identique, il ne crée rien et renvoie les 3 chemins dans `existing`.
3. `dryRun` (défaut) de `create_folders`, `move_to_folder` et `bulk_import_*` avec `folder`
   ne modifie aucun fichier.
4. `move_to_folder` range un objet non classé dans un dossier ; `get_tree` le montre dans ce
   dossier et plus dans `unclassified`. Avec `folder: null`, il revient dans `unclassified`.
5. Un objet rangé avec des sous-éléments est déplacé avec eux.
6. `bulk_import_requirements` (`dryRun: false`) avec `folder` sur chaque entrée crée les objets
   et les range dans les dossiers indiqués ; le YAML des objets ne contient pas de `folder`.
7. Les erreurs `FOLDER_PATH_INVALID`, `FOLDER_AMBIGUOUS`, `FOLDER_NOT_FOUND`,
   `OBJECT_NOT_FOUND`, `OBJECT_AMBIGUOUS`, `TYPE_NOT_SUPPORTED`, `READONLY_REPO`,
   `READONLY_BRANCH` sont renvoyées par entrée (ou pour l'appel, pour les deux dernières), sans
   exception non catchée.
8. Le fichier d'arbre écrit par le serveur MCP est relu à l'identique par l'application
   (même format que celui écrit par la Vue Système) ; aucune écriture n'ajoute de `name` aux
   éléments ni la queue non classée.
9. L'application ouverte sur le repo affiche le nouveau rangement sans réouverture.
10. Type d'un composant en repo séparé : le fichier d'arbre écrit est celui du repo du
    composant, celui que l'application affiche.

## Hors périmètre

- Renommer, supprimer ou réordonner des dossiers ; réordonner des objets dans un dossier.
- Arbres des campagnes, issues, versions et validations.
- Déplacer un objet vers un autre type ou un autre nœud (changement d'`objectTypeRef`).
- Désigner un dossier par son identifiant.
- Fusion d'écritures concurrentes : si l'utilisateur modifie le rangement dans l'application
  pendant qu'un agent écrit, la dernière écriture l'emporte (limitation documentée,
  SPEC-MCP-SERVER §7).
