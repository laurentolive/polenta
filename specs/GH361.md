# GH361 — Serveur MCP : gérer les dossiers des exigences, des tests et des issues

Issue : #361 — `type:feature`

## Contexte

Dans l'application, l'utilisateur range les exigences, les tests et les issues d'un type dans
des dossiers (arbre de la barre latérale, `SystemPanel` / `ElementTree`, fichier
`.polenta/trees/<nœud>/<type>.yaml`). Le rangement est curaté (GH180) : le fichier ne contient
que les dossiers et les objets rangés, tout objet absent est affiché « non classé » en fin de
liste.

Le serveur MCP ne construit plus de `TreeService` depuis GH180 (`mcp-server/container.ts`) : un
agent peut créer des centaines d'exigences (`bulk_import_*`), elles arrivent toutes non classées,
et aucun outil ne permet de les ranger ni même de voir le rangement existant.

## Objectif

Un agent connecté au serveur MCP gère le rangement comme l'utilisateur dans l'application :

1. **lire** le rangement d'un type ;
2. **créer, renommer, déplacer, supprimer** des dossiers, désignés par leur chemin ;
3. **ranger** des objets existants dans un dossier, ou les remettre en « non classé » ;
4. **réordonner** le contenu d'un dossier (ou de la racine) ;
5. **ranger dès la création** les objets d'un `bulk_import_requirements` / `bulk_import_tests`.

Sans jamais écraser un rangement que l'utilisateur est en train de modifier dans l'application
(§ Verrou).

Décisions de l'humain (2026-11-16) :
- adressage par chemin ; outil de lecture dédié ;
- périmètre complet sur les dossiers (créer, ranger, renommer, déplacer, supprimer, réordonner) ;
- types couverts : exigences, tests, issues — les seuls qui ont un arbre de dossiers dans
  l'application. Les campagnes (liste plate) et les versions (écran dédié) n'en ont pas : leur
  ajouter des dossiers, dans l'application puis au MCP, fait l'objet d'une issue séparée ;
- concurrence : **verrou exclusif long** (l'arbre affiché dans l'application n'est pas
  modifiable par le MCP).

## Désignation d'un dossier : le chemin

- Un chemin est une chaîne de noms de dossiers séparés par `/`, de la racine du type vers le
  dossier : `"Sécurité/Batterie"`.
- Chaque segment est comparé après suppression des espaces de début et de fin ; la comparaison
  est exacte (sensible à la casse et aux accents), comme ce que l'utilisateur voit dans l'arbre.
- Chemin refusé (`FOLDER_PATH_INVALID`) : chaîne vide, segment vide (`"A//B"`, `"/A"`, `"A/"`).
  Un nom de dossier fourni seul (renommage) ne peut pas contenir `/` ni être vide.
- Seuls les dossiers comptent dans un chemin : un élément (objet) n'est jamais un segment, même
  si des objets ont des enfants dans l'arbre.
- Deux dossiers frères de même nom rendent le chemin ambigu : `FOLDER_AMBIGUOUS` (l'agent doit
  demander à l'utilisateur de lever le doublon dans l'application). Aucun dossier n'est choisi au
  hasard. Les outils du MCP ne créent jamais eux-mêmes un tel doublon (`FOLDER_EXISTS`).
- Limite connue : un dossier dont le nom contient `/` (créé dans l'application) n'est pas
  désignable par chemin ; il reste lisible par `get_tree` (`path: null`).

## Types couverts, arbre visé

- Types de catégorie `requirement`, `test` et `issue`. Autre catégorie (campagne, version,
  validation) → `TYPE_NOT_SUPPORTED`. `objectTypeRef` inconnu → `TYPE_NOT_FOUND`.
- L'arbre visé est **celui que l'application affiche pour ce type** : pour un type d'un
  composant en repo séparé (mode workspace), le fichier d'arbre du repo de ce composant, comme
  pour ses objets (`SchemaService.resolveComponentRepoPath`).

## Outils

Tous les outils d'écriture prennent `dryRun?: boolean`, `true` par défaut (aperçu sans écriture),
comme les autres outils d'écriture. Dans un appel à plusieurs entrées, les entrées sont traitées
dans l'ordre, une entrée en erreur n'empêche pas les autres, et toutes les modifications valides
donnent **une seule écriture** du fichier d'arbre.

### `get_tree` (lecture)

Entrée : `{ objectTypeRef: string }`. Autorisé même quand l'arbre est verrouillé.

Sortie :

```ts
{
  objectTypeRef: string,
  locked: null | { by: 'app'; user?: string; since: string },   // § Verrou
  root: TreeEntry[],            // rangement curaté, dans l'ordre de l'arbre
  unclassified: Array<{ id: string; title: string }>,           // objets non rangés, triés par ID
}
type TreeEntry =
  | { kind: 'folder'; name: string; path: string | null; children: TreeEntry[] }
  | { kind: 'item'; id: string; title: string; children: TreeEntry[] }
```

- `title` est le titre courant de l'objet (comme l'affichage, GH180/GH261).
- Un élément rangé dont l'objet n'existe plus apparaît avec son ID comme titre (même repli que
  l'application) ; la lecture ne le retire pas.

### `create_folders`

Entrée : `{ objectTypeRef; paths: string[]; dryRun? }`

- Chaque chemin est créé de la racine vers la feuille : dossiers intermédiaires manquants créés,
  existants réutilisés. Un chemin qui existe déjà entièrement n'est pas une erreur (idempotent).
- Un dossier créé est ajouté **à la fin** des enfants de son parent (à la racine : après le
  rangement existant, donc avant les objets non classés, qui ne sont pas stockés).
- Sortie : `{ dryRun, created: string[] /* intermédiaires compris */, existing: string[], errors }`

### `rename_folder`

Entrée : `{ objectTypeRef; renames: Array<{ path: string; name: string }>; dryRun? }`

- Renomme le dossier désigné ; son contenu et sa position ne changent pas.
- `FOLDER_NOT_FOUND` si le chemin n'existe pas ; `FOLDER_EXISTS` si un frère porte déjà `name` ;
  même nom qu'avant → `unchanged`.
- Les entrées suivantes du même appel voient le nouveau chemin.
- Sortie : `{ dryRun, renamed: Array<{ from: string; to: string }>, unchanged: string[], errors }`

### `move_folder`

Entrée : `{ objectTypeRef; moves: Array<{ path: string; parent: string | null }>; dryRun? }`

- Déplace le dossier, avec tout son contenu, à la fin du dossier `parent` (`null` = racine).
  `parent` doit exister (`FOLDER_NOT_FOUND`).
- Refus : `FOLDER_CYCLE` (dans lui-même ou un de ses descendants), `FOLDER_EXISTS` (un dossier de
  même nom existe déjà dans `parent`). Déjà dans `parent` → `unchanged`.
- Sortie : `{ dryRun, moved: Array<{ from: string; to: string }>, unchanged: string[], errors }`

### `delete_folders`

Entrée : `{ objectTypeRef; paths: string[]; recursive?: boolean; dryRun? }`

- Dossier vide : supprimé.
- Dossier non vide : `FOLDER_NOT_EMPTY` sauf `recursive: true` ; alors le dossier et ses
  sous-dossiers sont supprimés, et **les objets qu'ils contenaient redeviennent « non classés »**.
  Aucun objet n'est supprimé (comme la suppression de dossier dans l'application, qui ne retire
  que le rangement).
- Sortie : `{ dryRun, deleted: string[], unclassified: string[] /* IDs d'objets */, errors }`

### `move_to_folder`

Entrée :
`{ objectTypeRef; moves: Array<{ id: string; folder: string | null }>; createMissing?: boolean; dryRun? }`

- `folder` : chemin du dossier cible ; `null` → l'objet est retiré du rangement et redevient
  « non classé ». Pour placer un objet à un endroit précis de la racine, utiliser `reorder_tree`.
- `createMissing` (défaut `true`) : crée le dossier cible et ses parents s'ils manquent, comme
  `create_folders` ; `false` → `FOLDER_NOT_FOUND`.
- L'objet doit exister et être du type `objectTypeRef` (`OBJECT_NOT_FOUND` sinon).
- Objet rangé une seule fois : son élément est déplacé **avec ses enfants** (sous-éléments rangés
  sous lui), à la fin du dossier cible. Objet non classé : un élément est créé à la fin du
  dossier cible.
- Objet présent plusieurs fois dans l'arbre (copies) : `OBJECT_AMBIGUOUS`, rien n'est déplacé
  pour cet objet.
- Déjà dans le dossier cible → `unchanged`.
- Sortie : `{ dryRun, moved: Array<{ id; folder: string | null }>, unchanged: string[], createdFolders: string[], errors }`

### `reorder_tree`

Entrée :
`{ objectTypeRef; folder: string | null; order: Array<{ folder: string } | { id: string }>; dryRun? }`

- Réordonne les enfants directs de `folder` (`null` = racine). `order` cite des dossiers (par leur
  nom, enfants directs) et des objets (par leur ID) ; ils sont placés **en tête, dans cet ordre** ;
  les enfants non cités suivent, dans leur ordre actuel.
- Un objet cité qui n'est pas un enfant direct de `folder` → `NOT_A_CHILD` (pour le déplacer,
  `move_to_folder`). Exception : à la racine, un objet non classé peut être cité ; il devient alors
  rangé à la racine à la position demandée.
- Un dossier ou un objet cité deux fois → `DUPLICATE_ENTRY` ; rien n'est modifié pour cet appel.
- Sortie : `{ dryRun, order: TreeEntry[] /* enfants directs après réordonnancement, sans leurs enfants */, errors }`

### `bulk_import_requirements` / `bulk_import_tests` : champ `folder`

- Chaque entrée accepte un champ facultatif `folder?: string` (chemin), hors DTO de création :
  il ne s'écrit jamais dans le YAML de l'objet. (Pas d'outil d'import massif d'issues aujourd'hui :
  une issue créée par `create_issue` se range ensuite avec `move_to_folder`.)
- `dryRun: true` : le chemin est validé (`FOLDER_PATH_INVALID`, `FOLDER_AMBIGUOUS`) comme une
  règle de plus de l'entrée, et le verrou est signalé (§ Verrou) ; la sortie indique en plus les
  dossiers qui seraient créés.
- `dryRun: false` : après la création des objets, les objets créés avec un `folder` sont rangés
  en **une** écriture par fichier d'arbre (dossiers manquants créés), dans l'ordre des entrées.
  Un échec de rangement (arbre verrouillé, fichier illisible…) n'annule pas la création : l'objet
  reste non classé et l'erreur est reportée pour l'entrée (`FOLDER_PLACEMENT_FAILED`, avec la
  cause, ex. `TREE_LOCKED`).
- Entrée sans `folder` : comportement actuel, l'objet reste non classé.

## Verrou

But : un agent ne doit jamais écraser un rangement que l'utilisateur a sous les yeux. Aujourd'hui
l'application garde l'arbre en mémoire et l'enregistre en entier à chaque action : une écriture
du MCP entre deux actions de l'utilisateur serait perdue silencieusement.

**Verrou de l'application (long).**
- Tant que l'application **affiche en édition** l'arbre d'un type (barre latérale Exigences /
  Tests / Issues, ce type sélectionné), elle détient le verrou de cet arbre (repo + nœud + type).
  Elle le libère quand l'utilisateur sélectionne un autre type ou un autre onglet, change de
  projet, ou ferme l'application.
- Un affichage en lecture seule de l'arbre (sélecteur de tests d'une campagne, impression) ne
  verrouille pas.
- Plusieurs fenêtres ou vues sur le même arbre dans l'application : le verrou reste tenu tant
  qu'au moins une l'affiche.
- Tout outil d'écriture du MCP sur un arbre verrouillé est refusé, sans rien écrire :
  `TREE_LOCKED`, avec un message qui dit à l'agent de demander à l'utilisateur de quitter ce type
  dans l'application (ou d'afficher un autre type) puis de réessayer. En `dryRun`, l'aperçu est
  calculé normalement et le verrou est signalé (`locked`), pour que l'agent prévienne avant
  d'écrire.
- `get_tree` reste autorisé et indique le verrou (`locked`).

**Verrou du MCP (court).**
- Une écriture du MCP (lecture, modification, écriture du fichier) se fait sous verrou : pendant
  ce temps, l'application ne peut pas prendre le verrou de cet arbre. Elle attend la fin de
  l'écriture (quelques dizaines de millisecondes) puis charge l'arbre à jour avant de l'afficher.
- Deux écritures MCP simultanées sur le même arbre (deux agents) se sérialisent : la seconde
  attend la première (délai max 5 s, puis `TREE_LOCKED`).

**Propriétés.**
- Le verrou ne vit dans aucun fichier versionné : il n'apparaît jamais dans `git status`, un
  commit ou une fusion.
- Un verrou laissé par un processus disparu (application plantée, agent tué) est ignoré : il ne
  bloque jamais durablement.
- Le verrou vaut pour un clone sur un poste : le client web et un autre poste travaillent sur
  d'autres clones, leurs conflits relèvent de la fusion git, comme aujourd'hui.

## Règles communes d'écriture

- Écriture refusée, sans rien écrire : branche en lecture seule (`READONLY_BRANCH`), repo en
  lecture seule ou nœud `readonly: true` (`READONLY_REPO`), arbre verrouillé (`TREE_LOCKED`).
- Le fichier d'arbre est écrit **par le `TreeService` de l'application** (stockage curaté GH180 :
  pas de `name` sur les éléments, queue non classée non écrite). Le container MCP reconstruit
  donc un `TreeService` branché sur les index exigences / tests / issues.
- Le serveur MCP ne commite rien (comme les autres outils) : les changements apparaissent dans
  l'application comme modifications locales.
- Quand l'utilisateur affiche ensuite le type dans l'application, il voit le rangement fait par
  l'agent (l'arbre est relu à la prise du verrou).
- L'ID d'un dossier créé est un UUID (`TreeService.generateId`), comme dans l'application.
- `AGENTS.md` (gabarit `agents-md.template.ts`) présente les nouveaux outils, le champ `folder`
  et le verrou (`TREE_LOCKED` : demander à l'utilisateur), et rappelle de ne jamais éditer
  `.polenta/trees/` à la main.

## Critères d'acceptation

1. `get_tree` sur un type rangé dans l'application renvoie les mêmes dossiers, dans le même
   ordre, que l'arbre de la barre latérale, avec les objets non rangés dans `unclassified` ; vaut
   pour un type d'exigence, de test et d'issue.
2. `create_folders` avec `["Sécurité/Batterie", "Sécurité/Moteur"]` sur un type sans rangement
   crée 3 dossiers en une écriture ; relancé à l'identique, il ne crée rien et renvoie les 2
   chemins demandés dans `existing`.
3. `rename_folder`, `move_folder`, `delete_folders`, `move_to_folder`, `reorder_tree` produisent
   l'arbre décrit ci-dessus, vérifié par `get_tree` et par l'affichage de l'application ; les
   refus (`FOLDER_EXISTS`, `FOLDER_CYCLE`, `FOLDER_NOT_EMPTY`, `NOT_A_CHILD`, `DUPLICATE_ENTRY`,
   `OBJECT_AMBIGUOUS`…) ne modifient rien pour l'entrée concernée.
4. `delete_folders` avec `recursive: true` ne supprime aucun objet : ses objets apparaissent
   dans `unclassified`.
5. `dryRun` (défaut) de chaque outil d'écriture et de `bulk_import_*` avec `folder` ne modifie
   aucun fichier.
6. `bulk_import_requirements` (`dryRun: false`) avec `folder` sur chaque entrée crée les objets
   et les range dans les dossiers indiqués ; le YAML des objets ne contient pas de `folder`.
7. Application ouverte, type T affiché dans la barre latérale : toute écriture MCP sur T est
   refusée (`TREE_LOCKED`) et le fichier d'arbre est inchangé ; sur un autre type, elle passe.
   L'utilisateur quitte T : l'écriture suivante passe. Il revient sur T : il voit le rangement de
   l'agent.
8. Application tuée pendant qu'elle affiche T : l'écriture MCP suivante sur T passe (verrou
   périmé ignoré).
9. Pendant une écriture MCP sur T, l'application qui affiche T attend la fin de l'écriture et
   affiche l'arbre à jour ; aucune action de l'utilisateur n'écrase l'écriture du MCP.
10. Le verrou n'apparaît dans aucun fichier suivi par git (`git status` propre après un cycle
    prise / libération).
11. Le fichier d'arbre écrit par le serveur MCP est relu à l'identique par l'application ; aucune
    écriture n'ajoute de `name` aux éléments ni la queue non classée.
12. Type d'un composant en repo séparé : le fichier d'arbre écrit (et le verrou) est celui du repo
    du composant, celui que l'application affiche.
13. Toutes les erreurs sont renvoyées par entrée (ou pour l'appel : `READONLY_*`, `TREE_LOCKED`,
    `TYPE_*`), sans exception non catchée (SPEC-MCP-SERVER §6).

## Hors périmètre

- Dossiers des campagnes et des versions (issue séparée, à créer : d'abord dans l'application).
- Déplacer un objet vers un autre type ou un autre nœud (changement d'`objectTypeRef`).
- Désigner un dossier par son identifiant.
- Verrou entre postes ou entre clones (client web) : relève de la fusion git.
- Réappliquer automatiquement une action refusée.
