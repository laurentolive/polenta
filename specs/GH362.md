# GH362 — MCP : créer, alimenter et changer le statut des versions et des validations

Issue : #362 — type:feature.

## 1. Contexte

Le serveur MCP ne fait aujourd'hui que **lire** les versions (`list_versions`, `get_version`,
`get_version_backlog`, `get_version_impact`, `get_version_tests` — GH201 §8, GH245) et, pour les
validations, lire et **proposer** une décision (`list_validations`, `get_validation`,
`propose_validation_decision` — GH204 §8, GH191 Q6).

Les services (`VersionsService`, `ValidationsService`) offrent déjà toutes les écritures utilisées par
l'UI, avec leurs contrôles. Le ticket les expose au MCP.

### Décisions de l'humain (2026-11-16)

- **Versions : tout, release compris.** Le MCP crée, alimente, change le statut et passe une version
  *released* (gel `freeze` + tag git annoté). Revient sur GH201 §8.
- **Validations : tout sauf signer.** Le MCP crée une validation, décide directement, confirme ou rejette
  une proposition, modifie et annule. La **signature reste un geste humain** dans la vue Validation.
  Revient en partie sur GH204 §8 / GH191 Q6.

## 2. Principes communs

- Paramètre `component` comme les outils existants (nom du repo dans le workspace ; absent = repo ouvert).
- Chaque outil appelle la méthode de service utilisée par l'IPC : **mêmes contrôles, mêmes erreurs**
  (`VersionError` / `ValidationError`), aucune règle dupliquée dans le MCP.
- Erreur métier attendue → `{ isError: true }` avec `code` et détail (SPEC-MCP-SERVER §6) ; en particulier
  `READONLY_REPO` sur un composant en lecture seule, `VERSION_LOCKED` / `VALIDATION_LOCKED` sur un objet figé.
- Écritures avec `source: mcp` dans `history` (acteur `--user`, sinon `local`), comme les autres écritures MCP.
- Processus sans watcher : chaque outil relit le disque (pas de cache périmé entre deux appels).
- Résultat : l'objet écrit (version ou validation), au même format que `get_version` / `get_validation`
  quand c'est utile à l'agent pour enchaîner.

## 3. Versions — nouveaux outils

| Outil | Service | Comportement |
|---|---|---|
| `create_version` | `create` | `title` (label, unique), `basedOn?`, `components?` (`{ dépendance: VER-ID }`), `fields?`. Statut initial du type. |
| `copy_version` | `copy` | Nouvelle version en cours à partir d'une existante (comme le bouton de l'UI). |
| `update_version` | `update` | `title?`, `basedOn?`, `components?`, `fields?` (fusion), `status?`. Statut vers un statut *released* refusé (`RELEASE_REQUIRED` → utiliser `release_version`). Une released ne peut que passer abandonnée ; une abandonnée ne revient pas. |
| `include_in_version` | `include` | `elementIds[]` : exigences / tests du repo ajoutés aux changements (base calculée par le service). `NOT_OWN_ELEMENT` hors du composant. |
| `remove_from_version` | `removeChanges` | `elementIds[]` retirés des changements. |
| `set_version_impact` | `setImpact` | `elementId`, `status` parmi les statuts d'analyse d'impact, `comment?`. Version en cours uniquement. Revient sur « pas d'écriture des statuts d'impact par le MCP » (SPEC-MCP-SERVER §4.8). |
| `get_version_release_preview` | `releasePreview` | Lecture : tag suggéré et problèmes bloquants (`tag?` pour tester un tag). |
| `release_version` | `release` | `tag?` (défaut : tag suggéré). Mêmes contrôles que l'UI : tag valide et libre, version en cours, composants released, pas de changement non commité (`DIRTY_CHANGES`). Gel `freeze { tag, sha }`, commit du seul fichier, tag annoté poussé au prochain push du repo. Irréversible. |

La description de `release_version` dit explicitement qu'elle est irréversible et invite à appeler
`get_version_release_preview` d'abord.

## 4. Validations — nouveaux outils

| Outil | Service | Comportement |
|---|---|---|
| `create_validation` | `create` | `versionId`, `title` (obligatoire, `TITLE_EMPTY`), `fields?` (même DTO que l'IPC). Reprend les décisions de la validation signée de `basedOn`. Refus `VALIDATION_EXISTS` si une validation non annulée existe déjà pour la version, `VERSION_ABANDONED` sur une version abandonnée. |
| `update_validation` | `update` | `title?`, `fields?`. Validation en cours uniquement. |
| `decide_validation` | `decide` | `requirementId`, `decision`, `comment?`, `fields?`. Décision **confirmée** directement (`decidedBy`, `decidedAt`) ; confirme aussi une proposition ; la valeur « en attente » retire l'entrée. |
| `confirm_validation_decision` | `confirm` | Confirme telle quelle une décision proposée ou « à revoir ». |
| `reject_validation_decision` | `reject` | Rejette une proposition (l'exigence repasse en attente). `NOT_PROPOSED` sinon. |
| `cancel_validation` | `cancel` | Passe la validation au statut terminal, depuis en cours ou signée. |

`propose_validation_decision` est conservé (un agent peut toujours préférer proposer).

**Pas de signature** : aucun outil n'appelle `sign`. `update_validation` ne prend pas de `status`
(le statut ne change que par `cancel_validation`), ce qui ferme toute voie de contournement vers le
statut d'approbation.

Une décision prise par le MCP porte `decidedBy` = acteur MCP (`--user`) ; aucun marqueur
supplémentaire dans l'entrée. L'humain qui signe voit toutes les décisions dans la vue et les contrôles
de signature (`signatureProblems`) s'appliquent sans changement.

## 5. Critères d'acceptation

1. Par le MCP seul, sur le projet de démo : créer une version, y inclure deux exigences, en retirer une,
   renseigner un statut d'impact, puis la passer released ; le fichier `versions/<ID>.yaml` porte `freeze`
   et le tag existe dans le repo.
2. `update_version` vers un statut released → `RELEASE_REQUIRED` ; toute modification d'une version
   released (hors passage abandonnée) → `VERSION_LOCKED`.
3. `release_version` avec un changement non commité → `DIRTY_CHANGES`, rien n'est écrit, aucun tag.
4. Par le MCP seul : créer une validation de la version released, décider sur toutes les exigences,
   rejeter puis confirmer une proposition ; `get_validation` n'affiche plus de décision restante.
5. Aucun outil MCP ne permet d'atteindre le statut d'approbation d'une validation.
6. Écriture sur un composant en lecture seule → `READONLY_REPO`, pour chaque outil d'écriture.
7. Les écritures MCP apparaissent dans `history` avec `source: mcp` (statut des versions et validations).
8. Les nouveaux outils sont listés dans `AGENTS.md` (gabarit régénéré) et décrits dans SPEC-MCP-SERVER.

## 6. Hors scope

- Signature d'une validation par le MCP (décision humaine du 2026-11-16).
- Suppression de version ou de validation par le MCP (`delete`).
- Client web : channels `versions:*` / `validations:*` toujours masqués (SPEC-WEB §11) — sans lien avec ce ticket.
- Aucun changement de modèle de données ni d'UI.
