# GH365 — Ajout d'un composant : tous les types de documents par défaut, nom et préfixe tirés du label affiché

Issue : #365 (`type:feature`). Décisions de l'humain du 2026-11-16 (portée « partout », préfixe sans
accents ni ponctuation).

## Contexte

La fenêtre `AddDependencyModal` (onglet Structure, « + Composant ») propose trois cases « Types
d'objets créés par défaut », cochées : Exigences, Tests, Campagnes. Les catégories `issue` (GH244),
`version` (GH201) et `validation` (GH204) ne sont pas proposées : il faut les ajouter ensuite une par
une avec « + ».

Le nom et le préfixe d'un type proposé sont formés par `emptyObjType` (`objectTypeEditor.tsx`) à
partir du **nom technique** du composant (nom de montage ou `SystemNode.name`) :
`comp-motor-control` → `COMP_MOTOR_CONTROL_REQ`. Les accents sont aujourd'hui remplacés par `_`
(`contrôle` → `CONTR_LE`).

## Comportement attendu

### 1. Cases « Types d'objets créés par défaut »

À l'ajout d'un **composant** (pas d'une interface, pas en édition) :

| Catégorie | Composant en repo séparé | Composant local |
|-----------|--------------------------|-----------------|
| Exigences | proposée, cochée | proposée, cochée |
| Tests | proposée, cochée | proposée, cochée |
| Campagnes | proposée, cochée | proposée, cochée |
| Issues | proposée, cochée | proposée, cochée |
| Versions | proposée, cochée | **non proposée** |
| Validations | proposée, cochée | **non proposée** |

Version et validation sont limitées à un type par repo, sur `root` (`VERSION_TYPE_INVALID`,
`VALIDATION_TYPE_INVALID`) : un composant local ne peut pas en porter. Cocher « Composant local »
masque ces deux cases (leur état n'est pas pris en compte) ; le décocher les ré-affiche avec l'état
qu'elles avaient.

L'ordre des types créés suit l'ordre du tableau. Le type `issue` apporte le type de lien
`issue-impact` s'il manque (comportement existant de l'enregistrement du schéma, GH244).

Inchangé : un repo séparé dont le `root` a déjà des types n'est pas amorcé (ses types sont gardés
tels quels) ; une interface n'est jamais amorcée.

### 2. Nom et préfixe des types proposés

Racine = **label affiché** du composant, ou à défaut son nom technique (label vide) :

1. accents retirés (décomposition Unicode, diacritiques supprimés : `Ô` → `O`, `é` → `E`, `ç` → `C` ;
   lettres non décomposables translittérées : `Œ` → `OE`, `Æ` → `AE`, `ß` → `SS`, `Ø` → `O`, `Ł` → `L`…) ;
2. majuscules ;
3. espaces et tout caractère hors `A-Z0-9` remplacés par `_`, suites de `_` réduites à un seul,
   `_` de début et de fin retirés.

Nom = préfixe = `<RACINE>_<SUFFIXE>`, suffixe inchangé (`REQ`, `TEST`, `CAMP`, `ISS`, `VER`, `VAL`).

| Label | Nom de montage | Exigence |
|-------|----------------|----------|
| `Contrôle moteur` | `comp-motor-control` | `CONTROLE_MOTEUR_REQ` |
| `Contrôle moteur v2.1` | — | `CONTROLE_MOTEUR_V2_1_REQ` |
| *(vide)* | `comp-motor-control` | `COMP_MOTOR_CONTROL_REQ` |
| `Œil — capteur` | — | `OEIL_CAPTEUR_REQ` (ligature `Œ` → `OE`) |
| `电机` ou `电机 2` | `motor` | `MOTOR_REQ` (repli sur le nom si la racine du label ne commence pas par une lettre) |

**Collision** : si un nom ou un préfixe proposé est déjà pris (préfixe d'un autre type du workspace,
nom d'un autre type du même nœud), le premier suffixe numérique libre est ajouté après la catégorie (`MOTEUR_REQ_2`, `_3`…),
comme pour « + élément » (GH97). C'est désormais vrai aussi à l'ajout d'un composant (deux composants
de même label ne produisent plus deux préfixes identiques, qui faisaient échouer l'enregistrement).

### 3. Portée : partout où un type est proposé

La même règle s'applique à « + Exigence / + Test / + Campagne / + Issue / + Version / + Validation »
sur un composant existant :
- ligne d'un composant local : label du `SystemNode`, repli sur son nom ;
- ligne d'un repo : label du nœud `root` de son schéma, repli sur le nom de montage.

Les types déjà existants ne sont **pas** renommés (renommer un type reste une action explicite,
GH100). Le nom et le préfixe proposés restent modifiables dans la fenêtre de configuration du type.

## Critères d'acceptation

1. Ajout d'un composant en repo séparé neuf, toutes cases laissées cochées, label « Contrôle moteur » :
   son `root` reçoit 6 types, `CONTROLE_MOTEUR_REQ`, `_TEST`, `_CAMP`, `_ISS`, `_VER`, `_VAL`
   (nom = préfixe), et le type de lien `issue-impact`.
2. Ajout d'un composant local, cases cochées : 4 types (REQ, TEST, CAMP, ISS), aucun VER/VAL,
   enregistrement sans erreur.
3. Cases décochées : seuls les types cochés sont créés ; tout décoché → aucun type.
4. Label vide : racine = nom de montage (comportement actuel).
5. Deux composants locaux de label « Moteur » : le second reçoit `MOTEUR_REQ_2`, `MOTEUR_TEST_2`…
   (règle GH97 : suffixe numérique après la catégorie), sans erreur de préfixe dupliqué.
6. « + Exigence » sur un composant local de label « Contrôle moteur » propose `CONTROLE_MOTEUR_REQ`
   (ou `CONTROLE_MOTEUR_REQ_2` s'il existe déjà).
7. « + Exigence » sur la ligne d'un repo dont le `root` a le label « Aspirateur V1 » propose
   `ASPIRATEUR_V1_REQ`.
8. Interface ajoutée : aucun type créé (inchangé).

## Hors scope

- Renommage des types existants dont le préfixe suit encore l'ancienne règle.
- Outil MCP `add_component` (n'amorce aucun type aujourd'hui ; inchangé).
- Changement du nom de montage proposé à partir du label.
