# GH368 — Membres d'un repo : complétion du login sur les membres des organisations de l'utilisateur

## Contexte

Quand on ajoute des membres à un repo depuis Polenta, le login se tape à la main. Le besoin est
d'avoir des suggestions pendant la saisie, comme sur GitHub.

### Existant (code, 2026-11-16)

| Écran | Champ login | Suggestions |
|---|---|---|
| Assistant « Créer un repo », section Membres (`RepoMembersEditor`, GH107) | saisie libre | **aucune** (seules les équipes sont proposées, dans une liste déroulante) |
| Paramètres du repo, section Membres (`RepoSettingsModal`, GH108) | saisie libre + `datalist` native | membres de l'**organisation propriétaire** du repo (`RepoSettings.orgMembers`) ; liste **vide** pour un repo personnel |

La spec GH103 §2.2 prévoyait pourtant « le même widget qu'au §3.2 » dans les deux écrans : les
deux écrans divergent aujourd'hui.

Données déjà lues sur les forges :
- organisations de l'utilisateur : `listOwners` (Forgejo `GET /user/orgs` ; GitHub
  `GET /user/memberships/orgs`, ou `GET /user/orgs` sans le scope `read:org`) ;
- membres d'une organisation : `orgMembers` (Forgejo `GET /orgs/{org}/members`, avec le nom
  affiché `full_name` ; GitHub `GET /orgs/{org}/members`, login seul).

### Décision (humain, 2026-11-16)

Les suggestions portent **uniquement sur les membres des organisations dont l'utilisateur est
membre** sur ce serveur. Pas de recherche dans l'annuaire complet du serveur (GitHub
`/search/users`, Forgejo `/users/search`) : sur une forge multi-clients, elle montrerait à un
client les comptes des autres clients.

## 1. Comportement

### 1.1 Où

Le champ « login » des collaborateurs, dans les **deux** écrans :
- assistant de création d'un repo (accueil et ajout d'un composant), section Membres ;
- Paramètres du repo, section Membres.

Les deux écrans utilisent le même champ et le même comportement. La `datalist` des Paramètres est
remplacée.

### 1.2 Source des suggestions

- **Compte** : le compte connecté utilisé pour l'opération, c'est-à-dire le compte choisi dans
  l'assistant, ou le compte qui donne accès au repo dans les Paramètres.
- **Personnes proposées** : l'union des membres de **toutes les organisations de ce compte** sur ce
  serveur, sans doublon (comparaison du login sans tenir compte de la casse).
- **Exclus** :
  - le compte de l'utilisateur lui-même ;
  - les personnes déjà présentes dans la liste des membres de l'écran : membres déjà ajoutés dans
    l'assistant, ou collaborateurs et invitations en attente dans les Paramètres.
- **Aucune organisation** (compte sans organisation) : aucune suggestion, la saisie libre reste
  possible. Rien ne signale l'absence de suggestions.

### 1.3 Affichage d'une suggestion

Chaque suggestion montre :
- le **login** ;
- le **nom affiché**, s'il est connu et différent du login. Forgejo le fournit ; GitHub ne le donne
  pas dans la liste des membres et Polenta ne fait pas d'appel par personne pour l'obtenir ;
- les **organisations** de la personne, en petit (ex. « acme, beta »). Cela permet de distinguer
  deux personnes au nom proche.

### 1.4 Ordre et filtre

- La liste s'ouvre dès le **premier caractère** saisi. Champ vide : pas de liste.
- **Filtre** : le texte saisi est cherché, sans tenir compte de la casse ni des accents, dans le
  login et dans le nom affiché. Un mot trouvé n'importe où dans le login ou le nom suffit (pas
  seulement au début).
- **Ordre** :
  1. membres de l'**organisation propriétaire** du repo (si le propriétaire est une organisation) ;
  2. les autres ;
  3. dans chaque groupe : d'abord les logins qui **commencent** par le texte saisi, puis l'ordre
     alphabétique du login.
- **Maximum 8 suggestions** affichées. Au-delà, la saisie de caractères supplémentaires affine la
  liste ; la liste n'est pas défilante.
- Aucun résultat : la liste se ferme, aucun message.

### 1.5 Interaction

- **Clavier** :
  - `↓` / `↑` déplacent la sélection dans la liste ;
  - `Entrée` ajoute la suggestion sélectionnée, ou le texte saisi s'il n'y a pas de sélection ;
  - `Échap` ferme la liste sans vider le champ. Un second `Échap` garde le comportement actuel de
    la fenêtre.
- **Souris** : un clic sur une suggestion l'ajoute.
- **Ajout** : il se fait au niveau choisi dans le sélecteur de niveau, ou au niveau imposé
  (GH356). Le champ se vide ensuite et la liste se ferme. Dans les Paramètres, l'ajout appelle la
  forge immédiatement, comme le bouton « Ajouter » aujourd'hui ; dans l'assistant, il ajoute une
  ligne à la liste des membres demandés.
- **Saisie libre** : elle reste acceptée. Un login qui n'est dans aucune organisation, par exemple
  un collaborateur externe, s'ajoute comme aujourd'hui. Un login inconnu du serveur est refusé à
  l'application par la forge, avec le message existant (`UnknownAccountError`).
- **Accessibilité** : le champ suit le motif ARIA *combobox* (`role="combobox"`,
  `aria-expanded`, `aria-activedescendant`, liste en `role="listbox"`, options en
  `role="option"`), utilisable au clavier seul.

### 1.6 Chargement

- La liste est **chargée une fois** à l'ouverture de l'écran, pour le compte utilisé. Elle n'est
  pas rechargée à chaque frappe : il n'y a ni appel réseau pendant la saisie, ni limite de débit.
- **Cache** : la liste est gardée en mémoire par compte pendant la session de l'application. Dans
  l'assistant, un changement de propriétaire ne la recharge pas : seul l'ordre change (§1.4).
  Dans l'assistant, changer de compte charge la liste de ce compte.
- **Pendant le chargement** : le champ est utilisable, sans suggestion. Les suggestions
  apparaissent dès que la liste est arrivée.
- **Échec**, que ce soit hors ligne, une forge injoignable ou un droit refusé sur une
  organisation : l'organisation en échec est ignorée, les autres sont proposées. Si tout échoue,
  il n'y a aucune suggestion. Aucun message d'erreur : la saisie libre suffit. Un échec n'est pas
  mis en cache.

### 1.7 Cas propres aux forges

- **GitHub sans le scope `read:org`** : la liste des organisations vient de `GET /user/orgs`, qui
  ne donne que les organisations où l'appartenance est **publique**. Les membres listés peuvent se
  limiter aux membres publics. Les suggestions sont alors partielles, sans message. La reconnexion
  proposée par les Paramètres pour les équipes (GH108, `scopeMissing`) couvre déjà ce cas.
- **Forgejo, organisation dont l'utilisateur ne peut pas lire les membres** : l'organisation est
  ignorée (§1.6).

### 1.8 Client web

Même comportement dans le client web. Le nouveau canal de lecture est ajouté à la liste blanche
(`channel-policy.ts`), avec la même garde de compte que `forge:org-teams`.

## 2. Critères d'acceptation

1. **Assistant, organisation** : compte Forgejo membre de `acme` (alice, bob) et de `beta`
   (carol). Propriétaire `acme`. Saisir `a` : la liste propose alice (acme) puis carol (beta). bob
   apparaît s'il correspond au texte. Les membres de `acme` sont toujours avant ceux de `beta`.
2. **Assistant, repo personnel** : même compte, propriétaire = le compte. Les membres de `acme` et
   de `beta` sont proposés ; le compte lui-même ne l'est jamais.
3. **Filtre** : `ali` trouve `alice` (login) ; `Martin` trouve un membre dont le nom affiché est
   « Alice Martin » ; `MARTIN` et `martín` aussi.
4. **Clavier** : `↓`, `↓`, `Entrée` ajoute la deuxième suggestion ; le champ se vide. `Échap`
   ferme la liste sans fermer la fenêtre.
5. **Saisie libre** : `externe42`, absent des organisations, puis `Entrée` (sans sélection) :
   ajouté comme aujourd'hui.
6. **Exclusion** : un membre déjà ajouté (assistant) ou déjà collaborateur ou invité (Paramètres)
   n'est plus proposé.
7. **Limite** : une organisation de 30 membres et la saisie `e` donnent au plus 8 suggestions.
8. **Paramètres** : sur un repo personnel, les suggestions sont présentes (aujourd'hui la liste est
   vide). Sur un repo d'organisation, les membres de l'organisation propriétaire sont en tête.
9. **Niveau imposé** (repo personnel GitHub, GH356) : une suggestion choisie s'ajoute en
   « Écriture ».
10. **Échec partiel** : une organisation dont la liste des membres échoue (403) n'empêche pas
    d'afficher les membres des autres. Hors ligne : champ utilisable, aucune suggestion, aucun
    message.
11. **Pas d'appel pendant la frappe** : saisir 10 caractères ne déclenche aucune requête vers la
    forge.
12. **Pas d'annuaire** : aucune requête vers `/search/users` (GitHub) ni `/users/search` (Forgejo).
13. **Client web** : critères 1, 4 et 8 vérifiés dans le client web.

## 3. Hors scope

- Recherche dans l'annuaire complet du serveur (décision ci-dessus).
- **Avatars** dans les suggestions. Il faudrait des images distantes dans le renderer, donc revoir
  la CSP et, pour le client web, passer par un proxy. À ouvrir à part si besoin.
- Nom affiché des membres GitHub : un appel `GET /users/{login}` par personne serait trop coûteux.
- **Équipes** : la liste déroulante des équipes reste inchangée.
- **Champ de type utilisateur des objets** (`UserFieldInput`, membres de l'organisation du repo
  `origin`, Forgejo seulement) : inchangé. Il pourra réutiliser le composant plus tard.
- Saisie par e-mail.

## 4. Points ouverts pour le Design

- **Nouvel appel de service** : il prend `accountKey` et rend `{ login, name, orgs[] }[]`. Il
  réutilise `listOwners`, ou un appel plus léger qui ne lit que les organisations, puis
  `orgMembers` du provider de chaque organisation. Les appels se font en parallèle, avec une
  limite raisonnable pour un compte qui a beaucoup d'organisations.
- **Paramètres du repo** : soit l'écran garde `RepoSettings.orgMembers` pour l'ordre, soit il
  passe le propriétaire au composant. Dans le second cas, `orgMembers` peut quitter
  `RepoSettings`.
- **Composant de complétion** : vérifier s'il en existe déjà un dans le renderer (`ExcelTextEditor`,
  `UserFieldInput`) avant d'en écrire un.
- **Tests e2e** : le faux serveur Forgejo (`e2e-web/support/fake-forgejo-api.ts`) doit répondre à
  `GET /user/orgs` et `GET /orgs/{org}/members` avec plusieurs organisations.
