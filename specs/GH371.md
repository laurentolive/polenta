# GH371 — Serveur MCP : modifier les statuts, les décisions, les entryFields et le displayIdField d'un type existant

Issue : #371 (`type:feature`). Spec validée sur la forme par l'humain (commentaire de l'issue du 2026-11-16) ;
ce fichier en est la rédaction.

## Contexte

Les outils de schéma du serveur MCP (`apps/desktop/src/mcp-server/tools/schema-mutation.tools.ts`) ne savent
qu'**ajouter** (`add_component`, `add_object_type`, `add_field`, `add_status`, `add_link_type`). Un utilisateur qui
configure un projet uniquement par le MCP (type validation `WASHER_VAL`, reprise des statuts de PH2) ne peut pas :

1. déclarer les `entryFields` d'un type validation (`add_field` n'accepte que `fields | runFields | stepFields`) ;
2. ajouter, modifier ou retirer une décision de validation (`decisions[]`) ;
3. modifier (libellé, couleur, nom, `isApproval`, `isTerminal`), retirer ou réordonner un statut — le premier
   statut est le statut de création ;
4. régler `displayIdField` (GH229) sur un type existant.

## Décisions validées par l'humain

| # | Décision |
|---|---|
| D1 | Outils fins, un par geste : `add_field` accepte `list: "entryFields"` ; `add_decision` / `update_decision` / `remove_decision` ; `update_status` / `remove_status` / `reorder_statuses` ; `update_object_type`. Renommage explicite (`name` → `to`). Pas d'outil de remplacement global d'un type. |
| D2 | Renommer un statut ou une décision **migre les objets existants comme l'application** (`FieldRenameService.renameValues` : valeur, historique, copies `testSnapshot` ; pour une décision : les `entries[].decision` des validations). `dryRun` donne le nombre d'objets touchés (cf. `previewValueRenames`). |
| D3 | Retirer un statut encore porté par des objets : **refusé**, sauf si `replaceWith` (statut existant du type) est fourni ; les objets y sont alors migrés (fusion, GH82 D4). |
| D4 | Hors périmètre : modification / suppression de champs, types de lien. |

## Décisions tranchées dans cette spec (signalées)

| # | Point | Décision | Justification |
|---|---|---|---|
| S1 | D2 vs le garde-fou `DECISION_IN_USE` (`assertValidationTypeStable` : « une décision utilisée ne se retire pas et **ne se renomme pas** ») | Le renommage d'une décision utilisée est **accepté avec migration** des `entries[].decision` ; `DECISION_IN_USE` reste opposé au **retrait** d'une décision utilisée et à un renommage qui ne migrerait pas. | Le garde-fou protège contre une entrée orpheline ; une migration n'en laisse pas. L'éditeur de l'application, lui, ne migre pas les décisions (champ `name` libre dans `DecisionsTable`, puis refus à l'enregistrement) : le MCP va ici **plus loin que l'application**, qui reste inchangée (hors périmètre). |
| S2 | Migration d'une décision dans une validation **signée** (« une validation signée est figée ») | Les validations signées ou annulées **sont migrées aussi**. | Convention existante : `ValidationsService.rewriteObjects` réécrit « les validations d'un type, signées comprises (renommage, pas une décision) » — c'est déjà ce que fait un renommage de statut ou de clé de champ. Un renommage ne change ni la décision rendue, ni `contentHash`, ni `atSignature` (qui ne contient pas la décision). Le refuser rendrait le renommage impossible dès la première signature. |
| S3 | Rendre « en attente » (`isPending: true`) une décision portée par des entrées | **Refusé** (`DECISION_IN_USE`). | Une exigence en attente n'a pas d'entrée (SPEC-REQ §13) : des entrées portant la décision en attente seraient incohérentes. |
| S4 | Champ d'entrée nommé `decision` | **Refusé** (`FIELD_NAME_TAKEN`, nom réservé). | `decision` est le pseudo-champ des `requiredWhen` d'entrée (GH266) ; l'éditeur ne le refuse pas, mais une déclaration MCP est contrôlée plus strictement (même principe que GH195 : à la déclaration MCP, une référence inconnue est refusée). |

## Comportement commun à tous les nouveaux outils

- **Cible** : `nodeName` + `typeName` dans le repo courant (`container.repoPath`), comme les `add_*`.
- **Refus communs** : nœud introuvable `NODE_NOT_FOUND` ; nœud `readonly` `NODE_READONLY` ; type introuvable
  `TYPE_NOT_FOUND`.
- **Validation avant écriture** : tout refus est levé **avant** la moindre écriture (schéma ou objet) — y compris
  en `dryRun`. Le schéma résultant passe par `SchemaService.save`, donc par tous ses garde-fous
  (`assertUniquePrefixes`, `assertRequiredWhen`, `assertTransitions`, `assertRunFields`, `assertVersionTypes`,
  `assertValidationTypes` / `validationTypeError`, `assertVersionTypeStable`, `assertValidationTypeStable`,
  `assertValidDisplayIdFields`).
- **Sérialisation** : chaque outil passe par `SchemaService.withMutationQueue(repoPath)` ; la migration des objets
  qui suit l'écriture du schéma est faite **dans la même entrée de file** (deux appels pipelinés ne s'entrelacent
  pas).
- **Réponse** : succès sans migration → le `ProjectSchema` complet (comme les `add_*`). Succès d'un outil qui
  migre (`update_status`, `remove_status`, `update_decision`) → `{ schema, migration }`, `migration` =
  `FieldRenameResult` (`migrated` : IDs, `skipped`, `failed`, `snapshots`) ; `migration` vide si rien à migrer.
- **Refus** : `{ isError: true, content: [{ type: 'text', text: '[<CODE>] <message>' }] }` (SPEC-MCP-SERVER §6) ;
  le message cite les éléments en cause (statut, décision, IDs d'objets ou de validations — 5 au plus, puis
  « … et N autres »).
- **`dryRun: true`** (outils qui migrent) : aucun écrit ; mêmes refus que l'appel réel ; réponse
  `{ dryRun: true, schema: <schéma qui serait écrit>, preview }` où `preview` donne `withOld` (objets portant
  l'ancienne valeur) et `withNew` (objets portant déjà la nouvelle : fusion), au sens de
  `FieldRenameService.previewValueRenames`.
- **Échec partiel de migration** : le schéma reste enregistré, les objets non migrés sont listés dans
  `migration.failed` / `skipped` (même philosophie que l'application, pas de retour arrière).
- **Écritures d'objets** : réécriture brute, sans ajout d'entrée d'historique (comme `renameValues`, qui ne fait
  que renommer les `value` de l'historique existant).

## Outils

### 1. `add_field` — liste `entryFields`

Entrée : `{ nodeName, typeName, field: SchemaField, list?: 'fields' | 'runFields' | 'stepFields' | 'entryFields' }`.

`list: 'entryFields'` ajoute `field` à la fin de `type.entryFields`.

| Refus | Code |
|---|---|
| type d'une autre catégorie que `validation` | `VALIDATION_TYPE_INVALID` (« Les entryFields sont réservés au type validation ») |
| nom déjà présent dans `entryFields` | `FIELD_NAME_TAKEN` |
| nom `decision` (réservé, S4) | `FIELD_NAME_TAKEN` |
| `requiredWhen` invalide : erreur de structure, **ou** clé / valeur inconnue — clés admises : les autres `entryFields` et le pseudo-champ `decision`, dont les valeurs sont les `decisions[].name` du type (`requiredWhenIssues(…, { key: 'decision', values })`) | `REQUIRED_WHEN_INVALID` |

Pas de migration (SPEC-REQ §13 : `entryFields` sans migration). Comportement des autres `list` inchangé.

### 2. Décisions de validation

Toutes : type de catégorie `validation`, sinon `VALIDATION_TYPE_INVALID`. Le type doit rester valide au sens de
`validationTypeError` (exactement une décision `isPending`, noms non vides et uniques), sinon
`VALIDATION_TYPE_INVALID`.

#### `add_decision`

Entrée : `{ nodeName, typeName, decision: { name, label?, color?, isPending?, proposesIssue? } }` — ajout en fin
de `decisions`.

| Refus | Code |
|---|---|
| `name` déjà pris | `DECISION_NAME_TAKEN` |
| `isPending: true` alors qu'une décision en attente existe (deux en attente) — utiliser `update_decision` pour déplacer la marque | `VALIDATION_TYPE_INVALID` |

#### `update_decision`

Entrée : `{ nodeName, typeName, name, to?, label?: string | null, color?: string | null, isPending?: true,
proposesIssue?: boolean, dryRun? }`. Au moins une propriété à modifier (sinon erreur d'entrée zod). `null` retire
`label` / `color` ; `proposesIssue: false` retire la clé.

- **`isPending: true`** déplace la marque « en attente » : la décision ciblée la prend, l'ancienne la perd (même
  geste que le bouton radio de `DecisionsTable`). `isPending: false` n'est pas accepté (il doit toujours y en
  avoir une) — erreur d'entrée.
- **`to`** (renommage) :
  - schéma : `decisions[].name` ; les `requiredWhen` des `entryFields` qui citent la décision (pseudo-champ
    `decision`) sont réécrits — `renameRequiredWhenRefs` ne le fait pas aujourd'hui pour ce pseudo-champ (à
    prévoir au design) ;
  - objets : `entries[].decision` (décisions confirmées et proposées) de **toutes** les validations du type, signées
    et annulées comprises (S2) ; rien d'autre n'est réécrit (les reflets GH210 et libellés sont lus à
    l'affichage) ;
  - le contrôle `DECISION_IN_USE` de `assertValidationTypeStable` ne doit pas refuser ce renommage (S1) — l'ordre
    écriture schéma / migration est un choix de design, sous la contrainte « aucun écrit si refus » ;
  - `dryRun` : `preview` = `{ validations, entries }` portant `name` (et `withNew` = entrées portant déjà `to`,
    toujours 0 puisque `to` est refusé s'il existe).

| Refus | Code |
|---|---|
| `name` introuvable | `DECISION_NOT_FOUND` |
| `to` déjà pris par une autre décision | `DECISION_NAME_TAKEN` |
| `isPending: true` sur une décision portée par au moins une entrée (S3) | `DECISION_IN_USE` |

#### `remove_decision`

Entrée : `{ nodeName, typeName, name }`.

| Refus | Code |
|---|---|
| `name` introuvable | `DECISION_NOT_FOUND` |
| décision en attente (le type n'en aurait plus) | `VALIDATION_TYPE_INVALID` |
| décision portée par au moins une entrée d'une validation du type (toutes, signées comprises) — message : IDs des validations | `DECISION_IN_USE` |
| décision citée par un `requiredWhen` d'`entryFields` (cf. Q1) | `REQUIRED_WHEN_INVALID` |

Pas de `replaceWith` pour une décision (non demandé, cf. Hors périmètre).

### 3. Statuts

Toutes : type d'une catégorie à statuts configurables (`requirement`, `test`, `issue`, `version`, `validation`) ;
type `campaign` (statuts fixes, `statuses[]` ignoré) → `STATUS_LIST_INVALID`.

Garde-fous repris de `save` : `validationTypeError` (un `isApproval`, un `isTerminal`, premier statut non marqué,
historique du statut) ; tant que des validations (resp. versions) existent, les statuts marqués du type validation
(resp. version) ne changent ni de nom ni de marque (`VALIDATION_TYPE_INVALID` / `VERSION_TYPE_INVALID`) ;
`assertTransitions` (`TRANSITION_INVALID`).

#### `update_status`

Entrée : `{ nodeName, typeName, name, to?, label?: string | null, color?: string | null, isApproval?: boolean,
isTerminal?: boolean, dryRun? }`. Au moins une propriété à modifier. `null` retire `label` / `color` ; `false`
retire `isApproval` / `isTerminal`.

- **`to`** (renommage), aligné sur `StructureTab.saveAndMigrate` (GH82) :
  - schéma : nom du statut ; `transitions[].from` / `.to` (`renameTransitionRefs`) ; `requiredWhen` des `fields`
    qui citent le statut (`renameRequiredWhenRefs`, pseudo-champ `status`) ;
  - objets : `FieldRenameService.renameValues` avec `{ target: { kind: 'status' }, from: name, to }` — statut
    courant et `history.status` des exigences, tests, campagnes, issues et validations du type, et copies
    `testSnapshot` des campagnes du repo pour un type de test ;
  - `dryRun` : `preview` = `previewValueRenames` (`withOld`, `withNew`).
- **`isApproval` / `isTerminal`** : changement de marque sans migration d'objet (comme l'éditeur) ; l'unicité n'est
  imposée que pour les types validation (et par `validationTypeError`).

| Refus | Code |
|---|---|
| `name` introuvable | `STATUS_NOT_FOUND` |
| `to` déjà pris par un autre statut du type (la fusion passe par `remove_status` + `replaceWith`) | `STATUS_NAME_TAKEN` |
| type validation invalide après modification (marques, premier statut) | `VALIDATION_TYPE_INVALID` |
| statut marqué renommé / démarqué, ou statut marqué ajouté, alors que des validations existent | `VALIDATION_TYPE_INVALID` |
| idem pour le type version avec des versions | `VERSION_TYPE_INVALID` |
| règle de transition rendue invalide | `TRANSITION_INVALID` |

#### `remove_status`

Entrée : `{ nodeName, typeName, name, replaceWith?, dryRun? }`.

- **Statut porté** = au moins un objet du type (exigence, test, campagne, issue, validation) dont le **statut
  courant** est `name` (périmètre de `previewValueRenames`). L'historique et les copies `testSnapshot` ne comptent
  pas.
- Sans `replaceWith` : retrait accepté seulement si le statut n'est pas porté ; les valeurs de l'historique et des
  copies restent telles quelles (comme l'application).
- Avec `replaceWith` : `renameValues` `{ status, from: name, to: replaceWith }` — fusion GH82 D4 : statut courant,
  `history.status` et copies `testSnapshot` passent à `replaceWith` ; puis retrait du statut. `dryRun` :
  `withOld` = objets migrés, `withNew` = objets portant déjà `replaceWith`.
- Le premier statut peut être retiré : le suivant devient le statut de création (sous réserve de
  `validationTypeError`).
- Références au statut dans `transitions` / `requiredWhen` : voir Q1 (comportement proposé : refus sans
  `replaceWith`, réécriture vers `replaceWith` sinon).

| Refus | Code |
|---|---|
| `name` introuvable, ou `replaceWith` introuvable | `STATUS_NOT_FOUND` |
| `replaceWith` = `name` ; retrait du dernier statut du type | `STATUS_LIST_INVALID` |
| statut porté et pas de `replaceWith` — message : nombre et IDs des objets | `STATUS_IN_USE` |
| statut marqué du type validation / version alors que des validations / versions existent ; type validation invalide après retrait | `VALIDATION_TYPE_INVALID` / `VERSION_TYPE_INVALID` |
| statut cité par une règle de transition (Q1) | `TRANSITION_INVALID` |
| statut cité par un `requiredWhen` de `fields` (Q1) | `REQUIRED_WHEN_INVALID` |

#### `reorder_statuses`

Entrée : `{ nodeName, typeName, order: string[] }` — permutation exacte des noms de statuts du type. Aucun objet
migré.

| Refus | Code |
|---|---|
| `order` n'est pas une permutation exacte (nom manquant, en trop, doublon) | `STATUS_LIST_INVALID` |
| type validation dont le premier statut serait marqué | `VALIDATION_TYPE_INVALID` |

### 4. `update_object_type`

Entrée : `{ nodeName, typeName, label?: string | null, color?: string | null, displayIdField?: string | null,
trackStatusHistory?: boolean }`. Au moins une propriété. `null` retire la clé ; `trackStatusHistory: true` retire
la clé (écrite seulement à `false`, GH77). Nom, préfixe et catégorie ne sont pas modifiables par cet outil (hors
périmètre).

| Refus | Code |
|---|---|
| `displayIdField` ni `title` ni un champ `text` / `number` / `enum` du type (`displayIdFieldError`) | `DISPLAY_ID_FIELD_INVALID` |
| `trackStatusHistory: false` sur le type validation | `VALIDATION_TYPE_INVALID` |

Désactiver `trackStatusHistory` ne supprime pas l'historique existant (GH77).

### Codes d'erreur

Nouveaux codes ajoutés à `SchemaValidationErrorCode` : `STATUS_NOT_FOUND`, `STATUS_IN_USE`,
`STATUS_LIST_INVALID`, `DECISION_NOT_FOUND`, `DECISION_NAME_TAKEN`. Codes existants réutilisés :
`NODE_NOT_FOUND`, `NODE_READONLY`, `TYPE_NOT_FOUND`, `FIELD_NAME_TAKEN`, `STATUS_NAME_TAKEN`,
`REQUIRED_WHEN_INVALID`, `TRANSITION_INVALID`, `VALIDATION_TYPE_INVALID`, `VERSION_TYPE_INVALID`,
`DECISION_IN_USE`, `DISPLAY_ID_FIELD_INVALID`.

## Critères d'acceptation

1. `add_field { list: 'entryFields' }` sur le type validation ajoute le champ en fin de `entryFields` de
   `.polenta/schema.yaml` ; sur un type `requirement` → `[VALIDATION_TYPE_INVALID]`, schéma inchangé (octet pour
   octet) ; nom `decision` ou déjà présent → `[FIELD_NAME_TAKEN]` ; `requiredWhen: { decision: [inconnue] }` →
   `[REQUIRED_WHEN_INVALID]`.
2. `add_decision` ajoute une décision ; un second `isPending: true` → `[VALIDATION_TYPE_INVALID]`.
3. `update_decision { isPending: true }` sur une décision non utilisée : elle seule porte `isPending` ensuite ; sur
   une décision portée par une entrée → `[DECISION_IN_USE]`.
4. Renommage d'une décision portée par 3 entrées réparties sur une validation en cours et une signée : `dryRun`
   annonce 2 validations / 3 entrées et n'écrit rien (aucun fichier modifié) ; l'appel réel réécrit les 3
   `entries[].decision`, les `requiredWhen` d'`entryFields` qui la citaient, le schéma, et laisse `contentHash`,
   `atSignature`, `decidedBy`, `decidedAt` inchangés ; `get_validation` lit ensuite les entrées sous le nouveau nom.
5. `remove_decision` d'une décision portée par une entrée → `[DECISION_IN_USE]` (IDs cités) ; de la décision en
   attente → `[VALIDATION_TYPE_INVALID]` ; d'une décision non utilisée → retirée.
6. `update_status { to }` sur un statut porté par N exigences : `dryRun` renvoie `withOld = N` sans écrire ; l'appel
   réel migre `status` et `history.status` de ces N objets, les copies `testSnapshot` pour un type de test, les
   règles `transitions` et les `requiredWhen` qui le citaient ; `to` existant → `[STATUS_NAME_TAKEN]`.
7. `update_status` change `label`, `color`, `isApproval`, `isTerminal` sans toucher aux objets ; `null` / `false`
   retirent la clé du YAML.
8. Sur le type validation avec au moins une validation : renommer ou démarquer le statut signée / annulée →
   `[VALIDATION_TYPE_INVALID]` ; même règle pour le type version avec des versions → `[VERSION_TYPE_INVALID]`.
9. `remove_status` d'un statut porté sans `replaceWith` → `[STATUS_IN_USE]` (nombre et IDs) ; avec
   `replaceWith` → objets migrés vers `replaceWith` (statut et historique), statut retiré ; non porté → retiré ;
   `replaceWith` inconnu → `[STATUS_NOT_FOUND]` ; dernier statut → `[STATUS_LIST_INVALID]`.
10. `reorder_statuses` réordonne `statuses` ; permutation incomplète → `[STATUS_LIST_INVALID]` ; signée en tête
    sur le type validation → `[VALIDATION_TYPE_INVALID]`.
11. `update_object_type { displayIdField }` : `title` ou un champ text/number/enum accepté ; champ richtext ou
    inconnu → `[DISPLAY_ID_FIELD_INVALID]` ; `null` retire la clé ; `trackStatusHistory: false` sur le type
    validation → `[VALIDATION_TYPE_INVALID]`.
12. Tous les nouveaux outils : nœud `readonly` → `[NODE_READONLY]`, nœud / type inconnu →
    `[NODE_NOT_FOUND]` / `[TYPE_NOT_FOUND]` ; statut / décision sur un type `campaign` / non validation →
    `[STATUS_LIST_INVALID]` / `[VALIDATION_TYPE_INVALID]`.
13. Aucun refus n'écrit quoi que ce soit (schéma, objets) ; dix appels pipelinés sans attente sur le même repo
    donnent le même schéma que les mêmes appels séquentiels.
14. Le reste du comportement des outils existants est inchangé (tests MCP existants verts).
15. Documentation : SPEC-MCP-SERVER §4.3 (tableau des outils, codes), SPEC-INDEX (mots-clés), et la liste des
    outils de schéma du gabarit `AGENTS.md` (`agents-md.template.ts`) mises à jour.

## Hors périmètre

- Modification / suppression de champs (`fields`, `runFields`, `stepFields`, `entryFields`) et de types de lien
  (D4) ; modification des règles `transitions` et des `requiredWhen`.
- Renommage d'un type (nom / préfixe, GH100), changement de catégorie, suppression d'un type ou d'un composant.
- `replaceWith` pour une décision (fusion de décisions) — non demandé.
- Alignement de l'éditeur de l'application sur S1 (renommage d'une décision utilisée avec migration) : l'éditeur
  garde son refus `DECISION_IN_USE`.
- Filtres des vues enregistrées (`.polenta/views`), requêtes et dashboards du Suivi qui citent un statut ou une
  décision renommés : non modifiés (comme l'application, GH82).
- Course inter-process avec l'application ouverte (cache du schéma, écriture simultanée d'une validation) : même
  limite que les autres écritures MCP (SPEC-MCP-SERVER §7).

## Questions ouvertes

- **Q1 — Statut / décision retirés encore cités par `transitions` ou `requiredWhen`.** L'application refuse un
  statut retiré cité par une transition (`TRANSITION_INVALID`), mais laisse un `requiredWhen` citant une valeur
  disparue devenir inerte (avertissement, GH195). Le MCP n'ayant aucun outil pour modifier transitions et
  `requiredWhen` (hors périmètre), un refus strict peut bloquer l'agent. **Proposition par défaut** retenue dans
  ce document : sans `replaceWith`, refus (`TRANSITION_INVALID` / `REQUIRED_WHEN_INVALID`, citations listées) ;
  avec `replaceWith` (statuts), les références sont réécrites vers `replaceWith`, et refus si cela produit une règle
  invalide (doublon, `from` = `to`). Alternative : parité stricte avec l'application (`requiredWhen` laissé inerte,
  signalé dans la réponse). À confirmer.
- **Q2 — Création d'un type validation / version par le MCP.** `add_object_type` n'accepte pas les catégories
  `version` et `validation` (`objectCategorySchema` : `requirement | test | campaign | issue`) ni `decisions` /
  `entryFields` : un projet configuré uniquement par le MCP ne peut pas créer `WASHER_VAL`. Hors du texte de
  l'issue (« type existant ») — proposition : issue séparée. À confirmer.
