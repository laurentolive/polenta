# GH373 — Ajout d'un composant : types de liens par défaut entre les types de documents choisis

Issue : #373 (`type:feature`). Dépend de #365 (mergé sur `main`). Décisions de l'humain du 2026-11-16 :
liens vérification, impact d'issue, implémentation (même composant et parent → enfant) ; un type de
lien **propre au composant** ; `issue-impact` affiché coché et non modifiable ; lien parent écrit
« comme lorsqu'on le crée à la main » (voir §3, interprétation à confirmer).

## Contexte

`AddDependencyModal` (onglet Structure, « + Composant ») propose depuis GH365 une case par catégorie
de type à créer (Exigences, Tests, Campagnes, Issues, et pour un repo séparé Versions, Validations).
Aucun type de lien n'est créé, sauf `issue-impact` : `SchemaService.save` l'ajoute (catégories
`issue` → `requirement`) quand le schéma reçoit son premier type issue.

Constats du code qui orientent la spec :
- La couverture (`matchCoverageLink`) ne regarde pas le type de lien : tout lien test ↔ exigence
  couvre. Le type de lien sert à **autoriser** la création du lien (`validateLinkEntries`, refs).
- Les types de liens en vigueur sont l'**union par nom** des schémas du workspace, repo racine
  prioritaire (`WorkspaceLinksService.unionLinkTypes`) : un type du composant portant le nom d'un
  type du produit serait masqué. D'où un type de lien **propre à chaque composant**, au nom unique.

## Comportement attendu

### 1. Section « Types de liens créés par défaut »

À l'ajout d'un **composant** (pas d'une interface, pas en édition), sous les cases des types
d'objets, une case par lien proposé, cochée par défaut. Un lien n'est affiché que si les cases de
ses deux extrémités sont cochées (et visibles) ; le masquer ne perd pas son état (re-cocher
l'extrémité le ré-affiche tel qu'il était). Section absente si aucun lien n'est proposable.

| Lien proposé | Extrémités requises | Sens (source → cible) | Libellés (source → cible / cible → source) |
|--------------|---------------------|-----------------------|--------------------------------------------|
| Vérification | Tests + Exigences | test du composant → exigence du composant | « vérifie » / « est vérifiée par » |
| Implémentation interne | Exigences | exigence du composant → exigence du composant | « est implémentée par » / « implémente » |
| Implémentation depuis le parent | Exigences, et le parent a au moins un type exigence | exigence du parent → exigence du composant | « est implémentée par » / « implémente » |
| Impact d'issue | Issues + Exigences | issue → exigence | « impacte » / « est impactée par » |

- **Impact d'issue** : case cochée et **grisée** (non modifiable), infobulle « Ajouté avec le type
  Issues ». C'est le `issue-impact` existant, rien de nouveau n'est créé par cette spec.
- Libellés dans la langue de l'interface, comme ceux des types d'objets par défaut (en anglais :
  « verifies » / « is verified by », « is implemented by » / « implements »).
- **Parent** : le nœud sous lequel le composant est ajouté — composant local parent
  (`parentName` / `localParent`) s'il y en a un, sinon le `root` du repo où « + Composant » a été
  cliqué. Ses types de catégorie `requirement` (tous) forment la source du lien parent.

### 2. Types de liens créés

Un **type de lien par lien coché**, propre au composant :

- **Nom** : racine du composant (même racine que ses types, GH365 : label affiché, repli sur le nom)
  en minuscules, `_` → `-`, suivie du suffixe : `<racine>-verification`, `<racine>-implementation`,
  `<racine>-implementation-parent`. Ex. « Contrôle moteur » → `controle-moteur-verification`.
- **Collision** : nom déjà pris par un type de lien d'un schéma du workspace → premier suffixe libre
  `-2`, `-3`… (`controle-moteur-verification-2`), comme pour les types d'objets (GH97).
- **Refs typées** (`<nœud>::<TYPE>`), jamais par catégorie :
  - composant local de nom `moteur` : `moteur::CONTROLE_MOTEUR_TEST` → `moteur::CONTROLE_MOTEUR_REQ` ;
  - composant en repo séparé : refs de son `root` (`root::CONTROLE_MOTEUR_REQ`), forme déjà écrite
    par l'onglet Liens pour un type d'un repo du workspace ;
  - lien parent : `sourceRefs` = tous les types exigence du parent, `targetRefs` = le type exigence
    du composant.
- `defaultVisible: true` sur le lien de vérification (colonne de lien affichée par défaut, comme
  `verification` du projet de démo) ; absent sur les autres.

### 3. Schéma où chaque type est écrit

| Lien | Composant local | Composant en repo séparé |
|------|-----------------|--------------------------|
| Vérification, implémentation interne | schéma du repo (le même que le composant) | schéma du composant (`.polenta/schema.yaml` de son repo) |
| Implémentation depuis le parent | schéma du repo | **schéma du repo parent** |
| Impact d'issue | inchangé (`SchemaService.save` du schéma qui reçoit le type issue) | idem |

Lien parent d'un repo séparé — **interprétation de « comme à la main »** : à la main, on le déclare
dans l'onglet Liens sur le schéma du repo parent, seul schéma qui connaît les deux bouts (un composant
ne connaît pas son parent, règle 7 de `CLAUDE.md`). La source étant l'exigence du parent, les liens
créés sont stockés dans le `links.yaml` du parent (stockage côté source, GH105) : le composant ouvert
seul reste autonome.

### 4. Cas où aucun lien n'est créé

- Repo séparé dont le `root` a déjà des types : non amorcé (GH365), aucun type de lien créé, même
  coché (la fenêtre ne peut pas le savoir avant le clonage).
- Interface : jamais (inchangé).
- Type de lien dont une extrémité n'a finalement pas été créée (décochée) : non créé.

## Critères d'acceptation

1. Composant local « Contrôle moteur » (`moteur`) sous le `root` d'un repo dont le `root` a un type
   exigence `SYS`, toutes cases cochées : le schéma reçoit `controle-moteur-verification`
   (`moteur::CONTROLE_MOTEUR_TEST` → `moteur::CONTROLE_MOTEUR_REQ`), `controle-moteur-implementation`
   (`moteur::CONTROLE_MOTEUR_REQ` → idem), `controle-moteur-implementation-parent`
   (`root::SYS` → `moteur::CONTROLE_MOTEUR_REQ`) et `issue-impact` ; un lien test → exigence du
   composant puis un lien SYS → exigence du composant se créent sans erreur.
2. Repo séparé neuf, mêmes cases : vérification et implémentation interne dans le schéma du
   composant (refs `root::…`), implémentation depuis le parent dans le schéma du repo parent ; liens
   créables depuis le workspace ; le lien parent est stocké dans le repo parent.
3. Décocher Tests masque la case Vérification ; la re-cocher la ré-affiche dans son état précédent.
   Décocher Exigences masque tous les liens. Case Impact d'issue toujours cochée et grisée.
4. Lien décoché → type non créé ; les autres le sont.
5. Parent sans type exigence → pas de case « Implémentation depuis le parent ».
6. Deux composants de label « Moteur » : le second reçoit `moteur-verification-2`, etc.
7. Le produit a déjà un type de lien `verification` : il n'est pas modifié, et le composant reçoit
   son propre type (pas de masquage).
8. Repo séparé dont le `root` a déjà des types : aucun type de lien créé ; interface : aucun.
9. **Équivalence avec une création à la main** : chaque type de lien est écrit par le même chemin
   que l'onglet Liens (`schema:save` → `SchemaService.save`), avec la même forme (`name`, deux
   libellés, `sourceRefs` / `targetRefs` en `<nœud>::<type>` tels que les déclare le schéma
   d'origine, `defaultVisible` seulement s'il est vrai) : le schéma obtenu est identique à celui
   qu'on obtient en saisissant les mêmes valeurs dans l'onglet Liens, sur le schéma du repo indiqué
   au §3. Le lien parent d'un repo séparé correspond à la saisie faite sur le schéma du parent :
   l'onglet Liens permet aussi de le déclarer dans le schéma du composant, variante écartée (type
   invalide quand le composant est ouvert seul).

## Hors scope

- Modifier la fusion par nom des types de liens du workspace (`unionLinkTypes`).
- Outil MCP `add_component` (n'amorce ni types d'objets ni types de liens).
- Types de liens vers les campagnes, versions, validations.
- Rendre `issue-impact` décochable.
- Mise à jour des types de liens existants quand un type d'objet est ajouté plus tard au composant.
