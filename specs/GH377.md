# GH377 — Serveur MCP : créer un type version ou validation (`add_object_type`)

Issue : #377 (`type:feature`, milestone v0.6.0). Repérée pendant la spec de #371 (Q2).

## Contexte

`add_object_type` (`apps/desktop/src/mcp-server/tools/schema-mutation.tools.ts`) valide son entrée avec zod :

- `objectCategorySchema` = `requirement | test | campaign | issue` → `version` et `validation` refusés (erreur
  d'entrée) ;
- `objectTypeDefinitionSchema` ne déclare ni `decisions` ni `entryFields` → ces clés sont **retirées en silence**
  par zod.

Un projet configuré uniquement par le MCP ne peut donc créer ni type version (`versions/`, GH201) ni type
validation (`validations/`, GH204, ex. `WASHER_VAL`) : les outils `create_version` / `create_validation` (GH362)
répondent alors `NO_VERSION_TYPE` / `NO_VALIDATION_TYPE`.

Côté application, l'éditeur (`objectTypeEditor.tsx` → `emptyObjType`) crée ces types avec des statuts et décisions
par défaut (`DEFAULT_VERSION_STATUSES`, `DEFAULT_VALIDATION_STATUSES`, `DEFAULT_VALIDATION_DECISIONS`) et
`SchemaService.save` impose les garde-fous : un seul type version / validation, déclaré sur `root`
(`assertVersionTypes`, `assertValidationTypes`), type validation bien formé (`validationTypeError` : une décision
« en attente », un statut `isApproval`, un `isTerminal`, premier statut non marqué, statut historisé).

## Comportement attendu

### Entrée

`add_object_type { nodeName, objectType }` ; `objectType` accepte en plus :

| Clé | Type | Admise pour |
|---|---|---|
| `category` | + `version`, `validation` | — |
| `decisions` | `{ name, label?, color?, isPending?, proposesIssue? }[]` (`ValidationDecisionDef`) | `validation` seulement |
| `entryFields` | `SchemaField[]` | `validation` seulement |

Le reste de l'entrée (`fields`, `statuses`, `trackStatusHistory`, `displayIdField`…) est inchangé.

### Valeurs par défaut (D1 — alignées sur l'éditeur)

Quand la clé est **absente** de l'entrée :

| Catégorie | `statuses` absent | `decisions` absent |
|---|---|---|
| `version` | `en_cours` (En cours, #2563eb) · `released` (Released, #16a34a, `isApproval`) · `abandonnee` (Abandonnée, #6b7280, `isTerminal`) | — |
| `validation` | `en_cours` (En cours, #2563eb) · `signee` (Signée, #16a34a, `isApproval`) · `annulee` (Annulée, #6b7280, `isTerminal`) | `en_attente` (En attente, `isPending`) · `conforme` (Conforme) · `non_conforme` (Non conforme, `proposesIssue`) · `hors_scope` (Hors scope) · `derogation` (Dérogation, `proposesIssue`) |

- Une liste **fournie** est prise telle quelle (pas de fusion avec les défauts), puis contrôlée (voir Refus).
- Une liste fournie **vide** (`statuses: []`, `decisions: []`) n'est pas remplacée par les défauts : elle est
  refusée par `validationTypeError` pour le type validation ; pour le type version, voir Refus.
- Les défauts sont une **source unique** partagée par l'éditeur et le MCP (déplacement des constantes hors du
  renderer — détail au design), pour qu'ils ne divergent pas.
- `entryFields` absent → aucun champ d'entrée (comme l'éditeur). `fields` absent → `[]` (inchangé).
- Les autres catégories ne changent pas : pas de statuts par défaut ajoutés (hors périmètre).

### `entryFields` (D3 — mêmes contrôles que `add_field { list: 'entryFields' }` de #371)

- `trackHistory` et `defaultVisible` sont **retirés** de chaque champ d'entrée (l'éditeur les force à `false` :
  ni historique ni colonne pour un champ d'entrée).
- Nom unique dans `entryFields` ; nom `decision` refusé (pseudo-champ réservé des `requiredWhen` d'entrée, GH266).
- `requiredWhen` : clés admises = les autres `entryFields` et `decision`, dont les valeurs sont les noms des
  `decisions` **résultantes** (fournies ou par défaut) ; toute clé ou valeur inconnue est refusée.

### Refus

Tous levés **avant** écriture ; schéma inchangé octet pour octet.

| Cas | Code |
|---|---|
| `version` ou `validation` sur un autre nœud que `root` | `VERSION_TYPE_INVALID` / `VALIDATION_TYPE_INVALID` (garde-fou existant de `save`) |
| un type de la même catégorie existe déjà dans le repo | `VERSION_TYPE_INVALID` / `VALIDATION_TYPE_INVALID` (idem) |
| `prefix` absent ou vide pour `version` / `validation` (D2) | `VERSION_TYPE_INVALID` / `VALIDATION_TYPE_INVALID` |
| type validation mal formé après application des défauts (`validationTypeError` : décisions en attente ≠ 1, nom de décision vide ou en double, statuts `isApproval` / `isTerminal` ≠ 1, premier statut marqué, `trackStatusHistory: false`) | `VALIDATION_TYPE_INVALID` |
| type version sans exactement un statut `isApproval` (released) (D4) | `VERSION_TYPE_INVALID` |
| `decisions` ou `entryFields` fournis pour une autre catégorie que `validation` (D5) | `VALIDATION_TYPE_INVALID` (« réservés au type validation ») |
| `entryFields` : nom en double ou `decision` | `FIELD_NAME_TAKEN` |
| `entryFields` : `requiredWhen` invalide ou citant une clé / valeur inconnue | `REQUIRED_WHEN_INVALID` |
| cas existants : `NODE_NOT_FOUND`, `NODE_READONLY`, `TYPE_NAME_TAKEN`, `PREFIX_TAKEN` | inchangés |

Le contrôle de stabilité (`assertVersionTypeStable` / `assertValidationTypeStable`) est sans objet à la création
(aucun type de la catégorie avant) ; si des fichiers `versions/` ou `validations/` orphelins existent (type retiré à
la main), le comportement est celui de `save`, inchangé.

### Réponse

Inchangée : le `ProjectSchema` complet (avec les défauts appliqués, donc visibles par l'agent).

- `SPEC-MCP-SERVER.md` §4.3 (ligne `add_object_type`, codes), `SPEC-INDEX.md` (mots-clés), gabarit `AGENTS.md`

## Décisions proposées (à valider)

| # | Point | Proposition | Justification |
|---|---|---|---|
| D1 | Défauts quand `statuses` / `decisions` sont absents | Défauts de l'éditeur, liste fournie prise telle quelle (pas de fusion) | Parité avec l'application ; une fusion rendrait le résultat imprévisible pour l'agent |
| D2 | `prefix` obligatoire pour version / validation | Oui, refus si absent | Sans préfixe, `create_version` échoue (`NO_VERSION_TYPE : préfixe manquant`) ; nom et préfixe sont ensuite **figés** dès le premier objet : mieux vaut l'exiger à la création |
| D3 | Contrôles des `entryFields` | Ceux de `add_field { list: 'entryFields' }` (#371 S4), plus le retrait de `trackHistory` / `defaultVisible` | Un même champ d'entrée doit être accepté ou refusé de la même façon par les deux outils |
| D4 | Type version : contrôle des statuts fournis | Exactement un `isApproval` exigé (passage released : tag, gel) ; `isTerminal` libre | `save` ne contrôle rien pour la version aujourd'hui ; sans statut released, une version ne se publie jamais. À confirmer — alternative : aucun contrôle, comme l'éditeur |
| D5 | `decisions` / `entryFields` sur une autre catégorie | Refus explicite plutôt que retrait silencieux | Un agent qui se trompe de catégorie doit le savoir |

## Critères d'acceptation

1. `add_object_type { nodeName: 'root', objectType: { name, prefix, category: 'version' } }` écrit le type avec les
   trois statuts par défaut (noms, libellés, couleurs, marques) ; `create_version` fonctionne ensuite.
2. Idem `category: 'validation'` : trois statuts et cinq décisions par défaut ; `create_validation` fonctionne
   ensuite sur une version.
3. Statuts / décisions fournis : écrits tels quels ; jeu invalide (deux `isPending`, aucun `isApproval`, premier
   statut signé, `trackStatusHistory: false`) → `[VALIDATION_TYPE_INVALID]`.
4. Second type version (ou validation) dans le repo, ou déclaration sur un composant local →
   `[VERSION_TYPE_INVALID]` / `[VALIDATION_TYPE_INVALID]`.
5. `prefix` absent → refus (D2).
6. `entryFields` : écrits sans `trackHistory` / `defaultVisible` ; nom `decision` ou en double →
   `[FIELD_NAME_TAKEN]` ; `requiredWhen: { decision: ['inconnue'] }` → `[REQUIRED_WHEN_INVALID]` ;
   `requiredWhen: { decision: ['non_conforme'] }` avec les décisions par défaut → accepté.
7. `decisions` ou `entryFields` sur un type `requirement` → `[VALIDATION_TYPE_INVALID]`.
8. Aucun refus n'écrit le schéma ; types `requirement | test | campaign | issue` : comportement et tests existants
   inchangés.
9. L'éditeur de l'application propose toujours les mêmes défauts (source unique, test unitaire existant vert).
10. Documentation mise à jour (§ Documentation).
