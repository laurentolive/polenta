# GH38 — "Publier" publie tous les repos ayant des modifications en attente

Issue : #38 — `type:feature`

## Contexte

Depuis T83/T87, "Publier" n'agit que sur **un seul repo**, le « repo concerné » résolu par
`useModificationMode` : le repo de `?repo=` s'il est présent dans l'URL, sinon le repo racine.
`?repo=` n'est posé que par la vue Système. Conséquence : un utilisateur qui modifie une exigence
ou un test d'un composant en repo séparé depuis les vues Exigences/Tests publie uniquement le repo
racine ; les fichiers modifiés du composant restent non commités, sans aucun signal. Le cas était
explicitement hors scope de T83 (« une modification = un repo ») et T84 (« Publier multi-repo
simultané »).

## Comportement attendu

### Périmètre d'une publication

Un clic sur "Publier" publie, sous **un seul titre de modification**, chaque repo du workspace qui
a quelque chose à publier — quel que soit le repo concerné ou la vue affichée :

- un repo a quelque chose à publier s'il a des modifications en attente (`staged` + `unstaged`
  non vides) **au moment de son tour** ;
- ou s'il est resté checkouté sur la branche éphémère `dev-<slug>` d'une précédente publication en
  conflit (reprise T87, voir « Échec » ci-dessous).

Projet simple (un seul repo, pas de workspace) : comportement strictement identique à avant.

### Ordre et propagation des pins

1. Les repos sont publiés **enfants avant parents** (post-ordre de l'arbre logique du workspace,
   chaque repo une seule fois même s'il est partagé par deux parents — cas diamant), la racine en
   dernier.
2. Chaque repo suit exactement le flux unitaire existant (T87/T154) : `dev-<slug>` éphémère si on
   est sur la branche d'intégration configurée (sinon commit direct sur la branche avancée),
   fast-forward de l'intégration, stage + commit (message = titre), merge, retour sur
   l'intégration et suppression de la branche éphémère.
3. Après la publication d'un repo, le SHA de merge est proposé comme pin à tous les repos qui le
   déclarent en dépendance (`propagatePinToDependents`, T82). Le `polenta-repo.yaml` du parent
   devient donc modifié ; comme le parent passe après, cette mise à jour de pin est **incluse dans
   sa propre publication** (même titre). Un parent sans autre modification est donc publié aussi,
   uniquement pour le pin.
4. Le push de la branche d'intégration de chaque repo publié reste best-effort et non bloquant ;
   les échecs sont agrégés dans la notification existante, préfixés du nom du repo.

### Contrôles préalables (avant toute écriture)

Évalués au clic sur le bouton de validation du popup, sur l'ensemble des **candidats** = repos
ayant quelque chose à publier + tous leurs ancêtres dans l'arbre logique (ils recevront une mise à
jour de pin) :

- **Branche bloquante** : un candidat en HEAD détaché, ou sur une branche `int-*` différente de sa
  branche d'intégration configurée → publication refusée **en entier**, rien n'est touché ; le
  message liste les repos concernés et leur branche.
- **Réseau (T154)** : `fetch` de chaque candidat. Un échec → publication refusée en entier avec le
  message « réseau indisponible » existant, complété du nom du repo ; rien n'est touché.

### Échec en cours de publication

Un conflit de merge (ou toute autre erreur) sur un repo **arrête** la publication à ce repo :

- les repos déjà publiés restent publiés (pas de rollback — un merge déjà poussé ne se défait pas)
  et sont poussés comme en cas de succès ;
- le popup d'erreur indique le repo en échec, la liste des repos déjà publiés, et (conflit) les
  fichiers en conflit ; « Résolution manuelle » ouvre le diff **sur le repo en échec** ;
- les repos restants ne sont pas publiés ; les pins déjà propagés vers eux restent en attente dans
  leur `polenta-repo.yaml` ;
- relancer "Publier" reprend : le repo en échec est repris depuis sa branche éphémère (logique T87
  existante), les repos déjà publiés n'ont plus rien à publier et sont ignorés, les autres suivent.

### Repos publiés laissés en HEAD détaché (cas diamant)

Un repo partagé par deux parents reçoit son nouveau pin dans chacun d'eux l'un après l'autre ;
entre les deux, la reconstruction de l'arbre (`rebuildTree`, lancée par la propagation T82) voit
deux pins différents et en checkoute un, laissant le repo tout juste publié en HEAD détaché —
édition bloquée. En fin de publication (succès ou échec), tout repo publié en HEAD détaché et
sans modification en attente est remis sur sa branche d'intégration (constaté pendant la
vérification sur le workspace de démo LL800 : `if-bus-interne`, dépendance du moteur et du
produit).

### UI

- Le bouton "Publier" est actif dès qu'**au moins un** repo du workspace a quelque chose à
  publier (et non plus seulement le repo concerné). Sa visibilité et l'affichage « branche
  bloquée » restent pilotés par le repo concerné, comme avant.
- Le popup de titre liste, sous le champ titre, les repos qui seront publiés (libellé du repo
  + nombre de fichiers modifiés), avec la mention que les repos parents seront aussi publiés pour
  la mise à jour des pins. Si un candidat est bloqué, le popup l'indique et le bouton de
  validation est désactivé.
- Le popup est invalidé (« état modifié ») si la liste des repos à publier change pendant qu'il
  est ouvert, comme déjà le cas pour un changement de repo/branche.

## Critères d'acceptation

1. Workspace racine + composant `compA` : une exigence de `compA` modifiée depuis la vue Exigences
   (sans `?repo=`) → le bouton "Publier" est actif ; après publication, `compA` a un commit de
   merge sur son intégration, la racine a un commit portant le nouveau pin de `compA` dans
   `polenta-repo.yaml`, aucun fichier en attente dans aucun des deux.
2. Modifications à la fois dans la racine et `compA` → un seul clic publie les deux ; le commit de
   la racine contient ses propres modifications **et** la mise à jour du pin.
3. Composant `compB` imbriqué sous `compA` (racine → compA → compB), seul `compB` modifié →
   ordre de publication `compB`, `compA` (pin de compB), racine (pin de compA).
4. Seule la racine modifiée → comportement identique à avant GH38 (un seul repo publié, aucune
   propagation de pin).
5. Un candidat sur une `int-*` non configurée → popup indique le blocage, aucune branche créée,
   aucun commit.
6. Échec de `fetch` sur un candidat → message réseau, aucune branche créée, aucun commit, dans
   aucun repo.
7. Conflit sur la racine après publication de `compA` → `compA` reste publié, le popup d'erreur
   nomme la racine et les fichiers en conflit ; « Résolution manuelle » ouvre le diff de la
   racine ; relancer "Publier" après résolution termine la racine.
8. Projet simple sans workspace → comportement inchangé.

## Hors scope

- Rollback des repos déjà publiés en cas d'échec sur un repo suivant.
- Publication parallèle des repos (séquentielle : `rebuildTree` n'est pas réentrant).
- Prise en compte de la préférence `autoPropagatePin` : le flux "Publier" propageait déjà le pin
  sans la consulter (T82) ; GH38 ne change pas ce point.
- Sélection manuelle d'un sous-ensemble de repos à publier.
- Composants locaux (dans le même repo) : ils font partie de leur repo, déjà couverts.
