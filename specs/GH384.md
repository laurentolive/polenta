# GH384 — Serveur MCP : défauts restants après GH371 / GH372 / GH377

Issue #384 (type:bug), relevés en important le fichier EMQS « Qualité » dans le projet washer.
Choix de l'humain (2026-11-17) : `multi_enum` en chaîne « a, b » ; suppression refusée pour un objet
utilisé ; auteur `--user` sinon `mcp` ; nom d'un type de lien non modifiable.

## 1. Une seule erreur par entrée

**Root cause** : `validateEntry` (import) et `planUpdate` (modification) s'arrêtaient à la première règle
en échec, et `fieldValuesError` (GH372) à la première valeur fautive.
**Correctif** : `fieldValuesErrors` rend une erreur par champ (`fieldValuesError` = la première, gardée) ;
`validateEntry` cumule requis manquants (un par champ), EARS, statut et valeurs ; `planUpdate` cumule
statut, valeurs, requis vidés et EARS (`errors`, la première restant en `reason` / `field`). Type
inconnu et nœud `readonly` arrêtent toujours l'entrée ; `prepareFieldsWrite` n'est contrôlé que si le
reste passe. `summary.failed` compte les entrées en erreur, plus les lignes d'`errors`.

## 2. Réponse trop longue de `update_status` / `remove_status`

**Root cause** : la réponse portait le schéma résolu complet (`{ schema, migration }` / `{ dryRun, schema,
preview }`).
**Correctif** : `type` (le type modifié) à la place de `schema` ; option `includeSchema: true` pour le
schéma complet.

## 3. `update_link_type`

Nouvel outil : libellés, `defaultVisible` (`false` retire), `sourceRefs` / `targetRefs` (remplacés en
bloc, `null` retire la restriction, liste vide refusée : `LINK_TYPE_INVALID`). Le nom ne se modifie
pas. Refus `LINK_TYPE_IN_USE` (IDs) si des liens existants du type, sur tout le workspace, ne seraient
plus acceptés dans aucun sens (`matchesRefs`, même règle que la création). `SchemaService.updateLinkType`,
dans la file de mutation du schéma.

## 4. `delete_requirements` / `delete_tests`

L'application n'a pas de suppression d'un objet seul (un objet abandonné devient `obsolete`). Les
outils ne suppriment donc qu'un objet **inutilisé** : refus `OBJECT_IN_USE` pour un objet lié (liens du
workspace — `delete_links` d'abord), présent dans une campagne, inclus dans une version ou cité par une
validation ; `NODE_READONLY` ; `OBJECT_NOT_FOUND`. `dryRun` par défaut. Écriture : pierre tombale puis
fichier (`deleteWithTombstone`, l'ID n'est jamais réattribué), puis `test-runs/<ID>` ou
`impact-acks/<ID>`, comme `SchemaDeleteService`. Le rangement en dossiers n'est pas réécrit (objet
disparu ignoré à l'affichage).

## 5. `createdBy: local`

**Root cause** : l'acteur de `HistoryService` dans le conteneur MCP valait `--user ?? 'local'`, alors
que `create_links` passait `'mcp'` en dur.
**Correctif** : `mcpActor(user)` = `--user`, sinon `mcp`, utilisé par l'historique (donc `createdBy` /
`updatedBy`) et par `create_links`.

## 6. `multi_enum` fourni en chaîne

**Constat inverse de l'issue** : le format de l'application est la chaîne « a, b »
(`serializeMultiEnumValue` : cases à cocher, vues Excel / Word, champs d'exécution) ; le format
divergent était la **liste** YAML écrite par les imports MCP en liste. Le contrat de données décrit
déjà « a, b » : rien à y changer.
**Correctif** : `canonicalMultiEnumFields` réécrit une liste ou une chaîne mal espacée en « a, b »
avant contrôle et écriture (`bulk_import_requirements` / `bulk_import_tests`, `update_requirements` /
`update_tests`). Les fichiers déjà importés en liste restent lisibles (`parseMultiEnumValue` accepte
les deux) ; ils reprennent le format chaîne à leur prochaine modification depuis l'application.
