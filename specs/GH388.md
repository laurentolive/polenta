# GH388 — Signer l'installeur Windows

Issue : [#388](https://github.com/laurentolive/polenta/issues/388) — type:feature, priority:P2

## 1. Contexte

- `Polenta-Setup-X.Y.Z.exe` (NSIS one-click par utilisateur, GH26) est construit par
  `.github/workflows/release.yml` (job `release`, `windows-latest`) via `scripts/package.ts` et
  `apps/desktop/electron-builder.config.ts`, qui ne contient **aucune configuration de signature**.
- Chez un client : écran SmartScreen « éditeur inconnu » à l'installation ; Edge bloque le
  téléchargement (« n'est pas couramment téléchargé »).
- `electron-builder` est en `^24.0.0`, `electron-updater` en `^6.1.0`.
- Les mises à jour (GH26/GH302) passent par `latest.yml` (sha512 de l'installeur) et
  `app-update.yml` embarqué. Quand l'application est signée, electron-builder écrit le
  `publisherName` du certificat dans `app-update.yml`, et electron-updater **refuse ensuite toute
  mise à jour dont l'installeur n'est pas signé par ce même éditeur**.

## 2. Décisions (humain, 2026-11-17)

| # | Question | Décision |
|---|----------|----------|
| D1 | Entité qui signe | **L'humain, en personne physique** (auto-entrepreneur ; marque « eSquareSoft » envisagée, pas de société). Azure Artifact Signing (ex-Trusted Signing) est donc exclu : il est réservé aux organisations, et l'identité « individu » n'est ouverte qu'aux USA et au Canada. |
| D2 | Certificat | **Certum « Open Source Code Signing in the Cloud »** (clé dans le HSM cloud SimplySign, ≈ 70–100 €/an). Polenta est éligible (AGPL, repo public). L'éditeur affiché est le nom légal de la personne, au format « Open Source Developer, <nom> » ; le nom commercial n'y figure pas, sauf si Certum l'accepte (à vérifier à la commande, sans bloquer le ticket). |
| D3 | Marques client (GH49, `workflow_dispatch`) | **Hors périmètre** : seule la marque `polenta` est signée. Une marque client signée avec l'identité Polenta afficherait un éditeur trompeur. |
| D4 | Critère Edge | Remplacé par : signature valide + éditeur affiché + **suivi de réputation** documenté. Aucune signature (même EV, depuis 2024) ne garantit l'absence de blocage SmartScreen dès la première version : la réputation s'acquiert au fil des téléchargements. |
| D5 | Où signer | **En CI** si l'ouverture de session SimplySign (TOTP) s'automatise de façon fiable sur le runner Windows. Sinon, **repli accepté : build et signature sur le poste de l'humain**, puis publication par un script documenté. |

## 3. Description fonctionnelle

### 3.1 Ce qui est signé (marque `polenta`)

- L'installeur `Polenta-Setup-X.Y.Z.exe`, le désinstalleur et `Polenta.exe` qu'il contient.
- Les exécutables et DLL **propres à Polenta** packagés à côté (`*.exe`, `*.dll`, `*.node` produits
  par le build, ex. `keytar.node`). Les binaires tiers **déjà signés** par leur éditeur (Electron
  ne l'est pas ; `conpty.dll`/`OpenConsole.exe` de node-pty et, s'il est embarqué (#337), PortableGit
  le sont) ne sont pas re-signés. La liste exacte est arrêtée au design, après inventaire des
  signatures du dossier `win-unpacked`.
- Algorithme SHA-256, **horodatage RFC 3161** (TSA de Certum) : la signature reste valide après
  l'expiration du certificat.
- Les marques sans signature (D3) et les builds locaux de développement restent possibles **sans
  certificat** : l'absence des secrets de signature ne fait pas échouer `pnpm package`, sauf pour
  une release publique (tag `vX.Y.Z`, marque `polenta`), où une signature manquante **fait échouer
  le job** : on ne publie jamais une release non signée une fois la signature en place.

### 3.2 Mise à jour automatique

- **Passage non signé → signé** : les versions déjà installées n'ont pas de `publisherName`, elles
  acceptent la première version signée sans vérification d'éditeur.
- **Signé → signé** : `app-update.yml` porte le `publisherName` du certificat Certum ; la version
  suivante, signée par le même éditeur, s'installe.
- **Changement d'identité futur** (passage à une société, autre AC) : le `publisherName` accepte
  une liste. La procédure du RUNBOOK impose de publier d'abord une version qui accepte l'ancien et
  le nouvel éditeur, **avant** de signer avec le nouveau ; sans cela, les postes installés ne se
  mettent plus à jour.
- Le `sha512` de `latest.yml` et le `.blockmap` sont calculés **sur l'installeur signé**.

### 3.3 Signature en CI (cible) ou sur le poste (repli)

- **CI** : les secrets (identifiant SimplySign, secret TOTP, empreinte du certificat) vivent dans
  les secrets GitHub Actions, jamais dans le dépôt ni dans les logs. Le job ouvre la session
  SimplySign sur le runner, et electron-builder signe via `signtool` (hook de signature).
- **Repli sur le poste**, si la CI ne tient pas (D5) : un script documenté construit et signe sur le
  poste de l'humain (session SimplySign ouverte à la main), vérifie les signatures, puis crée la
  release GitHub avec les mêmes fichiers que `release.yml` (installeur, `.blockmap`, `latest.yml`,
  `polenta-cli.cjs`, notes de version). Le job `release` de la CI ne publie plus l'installeur dans
  ce mode (pas de double publication) ; l'image web (`web-image`) reste en CI.
- Le choix entre les deux modes est fait au design, après un essai de session SimplySign sur un
  runner `windows-latest` ; il est consigné dans `specs/GH388-design.md` et dans le RUNBOOK.

### 3.4 Réputation SmartScreen / Defender

- Après la première release signée : soumission de l'installeur au portail Microsoft
  (Security Intelligence, « software developer ») si Edge ou Defender le bloquent.
- Le RUNBOOK décrit comment constater l'état (téléchargement Edge sur un poste propre, écran
  d'installation) et que faire en cas de faux positif sur une version.

### 3.5 Mesure liée à #337

Une fois une version signée installée, refaire la mesure de `specs/GH337-sprint0.md` (lectures et
écritures de `Polenta.exe`) et consigner le résultat dans le résumé de sprint : simple
constat, sans engagement de résultat.

## 4. Critères d'acceptance

- **CA1** — `Polenta-Setup-X.Y.Z.exe`, le désinstalleur et `Polenta.exe` installé portent une
  signature Authenticode **valide et horodatée** (`signtool verify /pa /v` ou
  `Get-AuthenticodeSignature` → `Valid`, avec un horodatage).
- **CA2** — Les binaires propres à Polenta retenus au design sont signés ; un contrôle automatique
  (script de vérification lancé après le packaging) échoue si l'un d'eux ne l'est pas.
- **CA3** — À l'installation sur un poste Windows 11 (Defender par défaut), l'écran affiche
  l'éditeur du certificat, pas « éditeur inconnu ».
- **CA4** — Mise à jour automatique vérifiée sur deux versions : depuis la dernière version non
  signée vers une version signée, puis d'une version signée vers la suivante.
- **CA5** — Une release publique (tag, marque `polenta`) sans signature échoue ; un build de marque
  client ou un `pnpm package` local sans secrets réussit, non signé.
- **CA6** — Aucun secret de signature dans le dépôt ni dans les logs de la CI.
- **CA7** — RUNBOOK : commande et renouvellement du certificat Certum (validité maximale de
  459 jours depuis le 27/02/2026, à renouveler avant échéance), gestion des secrets, signature
  (CI ou poste), vérification, changement d'identité (§3.2), réputation / faux positif (§3.4).
  L'échéance figure dans « Échéances à suivre ».
- **CA8** — Suivi Edge : l'état du téléchargement depuis Edge (bloqué ou non) est constaté sur la
  première release signée et noté sur l'issue ; un blocage restant n'empêche pas la clôture du
  ticket (D4).

## 5. Hors périmètre

- Signature des marques client (D3) : ticket ultérieur si un client le demande, avec son propre
  certificat.
- macOS (notarisation) et Linux.
- Microsoft Store / MSIX.
- Azure Artifact Signing, à reconsidérer si une société est créée (le changement d'identité suit
  alors §3.2).
- Toute action sur la lenteur Defender de #337 au-delà de la mesure §3.5.

## 6. Prérequis humains (hors code)

- Commande et validation d'identité du certificat Certum Open Source (pièce d'identité, URL du
  projet open source), puis activation SimplySign (application mobile). Le développement de la
  configuration peut avancer avant (signature désactivée sans secrets, CA5), mais CA1–CA4 attendent
  le certificat.
- Saisie des secrets dans GitHub Actions (mode CI).

## 7. Points ouverts pour le design

- Montée de version d'electron-builder (24 → 26) ou hook `sign` personnalisé appelant `signtool` :
  à trancher au design (impact sur le packaging existant, `scripts/check-gh49.ts`).
- Automatisation de la session SimplySign en CI (§3.3) : essai sur runner, puis choix CI ou poste.
- Inventaire des binaires non signés du build (§3.1).
