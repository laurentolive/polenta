# GH39 — Intégration divergée d'origin : rendre l'état visible, ne plus l'aggraver, s'en sortir

Issue : #39 (type:bug, traité en Spec → Design → Dev vu sa taille).

## 1. Constat et root cause

Le push qui suit "Publier" est best-effort (`ModificationControl.pushPublished`) : en cas d'échec
(réseau, auth, refus parce qu'`origin` a avancé), le commit de merge reste **uniquement local** et la
notification se ferme. À partir de là, l'intégration locale a des commits absents d'`origin` :

- l'auto-pull (T155, `useAutoPull`) fait `pullFastForwardOnly` → échec à chaque tick, seulement
  `console.warn` ; et il ne tourne que si le repo est propre, donc il ne fait même pas de fetch
  tant que l'utilisateur a des modifications en attente ;
- "Publier" (T154) fait `fetch` + `fastForwardBranch` → `'diverged'` est ignoré, le merge s'ajoute
  par-dessus l'intégration divergée → nouveaux commits locaux, nouveau push refusé.

La divergence s'**auto-entretient sans être signalée** : l'utilisateur ne récupère plus rien
d'`origin`, potentiellement pendant des semaines.

## 2. Vocabulaire — état de synchronisation de l'intégration

Pour chaque repo du workspace (racine + composants/interfaces) qui a un remote `origin`, on compare
la branche d'intégration **configurée** locale (`refs/heads/<int>`) à sa branche de suivi
(`refs/remotes/origin/<int>`, telle que connue au dernier fetch). La branche actuellement
checkoutée n'intervient pas.

| État | Définition | Alerte ? |
|---|---|---|
| `up-to-date` | mêmes commits | non |
| `behind` | origin a des commits absents en local, pas l'inverse | non (cas normal, l'auto-pull s'en charge) |
| `ahead` | des commits locaux sont absents d'origin, origin n'a rien de nouveau (push en attente ou en échec) | **oui** — « non publié sur le serveur » |
| `diverged` | les deux à la fois | **oui** — « divergé » |
| `no-remote` | pas de remote `origin` (projet local) ou branche absente d'origin | non |

`ahead` est attendu pendant les quelques secondes du push qui suit "Publier" ; l'alerte n'est pas
affichée pour un repo dont le push est en cours.

## 3. Comportements attendus

### 3.1 Indicateur (point 1 de l'issue)

- **En-tête** (à côté de "Publier", dans `ViewHeader`) : une pastille d'alerte, visible dès qu'au
  moins un repo est `ahead` ou `diverged`, avec le nombre de repos concernés. Un clic ouvre un
  popover qui liste ces repos : nom, état (« N modification(s) non publiée(s) sur le serveur » /
  « divergé : N en local, M sur le serveur »), dernière erreur de push/sync connue, et un bouton
  **Resynchroniser** par repo.
- **Panneau Version** (`VersionRepoFolder`) : dans l'en-tête de chaque repo, un badge `↑N ↓M` relatif
  à l'intégration quand l'état n'est pas `up-to-date`/`no-remote` (en couleur d'alerte pour
  `ahead`/`diverged`), et le même bouton **Resynchroniser** dans la ligne du repo quand l'état est en
  alerte.
- Rien n'est affiché dans un projet sans remote.

### 3.2 Action « Resynchroniser » (explicite, par repo)

1. `fetch` d'origin. Échec → message d'erreur dans le popover / sous la ligne du repo, rien d'autre.
2. Selon l'état recalculé :
   - `up-to-date` / `no-remote` → rien.
   - `behind` → l'intégration est avancée jusqu'à origin (fast-forward). Si elle est checkoutée,
     le répertoire de travail suit (même mécanique que `pull` : merge puis checkout) ; refusé avec
     un message si elle est checkoutée **et** que le repo a des modifications en attente.
   - `ahead` → push de l'intégration.
   - `diverged` → merge d'`origin/<int>` dans `<int>` (commit de merge « Merge origin/<int> into
     <int> ») ; si l'intégration est checkoutée, même garde « modifications en attente » et même
     mise à jour du répertoire de travail que pour `behind` ; puis push.
3. **Conflit sur le merge de `diverged`** (rien n'est écrit par la tentative de merge) :
   - une branche `dev-resync` (suffixe `-2`, `-3`… si déjà prise) est créée sur le commit actuel de
     l'intégration locale — elle porte les commits locaux non poussés ;
   - l'intégration locale est réalignée sur `origin/<int>` ;
   - si l'intégration était checkoutée (repo forcément propre, cf. garde du point 2), `HEAD` passe
     sur `dev-resync` (même commit que l'ancien HEAD : aucun fichier touché) ; sinon la branche
     courante et ses modifications en attente sont inchangées ;
   - un message explique la situation : « Vos modifications non publiées ont été mises de côté sur
     `dev-resync`. Cliquez sur Publier pour les fusionner : les conflits seront à résoudre comme
     d'habitude. »
4. Ensuite, sur `dev-resync`, "Publier" est **actif même sans modification en attente** (la branche
   contient des commits absents de l'intégration) ; il suit le flux "Publier" existant (cas
   éphémère : merge dans l'intégration, retour sur l'intégration, suppression de `dev-resync`,
   push). Un conflit passe par le flux §2.4 standard (liste des fichiers + Résolution manuelle).
   Aucun commit vide n'est créé quand il n'y a rien à committer.
5. Succès → l'état repasse à `up-to-date`, l'alerte disparaît (au prochain rafraîchissement ≤ 3 s).

### 3.3 "Publier" sur une intégration divergée (point 2 de l'issue)

Contrôle supplémentaire **avant toute écriture**, après les fetchs (T154), sur chaque repo
candidat (repos avec modifications + leurs ancêtres) :

- `diverged` → simulation (sans écriture) du merge d'`origin/<int>` dans `<int>` :
  - sans conflit → la publication continue ; pendant la publication du repo, une fois sorti de
    l'intégration (comme le fast-forward T154 aujourd'hui), `origin/<int>` est d'abord fusionné
    dans `<int>`, puis la branche de travail est fusionnée comme d'habitude, puis push ;
  - avec conflit → **toute la publication est refusée**, rien n'est touché ; message « L'intégration
    de <repo> a divergé du serveur et ne peut pas être resynchronisée automatiquement (conflit sur :
    <fichiers>). Utilisez Resynchroniser (indicateur de synchronisation). »
- `ahead` → aucun blocage : la publication avance l'intégration par-dessus, le push qui suit
  emporte aussi les anciens commits (pas de divergence créée).
- `behind` → fast-forward existant (T154), inchangé.

Le push qui suit "Publier" alimente l'indicateur : un échec y reste visible (§3.1) après la
fermeture de la notification existante.

### 3.4 Auto-pull (point 3 de l'issue)

À chaque tick (toujours toutes les 5 min, premier tick inchangé — pas de tentative à l'ouverture),
pour chaque repo :

1. `fetch` d'origin, **même si le repo a des modifications en attente** (un fetch n'écrit que des
   refs distantes) — pour que l'indicateur reflète l'état réel du serveur.
2. Repo propre → fast-forward de la branche courante comme aujourd'hui (`pullFastForwardOnly`,
   jamais de merge à trois voies).
3. Intégration `ahead` (et seulement `ahead`) → **relance automatique du push** de l'intégration,
   même si le repo a des modifications en attente (le push ne touche pas les fichiers).
4. Intégration `diverged` → aucune action automatique ; l'état est remonté par l'indicateur.
5. Toute erreur (fetch, push, pull) reste silencieuse en tant que telle (pas de popup), mais la
   dernière erreur par repo est conservée et affichée dans le popover de l'indicateur quand le repo
   y figure.

## 4. Critères d'acceptation

1. Intégration locale avec 1 commit non poussé, origin inchangé → en ≤ 3 s, la pastille d'en-tête
   affiche 1 repo, le panneau Version affiche `↑1` sur ce repo.
2. Même situation, origin injoignable puis joignable → au tick d'auto-pull suivant, le push est
   relancé et réussit ; la pastille disparaît sans action utilisateur.
3. Intégration divergée (1 local, 1 distant, fichiers différents) → la pastille indique « divergé » ;
   "Publier" d'une modification réussit, l'historique de l'intégration contient le merge d'origin
   puis le merge de la modification, le push réussit, l'état final est `up-to-date`.
4. Intégration divergée **en conflit** avec origin → "Publier" refuse avant toute écriture (aucune
   branche `dev-*` créée, aucun commit, statut git identique), le message nomme le repo et les
   fichiers.
5. Même cas → Resynchroniser crée `dev-resync`, réaligne l'intégration sur origin, l'utilisateur
   se retrouve sur `dev-resync` sans perte (aucun fichier modifié) ; "Publier"
   est actif ; il aboutit au conflit §2.4 standard ; après résolution et nouveau "Publier",
   l'intégration contient les deux historiques, `dev-resync` est supprimée, état `up-to-date`.
6. Intégration divergée sans conflit, intégration checkoutée, repo propre → Resynchroniser produit le
   merge, met à jour les fichiers affichés et pousse ; état `up-to-date`.
7. Intégration `behind`/`diverged` checkoutée **avec** modifications en attente → Resynchroniser
   refuse avec un message, rien n'est modifié.
8. Auto-pull sur un repo avec modifications en attente : le fetch a lieu (la divergence devient
   visible), aucun fichier de travail n'est modifié.
9. Projet sans remote : aucun indicateur, aucune erreur ; "Publier" inchangé.
10. Aucune régression des scénarios T154 / T155 / GH38 (fast-forward avant merge, échec réseau
    explicite, publication multi-repo enfants → parents).

## 5. Hors scope

- Résolution de conflit champ par champ (§2.4 « non implémentée ») — on réutilise le flux existant.
- Premier tick d'auto-pull avancé après l'ouverture du projet (écarté à la spec : décision T155
  maintenue).
- Retry automatique d'un push en échec pour une autre branche que l'intégration configurée.
- Le bruit `tree.cache.yaml` qui rend les repos « sales » (§2.5, note T155) — ticket distinct.
- Divergence d'une branche `dev-*`/libre avec son propre `origin/<branche>`.
