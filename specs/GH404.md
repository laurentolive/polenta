# GH404 — Objet d'un autre repo : index en mémoire mis à jour dans le mauvais repo

Bug (#404), repéré pendant #399. Lié : #255 / #269 (une campagne ne contient que les tests de son repo).

## Root cause

Les services d'écriture résolvent le repo qui porte l'objet (`targetRepo`, via
`SchemaService.resolveComponentRepoPath` sur l'`objectTypeRef`) et y écrivent le fichier, mais
mettent ensuite à jour l'index en mémoire du **repo appelant** (`repoPath`). Quand les deux
diffèrent (objet typé sur un composant en repo séparé, `<nom de montage>::<type>`) :

- l'index du repo appelant reçoit un objet / une exécution absente de ses fichiers (visible dans
  ses listes jusqu'à la prochaine reconstruction de cet index) ;
- l'index du repo de l'objet ne le voit qu'à sa reconstruction (watcher, redémarrage).

Le défaut n'était pas limité à la ligne citée dans l'issue : le même motif
`writeYaml(targetRepo, …)` suivi de `upsert(repoPath, …)` existait à cinq endroits.

| Écriture | Fichier | Avant | Après |
|---|---|---|---|
| Exécution d'un test (run) | `tests.service.ts` `execute` | `upsertRun(repoPath)` | `upsertRun(targetRepo)` |
| Création / modification d'un test | `tests.service.ts` `persist` | `upsertTestCase(repoPath)` | `upsertTestCase(targetRepo)` |
| Création / modification / transition d'une exigence | `requirements.service.ts` `persist` | `index.upsert(repoPath)` | `index.upsert(targetRepo)` |
| Création / modification / transition d'une issue | `issues.service.ts` `persist` | `upsert(repoPath)` | `upsert(targetRepo)` |
| Marquage `needsRevalidation` (T172) | `revalidation.service.ts` `writeElement` | `upsert(p)` | `upsert(targetRepo)` |

Les autres écritures d'index (`rewriteObjects`, `updateHistory`, campagnes, liens) écrivent et
indexent le même repo : non concernées.

## Appelants qui peuvent passer un repo différent du repo de l'objet

- **Exécution saisie dans l'application** (`tests:execute`, route
  `campaign.$campaignId_.execute.$testId`) : `repoPath` = repo de la campagne. GH255 limite une
  campagne aux tests de son repo ; une campagne antérieure peut encore contenir un test de composant.
- **Import du classeur d'exécution** (`CampaignExecutionService.apply`) : même `repoPath` (campagne).
- **Import JUnit** (`ResultsImportService.importJunit`) : appelle `execute` avec le repo du test
  (`target.repoPath`), sans `workspaceDir` — déjà correct, inchangé.
- **MCP** (`bulk_import_*`, `update_*`, `create`… avec `container.workspaceDir`) : `repoPath` = repo
  ouvert, objet typé sur un composant → écrit dans le composant. C'est ce chemin qui faisait entrer
  un test de composant dans l'index du produit (processus MCP), puis rendait possible son exécution
  « depuis le produit » avec cet index.
- **Revalidation** (`markImpactedBy`) : parcourt les repos du workspace ; `targetRepo` recalculé
  depuis le type de l'élément.
- Le renderer appelle `create` sans `workspaceDir` : même repo, non concerné.

Aucun écran du repo appelant ne dépend de la copie erronée : les vues lisent les objets d'un
composant dans l'index du repo du composant (`resolveTreeTarget`, `executionHistory`, JUnit,
liens inter-repos). Seul l'index du repo de l'objet est donc mis à jour.

Effet de bord voulu : un test de composant n'est plus « trouvable » depuis l'index du produit
après sa création par le produit ; il ne l'était déjà plus après un redémarrage. Exécuter un test
de composant depuis une campagne du produit reste refusé comme avant (`Test case … not found`),
conformément à GH255.

## Correctif

Les cinq mises à jour d'index ciblent `targetRepo`, le repo dont le fichier vient d'être écrit
(identique à `repoPath` dans le cas courant d'un objet du repo ouvert : aucun changement de
comportement hors workspace).

## Tests

`apps/desktop/src/main/services/index-target-repo.gh404.test.ts` — deux repos (produit, composant
`comp`), `resolveComponentRepoPath` qui range `comp::…` dans le composant, index des deux repos
construits avant l'écriture :

1. exécution d'un test typé `comp::test` depuis le produit : run écrit dans le composant, indexé
   dans le composant, absent de l'index du produit ;
2. même exécution : index en mémoire des deux repos identiques à une reconstruction depuis le disque ;
3. test créé depuis le produit : indexé dans le composant seulement ;
4. exigence créée depuis le produit puis modifiée : indexée dans le composant seulement ;
5. issue créée depuis le produit : indexée dans le composant seulement ;
6. revalidation : le flag posé sur une exigence du composant met à jour l'index du composant.

Les 6 tests échouent sans le correctif, passent avec.

## Comment vérifier

- Automatique : `npx vitest run src/main/services/index-target-repo.gh404.test.ts` (dans `apps/desktop`).
- Manuel : le symptôme n'est pas observable par un parcours ordinaire de l'interface (le renderer
  écrit dans le repo affiché ; le serveur MCP est un autre processus, sans watcher, qui relit ses
  index à chaque appel). La vérification manuelle est donc une **non-régression**, dans un workspace
  produit + composant en repo séparé (application desktop) :
  1. Dans une campagne du produit, puis dans une campagne du composant, exécuter un test : le
     résultat apparaît aussitôt dans l'historique d'exécution du test et dans la campagne.
  2. Importer un classeur d'exécution et un rapport JUnit sur ces campagnes : mêmes résultats visibles
     sans redémarrage.
  3. Créer et modifier un test, une exigence et une issue dans le produit et dans le composant ;
     repasser une exigence approuvée en brouillon (revalidation des éléments liés) : listes et flags
     à jour sans redémarrage, aucun objet du composant dans les listes du produit.
