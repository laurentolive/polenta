# GH414 — Bouton Rafraîchir à côté de « Publier » : retard et merge de l'intégration

Issue : #414 (type:feature). Validée par l'humain dans l'issue (version « merge uniquement »).

## Problème

Un utilisateur qui modifie des fichiers sur l'intégration bascule sur `dev-auto` (GH173). Tant qu'il
n'a pas publié, la branche de travail diverge de l'intégration : l'intégration avance sur origin
(auto-pull), mais la branche de travail reste sur l'ancien commit. « Publier » fusionne alors tout
au dernier moment, avec des conflits découverts tard.

L'auto-pull ne fait jamais avancer une branche qui a des modifications non commitées. Le bouton
« Rafraîchir » du panneau Version (T153) fait un `pull` sur la branche courante, mais il est désactivé
dès qu'il y a des modifs, et il cherche `origin/<branche de travail>`, qui n'existe pas pour
`dev-auto`. Sur une branche de travail, il ne fait donc rien.

Ce cas touche d'abord les utilisateurs sans git : ils ne créent pas de branche, `dev-auto` est créée
automatiquement, et leurs commits de la vue arbre y atterrissent.

## Comportement attendu

### Affichage (sans clic)

- Un bouton **Rafraîchir** à côté de « Publier » (dans `ModificationControl`).
- Il affiche discrètement le nombre de commits de l'intégration absents de la branche courante.
  Une info-bulle l'explique (« 3 commits de l'équipe à récupérer »).
- Le compteur lit les refs locales (poll 3 s) : il reflète le dernier fetch, c'est-à-dire le dernier
  tick de l'auto-pull ou le dernier clic. Pas de fetch à l'ouverture du projet (décision documentée
  dans `useAutoPull`) : le compteur attend donc le premier tick.
- Visible quand le mode est `active` (intégration ou branche de travail), masqué sinon.
- Si l'intégration diverge, le bouton l'indique (la résolution passe par « Resynchroniser »).

### Au clic — sur une branche de travail

1. **Fetch** de origin.
2. **Intégration divergée** : « Resynchroniser » existant (GH39). Fusion propre : faite et poussée.
   Conflit : les commits locaux sont mis de côté sur `dev-resync`, l'intégration est recalée sur origin.
   **Intégration en retard** (sans commit local) : fast-forward par référence.
3. **Rien à récupérer** (aucun commit de l'intégration absent de la branche) : fin, rien n'est écrit.
4. **Modifs non commitées** : commit WIP sur la branche de travail (tout l'arbre, message fixe
   `WIP — Rafraîchir (GH414)`), pour que l'arbre soit propre.
5. **Merge** de l'intégration dans la branche de travail (`mergeInto`).
   - Sans conflit : fusion faite. Les commits de la branche sont conservés.
   - Avec conflit : rien n'est écrit (le merge est calculé sur les objets git). Ouverture de la
     résolution de conflits existante (GH37), origine `merge` (`from` = intégration, `into` = branche),
     avec la référence du commit WIP.
6. **Terminer** la résolution : commit de merge sur la branche de travail (comportement GH37 existant).
7. **Abandonner** la résolution : la fusion n'a jamais été écrite ; le commit WIP est défait
   (`reset` de la branche sur son parent, index remis en non indexé pour les fichiers du WIP). Le
   contenu de l'arbre et la branche courante reviennent à l'état d'avant le clic.

### Au clic — sur la branche d'intégration

Pas de WIP, pas de merge. Fetch puis mise à jour de l'intégration (`autoSync`, même chemin que l'auto-pull).

Si l'intégration avait des modifs en cours, l'auto-pull les a déplacées sur `dev-auto` (GH173) : la
mise à jour de l'intégration peut alors ne pas avancer la branche de travail. Le clic reprend donc le
parcours « branche de travail » sur `dev-auto` : le commit de l'équipe arrive dans l'arbre, pas seulement
dans la ref de l'intégration.

### Choix assumés

- **Un seul comportement : merge, jamais de rebase.** Pas de réécriture d'historique, pas de
  distinction entre branches poussées et non poussées.
- Chaque clic peut ajouter un commit de fusion sur la branche de travail. Accepté.
- « Abandonner » ne défait pas une resynchronisation déjà faite : elle ne détruit rien (les commits
  locaux restent sur `dev-resync`). Le message de l'interface le précise.
- Le compteur et le bouton portent sur **le dépôt concerné** (celui de « Publier » en mode `active`),
  pas sur tous les dépôts du workspace. Les autres dépôts restent gérés par « Publier » et l'auto-pull.
- Le bouton T153 du panneau Version est **conservé tel quel** (il sert au cas propre sur la branche
  d'intégration). La question de son remplacement est reportée.

## Hors scope

- Rebase, force-push, merge automatique dans l'auto-pull.
- Traitement multi-dépôts du bouton.
- Retrait du bouton T153 du panneau Version.

## Pré-requis

- Git embarqué (GH337) : le merge passe par `isomorphic-git` (objets) et `mergeInto` ; aucun appel
  au `git` du PATH n'est ajouté. `sync.rebase` (vue graphe) n'est pas touché.

## Critères d'acceptation

- [ ] Le compteur affiche le nombre de commits de l'intégration absents de la branche courante, avec une info-bulle explicative.
- [ ] Sur la branche d'intégration, le bouton ne fait ni WIP ni merge.
- [ ] Sur une branche de travail propre et en retard : le merge ajoute les commits de l'intégration, les commits de la branche sont conservés.
- [ ] Sur une branche de travail avec modifs non commitées : un commit WIP est créé avant le merge, et les modifs sont présentes et identiques après.
- [ ] Intégration divergée : « Resynchroniser » est appliqué avant le merge (fusion propre, ou mise de côté sur `dev-resync`).
- [ ] Conflit : aucune écriture avant « Terminer » ; la résolution s'ouvre ; « Terminer » crée le commit de merge sur la branche.
- [ ] « Abandonner » après conflit : branche, HEAD et contenu de l'arbre identiques à l'état d'avant le clic ; les modifs sont non indexées.
- [ ] Rien à récupérer : aucun commit créé, aucune écriture.
- [ ] Le merge passe par les objets git ; aucun appel au `git` du PATH.
