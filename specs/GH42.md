# GH42 — Vue graphe : un merge réussi dans la branche courante laissait le working directory désynchronisé

Issue : #42 — `type:bug` (trouvé pendant GH37 sprint 3)

## Root cause

`SyncService.merge()` (vue graphe → « merger dans la branche courante ») et `mergeInto()`
appellent `git.merge` d'isomorphic-git. En cas de succès, merge réel comme fast-forward, cette
fonction **ne fait qu'avancer la ref** de la branche cible : ni l'index ni le working directory ne
sont mis à jour. Quand la cible est la branche checkoutée, le WD et l'index restent sur l'ancien
arbre. `git status` montre alors l'apport du merge comme des modifications stagées inverses (par
exemple `D  b.txt` pour un fichier apporté par la branche mergée), et **le prochain commit
(Publier, commit manuel) annule silencieusement le merge**.

Les autres appels à `git.merge` (`pull` réécrit par GH37, auto-pull, resync GH39) faisaient déjà
leur propre `checkout` : ils ne sont pas concernés. Publier appelle `mergeInto` depuis la branche
de travail, la cible (intégration) n'étant pas checkoutée : pas concerné non plus.

## Correctif appliqué

`apps/desktop/src/main/services/sync.service.ts` : `merge` et `mergeInto` passent par un
`mergeBranch(repoPath, from, into)` commun. Quand `into` est la branche checkoutée :
- **avant** : l'arbre doit être propre, sinon erreur `Uncommitted changes — cannot merge` et rien
  ne bouge. L'UI n'affichait déjà « merger » que sur un arbre propre, mais d'après un statut
  rafraîchi toutes les 3 s. La garde est revérifiée ici, parce que le checkout forcé qui suit
  écraserait une modification locale.
- **après** un succès qui a avancé la ref : `git.checkout({ ref: into, force: true })` réaligne
  le working directory et l'index sur le nouveau HEAD.

Quand `into` n'est pas checkoutée, le comportement est inchangé (pas de garde, WD intact).

## Comment vérifier

Script de vérification hors repo (isomorphic-git réel sur des repos temporaires), tous verts :

| Cas | Attendu | Résultat |
|---|---|---|
| Merge réel `feat` → `main` (courante) | fichier apporté présent sur disque, `git status` vide | ✔ |
| Fast-forward `feat` → `main` (courante) | idem | ✔ |
| `mergeInto(feat, main)` avec `main` checkoutée | idem | ✔ |
| `mergeInto(dev, main)` depuis `dev` avec une modification locale (cas Publier) | merge fait sur `main`, modification locale intacte | ✔ |
| Merge dans la branche courante avec une modification non commitée | refus, `main` non avancée, modification conservée | ✔ |

À la main : vue graphe, deux branches divergentes, sur `main` → menu de l'autre branche →
« Merger dans la branche courante ». Les fichiers apportés apparaissent sur disque et le panneau
Version n'affiche aucune modification en attente. Publier ensuite ne défait rien.

`tsc --noEmit` (apps/desktop) : 0 erreur.
