# GH428 — Champs d'exécution saisis en campagne (entrées) et colonnes configurables

> **Statut : spec proposée, à valider** (STOP HUMAIN). Aucun code avant validation des décisions §8.
> Repères : `specs/GH196.md` (champs d'exécution, `runFields`), `specs/GH202.md` (version testée),
> `specs/SPEC-TESTS.md` §3.2 (TestRun) et §4.2 (entrées de campagne), `specs/GH389.md` (grilles communes).

## But

Aujourd'hui un champ d'exécution (`runFields`) n'est saisi qu'au moment du résultat, par le testeur.
Le responsable de campagne doit pouvoir **renseigner à l'avance** certains de ces champs, sur chaque
entrée de campagne : par exemple la criticité et la quantité d'une instance de test.

Ces valeurs restent des données du **run** : elles sont copiées dans le run à l'exécution, puis figées
avec lui. Les autres champs d'exécution restent des résultats saisis par le testeur. Un même champ
d'exécution peut donc être un **entrant** (renseigné en campagne) ou un **résultat** (renseigné à
l'exécution), selon sa propriété.

## Principes

- **Ni le test ni sa copie ne changent.** Aucune surcharge sur `testSnapshot` : la copie reste celle de
  GH68 / GH81, remplacée à la saisie du résultat comme aujourd'hui.
- **Un run reste immuable** (GH196 §10). Une valeur d'entrée modifiée plus tard ne réécrit aucun run.
- **Une valeur d'entrée appartient à l'entrée de campagne**, pas au test : deux campagnes peuvent
  tester le même test avec des quantités différentes.

## Décisions

| # | Question | Proposition (à valider) |
|---|---|---|
| Q1 | Comment marquer un champ renseigné en campagne ? | Propriété `campaignInput: true` sur un champ de `runFields` (écrite seulement si vraie). Sans elle, le champ reste un résultat saisi par le testeur |
| Q2 | Où stocker la valeur avant l'exécution ? | Sur l'entrée de campagne (`runInputs`). Ni dans le test, ni dans sa copie |
| Q3 | Que se passe-t-il si la valeur change après un run ? | Les runs existants restent figés. La nouvelle valeur s'applique aux exécutions suivantes (retest de la même entrée). La grille affiche la valeur du dernier run à côté |
| Q4 | Où contrôle-t-on un champ d'entrée obligatoire ? | À l'exécution : refus avant toute écriture (comme GH196), et non à la saisie en campagne, qui reste libre |
| Q5 | Classeur Excel de la campagne | Les entrées exportent leurs valeurs pré-remplies. À l'import, la valeur du classeur est figée dans le run ; l'entrée n'est pas réécrite |
| Q6 | Colonnes visibles par défaut dans la grille | Réutiliser `defaultVisible` (GH139) tel quel |
| Q7 | Types admis en entrée | `text`, `number`, `enum`, `boolean`, `date` (éditables en cellule). Les autres types sont refusés à l'enregistrement du schéma |
| Q8 | Vue Exécutions (GH400) | Inchangée : lecture seule, puisqu'elle ne lit que des runs |

## 1. Schéma

- Propriété `campaignInput` sur les `runFields` du type de test. Écrite seulement si vraie, comme
  `defaultVisible` (GH139). Refusée sur `stepFields`.
- Refus à l'enregistrement du schéma si le type du champ n'est pas admis (Q7).
- Le nom reste unique dans le projet (GH196 Q4 ; pas de changement).
- Éditeur de schéma : case « Renseigné en campagne » dans la section « Champs d'exécution ».

## 2. Données de l'entrée

- Nouveau champ optionnel sur `CampaignTestRun` : `runInputs?: Record<string, string>`, indexé par nom
  de champ `campaignInput`. Absent tant que vide. Stocké dans `campaigns/<ID>.yaml`.
- Jamais écrit dans `testSnapshot`, ni dans `history`.
- Mise à jour par une méthode du service de campagne (nom à fixer en design). Même contrôle que la
  saisie d'un run : clé inconnue, valeur illisible → refus, rien n'est écrit.
- Entrée retirée (`removedRuns`) : non modifiable.

## 3. Exécution

- Page d'exécution : les champs `campaignInput` sont pré-remplis avec `runInputs`, affichés en lecture
  seule, libellés « renseigné en campagne ». Les autres champs d'exécution sont saisis comme aujourd'hui.
- `TestsService.execute` : prend les valeurs d'entrée de l'entrée de campagne, les fusionne avec les
  saisies de résultat, puis applique `prepareRunFields` sur le tout. Un champ d'entrée obligatoire absent
  donne `required_field_missing` (Q4) et rien n'est écrit.
- Les valeurs d'entrée utilisées sont copiées dans `run.fields`, sous leur nom. Le run est alors
  autonome : il ne lit plus l'entrée pour ses valeurs.

## 4. Grille des entrées de campagne

- Une colonne par champ de `runFields` du type de test, clé `run:<nom>` comme dans la Vue Exécutions.
  Elles entrent dans le panneau 👁 (GH389 §1.4) ; ordre et visibilité dans la préférence de la grille
  (`grid::campaign-entries`).
- Visibilité par défaut : `defaultVisible` (Q6).
- Valeur d'une colonne :
  - champ d'entrée : `runInputs` de l'entrée, **éditable** (double-clic, F2 ou Entrée ; éditeur selon le
    type, `GridEditor`, GH389) ;
  - champ de résultat : valeur du dernier run de l'entrée (`runId`), lecture seule, vide sinon.
- Ligne exécutée : la saisie reste possible et s'applique aux runs suivants (Q3). Une indication
  « dernier run : <valeur> » apparaît quand la valeur saisie diffère de celle du dernier run.
- La grille commune gère déjà l'édition de cellule (`onCellEdit`, utilisé par la Validation) : pas de
  nouveau mécanisme.

## 5. Vue Exécutions et classeur Excel

- Vue Exécutions (GH400) : inchangée (Q8).
- Classeur d'exécution de la campagne (format v4, GH202) : les colonnes `run:<nom>` des champs
  d'entrée sont pré-remplies à l'export. À l'import, la valeur du classeur est figée dans le run, sans
  réécrire l'entrée (Q5). Reste à décider en design si le format change de version.

## 6. Hors périmètre

- Surcharge des champs du test par entrée : écartée (voir discussion du ticket), car elle entre en
  conflit avec la copie figée et la resynchronisation.
- Rôles et droits : Polenta n'a pas de modèle de rôle. Toute personne qui peut éditer la campagne peut
  saisir les entrées.
- MCP : création d'entrées et exécution inchangées. La saisie de `runInputs` par MCP n'est pas couverte.
- Migration : aucune, la propriété et la clé sont optionnelles.
- Projet « Lave-linge » : `Criticité` (type `text`) et `quantité` ne sont pas touchés par ce ticket.
  Leur passage en `enum` / `number` relève du schéma du projet.
- Criticité calculée par release (option B de la discussion) : hors périmètre, sujet distinct.

## 7. Vérification (plan)

- **Unitaires** (niveau 1) :
  - schéma : `campaignInput` refusé hors `runFields` et sur un type non admis ;
  - `prepareRunFields` : valeurs d'entrée reprises, obligatoire absent refusé ;
  - `TestsService.execute` : `runInputs` copiés dans `run.fields` ; un run existant reste identique après
    modification de `runInputs`.
- **E2E** (niveau 2, `apps/desktop/e2e-web/gh428-run-inputs.spec.ts`) :
  1. créer une campagne avec un type de test à un champ d'entrée ;
  2. saisir la valeur dans la grille, vérifier la persistance dans le fichier de campagne ;
  3. exécuter : la page affiche la valeur en lecture seule, le run la contient ;
  4. modifier la valeur, réexécuter : nouveau run avec la nouvelle valeur, ancien run inchangé.
- Le niveau 3 se lance au merge sur `main`, après validation humaine.
