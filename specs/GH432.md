# GH432 — Test repo-conformity.gh340 : dépassement de délai en suite complète (blocage Git à expliquer)

## Statut

**Cause établie au niveau mesuré** : les attentes viennent de git lui-même, à l'écriture de nouveaux
objets. **Couche exacte non démontrée** (antivirus ou système de fichiers) : la preuve demande une
exclusion antivirus, donc des droits administrateur. Pas de correctif dans ce lot : la décision revient
à l'humain (voir « Décision à prendre »).

## Ce que le journal de blocage montre

Suite unitaire complète, quatre runs, `POLENTA_GIT_HANG_LOG` activé (journal de ce qui attend plus de 10 s,
avec horodatage, appelant, pid, état CPU et threads Windows) :

- Une seule forme d'attente longue, la même dans les quatre runs : `git add -A --pathspec-from-file=-`
  dans le dépôt de `version-requirements.gh439` (1 500 exigences écrites puis commitées). Durée : 19 à 29 s.
- Au moment de l'attente : CPU de git ~10 % (3,06 s → 4,56 s sur 16 s), ses trois threads en
  `Wait/EventPairLow`. Git ne calcule pas : il attend une ressource du système.
- À la fin : code 0, et **fermeture des tuyaux 0 ms après la fin de git**. Le mécanisme des tuyaux
  hérités (`EXIT_DRAIN_MS`) n'est donc pas en cause ici.
- Un `git fetch` de 8,4 s, identique à chaque run : c'est le délai voulu du test `fetch-queue.gh337`
  (serveur muet). Ce n'est pas un blocage.
- `repo-conformity.gh340` n'apparaît dans aucun journal de ces runs ; ses dépassements passés se
  situent dans la même famille (beaucoup d'objets créés par test).

## Ce que les expériences isolées établissent

Scripts dans le dossier de travail de session, sans suite vitest. Dépôt de 1 500 fichiers `.yaml`,
`git add -A` après avoir vidé l'index (donc relecture et écriture de tous les objets) :

| Expérience | Résultat |
|---|---|
| `git add -A` à froid, fichiers neufs | 18 à 21 s (trois cycles), 10 à 20 s selon la mesure |
| Second `git add -A` (objets déjà écrits) | 0,7 à 2 s |
| Attente de 0, 8 ou 25 s après l'écriture | 19 à 21 s dans les trois cas : pas un backlog asynchrone |
| Même chose avec 6 lanceurs git concurrents | à froid : 10 s, à chaud : 0,7 s : pas de contention entre processus |
| Lecture Node de 1 500 fichiers neufs | 0,73 s (`fs.readFileSync`) |
| Création Node de 1 500 fichiers | 0,4 à 0,6 s |
| Node : tmp + renommage, tmp + lien | 1,3 à 1,5 s |
| Options git (`core.fsync`, `core.fsyncObjectFiles`, `core.preloadIndex`, `index.threads`) | aucun gain fiable : 10 à 12 s, avec des valeurs par défaut elles-mêmes variables |

Conclusion de ces mesures : le coût est propre à la façon dont git écrit les objets loose (un fichier
neuf par blob), pas à la création de fichiers en général ; il n'est pas dû aux threads ni au `fsync`
seul ; il est payé une seule fois par fichier (la seconde écriture est rapide). Il est présent sans aucune
concurrence.

## Ce qui n'est pas établi

- **La couche qui coûte** : Windows Defender (protection temps réel active, `Get-MpComputerStatus`) est le
  suspect principal. Son CPU (`MsMpEng`) n'est pas lisible sans droits administrateur, donc non mesuré.
- Pourquoi git paie ce coût et une lecture Node non : le motif d'écriture de git (création, écriture,
  liaison, suppression du temporaire) est proche de celui testé en Node (1,3 s pour 1 500). Une trace
  système (ETW, Process Monitor) permettrait de voir l'appel qui attend.
- Le délai de 20 s : le test gh173 `beforeEach` (`git init --bare`, `clone`) a expiré sans entrée dans le
  journal. `trackPending` ne couvre que `runGit` ; les appels faits directement par les helpers de test
  (`execFile`) n'y figurent pas. Le journal est donc aveugle à une partie des appels git de test.

## Décision à prendre

1. **Vérifier la couche** (administrateur requis) : exclure le dossier temporaire des tests de l'analyse
   Défender, puis relancer l'expérience « froid / chaud » à 1 500 fichiers. Si le froid tombe sous 2 s,
   Défender est confirmé et la solution est une exclusion pour le dossier de test (décision de sécurité
   à prendre par l'humain, pas par l'agent).
2. **Réduire le coût dans les tests** : moins d'objets par test (la suite de volume gh439 écrit 1 500
   exigences ; 300 suffiraient pour le test de limite, à confirmer), ou un fichier de test à part pour les
   volumes.
3. **Parallélisme** : `maxThreads` de vitest pour les fichiers qui créent beaucoup d'objets. Ne règle pas
   la cause, réduit seulement la charge simultanée.

Piste écartée par les mesures : l'héritage des tuyaux (aucun tuyau retenu dans les attentes observées) et
le `fsync` seul (gain partiel et non reproductible).
