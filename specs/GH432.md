## Mécanisme déjà documenté dans le code

Sous Windows, les tests vitest lancent git depuis plusieurs threads d'un même processus. Un processus
lancé en même temps par un autre thread hérite des tuyaux de sortie ; tant qu'il vit, la fin de
sortie d'un git déjà terminé n'arrive pas. `git-runner.ts` attend donc 500 ms (`EXIT_DRAIN_MS`) après la
fin de git, puis ferme les tuyaux : chaque appel git coûte alors au moins 500 ms en charge, et un
test qui enchaîne quelques dizaines d'appels dépasse 20 s. `cat-file-batch.ts` garde son processus 2 s
(`POLENTA_GIT_BATCH_IDLE_MS`, vitest.config). En production, git est lancé depuis un seul thread : le
mécanisme n'existe pas hors des tests.

## Ce qui reste à établir

- Pourquoi `git add -A` reste vivant 18 s : pour un dépôt de test, il devrait finir en quelques
  dizaines de millisecondes. Hypothèses non vérifiées : charge CPU de la suite (antivirus sur le
  dossier temporaire), attente d'un verrou, ou lecture de stdin. Le journal ne le dit pas ; il
  faudrait enregistrer l'état du processus au moment où il attend.
- Le lien entre ce blocage et les dépassements à 20 s de `repo-conformity.gh340` : pas établi.

## Pistes de correctif (décision à prendre)

1. Réduire le parallélisme des fichiers qui lancent git (`maxThreads` dans `vitest.config`) : moins
   de processus concurrents, donc moins d'héritage de tuyaux. Coût : durée de la suite.
2. Isoler les fichiers dans des processus (`pool: 'forks'`) : supprime l'héritage. Le pool forks a
   perdu des processus sous Windows (GH283), d'où le passage aux threads.
3. Fermer stdin explicitement et passer les chemins par `--pathspec-from-file=<fichier>` au lieu de
   stdin : supprime une attente sur stdin, mais ne règle pas la charge.

## Comment vérifier (quand un correctif sera choisi)

  20 s ; durée des fichiers ci-dessus en baisse ; journal sans `git` en attente de plus de 10 s.
- Aucune hausse du délai de test.
