# GH438 — Dashboard lu pendant son écriture : « introuvable » transitoire

## Root cause

`writeObjectFolder` (`apps/desktop/src/main/services/suivi-store.util.ts`) écrivait chaque fichier
d'un objet Suivi avec `fsP.writeFile`, qui tronque le fichier puis écrit. Une lecture dans cette
fenêtre voit un fichier vide : `yaml.load('')` renvoie `undefined`, `readYamlFile` renvoie `null`,
`DashboardsService.get` renvoie `null`, et la page affiche « Dashboard introuvable ».

Deux écrivains passent par ce helper, donc le correctif est dans le helper :
- `dashboards.service.ts` (`writeShared`) ;
- `saved-queries.service.ts` (requêtes partagées), même risque.

## Correctif appliqué

- `writeFileAtomic` : écriture dans `<fichier>.<hex>.tmp` (même dossier, même volume) puis
  `rename` sur la cible. Le nom unique évite que deux écritures concurrentes du même objet se
  marchent dessus. En cas d'échec, le temporaire est supprimé.
- `renameWithRetry` : sous Windows, renommer par-dessus un fichier qu'un lecteur tient ouvert
  échoue en `EPERM` tant que la lecture dure. Mesuré (script isolé, lecteur en boucle, 200
  écritures) : ~2 000 échecs `EPERM`, jusqu'à 86 tentatives pour un même écrit, **zéro** lecture
  vide ou en erreur. D'où un nouvel essai sur `EPERM`/`EACCES`/`EBUSY` : 200 tentatives de 5 ms au
  maximum (≈ 1 s), puis l'erreur remonte.
- Nettoyage des fichiers retirés : ignore les `.tmp` (ceux d'une écriture concurrente en cours ne
  sont jamais retirés).

## Comment vérifier

- Test `dashboards-atomic.gh438.test.ts` : 200 écritures successives de `update` pendant une
  lecture en boucle de `get`, cadencée à 1 ms (sans pause, le lecteur garde le fichier ouvert et les
  renommages échouent sans fin en suite complète) : aucune lecture ne renvoie `null`. Sur le code
  d'origine ce test échoue (plusieurs `null` mesurés). Seul : 3,3 s ; sous charge (gh340, gh414,
  gh439 en parallèle) : 2,4 s.
- Second test : aucun fichier `.tmp` ne reste dans le dossier de l'objet après 20 écritures.
- Tests voisins (dashboards, suivi, requêtes sauvegardées, MCP dashboards) : 17 fichiers, 242 tests
  verts.
- À la main : ouvrir un dashboard partagé, relâcher plusieurs poignées de taille l'une après
  l'autre : le dashboard ne doit jamais s'afficher « introuvable ».
