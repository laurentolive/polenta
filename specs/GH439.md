# GH439 — Version : liste des exigences du repo à la version (vue Excel), couverture, export Excel / PDF

> Issue #439. Besoin client : « dans une version produit, comment savoir ce qui est implémenté, comment avoir la
> liste d'exigences dans le produit ? ». Décisions de l'humain du 2026-11-25 : voir § 1.

## Contexte

Une version (GH201, SPEC-REQ §11) fige l'état d'un **repo** et liste ses **changements** (delta par rapport à la
version précédente). Aucun écran ne donne **toutes les exigences que la version contient** :

| Écran existant | Pourquoi il ne répond pas |
|---|---|
| Page d'une version, section « Changements » | delta seulement, pas le contenu cumulé |
| Colonne « Design » des vues exigence (GH210) | répond à « dans quelle version est cette exigence ? », pas à « que contient la version X ? » |
| Validation d'une version (GH204) | liste le périmètre à `freeze.sha`, mais c'est un outil de décision go/no-go : il faut créer une validation, la grille est faite pour décider, pas pour livrer |
| Graphe de données (`versions`, `designVersion`) | exploitable par un script, pas par un client |

La brique de lecture existe : `VersionsService.requirementsOf` lit les exigences d'un repo à l'état d'une version
(commit figé si elle en a un, disque sinon, avec le schéma du gel — GH266). Elle est aujourd'hui seulement appelée
par la validation. Ce ticket l'expose dans une grille dédiée, lisible sans validation, et exportable.

## 1. Décisions de l'humain (2026-11-25)

1. **« Implémenté » = l'indicateur de couverture** existant (`coverageStatus`, colonne « Vérification »). Aucun nouvel
   indicateur.
2. **Repo de la version seulement** : pas d'agrégation des exigences des composants ni des dépendances. Une version
   produit liste les exigences du repo produit.
3. **Vue Excel**, comme la vue exigence : même grille, colonnes configurables, filtres par colonne.
4. **Export Excel et PDF** depuis cette vue.
5. Livrables : spec, design, scénarios de test (cette phase). Pas d'implémentation avant la validation de la spec.

## 2. Écran « Exigences de la version »

### 2.1 Accès

- Nouvelle page `/version/<ID>/requirements` (même paramètres d'URL que la page d'une version).
- Bouton **« Exigences »** dans l'en-tête de la page d'une version (à côté des actions existantes). Sans compteur : le
  nombre exige de lire toutes les exigences, la page d'une version reste rapide.
- Retour à la page de la version par le lien de l'en-tête de la grille (label de la version, `PageLink`).
- Absent pour une version **abandonnée sans gel** (jamais released) : aucun état figé à lire, le disque ne représenterait
  pas la version. Une version abandonnée **avec** gel s'affiche à son gel.

### 2.2 En-tête

Titre « Exigences — <label de la version> », composant (repo), pastille d'état de la version (en cours / released /
abandonnée), puis :

| Version | Ligne d'information |
|---|---|
| Released (ou abandonnée avec gel) | « État figé au tag `<tag>` (<date de gel>) — Vérification et Design : état courant du repo » |
| En cours | « État courant du repo (la version n'est pas figée) » |

### 2.3 Grille

Grille commune (`DataGrid`, SPEC-SYSTEM-VIEW § Grilles communes, GH389), **en lecture seule** : une ligne par
exigence, ordre des ID (numérique), aucun tri.

| Colonne | Contenu | Défaut |
|---|---|---|
| `id` | lien d'élément (ouvre l'exigence courante) | visible |
| `title` | titre à l'état de la version | visible |
| `status` | libellé du statut dans le **schéma du gel** | visible |
| `objectTypeRef` | libellé du type d'exigence | masquée |
| champs du schéma | un par champ des types d'exigence du repo (texte affiché, richtext aplati) ; au moins les champs `defaultVisible` du type, sinon les trois premiers, comme la vue Tableau (`defaultVisibleFields`) | `defaultVisible` / trois premiers visibles |
| `version` | révision de l'exigence à l'état de la version (colonne système de la vue Tableau) | masquée |
| `coverageStatus` | **Vérification** : badge de couverture (`not_covered`, `covered`, `validated`, `failing`, `needs_revalidation`), mêmes libellés que la vue Tableau | visible |
| `tests` | IDs des tests liés (liens d'élément) | masquée |
| `designStatus` | **Design** : label de la première version released qui livre l'exigence à l'identique (GH204 §3), lien de page ; « — » sinon | masquée |
| `changedSince` | **Modifiée depuis** : « Oui » si le contenu courant diffère de celui de la version ; vide sinon. Version released seulement | masquée |

- **Barre d'outils** (ordre GH389) : filtres de l'écran, 👁 Colonnes, ↕▯ hauteur des lignes, Exporter, « affichées /
  total ». Pas de vues enregistrées d'équipe (grille sans type unique, hors périmètre).
- **Filtre par colonne** sur le texte affiché ; la couverture se filtre sur le libellé du badge (comme GH224). Les
  filtres ne sont jamais mémorisés.
- **Préférences** (colonnes visibles et ordre, largeurs, colonnes figées) : par utilisateur, dans le `.pref` du repo,
  grille sans type `grid::version-requirements`.
- **Double-clic / Entrée** sur une ligne : ouvre l'exigence (comportement commun).
- **Défilement** : mémoire GH300 par onglet + page + grille (`useGridScrollKey`).
- **Liste vide** (repo sans exigence, ou toutes terminales) : message « Aucune exigence dans cette version ».
- **Erreur de lecture** (commit figé absent, clone partiel) : message d'erreur, **jamais une liste vide**
  (`VERSION_NOT_FOUND`, comme GH204).

## 3. Données et règles

### 3.1 Périmètre

Exigences **du repo** de la version, **hors statut terminal** (même règle que la validation, SPEC-REQ §13) :

- version released ou abandonnée avec gel : lues à `freeze.sha`, avec le schéma de ce commit ;
- version en cours : lues sur le disque (état courant, affiché comme tel) ;
- un fichier dont l'`objectTypeRef` n'est pas déclaré par le schéma du repo (élément d'un autre composant copié là)
  est ignoré ; les sous-composants et dépendances ne sont **pas** parcourus (décision 2).

### 3.2 Couverture (« implémenté »)

La couverture est celle de la vue exigence : même calcul (`computeCoverageStatus`, SPEC-TRACEABILITY §2), même badge,
mêmes libellés. Elle est lue dans l'**état courant** du repo (liens, tests, exécutions), par ID d'exigence — comme les
colonnes live de la validation avant signature (GH204 §3). Pour une version released, c'est donc « où en est la
vérification aujourd'hui des exigences de cette version ». La colonne **Modifiée depuis** signale les lignes où ce
n'est plus la même exigence : la couverture courante porte alors sur un contenu plus récent (D2).

### 3.3 Design et « Modifiée depuis »

- **Design** : `VersionsService.designVersionsFor` (déjà calculé pour la validation) ; calculé seulement si la colonne
  est visible.
- **Modifiée depuis** : comparaison du YAML courant avec celui du gel, hors `history`, `needsRevalidation`
  (clé du backlog, SPEC-REQ §11.3) ; seulement pour une version figée, calculée seulement si la colonne est visible.

### 3.4 Principe GH79 — indicateur Polenta ou projet ?

| Colonne | Décision | Pourquoi |
|---|---|---|
| Vérification | Polenta (déjà calculée) | fonction de Polenta (couverture test ↔ exigence) |
| Design | Polenta (déjà calculée) | fonction de Polenta (GH204, GH210) |
| Modifiée depuis | Polenta (même clé que le backlog) | sert le backlog et la validation (« contenu changé ») ; aucun nouvel agrégat |
| Compteurs par statut de couverture (ex. « 80 % couvertes ») | **hors Polenta** | indicateur de suivi : script ou tableau de bord côté projet (le graphe expose déjà tout) |

Rien n'est stocké : la liste est calculée à la demande.

## 4. Export

Bouton **Exporter** de la barre d'outils, formats **Excel** et **PDF**. Les deux reflètent **ce qui est affiché** : lignes
filtrées dans l'ordre, colonnes visibles dans l'ordre, texte affiché.

### 4.1 Excel (xlsx)

- Feuille de données : mêmes règles que l'export de grille (GH389 §1.10) — en-tête gras, volets figés, largeurs
  proches de l'écran ; nom de feuille = titre de la grille (31 caractères au plus).
- **Feuille « Version »** (identification du livrable) : composant, label de la version, état, tag, date de gel,
  commit figé, nombre d'exigences exportées / total, date d'export. Un classeur remis à un client se suffit à
  lui-même.
- Nom de fichier proposé : `<repo>-<label de la version>-exigences.xlsx`.

### 4.2 PDF

- Tableau statique des mêmes lignes et colonnes (aucun contrôle interactif, aucun lien cliquable obligatoire), **A4
  paysage**, marges `PRINT_MARGIN_MM`.
- Bloc d'identification en tête (mêmes informations que la feuille « Version »), **ligne d'en-tête du tableau répétée
  à chaque page**, aucune ligne coupée entre deux pages, **pied de page « page n / N »**.
- Nom de fichier proposé : `<repo>-<label de la version>-exigences.pdf`.
- Produit comme les autres PDF de l'application : route imprimable `/print/version-requirements` rendue par la
  fenêtre cachée (desktop) ou Chromium headless (web).

### 4.3 Droits et état de la version

Lecture seule : l'export est possible sur toute version lisible, y compris sur un composant en lecture seule. Aucun
fichier du repo n'est écrit.

## 5. Client web

La page, la grille et les deux exports sont disponibles sur le client web (versions et validation y sont déjà, GH252) :
nouveau canal `versions:requirements` dans la liste blanche, PDF par Chromium headless.

## 7. Décisions proposées (à valider avec la spec)

| # | Question | Recommandation | Pourquoi |
|---|---|---|---|
| D1 | Que contient « la liste d'une version » ? | toutes les exigences non terminales du repo à l'état de la version (pas seulement `changes`) | c'est la question du client ; `changes` n'en est que le delta |
| D2 | Couverture d'une version released | état **courant**, avec colonne « Modifiée depuis » pour lever l'ambiguïté | recalculer la couverture au gel exige de relire liens, tests et exécutions à un commit (nouvelle brique, coût) ; GH204 a la même règle jusqu'à signature, et la validation signée garde la copie figée (`atSignature`) |
| D3 | Colonne « Modifiée depuis » | incluse, masquée par défaut | évite de lire une couverture comme celle d'un contenu qu'elle ne concerne plus ; clé déjà calculée (backlog) |
| D4 | Colonne Design | incluse, masquée par défaut ; pas de colonne Validation | la décision porte sur la couverture ; la validation a son écran |
| D5 | Emplacement | page dédiée (grille pleine hauteur), pas une section de la page version | la grille de ce volume n'a pas sa place dans une section bornée ; même motif que le backlog (`versions_.backlog`) |
| D6 | Contenu de l'export | ce qui est affiché + identification de la version (feuille « Version », bloc d'en-tête PDF) | un livrable client doit dire de quelle version il parle |
| D7 | Version abandonnée sans gel | pas d'accès | le disque ne représente pas cette version |
| D8 | MCP | hors périmètre ; ticket séparé si besoin | lecture seule, aucune dépendance |

## Critères d'acceptation

1. Les cas U1 à U18 se vérifient (U17 sur le client web).
2. La liste d'une version released est identique avant et après une modification de l'exigence sur le disque
   (contenu et statut du gel), seules Vérification, Design et Modifiée depuis suivent l'état courant.
3. Aucune lecture de design ni de « modifiée depuis » quand la colonne n'est pas visible.
4. L'export Excel et l'export PDF contiennent exactement les lignes et colonnes affichées (filtres compris).
5. Aucune écriture dans le repo (ni fichier de version, ni tag, ni préférence hors `.pref`).
6. SPEC-REQ §11, SPEC-SYSTEM-VIEW (tableau « Grilles communes »), SPEC-WEB §11 et SPEC-INDEX à jour.

## Hors périmètre

- Exigences des composants et dépendances (décision 2) ; matrice par composant.
- Couverture recalculée **au gel** (D2) ; copie de la couverture dans le fichier de version.
- Compteurs et pourcentages de couverture (indicateurs de suivi, GH79).
- Vues enregistrées d'équipe (GH203) de cette grille.
- Colonne Validation, tests et issues dans la liste, exigences terminales (option « inclure les obsolètes »).
- Diff entre deux versions de la liste (voir « Voir les modifications », GH201).
- Outil MCP de lecture (D8).
- Export Word et gabarits client (GH34) pour cette vue.
