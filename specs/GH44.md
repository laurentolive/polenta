# GH44 — Client web de Polenta

Issue : #44 — `type:feature` — dépendance #45 **livrée** (merge `c4061c9`, 2026-10-10) : les
prérequis des sprints 3 et 4 sont satisfaits. Apports et impacts : § « Apports de #45 » ci-dessous.

## Contexte

Un client veut utiliser Polenta **depuis un navigateur**, sans installer l'application desktop
Electron. Son serveur git sera la forge auto-hébergée de #45 (Forgejo derrière Caddy, sur un VPS),
qui porte aussi les comptes, les équipes et les droits.

Constats dans le code (main @ c936c2c) :

- Le renderer desktop parle au process main **uniquement** via un pont générique :
  `window.polenta.invoke(channel, ...args)` / `on(channel, cb)` (preload, 26 lignes), encapsulé par
  `createIpcClient()` de `@polenta/api-client` (~196 channels, `ipc/index.ts`). Aucun composant
  React n'appelle Electron directement.
- Les services main **n'ont pas d'état global de workspace** : tout est paramétré par le chemin du
  repo. L'état par utilisateur vit dans `userData` (`auth.json`, `app-settings.json`,
  `workspace.json` des récents, `merge-drafts/`) et dans keytar (jetons).
- Le serveur MCP (`apps/desktop/src/mcp-server/`) prouve déjà que le noyau de services tourne
  dans un process Node sans Electron (`electron-shim.ts`).
- Couplage Electron résiduel, à remplacer côté web :
  - dialogues natifs `dialog.showOpenDialog` / `showSaveDialog` : `dialog:pick-folder`,
    `dialog:pick-image-file` / `image:pick-file`, `dialog:pick-drawio-file`, exports (enregistrer
    sous), import du classeur d'exécution de campagne (GH36) ;
  - `shell.openPath` / `showItemInFolder` / `openExternal` : `drawio:open-external`,
    `export:open-file`, page de release ;
  - événements poussés `webContents.send` : `repo:file-changed`, `update:state-changed`,
    `menu:open-workspace`, `menu:close-project` ;
  - `BrowserWindow` hors écran : export PDF (`pdf.util.ts`, `printToPDF`) et instantané drawio
    (`drawio-snapshot.ts`) ;
  - auto-update (`electron-updater`), lancement du serveur MCP local.
- `apps/web` (Vite + Auth0) et `apps/api` (NestJS) sont des squelettes du commit initial, jamais
  maintenus (2 300 lignes, modèle de données antérieur à T130). L'analyse #45 §8 recommande de
  **remplacer** Auth0, pas de le réutiliser.

Décisions prises avec le demandeur (2026-10-08) :

| Sujet | Décision |
|---|---|
| Périmètre V1 | **Parité desktop** : même UI, mêmes vues, mêmes règles métier. |
| Hébergement | **On-premise client**, sur le même VPS / compose que la forge de #45. *(Révisé 2026-10-11 : l'hôte de #45 sert une instance de forge isolée par client derrière un Caddy commun ; le client web est une instance `polenta-web` **par instance de forge**, profil compose `web`.)* |
| Authentification | **Par la forge** (jeton de l'utilisateur) — cf. #45 : Forgejo fournisseur d'identité unique, OIDC pour le web. |
| Concurrence | **Un clone par utilisateur** côté serveur, comme N postes desktop ; la synchro passe par git. |

l'image `polenta-web` est construite **par marque**.

## Description fonctionnelle

Polenta Web est **la même application** que le desktop, servie par un serveur Node et affichée
dans un navigateur. L'utilisateur se connecte avec son compte de la forge ; le serveur ouvre pour
lui, dans un espace disque qui lui est propre, des clones des repos auxquels il a accès ; il
consulte, édite, publie, exécute des campagnes, exporte — comme sur le desktop. Ses commits sont
à son nom et poussés avec son jeton : la forge applique exactement les mêmes droits que pour le
desktop.

Le desktop n'est pas modifié fonctionnellement : il continue de fonctionner hors ligne, sans
serveur, sur des clones locaux. Les deux clients coexistent sur les mêmes repos.

Principe directeur : **un seul code applicatif**. Le renderer React et les services métier sont
partagés ; seuls changent le transport (IPC → HTTP/WebSocket), l'hôte des services (process
Electron → serveur Node, une instance par utilisateur) et les quelques fonctions liées au poste
local (dialogues, shell, fenêtres).

## Comportements attendus

### 1. Connexion

1. L'utilisateur ouvre `https://polenta.<domaine-client>` (route Caddy de #45).
2. Non connecté → redirection vers la forge (OAuth2/OIDC, Authorization Code + PKCE). Pas de
   formulaire de mot de passe dans Polenta Web, pas de PAT à saisir.
3. Retour → le serveur crée une **session** (cookie `HttpOnly`, `Secure`, `SameSite=Lax`). Le
   jeton forge de l'utilisateur reste **côté serveur**, jamais exposé au navigateur.
4. L'identité affichée et l'identité des commits sont celles de la forge
   (`GitProvider.resolveIdentity` de #45) — jamais un compte technique.
5. Jeton révoqué / compte désactivé sur la forge (401 au fetch/push ou au rafraîchissement du
   jeton ; un compte désactivé Forgejo répond 403 « prohibited » à l'API et une page HTML à git,
   classés par la sonde de #45) → session invalidée, message « Votre accès a été révoqué ou a expiré, reconnectez-vous »
   (même libellé que #45 P0-5), retour à l'écran de connexion. Les modifications non publiées
   restent dans le clone serveur de l'utilisateur et réapparaissent s'il se reconnecte.
6. Déconnexion explicite → fin de session ; le clone serveur est conservé (cf. §3).

### 2. Écran de démarrage

Même écran que le desktop (SPEC-ELECTRON-DESKTOP §16), adapté :

| Action desktop | Web |
|---|---|
| Démo | Conservée (projet de démo copié dans l'espace de l'utilisateur). |
| Ouvrir (dossier local) | **Remplacée** par « Mes projets » : liste des workspaces déjà clonés dans l'espace serveur de l'utilisateur. |
| Depuis un repo (URL) | Conservée ; le clone se fait côté serveur. Les repos du serveur visibles par l'utilisateur sont proposés (#45, livré) ; saisie d'URL sinon. |
| Projets de votre équipe (#45) | Conservée : clone dans un dossier neuf de « Mes projets », ou ouverture si le projet y est déjà (même `origin`). |
| Créer | Conservée ; le projet est créé dans l'espace serveur, et sur la forge par « Créer sur le serveur » (#45, livré). |

Les écrans de compte (ajout de PAT, Device Flow GitHub) sont masqués : le compte est celui de la
session.

### 3. Espace serveur par utilisateur

- Chaque utilisateur dispose d'un répertoire racine `<data>/users/<login-forge>/` contenant ses
  clones de workspaces et l'équivalent de son `userData` desktop (réglages, récents, brouillons de
  merge GH37). Aucun autre utilisateur n'y accède, ni en lecture ni en écriture.
- Deux utilisateurs qui ouvrent le même projet ont **deux clones distincts** ; leurs modifications
  se rencontrent par push/pull, avec les mécanismes existants (Publier, Rafraîchir, auto-sync,
  résolution de conflits GH37).
- Un même utilisateur ouvrant Polenta Web dans **deux onglets** partage le même clone et la même
  instance de services (comme deux fenêtres desktop sur le même dossier) ; les écritures de l'un
  sont notifiées à l'autre (`repo:file-changed`).
- Les clones persistent entre les sessions et les redémarrages du serveur. L'utilisateur peut
  supprimer un projet de « Mes projets » (suppression du clone serveur, confirmation si des
  modifications ne sont pas publiées).
- Les ressources mémoire (index, watchers) d'un utilisateur sont libérées après une période
  d'inactivité configurable (défaut 30 min) et reconstruites à la reconnexion. Les fichiers ne
  sont jamais supprimés par cette éviction.

### 4. Parité fonctionnelle

Toutes les vues et actions du desktop sont disponibles et se comportent à l'identique (mêmes
services, mêmes règles : IDs + pierres tombales, revalidation, traçabilité, campagnes, baselines,
dashboards, recherche, merge GH37, i18n, thèmes…). Exceptions et adaptations :

| Fonction desktop | Comportement web |
|---|---|
| Sélecteur de fichier image / drawio | Sélecteur du navigateur → **upload** ; le fichier est copié dans le repo selon les mêmes règles que le desktop (T76). Le cas « fichier déjà dans le repo » est remplacé par un sélecteur des fichiers du repo. |
| Ouvrir un `.drawio` dans l'éditeur externe | **Non disponible en V1** (pas d'application locale). Le diagramme reste affiché et remplaçable par upload ; l'édition intégrée (embed diagrams.net) fait l'objet d'une issue séparée. |
| Exports (Word, Excel, PDF, gabarits GH34, classeur d'exécution GH36) | Génération côté serveur → **téléchargement** par le navigateur. « Ouvrir le fichier » / « Afficher dans le dossier » sont masqués. |
| Import du classeur d'exécution (GH36) | Upload du fichier, puis même aperçu / validation que le desktop. |
| Export PDF, instantané drawio | Même rendu que le desktop (moyen technique côté serveur à choisir en Design). |
| Auto-update | Masqué : le serveur est mis à jour par l'exploitant (`update.sh` de #45). La version du serveur est affichée dans « À propos ». |
| Serveur MCP / AGENTS.md / lancement Claude Code | Masqué (nécessite un poste local). |
| Menu natif, titre de fenêtre OS | Titre = titre de l'onglet navigateur. |
| Raccourcis Ctrl+T / Ctrl+W (onglets internes) | Conservés quand le navigateur les laisse passer ; sinon raccourcis alternatifs documentés (à trancher en Design). |
| Proxy système, CA interne (Electron) | Sans objet côté navigateur ; côté serveur, configuration de l'exploitant. |

Une fonction masquée l'est **proprement** : pas de bouton mort, pas d'erreur IPC.

### 5. Écritures externes et rafraîchissement

Le watcher de fichiers existant (`repo:file-changed`) est conservé côté serveur et poussé au
navigateur par un canal temps réel. Comportement identique au desktop : un autre onglet du même
utilisateur ou un pull met la vue à jour.

### 6. Sécurité

- Toute requête applicative exige une session valide ; aucune route ne permet d'accéder à un
  chemin hors de l'espace de l'utilisateur (les arguments `repoPath` reçus du navigateur sont
  validés : pas de traversée de répertoire, pas de chemin absolu arbitraire).
- Les channels propres au poste local (dialogues natifs, `shell.*`, MCP, update) ne sont **pas
  exposés** par le serveur web.
- Pas de jeton forge ni de stack trace dans les réponses au navigateur. Les chemins absolus de
  l'espace **de l'utilisateur** peuvent y apparaître (le renderer identifie les repos par leur
  chemin, comme sur le desktop) ; aucun chemin hors de cet espace n'est jamais renvoyé ni accepté.
- Protection CSRF sur les appels mutants ; en-têtes de sécurité posés par Caddy (#45).
- Uploads limités en taille (défaut 20 Mo, configurable) et en types (ceux déjà acceptés par le
  desktop).

### 7. Déploiement

- Livré comme **image Docker** `polenta-web`, ajoutée au compose de #45 (service prévu inactif par
  défaut, route Caddy `polenta.<domaine>`).
- Une instance `polenta-web` **par instance de forge** de l'hôte #45 (profil compose `web`, volume
  `web-data` déjà déclarés par #45).
- Configuration par variables d'environnement : URL de la forge, client OAuth (id/secret), URL
  publique, répertoire de données, durée de session, délai d'éviction, taille max d'upload.
- Le répertoire de données est un volume, **inclus dans la sauvegarde** de #45 (`polenta-host`
  `backup_instance`, qui ne le prend pas encore) —
  il contient des modifications non publiées.
- Dimensionnement : profil 4 vCPU / 8 Go / 160 Go si forge et web sur le même VPS (#45 §7).

## Cas d'usage

1. **Consultation** — Un chef de projet sans poste configuré se connecte, ouvre le projet,
   consulte la matrice de traçabilité et un dashboard. Aucune installation.
2. **Édition et publication** — Une ingénieure système modifie SYS-0012, crée un lien, publie.
   Le commit est à son nom (identité forge) ; un collègue sur desktop voit la modification après
   Rafraîchir.
3. **Conflit** — Deux utilisateurs web modifient le même champ ; le second à publier passe par la
   résolution de conflits GH37 dans son navigateur.
4. **Campagne hors outil** — Un testeur exporte le classeur d'exécution (téléchargement), le
   remplit, le réimporte (upload), valide l'aperçu.
5. **Départ d'un salarié** — L'administrateur désactive le compte sur la forge : la session web
   en cours tombe à la prochaine opération git ou au rafraîchissement du jeton, et toute nouvelle
   connexion est refusée.
6. **Cloisonnement** — Un sous-traitant ne voit dans « Depuis un repo » / le clone que les repos
   que la forge lui donne, et ne peut ouvrir aucun fichier d'un autre utilisateur du serveur.

## Critères d'acceptation

1. Connexion via la forge (OIDC + PKCE), aucun mot de passe ni PAT saisi dans Polenta Web ; le
   jeton forge n'apparaît dans aucune réponse HTTP, aucun cookie lisible par JS, aucun log.
2. Un commit publié depuis le web a pour auteur l'identité forge de l'utilisateur
   (`git log --format='%an <%ae>'`), et `createdBy`/`updatedBy` affichent cette identité.
3. Compte désactivé ou jeton révoqué → message de révocation et retour à la connexion, au plus
   tard à la prochaine opération git ; aucune donnée non publiée perdue.
4. Deux utilisateurs connectés en même temps sur le même projet ont des clones distincts ; une
   écriture de A n'est jamais visible dans l'espace de B avant push/pull.
5. Une requête portant un `repoPath` hors de l'espace de l'utilisateur (autre utilisateur,
   `../`, chemin absolu) est refusée (403), sans effet de bord.
6. Les channels `dialog:*`, `shell`-based, MCP et `update:*` ne sont pas appelables via le serveur
   web.
7. Les scénarios golden path de parité (liste en Design, `GH44-tests.md`) passent à l'identique
   sur desktop et web : création/édition/suppression d'exigence et de test, liens, campagne
   (création, exécution, export/import Excel), baseline, dashboard, recherche, Publier,
   Rafraîchir, résolution de conflit, exports Word/Excel/PDF/gabarit.
8. Aucune fonction masquée n'affiche de bouton inopérant ni d'erreur dans la console navigateur.
9. Un deuxième onglet du même utilisateur reflète une écriture du premier sans rechargement
   manuel (même délai que le desktop pour une écriture externe).
10. Après 30 min d'inactivité, la mémoire de l'utilisateur est libérée ; à la reprise, le projet
    se rouvre sans perte.
11. Redémarrage du conteneur `polenta-web` : les clones et modifications non publiées sont
    conservés ; les utilisateurs se reconnectent.
12. Le desktop reste fonctionnellement inchangé : sa suite de tests passe, et il ne dépend
    d'aucun code serveur web à l'exécution.
13. `docker compose up` avec la configuration documentée sert l'application derrière Caddy ; le
    volume de données figure dans `backup.sh`.

## Hors scope

- Développement de #45 (forge, `GitProvider`, identité Forgejo, kit `deploy/`) — **livré** (prérequis satisfait).
- SaaS multi-tenant, facturation, administration des comptes dans Polenta (la forge s'en charge).
- Modèle de droits propre au web (lecture seule par rôle, etc.) — la forge fait foi (#45 §3).
- Clone partagé entre utilisateurs, édition collaborative temps réel (curseurs, co-édition).
- Édition de diagrammes drawio dans le navigateur (issue séparée à créer).
- Serveur MCP / intégration Claude Code depuis le web.
- Mode hors ligne / PWA, application mobile dédiée (l'UI n'est pas retravaillée pour mobile).
- Navigateur de repos de la forge et création de repo distant — livrés par #45, utilisés tels quels.
- Support de GitHub.com comme fournisseur OIDC pour le web en V1 : le cible est la forge #45 ;
  l'abstraction ne doit pas l'empêcher (GitHub OAuth App) mais ce n'est pas testé ni livré.
- Reprise ou maintenance des squelettes `apps/web` / `apps/api` existants — leur sort (suppression
  ou remplacement) est décidé en Design.

## Points ouverts pour le Design

- Réutilisation du renderer : build web du renderer desktop (`apps/desktop/src/renderer`) avec un
  transport injecté, vs déplacement du renderer dans un package partagé.
- Transport : un endpoint générique `POST /rpc/:channel` + WebSocket pour `on()`, vs une route REST
  par channel. Le pont générique actuel plaide pour le premier.
- Hôte des services : extraction du container (`container.ts`) et des handlers (`ipc/index.ts`)
  en un registre de handlers indépendant d'`ipcMain`, partagé desktop/web/MCP.
- Stockage de jeton injecté (keytar desktop / session serveur) — en commun avec #45.
- Rendu PDF / instantané drawio sans Electron (Chromium headless dans l'image, ex. Playwright).
- Liste exhaustive des channels « poste local » à exclure et des channels à adapter
  (upload / download).
- Découpage en sprints (le volume plaide pour ≥ 3).
