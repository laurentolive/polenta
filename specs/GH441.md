# GH441 — Couverture figée d'une version (`verification`) exposée au graphe de données et au MCP

Issue : #441 (milestone V0.8.0). Suite de #439 : la décision D8 de `specs/GH439.md` a laissé hors
périmètre l'exposition de `verification` ; ce ticket la porte.

## Contexte

Au passage released, #439 fige dans `versions/<ID>.yaml` le champ système `verification` :
`{ computedAt, rows: [{ id, status, tests }] }`, une ligne par exigence du périmètre (SPEC-REQ §11, §13).
La section « Exigences » de la page d'une version le lit, mais le graphe de données (`GraphVersion`, contrat
v1 de SPEC-DASHBOARDS §2) et le MCP (`get_version`) ne l'exposent pas.

Conséquence : un script de projet (vue Suivi) ne peut pas calculer un indicateur sur la couverture
**figée** d'une version (« % d'exigences vérifiées dans la version 1.2 », évolution d'une version à
l'autre) — ces indicateurs vivent côté projet (GH79, SPEC-TECH-stack §1.1). Polenta n'expose que la donnée
brute.

État constaté dans le code (2026-11-27) :

- `packages/types/src/product-version.ts` : `ProductVersion.verification?: VersionVerification` existe
  (lignes 47-49, 107-117) ; `VersionVerificationRow.status` est un `CoverageStatus`.
- `packages/types/src/graph.ts` : `GraphVersion` (l. 300) n'a pas de `verification` ; `GraphCoverageStatus`
  (l. 212) est déjà le vocabulaire des exigences (`GraphRequirement.coverageStatus`).
- `apps/desktop/src/main/services/graph.service.ts` `listVersions` (l. 263-290) construit `GraphVersion`
  champ par champ ; `analysis` y est lu défensivement (`?? []`, un bloc incomplet ne casse pas le graphe).
- `apps/desktop/src/main/services/versions.service.ts` `page()` (l. 559) **retire** volontairement
  `verification` de la page (« se lit par `versions:requirements` »). `get()` (l. 106) renvoie la version
  brute, avec `verification`.
- `apps/desktop/src/mcp-server/tools/versions.tools.ts` `get_version` (l. ~38) renvoie `page.version`, donc
  sans `verification`.
- Contrat : `apps/desktop/resources/dashboard-lib/polenta.d.ts` est généré depuis `graph.ts` par
  `scripts/generate-graph-dts.ts` (test L8 de `dashboard-lib.test.ts`) ; `manifest.json` garde une version
  par changement livré (`scripts/dashboard-lib-manifest.ts --bump`, test L11). Chaque ajout passé
  (GH201, GH245, GH268…) a sa ligne dans SPEC-DASHBOARDS §2.

## 1. Décisions proposées (à valider)

## 2. Comportements

### 2.1 Graphe de données

- Version `released` dont le fichier porte `verification` : `GraphVersion.verification` = `{ computedAt, rows }`,
  copie fidèle du fichier. Lignes dans l'ordre stocké (trié par ID, `buildVerification`).
- Version `in_progress`, `abandoned` sans gel, ou `released` sans `verification` (avant GH439) : `verification: null`.
- Version `released` puis `abandoned` : `verification` est gardé tel quel. Le gel est un fait (GH439 S9 : la page se lit au gel).
- Bloc incomplet ou édité à la main : `rows ?? []`, `tests ?? []`, `computedAt` repris tel quel ; le graphe ne
  casse pas (même garde que `analysis`).
- La valeur ne dépend ni des liens, ni des tests, ni des exécutions d'aujourd'hui : modifier un lien après le
  passage released ne change pas `verification` dans le graphe.

### 2.2 MCP `get_version`

- Sortie : clé `verification` au même format que le graphe (`{ computedAt, rows }` ou `null`), lue par
  `versions.get()` (version brute), à côté de `version`, `state`, `component`, `basedOn`, `components`, `changes`.
- Les autres clés et leur forme ne changent pas (rétrocompatibilité).
- Description du tool mise à jour (une phrase : « couverture figée au passage released, `null` sinon »).

### 2.3 Contrat et documentation

- `packages/types/src/graph.ts` : `GraphVersion.verification` avec son JSDoc (figée, `null` sinon, D1).
- `polenta.d.ts` régénéré (`tsx scripts/generate-graph-dts.ts`) ; manifeste : une version de plus pour
  `polenta.d.ts` (`tsx scripts/dashboard-lib-manifest.ts --bump polenta.d.ts "…" "…"`).
- SPEC-DASHBOARDS §2 : note « GH441 (contrat v1, ajout) » ; SPEC-MCP-SERVER §4.8 : `get_version` renvoie
  `verification` ; SPEC-INDEX : colonne MAJ.

## 3. Critères d'acceptation

1. Un test du graphe (`graph.service.test.ts`) : version `released` avec `verification` → `GraphVersion.verification`
   égal au fichier (`computedAt` et chaque ligne `id`, `status`, `tests`).
2. Même test : version `in_progress`, `abandoned` sans gel, et `released` sans `verification` → `null` ; version `released`
   puis `abandoned` → `verification` gardé.
3. Un bloc `verification` incomplet (rows absentes, tests absents, ligne `null`) ne fait pas tomber le graphe et ne fait pas
   disparaître les autres versions du repo.
4. La couverture figée ne bouge pas : après passage released, un lien ou un test modifié ne change pas
   `GraphVersion.verification` (test sur la séquence réelle : release → modification → relecture du graphe).
5. `polenta.d.ts` est à jour (test L8) et le manifeste a l'empreinte du contenu livré (test L11).
6. Un script de la vue Suivi (bac à sable, contrat v1) lit `versions[i].verification.rows` ; une version non figée
   donne `null`. (Test dans la suite dashboards existante.)
7. MCP : `get_version` sur une version released renvoie `verification` identique à celui du fichier ; sur une version
   en cours, `verification: null` ; les clés `version`, `state`, `component`, `basedOn`, `components`, `changes` sont
   inchangées (comparaison à la sortie d'avant le changement).
8. Aucun nouveau calcul d'agrégat, aucun pourcentage, aucune écriture (le graphe et le MCP restent en lecture).

## 4. Hors périmètre

- Compteurs et pourcentages de couverture (GH79) — à faire côté projet à partir de ce champ.
- Calcul live de `verification` pour une version en cours (D1).
- Recalcul pour une version released avant GH439 (D1 / GH439 D2b).
- Nouveau tool MCP (la donnée passe par `get_version`).
- Affichage : la page d'une version (GH439) ne change pas.
