# GH446 — Vue d'historique des objets : clic droit « Historique » (panneau latéral, vues Excel / Word)

Issue : #446 (milestone V0.8.0). Sans statut de design : ce document est la spec à valider.

## 1. Contexte

Pour voir l'historique d'un objet (GH77, `history`), il faut ouvrir son éditeur et descendre à la section
repliée « Historique » en bas de l'écran. `HistorySection` (`components/history/HistorySection.tsx`) ne sert
qu'à `EditView`, `req.$reqId`, `test.$testId` et `campaign.$campaignId`.

Le ticket demande une entrée « Historique » au clic droit, à deux endroits : le panneau latéral (six types
d'objets) et les vues Excel / Word (exigences, tests, campagnes, issues).

État constaté dans le code (2026-11-27, base `milestone-v0.8.0` = `origin/main`) :

| Surface | Menu contextuel aujourd'hui | Fichier |
|---|---|---|
| Arbre exigences / tests / issues | oui (créer, renommer, copier, couper, coller, supprimer) | `components/system/ElementTree.tsx` |
| Versions | oui | `components/sidebar/version/ProductVersionsPanel.tsx` |
| Vue Excel | oui (copier, couper, coller, supprimer) | `components/system/ExcelView.tsx` |
| Liste des campagnes | **non** | `components/system/CampaignListView.tsx` |
| Liste des validations | **non** | `components/sidebar/ValidationPanel.tsx` |
| Vue Word | **non** | `components/system/WordView.tsx` |

Données : `history:get` (`apps/desktop/src/main/ipc/index.ts:607`) appelle `readEffectiveHistory`
(`main/services/history.service.ts:141`), qui ne connaît que `requirement | test | campaign | issue`
(`HistoryObjectKind`) et lève `unknown object kind` pour une version ou une validation.
Or les versions et les validations sont déjà estampillées à chaque écriture (`VersionsService` →
`history.stamp` / `stampVersionChanges` ; `ValidationsService` → `history.stamp`) : la donnée existe, il
manque la lecture.

Vue cible : `historySections(history, typeDef, labels)` (`components/history/historySections.ts`) et le rendu
de `HistorySection` (données brutes, entrées « déduites » comprises, aucune synthèse) sont réutilisés, pas
réécrits.

## 2. Décisions (proposées — à valider)

Les quatre questions ouvertes de l'issue reçoivent une recommandation. Elles sont à trancher à la validation
de la spec ; le design part de ces réponses.

| # | Question (issue) | Recommandation | Pourquoi |
|---|---|---|---|
| Q1 | Forme de la vue : popup, onglet ou panneau latéral ? Garder la section repliée dans les éditeurs ? | **Popup modale** (même famille que l'aperçu d'exécution, GH399), ouverte depuis le menu. **Section repliée des éditeurs conservée telle quelle** (aucune régression de `gh77` ni de `gh389`). | Pas de nouvel onglet ni de route : la vue reste là où l'utilisateur travaille ; Échap ferme ; le rendu est celui de `HistorySection`, donc pas de second rendu. |
| Q2 | Version et validation : statut seulement, ou aussi les événements (gel, signature, annulation) ? | **Données brutes du `history` tel qu'estampillé** : statut et champs suivis ; pour une version, `history.changes` (liste des changements) ; pour une validation, `history.status` et champs suivis. **Pas d'événement synthétisé** : le passage released / signé est déjà une entrée de statut. | GH79 : Polenta n'interprète pas. Les événements seraient une reconstitution. |
| Q3 | Objets de composant vus depuis le produit : l'historique s'ouvre sur le repo du composant ? | **Oui, sur le repo propriétaire** (comme `findOwnerScope` côté MCP, GH447), lecture seule. Même comportement que la grille d'historique de #269. | `history:get` prend un `repoPath` ; l'historique d'un objet est dans le repo qui le porte. |
| Q4 | Sélection multiple (panneau ou Excel) : entrée désactivée, ou première ligne ? | **Entrée désactivée** quand plusieurs lignes sont sélectionnées (info-bulle « sélectionner une seule ligne »). | Pas d'ambiguïté sur l'objet affiché. Une ligne seule suffit au besoin. |

Autres décisions proposées :

- **D1** — `HistoryObjectKind` passe à `requirement | test | campaign | issue | version | validation`. Les
  lecteurs `HistoryObjectReaders` reçoivent `versions` et `validations`.
- **D2** — L'entrée reste disponible sur un composant en lecture seule et pour un utilisateur sans droit d'édition
  (le ticket le demande ; la vue ne fait aucune écriture).
- **D3** — Le tool MCP de lecture d'historique (`read.tools.ts`, enum `kind` à 4 valeurs) **n'est pas élargi** dans ce
  ticket : le ticket vise la vue. Hors périmètre, à ouvrir si un agent en a besoin.
- **D4** — Le client web (`apps/web`, bridge HTTP) reçoit la même entrée sans code propre : `history:get` est déjà
  autorisé (`web-server/channel-policy.ts:33`), le canal ne change pas.

## 3. Comportements attendus

### 3.1 Panneau latéral (six types)

- Clic droit sur une ligne exigence, test ou issue (arbre `ElementTree`), version (`ProductVersionsPanel`),
  campagne (`SystemPanel` / `CampaignListView`) ou validation (`ValidationPanel`) → menu avec « Historique ».
- « Historique » ouvre la popup pour cet objet : entrées triées par date, par champ suivi, statut compris.
- Objet sans historique → l'état vide existant (`history.empty`), pas d'erreur.
- Le menu ouvert sur une ligne ne ferme pas la popup ; la popup ne ferme pas les menus parents au clic
  (consommation de `mousedown` et `click`, leçon GH416).

### 3.2 Vue Excel et vue Word

- Clic droit sur une ligne exigence, test, campagne ou issue (Excel) ou sur un bloc (Word) → même entrée, même popup.
- **Pas d'entrée** pour une version ou une validation dans ces vues (elles n'y figurent pas).
- Une sélection multiple désactive l'entrée (Q4).
- Vue Word : c'est la première fois qu'elle a un menu contextuel ; le menu ne contient que « Historique »
  (pas de copier / coller ajouté par ce ticket).

### 3.3 Lecture de l'historique

- `history:get(repoPath, kind, id)` accepte `version` et `validation` (D1) ; lecture via `readEffectiveHistory`
  avec le `filePath` de l'objet (`versions/<id>.yaml`, `validations/<id>.yaml`), comme les autres kinds.
- Entrées déduites (`implicit: true`) : affichées comme aujourd'hui, comblées à la prochaine écriture (règle 12 de CLAUDE.md).
- Une lecture en échec n'ouvre pas une popup vide : message d'erreur dans la popup.

## 4. Critères d'acceptation

1. Clic droit sur un objet de chacun des six types dans le panneau latéral → « Historique » → la popup affiche les
   entrées de cet objet (test e2e-web, clic souris).
2. Clic droit sur une exigence, un test, une campagne et une issue, en vue Excel et en vue Word → même entrée, même
   popup (quatre types × deux vues).
3. Aucune entrée « Historique » dans les vues Excel et Word pour une version ou une validation.
4. Objet sans historique → état vide (`history.empty`) ; aucune erreur affichée.
5. Composant en lecture seule et utilisateur sans droit d'édition → entrée présente et fonctionnelle.
6. Aucune écriture dans le repo pendant l'ouverture et la fermeture de la popup (comparaison de `git status` avant / après).
7. `readEffectiveHistory` accepte `version` et `validation` (test unitaire) ; un kind inconnu lève toujours l'erreur.
8. La popup réutilise `historySections` et le rendu de `HistorySection` (test : pas de second rendu, mêmes libellés).
9. Chaque point d'entrée a son test e2e-web avec clic souris (pas seulement clavier), et le cas « objet vide ».
10. La section repliée des éditeurs reste présente et inchangée (non-régression `gh77`).
11. SPEC-SYSTEM-VIEW (menus Excel / Word, grilles), SPEC-REQ §4.4 (historique), SPEC-INDEX et SPEC-WEB à jour.

## 5. Hors périmètre

- Élargir le tool MCP `read.tools.ts` aux versions et validations (D3).
- Événements synthétisés (gel, signature, annulation) : Polenta n'interprète pas l'historique (Q2).
- Filtres, export ou comparaison de deux entrées dans la popup.
- Historique des éléments de composant dans la vue système du produit (#269 est déjà traité).
- Menus contextuels autres que « Historique » pour les vues Word, campagnes et validations.

## 6. Points de vigilance (leçons du dépôt)

- **Recenser tous les points d'entrée** avant de coder (panneau, Excel, Word, campagnes, validations) : un correctif
  sur un seul chemin a déjà été revu par l'humain (leçons 2026-11-03).
- **Clic souris** dans chaque menu et popup, pas seulement le clavier (leçon 2026-11-19, GH416).
- **Un menu ou une popup rendu hors de son parent** stoppe `mousedown` et `click`.
- **Test sur le symptôme** : la popup s'ouvre et affiche les bonnes entrées, à partir de chaque vue, pas seulement
  sur la première rencontrée.
