# GH446 — Vue d'historique des objets : clic droit « Historique » (panneau latéral, vues Excel / Word)

Issue : #446 (milestone V0.8.0). Sans statut de design : ce document est la spec à valider.

> **Révision 3 (2026-11-27)** — décisions de l'humain : la popup « Historique » affiche **l'historique Git de l'objet**
> (un élément par commit qui touche son fichier) ; l'historique GH77 n'y figure pas et reste dans les éditeurs.
> Le diff se présente **en brut ou par champ, au choix de l'utilisateur**. Révisions 1 et 2 remplacées.

## 1. Contexte

Le ticket demande une entrée « Historique » au clic droit, à deux endroits : le panneau latéral (six types d'objets) et
les vues Excel / Word (exigences, tests, campagnes, issues). La popup affiche l'historique Git de l'objet : la liste
des commits qui modifient son fichier, et le diff de ce fichier à chaque commit.

Ce choix repose sur le versionnement natif Git de Polenta (SPEC-REQ, intro) : les fichiers sont la source de vérité,
et l'historique Git est l'historique des versions.

État constaté dans le code (2026-11-27, base `milestone-v0.8.0` = `origin/main`) :

| Surface | Menu contextuel aujourd'hui | Fichier |
|---|---|---|
| Arbre exigences / tests / issues | oui (créer, renommer, copier, couper, coller, supprimer) | `components/system/ElementTree.tsx` |
| Versions | oui | `components/sidebar/version/ProductVersionsPanel.tsx` |
| Vue Excel | oui (copier, couper, coller, supprimer) | `components/system/ExcelView.tsx` |
| Liste des campagnes | **non** | `components/system/CampaignListView.tsx` |
| Liste des validations | **non** | `components/sidebar/ValidationPanel.tsx` |
| Vue Word | **non** | `components/system/WordView.tsx` |

Briques existantes réutilisées :
- `git.fileCommits` (`main/services/git.service.ts`, l. 264) : commits de la chaîne des premiers parents qui touchent
  un fichier. Il ne renvoie ni le message ni le diff.
- `sync:commit-diff` (`sync.service.ts`, `commitDiff`) : diff d'un fichier entre un commit et son premier parent, sous
  forme de `FileDiffContents`. Déjà autorisé sur le client web (`web-server/channel-policy.ts`).
- `RawDiffView` (`components/diff/RawDiffView.tsx`) : diff brut, lecture seule (sans `onChange`).
- Le mode « Rendu » de `FileDiffView` (`components/diff/FileDiffView.tsx`) : diff présenté par champ, pour les
  exigences et les tests.

## 2. Décisions

Décidées par l'humain (2026-11-27) : Q2 (historique Git seul) et le choix du rendu par l'utilisateur.

| # | Question (issue) | Décision | Pourquoi |
|---|---|---|---|
| Q1 | Forme de la vue : popup, onglet ou panneau latéral ? Garder la section repliée dans les éditeurs ? | **Popup modale** (même famille que l'aperçu d'exécution, GH399), ouverte depuis le menu. **Section repliée des éditeurs conservée telle quelle.** | Pas de nouvelle route. Échap ferme. La section GH77 des éditeurs reste inchangée. |
| Q2 | Version et validation : statut seulement, ou aussi les événements ? | **Décidée : historique Git seul.** La popup liste les commits qui modifient le fichier de l'objet, avec le diff de ce fichier. Elle n'affiche pas les champs suivis GH77. | SPEC-REQ : l'historique Git est l'historique des versions. Aucun événement n'est synthétisé. |
| Q3 | Objets de composant vus depuis le produit : l'historique s'ouvre sur le repo du composant ? | **Oui, sur le repo propriétaire** (comme `findOwnerScope` côté MCP, GH447), lecture seule. Même comportement que la grille d'historique de #269. | Le commit et le fichier sont dans le repo qui porte l'objet. |
| Q4 | Sélection multiple (panneau ou Excel) : entrée désactivée, ou première ligne ? | **Entrée désactivée** quand plusieurs lignes sont sélectionnées (info-bulle « sélectionner une seule ligne »). | Pas d'ambiguïté sur l'objet affiché. |

Autres décisions :

- **D1** — Chemin du fichier selon le type : `requirement` → `requirements/<ID>.yaml`, `test` → `tests/<ID>.yaml`,
  `campaign` → `campaigns/<ID>.yaml`, `issue` → `issues/<ID>.yaml`, `version` → `versions/<ID>.yaml`,
  `validation` → `validations/<ID>.yaml`. `history:get` et `HistoryObjectKind` ne changent pas (la popup ne lit pas GH77).
- **D2** — L'entrée reste disponible sur un composant en lecture seule et pour un utilisateur sans droit d'édition
  (la vue ne fait aucune écriture).
- **D3** — Le tool MCP de lecture d'historique (`read.tools.ts`, enum `kind` à 4 valeurs) **n'est pas élargi** dans ce
  ticket.
- **D4** — Le client web (serveur `apps/desktop/src/web-server`, bridge HTTP) reçoit la même entrée sans code propre :
  `sync:commit-diff` est déjà sur la liste blanche ; le nouveau canal de D5 y est ajouté.
- **D5** — Nouveau canal `history:commits(repoPath, kind, id)` : chemin selon D1, puis `git.fileCommits`. Son retour porte
  l'oid, la date, l'auteur et la première ligne du message : le message est ajouté à `fileCommits`. Pas de `--follow` : un
  fichier d'objet ne se renomme pas, et son ID n'est jamais réutilisé (SPEC-REQ §6).
- **D6** — Diff par commit : `sync:commit-diff`. Le diff s'affiche **en Brut ou en Rendu, au choix de l'utilisateur** :
  - **Brut** : texte YAML, `RawDiffView` ;
  - **Rendu** : diff par champ, le mode que `FileDiffView` propose déjà pour les exigences et les tests. Le choix est un
    bouton de la popup, mémorisé entre deux ouvertures.
  Le design tranche deux points : réutiliser le rendu de `FileDiffView` en lecture seule, ou en extraire la partie
  présentation (`FileDiffView` porte des actions d'enregistrement) ; et proposer le Rendu seulement pour exigences et
  tests, comme aujourd'hui, ou aussi pour les autres types.
- **D7** — Popup à contenu unique : l'historique Git de l'objet, avec son sélecteur Brut / Rendu. Pas d'onglet GH77.

## 3. Comportements attendus

### 3.1 Panneau latéral (six types)

- Clic droit sur une ligne exigence, test ou issue (arbre `ElementTree`), version (`ProductVersionsPanel`),
  campagne (`SystemPanel` / `CampaignListView`) ou validation (`ValidationPanel`) → menu avec « Historique ».
- « Historique » ouvre la popup de l'historique Git de cet objet (§3.4).
- Objet jamais commité → « Aucun commit », pas d'erreur.
- Le menu ouvert sur une ligne ne ferme pas la popup ; la popup ne ferme pas les menus parents au clic
  (consommation de `mousedown` et `click`, leçon GH416).

### 3.2 Vue Excel et vue Word

- Clic droit sur une ligne exigence, test, campagne ou issue (Excel) ou sur un bloc (Word) → même entrée, même popup.
- **Pas d'entrée** pour une version ou une validation dans ces vues (elles n'y figurent pas).
- Une sélection multiple désactive l'entrée (Q4).
- Vue Word : c'est la première fois qu'elle a un menu contextuel ; le menu ne contient que « Historique »
  (pas de copier / coller ajouté par ce ticket).

### 3.3 Lecture

- `history:commits(repoPath, kind, id)` (D5) : chemin du fichier selon D1, liste des commits. Lecture en échec → message
  d'erreur dans la popup.
- `history:get` et `readEffectiveHistory` restent inchangés : ils alimentent toujours la section GH77 des éditeurs.

### 3.4 Historique Git de l'objet

- **Liste** : les commits de la chaîne des premiers parents qui modifient le fichier de l'objet, du plus récent au plus
  ancien. Une entrée : date du commit, auteur, première ligne du message, hash court.
- **Sélection** : le diff de ce fichier entre le commit et son premier parent (`sync:commit-diff`), en lecture seule,
  affiché en Brut ou en Rendu (D6). Un commit qui touche d'autres fichiers n'affiche que celui de l'objet.
- **Premier commit du fichier** : tout son contenu apparaît en ajout. **Commit de fusion** : diff contre son premier
  parent, c'est-à-dire le changement intégré par la branche.
- **Chargement** : la liste est lue à l'ouverture de la popup ; le diff n'est lu qu'à la sélection d'une entrée.
- **Cas limites** : fichier jamais commité, ou dépôt sans commit → « Aucun commit ». Modifications non commitées →
  non listées (§5).
- **Donnée brute** : pas de compteur, de durée, ni de regroupement par auteur ou par période.
- **Lecture seule** : aucun bouton d'enregistrement ni de restauration.

## 4. Critères d'acceptation

1. Clic droit sur un objet de chacun des six types dans le panneau latéral → « Historique » → la popup affiche les
   commits de cet objet (test e2e-web, clic souris).
2. Clic droit sur une exigence, un test, une campagne et une issue, en vue Excel et en vue Word → même entrée, même
   popup (quatre types × deux vues).
3. Aucune entrée « Historique » dans les vues Excel et Word pour une version ou une validation.
4. Objet jamais commité → « Aucun commit » ; aucune erreur affichée (test e2e-web, clic souris).
5. Composant en lecture seule et utilisateur sans droit d'édition → entrée présente et fonctionnelle.
6. Aucune écriture dans le repo pendant l'ouverture et la fermeture de la popup (comparaison de `git status` avant / après).
7. `history:commits` renvoie le fichier attendu pour chacun des six types, et rejette un kind inconnu (test unitaire).
8. Brut et Rendu : le choix est proposé dans la popup, et il est mémorisé entre deux ouvertures (test e2e-web). Le
   Rendu n'est proposé que pour les types où `FileDiffView` le propose aujourd'hui (ou ceux décidés au design).
9. Chaque point d'entrée a son test e2e-web avec clic souris (pas seulement clavier), et le cas « Aucun commit ».
10. La section GH77 des éditeurs reste présente et inchangée (non-régression `gh77`), et la popup n'affiche pas les
    champs suivis.
11. SPEC-SYSTEM-VIEW (menus Excel / Word, grilles), SPEC-REQ, SPEC-INDEX et SPEC-WEB à jour.
12. Un objet modifié trois fois affiche trois entrées, du plus récent au plus ancien, avec date, auteur et première
    ligne du message exacts (test unitaire sur un dépôt git temporaire, et test e2e-web).
13. Sélection d'un commit : le diff affiché correspond à `git show <commit> -- <fichier>` ; un commit qui touche
    plusieurs fichiers n'affiche que celui de l'objet.
14. Premier commit du fichier : diff en ajout.
15. Le diff n'est lu qu'à la sélection : aucun appel `sync:commit-diff` à l'ouverture de la popup (test).
16. Les six types listent leur propre fichier (test du chemin par type, pour chacun des six).
17. Client web : la popup fonctionne, et `history:commits` et `sync:commit-diff` sont sur la liste blanche (test de
    `channel-policy`).
18. En Rendu, une exigence dont un champ a changé à un commit affiche ce champ (test sur un commit réel).

## 5. Hors périmètre

- Historique GH77 (champs suivis, statut, entrées déduites) dans la popup : il reste dans les éditeurs.
- Élargir le tool MCP `read.tools.ts` aux versions et validations (D3).
- Événements synthétisés (gel, signature, annulation) : Polenta n'interprète pas l'historique.
- Modifications non commitées dans la popup.
- Comparaison de deux commits quelconques, ou historique du dépôt entier.
- Restauration d'un état antérieur depuis cette vue (écriture, hors lecture seule).
- Filtres, export ou comparaison de deux entrées dans la popup.
- Historique des éléments de composant dans la vue système du produit (#269 est déjà traité).
- Menus contextuels autres que « Historique » pour les vues Word, campagnes et validations.

## 6. Points de vigilance (leçons du dépôt)

- **Recenser tous les points d'entrée** avant de coder (panneau, Excel, Word, campagnes, validations) : un correctif
  sur un seul chemin a déjà été revu par l'humain (leçons 2026-11-03).
- **Clic souris** dans chaque menu et popup, pas seulement le clavier (leçon 2026-11-19, GH416).
- **Un menu ou une popup rendu hors de son parent** stoppe `mousedown` et `click`.
- **Test sur le symptôme** : la popup affiche les bons commits à partir de chaque vue, pas seulement de la première
  rencontrée.
- **Rendu par champ** : réutiliser celui de `FileDiffView` ; ne pas écrire un second moteur de présentation.
