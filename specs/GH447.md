# GH447 — Serveur MCP : composants en repo séparé inaccessibles

Issue #447 (bug, P2). Constaté sur PH2 : produit `handstickProduct`, composants en repo séparé
(`hmi-PH2`, `acc-*`…) déclarés dans `polenta-repo.yaml`.

## Symptômes

1. `bulk_import_requirements` vers `hmi-PH2::HMI_PH2_REQ` : IDs `HMI_PH-0001`… (préfixe tronqué,
   numérotation qui ignore les fichiers du composant).
2. `update_requirements` sur `HMI_PH2_REQ-0001` : « objet introuvable ».
3. `list_requirements` : aucune exigence de composant ; filtre `hmi-PH2::HMI_PH2_REQ` vide.
4. (commentaire) Le `.mcp.json` généré lance le serveur avec `--repo .` seulement : sans
   `--workspace`, aucun composant n'est vu, liens compris.
5. (commentaire) La commande du `.mcp.json` de PH2 pointe vers un dossier `%TEMP%` (extraction d'un
   ancien build portable) : le serveur ne démarre plus après nettoyage.

## Root cause

- **Point 4** : `mcp-launch.ts` écrit `--repo .` (fichier commité, chemin propre au poste) et le
  serveur ne cherchait pas le workspace autour du repo : `workspaceDir` absent → mode mono-repo.
- **Points 1-3** : même avec `--workspace`, les outils d'exigences et de tests travaillaient sur le
  seul repo racine, avec son schéma :
  - listes et recherche par ID : index du repo racine uniquement ;
  - import : validation et préfixe lus dans le schéma racine, qui ne déclare pas les types du
    composant (`'unresolvable'`) → repli sur les 6 premiers caractères du nom de type (`HMI_PH`) ;
    l'objet aurait en plus été écrit dans le composant avec `hmi-PH2::HMI_PH2_REQ`, alors que
    l'application y écrit `root::HMI_PH2_REQ` (forme constatée sur tous les composants de PH2).
- **Point 5** : le `.mcp.json` n'était proposé à nouveau que sur changement de version du gabarit.

## Correctif

Principe : un composant en repo séparé est traité comme l'application le fait quand on le
sélectionne — repo autonome, objets `root::<type>`, services appelés avec le chemin de ce repo.

- `mcp-server/workspace-detect.ts` : sans `--workspace`, workspace = dossier parent dont
  `.polenta/workspace.yaml` a pour `rootRepo` ce repo (ou `selfContained` sur le repo).
- `mcp-server/tools/workspace-scope.ts` : repos du workspace (cache d'arbre), conteneur `scoped`
  sur un repo, traduction `<composant>::<type>` ↔ `root::<type>`, repo propriétaire d'un ID,
  lecture seule d'un composant.
- `get_schema` : `workspaceComponents`, paramètre `component`.
- `list_requirements` / `list_tests` : tous les repos ; objets de composant avec `component` et
  `objectTypeRef` sous le nom de montage.
- `bulk_import_requirements` / `bulk_import_tests` : entrées réparties par repo cible, chaque lot
  traité par le chemin existant dans son repo (schéma, préfixe, numérotation, rangement) ; préfixe
  inconnu refusé en workspace.
- `update_*`, `delete_*`, `get_history` : objet traité dans le repo qui le porte ; composant en
  lecture seule refusé.
- `.mcp.json` : proposé par la mise en conformité quand un chemin absolu de sa commande n'existe
  plus sur le poste (choix validé dans #447 ; deux postes aux chemins différents se le proposent).

Hors périmètre : mutation du schéma d'un composant, campagnes (repo ouvert seulement).

## Vérification

- `src/main/services/mcp-workspace.gh447.test.ts` (15 tests) : workspace produit + composant
  `comp-hmi` au préfixe `HMI_PH2_REQ`. Les 15 échouent sur le code d'avant le correctif avec les
  symptômes de l'issue (`HMI_PH-0001`, « objet introuvable », liste sans composant).
- Tests MCP et conformité existants (15 fichiers, 195 tests) : verts.
- PH2 réel, serveur lancé comme par le `.mcp.json` (`--repo .` depuis `handstickProduct`), lecture
  et `dryRun` seulement : workspace détecté ; `list_requirements` 343 exigences sur 7 repos ; filtre
  `hmi-PH2::HMI_PH2_REQ` → 3 ; import `dryRun` → `HMI_PH2_REQ-0004` ; `update_requirements` `dryRun`
  et `get_history` sur `HMI_PH2_REQ-0001` OK ; aucun fichier modifié dans PH2.

## Comment vérifier à la main

1. Relancer le client MCP (Claude Code…) ouvert sur `PH2/handstickProduct` (serveur construit depuis
   `main`, ou `pnpm dev` qui régénère la commande).
2. `get_schema` → `workspaceComponents` liste `hmi-PH2`, `acc-*`… ; `get_schema { component: "hmi-PH2" }`.
3. `list_requirements { filters: { type: "hmi-PH2::HMI_PH2_REQ" } }` → `HMI_PH2_REQ-0001..0003`.
4. `bulk_import_requirements` `dryRun` vers `hmi-PH2::HMI_PH2_REQ` → `HMI_PH2_REQ-0004` ; en écriture,
   fichier dans `hmi-PH2/requirements/` avec `objectTypeRef: root::HMI_PH2_REQ`, visible dans l'app.
5. Mise en conformité du repo produit : le `.mcp.json` dont la commande pointe vers `%TEMP%` est
   proposé à la réécriture.
