# GH45 — Serveur git auto-hébergé (Forgejo) : comptes, équipes, droits, déploiement VPS

Issue : #45 — `type:feature` — branche `GH45` créée depuis `GH44` (ece9810), **à merger avec ou
après GH44**. Prérequis de GH44 sprint 3 (P0) et sprint 4 (infra).

Analyse préalable : `specs/ANALYSE-SERVEUR-AUTOHEBERGE.md` (2026-10-08).

## Contexte

Un client refuse GitHub. Il veut que ses repos, ses comptes, ses équipes et ses droits vivent sur
**son propre serveur**, déployé simplement sur un VPS. L'analyse retient de **ne pas développer de
serveur de comptes** dans Polenta, mais de déployer **Forgejo** (forge git légère, API `/api/v1`
commune avec Gitea) derrière Caddy. Il faut ensuite adapter Polenta pour qu'il s'y connecte aussi
bien qu'à GitHub.

Constats dans le code (branche GH44 @ ece9810) :

- `AuthService` (`main/services/auth.service.ts`) ne dépend plus d'Electron depuis GH44 S1. Les
  jetons passent par `HostContext.tokenStore` (keytar sur le desktop, mémoire/session sur le web).
- `resolveIdentity` n'interroge que `api.github.com`. Pour tout autre hôte, elle renvoie
  `{ login: 'unknown', name: 'Unknown User' }`. En cas d'échec, `persistToken` se replie sur
  `{ login: 'git', name: 'Git User' }`. **Conséquence : les commits faits avec un compte non
  GitHub ne portent pas l'identité réelle**, et `createdBy`/`updatedBy` (lus dans `git log`) sont
  faux. Le support Gitea (`/api/v1/user`) a été retiré en T130.
- `hasAnyAccount` et `projectUsername` sondent `github.com` et `gitlab.com` en dur. `login.tsx`
  propose `github.com` / `gitlab.com` / « Autre… ». Le Device Flow est réservé à github.com.
- L'accueil (`routes/index.tsx`) propose 4 actions : démo (clone de
  `github.com/laurentolive/demo-ll800-produit`), ouvrir, depuis un repo (saisie d'URL), créer
  (projet local sans repo distant, GH27).
- `workspace-tree.service.ts` (GH30) traduit 401/403/404 en un message centré sur GitHub
  (« scope repo », « token fine-grained »).
- Le champ de type `user` (`EditView.tsx`) est une saisie de texte libre.
- Le transport git HTTPS (`git-http.ts`, undici + proxy) fonctionne avec n'importe quelle forge.
- L'auto-update interroge les GitHub Releases (`update.service.ts`, `provider: github`).
- Côté web (GH44), `POLENTA_WEB_GIT_HOSTS` limite les hôtes git joignables (anti-SSRF).

Décisions prises avec le demandeur (2026-10-09) :

| Sujet | Décision |
|---|---|
| Branche | `GH45` part de `GH44` : réutilise `TokenStore`/`HostContext` sans conflit. |
| Périmètre | **Infra + P0 + P1** de l'analyse. P2 (SSO desktop OAuth2 PKCE, auto-update servi par le serveur, CA interne) → issues de suivi. |
| Annuaire client | Inconnu → **comptes Forgejo locaux** par défaut. LDAP/OIDC documentés dans le RUNBOOK, non automatisés. |
| Forges supportées | **Forgejo et Gitea**, via un provider unique « forgejo » (API `/api/v1` commune). Le kit installe Forgejo. |
| Hébergement | **Multi-instance** : l'éditeur héberge ses clients sur son VPS (`vps-f515f9c6.vps.ovh.net`, Debian 13), **une instance Forgejo isolée par client** derrière un Caddy partagé. Le même kit installe une instance unique sur le VPS propre d'un client. |
| Tests Infra | Sur le VPS de l'éditeur, **avant** d'y installer un client. Réinstallation de l'OS avant la mise en production (§9.9). |

## Description fonctionnelle

Deux livrables :

1. **Un kit de déploiement `deploy/`** qui prépare un VPS Debian/Ubuntu et y installe **une forge
   Forgejo privée par client**, isolée des autres et prête pour Polenta. Chaque forge a son HTTPS,
   son organisation et ses équipes, ses sauvegardes chiffrées externalisées, ses mises à jour, son
   export de restitution, et un outil d'administration en ligne de commande. Le kit prévoit la
   place du service `polenta-web` de GH44.
2. **Le support de cette forge dans Polenta** (desktop, et web via le même code), au même niveau
   que GitHub :
   - identité réelle dans les commits ;
   - connexion par identifiant et mot de passe ;
   - serveur pré-configuré par la DSI ;
   - messages clairs en cas d'accès révoqué ou insuffisant ;
   - liste des repos accessibles et création d'un projet directement sur le serveur ;
   - choix d'un utilisateur parmi les membres de l'organisation.

Les comptes, les équipes et les droits ne s'administrent **pas** dans Polenta. Ils se gèrent dans
l'interface web de Forgejo ou avec `polenta-admin.sh`. Polenta est un client de la forge.

GitHub reste supporté sans régression. Un poste peut avoir à la fois un compte GitHub et un
compte Forgejo.

## Comportements attendus

### 1. Provider de forge (P0)

1. Chaque compte enregistré porte un **type de forge** : `github`, `forgejo` (Forgejo ou Gitea) ou
   `generic` (git HTTPS sans API connue). Pour un compte existant sans type : `github` si l'hôte est
   `github.com`, `generic` sinon. Aucune action utilisateur n'est demandée.
2. Détection à la connexion : `github.com` → `github`. Sinon, Polenta interroge
   `<serveur>/api/v1/version`. Une réponse JSON valide donne `forgejo`, sinon `generic`.
3. Toute la logique propre à une forge (identité, liste des repos, création de repo, membres,
   permissions, création de jeton) passe par une interface unique. Plus aucun code applicatif ne
   teste `host === 'github.com'` en dehors du provider GitHub (Device Flow compris).
4. Cette interface ne dépend ni d'Electron ni de keytar, pour être utilisable par le serveur web
   de GH44 (sprint 3), le desktop et le serveur MCP.

### 2. Identité (P0)

1. Compte `forgejo` : l'identité vient de `GET /api/v1/user` (`login`, `full_name` ou `login` à
   défaut, `email`). Elle sert d'auteur à tous les commits faits avec ce compte.
2. Si l'identité ne peut pas être résolue à la connexion (serveur injoignable, jeton invalide),
   **la connexion échoue avec un message explicite**. On ne garde plus de compte « Git User » pour
   une forge connue. Le repli minimal ne subsiste que pour `generic`, comme aujourd'hui.
3. Une forge peut masquer l'e-mail de l'utilisateur (paramètre de confidentialité). Dans ce cas,
   Polenta utilise l'adresse renvoyée par l'API telle quelle (souvent `<login>@noreply.<domaine>`)
   et ne demande rien à l'utilisateur.
4. `projectUsername` et `hasAnyAccount` s'appuient sur les comptes enregistrés et sur le serveur
   par défaut (§3), plus sur une liste d'hôtes en dur.

### 3. Configuration machine (P0) — option réservée aux DSI (révisé le 2026-10-10, cf. §3bis)

> **Révision du 2026-10-10** : le poste de l'utilisateur ne doit rien avoir à gérer. La configuration
> courante vient désormais **de la forge**, par équipe (§3bis), et le premier accès se fait par un
> **lien d'invitation** (§3ter). Le fichier ci-dessous reste une **option** pour les DSI qui veulent
> imposer une politique sur un parc géré (serveur unique, mises à jour bloquées). Il l'emporte alors
> sur la configuration de la forge pour les clés qu'il fixe.

1. Le desktop lit au démarrage un fichier de configuration **machine**, déployable par la DSI
   (GPO, outil de télédistribution) :
   - Windows : `%ProgramData%\Polenta\config.json` ;
   - macOS : `/Library/Application Support/Polenta/config.json` ;
   - Linux : `/etc/polenta/config.json`.

   La variable d'environnement `POLENTA_CONFIG` peut pointer vers un autre fichier (tests,
   portable). Si le fichier est absent, Polenta se comporte exactement comme aujourd'hui.
2. Clés reconnues (toutes facultatives) :

   | Clé | Effet |
   |---|---|
   | `defaultServer` | URL de la forge de l'entreprise. Pré-remplie et sélectionnée à l'écran de connexion ; seul choix proposé si `hideGithub`. |
   | `hideGithub` | `true` : masque github.com/gitlab.com et le Device Flow à la connexion. Les comptes GitHub déjà enregistrés restent utilisables. |
   | `demoProjectUrl` | URL du projet de démo. Si `hideGithub` est actif et que cette clé est absente, le bouton « Démo » de l'accueil est masqué. |
   | `autoUpdate` | `false` : désactive la vérification de mise à jour, qui ne peut alors pas être réactivée dans les préférences. Pour un parc mis à jour par la DSI, ou un réseau qui bloque github.com. |

3. Une clé inconnue ou une valeur invalide est ignorée et journalisée. Un fichier JSON illisible
   est ignoré en entier, avec un avertissement dans le journal. L'application démarre toujours.
4. Web (GH44) : les mêmes valeurs sont fournies par l'exploitant via des variables d'environnement
   du serveur web. `defaultServer` correspond alors à la forge du compose.

### 3bis. Configuration centralisée par équipe (décision du 2026-10-10)

1. **Où** : un repo **`<organisation>/polenta-config`** sur la forge du client, contenant un fichier
   `config.yaml`. `instance add` le crée avec un modèle commenté. L'admin du client le modifie dans
   l'interface web de la forge : il est versionné, et l'historique trace qui a changé quoi.
2. **Qui peut le modifier** : seuls les propriétaires de l'organisation. Sa branche `main` est
   protégée (push réservé à l'équipe `Owners`), même pour les équipes qui ont l'écriture sur tous
   les repos. Tous les membres de l'organisation peuvent le lire.
3. **Contenu** (V1) :

   ```yaml
   version: 1
   defaults:                     # tous les membres de l'organisation
     updates: auto               # auto | managed (mises à jour gérées par l'informatique)
     projects:                   # projets proposés à l'accueil
       - repo: acme/demo-ll800-produit
         label: Démonstration
     preferences:
       language: fr              # fr | en
       theme: light              # light | dark
       projectHome: dashboard    # vue d'ouverture d'un projet : dashboard | system | traceability | campaigns
       fieldVisibility:          # champs visibles par défaut, par type d'objet et par vue
         root::exigence-systeme:
           excel: [priority, statement]
   teams:                        # surcharges par équipe (nom de l'équipe Forgejo)
     testeurs:
       projects:
         - repo: acme/essai
       preferences:
         projectHome: campaigns
     lecteurs:
       updates: managed
   ```

4. **Résolution pour un utilisateur** (équipes lues sur la forge avec son jeton) :
   - `projects` : `defaults` + projets de **chacune** de ses équipes (union, sans doublon, ordre du
     fichier) ;
   - `updates` : `managed` dès qu'une source le demande (la plus restrictive l'emporte) ;
   - `preferences` : `defaults`, surchargé par la **première** de ses équipes dans l'ordre du
     fichier qui définit la clé ;
   - un repo de config absent, illisible ou invalide → aucun effet (comportement actuel), avec un
     message discret dans le panneau Compte pour l'admin (« configuration du serveur ignorée : … »).
5. **Préférences par défaut** : elles ne s'appliquent **que si l'utilisateur n'a pas déjà choisi**
   (langue, thème, champs visibles d'une vue). Un choix personnel n'est jamais écrasé. Elles ne
   sont pas réécrites dans ses préférences : retirer une valeur du fichier rend la main au
   comportement par défaut de Polenta.
6. **Projets proposés** : listés en tête de l'accueil (« Projets de votre équipe »), un clic clone et
   ouvre le projet (ou l'ouvre s'il est déjà cloné sur le poste). Un repo inaccessible à
   l'utilisateur n'est pas affiché.
7. **Mises à jour** : `managed` → vérification des mises à jour désactivée et verrouillée, comme
   `autoUpdate: false` dans le fichier DSI. Sans effet sur le web (GH44).
8. **Quand** : la configuration est lue à la connexion, au démarrage et toutes les 30 minutes, et
   gardée en cache sur le poste (dernière version connue). Hors ligne, c'est le cache qui
   s'applique.
9. **Plusieurs serveurs** : la configuration est celle du serveur du compte courant.
10. **Web (GH44)** : même configuration, lue avec le jeton de la session.

### 3ter. Lien d'invitation (décision du 2026-10-10)

1. `polenta-admin user add` (et `user import`) affiche pour chaque compte un **lien d'invitation**
   et un **message prêt à envoyer** (texte en français : adresse du serveur, identifiant, mot de
   passe temporaire si pas de SMTP, lien de téléchargement de Polenta, lien d'invitation).
2. Le lien `polenta://connect?server=<url>&login=<identifiant>` ouvre Polenta (ou le démarre) sur
   l'écran de connexion, avec le serveur et l'identifiant **pré-remplis**. Il ne connecte jamais
   tout seul : l'utilisateur saisit son mot de passe.
3. Le lien n'accepte qu'une adresse `https` (ou `http` si le serveur est configuré ainsi). Le
   serveur est affiché en clair à l'écran. Un lien malformé est ignoré, avec un message.
4. Si Polenta est déjà ouvert, le lien est traité dans la fenêtre existante (instance unique).
   S'il est déjà connecté au même serveur et avec le même identifiant, il affiche simplement
   l'accueil.
5. Sans lien : l'écran de connexion propose un champ « Adresse du serveur de votre entreprise »
   (une saisie, une seule fois), en plus de GitHub, sauf si une politique DSI masque GitHub.
6. Le protocole `polenta://` est enregistré par l'installateur Windows, et au premier lancement.

### 4. Connexion à une forge (P0)

1. L'écran de connexion propose, pour un serveur Forgejo, **identifiant + mot de passe** (+ code
   2FA si le compte en a un). Le formulaire « jeton d'accès personnel » reste accessible
   (« Utiliser un jeton »).
2. Avec identifiant et mot de passe, Polenta demande à la forge de **créer un jeton d'accès**
   (`POST /api/v1/users/{login}/tokens`) :
   - scopes minimaux nécessaires à Polenta (liste exacte figée au Design, validée sur une
     instance réelle) ;
   - nom unique et lisible, par exemple `polenta-<nom-du-poste>-<AAAAMMJJ-HHmm>`.

   Le jeton est stocké dans le `TokenStore`. **Le mot de passe n'est jamais stocké, ni journalisé,
   ni conservé en mémoire après l'appel.**
3. Si la forge exige un code 2FA et qu'il n'a pas été saisi, le champ code s'affiche et
   l'utilisateur recommence, sans ressaisir le reste.
4. Erreurs à distinguer à l'écran :
   - identifiants invalides ;
   - compte désactivé ;
   - code 2FA invalide ;
   - serveur injoignable (message réseau existant, proxy pris en compte) ;
   - serveur qui n'est pas une forge Forgejo/Gitea.
5. Déconnexion : Polenta supprime le jeton local et le compte. Il ne peut pas révoquer le jeton
   côté serveur sans le mot de passe. L'écran de déconnexion l'indique en une ligne (« Le jeton
   reste visible dans vos paramètres Forgejo › Applications, où vous pouvez le révoquer »).

### 5. Accès révoqué ou insuffisant (P0)

1. **401** sur une opération git (clone, fetch, pull, push, auto-pull) ou sur un appel API vers une
   forge connue (`github`, `forgejo`) : Polenta affiche « Votre accès au serveur <hôte> a été révoqué
   ou a expiré. Reconnectez-vous. » avec un bouton qui ouvre la connexion, serveur pré-rempli. Les
   modifications locales non publiées ne sont jamais perdues.
2. L'auto-pull (T155/GH39) ne réaffiche pas ce message à chaque tick. Il s'affiche une fois, puis
   l'auto-pull de cet hôte est suspendu jusqu'à la reconnexion.
3. **403** sur un push (droit d'écriture absent ou branche protégée) : « Vous n'avez pas le droit de
   publier sur <repo> (lecture seule ou branche protégée). Contactez votre administrateur. » Le
   commit local est conservé, comme lors d'un échec réseau de Publier (T154).
4. Le message de chargement de workspace GH30 (401/403/404) cesse de parler de « scope repo » pour
   un compte `forgejo`. Il indique que le compte n'a pas accès au dépôt et qu'il faut demander à
   l'administrateur de l'ajouter à une équipe. Le message GitHub actuel reste inchangé pour les
   comptes `github`.

### 6. Liste des repos et création sur le serveur (P1)

1. « Depuis un repo » (accueil) : si un compte `forgejo` est enregistré, la fenêtre propose
   d'abord la **liste des repos accessibles** à ce compte (`GET /api/v1/user/repos`, toutes pages).
   - Recherche sur `organisation/nom`, avec la description du repo affichée.
   - Un badge « lecture seule » apparaît si le compte n'a pas l'écriture.
   - La saisie d'URL reste disponible (« Saisir une URL »). Avec plusieurs comptes `forgejo`, un
     sélecteur de compte est proposé.
2. « Créer » (accueil) : en plus de la création locale actuelle (inchangée), une option « Sur le
   serveur <hôte> » apparaît si un compte `forgejo` existe. L'utilisateur choisit une organisation
   **dans laquelle il a le droit de créer des repos** (les autres ne sont pas proposées) et saisit le
   nom. Polenta enchaîne :
   1. création du repo distant, **toujours privé** et vide ;
   2. création du projet local comme aujourd'hui (GH27) ;
   3. ajout de `origin` ;
   4. publication initiale de la branche d'intégration.

   Si l'utilisateur n'a aucune organisation éligible, l'option est
   affichée désactivée avec l'explication.
3. Échec partiel lors de la création : si le repo distant est créé mais que le push échoue, le
   projet local reste ouvert avec `origin` configuré, et un message invite à publier plus tard.
   Polenta ne supprime jamais un repo distant.
4. Nom déjà pris dans l'organisation : erreur explicite avant toute création locale.
5. Ajout d'un composant (`AddDependencyModal`) : même choix « Créer le repo sur le serveur », en
   plus de la saisie d'URL actuelle. L'URL du repo créé est inscrite dans `polenta-repo.yaml`.
6. Web (GH44) : ces deux flux fonctionnent à l'identique dans l'espace serveur de l'utilisateur.

### 7. Choix d'un utilisateur (P1)

1. Champ de type `user` dans un repo dont `origin` est sur une forge `forgejo` : la saisie propose
   en autocomplétion les **membres de l'organisation propriétaire du repo** (login, nom affiché),
   chargés une fois par session et par organisation.
2. La valeur enregistrée est le **login** (chaîne, format YAML inchangé). Une valeur saisie à la
   main reste acceptée (hors ligne, utilisateur externe), sans erreur.
3. Repo d'un utilisateur personnel (pas d'organisation), forge injoignable ou compte `github` /
   `generic` : comportement actuel (texte libre), sans message d'erreur.

### 8. Diagnostic des droits à l'ouverture d'un workspace (P1)

1. Au chargement d'un workspace, pour chaque repo (racine et dépendances) hébergé sur une forge
   `forgejo`, Polenta lit les permissions du compte (`GET /api/v1/repos/{owner}/{repo}`, champ
   `permissions`). Cet appel ne bloque pas l'ouverture.
2. Racine en lecture seule : bandeau non bloquant « Vous avez un accès en lecture seule à ce
   projet : vous pouvez consulter mais pas publier. » Les actions d'édition **ne sont pas**
   désactivées en V1 : le refus arrive au push, avec le message §5.3.
3. Dépendance inaccessible : message §5.4, qui nomme le composant concerné.
4. Hors ligne, ou forge non `forgejo` : aucun diagnostic, aucun message.

### 9. Kit de déploiement `deploy/` (Infra) — multi-instance

**Modèle d'hébergement** (décision du 2026-10-09) : un **hôte** (un VPS) porte **une instance
Forgejo par client**. Chaque instance a ses propres données, son sous-domaine, sa sauvegarde et
ses comptes, et peut avoir son propre admin. Les instances partagent un Caddy qui fait le
reverse proxy et le TLS. Le même kit couvre les deux situations :

- l'hôte de l'éditeur (ton VPS), avec N clients ;
- le VPS propre d'un client, avec une seule instance.

Aucune donnée, aucun compte, aucun réseau n'est partagé entre deux instances.

Dossier `deploy/` à la racine du monorepo, autonome (copiable seul sur le VPS) :

```
deploy/
├── polenta-host.sh        point d'entrée unique de l'exploitant (§9.2, §9.3)
├── polenta-admin.sh       opérations courantes dans une instance (§9.5)
├── host/
│   ├── docker-compose.yml Caddy partagé
│   └── Caddyfile          importe un fichier de site par instance ; en-têtes de sécurité
├── instance/
│   ├── docker-compose.yml forgejo ; polenta-web en profil compose inactif par défaut
│   ├── app.ini.tmpl       configuration Forgejo de référence (§9.3-4)
│   └── instance.env.example
├── host.env.example       ACME_EMAIL, BASE_DOMAIN (option), BACKUP_S3_* par défaut, BACKUP_PING_URL
├── config.example.json    modèle de configuration machine Polenta (§3) à distribuer aux postes
└── RUNBOOK.md             procédures de l'exploitant et de l'admin d'instance (FR)
```

Sur le VPS, l'état vit sous `/opt/polenta/` : `host.env`, puis un dossier
`instances/<nom>/` (`instance.env`, données, journaux) par instance.

1. **OS cibles** : Debian 12, Debian 13, Ubuntu 24.04 LTS. Sur un autre OS, `polenta-host.sh`
   refuse de s'exécuter avec un message.

2. **`polenta-host.sh setup`** — préparation de l'hôte, une fois par machine (root, rejouable sans
   effet de bord) :
   1. vérifications préalables : OS supporté, ports 80/443 libres ou déjà tenus par le Caddy du
      kit, `host.env` complet ;
   2. installation de Docker (dépôt officiel), `ufw` (22/80/443 uniquement), `fail2ban` (sshd +
      échecs de connexion de chaque instance), `unattended-upgrades`, `restic` ;
   3. durcissement SSH : authentification par clé uniquement et root interdit, **seulement si** une
      clé est déjà autorisée pour l'utilisateur d'admin. Sinon, avertissement et pas de
      modification, pour ne jamais enfermer l'exploitant dehors ;
   4. démarrage du Caddy partagé ;
   5. installation du cron de sauvegarde (qui parcourt toutes les instances) et du cron de rapport
      d'état.

3. **Cycle de vie d'une instance** :

   | Commande | Effet |
   |---|---|
   | `instance add <nom> --domain <fqdn> [--org <organisation>] [--client-admin <login> <email>]` | Crée et démarre une instance (§9.3-4). `--domain` vaut par défaut `<nom>.<BASE_DOMAIN>`. |
   | `instance list` | Nom, domaine, version Forgejo, état (santé), disque utilisé, date de la dernière sauvegarde réussie |
   | `instance update <nom> <version>` / `instance update --all <version>` | Sauvegarde → mise à jour de version (explicite, jamais `latest`) → contrôle de santé → **retour à la version précédente si échec** |
   | `instance backup <nom>` / `--all` | Sauvegarde immédiate (§9.4) |
   | `instance restore <nom> --from <instantané\|latest> [--domain …]` | Restauration complète d'une instance sur cet hôte : vierge, ou même hôte sous un autre nom |
   | `instance export <nom>` | Archive de restitution au client : dump Forgejo + repos git bruts + mode d'emploi, avec somme de contrôle |
   | `instance stop <nom>` / `start <nom>` | Suspension (client en impayé, maintenance), sans perte |
   | `instance remove <nom>` | Export final obligatoire, puis suppression des conteneurs, données et site Caddy, après saisie du nom de l'instance pour confirmer. Les sauvegardes externes sont conservées (purge manuelle documentée). |

4. **`instance add`** :
   1. vérifie que `<nom>` est libre et valide (`[a-z0-9-]`), que le domaine résout vers l'IP de
      l'hôte, et qu'il reste assez de mémoire (avertissement sous 512 Mo disponibles) ;
   2. génère les secrets de l'instance dans `instance.env` (chmod 600), dont le **mot de passe
      restic propre à l'instance**, jamais régénérés s'ils existent ;
   3. configure Forgejo :
      - inscriptions désactivées ;
      - connexion obligatoire pour tout voir ;
      - repos privés forcés ;
      - SSH git désactivé ;
      - `ROOT_URL` en HTTPS ;
      - SMTP (hérité de l'hôte ou propre à l'instance) ;
      - taille maximale de fichier ;
      - pas de LFS ;
      - hooks git désactivés ;
   4. démarre l'instance sur **son propre réseau Docker**. Seul Caddy y est relié, et deux
      instances ne peuvent pas se joindre ;
   5. ajoute le site Caddy (certificat TLS automatique), attend `/api/healthz` en HTTPS ;
   6. crée :
      - un **compte d'exploitation** (admin de l'instance, réservé à l'éditeur, mot de passe dans
        `instance.env`) ;
      - si `--client-admin` est fourni, le compte admin du client (mot de passe à changer à la
        première connexion) ;
      - l'organisation ;
      - les équipes `auteurs` (écriture), `testeurs` (écriture), `lecteurs` (lecture), sur tous
        les repos de l'organisation ;
      - un miroir du projet de démo (désactivable) ;
   7. fait une première sauvegarde suivie d'un `restic check` ;
   8. affiche le récapitulatif : URL, comptes créés, chemin du `config.json` Polenta pré-rempli
      pour cette instance (`defaultServer`, `hideGithub: true`, `demoProjectUrl` du miroir).

5. **Sauvegarde** :
   - quotidienne, **un dépôt restic par instance**, chacun avec son mot de passe. On peut restaurer
     ou restituer un client sans toucher aux autres, et lui remettre sa clé ;
   - rétention 7 quotidiennes / 4 hebdomadaires / 12 mensuelles ;
   - destination S3 par défaut dans `host.env` (préfixe par instance), surchargeable par instance ;
   - le RUNBOOK exige de conserver les mots de passe restic **hors de l'hôte** ;
   - le volume de données de `polenta-web` de l'instance est inclus quand ce profil est actif ;
   - en fin de passe, ping optionnel vers `BACKUP_PING_URL`. Un échec sur une instance n'empêche
     pas la sauvegarde des autres, et il est signalé.

6. **`polenta-admin.sh --instance <nom>`** — opérations courantes dans une instance, via l'API
   Forgejo et le compte d'exploitation. Le paramètre est facultatif quand l'hôte n'a qu'une
   instance.

   | Commande | Effet |
   |---|---|
   | `user add <login> <email> [--name …] [--team …]` | Crée le compte (mot de passe temporaire envoyé par e-mail ou affiché si pas de SMTP), l'ajoute aux équipes |
   | `user import <fichier.csv>` | Création en masse : `login;email;nom;équipes` ; rapport ligne par ligne, une erreur n'arrête pas l'import |
   | `user disable <login>` | Départ : interdit la connexion et révoque tous ses jetons |
   | `user enable <login>` | Réactivation |
   | `team add <nom> <read\|write> [repo…]` | Équipe projet limitée à certains repos |
   | `team member <add\|rm> <équipe> <login>` | |
   | `project create <nom> [--team …]` | Repo privé dans l'organisation, initialisé avec un projet Polenta vide, attaché aux équipes |
   | `access report [--csv]` | Accès effectifs utilisateur × repo × droit (revue d'accès périodique) |
   | `oauth-app create <nom> <redirect-uri>` | Application OAuth2 Forgejo (GH44 sprint 3 : `polenta-web`), affiche client id/secret |

   Chaque commande d'écriture journalise son exécution (date, instance, commande, résultat) dans
   `instances/<nom>/admin.log`. L'admin du client peut faire tout cela lui-même dans l'interface
   web de son instance, sans accès SSH à l'hôte.

7. **Profil `polenta-web`** : service et route Caddy par instance (sous-domaine configurable)
   déclarés mais inactifs. GH44 sprint 4 fournit l'image et active le profil. GH45 n'a pas à livrer
   d'image web.

8. **RUNBOOK.md**, en deux parties :
   - **exploitant** (l'éditeur, ou la DSI d'un client sur son propre VPS) :
     - préparation de l'hôte, ajout et retrait d'un client, mises à jour, sauvegardes ;
     - **test de restauration trimestriel** ;
     - restitution des données (`instance export` + clé restic) ;
     - incidents : disque plein, certificat, instance arrêtée, hôte perdu → nouvel hôte +
       `instance restore` ;
     - dimensionnement (RAM par instance, avec et sans `polenta-web`) ;
     - bascule DNS ;
   - **admin du client** :
     - ajout et départ d'un utilisateur, équipes et cloisonnement ;
     - limite des droits : lecture / écriture par repo, rôles Polenta non garantis par le serveur
       (analyse §3) ;
     - branchement LDAP/AD ou OIDC (manuel, documenté) ;
     - distribution du `config.json` aux postes.

9. **Hôte de test** : la validation du sprint Infra se fait sur le VPS de l'éditeur **avant** qu'un
   client y soit installé. On y exécute `setup`, deux instances, les tests d'isolation, la mise à
   jour avec retour arrière, puis une **réinstallation complète de l'OS** (console OVH) suivie
   d'un `setup` et d'un `instance restore` pour prouver la reprise sur machine vierge. La mise en
   production d'un client se fait ensuite sur une machine réinstallée proprement. Les évolutions
   ultérieures du kit qui comportent des opérations destructives devront être validées sur un
   hôte jetable : à prévoir dans le RUNBOOK.

## Cas d'usage

| # | Cas | Résultat attendu |
|---|---|---|
| UC1 | L'exploitant prépare un VPS vierge (`setup`) puis ajoute un client (`instance add acme`) | Forge `acme` en HTTPS valide en moins de 30 min, organisation et équipes créées, première sauvegarde vérifiée |
| UC1b | L'exploitant ajoute un second client (`instance add globex`) sur le même hôte | Deux forges indépendantes : un compte d'`acme` ne peut pas se connecter sur `globex`, et aucun conteneur d'une instance ne joint l'autre |
| UC1c | Un client part : `instance export` puis `instance remove` | Archive de restitution complète remise au client ; plus aucune donnée du client sur l'hôte ; les autres instances ne sont pas interrompues |
| UC2 | L'admin crée 10 comptes par `user import` | 10 comptes, rattachés à leurs équipes, rapport sans erreur |
| UC3 | Un poste avec le `config.json` de la DSI lance Polenta pour la première fois | L'écran de connexion n'affiche que le serveur de l'entreprise ; connexion identifiant + mot de passe ; aucun PAT à créer |
| UC4 | L'utilisateur clone un projet en le choisissant dans la liste | Workspace ouvert, composants clonés ; commits signés de son nom et e-mail Forgejo |
| UC5 | Un chef de projet crée un nouveau projet « Sur le serveur » | Repo privé créé dans l'organisation, projet local ouvert, branche d'intégration poussée |
| UC6 | Un membre de `lecteurs` ouvre un projet et tente de publier | Bandeau lecture seule à l'ouverture ; Publier → message 403 explicite ; commit local conservé |
| UC7 | L'admin exécute `user disable` pour un salarié qui part | Au prochain fetch/push, son poste affiche « accès révoqué » ; aucune donnée locale perdue ; l'auto-pull ne boucle pas sur le message |
| UC8 | Un testeur renseigne un champ « Responsable » (type `user`) | Autocomplétion sur les membres de l'organisation ; le login est enregistré |
| UC9 | L'hôte est perdu : l'exploitant réinstalle l'OS, lance `setup` puis `instance restore` pour chaque client | Forges identiques (comptes, équipes, repos, historique) ; les postes se reconnectent sans action (même domaine) |
| UC10 | Un utilisateur GitHub existant met à jour Polenta (sans `config.json`) | Aucun changement visible ; son compte, ses projets et le Device Flow fonctionnent comme avant |
| UC11 | Une forge **Gitea** au lieu de Forgejo | UC3 à UC8 fonctionnent à l'identique |
| UC12 | L'admin ajoute dora (équipe `testeurs`) et lui envoie le message d'invitation | Dora installe Polenta, clique sur le lien : écran de connexion avec serveur et identifiant pré-remplis ; aucun fichier à déposer sur son poste |
| UC13 | L'admin ajoute dans `polenta-config` le projet `acme/essai` pour l'équipe `testeurs` et `projectHome: campaigns` | Au démarrage suivant (ou dans les 30 min), les testeurs voient `essai` dans « Projets de votre équipe » et ouvrent les projets sur les campagnes ; les autres équipes ne voient pas ce projet |
| UC14 | `lecteurs: updates: managed` | Chez charlie (lecteur), la case des mises à jour est désactivée et aucune vérification n'est faite |
| UC15 | Un auteur tente de modifier `polenta-config` | Push refusé (branche protégée) ; seuls les propriétaires de l'organisation la modifient |

## Critères d'acceptation

Polenta :

1. Un commit fait avec un compte `forgejo` a pour auteur le nom et l'e-mail renvoyés par
   `/api/v1/user`. Jamais « Unknown User », « Git User » ni « Polenta User ».
2. Après une connexion par identifiant et mot de passe, aucun fichier de `userData` ni aucun
   journal ne contient le mot de passe. Le jeton n'est présent que dans le `TokenStore`.
3. Avec un `config.json` contenant `defaultServer` + `hideGithub: true`, l'écran de connexion ne
   montre ni github.com, ni gitlab.com, ni le Device Flow. Sans `config.json`, l'écran est
   identique à celui de GH44 ece9810.
4. `autoUpdate: false` → aucune requête vers github.com au démarrage ni ensuite. Vérifiable au
   proxy ou dans le journal.
5. Compte désactivé côté forge → au premier fetch ou push, message « accès révoqué » affiché **une
   seule fois** pendant les ticks d'auto-pull suivants ; aucun fichier du working tree modifié.
6. Push refusé en 403 → message de droits ; le commit local existe toujours (`git log`).
7. La liste des repos affiche tous les repos accessibles, pagination comprise : vérifié avec plus
   de 50 repos.
8. « Créer sur le serveur » produit un repo **privé** dans l'organisation choisie, avec la branche
   d'intégration poussée. Les organisations sans droit de création ne sont pas proposées.
9. Aucun `host === 'github.com'` ni liste d'hôtes en dur ne subsiste hors du provider GitHub
   (revue de code).
10. Le provider, l'identité et la création de jeton sont importables par le serveur web de GH44 sans
    `electron` ni `keytar` (le build web passe).
11. Les scénarios UC3 à UC8 passent sur Forgejo **et** sur Gitea (versions figées au Design).
12. Typecheck, lint et tests existants passent. Les nouveaux modules (provider, config machine,
    classification 401/403) ont des tests unitaires avec un serveur HTTP simulé.

Infra :

13. `setup` puis `instance add` sur un VPS vierge (Debian 13, celui de l'éditeur) aboutissent sans
    intervention en dehors de `host.env` et des arguments. Relancés une seconde fois, ils ne
    modifient rien et sortent en succès. Debian 12 et Ubuntu 24.04 : `setup` validé sur un hôte
    jetable ou une VM.
14. Après installation : HTTPS valide sur chaque domaine d'instance (pas d'avertissement
    navigateur), forge inaccessible sans connexion, création de compte publique impossible, seuls
    les ports 22/80/443 sont ouverts (`nmap` depuis l'extérieur).
15. **Isolation** avec deux instances sur l'hôte :
    - un compte de l'une est refusé sur l'autre ;
    - depuis le conteneur Forgejo de l'une, l'autre est injoignable ;
    - `instance stop`, `update` ou `remove` sur l'une n'interrompt pas l'autre (sonde de santé
      continue).
16. Après réinstallation complète de l'OS, `setup` puis `instance restore` reproduisent comptes,
    équipes, repos et historique git de chaque instance (UC9). Les données envoyées au stockage S3
    sont chiffrées, et le dépôt d'une instance ne s'ouvre pas avec le mot de passe d'une autre.
17. `instance update` vers une version invalide revient automatiquement à la version précédente,
    avec la forge fonctionnelle.
18. `instance export` produit une archive dont le contenu permet de remonter la forge du client
    ailleurs, avec un Forgejo standard, en suivant le mode d'emploi joint. `instance remove` ne
    laisse aucune donnée de l'instance sur l'hôte (hors sauvegardes externes).
19. `user disable` rend immédiatement inutilisable un jeton existant de l'utilisateur
    (`git fetch` → 401).
20. Le RUNBOOK permet à une personne n'ayant pas participé au projet de préparer un hôte, d'ajouter
    un client, d'ajouter un utilisateur et de restaurer : validation humaine en relecture.

Configuration centralisée et invitation (§3bis, §3ter) :

21. Un utilisateur sans aucun fichier local se connecte via le lien d'invitation sans saisir
    l'adresse du serveur. Le lien ne déclenche jamais une connexion sans mot de passe.
22. La configuration effective d'un utilisateur suit les règles de résolution du §3bis-4 (tests
    unitaires sur des cas multi-équipes).
23. Une préférence par défaut ne remplace jamais un choix personnel déjà fait (langue, thème,
    champs visibles).
24. `polenta-config` : branche `main` protégée ; un membre d'`auteurs` ne peut pas la modifier, un
    propriétaire le peut.
25. Repo de config absent, YAML invalide, serveur hors ligne : Polenta fonctionne comme sans
    configuration (ou avec le cache), sans erreur bloquante.
26. Le fichier DSI, s'il est présent, l'emporte sur la configuration de la forge pour les clés qu'il
    fixe.

## Hors scope

- **SSO desktop OAuth2 PKCE**, nécessaire si le client branche Forgejo sur Entra ID ou Google sans
  mot de passe Forgejo : issue de suivi à créer.
- **Auto-update servi par le serveur du client** (provider `generic` d'electron-updater) : issue de
  suivi. En V1, `autoUpdate: false` et distribution par la DSI.
- **Certificat d'une autorité interne** (serveur accessible uniquement par VPN avec CA privée) :
  issue de suivi. En V1, certificat Let's Encrypt public obligatoire.
- Administration des comptes, équipes ou droits **dans Polenta** : la forge et `polenta-admin.sh`
  font foi.
- Rôles fins côté serveur (Testeur vs Auteur), hook `pre-receive` par chemin, signature des commits
  (analyse §3, §4.5).
- Désactivation des actions d'édition dans l'UI pour un utilisateur en lecture seule (le bandeau
  suffit en V1).
- Liste des repos et création distante pour les comptes `github` (l'abstraction le permet, mais ce
  n'est pas demandé).
- Révocation du jeton côté serveur à la déconnexion.
- Configuration automatique de LDAP/OIDC par `instance add` (documentée seulement).
- Forgejo Actions / CI, GitLab, SSH git.
- Provisionnement du VPS lui-même (commande chez l'hébergeur, DNS, réinstallation de l'OS) : fait
  par un humain.
- Multi-instance : facturation, quotas disque ou RAM par client, création d'instance en
  libre-service par le client, tableau de bord centralisé de supervision (`instance list` et le
  rapport d'état suffisent en V1), répartition des instances sur plusieurs hôtes.
- Contrat de sous-traitance RGPD (art. 28) avec les clients hébergés : contractuel, hors code. Le
  kit fournit seulement les moyens techniques (isolation, export, suppression).
- Image Docker `polenta-web` et OIDC web : GH44 sprints 3 et 4.

## Points ouverts pour le Design

1. Scopes exacts du jeton : à valider sur une instance réelle. Repos de l'organisation (lecture et
   écriture), création de repo dans une organisation, lecture de l'utilisateur et des membres.
2. Versions Forgejo (LTS) et Gitea figées pour les tests (critère 11), et environnement de test :
   conteneurs locaux pour le développement Polenta, VPS de l'éditeur pour les critères 13 à 19
   (§9.9).
2b. Multi-instance : isolation réseau Docker (Caddy relié à chaque réseau d'instance), génération
   et rechargement des sites Caddy sans coupure, jails fail2ban par instance, empreinte mémoire
   mesurée par instance (RUNBOOK §dimensionnement), format et contenu de l'archive
   `instance export`.
3. Où vit la lecture de la configuration machine (service dédié injecté via `HostContext`, ou
   extension d'`AppSettingsService`) et comment le serveur web la reçoit.
4. Classification des erreurs HTTP : isomorphic-git (`HttpError`), binaire git natif (remotes SSH ou
   locaux, T154) et appels API. Un seul point de traduction en 401/403/réseau.
5. Suspension de l'auto-pull sur 401 : état par hôte, levé à la reconnexion.
6. Contenu initial du repo pour `project create` / « Créer sur le serveur » : mêmes fichiers que
   `workspace.createNew` (GH27).
7. Interaction avec `POLENTA_WEB_GIT_HOSTS` (GH44) pour les appels API de la forge depuis le
   serveur web.
7b. Configuration centralisée (§3bis/§3ter) : format exact et validation du `config.yaml`,
    endpoint des équipes de l'utilisateur, protection de branche par l'API, enregistrement du
    protocole `polenta://` (Electron + NSIS), instance unique, interaction avec la liste des repos
    du sprint 4 (« Projets de votre équipe »).
8. Découpage en sprints. Proposition à confirmer :
   - S1 : provider, identité, configuration machine, connexion, 401/403 → débloque GH44 S3 ;
   - S2 : kit `deploy/` → débloque GH44 S4 ;
   - S3 : P1.
