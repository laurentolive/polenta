# GH451 — Version : « Basée sur » accepte une version en cours (planification des versions)

> Issue #451. Constat sur le projet washer (`ver-washer`) : les 7 versions (Pre-assessment, Proto V1…V4, FOT, PRV)
> sont toutes en cours, la liste « Basée sur » d'une version est vide. Besoin : **planifier les versions à l'avance**
> — déclarer que Proto V2 suit Proto V1 sans attendre que Proto V1 soit released. Décisions de l'humain du
> 2026-11-26 : § 1.

## Contexte

`basedOn` est la version précédente d'une version, dans le même repo (SPEC-REQ §11.1). Aujourd'hui elle doit être
**released** : la liste ne propose que les versions released (`basedOnOptions`, `versions.service.ts`) et
l'enregistrement le contrôle (`assertBasedOn`, `VERSION_NOT_FOUND « version released attendue »`).

Ce qui s'appuie sur `basedOn` :

| Usage | Effet d'une base en cours |
|---|---|
| Lignée « disponible » (§11.5, `availableIds`) — section « Exigences » | la lignée parcourt déjà toute version non abandonnée : une base en cours y entre (décision 2) |
| Page : changements des dépendances postérieurs à `basedOn` (§11.3, `rowsOf`) | s'arrête aux `components` de la base, qu'elle soit figée ou non : inchangé |
| Racines de l'analyse d'impact (§11.4) | mêmes lignes que la page : inchangé |
| Reprise des décisions à la création d'une validation (§13) | ne lit que la validation **signée** de `basedOn` ; une base en cours n'en a pas : rien n'est repris, inchangé |
| `base` d'un changement (§11.3) | état dans la dernière version **released** qui incluait l'élément, indépendant de `basedOn` : inchangé |
| Backlog, statut de design, ordre des livraisons | fondés sur les versions released et `freeze.at`, pas sur `basedOn` : inchangés |
| Passage released | aucun contrôle sur `basedOn` aujourd'hui (elle était forcément released) : **contrôle ajouté** (décision 1) |
| Suppression d'une version jamais figée | aucune ne pouvait servir de base ; désormais oui : **contrôle ajouté** (décision 4) |

## 1. Décisions de l'humain (2026-11-26)

1. **Passage released refusé tant que la base est en cours** — nouveau motif, comme une version de composant non
   released. Une base **abandonnée** ne bloque pas (elle ne livre rien). Conséquence : une version released repose
   toujours sur une lignée released ou abandonnée ; tout ce qui est figé (lignée, couverture `verification`,
   analyse, reprise de validation) garde son sens actuel.
2. **Section « Exigences » d'une version en cours = vue plan** : ses changements et ceux de toute sa lignée non
   abandonnée, released **ou en cours**. Exemple : V1 (en cours) inclut R1, R2 ; V2 (en cours, basée sur V1) inclut
   R3 → V2 liste R1, R2, R3 ; V1 liste R1, R2. Une fois V2 released, la liste figée (`verification`) ne bouge plus.
3. **Création : défaut inchangé** = dernière released (aucune s'il n'y en a pas). La liste propose ensuite toutes les
   versions sélectionnables (§ 2.1).
4. **Suppression refusée** d'une version qui sert de base à une autre, avec un message qui nomme les versions
   concernées ; l'utilisateur change d'abord leur base.

## 2. Comportement attendu

### 2.1 Versions sélectionnables comme base

Pour une version V du repo (page de V, ou création — V n'existe pas encore) :

- toutes les versions du repo **released ou en cours** ;
- sauf V elle-même et **ses descendantes** (versions dont la lignée `basedOn` passe par V), pour qu'aucun cycle ne
  puisse être créé ;
- sauf les versions **abandonnées** (elles ne livrent rien ; on ne planifie pas sur elles).

Affichage de chaque option : `<label> (<ID>)` suivi de l'état quand la version n'est pas released (« — En cours », ou « — Abandonnée » pour une base actuelle
abandonnée) ; ordre
inchangé (plus récentes d'abord). Valeur actuelle hors liste (base devenue abandonnée, fichier édité à la main) :
affichée telle quelle en tête, sélectionnée, pour ne pas la perdre au premier changement d'un autre champ.

Exemple washer : sur Proto V3, la liste propose PRV, FOT, Proto V4, Proto V2, Proto V1, Pre-assessment (toutes en
cours), sans Proto V3. Si Proto V4 est basée sur Proto V3, Proto V4 disparaît de la liste de Proto V3.

### 2.2 Enregistrement (interface, MCP, web)

Le contrôle serveur (`assertBasedOn`) applique la même règle qu'en § 2.1 : version du repo existante, ni V, ni
descendante de V, ni abandonnée → sinon refus (`VERSION_NOT_FOUND`, détail explicite : « version abandonnée »,
« boucle de lignée »…). Une version released reste verrouillée (sa base ne change plus). Valable à la création, à la
modification et pour les outils MCP (GH362), mêmes contrôles.

### 2.3 Passage released

Nouveau motif de refus dans l'aperçu et l'action de passage released : **`BASE_NOT_RELEASED`**, détail
`<ID> <label>` de la première version en cours de la lignée (`basedOn` de proche en proche, abandonnées sautées :
une version en cours derrière une base abandonnée bloque aussi). Libellé : « La version de base <label> n'est
pas encore released ». Base released, abandonnée, ou absente : pas de refus.

### 2.4 Suppression

Suppression d'une version jamais figée refusée si au moins une version du repo (quel que soit son état) a
`basedOn` = cette version : **`VERSION_IS_BASE`**, détail : liste des versions concernées (`<ID> <label>`). Libellé :
« Sert de base à <liste> : changez d'abord la base des versions en cours (une version released ou abandonnée
garde la sienne) » — une version abandonnée qui sert de base à une version figée reste donc en place, comme
historique. La copie d'une version garde sa base (inchangé).

### 2.5 Section « Exigences » (§11.5)

Une version **en cours** liste ses changements et ceux de sa lignée non abandonnée (released ou en cours), lus sur le
disque — décision 2. Une version released : inchangé (liste figée ; sa lignée est released ou abandonnée, § 2.3).

### 2.6 Création

Défaut « dernière released » inchangé. La liste de la boîte de création suit § 2.1 (toutes les versions released ou
en cours du repo, hors abandonnées).

## 3. Critères d'acceptation

1. Repo washer (7 versions en cours) : la liste « Basée sur » de Proto V2 propose les 6 autres versions avec la
   mention « en cours » ; choisir Proto V1 l'enregistre (`basedOn: WASHER_VER-0002`) et la page affiche
   le lien vers Proto V1.
2. Proto V1 basée sur rien, Proto V2 basée sur Proto V1 : la liste de Proto V1 ne propose pas Proto V2 ; un appel
   serveur/MCP qui pose `basedOn` = Proto V2 sur Proto V1 est refusé (boucle).
3. Une version abandonnée n'apparaît pas dans la liste ; la poser par MCP est refusé.
4. Passage released de Proto V2 alors que Proto V1 est en cours : refusé, motif `BASE_NOT_RELEASED` affiché dans
   l'aperçu. Proto V1 released (ou abandonnée) → le passage de Proto V2 n'a plus ce motif.
5. Suppression de Proto V1 alors que Proto V2 est basée sur elle : refusée, motif `VERSION_IS_BASE` nommant Proto V2.
   Base de Proto V2 changée → suppression possible.
6. Section « Exigences » : V1 (en cours) inclut R1, R2 ; V2 (en cours, basée sur V1) inclut R3 → V2 liste R1, R2, R3.
   V1 abandonnée → V2 liste R3.
7. Création d'une version dans un repo sans release : « Basée sur » vaut « Aucune » par défaut, la liste propose les
   versions en cours.
8. Comportements inchangés vérifiés : une version released avec une base released garde sa page, sa section
   « Exigences » figée et la reprise de validation de sa base signée.

## 4. Hors scope

- Les **versions des composants** (`components`) : choix et contrôle au passage released inchangés (le refus
  `COMPONENT_NOT_RELEASED` reste).
- Changement de la valeur par défaut à la création (décision 3).
- Rebase automatique à la suppression (décision 4) ou à l'abandon d'une base : une version dont la base est
  abandonnée garde cette base.
- Vue graphique / planning des lignées de versions.
