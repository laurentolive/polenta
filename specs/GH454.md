# GH454 — Composants épinglés sur une branche qui repassent en HEAD détaché

Bug, issue #454. Constaté sur le workspace PH2 le 2026-11-26.

## Symptôme

Des composants placés sur leur branche d'intégration (`int-*`, `main`) via la combo de branche
repassent en « détaché » un peu plus tard, sans que l'utilisateur les touche. « Ça marche une fois,
puis plus. » Les commits faits ensuite sur la branche (mise en conformité, exigences publiées) ne
sont plus dans le dossier du composant.

Reflogs de PH2 :
- 11:25 : bascule de 5 composants sur leurs branches `int-*`, puis commits de mise en conformité
  sur ces branches (elles dépassent le SHA épinglé).
- 12:16:58 : commit sur le repo produit (le HEAD racine change, le cache de l'arbre est périmé).
- 12:18:53 → 12:19:06 : `checkout: moving to <sha>` sur les 5 composants (reconstruction).
- 12:29 : publication d'une exigence dans `hmi-PH2`, épinglé sur `int-PH2` : le manifeste du produit
  passe de `pin: int-PH2` à `pin: ca6b7e0…`.

## Root cause

Deux mécanismes, qui s'enchaînent :

1. **La publication remplace un pin de branche par un SHA.** Après le merge d'un composant dans sa
   branche d'intégration, `publishWorkspace` appelle `propagatePinToDependents(…, sha)` : tout parent
   qui déclare ce composant reçoit le SHA du merge, y compris un parent qui épinglait justement cette
   branche d'intégration. Le choix « suivre la branche » est perdu à la première publication.
2. **La reconstruction de l'arbre re-détache.** `WorkspaceTreeService.buildTree` fait un checkout du
   pin dès que `repoExistsAtPin` est faux. Pour un pin SHA, ce test comparait seulement HEAD au SHA :
   un composant sur une branche qui contient ce SHA mais a avancé était remis sur le SHA, HEAD
   détaché, sans message. La reconstruction suit tout changement de HEAD du repo racine (commit,
   pull, checkout) ou toute écriture de pin d'un autre composant.

## Correctif

1. `propagatePinToDependents` (`renderer/lib/workspaceActions.ts`) prend une option
   `keepBranch` : un parent dont le pin est cette branche est laissé tel quel. `publishWorkspace` et
   `resumePublishAfterResolution` (`renderer/lib/publishWorkspace.ts`) passent la branche
   d'intégration où le merge a eu lieu. Un parent qui épinglait un commit, un tag ou une autre
   branche reçoit toujours le SHA (comportement inchangé). Le choix de branche dans la combo
   (`useBranchCheckout`) n'est pas concerné : il écrit le nom de la branche, comme avant.
2. `repoExistsAtPin` (`main/services/workspace-tree.service.ts`) : pour un pin SHA, un composant
   **sur une branche** dont HEAD descend du commit épinglé est considéré à jour, aucun checkout.
   Restent remis sur le pin : un HEAD détaché ailleurs, et une branche qui ne contient pas le commit
   épinglé (un pin déplacé par un collègue sur une autre ligne s'applique donc toujours).

Diamant (GH324) : tous les parents d'un même montage portent le même pin, donc ils sont soit tous
conservés, soit tous mis à jour ; pas de conflit introduit.

Hors périmètre (point 3 de l'issue, « à discuter ») : avertir avant « Annuler les modifications »
ou « Tout annuler » sur `polenta-repo.yaml`. Non fait.

- `renderer/lib/workspaceActions.pinPropagation.gh454.test.ts` : parent sur la branche du merge →
  pin conservé, aucun rebuild ; parent sur un commit, une autre branche ou un tag → SHA ; sans
  `keepBranch` → inchangé.
- `renderer/lib/publishWorkspace.gh133.test.ts` : la publication passe `keepBranch` = branche
  d'intégration.

Sans le correctif, 5 de ces tests échouent.

## Comment vérifier (à la main, sur PH2)

1. Remettre `hmi-PH2` sur `int-PH2` avec la combo de branche, publier (le pin `int-PH2` est commité
   dans `handstickProduct/polenta-repo.yaml`).
2. Modifier une exigence de `hmi-PH2` et publier : le pin du produit reste `int-PH2` (pas de SHA).
3. Composant épinglé sur un SHA et posé sur sa branche d'intégration (état laissé par une publication
   quand le parent épinglait un commit) : un collègue pousse sur cette branche, « Rafraîchir » le
   composant (pull), puis faire un commit sur le produit : le composant reste sur sa branche, avec le
   travail du collègue. Avant le correctif, il repassait en « détaché » sur l'ancien SHA.
