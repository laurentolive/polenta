# GH470 — Client web 0.7.0 : certificat HTTPS de la forge non vérifié (« CAfile: none »)

Type : bug — issue #470

## Constat

Avec l'image `polenta-web:0.7.0`, « Récupérer » échoue sur une forge HTTPS au certificat public valide :
`git fetch --tags origin : fatal: unable to access '…': server certificate verification failed. CAfile: none CRLfile: none`.
L'image 0.6.0 récupérait sans erreur sur la même instance.

## Root cause

GH337 fait passer git par le `git` natif de l'image. `apps/desktop/Dockerfile.web` l'installe avec
`apt-get install --no-install-recommends git openssh-client` : `ca-certificates`, simple *recommends* de git
sous Debian, n'est pas installé. Le conteneur n'a pas de `/etc/ssl/certs` et libcurl ne peut vérifier
aucun certificat. Toutes les opérations git HTTPS du client web sont touchées (récupérer, publier, cloner).
Le client de bureau n'est pas concerné (git et autorités du poste).

## Correctif

`ca-certificates` ajouté à l'`apt-get install` de git dans l'étape d'exécution de `Dockerfile.web`.

Test de non-régression : `apps/desktop/src/main/git/web-image-ca.gh470.test.ts` (statique, sans construire
l'image) — échoue sans le correctif, passe avec.

## Vérification effectuée

Conteneurs jetables `node:20-bookworm-slim` sur l'hôte de déploiement, `git ls-remote` vers la forge :
- `git openssh-client` seuls → `server certificate verification failed. CAfile: none` (bug reproduit) ;
- avec `ca-certificates` → la poignée TLS passe, git demande l'identifiant (comportement attendu sans jeton).

## Comment vérifier

Image construite depuis cette version, client web activé sur une forge HTTPS : « Récupérer » réussit ;
`docker exec <conteneur> ls /etc/ssl/certs` liste les certificats.
