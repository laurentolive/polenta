# GH49 — Marque blanche : nom, icône et couleurs personnalisables par client

Issue : [#49](https://github.com/laurentolive/polenta/issues/49) — type:feature

## 1. Contexte

Un client n'aime pas le nom « Polenta » et veut livrer l'outil à ses propres clients finaux
sous **sa** marque. Aujourd'hui la marque est codée en dur à plusieurs endroits :

| Endroit | Occurrence actuelle |
|---------|---------------------|
| Packaging (`apps/desktop/electron-builder.yml`) | `appId: com.polenta.desktop`, `productName: Polenta`, `extraMetadata.name: polenta`, `artifactName: Polenta-Setup-${version}.${ext}`, `nsis.shortcutName: Polenta`, `publish` → `laurentolive/polenta` |
| Icônes | `apps/desktop/build/icon.ico`, `icon.png`, `icon-256.png`, `icon.svg` |
| Nom de l'app / données utilisateur | `app.setName('Polenta')` (`src/main/index.ts`) → dossier `userData` ; `KEYTAR_SERVICE = 'polenta'` (`auth.service.ts`) |
| Titre de fenêtre | `<title>Polenta</title>` (`renderer/index.html`), `Polenta v${version} — …` (`ProjectPanel.tsx`) |
| Textes UI (i18n FR/EN) | `login.welcome`, `demoTitle`, `demoFolderNotEmpty`, `notAWorkspace`, `openExistingHelp`, `notAnExecutionSheet`, titre de mise à jour disponible, `exportTemplatesExamplesHint`… ; messages en dur dans `useWorkspaceStructure.ts`, `workspace-tree.service.ts`, `workspace.service.ts` |
| Fichiers générés | `AGENTS.md` (`agents-md.template.ts`, nom + lien `polenta.dev`), dossier `Exemples Polenta` (`export-template-library.ts`), `workbook.creator = 'Polenta'` (export Excel), auteur git par défaut `Polenta <polenta@localhost>` et `Polenta User` (`workspace.service.ts`, `auth.service.ts`) |
| Couleurs | Tokens de `src/renderer/theme.config.ts` → `index.css` (clair + `.dark`) et `tailwind.theme.generated.js` via `pnpm theme:generate` |

## 2. Décisions prises (questions Spec)

| Question | Décision |
|----------|----------|
| Moment de la personnalisation | **Au build** : un installeur par marque. Pas de réglage de marque au runtime. |
| Périmètre | Nom affiché, icône, **couleurs et logo dans l'UI**, textes générés. |
| Identifiants techniques de format | **Inchangés** : `.polenta/`, `polenta-repo.yaml`, `window.polenta`, packages `@polenta/*`, marqueurs `polenta:agents-md-version`, nom du serveur MCP `polenta-mcp-server`, IDs internes (`rIdPolenta…`). Un projet créé avec une marque s'ouvre avec n'importe quelle autre. |
| Mises à jour / coexistence | **Canal par marque** : chaque marque a son `appId`, son dossier de données, ses credentials et sa source de mise à jour. Polenta et une marque client cohabitent sur un même poste sans se mélanger. |

## 3. Description fonctionnelle

### 3.1 Définition d'une marque

Une marque est un **dossier** `apps/desktop/brands/<brandId>/` versionné dans le repo Polenta,
contenant :

- `brand.yaml` — l'identité de la marque :

  | Clé | Obligatoire | Rôle | Exemple |
  |-----|-------------|------|---------|
  | `id` | oui | identifiant technique (`[a-z0-9-]+`), égal au nom du dossier | `acme` |
  | `productName` | oui | nom affiché partout (fenêtre, UI, installeur, raccourci, fichiers générés) | `Acme Specs` |
  | `appId` | oui | identifiant OS de l'application, unique par marque | `com.acme.specs` |
  | `executableName` | non (défaut : `id`) | nom npm packagé / dossier d'installation | `acme-specs` |
  | `website` | non | lien cité dans `AGENTS.md` ; absent → phrase sans lien | `https://acme.example` |
  | `update` | non | source de mise à jour (`provider: github` + `owner`/`repo`, ou `provider: generic` + `url`) ; absent → auto-update **désactivé** pour cette marque | — |
  | `theme` | non | surcharges de tokens de couleur, clair et sombre (§3.4) | — |

- `icon.ico`, `icon.png` (≥ 512 px), `icon-256.png`, `icon.svg` — icônes de l'app.
- `logo.svg` (optionnel) — logo affiché dans l'UI (§3.4) ; absent → pas de logo, comme aujourd'hui.

**Polenta est elle-même une marque** (`brands/polenta/`), contenant les valeurs et icônes
actuelles. Le build par défaut (`pnpm build`, `pnpm dev`, CI actuelle) utilise `polenta` :
**aucun changement visible** pour les utilisateurs existants de Polenta, ni de leurs données.

### 3.2 Choix de la marque au build

- La marque est choisie par une variable d'environnement `POLENTA_BRAND=<brandId>` (défaut
  `polenta`) lue par le build (`electron-vite`, `electron-builder`, `theme:generate`) et par
  `pnpm dev` — pour pouvoir voir une marque en développement.
- Une marque inconnue, ou un `brand.yaml` invalide (clé obligatoire manquante, `id` ≠ nom du
  dossier, icône manquante, token de thème inconnu), **fait échouer le build** avec un message
  qui nomme la marque et le problème. Jamais de repli silencieux sur Polenta.
- La marque est **figée** dans le binaire : rien dans l'UI ne permet de la changer ni de voir
  « Polenta » à la place.
- La CI (`release.yml`) peut produire l'installeur d'une marque (ex. tag `vX.Y.Z` → Polenta ;
  déclenchement manuel avec paramètre `brand`). Le détail est laissé au Design.

### 3.3 Nom affiché

Partout où « Polenta » désigne le **produit** pour l'utilisateur, on affiche `productName` :

- installeur `<productName>-Setup-<version>.exe`, dossier d'installation, raccourcis bureau /
  menu Démarrer, nom du processus, liste « Applications installées » ;
- titre de fenêtre (`<productName> v<version> — <projet> — <chemin>`) et `<title>` HTML ;
- textes UI FR et EN : les chaînes i18n concernées utilisent une interpolation `{{appName}}`
  (aucune chaîne traduite ne contient plus « Polenta » en dur) ; idem pour les messages d'erreur
  écrits côté main ;
- notification de mise à jour (« <productName> vX.Y.Z est disponible ») ;
- fichiers générés : `AGENTS.md` (nom + `website`), dossier d'exemples `Exemples <productName>`,
  propriété « auteur » des classeurs Excel exportés, identité git par défaut
  (`<productName> <<id>@localhost>`) et nom d'utilisateur par défaut.

Restent « polenta » (identifiants de format, §2) : ce qu'on ne voit qu'en ouvrant le repo
(`.polenta/`, `polenta-repo.yaml`) ou en inspectant la configuration MCP (`.mcp.json`).
Dans `AGENTS.md`, la phrase qui explique ces fichiers les nomme tels quels (un agent IA doit
les trouver), mais présente le produit sous `productName`.

### 3.4 Icône, logo et couleurs

- **Icône** : celle de la marque pour l'exécutable, l'installeur, les raccourcis, la barre des
  tâches et la fenêtre.
- **Logo** : si `logo.svg` est fourni, il s'affiche sur l'écran d'accueil (au-dessus du titre
  « Bienvenue dans <productName> », `routes/login.tsx` / `routes/index.tsx`). La marque Polenta
  n'en fournit pas aujourd'hui → écran d'accueil inchangé.
- **Couleurs** : `brand.yaml > theme` surcharge des tokens existants de `theme.config.ts`, pour
  le thème clair (`light`) et sombre (`dark`) séparément. Seuls les tokens nommés sont surchargés,
  les autres gardent la valeur Polenta. Un token inconnu fait échouer le build (§3.2).
  La surcharge passe par `theme:generate` : pas de code de thème spécifique à une marque dans
  le renderer. Les couleurs de **statut** (succès, alerte, danger…) restent personnalisables
  techniquement, mais le Design recommande de limiter la surcharge aux tokens d'identité
  (`prim`, `prim-fg`, accent, barre d'activité).

### 3.5 Coexistence et mises à jour

- Chaque marque a son propre `appId`, son propre nom d'app (`app.setName(productName)`) donc son
  propre dossier `userData` (`workspace.json`, `auth.json`, `app-settings.json`), et son propre
  service keytar (`KEYTAR_SERVICE` dérivé de `id`) : installer « Acme Specs » sur un poste qui a
  déjà Polenta ne montre ni les projets récents ni les comptes de Polenta, et réciproquement.
- **Polenta garde exactement ses valeurs actuelles** (`userData` « Polenta », keytar `polenta`,
  `appId com.polenta.desktop`) : aucune migration pour les utilisateurs existants.
- Le serveur MCP packagé dans une marque lit les credentials de **cette** marque (même service
  keytar que l'app qui l'a installé).
- Mise à jour : si `update` est défini, `UpdateService` interroge cette source (et uniquement
  elle) ; une installation Acme ne se met jamais à jour avec un installeur Polenta, et
  inversement. Si `update` est absent, la vérification n'est pas lancée et la préférence
  « Vérifier les mises à jour » est masquée.

## 4. Critères d'acceptation

1. `pnpm build` / `pnpm dev` sans `POLENTA_BRAND` produit une app **identique** à aujourd'hui :
   mêmes nom, icône, couleurs, `appId`, dossier `userData`, service keytar, nom d'installeur,
   source de mise à jour. Un utilisateur existant retrouve projets et comptes après mise à jour.
2. Avec `POLENTA_BRAND=demo` (marque de test `brands/demo/` fournie avec le ticket : nom
   « Demo Specs », icône et couleur primaire distinctes), l'installeur s'appelle
   `Demo Specs-Setup-X.Y.Z.exe`, s'installe dans son propre dossier, crée un raccourci
   « Demo Specs » avec l'icône de la marque.
3. Dans l'app « Demo Specs », en FR et en EN, **aucun texte visible** ne contient « Polenta » :
   titre de fenêtre, écran d'accueil, projet de démo, messages « pas un projet… », notification
   de mise à jour, panneau Compte. Vérifiable par un test qui cherche « Polenta » dans les
   fichiers i18n (hors clés) et échoue s'il en trouve.
4. Dans un projet créé avec « Demo Specs » : `AGENTS.md` présente le produit comme « Demo Specs »,
   les exemples sont copiés dans `Exemples Demo Specs/`, un export Excel a pour auteur
   « Demo Specs ». Le projet contient toujours `.polenta/` et s'ouvre sans erreur dans Polenta.
5. La couleur primaire de la marque `demo` est appliquée en thème clair et en thème sombre ;
   les tokens non surchargés ont la valeur Polenta.
6. Le logo de `demo` s'affiche sur l'écran d'accueil ; sans `logo.svg`, l'écran d'accueil
   est identique à aujourd'hui.
7. Polenta et Demo Specs installés sur le même poste : projets récents, comptes et préférences
   sont séparés ; les deux peuvent tourner en même temps.
8. Une marque sans `update` ne lance aucune vérification de mise à jour et n'affiche pas la
   préférence ; une marque avec `update` n'interroge que sa propre source.
9. `POLENTA_BRAND=inconnue`, un `brand.yaml` sans `productName`, une icône manquante ou un token
   de thème inconnu font échouer le build avec un message explicite.

## 5. Hors scope

- Changer la marque **au runtime** (réglage, fichier de config après installation).
- Renommer les identifiants de format : `.polenta/`, `polenta-repo.yaml`, `window.polenta`,
  `@polenta/*`, nom du serveur MCP, marqueurs internes.
- Migrer les données d'un utilisateur d'une marque vers une autre.
- Signature de code et certificats par marque (à traiter si un client l'exige).
- Polices, mise en page ou textes métier personnalisés par marque (seuls nom, icône, logo et
  couleurs sont couverts).
- Gabarits d'export Word/Excel d'exemple aux couleurs de la marque (les gabarits restent ceux
  de Polenta ; seul le dossier d'exemples est renommé).
- `apps/web` / client web (GH44).

## 6. Points d'attention pour le Design

- **Source unique** : un module de marque (`brand` résolu au build, injecté en constante dans
  main, preload et renderer — ex. `define` d'electron-vite) ; aucune chaîne « Polenta » ailleurs.
  Exposer `appName` au renderer sans nouvel aller-retour IPC si possible.
- `electron-builder.yml` statique → probablement config JS (`electron-builder.config.ts`) qui lit
  `brand.yaml`, ou surcharge par `--config.*`. Garder les commentaires GH26 (MAX_PATH,
  `extraMetadata.name`, keytar).
- `extraMetadata.name` (GH26) dérive de `executableName` : vérifier que le dossier d'installation
  et le cache updater restent `Polenta` pour la marque par défaut.
- i18n : `{{appName}}` injecté globalement (`defaultVariables` d'i18next) plutôt que passé à
  chaque appel `t()`.
- `AGENTS.md` : changer le gabarit implique d'incrémenter `AGENTS_MD_TEMPLATE_VERSION`, ce qui
  **régénère** `AGENTS.md` dans les projets existants — acceptable, mais à mentionner. Un projet
  ouvert successivement par deux marques ne fait pas de ping-pong : le marqueur compare la
  version du gabarit, pas le nom, donc la première marque qui régénère fixe le nom affiché.
- Le serveur MCP (bundle esbuild séparé) doit recevoir la même marque que l'app.
- `theme:generate` aujourd'hui produit des fichiers **commités** (`index.css`,
  `tailwind.theme.generated.js`) : générer la variante de marque sans salir le working tree
  (fichier généré au build, ou surcharge CSS injectée).
- Test de non-régression « aucun Polenta visible » (critère 3) intégré à la CI.
