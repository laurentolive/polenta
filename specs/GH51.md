# GH51 — Connexion SSO du desktop sur une forge (OAuth2 PKCE)

Issue : #51 (feature). Suite de #45 (kit forge, `polenta-admin oauth-app create`). Prévu dans
`specs/ANALYSE-SERVEUR-AUTOHEBERGE.md` §4.3-10.

## Constat

Le desktop se connecte à une forge Forgejo de deux façons : jeton d'accès saisi à la main (PAT, `auth.setup`),
ou Device Flow pour github.com uniquement (`startDeviceFlow`, refusé pour les autres hôtes). Quand le client
branche Forgejo sur son annuaire (Entra ID, Google Workspace, Keycloak… en OIDC), il n'y a plus de mot de
passe Forgejo : la connexion « identifiant + mot de passe » de #45 ne marche plus, et l'utilisateur doit créer
un jeton à la main dans la forge.

Forgejo est fournisseur OAuth2. La doc Forgejo (lue pour cette spec, `forgejo.org/docs/latest/user/authentication/oauth2-provider/`)
indique : les clients publics sont supportés, PKCE (S256) est une extension supportée, et une redirection
loopback `http://127.0.0.1/` autorise **n'importe quel port** pour un client public. Elle ne dit rien sur le
renouvellement : aucun `grant_type=refresh_token` n'est listé, la durée de vie de l'access token n'est pas une
règle (l'exemple montre `expires_in: 3600`), et les scopes ne sont pas implémentés (un token agit avec tous les
droits de l'utilisateur). Ces points sont à vérifier sur la forge réelle (voir Vérification préalable).

## Besoin

Un utilisateur du desktop se connecte à une forge Forgejo en choisissant « Se connecter avec le navigateur » :
le navigateur ouvre la page d'autorisation de la forge (et donc l'annuaire de l'entreprise), Polenta reçoit le
code sur un port loopback, l'échange contre un jeton, et l'enregistre comme une connexion normale. Pas de mot de
passe Forgejo, pas de jeton à créer à la main.

## Hors scope

- GitHub : son Device Flow ne change pas.
- Forgejo sans client public enregistré (l'administrateur doit l'avoir créé, voir D2) : le PAT reste disponible.
- Configuration de l'OIDC côté forge (Entra, Keycloak…) : elle se fait dans Forgejo, hors Polenta.
- Scopes fins : non supportés par Forgejo à ce jour.
- Connexion SSO du serveur web : déjà traitée par #44 (OIDC côté serveur).
- Gestion MFA côté Polenta : déléguée à la forge et à l'annuaire.

## Description fonctionnelle

- **Écran de connexion** (`routes/login.tsx`) : pour une forge Forgejo, un bouton **Se connecter avec le navigateur**
  s'ajoute au PAT (D4). Pendant l'attente : message « Terminez la connexion dans votre navigateur », bouton
  **Annuler**, délai de 5 minutes (D6).
- **Flux** (main process) : génération d'un `code_verifier` (43 à 128 caractères) et de son `code_challenge`
  (S256) et d'un `state` aléatoire ; ouverture du navigateur sur `/login/oauth/authorize` avec `client_id`,
  `redirect_uri` loopback, `response_type=code`, `state`, `code_challenge`, `code_challenge_method=S256` ;
  écoute sur `127.0.0.1` (port libre choisi par le système, D1) pour le retour ; vérification du `state` ;
  échange du `code` sur `/login/oauth/access_token` (`grant_type=authorization_code`, `code`, `client_id`,
  `redirect_uri`, `code_verifier`, sans secret) ; identité vérifiée (`/api/v1/user`) ; enregistrement du compte
  par le chemin existant (`persistToken`).
- **Renouvellement** : si la réponse contient un `refresh_token` et que la forge l'accepte (vérification
  préalable), le jeton est renouvelé avant son expiration et sur un 401 ; sinon, à l'expiration, la connexion
  repasse par le navigateur (D5).
- **Déconnexion** : efface le jeton d'accès et, s'il existe, le refresh token.
- **Client OAuth** : une application **publique** (sans secret), créée par l'administrateur avec `polenta-admin`.
  Le kit crée aujourd'hui des applications confidentielles (`confidential_client: true`, `cmd_oauth_app_create`) :
  il faut une option pour les créer publiques (D2).
- **Identifiant du client sur le poste** : dans la configuration machine (D3).

## Décisions (validées par l'humain le 2026-11-27 : D1 à D7, recommandations retenues)

- **D1 — Port de redirection** : port libre choisi à chaque connexion, sur `127.0.0.1` (la doc Forgejo l'autorise
  pour un client public). *Alternative* : un petit ensemble de ports fixes enregistrés dans l'application, si la
  vérification préalable montre que le port libre est refusé.
- **D2 — Client public** : le kit crée une application **publique** (`polenta-admin oauth-app create --public`,
  redirection `http://127.0.0.1/`). Les applications confidentielles existantes (web, #44) ne changent pas.
  *Alternative* : réutiliser le client confidentiel du web (non recommandé : un secret ne doit pas être dans le
  poste client).
- **D3 — Identifiant du client** : `MachineConfig.forgeSsoClientId`, posé par l'installeur ou l'administrateur de
  poste (comme `defaultServer`). *Alternative* : configuration d'équipe (dépôt de configuration de la forge),
  plus pratique pour plusieurs forges, mais à ouvrir dans un ticket séparé.
- **D4 — Écran** : le bouton navigateur s'ajoute au PAT ; le PAT reste le repli, pour une forge sans client public.
- **D5 — Renouvellement** : si la forge accepte le `refresh_token` : renouvellement silencieux. Sinon, à
  l'expiration du jeton, nouvelle connexion par le navigateur. *Alternative* : aucune (la connexion navigateur à
  chaque expiration est la seule option sans renouvellement).
- **D6 — Délai** : 5 minutes pour terminer la connexion dans le navigateur, puis échec proprement signalé.
- **D7 — Sécurité** : le jeton OAuth a les droits complets de l'utilisateur (scopes non supportés par Forgejo). Il
  est rangé comme le jeton d'accès actuel (magasin de jetons du poste, jamais dans `auth.json`). À noter pour la
  revue d'audit (`ANALYSE-SERVEUR-AUTOHEBERGE.md` §4.5) : le risque est le même qu'avec un PAT à tous les droits.

## Vérification préalable (bloquante avant le merge)

À faire sur la forge déployée (serveur de test du kit, `polenta-admin oauth-app create --public`) :

1. Création d'un client public ; la réponse ne contient pas de `client_secret`.
2. Autorisation avec PKCE S256 et redirection `http://127.0.0.1:<port>/callback` à un port non enregistré : acceptée.
3. Échange du code avec le `code_verifier` : jeton reçu ; l'échange sans `code_verifier` est refusé.
4. Durée de vie de l'access token (`expires_in`) mesurée.
5. Présence d'un `refresh_token` ; s'il existe, échange `grant_type=refresh_token` : nouveau jeton accepté.

Le résultat décide de D5 (renouvellement silencieux ou nouvelle connexion navigateur) et est consigné dans
`specs/GH51-design.md`. Le code couvre les deux cas. Si le point 2 échoue, D1 passe à l'alternative (ports fixes).

## Critères d'acceptation mesurables

- [ ] **AC1** — Pour une forge Forgejo, l'écran de connexion propose « Se connecter avec le navigateur » ; le PAT reste
      disponible. Pour github.com, rien ne change.
- [ ] **AC2** — La page d'autorisation reçoit `response_type=code`, `code_challenge` (S256, 43 à 128 caractères),
      `state`, et une `redirect_uri` `http://127.0.0.1:<port>/callback` (test : lecture de l'URL ouverte).
- [ ] **AC3** — Un retour avec un `state` différent est refusé : aucun jeton, aucun compte.
- [ ] **AC4** — `error=access_denied` ou une réponse sans `code` : message clair, aucun compte, aucun jeton.
- [ ] **AC5** — Un retour correct : l'échange envoie le `code_verifier` ; le compte est enregistré par `persistToken`
      (identité vérifiée) ; les dépôts de la forge deviennent accessibles.
- [ ] **AC6** — Sans `code_verifier` valide, la forge refuse l'échange : rien n'est enregistré (test sur le serveur
      de test, vérification préalable point 3).
- [ ] **AC7** — Pas de retour dans 5 minutes, ou « Annuler » : la connexion est abandonnée, le serveur loopback est fermé.
- [ ] **AC8** — Port loopback occupé : essai du port suivant ; échec signalé sans blocage si aucun n'est libre.
- [ ] **AC9** — Renouvellement (si la forge accepte le `refresh_token`) : un jeton expiré est renouvelé sans
      intervention, et la requête est rejouée. Si le renouvellement est refusé, le compte passe en « à reconnecter ».
- [ ] **AC10** — Déconnexion : le jeton d'accès et le refresh token sont effacés du magasin ; rien dans `auth.json`.
- [ ] **AC11** — Aucun jeton, `code` ni `code_verifier` dans les journaux ni dans le renderer (les messages
      n'affichent que le type d'erreur).
- [ ] **AC12** — `polenta-admin oauth-app create --public` crée un client sans secret ; sans l'option, le comportement est
      inchangé (test du script du kit).

## Compatibilité avec la v0.7.0 (décision du 2026-11-27)

Les comptes existants (format `auth.json`, clés du magasin de jetons, écran de connexion, fournisseurs) ne changent
pas entre v0.6.0 et v0.7.0 ; les tests de `auth.service.test.ts` couvrent les comptes anciens. Le SSO n'ajoute que des
champs optionnels et des clés réservées aux comptes SSO. Décision de l'humain : cette compatibilité est établie sur la
base du code et des tests ; pas d'essai de mise à jour manuel exigé. Un écart éventuel sera corrigé après coup.
