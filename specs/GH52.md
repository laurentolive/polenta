# GH52 — Mises à jour de Polenta servies par le serveur du client

Type : feature (`type:feature`). Milestone B — Déploiement serveur. Branche `milestone-B`, pas de branche ni de worktree par ticket.
Issue d'origine : suite de #45 (hors périmètre V1, P2 — `specs/ANALYSE-SERVEUR-AUTOHEBERGE.md` §4.3-11).

Statut : **spec en attente de validation humaine**. Les questions de la dernière section doivent être tranchées avant la phase Design.

## Besoin

Un client dont le pare-feu bloque `github.com` ne reçoit pas les mises à jour : l'auto-update lit aujourd'hui les GitHub Releases.
En V1 (#45), la parade est `autoUpdate: false` (config machine) ou `updates: managed` (config d'équipe), et la DSI distribue le MSI à la main.
Ce ticket doit permettre à l'application de lire le flux de mise à jour sur le serveur du client, pour que les mises à jour arrivent sans sortie vers internet.

## État du code (vérifié, pas seulement d'après l'issue)

Source : compte rendu de l'exploration du code à la reprise (`origin/main` db4559b).

- **Vérification et téléchargement** : `apps/desktop/src/main/services/update.service.ts`. `scheduleStartupCheck` (:39-49) ne fait rien hors build packagé ; `check()` appelle `autoUpdater.checkForUpdates()` (:196), répété toutes les 4 h (:132). `autoDownload = false` (:51). Aucun appel direct à l'API GitHub : le flux est `latest.yml` / `app-update.yml`, générés depuis la config de publication.
- **Provider** : `apps/desktop/electron-builder.config.ts`, `publishConfig()` (:27-34) lit `brand.update` de `apps/desktop/brands/polenta/brand.yaml` (:9-12) : `provider: github`, `owner: laurentolive`, `repo: polenta`. **Le provider est donc figé au build**, il n'est pas lu à l'exécution.
- **Config machine** : `packages/types/src/forge.ts:29-38` (`MachineConfig`), lue par `apps/desktop/src/main/services/machine-config.ts` (chemin Windows : `%ProgramData%\Polenta\config.json`, surcharge `POLENTA_CONFIG`). Seule clé liée aux mises à jour : `autoUpdate: false` (:86-88) ; une clé inconnue est signalée (:91). **Aucune clé d'URL ni de provider.**
- **Verrou** : `app-settings.service.ts:33-35` (`updatesLocked = autoUpdate === false || forgeUpdatesManaged()`) et :41-45 (force `autoCheckUpdates=false`).
- **Config d'équipe** : `updates: managed` lu dans le dépôt `<org>/polenta-config/config.yaml` (`forge-config.service.ts`, `team-config.ts`). Ce n'est qu'un verrou, pas une URL.
- **Serveur** : `deploy/lib/caddy.sh` n'a aucune route statique (seulement `reverse_proxy` vers `forgejo-<nom>:3000` :122 et `polenta-web-<nom>:8787` :207). Aucun `file_server`, aucun dossier `polenta-updates` dans `deploy/`.

Écart entre la piste de l'issue et le code : la spec §4.3-11 dit que le provider se choisit par la config machine (§4.1-3), or elle n'a pas de clé pour cela et le provider est figé au build.

## Description fonctionnelle

- **Cas 1 — flux de l'hôte** : la DSI déclare dans la config machine l'URL du flux du serveur client. L'application interroge ce flux à la place de GitHub, avec le même cycle (vérification au démarrage, toutes les 4 h, téléchargement manuel ou automatique selon la préférence utilisateur).
- **Cas 2 — pas de clé** : comportement actuel (GitHub), inchangé. Pas de régression pour les postes sans config machine.
- **Cas 3 — flux injoignable** : l'application ne plante pas, n'affiche pas d'erreur bloquante, journalise l'échec de vérification (même traitement qu'un GitHub injoignable aujourd'hui).
- **Cas 4 — publication** : l'exploitant publie une version sur l'hôte (commande du kit) à partir des artefacts de la release ; le flux `latest.yml` et les fichiers associés sont servis en statique par le Caddy du kit, sur le domaine de la forge.
- **Cas 5 — coexistence** : `autoUpdate: false` garde la priorité (aucune vérification, quel que soit le flux).

## Critères d'acceptation (provisoires, à figer après les réponses)

1. Avec une clé de flux dans `config.json`, `update.service.ts` interroge cette URL et non `github.com` (test unitaire du service, avec `autoUpdater` simulé).
2. Sans clé de flux, le comportement est identique à `origin/main` (test de non-régression existant).
3. Clé de flux invalide ou inconnue : avertissement journalisé, retour au comportement par défaut ; l'application démarre.
4. `polenta-host update publish <version> <dossier>` copie les artefacts et le `latest.yml` sous `/opt/polenta/updates/…` et les rend servis (`curl -fsS https://<domaine>/polenta-updates/latest.yml` → 200) ; une deuxième publication n'écrase pas la version précédente.
5. Le bloc Caddy de l'instance sert `/polenta-updates/*` et seulement ce chemin ; le reste du site n'est pas modifié (`acceptance.sh` existant passe).
6. `autoUpdate: false` : aucun appel au flux (test).

## Hors scope

- La signature des installeurs (`GH388`, « éditeur inconnu »). Un flux servi par le client sans signature reste bloqué par Windows ou electron-updater selon le réglage ; à trancher (question 5).
- La construction des artefacts : ils restent produits par la release GitHub. Ce ticket ne fait que les servir.
- Le réseau de l'hôte et la résolution DNS du serveur client.
- Les mises à jour de la forge elle-même (`polenta-host instance update`, #...) : sans rapport.

## Questions à trancher avant le Design

1. **Où se configure l'URL du flux ?** Recommandation : nouvelle clé de config machine `updateFeedUrl` (URL de base, ex. `https://forge.client.fr/polenta-updates/`), lue au démarrage, appliquée avec `autoUpdater.setFeedURL({ provider: 'generic', url })`. Pas de clé d'équipe (elle serait lue depuis la forge, ce qui n'est pas le bon endroit pour un flux qu'on doit pouvoir joindre sans elle). Confirmer ?
2. **Build ou runtime ?** Recommandation : binaire inchangé (provider `github` au build), bascule à l'exécution quand `updateFeedUrl` est présent. Évite un build par client. Confirmer ?
3. **Qui produit les artefacts ?** Recommandation : la DSI télécharge la release GitHub une fois (ou un script du kit le fait), puis `polenta-host update publish <version> <dossier>`. Le kit ne construit rien. Confirmer ?
4. **Route Caddy** : `handle /polenta-updates/*` dans le bloc de chaque instance (`<nom>.caddy`), dossier `/opt/polenta/updates/` monté en lecture seule. En mode `external`, le Caddy existant doit avoir la même route : à documenter comme les `_*.caddy` (A10), ou à générer ? Recommandation : documenter pour external, générer pour managed.
5. **Signature** : un flux non signé est-il acceptable pour la V1 de cette feature, sachant que `GH388` traite la signature Windows ? Si non, ce ticket est bloqué par GH388 et doit attendre.
6. **Verrou du flux GitHub** : quand `updateFeedUrl` est présent, GitHub n'est plus interrogé du tout (recommandé) ou seulement en repli ?
