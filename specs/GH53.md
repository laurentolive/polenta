# GH53 — Forge interne avec autorité de certification privée

Type : feature (`type:feature`). Milestone B — Déploiement serveur. Branche `milestone-B`, pas de branche ni de worktree par ticket.
Issue d'origine : suite de #45 (hors périmètre V1, P2 — `specs/ANALYSE-SERVEUR-AUTOHEBERGE.md` §4.3-12).

Statut : **spec en attente de validation humaine**. Les questions de la dernière section doivent être tranchées avant la phase Design.

## Besoin

Un client exige une forge accessible seulement par VPN, avec un certificat émis par son autorité interne.
Aujourd'hui Polenta ne sait pas faire confiance à cette autorité : Electron ne lit pas le magasin Windows, donc les appels HTTPS (API et git) échouent.
En V1 (#45), un certificat Let's Encrypt public est obligatoire.

## État du code (vérifié à la reprise, `origin/main` db4559b)

Compte rendu d'exploration du code, chaque point vérifié par lecture.

- **Appels API** : `apps/desktop/src/main/services/forge/forge-http.ts` utilise `undici.request` avec `dispatcher: await resolveProxyDispatcher(url)` (:105, et :115 pour les redirections). Aucune option `ca` ni `rejectUnauthorized`.
- **Dispatchers** : `apps/desktop/src/main/services/net-proxy.ts` construit `new ProxyAgent({ uri, proxyTls, requestTls })` (:46) et `new Agent({ connect: { timeout } })` (:47), mis en cache par proxy et délai (:14, :42-49). Seule option TLS : le délai. **C'est le point d'injection de la CA pour l'API.**
- **Git** : il n'y a pas de dispatcher pour git. Les échanges git HTTP passent par le **CLI git** (`git-backend.ts`, `netRun` :1184-1205) ; seule option liée au réseau : `http.proxy` (:1189-1191). Aucune option TLS. Pour git, la CA se passerait par `http.sslCAInfo`.
- **Configuration git** : `git-config.ts:202-203` pose `GIT_CONFIG_NOSYSTEM=1` et un fichier global propre à Polenta : le `gitconfig` système ne s'applique pas, il faudra donc écrire `http.sslCAInfo` dans ce fichier.
- **Aucune lecture de CA aujourd'hui** : pas de `NODE_EXTRA_CA_CERTS`, pas de `rootCertificates`, pas de `setCertificateVerifyProc`, pas de magasin Windows. `net-proxy.ts:167-171` ne fait que traduire l'erreur de certificat en message (« certificat racine de l'entreprise à installer »).
- **Config machine** : `packages/types/src/forge.ts:29-38` (`MachineConfig`), lue par `machine-config.ts`. Clés existantes : `defaultServer`, `demoProjectUrl`, `hideGithub`, `autoUpdate`. **Aucune clé de CA ni de proxy.** Une clé inconnue est signalée et ignorée (:90-91).
- **Serveur (kit)** : `deploy/lib/caddy.sh` ne contient aucune directive TLS. Les blocs de site (`caddy_render_site` :104-125, `caddy_render_web_site` :190-210) n'ont pas de `tls`. Le seul réglage ACME est l'e-mail (:47-51). Un certificat fourni (`tls /chemin/cert /chemin/clé`) **n'est pas possible aujourd'hui** : ni variable, ni modèle, ni montage pour les certificats (volumes `etc:ro` et `data`, :33-34).
- **Mode external** : le certificat relève du Caddy de l'exploitant (`RUNBOOK.md` :467, :521).

Écarts entre la spec §4.3-12 et le code (à corriger dans la spec, pas dans le code) :

- La spec cite `git-http.ts` : ce fichier n'existe pas. Git passe par le CLI (voir ci-dessus).
- La spec dit « Node 20 (Electron 31) » : `apps/desktop/package.json` indique Electron `^45.1.0`. Le raisonnement reste valable (Electron ne lit pas le magasin Windows) mais la version citée est fausse.
- La spec dit « config machine » pour le chemin de la CA : cette clé n'existe pas encore.

## Description fonctionnelle

- **Cas 1 — CA interne déclarée** : la DSI déclare dans la config machine le chemin d'un fichier PEM (CA racine, éventuellement chaîne). Polenta charge ce fichier et l'utilise pour :
  - les appels API (`forge-http.ts` via le dispatcher de `net-proxy.ts`) ;
  - git (`http.sslCAInfo` dans le fichier de configuration git de Polenta).
- **Cas 2 — pas de clé** : comportement actuel, inchangé (CA publiques seulement).
- **Cas 3 — fichier absent ou illisible** : avertissement journalisé, comportement par défaut ; l'application démarre (règle de `machine-config.ts`).
- **Cas 4 — côté kit** : une instance peut être servie avec un certificat fourni (chemin cert et clé sur l'hôte) au lieu d'ACME, pour un domaine interne.
- **Cas 5 — la CA ne sert qu'au client concerné** : elle n'élargit pas la confiance à d'autres hôtes que la forge déclarée (à préciser, voir question 3).

## Critères d'acceptation (provisoires)

1. Avec `caPath` valide dans `config.json`, un appel API à une forge utilisant une CA de test est accepté ; sans la clé, il échoue comme aujourd'hui (test d'intégration avec un serveur HTTPS local signé par une CA de test).
2. git clone/fetch via HTTPS sur cette forge réussit avec la clé, échoue sans (test e2e avec le serveur git de test `apps/desktop/e2e-web/support`).
3. `caPath` absent, illisible ou non PEM : avertissement journalisé, démarrage normal (test unitaire de `machine-config.ts`).
4. Côté kit : `polenta-host instance add … --tls-cert <cert> --tls-key <clé>` (ou équivalent) génère un bloc Caddy avec `tls <cert> <clé>` et sans ACME ; `acceptance.sh` existant reste vert pour les instances ACME.
5. Aucun changement de comportement pour les instances en ACME (rendu octet pour octet identique à `origin/main`, test du rendu existant).

## Hors scope

- Le VPN et le DNS interne : hors Polenta, à la charge du client.
- Le renouvellement du certificat fourni : à la charge de l'exploitant (à documenter).
- Un magasin de certificats Windows complet (lecture de `ROOT` système) : non retenu, voir question 2.
- Le mode `external` : le certificat y relève du Caddy de l'exploitant, rien à générer.

## Questions à trancher avant le Design

1. **Où vit la CA côté poste ?** Recommandation : clé de config machine `caPath` (chemin d'un PEM déployé par la DSI avec `config.json`). Alternative : lire le magasin Windows `ROOT` (plus proche de la pratique DSI, mais plus complexe et non portable vers macOS/Linux). Confirmer `caPath` ?
2. **Magasin Windows ou PEM ?** Si la DSI veut le magasin système, faut-il le lire (via PowerShell ou une lib native) ? Recommandation : PEM seulement pour la V1, le magasin en évolution.
3. **Portée de la CA** : la CA est-elle ajoutée à la confiance de toutes les connexions de Polenta (y compris GitHub, si GitHub reste joignable) ou seulement aux hôtes de la forge déclarée ? Recommandation : confiance ajoutée à toutes les connexions (`ca` dans les agents = CA supplémentaire, les CA publiques restent acceptées par défaut — à vérifier dans undici). Confirmer, et vérifier que undici `ca` ajoute sans remplacer.
4. **Certificat fourni côté kit** : nouveau paramètre `instance add --tls-cert/--tls-key`, avec les fichiers copiés dans `instances/<nom>/tls/` (montage en lecture seule dans le Caddy), ou montage direct de l'hôte ? Recommandation : copie dans l'instance, droits 600, pour que `instance remove` les emporte.
5. **Renouvellement** : un certificat fourni expire ; faut-il une alerte (comme la clé S3 dans A9) ? Recommandation : oui, une ligne dans `status` et dans A9.
6. **Chaîne** : le PEM contient-il la chaîne intermédiaire ou la CA racine seule ? Recommandation : accepter les deux (le PEM peut contenir plusieurs certificats).
7. **Priorité avec GH52** : si les deux tickets sont retenus pour le même client, l'URL du flux de mise à jour (GH52) passe aussi par cette CA. À confirmer qu'on garde l'ordre GH52 puis GH53, ou l'inverse.
