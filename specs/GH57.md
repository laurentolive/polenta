# GH57 — Client web : pas d'écran de consentement de la forge à la première connexion

Issue : #57. Dépend de : #44 (client web, livré), #45 (kit `deploy/`, livré).

## 1. Contexte

À sa **première** connexion au client web, chaque utilisateur passe par la page de consentement
OAuth2 de Forgejo (`/login/oauth/authorize`) :

> Autoriser "polenta-web" à accéder à votre compte ? Si vous accordez l'accès, il sera en mesure
> d'accéder et d'écrire toutes les informations de votre compte, y compris les dépôts privés et les
> organisations. Cette application a été créée par @polenta-ops. With scopes: openid profile email.

Les connexions suivantes ne la montrent plus : la forge garde l'autorisation (« grant ») de
l'utilisateur pour l'application. Mais cette première fois inquiète, alors que l'application est
installée par l'entreprise sur sa propre forge.

Constats (Forgejo 15.0.9, instance `acme`, 2026-10-11) :
- pas d'option « application de confiance / sans consentement » : ni dans l'API
  (`CreateOAuth2ApplicationOptions` = `name`, `redirect_uris`, `confidential_client`), ni en base
  (table `oauth2_application` sans colonne `skip_secondary_authorization`, que Gitea a ajoutée
  pour ses seules applications intégrées) ;
- la forge accepte des **modèles de pages personnalisés** dans son dossier `custom`
  (`GITEA_CUSTOM=/data/gitea` → `templates/user/auth/grant.tmpl`), qui remplacent les modèles
  intégrés ;
- pas d'en-tête Content-Security-Policy sur la forge (la forge utilise elle-même des scripts en
  ligne) ;
- le texte affiché est exact : le jeton donne accès en écriture aux dépôts (nécessaire pour
  publier). On ne réduit pas les droits, on supprime une confirmation inutile pour une
  application maison.

## 2. Comportement attendu

### 2.1 Connexion

| Cas | Attendu |
|---|---|
| Premier accès d'un utilisateur au client web (pas encore d'autorisation) | Après la page de connexion de la forge (identifiant, mot de passe, 2FA éventuelle, changement de mot de passe imposé), **aucune page de consentement** : une page de transition « Connexion à Polenta… » au plus, validée automatiquement, puis retour dans Polenta. L'autorisation est enregistrée comme si l'utilisateur avait cliqué « Autoriser » (visible et révocable dans les paramètres du compte → Applications). |
| Utilisateur ayant déjà autorisé | Inchangé : la forge ne montre aucune page. |
| Navigateur sans JavaScript | La page de transition affiche un seul bouton « Continuer vers Polenta » (aucun texte d'avertissement). |
| Autorisation révoquée par l'utilisateur dans ses paramètres | Prochaine connexion : comme un premier accès (validée automatiquement). |
| **Toute autre application OAuth2** de la forge — y compris une application créée par un utilisateur et nommée « polenta-web » | Page de consentement **d'origine**, inchangée. L'application du client web est reconnue par son `client_id` (identifiant aléatoire attribué par la forge, conservé dans `instance.env`), jamais par son nom. |
| Requête d'autorisation invalide (redirection non enregistrée, application inconnue…) | Inchangé : la forge affiche son erreur avant d'arriver à cette page. |

### 2.2 Exploitation (kit `deploy/`)

| Commande | Attendu |
|---|---|
| `instance web enable <nom>` | Installe (ou met à jour) la page personnalisée pour l'application `polenta-web` de l'instance. Redémarre la forge **seulement si** la page a changé (quelques secondes), après l'avoir signalé. Rejouable sans effet. |
| `instance web enable` qui recrée l'application OAuth2 (nouveau `client_id`) | Page régénérée avec le nouveau `client_id`. |
| `instance web disable <nom>` | Retire la page personnalisée (page d'origine rétablie), redémarrage de la forge. |
| `instance update <nom> <version>` d'une instance avec client web | La page est régénérée pour la **nouvelle** version de la forge. Si la page de consentement de cette version n'a plus la forme attendue (formulaire et champs utilisés pour la validation automatique), la page personnalisée est **retirée** (page d'origine) et un avertissement l'indique — la mise à jour n'échoue pas pour autant. |
| `instance restore` / `backup` / `export` | La page personnalisée est dans les données de la forge (sauvegardée avec elles) ; une restauration avec client web la régénère (comme pour `web.env`). |
| Instance sans client web | Aucune page personnalisée. |

La page personnalisée reprend la page d'origine **de la version installée** pour tout ce qui n'est
pas l'application du client web : une mise à jour de la forge ne fige pas une ancienne version de la
page pour les autres applications.

### 2.3 Forges compatibles

Forgejo (cible). Le kit accepte aussi Gitea (instance de compatibilité `gitea-test`) : même
mécanisme si sa page de consentement a la forme attendue, sinon page d'origine + avertissement
(règle du §2.2, mise à jour).

## 3. Critères d'acceptation

1. Un compte neuf (`polenta-admin user add`) se connecte au client web de `acme` : aucune page
   contenant « Autoriser l'application » / « Authorize Application » n'est affichée ; il arrive dans
   Polenta ; l'autorisation `polenta-web` figure dans ses paramètres (Applications). Test e2e contre
   l'instance déployée.
2. Une seconde application OAuth2 nommée « polenta-web », créée par un utilisateur ordinaire,
   présente la page de consentement d'origine (test e2e).
3. `instance web enable` rejoué sans changement : pas de redémarrage de la forge.
4. `instance web disable` : la page d'origine revient pour `polenta-web`.
5. Mise à jour de la forge vers une version dont la page n'a pas la forme attendue (simulée) :
   page personnalisée retirée, avertissement, mise à jour réussie.
6. Les tests e2e S3/S4 du client web (#44) restent verts ; la recette `completeForgeLogin` gère les
   deux cas (avec et sans page de consentement).
7. RUNBOOK (A15) et `SPEC-WEB.md` décrivent le mécanisme et la vérification après mise à jour.

## 4. Hors scope

- Desktop : sa connexion par mot de passe (#45) ne passe pas par OAuth2 ; une future connexion
  SSO du desktop (#51) réutilisera le mécanisme si besoin.
- Reformuler la page de consentement des autres applications.
- Réduire les droits du jeton (le client web a besoin d'écrire dans les dépôts).
- Personnaliser d'autres pages de la forge (connexion, accueil).

## 5. Décisions

- **Validation automatique par une page personnalisée de la forge** plutôt que : une option de la
  forge (inexistante) ; l'écriture directe d'autorisations en base pour chaque compte (contourne
  la forge, dépend de son schéma interne, à refaire à chaque nouvel utilisateur) ; une connexion
  automatique « au nom de » l'utilisateur à sa création (mot de passe temporaire, changement
  imposé : fragile).
- **Reconnaissance par `client_id`** : l'unique identifiant que seul le kit attribue à son
  application ; un nom est à la portée de n'importe quel utilisateur.
- **En cas de doute, page d'origine** : une page personnalisée inadaptée à une nouvelle version de
  la forge pourrait casser toutes les connexions ; revenir à la page d'origine ne fait que rétablir
  la confirmation.
