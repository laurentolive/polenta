# GH61 — Kit de déploiement : Caddy et réseau Docker optionnels (hôte partagé)

Issue : #61 — `type:feature`. Suite de #45 (kit `deploy/`) et #44 (client web), tous deux livrés.
Hors scope de ce ticket : durcissement de l'hôte (issue 2), conteneur admin (issue 3).

## 1. Contexte

Le kit `deploy/` impose son propre Caddy : `polenta-host setup` démarre systématiquement un
conteneur `polenta-caddy` (ports 80, 443, 443/udp), ouvre ces ports dans ufw et le rattache à un
réseau `polenta-edge` codé en dur. Sur un serveur qui héberge déjà d'autres projets dockerisés
derrière leur propre Caddy, le démarrage échoue (ports pris) ou concurrence l'existant.

Constats dans le code (main) :

- `deploy/lib/caddy.sh` : `caddy_up`, `caddy_add_site`, `caddy_add_web_site`, `caddy_remove_site`,
  `caddy_remove_web_site`, `caddy_reload`, `caddy_connect_network` ; blocs de site rendus par
  `caddy_render_site` (`<instance>.caddy`, vers `forgejo-<nom>:3000`) et `caddy_render_web_site`
  (`<instance>.web.caddy`, vers `polenta-web-<nom>:8787`).
- **Isolation actuelle** : chaque instance a son réseau `polenta-<nom>` (compose
  `deploy/instance/docker-compose.yml`, réseau `default`) ; c'est Caddy qui est relié à chacun de ces
  réseaux, à chaud. Le réseau `polenta-edge` ne relie que Caddy à lui-même : aucune forge n'y est
  rattachée aujourd'hui. Une instance ne peut joindre aucune autre (RUNBOOK §A1).
- `polenta-host.sh` : `cmd_setup` appelle `setup_firewall` (22, 80/tcp, 443/tcp, 443/udp) puis
  `caddy_up` ; `wait_https` interroge `https://<domaine>` via `--resolve <domaine>:443:127.0.0.1` et
  affiche les journaux de `polenta-caddy` en cas d'échec ; `cmd_status` affiche l'état de Caddy ;
  `instance add / restore / update / start / remove / web enable / web disable` appellent les
  fonctions `caddy_*`.
- `deploy/tests/acceptance.sh` s'exécute depuis l'extérieur et vérifie notamment que 80 et 443
  sont ouverts et que les autres ports sont fermés.

## 2. Description fonctionnelle

Deux nouvelles clés optionnelles de `host.env`, plus deux de réglage du mode externe :

| Clé | Défaut | Rôle |
|---|---|---|
| `CADDY_MODE` | `managed` | `managed` : comportement actuel, strictement inchangé. `external` : le kit ne crée aucun Caddy et ne touche pas à 80/443. |
| `EDGE_NETWORK` | `polenta-edge` | Nom du réseau Docker « de bord » (voir §2.2 et §4). |
| `CADDY_SITES_DIR` | `/opt/polenta/caddy-sites` | (mode `external`) dossier où le kit écrit les blocs de site. Chemin absolu. |
| `CADDY_RELOAD_CMD` | *(vide)* | (mode `external`) commande shell exécutée en root après chaque modification des blocs de site pour que le Caddy existant les recharge, ex. `docker exec caddy caddy reload --config /etc/caddy/Caddyfile`. Vide : le kit n'invoque rien et affiche un rappel de rechargement manuel. |

Valeurs invalides (`CADDY_MODE` hors `managed|external`, `EDGE_NETWORK` ne respectant pas
`[a-zA-Z0-9][a-zA-Z0-9_.-]*`, `CADDY_SITES_DIR` relatif) : refus explicite, avant toute action, par
`load_host_env` (message en français, exit non nul).

### 2.1 Mode `managed` (défaut)

Aucun changement observable : mêmes fichiers générés, mêmes ports, même réseau `polenta-edge`,
même `acceptance.sh`. Seule différence autorisée : le nom du réseau de bord vient de `EDGE_NETWORK`
(défaut `polenta-edge`, donc identique). Un `host.env` sans les nouvelles clés se comporte comme avant.

### 2.2 Mode `external`

1. **setup** : n'appelle pas `caddy_up`, n'écrit ni `caddy/docker-compose.yml` ni `Caddyfile`, ne
   crée aucun conteneur Caddy ; `setup_firewall` n'ouvre que `22/tcp` (message « pare-feu : seul 22
   ouvert (Caddy externe : 80/443 non gérés) ») et **ne supprime jamais** une règle existante. Si
   ufw est déjà actif avec 80/443 ouverts par un autre projet, ils restent tels quels.
   Le réseau `EDGE_NETWORK` doit exister ; `setup` le vérifie et échoue avec un message explicite
   (commande `docker network create` proposée) s'il est absent. `setup` crée le dossier
   `CADDY_SITES_DIR` (root, 755) et affiche la ligne à ajouter au Caddyfile existant :
   `import /opt/polenta/caddy-sites/*.caddy`.
2. **Rattachement réseau** : les services `forgejo` et `polenta-web` de
   `deploy/instance/docker-compose.yml` rejoignent aussi `EDGE_NETWORK` (réseau déclaré
   `external: true`), en plus du réseau `polenta-<nom>`. Le kit ne relie **pas** le Caddy existant
   aux réseaux d'instance (`caddy_connect_network` inactif en `external`) : ce Caddy doit déjà être
   sur `EDGE_NETWORK`.
3. **Blocs de site** : `caddy_add_site` / `caddy_add_web_site` écrivent
   `$CADDY_SITES_DIR/<instance>.caddy` et `<instance>.web.caddy`, avec **le même contenu** qu'en mode
   `managed` (mêmes en-têtes, `request_body max_size`, `reverse_proxy forgejo-<nom>:3000` /
   `polenta-web-<nom>:8787`). Écriture via `write_if_changed`. Pas de `caddy_reload` du conteneur
   `polenta-caddy` ; si `CADDY_RELOAD_CMD` est défini il est exécuté après toute écriture ou
   suppression effective. Échec de la commande : le fichier de site écrit est retiré (comme le fait
   aujourd'hui le mode managed sur rechargement refusé, pour ne pas empoisonner les rechargements
   suivants), `die` avec la sortie de la commande. `CADDY_RELOAD_CMD` vide : avertissement unique par
   commande « blocs de site mis à jour dans … : rechargez votre Caddy ».
4. **Suppression** (`instance remove`, `instance web disable`) : supprime le bloc concerné, exécute
   `CADDY_RELOAD_CMD` s'il existe ; pas de `docker network disconnect` sur Caddy. Les fichiers
   d'autres projets dans `CADDY_SITES_DIR` (convention `_*.caddy`, comme RUNBOOK §A10) ne sont
   jamais lus, modifiés ni supprimés.
5. **Attente HTTPS** : `wait_https` n'a plus de sens (TLS, 80/443 et DNS appartiennent au Caddy
   existant, qui peut aussi être derrière un autre proxy). En `external`, il est remplacé par
   `wait_edge_http` : requête `GET /api/healthz` (forge) ou `/healthz` (web) depuis un conteneur
   éphémère rattaché à `EDGE_NETWORK` (`docker run --rm --network $EDGE_NETWORK` d'une image déjà
   présente, ex. celle de la forge, `wget` interne), vers `forgejo-<nom>:3000` /
   `polenta-web-<nom>:8787`. Succès = le routage réseau est prouvé. Le message final indique que
   `https://<domaine>` n'est **pas vérifié** (« le certificat dépend de votre Caddy »). Échec : `die`
   avec le diagnostic réseau (conteneur non joignable sur `EDGE_NETWORK`).
6. **Commandes concernées** (même traitement partout où `caddy_add_site` / `caddy_remove_site` /
   `wait_https` sont appelés) : `instance add`, `restore`, `update` (contrôle de santé après mise à
   jour), `start`, `remove`, `web enable`, `web disable`. `instance stop` ne touche pas au bloc de
   site (comportement actuel : le bloc reste, le reverse_proxy répond 502 tant que l'instance est
   arrêtée).
7. **status** : ligne « Caddy : externe (blocs dans <dossier>, réseau <EDGE_NETWORK>) » ; présence
   du réseau vérifiée (« réseau absent » en rouge sinon). Plus d'état de conteneur Caddy.
8. **Conséquence sur l'isolation** : en mode `external`, les forges (et clients web) de plusieurs
   instances partagent `EDGE_NETWORK` ; elles pourraient donc se joindre entre elles et joindre les
   conteneurs des autres projets du même réseau. Mitigations : (a) aucun port publié, comme
   aujourd'hui ; (b) noms de conteneur uniques `forgejo-<nom>` / `polenta-web-<nom>` (déjà garantis par
   `container_name`) ; (c) la limite est documentée au RUNBOOK avec la recommandation d'un réseau
   d'accès dédié à Polenta (`EDGE_NETWORK=polenta-edge`, auquel le Caddy existant se rattache) plutôt
   que du réseau commun des autres projets.

### 2.3 Cas limites et choix par défaut

| Cas | Comportement retenu |
|---|---|
| `EDGE_NETWORK` absent à `setup` / `instance add` | Échec clair, rien créé ; le kit **ne crée pas** le réseau en `external` (il appartient à l'exploitant). En `managed`, il reste créé par le compose Caddy. |
| `EDGE_NETWORK` supprimé après coup | `docker compose up` d'une instance échoue : message ré-écrit (« réseau … absent ») ; `status` le signale. |
| `CADDY_SITES_DIR` absent ou non inscriptible | Créé par `setup` ; si création impossible, `die`. Le Caddy existant doit pouvoir le lire (monté en lecture seule dans son conteneur) : documenté. |
| Caddy existant sans accès à `CADDY_SITES_DIR` | Détectable seulement par l'exploitant (site non servi ou rechargement en erreur). Documenté dans le dépannage RUNBOOK. |
| Domaine déjà déclaré dans le Caddy existant | Erreur « ambiguous site definition » au rechargement, donc rollback du bloc (cf. 2.2-3). |
| **Migration d'un hôte `managed` existant vers `external`** | Non automatique. Procédure RUNBOOK : retirer `polenta-caddy`, déplacer les `*.caddy` générés vers `CADDY_SITES_DIR`, passer `CADDY_MODE=external`, relancer `setup`, puis `instance sync` sur chaque instance (réécriture des blocs et rattachement à `EDGE_NETWORK`). Le kit **refuse** de basculer à chaud : si `CADDY_MODE=external` alors qu'un conteneur `polenta-caddy` tourne, `setup` s'arrête avec l'instruction de le retirer d'abord (évite deux Caddy sur 80/443). |
| Retour `external` vers `managed` | Idem, procédure RUNBOOK ; `setup` refuse si 80/443 sont occupés par un autre processus que `polenta-caddy`. |
| Instances créées avant la fonctionnalité | Leurs conteneurs ne sont pas sur `EDGE_NETWORK` : `instance sync` (et `instance update`) recréent les conteneurs avec le nouveau compose. |
| `restore` d'une sauvegarde d'un hôte du mode opposé | Neutre : les sauvegardes ne contiennent ni blocs de site ni réseau ; le mode de l'hôte cible s'applique. |
| `ACME_EMAIL` / `CADDY_VERSION` en `external` | Ignorés (non bloquant). |
| fail2ban forge (`setup_fail2ban_forge`, chaîne `DOCKER-USER`) | Inchangé. Remarque RUNBOOK : l'IP vue par la forge est celle transmise par le Caddy existant (`X-Forwarded-For`, comportement par défaut de `reverse_proxy`). |
| `acceptance.sh` en `external` | Option `--external` : n'exige plus 80/443 ouverts ; vérifie toujours que `2222`, `3000`, `5355`, `8080`, `2375` sont fermés. Sans option : inchangé. |

## 4. Réseau : synthèse

| | `managed` | `external` |
|---|---|---|
| Réseau d'instance `polenta-<nom>` | oui | oui |
| `EDGE_NETWORK` | relie Caddy à lui-même (compose Caddy) ; nom configurable | partagé par forge/web de chaque instance **et** par le Caddy existant (`external: true`) |
| Rattachement du proxy aux instances | `docker network connect` à chaud sur chaque `polenta-<nom>` | aucun : le proxy est déjà sur `EDGE_NETWORK` |

## 5. Critères d'acceptation

Mesurables, vérifiés sur un hôte de test (VM Debian 13 / Ubuntu 24.04) :

1. **Défauts inchangés** : avec un `host.env` sans nouvelle clé, `diff` du `docker-compose.yml`, du
   `Caddyfile` et des `sites/*.caddy` générés avant/après la contribution est vide ; `polenta-caddy`
   publie 80/443 ; `deploy/tests/acceptance.sh <domaine>` passe comme avant.
2. **Aucun conteneur Caddy en `external`** : après `setup` + `instance add` + `web enable`,
   `docker ps -a --filter name=polenta-caddy -q` est vide et `/opt/polenta/caddy/` n'existe pas.
3. **80/443 non touchés** : `ufw status numbered` avant/après `setup` en `external` identique pour
   les règles 80/443 (présentes ou absentes) ; un listener tiers sur 80 et 443 reste fonctionnel
   pendant et après `setup`.
4. **Blocs de site** : `CADDY_SITES_DIR/<nom>.caddy` et `<nom>.web.caddy` existent après
   `instance add` / `web enable`, contenu identique octet pour octet à celui produit en `managed` pour
   les mêmes entrées ; ils disparaissent à `web disable` / `remove` ; un fichier `_vitrine.caddy`
   pré-existant dans le dossier a une empreinte inchangée.
5. **Routage** : un Caddy tiers (conteneur d'essai sur `EDGE_NETWORK`, important les blocs, `tls
   internal` pour le test) sert `https://<domaine>/api/healthz` en HTTP 200 via
   `reverse_proxy forgejo-<nom>:3000`.
6. **Réseau** : `docker inspect forgejo-<nom>` liste `polenta-<nom>` et `EDGE_NETWORK` ; aucun
   `docker network connect` vers un Caddy n'est émis.
7. **Réseau absent** : `EDGE_NETWORK` inexistant : `setup` et `instance add` sortent non nuls avec un
   message citant le réseau et la commande `docker network create`, sans instance créée.
8. **Rechargement** : `CADDY_RELOAD_CMD=false` : `instance add` échoue, bloc retiré ; commande vide :
   avertissement affiché, bloc conservé ; commande valide : exécutée exactement une fois par
   modification effective (idempotence : seconde exécution = « déjà à jour », zéro rechargement).
9. **Validation de configuration** : `CADDY_MODE=foo`, `EDGE_NETWORK='a b'` et `CADDY_SITES_DIR=relatif`
   sont refusés avec message clair, avant toute modification de l'hôte.
10. **Garde-fou de bascule** : `CADDY_MODE=external` avec `polenta-caddy` en marche : `setup` refuse,
    rien modifié.
11. **Cycle de vie** : `restore`, `update`, `start`, `stop`, `status` fonctionnent en `external`
    (`status` affiche la ligne Caddy externe, jamais « arrêté »).
12. **Scénario d'acceptation** : `deploy/tests/acceptance-external.sh` (sur l'hôte, instance de test
    créée puis supprimée) enchaîne les points 2 à 6 et renvoie un code non nul au premier écart ;
    `acceptance.sh --external` passe depuis l'extérieur.
13. **Qualité** : `shellcheck` sans nouvel avertissement sur `deploy/` ; `deploy/tests/grant-template.test.sh`
    toujours vert.
14. **RUNBOOK** : nouvelle section « Cohabitation avec d'autres projets dockerisés sur un même
    serveur » contenant : prérequis (Caddy existant sur `EDGE_NETWORK`, montage de `CADDY_SITES_DIR`),
    exemple de `host.env`, ligne `import`, exemple de `CADDY_RELOAD_CMD`, limites d'isolation (§2.2-8),
    procédures de migration dans les deux sens, dépannage ; mise à jour de A1 (arborescence), A2
    (préparation), A10 (sites additionnels en `external`) et A12 (reprise : republier aussi
    `CADDY_SITES_DIR`).

## 6. Hors scope

- Durcissement de l'hôte (issue 2) et conteneur admin (issue 3).
- Gestion, installation, configuration ou mise à jour du Caddy existant ; génération de son Caddyfile.
- Autres reverse proxies (nginx, Traefik) ; Caddy installé hors Docker (les blocs écrits restent
  utilisables, mais aucune joignabilité réseau n'est organisée).
- Création ou suppression automatique de `EDGE_NETWORK` en `external`.
- Migration automatique `managed` / `external`.
- Cloisonnement renforcé entre instances en `external` (réseau par instance + proxy rattaché
  dynamiquement) : évolution possible, non traitée ici.
- Sauvegarde des fichiers de site ou de la configuration du Caddy existant.

## Questions ouvertes

1. **Isolation en `external`** : accepte-t-on que les forges de plusieurs clients partagent
   `EDGE_NETWORK` (défaut retenu, §2.2-8) ? Alternative : un réseau par instance auquel l'exploitant
   rattache son Caddy (lourd), ou une commande qui le fait.
2. **`CADDY_SITES_DIR` par défaut** (`/opt/polenta/caddy-sites`) : convient-il, ou réutiliser
   `/opt/polenta/caddy/etc/sites` pour limiter les changements ?
3. **Rechargement** : `CADDY_RELOAD_CMD` générique (retenu) suffit-il, ou ajouter un
   `EXTERNAL_CADDY_CONTAINER` pour un rechargement `docker exec` automatique ?
4. **Vérification HTTPS en `external`** : sonde réseau interne seule (retenu) ou aussi une sonde
   `https://` optionnelle ?
5. **Caddy existant hors Docker** : à supporter plus tard (ports publiés en loopback) ?
6. **Scénario d'acceptation** : option `--external` d'`acceptance.sh` plus script
   `acceptance-external.sh` (retenu), ou un seul fichier ?
7. **ufw en `external`** : ouvrir tout de même 80/443 si ufw est inactif sur un hôte neuf ? Retenu :
   non, jamais.
