# GH64 — Ajouter des tests depuis une autre campagne selon le statut de leurs entrées (report)

Issue : #64

## 1. Besoin

Une campagne n'est pas toujours exécutée en entier (manque de temps, point bloquant, matériel
indisponible…). Le responsable de la campagne suivante doit pouvoir **lister les entrées d'une ou
plusieurs campagnes précédentes selon leur statut** et **les reprendre facilement** dans sa
campagne. Le report reste à sa discrétion : rien n'est automatique, rien n'est imposé.

La baseline des campagnes source et cible est indifférente.

## 2. Points d'entrée

Le sélecteur de tests de GH33 (`TestPickerModal`) est utilisé à deux endroits ; le report est
proposé **dans les deux** :

- **Création** (`/campaign/new`, « Sélectionner des tests… ») — cas typique « nouvelle campagne
  à partir des restes de la précédente » ;
- **Ajout** (« + Ajouter des tests » d'une campagne non clôturée).

L'étape 1 de la modale (sélection) propose deux **sources**, en onglets :

| Onglet | Contenu |
|--------|---------|
| **Tests** | Vue Excel du type de test choisi — comportement GH33 inchangé |
| **Depuis une campagne** | Nouvelle source décrite au §3 |

La sélection faite dans les deux onglets est **cumulée** (union, avec la déduplication du §4.4).
Le compteur de la modale compte le total. L'étape 2 (paramètres / exigences) est commune et
inchangée dans son principe (§4.3).

## 3. Onglet « Depuis une campagne »

### 3.1 Choix des campagnes source

- Liste de **toutes les campagnes du repo**, quel que soit leur statut (`planned`,
  `in_progress`, `completed`, `abandoned`), **sauf la campagne cible** (à l'ajout).
- Pour chacune : ID, titre, statut de campagne, baseline, composant/niveau, date de création, et
  un résumé des statuts de ses entrées (même pastilles que la liste des campagnes).
- Tri : plus récente d'abord (date de création décroissante).
- Sélection **multiple** (cases à cocher). Aucune campagne cochée par défaut.

### 3.2 Filtre par statut d'entrée

Cases à cocher, combinables :

| Statut | Coché par défaut |
|--------|------------------|
| `pending` (non exécuté) | oui |
| `BLOCKED` | oui |
| `INCOMPLETE` | oui |
| `FAIL` | non |
| `PASS` | non |

### 3.3 Liste des entrées

Une ligne par entrée (`CampaignTestRun`) des campagnes cochées dont le statut passe le filtre :

| Colonne | Contenu |
|---------|---------|
| Case à cocher | sélection de l'entrée |
| Test | ID + titre (titre de l'état actuel du test) |
| Exigence | `requirementId` de l'instance (T179), vide sinon |
| Paramètres | valeurs saisies à la main (`paramValues`) de l'entrée source, en résumé |
| Statut | statut de l'entrée source |
| Exécution | `executedAt` / `executedBy` de l'entrée source, vides si `pending` |
| Campagne source | ID de la campagne |
| Remarque | motif d'indisponibilité ou avertissement (§4.1, §4.2, §4.4) |

- Les entrées **disponibles** sont **cochées par défaut** quand elles apparaissent ; le
  responsable décoche ce qu'il ne veut pas. Changer les campagnes cochées ou le filtre de statut
  ajoute/retire des lignes mais **conserve les choix** (cochée/décochée) des lignes déjà vues.
- Case d'en-tête « tout cocher / tout décocher » (sur les lignes disponibles).
- Filtre texte global sur la liste (ID/titre de test, exigence).
- Liste vide : message « Aucune entrée ne correspond » (aucune campagne cochée, ou filtre trop
  restrictif).

## 4. Règles

### 4.1 Disponibilité d'une entrée

Une entrée est **listée mais non sélectionnable** (grisée, motif en colonne Remarque) quand :

| Cas | Motif affiché |
|-----|---------------|
| Le test n'existe plus | « Test supprimé » |
| À l'ajout : le test n'est pas approuvé (état actuel) — **même règle que l'onglet Tests** | « Non approuvé » |
| À la création : le test est hors du filtre composant/niveau du formulaire — **même règle que l'onglet Tests** | « Hors périmètre » |
| Instance d'exigence (T179) dont l'exigence n'est plus liée au test (lue au `baselineRef` de la cible s'il existe, sinon état courant) | « Exigence plus liée » |
| Doublon (§4.4) | « Déjà présent » |

Autrement dit, le report ne contourne aucune règle d'éligibilité de l'ajout normal.

### 4.2 Contenu de l'instance créée

Chaque entrée source reportée devient **une instance** dans la campagne cible :

- **Copie figée (T49)** : nouvelle copie du test **dans son état actuel** (`testSnapshot`), jamais
  celle de l'entrée source. Si la `version` du test diffère de celle de la copie de l'entrée
  source, la colonne Remarque l'indique (« Test modifié depuis : v2 → v3 ») — simple
  avertissement, l'entrée reste sélectionnable.
- **Paramètres de la base (T171)** : relus selon le `baselineRef` de la campagne **cible** (ou
  état courant), exactement comme un ajout normal ; jamais recopiés de l'entrée source.
- **Paramètres saisis à la main (`paramValues`)** : **pré-remplis** à l'étape 2 avec les valeurs
  de l'entrée source, modifiables. Une clé de la source qui n'est plus une référence à saisir du
  test (supprimée du test, ou désormais résolue par la base) est ignorée ; une nouvelle référence
  à saisir est demandée vide. Règle de complétude inchangée.
- **Exigence (T179)** : le `requirementId` de l'entrée source est conservé. Si le test n'est plus
  itérant (plus de `{req.…}`), l'instance est créée sans exigence. Une entrée source **sans**
  `requirementId` d'un test devenu itérant passe par le `ReqInstancePicker` de l'étape 2 comme un
  ajout normal.
- **Statut** : `pending`, sans `runId`, `executedAt`, `executedBy` (nouvelle exécution).
- **Traçabilité** : nouveau champ optionnel `carriedFrom: { campaignId, entryId }` sur
  l'instance créée.

### 4.3 Étape 2 (paramètres / exigences)

Inchangée, avec deux précisions :

- une entrée reportée d'un test à paramètres saisis apparaît comme **une instance distincte**
  (avec ses valeurs pré-remplies) — plusieurs entrées reportées du même test donnent plusieurs
  instances, contrairement à l'onglet Tests (une instance par test) ;
- une entrée reportée avec `requirementId` est **figée sur son exigence** : pas de
  `ReqInstancePicker` pour elle.

L'étape 2 n'est montrée que si au moins une instance sélectionnée a des références à saisir ou
des exigences à choisir (règle GH33).

### 4.4 Doublons

Clé d'une instance : `(testCaseId, requirementId, paramValues saisis)`.

- **Contre la campagne cible** (à l'ajout) : une entrée dont la clé correspond à une instance déjà
  présente est grisée « Déjà présent ».
- **Entre sources** : si plusieurs entrées sélectionnées ont la même clé (même test en échec dans
  CAMP-0003 puis non exécuté dans CAMP-0004…), **une seule ligne** est proposée — celle de
  l'entrée la plus récente (`executedAt`, à défaut date de création de sa campagne) ; les autres
  campagnes source sont mentionnées dans la Remarque.
- **Entre onglets** : un test coché dans l'onglet Tests et présent par une entrée reportée avec la
  même clé ne crée qu'une instance ; l'entrée reportée l'emporte (elle porte `carriedFrom`).

La comparaison des `paramValues` se fait sur les valeurs de la source (avant édition à l'étape 2).

### 4.5 Campagne source

**Jamais modifiée** : pas de statut « reporté », pas de lien retour. Une entrée `pending` dans une
campagne clôturée suffit à signifier « non exécuté ».

### 4.6 Affichage dans la campagne cible

Dans la liste des tests de la campagne, une instance portant `carriedFrom` affiche une mention
discrète « ↩ CAMP-0003 » (lien vers la campagne source). Rien de plus : les exports de campagne
(plan, rapport, classeur d'exécution, gabarits) ne sont pas modifiés.

## 5. Critères d'acceptation

1. À l'ajout comme à la création, l'étape 1 du sélecteur propose les onglets « Tests » et
   « Depuis une campagne » ; l'onglet Tests se comporte exactement comme avant.
2. L'onglet « Depuis une campagne » liste toutes les campagnes du repo sauf la cible, y compris
   clôturées et abandonnées.
3. Avec une campagne cochée et le filtre par défaut, la liste montre exactement ses entrées
   `pending`, `BLOCKED` et `INCOMPLETE`, toutes cochées sauf celles indisponibles (§4.1).
4. Cocher `FAIL` / `PASS` ajoute les entrées correspondantes ; les choix déjà faits sont conservés.
5. Une entrée d'un test supprimé, non approuvé (ajout), hors périmètre (création), dont l'exigence
   n'est plus liée, ou déjà présente dans la cible est grisée avec son motif et non sélectionnable.
6. Valider crée une instance `pending` par entrée retenue, avec : copie du test dans son état
   actuel, paramètres de base relus selon la baseline de la cible, `paramValues` issus de l'étape 2
   (pré-remplis depuis la source), `requirementId` conservé, `carriedFrom` renseigné.
7. Deux entrées sources d'un même test à paramètres saisis, avec des valeurs différentes, donnent
   deux instances dans la cible.
8. Une même clé présente dans deux campagnes source n'est proposée qu'une fois (la plus récente).
9. Le fichier de la campagne source est inchangé après le report.
10. La liste des tests de la campagne cible affiche « ↩ <CAMP-ID> » sur les instances reportées.
11. Une campagne cible `completed`/`abandoned` refuse l'ajout (garde existante de `addTests`).
12. Les campagnes existantes (sans `carriedFrom`) se lisent et s'affichent sans changement.

## 6. Hors périmètre

- Sélection / ajout depuis la vue Suivi (Requêtes), table `campaign_entries` — voir #65.
- Vue calculée « reste à tester » transverse aux campagnes ; validité d'un PASS entre baselines.
- Statut « reporté » ou motif de report sur la campagne source.
- Report automatique à la clôture d'une campagne.
- Campagnes d'autres repos (composants) comme source.
- Mention de `carriedFrom` dans les exports.
