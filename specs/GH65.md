# GH65 — Suivi : avancement des campagnes de test en temps réel, avec navigation vers les résultats

Issue : #65 — type `feature`.

## Description fonctionnelle

La vue **Suivi** (dashboards) doit permettre de suivre l'avancement des campagnes de test et, en cas
de problème, de descendre jusqu'au détail : campagne, puis résultat d'exécution d'une entrée.

Quatre volets :

1. **Données de campagne dans le moteur de requêtes** — nouvelle table `campaign_entries`,
   interrogeable en mode builder et en SQL avancé.
2. **Navigation depuis les widgets** (générique : vaut pour exigences, tests et entrées de campagne)
   — clic sur une barre / une part / un point / un indicateur → popup listant les lignes
   concernées ; clic sur une ligne (popup ou widget table) → ouverture de l'objet.
3. **Tableau de bord « Campagnes »** préconfiguré, livré à tout projet (nouveau ou existant).
4. **Temps réel côté consultation** — les résultats publiés par les autres arrivent par le pull
   automatique ; le tableau de bord se rafraîchit seul, quel que soit le repo modifié. Intervalle de
   pull réglable par projet.

**Décision de cadrage** (commentaire de l'issue) : pas de publication automatique des résultats. Le
testeur publie à la main (« Publier ») ; tant qu'il ne l'a pas fait, ses résultats ne sont pas visibles
des autres. Le risque de conflits entre testeurs sur un même `campaigns/<id>.yaml` est hors périmètre.

## Comportements attendus

### 1. Table `campaign_entries`

Une ligne **par entrée de campagne** (`CampaignTestRun`) de toutes les campagnes du périmètre
(repo courant + composants du workspace, même agrégation que `requirements`/`tests`).

| Colonne | Source | Remarque |
|---|---|---|
| `campaignId`, `campaignTitle`, `campaignStatus` | `TestCampaign.id/title/status` | |
| `campaignObjectTypeRef` | `TestCampaign.objectTypeRef` | vide si absent |
| `baselineRef`, `level` | `TestCampaign` | vides si absents |
| `campaignComponent` | `TestCampaign.component` | composant ciblé par la campagne |
| `component` | repo / composant local où vit le fichier campagne | même règle que les autres tables |
| `entryId`, `testCaseId`, `requirementId` | `CampaignTestRun` | `requirementId` vide hors T179 |
| `testTitle` | `testSnapshot.title`, à défaut test live | |
| `status` | `CampaignTestRun.status` | `pending` / `PASS` / `FAIL` / `BLOCKED` / `INCOMPLETE` |
| `executed` | booléen `status !== 'pending'` | facilite « % exécuté » |
| `executedAt`, `executedDay`, `executedBy`, `runId` | `CampaignTestRun` | vides si non exécutée ; `executedDay` = `AAAA-MM-JJ` (UTC) pour la courbe jour par jour |
| champs personnalisés de la campagne | `TestCampaign.fields{}` étalés | préfixés `campaign_` pour éviter les collisions avec les colonnes ci-dessus |

- Une seule ligne par entrée : son **dernier** état. L'historique des exécutions successives d'une
  même entrée n'est pas restitué (une ré-exécution déplace `executedAt`).
- Builder : un type de catégorie `campaign` du schéma devient sélectionnable comme source ; la
  requête porte alors sur `campaign_entries` filtrée par `campaignObjectTypeRef` (+ `component`
  comme pour les autres types). Une campagne sans `objectTypeRef` (anciennes campagnes) n'est
  visible qu'en SQL avancé. Allowlist builder = colonnes ci-dessus + champs du type de campagne.
- SQL avancé : `SELECT … FROM campaign_entries …`, mêmes garde-fous lecture seule.
- Tools MCP `run_query` / `create_query` : la nouvelle table est accessible comme les autres
  (aucun tool nouveau).

### 2. Navigation depuis les widgets

**Clic sur un élément agrégé** (barre ou segment de barre, part de camembert, point de courbe,
tuile KPI) → popup « Détail » :
- Titre : titre du widget + valeur(s) cliquée(s) (`catégorie`, `série` éventuelle).
- Contenu : les **lignes sources** qui composent cet élément, sous forme de table (mêmes composants
  que le widget table), avec compteur.
- Calcul des lignes sources :
  - **Requête builder** : on reprend le `builderConfig`, on retire le `groupBy`, on ajoute les
    conditions `catégorie = valeur` (et `série = valeur` si présente) ; KPI → toutes les lignes de
    la requête sans agrégation.
  - **Requête SQL** : si la requête est une sélection sur **une seule table**, sans jointure, union
    ni sous-requête, et que les colonnes catégorie/série sont des colonnes de la table (pas des
    expressions ou alias calculés), elle est réécrite : `SELECT *`, même `FROM`, même `WHERE`
    complété des conditions cliquées, sans `GROUP BY`/`HAVING`/`ORDER BY`/`LIMIT`. Sinon, repli :
    le popup affiche les lignes **du résultat** de la requête correspondant aux valeurs cliquées,
    avec la mention « Détail non disponible pour cette requête — lignes du résultat affichées ».
- La popup s'ouvre dans le dashboard (aucun changement de route) ; `Échap` / bouton fermer.

**Clic sur une ligne** (popup Détail ou widget table) → ouverture de l'objet dans un onglet, selon
les colonnes présentes dans la ligne :
1. `campaignId` + `entryId` présents :
   - entrée exécutée (`status ≠ pending`) → résultat d'exécution
     (`/campaign/$campaignId/run/$entryId`) ;
   - entrée `pending` → page de la campagne, **filtrée sur le statut `pending`**.
2. Sinon `campaignId` seul → page de la campagne (filtrée sur `status` si la ligne en porte un).
3. Sinon `id` → objet correspondant (exigence, test ou campagne), retrouvé dans les index du
   périmètre ; introuvable → ligne non cliquable.
4. Aucune de ces colonnes → ligne non cliquable (pas de curseur main, pas de survol actif).

Les lignes cliquables ont un curseur main et un survol ; un clic simple suffit.

**Page de campagne — filtre par statut** : nouveau paramètre d'URL `status` (optionnel) et contrôle
de filtre visible sur la page ; les compteurs par statut existants deviennent cliquables (même
filtre). Sans paramètre : comportement actuel.

### 3. Tableau de bord « Campagnes » préconfiguré

- Créé **une fois par utilisateur** dans tout projet, nouveau ou existant, au premier accès à
  l'onglet Suivi après mise à jour, par un seed **indépendant** du seed « Status », marqueur dans le
  `.{user}.pref`. Supprimé par l'utilisateur → jamais recréé.
- **Privé** (décision sprint 1, après revue) : dashboard et requêtes dans le `.{user}.pref`, ignoré
  par git — **aucune écriture dans le repo**. Un seed partagé aurait été créé par chaque membre de
  l'équipe sur son propre clone (doublons, conflits add/add) et ses fichiers non publiés auraient
  rendu le repo « sale », bloquant le pull automatique. L'utilisateur peut ensuite le **partager**
  (passage en partagé des requêtes puis du dashboard, mécanisme existant SPEC-DASHBOARDS §3.1).
- Garde-fous : reprise sans doublon après un échec partiel, appels concurrents dédupliqués, un échec
  du seed n'empêche jamais de lister les dashboards.
- Requêtes en SQL avancé (les campagnes sans `objectTypeRef` doivent être comptées), tous modifiables
  / supprimables comme n'importe quel dashboard :
  - **Avancement par campagne** — barre empilée, catégorie `campaignTitle`, série `status`,
    mesure `count` ; campagnes `planned` et `in_progress` uniquement.
  - **% exécuté** — KPI, sur les campagnes `in_progress`.
  - **% PASS** — KPI, PASS / exécutées, sur les campagnes `in_progress`.
  - **Exécutions par jour** — courbe, catégorie `executedDay`, mesure `count`, entrées exécutées.
  - **Entrées en échec** — table des entrées `FAIL` / `BLOCKED` des campagnes `in_progress`
    (`campaignId`, `campaignTitle`, `entryId`, `testCaseId`, `testTitle`, `status`, `executedAt`,
    `executedBy`) → clic = résultat d'exécution.
- Le libellé des titres (dashboard, requêtes, widgets) suit la langue de l'UI au moment du seed.

### 4. Temps réel côté consultation

- **Rafraîchissement des widgets** : tout résultat de widget (et la popup Détail ouverte) est
  invalidé quand un fichier `requirements/`, `tests/`, `links/` ou `campaigns/` change, ou quand une
  ref change (`'*'` : checkout, pull, fast-forward), **dans n'importe quel repo du workspace** — pas
  seulement le repo racine. Cela couvre : l'avance rapide faite par le pull automatique, une
  écriture locale (résultat saisi sur le poste), un pull dans un repo composant.
- **Intervalle de pull** : préférence projet `preferences.autoPullIntervalMinutes` dans
  `.polenta/schema.yaml` (repo racine), entier, **défaut 5**, **minimum 1**, maximum 60 ; une valeur
  absente ou invalide vaut le défaut. Réglable dans l'UI là où se règle `autoPropagatePin`. Prise en
  compte sans redémarrer (le minuteur est réarmé au changement). Le libellé « nouvel essai toutes les
  5 minutes » de l'indicateur hors ligne reprend la valeur effective.
- Pas de pull à l'ouverture du projet (inchangé).
- **Client web** : même comportement (chaque utilisateur a son propre espace de travail sur le
  serveur, le pull automatique y tourne déjà).

## Critères d'acceptation

1. `SELECT status, COUNT(*) AS n FROM campaign_entries GROUP BY status` renvoie le nombre d'entrées
   par statut, toutes campagnes du workspace confondues (repo racine + composants).
2. Une campagne de 10 entrées dont 4 exécutées (3 PASS, 1 FAIL) : `% exécuté` = 40 %, `% PASS` = 75 %.
3. En builder, un type de campagne du schéma est proposé comme source ; un `groupBy status` produit
   le même décompte que la requête SQL équivalente filtrée sur ce type.
4. Clic sur le segment `FAIL` d'une barre empilée « Avancement par campagne » (requête builder ou
   SQL simple) → popup listant exactement les entrées FAIL de cette campagne ; nombre de lignes =
   hauteur du segment.
5. Requête SQL avec jointure : clic sur une barre → popup avec les lignes du résultat filtrées et la
   mention de repli ; aucune erreur.
6. Clic sur une ligne d'entrée exécutée → résultat d'exécution de cette entrée ouvert dans un onglet ;
   entrée `pending` → page de campagne filtrée sur `pending`.
7. Clic sur une ligne de la table `requirements` (colonne `id`) → éditeur de l'exigence ; une ligne
   sans colonne exploitable n'est pas cliquable.
8. Projet existant déjà seedé (« Status ») : à la première ouverture de Suivi après mise à jour, le
   dashboard privé « Campagnes » apparaît, sans aucune modification du repo ; supprimé puis Suivi
   rouvert → il ne revient pas.
9. Dashboard ouvert sur le poste A ; le poste B saisit un résultat et publie ; au tick suivant du
   pull automatique de A (A sans modification en cours), les widgets de A se mettent à jour **sans
   action**. Idem si la campagne vit dans un repo composant.
10. Sur le poste A, saisir un résultat dans une campagne → le dashboard ouvert dans un autre onglet
    se met à jour sans action.
11. `autoPullIntervalMinutes: 1` → un pull par minute ; valeur `0`, négative ou non numérique →
    5 minutes ; changement de la valeur → nouvel intervalle appliqué sans redémarrage.
12. Les scénarios 1, 4, 6, 8, 10 sont couverts en e2e web (`e2e-web/gh65-*.spec.ts`).

## Hors scope

- Publication automatique des résultats côté testeur ; conflits entre testeurs sur un même
  `campaigns/<id>.yaml`.
- Historique des exécutions successives d'une entrée dans `campaign_entries` (seul le dernier état).
- Pull à l'ouverture du projet ; notification / popup à l'arrivée de nouveaux résultats.
- Drill-down en cascade (clic dans la popup Détail sur autre chose qu'une ligne).
- Report de tests d'une campagne à l'autre : #64.
- Nouveaux tools MCP (la table est seulement exposée via les tools de requête existants).
