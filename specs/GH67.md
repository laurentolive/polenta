# GH67 — Suivi : partager un dashboard privé avec ses requêtes en une seule action

> Issue : #67 (`type:feature`). Débloquée le 2026-11-04 (commentaire de l'humain sur l'issue :
> #74 clos le 2026-10-14, `SPEC-DASHBOARDS.md` §7.0b garde requêtes et widgets séparés → ticket
> non absorbé, à spécifier sur le modèle actuel).
> Les points marqués **[Q n]** dépendent d'une question ouverte (§9) ; la spec est rédigée sur la
> recommandation.

## 1. Contexte et constat

Règle actuelle (`SPEC-DASHBOARDS.md` §7.0b, l'issue cite l'ancienne numérotation « §3.1 ») : un
widget ne peut être partagé que si sa requête l'est. Cliquer **Partagé** sur un dashboard privé
dont un widget utilise une requête privée échoue avec le message du service
(`DashboardsService.assertWidgetsShareable`) : « Impossible de partager ce dashboard : N widget(s)
référencent une requête privée — … Partagez d'abord ces requêtes. »

Constat fait à l'exploration du code (à vérifier par l'humain, il élargit le besoin de l'issue) :
**l'application n'a aucune action UI pour changer la portée d'une requête**. Le service
`SavedQueriesService.setScope` et le canal `queries:set-scope` existent, mais aucun écran ne les
appelle, et le MCP ne le permet pas (`SPEC-DASHBOARDS.md` §10). Ce constat est déjà noté dans
`specs/GH70-sprint1.md` (§ Divergences, 2026-10-19) : « l'application n'a aucune action UI pour
changer la portée d'une requête (seul le service l'expose ; le MCP ne le permet pas) ».
Conséquence : le conseil « Partagez d'abord ces requêtes » n'est pas réalisable tel quel ; le
seul chemin aujourd'hui est « Enregistrer sous… » en *Partagée* (copie, sans remappage), puis
reconfigurer chaque widget du dashboard sur la copie, puis supprimer les privées. Pour le
dashboard « Campagnes » seedé en privé par #65 : 6 requêtes (la spec #65 en annonçait 5 ;
« Avancement dans le temps » ajouté par GH112), 6 widgets à reconfigurer.

Mécanisme réutilisable : la promotion d'une requête (`SavedQueriesService.setScope(… 'shared')`)
écrit la copie partagée (nouvel id `QUERY-NNNN`) **avant** de retirer la privée, puis remappe les
widgets des dashboards privés de l'utilisateur (`DashboardsService.remapWidgetQueryId`) et l'ordre
du panneau latéral.

## 2. Description fonctionnelle

Lors du passage **privé → partagé** d'un dashboard, si des widgets utilisent des requêtes privées,
Polenta propose, dans une confirmation qui les liste, de **partager aussi ces requêtes** en une seule
action. Confirmer :

1. passe chacune de ces requêtes en partagé (mécanisme de promotion existant : nouvel id, copie
   partagée écrite avant le retrait de la privée, widgets des dashboards privés de l'utilisateur
   remappés — y compris ceux d'**autres** dashboards privés qui l'utilisent, ordre du panneau suivi) ;
2. puis passe le dashboard en partagé (mécanisme existant : nouvel id `DASHBOARD-NNNN`, ordre du
   panneau et valeurs de paramètres suivis).

Sans requête privée dans le dashboard, le passage en partagé reste immédiat, sans confirmation
(comportement actuel inchangé). Le passage partagé → privé d'un dashboard est inchangé.

Le comportement est le même dans l'application desktop et dans le client web (client web maintenu :
décision de l'humain du 2026-11-03, mémoire de l'agent « Web client maintained » et
`tasks/lessons.md`).

## 3. Comportements attendus par cas d'usage

### 3.1 Nominal — dashboard « Campagnes » privé (seed #65)

- L'utilisateur ouvre le dashboard privé « Campagnes » et clique **Partagé**.
- Une fenêtre de confirmation s'ouvre : « Partager le dashboard et ses requêtes privées ».
  Elle liste les requêtes privées utilisées (une ligne par requête, même si plusieurs widgets du
  dashboard l'utilisent), avec pour chacune :
  - son titre ;
  - les widgets de ce dashboard qui l'utilisent ;
  - le cas échéant, les **autres dashboards privés** de l'utilisateur qui l'utilisent (« Aussi
    utilisée par : … — ces widgets suivront la requête partagée ») ;
  - le cas échéant, un avertissement de **titre déjà pris** (§3.4).
- Un texte rappelle l'effet : les requêtes et le dashboard deviennent visibles de toute l'équipe et
  sont écrits dans le dépôt (modifications à publier) ; ils ne sont plus dans les éléments privés.
- Boutons : **Partager (N requêtes + le dashboard)** et **Annuler**.
- Confirmer → les N requêtes puis le dashboard passent en partagé ; l'URL suit le nouvel id du
  dashboard (comportement actuel de `scopeMutation`) ; le panneau latéral montre le dashboard et
  les requêtes avec l'icône *Partagé*, à la même place dans l'ordre ; les widgets s'affichent avec
  les mêmes résultats qu'avant.
- Annuler → rien n'est écrit, le dashboard reste privé.

### 3.2 Requête utilisée par d'autres dashboards privés

Les widgets de ces dashboards sont remappés sur le nouvel id (comportement déjà en place de la
promotion d'une requête). Ces dashboards **restent privés** : seul le dashboard sur lequel l'action
est lancée change de portée. Ils continuent à fonctionner (un dashboard privé peut utiliser une
requête partagée).

### 3.3 Mélange de requêtes privées et partagées

Seules les requêtes privées sont listées et promues ; les widgets sur requête déjà partagée ne
changent pas.

### 3.4 Collision de titre **[Q 2]**

Les titres de requête ne sont pas uniques aujourd'hui (aucun contrôle en création ni en promotion).
Cas réaliste : deux membres de l'équipe partagent chacun leur dashboard « Campagnes » seedé — les
6 requêtes existent alors en double dans le dépôt, avec les mêmes titres.

Comportement retenu (recommandation) : la promotion n'est **ni bloquée ni renommée**. La
confirmation signale, sur la ligne de la requête, « Une requête partagée porte déjà ce titre :
QUERY-NNNN » (une ou plusieurs). L'utilisateur peut annuler et renommer, ou continuer. Le titre est
comparé sans tenir compte de la casse ni des espaces en tête/fin.

### 3.5 Cas bloquants (aucune écriture)

Le partage est refusé **avant toute écriture** si une requête privée du dashboard ne peut pas être
promue. La confirmation (ou, si l'on préfère, le message d'erreur actuel sous l'en-tête) liste la
cause par requête, sans bouton de confirmation :

| Cas | Message (sens) |
|---|---|
| Requête privée en lecture seule (`legacy-sql`, `newer-format`) | « <titre> : requête en lecture seule (<raison>), à réécrire ou retirer du dashboard » |
| Déclaration de paramètres invalide (`parametersError`) | « <titre> : paramètres invalides, à corriger dans /query » |
| Requête introuvable (widget pointant vers un id privé qui n'existe plus) | « Widget <titre> : requête introuvable, à reconfigurer ou supprimer » |

Les mêmes vérifications sont faites côté service (main), pas seulement dans l'UI : la liste peut être
périmée (requête modifiée dans un autre onglet du client web, `.pref` modifié).

### 3.6 Échec en cours de route

Les écritures se font une requête après l'autre, puis le dashboard. Chaque promotion de requête
laisse un état cohérent (copie partagée écrite avant le retrait de la privée, widgets remappés).
En cas d'échec au milieu (disque, git) :

- les requêtes déjà promues **restent partagées** (aucune annulation automatique) et leurs widgets
  sont remappés ;
- le dashboard reste privé ;
- l'erreur est affichée et nomme ce qui a été fait (« 3 requêtes sur 6 partagées ; le dashboard
  n'a pas été partagé : <erreur> ») ;
- relancer **Partagé** reprend : la confirmation ne liste plus que les requêtes encore privées.

Aucune requête n'est jamais perdue ni dupliquée par l'action (règle d'écriture de la promotion).

### 3.7 Dashboard, branche ou requête en lecture seule

- Dashboard en lecture seule : le sélecteur de portée n'est pas affiché (inchangé).
- Branche en lecture seule : mêmes garde-fous que les écritures partagées actuelles (rien de
  nouveau ; le refus est remonté comme aujourd'hui, avant toute écriture si la vérification
  existante le permet).

### 3.8 Retour en privé

Repasser ensuite le dashboard en privé ne rétrograde **pas** ses requêtes : elles restent
partagées (la rétrogradation d'une requête reste une opération distincte, sans UI aujourd'hui).
La fenêtre de confirmation le dit en une ligne.

### 3.9 Valeurs des paramètres choisis à l'affichage

Les valeurs mémorisées dans le `.pref` (`suiviParamValues`, GH93) suivent le nouvel id du
dashboard, comme aujourd'hui. Les ids de widget ne changent pas. Voir §6 pour l'interaction avec
#125.

### 3.10 MCP **[Q 3]**

Hors scope (recommandation) : le changement de portée reste réservé à l'app
(`SPEC-DASHBOARDS.md` §10), y compris ce partage groupé. Les tools MCP existants ne changent pas.
Un dashboard partagé par l'app est ensuite lisible / modifiable par MCP comme tout dashboard
partagé.

## 4. Critères d'acceptation

1. Dashboard privé « Campagnes » (6 widgets, 6 requêtes privées) : **Partagé** → confirmation
   listant 6 requêtes ; confirmer → 6 dossiers `queries/QUERY-NNNN/` et 1 dossier
   `dashboards/DASHBOARD-NNNN/` écrits, `.pref` sans ces 6 requêtes ni ce dashboard, chaque widget
   partagé référence un `QUERY-NNNN` ; résultats des 6 widgets identiques à avant le partage.
2. Une requête utilisée par 2 widgets du dashboard : listée une fois, une seule copie partagée,
   les 2 widgets remappés.
3. Requête privée aussi utilisée par un autre dashboard privé : listée avec « Aussi utilisée
   par » ; après partage, l'autre dashboard reste privé et son widget référence le nouvel id.
4. Dashboard privé sans requête privée : **Partagé** passe directement, sans confirmation
   (non-régression).
5. Annuler : aucun fichier écrit, `.pref` inchangé.
6. Requête privée `legacy-sql` (ou paramètres invalides, ou requête introuvable) dans le
   dashboard : partage refusé, cause listée, aucun fichier écrit ni `.pref` modifié — vérifié côté
   service (test unitaire) et côté UI.
7. Collision : une requête partagée de même titre existe → avertissement sur la ligne, partage
   possible, aucune requête renommée.
8. Échec simulé à la 3e promotion (test unitaire du service) : 2 requêtes partagées et remappées,
   la 3e et les suivantes encore privées, dashboard privé, erreur explicite ; relance → reprise sur
   les requêtes restantes, aucun doublon.
9. Ordre du panneau latéral (requêtes et dashboards) et valeurs de paramètres choisies conservés
   (mêmes positions, mêmes valeurs sous les nouveaux ids).
10. Client web : même parcours (e2e `e2e-web/gh67-*.spec.ts`), canal éventuel ajouté à
    `channel-policy.ts`.
11. Libellés fr / en.

## 5. Hors scope

- **Action UI pour changer la portée d'une requête seule** (promotion / rétrogradation depuis
  `/query` ou le panneau latéral) — manque constaté (§1), **[Q 1]** : nouvelle issue recommandée.
- Rétrogradation groupée (dashboard partagé → privé avec ses requêtes).
- Changement de portée via MCP (§3.10, **[Q 3]**).
- Dédoublonnage des requêtes identiques (réutiliser une requête partagée au même script plutôt que
  d'en créer une copie) — **[Q 2]** alternative.
- Unicité des titres de requêtes ou de dashboards.
- Dashboards privés des autres utilisateurs (limite connue §7.0b : non visibles, donc non remappés —
  sans objet ici puisque la requête promue n'existe que dans le `.pref` de l'utilisateur).
- Partage du seed « Campagnes » proposé automatiquement (le seed reste privé, décision #65).

## 6. Interaction avec #125 (paramètres choisis par widget, spécifié en parallèle)

#125 retire la barre de paramètres du dashboard et mémorise la valeur **par dashboard + widget**
dans le `.pref` (issue #125, § Décisions déjà prises) ; les choix au niveau du dashboard sont
abandonnés à la migration.

- **Point de contact** : au changement de portée d'un dashboard, `DashboardsService.renameInOrder`
  déplace aujourd'hui `suiviParamValues[ancienId]` vers `suiviParamValues[nouvelId]`. Avec #125, la
  structure de la clé change (dashboard + widget). Le partage groupé de #67 passe par le même
  `setScope` du dashboard : **quelle que soit la structure retenue par #125, le déplacement des
  valeurs au changement d'id du dashboard doit couvrir les valeurs par widget**. Les ids de widget
  ne changent pas au changement de portée, donc seul le niveau « dashboard » de la clé est à
  renommer. Si la clé de #125 incluait le `queryId` (ce que l'issue ne prévoit pas), le remappage de
  requête de #67 devrait aussi la renommer.
- **Ordre de merge** : le second ticket mergé reprend ce point ; un test unitaire « valeurs de
  paramètres conservées après partage groupé » (critère 9) le verrouille quel que soit l'ordre.
- **Pas d'autre recouvrement** : #67 ne touche ni `ParamBar`, ni `useDashboardParams`, ni
  l'impression / l'export docx. La fenêtre de confirmation de #67 n'affiche pas de paramètres.
- **Fichier partagé** : les deux tickets modifient `SPEC-DASHBOARDS.md` (#67 : §7.0b ; #125 :
  §5.1, §7.0, §10) et probablement `routes/dashboard.tsx` (#67 : action de portée dans l'en-tête ;
  #125 : retrait de la barre) — conflits de merge textuels attendus, sans conflit de fond.

## 9. Questions ouvertes

1. **Pas d'action UI pour changer la portée d'une requête** (constat §1). Recommandation : garder
   #67 sur le partage groupé depuis le dashboard, et ouvrir une issue séparée « Suivi : passer une
   requête en partagé / privé depuis l'app » (le message d'erreur actuel « Partagez d'abord ces
   requêtes » devient sans objet pour le partage d'un dashboard grâce à #67). Alternative : ajouter
   à #67 l'action sur une requête seule (`/query` + panneau latéral, avec la confirmation de retrait
   de colonne au passage en privé laissée de côté par GH70 sprint 1).
2. **Collision de titre**. Recommandation : avertissement non bloquant dans la confirmation, aucun
   renommage (§3.4). Alternatives : (a) réutiliser une requête partagée **identique** (même script,
   mêmes paramètres, même modèle) au lieu d'en créer une copie — évite les doublons quand plusieurs
   membres partagent leur « Campagnes », mais une requête identique aujourd'hui peut diverger demain
   sous les widgets de l'autre ; (b) suffixer le titre (« … (2) ») ; (c) bloquer.
3. **MCP**. Recommandation : hors scope, cohérent avec §10 (scope réservé à l'app). Alternative :
   paramètre `withQueries` sur un futur tool de changement de portée (impose d'abord d'ouvrir le
   changement de portée au MCP).
4. **Échec en cours de route**. Recommandation : pas d'annulation, reprise à la relance (§3.6).
   Alternative : rétrograder les requêtes déjà promues en cas d'échec (rollback) — plus de code et
   un second risque d'échec, pour un cas rare.
