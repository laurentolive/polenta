# GH68 — Campagnes : autoriser les tests non approuvés (planification en amont)

## Contexte

Une campagne ne peut aujourd'hui recevoir que des tests **approuvés** (`isTestApproved()` dans
[campaign.$campaignId.tsx](../apps/desktop/src/renderer/routes/campaign.$campaignId.tsx), règle T49
reprise par GH33 §2.2 et par le report GH64 via `isCarryEligible`). Un utilisateur qui veut
construire ses campagnes en amont (périmètre, charge, visibilité dans le suivi GH65) ne le peut pas
tant que ses tests sont en `draft`/`review`.

État constaté du code :
- **Ajout à une campagne** (« + Ajouter des tests », `TestPickerModal` mode `add`) : filtre
  `isTestApproved` ; message vide `campaignPage.noApprovedTestAvailable`.
- **Report GH64** à l'ajout : entrée « Non approuvé » grisée (`CarryEligibility = 'notApproved'`).
- **Création** (`/campaign/new`) : aucun filtre de statut dans le code (filtre composant/niveau
  seulement) — à vérifier lors de la recette, l'utilisateur a constaté que seuls les tests
  approuvés étaient proposés.
- **Analyse d'impact (T46)** : envoie `testCaseFilter: 'approved_only'`, mais
  `TraceabilityService.generateTestPlan` n'exploite pas ce paramètre (aucun filtre effectif).
- **Exécution** : aucun contrôle de statut ; elle se fait contre `testSnapshot`, figé à l'ajout (T49).

Le filtre existait parce que le snapshot T49 est pris à l'ajout : lever le filtre sans autre
changement ferait exécuter une version brouillon figée. GH68 déplace donc le contrôle de l'ajout
vers l'exécution et resynchronise la copie tant que l'instance n'est pas exécutée.

## Décisions de cadrage

| # | Question | Décision |
|---|----------|----------|
| D1 | Statuts proposés à l'ajout | **Tous les statuts**, y compris terminaux (`obsolete`) |
| D2 | Exécution d'un test non approuvé | **Avertissement**, pas de blocage |
| D3 | Version figée d'une instance ajoutée non approuvée | **Resynchronisation automatique tant que l'instance est `pending`**, figée dès qu'un résultat est saisi |
| D4 | Analyse d'impact (T46) | **Alignée** : pas de filtre de statut |

## Comportements attendus

### 1. Sélection des tests (création, ajout, report)

1. Le sélecteur (`TestPickerModal`, onglet « Tests ») propose **tous les tests**, quel que soit leur
   statut, à la création comme à l'ajout. Les règles de déduplication existantes sont inchangées
   (test sans référence à saisir déjà présent → non proposé ; T97 ; T179).
2. Un test non approuvé est **signalé** dans la grille par son statut (la colonne statut de la Vue
   Excel s'il est affiché ; sinon un badge « Non approuvé » à côté de l'ID). Un test non approuvé
   n'est ni décoché ni grisé.
3. Onglet « Depuis une campagne » (GH64) : le motif d'indisponibilité « non approuvé » disparaît ;
   une entrée dont le test n'est pas approuvé est disponible, avec la même signalisation qu'au §1.2.
   Les autres motifs (test supprimé, hors filtre composant/niveau à la création, exigence T179
   plus liée) sont inchangés.
4. Le libellé vide `noApprovedTestAvailable` n'a plus lieu d'être : à l'ajout, même message que
   la création (`noTestCaseAvailable`).
5. Bouton « Dupliquer » une instance : autorisé quel que soit le statut du test (il l'était déjà
   côté main ; vérifier qu'aucun garde côté UI ne le restreint).

**Statut « approuvé »** : toujours résolu depuis `statuses[].isApproval` du type du test, repli sur
`approved` (logique `isTestApproved` / `maturity.util.ts` existante).

### 2. Liste des tests d'une campagne

6. Une instance dont la copie (`testSnapshot`, à défaut le test live pour les entrées pré-T49) n'est
   **pas dans un statut d'approbation** porte un badge « Non approuvé » (infobulle : statut du test,
   ex. « Brouillon »).
7. Pour une instance `pending`, le badge reflète l'état **live** du test (cohérent avec la
   resynchronisation §3) ; pour une instance exécutée, il reflète la copie figée — c.-à-d. le
   statut du test au moment de l'exécution.
8. Un bandeau (même style que le bandeau des références non résolues T171) indique « N instance(s)
   à exécuter portent sur des tests non approuvés » lorsque N > 0 parmi les instances `pending`.
   Pas de bandeau si seules des instances déjà exécutées sont concernées.

### 3. Resynchronisation de la copie (T49 assoupli)

9. **Règle** : une instance est *resynchronisable* si son `status` est `pending` **et** sa copie
   `testSnapshot` n'est pas dans un statut d'approbation. Elle est alors recopiée depuis l'état
   actuel du test (objet `TestCase` complet, même mécanisme que l'ajout).
10. **Moments de resynchronisation** :
    - ouverture de la page d'exécution de l'instance
      ([campaign.$campaignId_.execute.$testId.tsx](../apps/desktop/src/renderer/routes/campaign.$campaignId_.execute.$testId.tsx)) ;
    - saisie d'un résultat (`updateRun()`, côté main) : la copie est rafraîchie **juste avant**
      d'enregistrer le résultat, dans la même écriture ; c'est elle qui est figée ensuite ;
    - import d'un classeur d'exécution (GH36, `CampaignExecutionService.apply`) : même règle que
      `updateRun()` — la copie figée est celle du test au moment de l'import ;
    - export d'un classeur d'exécution (GH36) : le contenu exporté pour une instance
      resynchronisable est celui du test **live** (sans réécrire la campagne).
11. Une instance ajoutée **approuvée** garde le comportement T49 actuel : jamais resynchronisée,
    même si le test a été modifié ou est repassé en brouillon depuis.
12. Une instance resynchronisée sur une version **devenue approuvée** cesse d'être
    resynchronisable (§9) : elle se comporte ensuite comme une instance ajoutée approuvée.
13. Les paramètres (`resolvedParams`, `paramValues`, `paramSourceRef`, `unresolvedParams`,
    `requirementId`) **ne sont pas** recalculés par la resynchronisation — seule la copie du test
    change. Si la nouvelle version introduit une référence absente de l'instance, elle apparaît non
    résolue/vide à l'exécution, comme aujourd'hui pour une entrée pré-T49 (voir Cas limites).
14. Test source **supprimé** : pas de resynchronisation, la copie existante est conservée
    (comportement T49 inchangé).
15. Campagne `completed`/`abandoned` : aucune resynchronisation (les instances `pending` d'une
    campagne fermée restent figées).

### 4. Exécution d'un test non approuvé (avertissement)

16. Page d'exécution : si la copie (après resynchronisation) n'est pas dans un statut
    d'approbation, un bandeau d'avertissement s'affiche en haut : « Ce test n'est pas approuvé
    (statut : <libellé>). Le résultat sera enregistré contre cette version non validée. »
17. À la **première** saisie d'un résultat sur cette instance, une confirmation est demandée
    (« Exécuter quand même ? »). Annuler n'enregistre rien. Pas de nouvelle confirmation pour les
    modifications ultérieures du résultat de la même instance.
18. Pas de champ de trace dédié : le statut du test au moment de l'exécution est conservé dans
    `testSnapshot.status` de l'instance exécutée (figé par §10).
19. Import Excel (GH36) : pas de confirmation ; l'aperçu d'import (`preview`) liste en
    avertissement les instances portant sur un test non approuvé. L'import n'est pas refusé.
20. Passage `planned` → `in_progress` : inchangé (automatique à la première saisie), aucun contrôle
    de statut des tests.

### 5. Analyse d'impact (T46)

21. La génération de campagne depuis l'analyse d'impact ne filtre pas les tests sur leur statut :
    `impact-analysis.tsx` envoie `testCaseFilter: 'include_draft'` (le main n'applique de toute
    façon aucun filtre aujourd'hui — on aligne l'intention sur le comportement). Le reste
    (navigation vers `/campaign/new` préremplie) est inchangé.

## Critères d'acceptation

- [ ] CA1 — Campagne `planned` avec un test `draft` dans le repo : « + Ajouter des tests » liste ce
      test, signalé non approuvé ; l'ajout crée une instance `pending`.
- [ ] CA2 — Même chose à la création (`/campaign/new`) et pour un test `obsolete`.
- [ ] CA3 — Report GH64 : une entrée `pending` d'une autre campagne dont le test est `draft` est
      sélectionnable (plus grisée « non approuvé ») et crée une instance.
- [ ] CA4 — Liste de la campagne : badge « Non approuvé » sur l'instance, bandeau « 1 instance à
      exécuter… ».
- [ ] CA5 — Test `draft` ajouté, puis son étape 1 modifiée dans l'éditeur : ouverture de la page
      d'exécution → l'étape modifiée est affichée (copie resynchronisée).
- [ ] CA6 — Le test passe `approved` puis est modifié à nouveau : l'instance a été resynchronisée
      sur la version approuvée au passage précédent (ouverture exécution ou saisie) et ne bouge plus
      ensuite ; le badge disparaît.
- [ ] CA7 — Saisie d'un résultat sur une instance non approuvée : bandeau + confirmation ; après
      confirmation, `testSnapshot` = version du test au moment de la saisie, `status` du résultat
      enregistré ; une modification ultérieure du test ne change plus cette copie.
- [ ] CA8 — Instance ajoutée **approuvée**, test repassé `draft` puis modifié : copie inchangée,
      pas de badge (comportement T49 conservé).
- [ ] CA9 — Export Excel d'une campagne avec une instance non approuvée `pending` : contenu = état
      live du test ; import du classeur → aperçu avec avertissement, import accepté, copie figée =
      état au moment de l'import.
- [ ] CA10 — Campagne fermée avec une instance `pending` non approuvée : aucune resynchronisation.
- [ ] CA11 — Génération depuis l'analyse d'impact : un test `draft` couvrant une exigence impactée
      est présélectionné dans `/campaign/new`.
- [ ] CA12 — Les tests existants (unitaires carry/campaigns, e2e GH64) sont mis à jour pour la
      nouvelle règle d'éligibilité et passent.

## Cas limites

- **Nouvelle référence de paramètre** introduite par la resynchronisation (§13) : la valeur
  n'existe ni dans `resolvedParams` ni dans `paramValues` → affichée littérale à l'exécution.
  Accepté pour ce ticket ; l'utilisateur peut corriger via l'édition des `paramValues`
  si la référence est à saisir. Une re-résolution complète des paramètres est hors scope.
- **Test devenu itérant** (T179) entre l'ajout et la resynchronisation : l'instance garde son
  `requirementId` (absent) ; pas de génération d'instances supplémentaires.
- **Changement de type** (`objectTypeRef`) du test : la copie suit, sans autre effet.
- **Entrée pré-T49** (sans `testSnapshot`) : déjà résolue en live ; badge calculé sur le live ;
  la saisie d'un résultat ne crée pas de copie (comportement inchangé).
- **Course export/import Excel** : le test peut changer entre l'export et l'import ; la copie figée
  est celle de l'import (pas de l'export). Accepté.

## Hors scope

- Re-résolution des paramètres (T171) ou des instances par exigence (T179) lors d'une
  resynchronisation.
- Resynchronisation des instances ajoutées approuvées (§11) ou action manuelle « mettre à jour
  vers la version actuelle ».
- Blocage du démarrage ou de la clôture d'une campagne selon le statut des tests.
- Nouvelle colonne « statut du test » dans la table `campaign_entries` / dashboard Campagnes (GH65).
- Exports plan/rapport (xlsx/docx/pdf) : pas de mention spécifique « non approuvé » (ils lisent
  `testSnapshot`, donc le statut figé est déjà disponible pour un gabarit client).
