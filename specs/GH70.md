# GH70 — Vues : colonnes calculées définies par le projet (premier cas : « Dernier résultat »)

> Issue : #70 — dépend de #73 (runs rattachés aux entrées de campagne) et #74 (moteur de scripts,
> bibliothèque projet), tous deux fermés.

## 1. Besoin

Afficher dans les vues de la Vue Système des **colonnes calculées définies par le projet** :
une valeur par élément, calculée par un script du projet, présentée **comme un champ parmi les
autres** (proposée dans le panneau ⚙️, rendue selon son type). Premier cas livré : **« Dernier
résultat »** sur les cas de test — le statut de la dernière exécution du test en campagne, pour
répondre à « où en est ce test ? » sans quitter la vue.

## 2. Décision indicateur (principe GH79, SPEC-TECH-stack §1.1)

*« Dernier résultat » sert-il à une fonction de Polenta ?* **Non** : c'est un indicateur de suivi.
Il n'est donc **pas** codé dans Polenta. Ce ticket livre :

- dans Polenta, le **mécanisme générique** (déclaration, exécution par le moteur isolé de #74,
  affichage en champ, filtre, export) — sans aucune connaissance des campagnes ;
- côté projet, l'**exemple** « Dernier résultat » : une fonction de la bibliothèque de départ
  (`dashboards/lib/campaign.js`) et un modèle de requête qui la déclare comme colonne. Les règles
  (quelles exécutions comptent, instances multiples, campagnes abandonnées) sont celles du script,
  modifiables par le projet.

## 3. Déclaration : une requête partagée

Une colonne calculée **est une requête partagée** (`queries/QUERY-NNNN/`) qui porte en plus une
déclaration de colonne dans son `query.yaml` :

```yaml
# queries/QUERY-0012/query.yaml
id: QUERY-0012
title: Dernier résultat de campagne
formatVersion: 1
column:
  label: Dernier résultat          # libellé de la colonne (en-tête, panneau ⚙️, exports)
  appliesTo:                       # types d'objet pour lesquels la colonne est proposée
    categories: [test]             # catégorie(s) : requirement | test
    objectTypes: []                # et/ou types précis `<nœud>::<type>`
  type: enum                       # type de champ (SchemaFieldType) qui gouverne le rendu
  values: [PASS, FAIL, BLOCKED, INCOMPLETE]   # enum / multi_enum uniquement
```

Règles :

- **Partagée uniquement** : une requête privée ne peut pas être une colonne (la colonne est une
  définition du projet, vue par tous). Rétrograder en privé une requête déclarée comme colonne
  demande confirmation et retire la déclaration.
- `type` : un type de champ du schéma (`text`, `textarea`, `number`, `enum`, `multi_enum`, `date`,
  `boolean`, `richtext`…) ; `drawio` refusé. La cellule est rendue **exactement comme un champ de
  ce type** (même composant de lecture que pour un champ personnalisé).
- `appliesTo` : la colonne est proposée pour un type affiché si sa catégorie figure dans
  `categories` **ou** si son `objectTypeRef` figure dans `objectTypes`. Vide → proposée nulle part.
- Déclaration invalide (fichier modifié à la main : type inconnu, `values` absent pour un enum…)
  → la requête reste utilisable en Suivi, la colonne n'est pas proposée et l'erreur est affichée
  dans la vue `/query` (même traitement que `parametersError`, GH93).
- Requête avec paramètres (GH93) : exécutée avec toutes les valeurs à `null` ; un paramètre
  obligatoire rend la colonne en erreur (`params`).
- Requête en lecture seule (`legacy-sql`, `newer-format`) : jamais proposée comme colonne.
- La déclaration entre dans l'empreinte du modèle comme la déclaration de paramètres
  (`queryCodeForHash`) : la modifier détache la requête de son modèle.

### 3.1 Saisie dans la vue `/query`

Section « Colonne des vues » de l'éditeur de requête (requête partagée) : case « Utiliser comme
colonne dans la Vue Système », libellé (défaut : titre de la requête), catégories / types d'objet
concernés, type de champ et, pour un enum, liste des valeurs. Enregistrée avec la requête.

### 3.2 MCP

`create_query` / `update_query` acceptent `column` (même format, même validation) ;
`list_queries` le renvoie.

## 4. Contrat du script

Script de données ordinaire (SPEC-DASHBOARDS §3) : `export default function (data, polenta)`,
même bac à sable, mêmes limites. Il renvoie **une ligne par élément** :

| Colonne de ligne | Obligatoire | Rôle |
|---|---|---|
| `id` | oui | ID de l'élément (exigence ou test) auquel la valeur s'applique |
| `value` | oui | valeur du champ (scalaire, `null` = vide) — `multi_enum` : chaîne CSV |
| `tooltip` | non | texte de l'infobulle de la cellule |
| `_ids` | non | cible du clic : le premier identifiant est ouvert (objet, campagne, entrée `CAMP-xxxx/<entryId>`) |

- Un élément sans ligne → cellule vide.
- Plusieurs lignes pour le même `id` → la première est retenue.
- `id` inconnu → ignoré.
- Valeur hors type (texte pour un `number`, valeur hors liste d'un enum) → affichée telle quelle,
  comme une valeur de champ non conforme saisie à la main.
- Ligne sans `id` ou `value` absent → erreur `rows` (§6.4).

## 5. Exemple livré : « Dernier résultat »

### 5.1 Bibliothèque de départ (`dashboards/lib/campaign.js`)

Nouvelle fonction `lastEntryResults(data)` (+ `lastEntryResult(data, testId)`) — `lastResult(s)`
existante inchangée (elle compte tous les runs, des scripts peuvent en dépendre) :

- ne compte que les **entrées de campagne exécutées** (`executedAt` renseigné), actives, de
  **toutes les campagnes** du graphe, **abandonnées comprises** ;
- par `testCaseId`, retient l'entrée au `executedAt` le plus récent — plusieurs instances d'un
  même test (test itérant) : la plus récente l'emporte ;
- les runs hors campagne sont ignorés ;
- renvoie `{ status, executedAt, executedBy, campaignId, campaignTitle, entryId }`.

Version de `campaign.js` incrémentée : proposée aux projets existants par le bandeau des mises à
jour (SPEC-DASHBOARDS §8.1).

### 5.2 Modèle de requête « Dernier résultat de campagne »

Nouveau modèle de requête (`suivi-templates.ts`) qui génère le script et la déclaration :

- une ligne par test exécuté : `id` = test, `value` = statut (`PASS` / `FAIL` / `BLOCKED` /
  `INCOMPLETE`), `tooltip` = « `CAMP-xxxx` — titre · date locale · exécutant »,
  `_ids` = `[CAMP-xxxx/<entryId>]` ;
- déclaration : libellé « Dernier résultat » (« Last result » en anglais), `categories: [test]`,
  `type: enum`, `values: [PASS, FAIL, BLOCKED, INCOMPLETE]`.

Le projet de démonstration (`scripts/demo-lave-linge/generate.mjs`) contient cette requête. Pas de
seed automatique dans les projets existants (cf. hors scope).

## 6. Comportement dans les vues

### 6.1 Panneau ⚙️ (Configuration des champs)

- Nouvelle section « Colonnes calculées » (après les champs, avant Étapes / Liens) listant les
  colonnes applicables au type affiché : libellé + badge `(calc)` ; infobulle = ID et titre de la
  requête.
- Onglets **Tableau** et **Document** : réglage indépendant, comme tout champ. Décochée par défaut
  (absente de `defaultVisibleFields`).
- Clé de colonne dans `fieldVisibility` : `query::<QUERY-ID>`. Requête supprimée, rendue privée ou
  dont la déclaration ne s'applique plus → clé ignorée à l'affichage (non réécrite).
- Pas de section si aucune colonne n'est applicable.

### 6.2 Vue Excel (Tableau)

- Colonne à part entière, en-tête = libellé, positionnée selon l'ordre des colonnes comme les autres
  (glisser-déposer d'en-tête compris).
- **Lecture seule** : sélection de cellule possible ; ni double-clic d'édition, ni F2, ni édition
  en masse, ni coller, ni suppression. Visuellement distincte comme les champs système.
- **Double-clic** sur une cellule dont la ligne a des `_ids` → ouverture de la cible
  (`suivi:resolve-target`, même navigation que le drill-down des widgets : entrée de campagne →
  page de la campagne sur cette entrée). Sans `_ids` : rien.
- **Infobulle** : `tooltip` au survol de la cellule.
- **Filtre par colonne (T51)** : icône et popover comme les autres colonnes ; porte sur la valeur
  affichée.
- Hauteur max des lignes (T168) : appliquée comme pour un champ du même type.
- Mode sélection (sélecteur de tests GH33) : la colonne y apparaît si elle est visible dans la
  configuration Tableau du type, comme les autres champs.

### 6.3 Vue Word (Document)

La valeur s'affiche dans la carte de l'élément comme un champ du même type (libellé + valeur),
lecture seule ; clic sur la valeur → même ouverture de cible que le double-clic Excel ; infobulle
identique.

### 6.4 Exécution, rafraîchissement, erreurs

- Une exécution **par requête** pour toute la vue (pas une par élément), seulement si la colonne
  est visible dans la vue courante.
- Pas de blocage de l'ouverture de la vue (dérogation assumée à « un seul affichage », T176) : le
  tableau s'affiche, les cellules de la colonne montrent un indicateur discret de chargement jusqu'au
  résultat.
- Résultat mis en cache et invalidé comme les résultats de widgets (SPEC-DASHBOARDS §8.2) :
  changement de `requirements/`, `tests/`, `test-runs/`, `links/`, `campaigns/`, `queries/`,
  `dashboards/lib/` ou de ref, dans n'importe quel repo du workspace — un résultat saisi en campagne
  met à jour la colonne sans recharger.
- Erreur d'exécution (toutes les erreurs du moteur, §3 de SPEC-DASHBOARDS) : cellules vides, ⚠ dans
  l'en-tête avec le message (`message (fichier:ligne)`) en infobulle. La vue reste utilisable.

### 6.5 Exports

Les exports qui suivent les colonnes visibles (Excel, Word / PDF de la Vue Système) incluent la
colonne avec sa valeur en texte (même libellé d'en-tête).

## 7. Critères d'acceptation

1. Une requête partagée avec `column` valide (`categories: [test]`) est proposée dans ⚙️ (Tableau
   et Document) pour tout type de test, et pour aucun type d'exigence.
2. Cochée en Tableau, la colonne s'affiche ; décochée par défaut ; le réglage est persisté par
   type et par utilisateur sous la clé `query::<ID>`.
3. Avec le modèle « Dernier résultat de campagne » sur le projet de démonstration : un test dont
   la dernière entrée exécutée est `FAIL` affiche `FAIL` rendu comme un enum ; un test jamais
   exécuté en campagne affiche une cellule vide ; un test exécuté seulement hors campagne aussi.
4. Test présent dans deux campagnes : la valeur est celle de l'entrée au `executedAt` le plus
   récent, campagne abandonnée comprise.
5. Saisir un résultat dans une campagne met à jour la cellule sans recharger la vue.
6. L'infobulle montre ID et titre de campagne, date, exécutant ; le double-clic ouvre la page de la
   campagne sur l'entrée.
7. La cellule n'est pas éditable (double-clic, F2, coller, édition en masse sans effet).
8. Le filtre de colonne (T51) sur `FAIL` ne garde que les tests en échec.
9. Une erreur dans le script (ex. `throw`) laisse la vue utilisable, cellules vides et ⚠ dans
   l'en-tête avec le message.
10. La colonne apparaît dans la carte en Vue Word si cochée dans l'onglet Document.
11. L'export Excel de la vue contient la colonne avec ses valeurs.
12. Une requête privée ne peut pas porter de déclaration de colonne (UI et service) ; une
    déclaration invalide écrite à la main n'est pas proposée et l'erreur s'affiche dans `/query`.
13. `create_query` (MCP) avec `column` crée une colonne proposée dans ⚙️.
14. Polenta ne contient aucun code propre aux campagnes pour cette colonne (le calcul est
    entièrement dans le script / la bibliothèque projet).

## 8. Hors scope

- **Tri** par colonne : la Vue Excel n'a pas de tri aujourd'hui (aucune colonne n'est triable) —
  nouvelle issue si besoin, pour toutes les colonnes.
- Vue Édition (pas d'onglet Édition dans ⚙️, écart connu T138) et autres vues (Recherche,
  traçabilité, page campagne).
- Colonnes calculées éditables, ou écrites dans les fichiers des éléments.
- Seed automatique de « Dernier résultat » dans les projets existants (le projet crée la requête
  depuis le modèle en deux clics) ; proposition au bandeau des mises à jour.
- Requêtes privées comme colonnes personnelles.
- Paramètres choisis à l'affichage pour une colonne (valeurs toujours `null`).
- Matrice test × campagne (#69, livrée côté Suivi).

## 9. Évolution après test (sprint 3, demandée le 2026-10-20)

Constat au test dans PH2 : devoir passer par un modèle dédié, ou réécrire une requête en Script, pour
obtenir une colonne manque de souplesse. Deux évolutions :

- **A — Colonne déclarable sur toute requête partagée, y compris en mode modèle.** La déclaration
  `column` devient **indépendante du modèle** : elle n'entre plus dans l'empreinte (`hash`) et sa
  modification ne détache plus la requête de son modèle (révise §3 « La déclaration entre dans
  l'empreinte du modèle »). Un modèle peut toujours **proposer** une déclaration à la création
  (`campaign-last-result`) ; elle reste modifiable. Une requête enregistrée avant ce changement,
  avec une colonne comptée dans son empreinte, n'est pas vue comme personnalisée.
- **B — Colonnes du résultat choisies.** La déclaration peut nommer les colonnes du résultat qui
  servent d'identifiant, de valeur et d'infobulle :

  ```yaml
  column:
    label: Statut en campagne
    appliesTo: { categories: [test], objectTypes: [] }
    type: enum
    values: [pending, PASS, FAIL, BLOCKED, INCOMPLETE]
    idColumn: testCaseId        # défaut : id
    valueColumn: status         # défaut : value
    tooltipColumn: campaignTitle  # défaut : tooltip (absente → pas d'infobulle)
  ```

  Saisie : listes déroulantes alimentées par les colonnes du dernier résultat de la requête (et la
  valeur enregistrée). Cible du double-clic : toujours `_ids` de la ligne. Plusieurs lignes pour un
  même élément : la première est retenue (l'ordre, donc la règle, reste celle du script).

Critères d'acceptation ajoutés :

15. Une requête « Entrées de campagne » (mode modèle) déclarée en colonne avec
    `idColumn: testCaseId`, `valueColumn: status` affiche le statut dans la Vue Tableau des tests,
    sans passer en Script, et reste non personnalisée.
16. Modifier la déclaration d'une requête issue d'un modèle ne la détache pas de son modèle.
17. Colonne d'identifiant ou de valeur absente du résultat → ⚠ « colonne « X » manquante ».
