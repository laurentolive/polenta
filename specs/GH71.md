# GH71 — Campagnes : avancement de la définition des tests au résultat

## Contexte

Depuis GH68, une campagne peut contenir des tests pas encore approuvés : on la construit en amont,
pendant que les tests sont rédigés et revus. Le suivi ne montre pas cette phase. Le widget
« Avancement par campagne » du dashboard Campagnes (GH65, SPEC-DASHBOARDS §5.1b) empile
`campaign_entries.status`, et toute entrée non exécutée y est `pending`, qu'il s'agisse d'un test en
brouillon ou d'un test prêt. De même, les pastilles de la page campagne (SPEC-TESTS §4.3) n'ont
qu'une pastille « En attente ».

État du code :
- `flattenCampaignEntry` (`query-engine.service.ts`) produit une ligne par entrée, sans
  information sur le test au-delà de son titre.
- `BarWidget` : séries dans l'ordre de première apparition dans les lignes, libellé = valeur brute,
  couleur = position dans la palette catégorielle (`seriesColor(i)`).
- Seed GH65 : requête `progress` =
  `SELECT [campaignTitle], [status], COUNT(*) …`, widget `fieldMapping { category: 'campaignTitle',
  measure: 'count', series: 'status', stacked: true }`. Dashboard et requêtes privés (`.{user}.pref`).
- Page campagne : pastilles `RUN_STATUSES` (`PASS, FAIL, BLOCKED, INCOMPLETE, pending`), filtre par
  le paramètre d'URL `status`.

## Décisions de cadrage

| # | Question | Décision |
|---|----------|----------|
| D1 | Découpage de la phase avant exécution | **Statuts du schéma** : une étape par statut non approuvé du type de test, puis « Prêt à exécuter », puis les résultats |
| D2 | Où | **Dashboard** (`campaign_entries` + widget du seed + drill-down) **et page campagne** (pastilles) |
| D3 | Widget existant déjà créé | **Mis à jour** s'il n'a pas été modifié par l'utilisateur |
| D4 | Libellés / ordre / couleurs du graphe | **Préréglage de widget** « avancement de campagne » : clés techniques dans les données ; ordre, libellés et couleurs sémantiques au rendu |
| D5 | Pastilles de la page campagne | **Remplacer « En attente »** par une pastille par étape de préparation + « Prêt » |

## Comportements attendus

### 1. Étape d'avancement d'une entrée

1. Chaque entrée de campagne a une **étape d'avancement**, clé technique calculée ainsi :
   - entrée exécutée (`status ≠ pending`) → son résultat : `PASS`, `FAIL`, `BLOCKED`, `INCOMPLETE` ;
   - entrée `pending` dont le test retenu est approuvé → `ready` ;
   - entrée `pending` dont le test retenu n'est pas approuvé → `prep:<nom du statut>` (ex.
     `prep:draft`, `prep:review`). Le préfixe évite toute collision avec un statut de schéma qui
     s'appellerait `ready` ou `PASS`.
2. **Test retenu** (même règle que GH68) : tant que l'instance est *resynchronisable* (`pending`,
   copie présente, copie non approuvée) **et que la campagne est ouverte**, l'état **live** du test ;
   sinon la copie (`testSnapshot`), à défaut le test live (entrée pré-T49). Test introuvable et
   pas de copie → `ready` (on ne peut rien dire de sa préparation ; cas marginal).
   *Correction associée de GH68* : la pastille « Non approuvé » applique aussi la condition
   « campagne ouverte » (une campagne clôturée est jugée sur ses copies).
3. Approuvé = `statuses[].isApproval` du type du test, repli sur `approved` (`isApprovalStatus`).
4. **Ordre canonique** des étapes, utilisé par le graphe et les pastilles :
   1. `prep:*` dans l'ordre de déclaration des statuts du type de test dans `schema.yaml` ; si une
      campagne mélange plusieurs types de test, rang = position du statut dans **son** type, à
      égalité par ordre alphabétique de nom ; un même nom de statut présent dans plusieurs types
      est une seule étape ;
   2. `ready` ;
   3. `INCOMPLETE`, `BLOCKED`, `FAIL`, `PASS`.
5. **Libellés** : `prep:<nom>` → `label` du statut dans le schéma (premier type de test qui le
   déclare), à défaut le nom ; `ready` → « Prêt à exécuter » / « Ready to run » ; résultats →
   libellés existants (`campaignPage.runStatus.*`).

### 2. Table `campaign_entries` (dashboard)

6. Nouvelles colonnes :
   - `progress` : clé d'étape (§1) ;
   - `progressRank` : entier, rang dans l'ordre canonique (§4), pour trier en SQL ;
   - `testStatus` : statut du test retenu (§2), `null` si inconnu.
   La colonne `status` (statut de l'entrée) est **inchangée**.
7. Builder : `progress` et `testStatus` sont proposées (allowlist) ; `progressRank` en SQL seulement.
8. Le drill-down d'un segment cliqué filtre sur la clé brute (`[progress] = 'prep:draft'`) —
   mécanisme GH65 inchangé.
9. Ouverture d'une ligne d'entrée non exécutée (`resolveRowTarget`) : page de la campagne filtrée
   sur **l'étape** de l'entrée (§4.12) plutôt que sur `pending`.

### 3. Préréglage de widget « Avancement de campagne »

10. Nouveau champ optionnel du `fieldMapping` d'un widget barre : `preset: 'campaignProgress'`.
    Il s'applique à la série (`fieldMapping.series`) dont les valeurs sont des clés d'étape :
    - séries **ordonnées** selon l'ordre canonique (§4), quel que soit l'ordre des lignes ;
    - **libellées** selon §5 (légende, infobulle) ;
    - **colorées** sémantiquement : préparation en gris (du plus foncé au plus clair à mesure qu'on
      approche de l'approbation), `ready` bleu, `INCOMPLETE` jaune, `BLOCKED` orange, `FAIL` rouge,
      `PASS` vert ; couleurs issues des jetons de thème (clair et sombre) ;
    - une valeur qui n'est pas une clé d'étape garde le rendu standard, placée après les étapes.
11. Le préréglage se choisit dans l'éditeur de widget (widget barre avec série) : « Présentation
    des séries : Standard / Avancement de campagne ». Il est conservé quand on modifie le widget.

### 4. Dashboard Campagnes (seed)

12. Nouvelle définition du widget **Avancement par campagne** : requête
    `SELECT [campaignTitle], [progress], COUNT(*) AS [count] FROM [campaign_entries]
    WHERE [campaignStatus] IN ('planned', 'in_progress') GROUP BY [campaignTitle], [progress]`,
    `fieldMapping { category: 'campaignTitle', measure: 'count', series: 'progress', stacked: true,
    preset: 'campaignProgress' }`. Utilisée par tout nouveau seed.
13. **Mise à jour d'un dashboard déjà semé** (une fois par utilisateur et par repo, à la première
    lecture des dashboards après la mise à jour) : si la requête `progress` connue du marqueur
    `campaignsSeed` existe encore **et** que son SQL est exactement celui de GH65, son SQL est
    remplacé ; si le widget qui l'utilise existe **et** que son `fieldMapping` est exactement celui
    de GH65, il est remplacé. Requête ou widget modifié par l'utilisateur, supprimé, ou dashboard
    supprimé → rien n'est touché. Marqueur `campaignsSeed.progressV2: done` (ou équivalent) posé
    dans tous les cas pour ne pas réessayer. Le titre du widget n'entre pas dans la comparaison.
14. KPI « % exécuté », « % PASS », « Exécutions par jour », « Entrées en échec » : inchangés.

### 5. Page campagne (pastilles)

15. La pastille « En attente » est remplacée par **une pastille par étape de préparation présente**
    (`prep:*` ayant au moins une entrée) puis **« Prêt à exécuter »**, dans l'ordre canonique, suivies
    des pastilles de résultat. Ordre complet : préparation…, Prêt, Incomplet, Bloqué, Échoué, Passé
    (aligné sur le graphe ; aujourd'hui `PASS, FAIL, BLOCKED, INCOMPLETE, pending`).
    Comme aujourd'hui, une étape sans entrée n'a pas de pastille (sauf l'étape filtrée) — *précisé
    au sprint 2 : la spec supposait à tort que les pastilles à 0 étaient affichées.*
16. Couleurs des pastilles : mêmes teintes sémantiques que le graphe.
17. Clic sur une pastille = filtre de la liste (bascule), comme GH65. Paramètre d'URL `progress`
    (clé d'étape, valeur inconnue ignorée). `status` reste accepté : `status=pending` filtre toutes
    les entrées non exécutées (préparation + prêt), `status=PASS` etc. inchangé ; si les deux sont
    présents, `progress` l'emporte.
18. Le récapitulatif « Filtre : X ✕ » affiche le libellé de l'étape.

## Critères d'acceptation

- [ ] CA1 — Campagne avec : 1 test brouillon, 1 test en revue, 1 test approuvé non exécuté, 1 PASS,
      1 FAIL → `campaign_entries.progress` = `prep:draft`, `prep:review`, `ready`, `PASS`, `FAIL` ;
      `progressRank` croissant dans cet ordre (draft < review dans le schéma).
- [ ] CA2 — Le test brouillon passe en revue dans l'éditeur → au rafraîchissement, l'entrée passe
      de `prep:draft` à `prep:review` (statut live, instance resynchronisable).
- [ ] CA3 — Entrée exécutée sur un test brouillon → `progress` = son résultat.
- [ ] CA4 — Instance ajoutée approuvée, test repassé brouillon → `ready` (copie approuvée, T49).
- [ ] CA5 — Campagne clôturée avec une instance pending sur copie brouillon, test approuvé depuis →
      `prep:draft` (copie) ; la pastille « Non approuvé » est affichée.
- [ ] CA6 — Nouveau seed : le widget « Avancement par campagne » empile Brouillon, En revue, Prêt à
      exécuter, Échoué, Passé dans cet ordre, en gris / gris / bleu / rouge / vert, légende avec ces
      libellés ; clic sur « En revue » → drill-down des entrées `prep:review`.
- [ ] CA7 — Dashboard semé avec GH65, requête et widget non modifiés → mis à jour (CA6) à

- [ ] CA8 — Widget barre quelconque : « Présentation des séries : Avancement de campagne » dans

## Cas limites

- **Statut terminal** (`obsolete`) d'un test non approuvé en campagne : étape `prep:obsolete`
  comme une autre (rang selon le schéma). Pas de traitement particulier.
- **Statut absent du schéma** (YAML édité à la main, type supprimé) : `prep:<nom>`, rang après
  tous les statuts connus, libellé = nom.
- **Type de test introuvable** : repli `approved` (§3) ; statut ≠ `approved` → `prep:<nom>`.
- **Projet sans statut `isApproval`** : seul `approved` vaut « approuvé » — comportement GH68.
- **Préréglage sur une série qui n'a aucune clé d'étape** : rendu standard (toutes les valeurs
  passent par le repli §10).

## Hors scope

- Historique de l'avancement dans le temps (courbe de burn-up préparation → exécution) : la table
  ne restitue que l'état courant (comme GH65).
- Pie / ligne / KPI avec préréglage : barre seulement.
- Exports de campagne (plan, rapport) : pas d'étape de préparation.
- Statistiques de la vue système (Vue Excel) : inchangées.
