# GH73 — Campagnes : historique daté des exécutions (rattachement des runs, dates d'ajout et de retrait des entrées)

## Contexte

Besoin final : suivre l'avancement d'une campagne **dans le temps** — à chaque date, combien
d'entrées sont en attente, PASS, FAIL, BLOCKED ou INCOMPLETE (courbe empilée). Le modèle actuel ne
garde que le **dernier** état de chaque entrée : impossible de reconstruire l'état d'une campagne à
une date passée.

### Principe « données brutes » (GH79, décision du 2026-10-13)

Ce ticket ne livre que des **faits bruts**, enregistrés au moment où ils se produisent : à quelle
entrée appartient un run, quand une entrée a été ajoutée, quand elle a été retirée. Le calcul
« état de chaque entrée d'une campagne à une date » n'est utilisé par **aucune fonction de
Polenta** : c'est un script de la bibliothèque projet livrée par #74 (`campaignTimeline`), pas du
code de Polenta. Même chose pour le **rattrapage des données existantes** (§6.2) : la règle de
repli est spécifiée ici, implémentée côté projet.

### État du code (vérifié sur `main` @ ee2a32d)

- `CampaignTestRun.status / runId / executedAt / executedBy` sont **écrasés** à chaque saisie
  (`CampaignsService.updateRun`).
- Les fichiers `test-runs/<TEST>/<runId>.yaml` sont ajoutés, jamais réécrits (`TestsService.execute`),
  dans le repo du test (composant éventuel) — l'historique des verdicts existe sur disque.
- `TestRun.campaignRunId` vaut **toujours `null`** (`tests.service.ts`) et n'est **lu nulle part**.
- Deux chemins créent un run depuis une campagne, chacun en deux appels (`tests.execute` puis
  `campaigns.updateRun(…, run.id)`) :
  - page d'exécution (`campaign.$campaignId_.execute.$testId.tsx`) ;
  - import du classeur d'exécution (`CampaignExecutionService.apply`, GH36).
- `updateRun` accepte un `runId` optionnel ; seuls les specs e2e (GH64, GH65, GH69, GH71) l'appellent
  sans run.
- Pas de date d'ajout d'une entrée. `removeEntries` **supprime** l'entrée du fichier.
- Numérotation des `entryId` : `lastEntrySuffixes(existingRuns)` (correction #66, plus grand suffixe).
- ~14 fichiers lisent `campaign.runs` (page campagne, liste des campagnes, exécution, relecture,
  exports, classeur Excel GH36, report GH64, sélecteur, moteur SQL `campaign_entries`,
  traçabilité, MCP `list_campaigns`…).
- Historique du statut de campagne : déjà fourni par GH77 (`history.status` :
  `planned` → `in_progress` → `completed` / `abandoned`).

## Décisions de cadrage (validées le 2026-10-13)

| Question | Décision |
|---|---|
| Où conserver les entrées retirées ? | Dans une **liste séparée** `removedRuns[]` du fichier de campagne ; `runs` garde son sens « entrées actives » |
| Format du rattachement run → entrée | Champ structuré **`campaignEntry: { campaignId, entryId }`** sur `TestRun`, qui **remplace** `campaignRunId` |
| Statut d'entrée sans run (`updateRun` sans `runId`) | **Interdit** : chaque verdict d'entrée correspond à un fichier `test-runs/` daté |
| Rattrapage des données existantes | **Côté projet** (#74) : Polenta n'écrit des faits exacts que pour les nouvelles données ; la règle de repli est spécifiée en §6.2 |
| Nouveau journal d'événements | Non : les fichiers `test-runs/` en tiennent lieu (ajout seul, un fichier par run, pas de conflit git entre testeurs) |
| Historique du statut de campagne | Mécanisme générique GH77, rien de propre aux campagnes |

## 1. Rattachement d'un run à son entrée de campagne

### 1.1 Modèle

`TestRun` :

| Attribut | Avant | Après |
|---|---|---|
| `campaignRunId` | `string \| null`, toujours `null` | **retiré du type** ; ignoré à la lecture des fichiers existants (`campaignRunId: null`), plus écrit |
| `campaignEntry` | — | `{ campaignId: string; entryId: string }` — **optionnel** : présent si et seulement si le run a été créé depuis une entrée de campagne ; absent pour une exécution isolée et pour les runs antérieurs à GH73 |

Même forme que `CarriedFrom` (GH64) : un type partagé `CampaignEntryRef { campaignId; entryId }`
dans `@polenta/types` (`CarriedFrom` peut en devenir un alias — au choix du Design).

### 1.2 Écriture

- `ExecuteTestCaseDto` reçoit un `campaignEntry?` ; `TestsService.execute` l'écrit tel quel dans le run.
- **Page d'exécution** : passe `{ campaignId, entryId }` de l'instance exécutée.
- **Import Excel (GH36)** : `CampaignExecutionService.apply` passe `{ campaignId, entryId }` de
  chaque instance importée.
- Le run est écrit dans le repo du test (composant éventuel), la campagne dans le repo ouvert :
  `campaignId` désigne une campagne **du repo produit** qui a lancé l'exécution. Pas de chemin de
  repo dans la référence (comme `carriedFrom`).
- Le run est immuable (SPEC-TESTS §3.1) : `campaignEntry` n'est jamais réécrit, même si l'entrée
  est retirée ensuite.

### 1.3 Cohérence avec l'entrée

`CampaignTestRun.runId` reste la référence vers le **dernier** run de l'entrée (inchangé, utilisé
par la relecture). Les runs **antérieurs** de l'entrée ne sont retrouvables que par
`campaignEntry` — c'est le fait brut qui permet la reconstruction.

## 2. Date d'ajout d'une entrée — `addedAt`

- Nouveau champ `CampaignTestRun.addedAt: string` (ISO 8601, instant de l'ajout), posé par **tous**
  les chemins qui créent une entrée :
  - sélection initiale de `create()` (= `createdAt` de la campagne) ;
  - `addTests()` (ajout groupé, dont tests non approuvés GH68 et instances par exigence T179) ;
  - `duplicateTest()` ;
  - report depuis une autre campagne (GH64, `buildCarriedRuns`) — date du report, **pas** la date
    d'ajout dans la campagne source.
- Jamais modifié ensuite (ni par l'exécution, ni par `updateRunParams`, ni par la
  resynchronisation GH68 `refreshEntries`).
- Optionnel dans le type (entrées antérieures à GH73) ; **aucun backfill** écrit ni calculé à la
  lecture par Polenta (repli : §6.2).

## 3. Entrées retirées — `removedRuns`

### 3.1 Modèle

- Nouveau champ `TestCampaign.removedRuns?: CampaignTestRun[]` — absent tant qu'aucune entrée n'a
  été retirée (pas de `removedRuns: []` écrit).
- Nouveau champ `CampaignTestRun.removedAt?: string` — présent uniquement sur les entrées de
  `removedRuns`.

### 3.2 `removeEntries()`

- Garde inchangée : refusé sur une campagne `completed` / `abandoned`.
- L'entrée retirée **sort de `runs`** et est **ajoutée à la fin de `removedRuns`**, complète
  (copie `testSnapshot`, paramètres, statut, `runId`, `executedAt`… tels quels) avec
  `removedAt` = maintenant. Retirer une entrée déjà exécutée reste permis (comme aujourd'hui) : son
  dernier état est conservé.
- `testCaseIds` : inchangé (une occurrence retirée par entrée retirée) — il ne reflète que les
  entrées actives.
- Un `entryId` absent de `runs` est ignoré (comme aujourd'hui) — y compris un `entryId` déjà dans
  `removedRuns` (pas de double retrait, `removedAt` non réécrit).
- Pas de restauration d'une entrée retirée : on ré-ajoute le test (nouvelle entrée, §3.3).

### 3.3 Effets sur le reste de l'application

Principe : **tout lecteur de `runs` ignore les entrées retirées sans modification**, puisqu'elles
n'y sont plus. Seuls deux points doivent prendre `removedRuns` en compte :

1. **Numérotation des `entryId`** (#66) : le plus grand suffixe est calculé sur `runs` **et**
   `removedRuns` — un `entryId` n'est **jamais réutilisé** dans une campagne, même après retrait
   (sinon un run rattaché par `campaignEntry` serait attribué à la mauvaise instance).
   Concerne `buildNewRuns`, `buildCarriedRuns`, `duplicateTest`.
2. **Backfill des `entryId` pré-T97** (`ensureEntryIds`) : inchangé, il ne s'applique qu'à `runs`
   (une campagne pré-T97 n'a pas de `removedRuns` ; une entrée retirée a toujours un `entryId`
   puisque le retrait passe par `get()`, qui backfille avant). **À vérifier en Design** : le
   backfill étant en mémoire, une campagne pré-T97 dont une entrée est retirée voit son fichier
   réécrit avec les `entryId` backfillés — les positions changent après retrait ; il faut que la
   réécriture fige les `entryId` de **toutes** les entrées restantes (c'est le cas si `persist`
   écrit l'objet backfillé).

Écrans et fonctions qui **ne voient pas** les entrées retirées (par construction) : page campagne
(liste, pastilles, filtres, bandeaux GH68/T171), liste des campagnes, exécution et relecture
(`/campaign/$id/execute|run/$entryId` → « entrée introuvable » pour une entrée retirée, comme
aujourd'hui), exports plan/rapport (xlsx/docx/pdf, gabarits GH34), classeur d'exécution GH36
(export et import : une instance retirée entre l'export et l'import est une « instance absente de
la campagne », erreur par instance déjà prévue), report GH64 (onglet « Depuis une campagne » :
une entrée retirée de la source n'est pas proposée ; une entrée retirée de la cible n'est pas
« Déjà présent » → le test peut être reporté à nouveau), déduplication `addTests` / T179 / `carryKey`
(une entrée retirée ne bloque pas le ré-ajout), `refreshEntries` GH68, table SQL `campaign_entries`
et dashboards, traçabilité.

Exposées **telles quelles** (données brutes) : fichier YAML, MCP `list_campaigns` (renvoie l'objet
campagne complet, donc `removedRuns`), et le futur graphe #74.

## 4. Saisie d'un résultat sans run : interdite

- `CampaignsService.updateRun(repoPath, campaignId, entryId, status, runId, meta?)` : `runId`
  devient **obligatoire** ; appel sans `runId` (ou `runId` vide) → erreur, rien n'est écrit.
- `status` doit être un résultat de run (`PASS` / `FAIL` / `BLOCKED` / `INCOMPLETE`) : `pending`
  est refusé (aucune fonction ne remet une entrée à `pending` aujourd'hui).
- Pas de vérification croisée du fichier de run (il peut vivre dans un autre repo) : l'appelant
  crée le run puis met à jour l'entrée, comme aujourd'hui.
- Signatures alignées : IPC `campaigns:update-run`, `api-client` (`updateRun(…, runId: string)`),
  politique du client web inchangée.
- Les specs e2e GH64 / GH65 / GH69 / GH71 qui appellent `campaigns:update-run` sans run passent par
  `tests:execute` (avec `campaignEntry`) puis `campaigns:update-run` avec le `runId` obtenu — un
  utilitaire e2e commun au choix du Design.

## 5. Historique du statut de campagne

Rien à développer : `history.status` (GH77) trace `planned` (création), `in_progress` (premier
résultat), `completed` / `abandoned` (clôture), y compris pour les campagnes antérieures (entrée
implicite / reprise git GH77). Les entrées de `runs` / `removedRuns` n'ont pas d'historique propre :
leur chronologie est portée par `addedAt`, `removedAt` et les runs rattachés.

## 6. Faits disponibles pour la reconstruction (contrat pour `campaignTimeline`, #74)

Cette section ne décrit **pas** du code Polenta : elle fixe les faits que la bibliothèque projet
(#74) peut exploiter, et la règle de repli des données antérieures, pour que #74 n'ait pas à les
redécouvrir. Elle sera reprise dans SPEC-TESTS §4.2.

### 6.1 Données GH73 et postérieures

Pour une entrée `e` d'une campagne `c` (dans `runs` ou `removedRuns`) :

- **Présence** : `e` compte dans la campagne sur `[e.addedAt, e.removedAt)` (`removedAt` absent =
  toujours présente).
- **Runs de l'entrée** : tous les `TestRun` tels que `campaignEntry = { campaignId: c.id, entryId: e.entryId }`,
  datés par `TestRun.executedAt` (date saisie par le testeur pour un import Excel GH36, sinon
  instant de l'exécution).
- **Statut à une date `d`** : résultat du dernier run de l'entrée tel que `executedAt ≤ d` ; aucun →
  `pending`.
- **Statut de la campagne à `d`** : `valueAt(c, 'status', d)` sur `history` (GH77).

### 6.2 Données antérieures à GH73 — règle de repli (approximative, signalée comme telle)

- `addedAt` absent → `c.createdAt`.
- Entrée retirée avant GH73 : perdue (le fichier ne la contient plus) — limite connue.
- Run sans `campaignEntry` :
  - le run référencé par `e.runId` est rattaché à `e` (exact) ;
  - un autre run est rattaché à `e` (approximatif) s'il porte sur le même test (`testCaseId`) et la
    même exigence (`requirementId`, absent = absent) et que
    `c.createdAt ≤ run.executedAt ≤ date du run e.runId` ;
  - plusieurs entrées candidates (même test dans deux instances paramétrées, ou deux campagnes qui
    se chevauchent) → le run n'est rattaché à **aucune** (ambigu), plutôt que mal attribué.
- Les valeurs issues du repli sont marquées (ex. `approximate: true`) dans la sortie du script.

### 6.3 Fuseau horaire

Polenta stocke des **instants** ISO 8601 (`addedAt`, `removedAt`, `executedAt`) ; il ne découpe pas
par jour. Le découpage (UTC ou heure locale) est un paramètre du script projet. La colonne SQL
`executedDay` (UTC) n'est pas modifiée ici ; elle disparaît avec #74.

### 6.4 Étapes de préparation dans le temps (hors périmètre, faits vérifiés)

L'interprétation (ex-règle GH71) est côté projet. Faits nécessaires, déjà disponibles :
`history.status` du test live (GH77), statut d'approbation (`isApproval`), `addedAt`, runs
rattachés, et la règle GH68 (tant que l'entrée est `pending`, sa copie non approuvée et la campagne
ouverte, la préparation suit le test **live**). La **date des resynchronisations** de copie n'est
donc **pas nécessaire** : pas de nouveau champ.

## 7. Cas limites

| Cas | Comportement attendu |
|---|---|
| Retrait puis ré-ajout du même test | Nouvelle entrée, nouvel `entryId` (suffixe > tous ceux de `runs` et `removedRuns`), nouvel `addedAt` ; l'ancienne reste dans `removedRuns` avec ses runs rattachés |
| Retrait d'une entrée exécutée | Conservée dans `removedRuns` avec son dernier statut et `runId` ; ses runs gardent leur `campaignEntry` |
| Exécution en cours sur une entrée retirée entre-temps | Le run est écrit (avec `campaignEntry`), puis `updateRun` échoue « entrée introuvable » (comportement actuel) ; le run orphelin reste sur disque, rattaché à une entrée retirée — cohérent avec `removedAt` |
| Import Excel d'une instance retirée depuis l'export | Erreur par instance « absente de la campagne » (GH36 inchangé), aucun run créé |
| Ré-exécution d'une entrée (retest) | Nouveau run avec le même `campaignEntry` ; l'entrée pointe sur le dernier, les précédents restent rattachés |
| Report GH64 d'une entrée | La nouvelle entrée a son propre `addedAt` et ses propres runs ; les runs de l'entrée source restent rattachés à la source (`carriedFrom` relie les deux) |
| Campagne renumérotée par « Garder les deux » (GH37) | Les `campaignEntry.campaignId` des runs (autre fichier, éventuellement autre repo) ne sont pas renumérotés — **à évaluer en Design** (`merge-core/renumber.ts`) ; à défaut, limite connue documentée |
| Exécution isolée (hors campagne) | Pas de `campaignEntry` |
| Campagne pré-T97 (sans `entryId`) dont on retire une entrée | `entryId` backfillés figés à la réécriture (§3.3 point 2) |
| `updateRun` sans `runId`, ou avec `pending` | Refusé, fichier inchangé |

## 8. Critères d'acceptation

1. Exécuter une entrée depuis la page d'exécution écrit un run avec
   `campaignEntry: { campaignId, entryId }` de cette entrée ; aucun run n'écrit plus `campaignRunId`.
2. Importer un classeur d'exécution (GH36) écrit, pour chaque instance importée, un run avec le
   `campaignEntry` de l'instance.
3. Deux exécutions successives de la même entrée produisent deux runs portant le même
   `campaignEntry` ; l'entrée référence le second (`runId`).
4. Toute entrée créée par `create`, `addTests`, `duplicateTest` ou un report GH64 porte `addedAt` ;
   à la création, `addedAt` des entrées initiales = `createdAt` de la campagne.
5. `removeEntries` déplace l'entrée de `runs` vers `removedRuns` avec `removedAt` ; le fichier n'a
   pas de `removedRuns` tant que rien n'a été retiré.
6. Après retrait de `TEST-0002-1` et `TEST-0002-2` puis ajout d'une instance de `TEST-0002`, la
   nouvelle instance est `TEST-0002-3`.
7. Une entrée retirée n'apparaît ni dans la page campagne, ni dans ses pastilles et filtres, ni
   dans les exports plan/rapport, ni dans le classeur d'exécution, ni dans l'onglet de report GH64,
   ni dans `campaign_entries` ; elle ne bloque pas le ré-ajout du même test.
8. `campaigns:update-run` sans `runId`, ou avec le statut `pending`, est refusé et n'écrit rien.
9. Les campagnes et runs existants (sans `addedAt`, sans `campaignEntry`, avec `campaignRunId: null`)
   se lisent et s'affichent sans erreur ni réécriture.
10. `pnpm test` et les e2e web (dont GH64/65/69/71 adaptés au §4) passent.

## 9. Hors périmètre

- Calcul de l'état d'une campagne à une date, courbe empilée, découpage par jour : script
  `campaignTimeline` de la bibliothèque projet (#74).
- Rattrapage des données existantes (§6.2) : implémenté dans ce même script, pas dans Polenta.
- Étapes de préparation dans le temps (interprétation ex-#71).
- Affichage des entrées retirées ou de l'historique des runs d'une entrée dans l'UI.
- Restauration d'une entrée retirée.
- Couverture test ↔ exigence : le dernier run d'un test compte quelle que soit sa campagne (ou
  l'état de son entrée) — inchangé.
- `addedBy` / `removedBy` (non demandés ; l'auteur reste lisible dans git).

## Indicateur : décision Polenta / côté projet

Le ticket introduit **aucun indicateur** dans Polenta. « État d'une entrée / d'une campagne à une
date » et le rattrapage des données antérieures ne servent à aucune fonction de Polenta
(SPEC-TECH-stack §1.1) → **côté projet**, bibliothèque #74. Polenta n'ajoute que des faits bruts :
`TestRun.campaignEntry`, `CampaignTestRun.addedAt`, `TestCampaign.removedRuns` / `removedAt`.
