# GH74 — Suivi : remplacer SQL par un graphe de données JSON, des scripts JS isolés et un rendu Vega-Lite (vue temporelle des campagnes)

## Contexte

Chaque nouveau besoin d'indicateur client devient aujourd'hui du développement dans Polenta : nouveau
type de widget (matrice GH69), nouvelle table ou colonne SQL (`campaign_entries` GH65, étapes de
préparation GH71), migration de seed. Le prochain besoin connu est une **vue temporelle de
l'avancement des campagnes** (courbe empilée des statuts d'entrée par date), rendue possible par
GH73 (runs rattachés, `addedAt`, `removedRuns`) et GH77 (`history`).

Objectif : Polenta **rend les données accessibles** ; la mise en forme propre à chaque client vit
dans le repo du client, écrite le plus souvent par l'IA via le serveur MCP. SQL est retiré : il
impose d'aplatir des données imbriquées (campagne → entrées → runs) et sa maîtrise est trop rare.

### Principe « données brutes » (GH79, SPEC-TECH §1.1)

Polenta expose les données brutes du modèle et les seuls indicateurs qui servent à ses propres
fonctions. Décisions pour les indicateurs touchés par ce ticket :

| Indicateur | Sert-il à une fonction de Polenta ? | Décision |
|---|---|---|
| `coverageStatus` | Oui (matrice de traçabilité, analyse d'impact, badges) | Dans le graphe |
| `needsRevalidation` | Oui (T172) | Dans le graphe |
| `isApproval` (schéma) | Oui (verrouillage, pastille « Non approuvé » GH68) | Dans le graphe (schéma) |
| Resynchronisable (GH68) | Oui (resynchronisation des copies) | Dans le graphe (`entry.resyncable`) |
| Maturité (`maturity*`) | Non (dashboards seulement) | Retiré de Polenta → `dashboards/lib/maturity.js` |
| Étape d'avancement (`progress`, `progressRank`, `testStatus`, GH71) | Non | Retiré de Polenta → `dashboards/lib/campaign.js` |
| État d'une campagne à une date | Non | `campaignTimeline` dans `dashboards/lib/campaign.js` |
| Dernier résultat d'un test | Non | `lastResult` dans `dashboards/lib/campaign.js` (affichage en vue : #70) |
| `isEarsCompliant`, `isFilled` | Oui (import en masse, résolution de conflits) | Restent dans Polenta (hors graphe) |

## 1. Graphe de données (contrat v1)

### 1.1 Contenu

Le graphe est un document JSON construit par le main à partir des index en mémoire, sur le même
périmètre que le dataset actuel : repo ouvert + composants du workspace (`WorkspaceTreeService`).
Racine `PolentaGraph` (base : `spikes/GH78/contract.ts`, ajusté au Design) :

- `contractVersion: 1`, `generatedAt` ;
- `repos[]` : `name`, `label`, `isRoot` ;
- `components[]` : `name`, `label`, `repo` (nœuds locaux et repos composants — libellés manquants
  signalés par #78) ;
- `schema` : `objectTypes[]` (repo, ref, composant, label, prefix, category, champs avec type /
  valeurs / required / trackHistory, statuts ordonnés avec `isApproval` / `isTerminal`), `linkTypes[]`,
  `entryStatuses[]` et `campaignStatuses[]` (statuts fixes : `name`, `label` dans la langue de
  l'utilisateur, `order` d'affichage canonique `pending`, `INCOMPLETE`, `BLOCKED`, `FAIL`, `PASS`, et
  pour les entrées `severity` = règle « pire statut » actuelle `FAIL > BLOCKED > INCOMPLETE > pending
  > PASS`, `lib/runStatus.ts`) ;
- **Un type se désigne par le couple (`repo`, `objectTypeRef`)** : `root::…` n'est pas unique entre
  repos (chaque repo a son schéma). `repo` est porté par chaque objet et chaque type ;
- `requirements[]`, `tests[]` : `id`, `repo`, `component`, `objectTypeRef`, `title`, `status`,
  `version`, `fields` (tels que stockés), `history` (`{}` si vide, entrées implicites comprises,
  GH77 §7), `needsRevalidation`, `createdAt/By`, `updatedAt/By` (git log). Exigences : `coverageStatus`
  (calcul `TraceabilityService.computeCoverage` sur le graphe agrégé, inchangé). Tests : pas de
  `steps` / `preconditions` / `postconditions` en v1 (HTML volumineux, aucun indicateur ne s'en sert —
  #78 §8 ; ajout possible dans la majeure) ;
- `links[]` : `id`, `type`, `sourceId`, `targetId`, `repo`, `createdAt`, `createdBy` ;
- `campaigns[]` : champs de la campagne (`status`, `fields`, `history`, `baselineRef`, `component`,
  `level`, `createdAt`, `completedAt` = instant de clôture, `completed` **ou** `abandoned`, `null`
  sinon), `entries[]` (actives) et `removedEntries[]` (GH73, avec
  `removedAt`). Une entrée : `entryId`, `testCaseId`, `requirementId`, `status`, `addedAt`, `runId`,
  `executedAt`, `executedBy`, `carriedFrom`, `snapshot` (`title`, `status`, `version` de la copie
  `testSnapshot`, `null` si absente), `resyncable` (règle GH68) ;
- `runs[]` : toutes les exécutions (`test-runs/`), campagne ou non : `id`, `testCaseId`, `repo`,
  `campaignEntry` (GH73), `requirementId`, `result`, `executedAt`, `executedBy`, `duration`,
  `origin`. Le détail des pas (`stepResults`) n'est pas exposé en v1 (ajout possible dans la majeure).
  Depuis GH73 tout verdict d'entrée a son run ; les entrées antérieures peuvent n'en avoir aucun
  (repli GH73 §6.2, dans la bibliothèque).

Dates : ISO 8601 UTC. Le découpage en jours est fait par le script, dans le fuseau
`polenta.timezone` (§2.1). IDs uniques sur le projet. Aucune colonne dérivée de suivi (§Principe).

### 1.1b Cache

Le graphe est construit une fois par workspace et **gardé en cache** (387 ms à chaud sur ×50,
#78 §3.1), invalidé par tout changement d'index (exigences, tests, liens, campagnes, runs, schéma,
changement de ref) — mêmes événements que l'invalidation actuelle des résultats de widget (SPEC-
DASHBOARDS §6.1). Le contexte du bac à sable préparé à partir de ce graphe suit la même
invalidation (§2.3).

### 1.2 Versionnement du contrat

- Une **version majeure** (`contractVersion`), déclarée par chaque script (§2.1).
- Dans une majeure : **ajouts seulement** (champs, collections). Renommer ou supprimer = nouvelle
  majeure ; l'ancien champ reste présent et marqué `@deprecated` dans le `.d.ts` pendant au moins une
  version mineure de l'app.
- Un script qui déclare une majeure que l'app ne sait pas produire → erreur visible « contrat v{N}
  non pris en charge par cette version de Polenta » (pas d'exécution).

### 1.3 Publication des types

- Source unique : `packages/types/src/graph.ts` (types TypeScript, commentaires JSDoc = documentation
  du contrat).
- Fichier dérivé `dashboards/lib/polenta.d.ts` (types du graphe + signature `PolentaHost` + type
  `Row`) et `dashboards/jsconfig.json` (`checkJs`, `module: esnext`) écrits dans le repo au premier
  seed ; mis à jour par le mécanisme de proposition (§6.3).
- Documentation : nouvelle section SPEC-DASHBOARDS « Graphe de données », lue par l'outil MCP
  `get_data_contract` (§9).

## 2. Script de données (ex-requête)

### 2.1 Forme

```js
// @polenta contract 1
import { campaignTimeline } from 'lib/campaign.js'

export default function (data, polenta) {
  return [ /* lignes */ ]
}
```

- Module ES ; export par défaut `(data: PolentaGraph, polenta: PolentaHost) => Row[]` (synchrone).
- Première ligne `// @polenta contract <N>` (absente → 1).
- `PolentaHost` v1 : `locale` (`fr` | `en`), `timezone` (fuseau IANA de l'utilisateur, ex.
  `Europe/Paris`), `today` (date du jour `AAAA-MM-JJ` dans ce fuseau), `contractVersion`, `drill`
  (`null`, sauf relance pour un drill-down à la demande, §4). Rien d'autre (pas d'accès au disque, au
  réseau, aux timers).
- `Row` = objet plat de valeurs JSON scalaires (chaîne, nombre, booléen, `null`) ; une colonne
  réservée **`_ids: string[]`** (IDs des objets dont la ligne provient, §4), facultative mais, si
  présente, un tableau de chaînes. Toute autre valeur non scalaire → erreur « ligne {i}, colonne {c} :
  valeur non scalaire ». Un script qui renvoie une promesse (fonction `async`) → message dédié
  « Le script doit être synchrone ».
- **L'agrégation se fait en JS, jamais dans la spec** : un `aggregate` (ou `bin` / `timeUnit`
  agrégeant) de Vega-Lite perd `_ids` (#78 §5). Un script de données partagé renvoie de préférence
  une ligne par objet ; le regroupement propre à un widget se fait dans sa **transformation** (§3),
  qui fait l'union des `_ids` des lignes regroupées.
- Colonnes du résultat : union ordonnée des clés dans l'ordre de première apparition ; type déduit
  (`string` / `number` / `boolean` / `date` si chaîne ISO) comme `QueryResultColumn` aujourd'hui.

### 2.2 Imports

- `lib/<module>.js` → `dashboards/lib/<module>.js` du repo du script.
- `<composant>::lib/<module>.js` → `dashboards/lib/<module>.js` du composant déclaré (même résolution
  de nom que les références de paramètres T171). Composant inconnu ou fichier absent → erreur
  d'import nommant la référence.
- Un module de bibliothèque importe par les mêmes formes, ou par un chemin relatif (`./x.js`) qui
  reste dans le même `dashboards/lib/`. Aucune autre forme d'import (sortie de `lib/` par `..`, URL,
  `os`, `std`, `fs`, paquet npm) → erreur « Module introuvable : … ».

### 2.3 Exécution

- **QuickJS** (`quickjs-emscripten-core` + `@jitl/quickjs-wasmfile-release-sync` ; variante
  `quickjs-ng` écartée, 25–35 % plus lente). Aucun accès aux fichiers, au réseau, à `require` /
  `process` / `fetch` / timers / `console` ; données gelées (lecture seule).
- **Exécution dans le process main, hors de son thread principal** (`worker_threads` ou
  `utilityProcess`, choix au Design) — jamais dans le renderer. QuickJS est synchrone : un script qui
  va jusqu'à sa limite ne doit bloquer ni l'IPC ni le serveur web. Même moteur pour l'app desktop, le
  serveur web (#44) et le serveur MCP ; le renderer ne reçoit que des lignes.
- **Contexte préparé en cache** par workspace : graphe injecté et gelé, intrinsèques et objet global
  gelés (durcissement : un widget ne laisse aucune trace au suivant), modules de bibliothèque
  compilés. Invalidé avec le graphe (§1.1b) **et** à toute modification de `dashboards/lib/`. Les
  widgets d'un dashboard partagent ce contexte.
- **Limites par défaut** : 64 Mo par runtime ; mémoire wasm **plafonnée à 128 Mo par module**
  (`WebAssembly.Memory` bornée — `setMemoryLimit` seul laisse monter le process à 2 Go, #78 §3.4) ;
  **2 s** par exécution ; pile 256 Ko (taille sûre à revérifier dans le worker retenu). Module
  recréé après un dépassement mémoire ou un abandon. Dépassement → erreur « délai dépassé » /
  « mémoire dépassée » / « pile dépassée ».
- Chargement paresseux de QuickJS (`import()` mémoïsé, comme `alasql` aujourd'hui), `.wasm` livré à
  côté des bundles main, serveur web et MCP.

### 2.4 Erreurs

Toute erreur (syntaxe, import, exécution, limite, ligne non scalaire, contrat) s'affiche **dans le
widget et dans la vue Requêtes** : message, fichier (`script.js`, transformation `<widgetId>.js` ou
module de bibliothèque) et numéro de ligne. Jamais un graphe vide. Un résultat vide (`[]`) reste
l'état vide actuel.

## 3. Widget

- Champs conservés : `id`, `title`, `queryId`, `size` (`sm` / `md` / `lg`), ordre dans le dashboard.
- **Transformation** (facultative) : module JS de même forme que le script de données, mais
  `export default function (rows, polenta) { … }` — `rows` = lignes du script (gelées), même
  `PolentaHost`, mêmes imports de bibliothèque, mêmes limites (le budget de temps couvre script +
  transformation), mêmes contrôles de sortie (§2.1). Elle regroupe (catégorie × série → nombre,
  somme, pire statut…) en faisant l'union des `_ids`, trie, renomme. Absente : la spec reçoit les
  lignes du script telles quelles. Les lignes d'un script partagé par plusieurs widgets ne sont
  calculées qu'une fois par rafraîchissement.
- **Spec Vega-Lite** (JSON) dont la source de données est nommée : `"data": { "name": "rows" }` ;
  l'app y injecte les lignes transformées. Les `datasets` / `url` externes sont refusés (erreur
  visible). La spec n'agrège pas (§2.1) : un `aggregate` déclenche un avertissement dans l'éditeur et
  dans les validations MCP (rendu quand même, drill-down indisponible sur ces marques).
- Rendu dans le renderer (chunk paresseux `vega-embed` + `vega-lite` + `vega` + `vega-interpreter`,
  ~290 Ko gzip), **sans `eval`** : `ast: true` + interpréteur d'expressions (vérifié Electron 31 et
  Chromium 156 par #78). L'app n'a pas de CSP aujourd'hui ; en ajouter une relève de #88.
- **Thème** : une spec désigne ses couleurs par jeton (`"var(--status-success-solid)"`) ; l'hôte les
  remplace par les valeurs du thème courant et construit la `config` Vega depuis les jetons (`ink`,
  `edge`, `activity-fg` pour axes et légendes, `surface` pour le fond, `chart-series-1…8` pour la
  palette catégorielle). Changement de thème → recompilation. Une couleur littérale est respectée.
- `type` du widget remplacé par le **modèle** d'origine (§4) ou `custom`.
- Erreur de spec (JSON invalide, schéma Vega-Lite non respecté, champ absent des lignes) : message
  dans le widget.
- Le type n'est jamais contraint par la forme des lignes (comme aujourd'hui) ; aperçu live dans la
  popup de configuration.

## 4. Drill-down et navigation

Règle unique, sans réécriture de requête. Aucun nom de paramètre de sélection Vega-Lite n'est
imposé à la spec :

1. Clic sur une marque → l'hôte lit `item.datum` (écouteur `click` de la vue Vega).
2. Le `datum` porte `_ids` → ces objets.
3. Sinon, **IDs à la demande** (séries longues : `_ids` sur chaque point d'une série temporelle
   double le temps d'exécution et pèse 1,9 Mo sur ×50, #78 §3.3) : l'hôte relance la chaîne
   script + transformation avec `polenta.drill` = colonnes scalaires du `datum` ; la chaîne renvoie
   alors la ou les lignes correspondantes **avec** `_ids`. Les modèles de série temporelle (§7)
   gèrent `polenta.drill`.
4. Ni `_ids` ni relance utile → « Détail non disponible : le script ne fournit pas d'identifiants ».
5. Popup « Détail » (`DrillDownModal`) : un objet par ID (ID, type, titre, statut), clic → ouverture
   dans un nouvel onglet (exigence, test, campagne ; une entrée de campagne s'identifie par
   `CAMP-xxxx/<entryId>` → page d'exécution si exécutée, sinon page de campagne filtrée sur son
   statut brut). Pas de lien d'objet pour un ID inconnu : « Objet introuvable ».
6. Widget table : clic sur une ligne porteuse d'un seul ID → ouverture directe.

KPI : clic → union des `_ids` des lignes transformées. Rien de cliquable dans l'aperçu ni en
impression.

  l'utilisateur enregistre l'objet. Aucune réécriture en masse au lancement.
- Fichier d'une `formatVersion` supérieure à celle connue → affiché **en lecture seule** avec le
  message « Créé par une version plus récente de Polenta », jamais réécrit, jamais d'échec du listing.

  - requête *builder* → convertie en script du modèle « Liste filtrée » (§7) avec les mêmes

    (§7 : transformation + spec), `preset: campaignProgress` → barres empilées standard (le
    préréglage disparaît) ;
  - seeds connus : §8.

## 6. Bibliothèque projet

### 6.1 Contenu de départ (livré par Polenta, copié au seed)

- `history.js` : `valueAt(obj, champ, date)`, `timeline(objets, champ, { from, to, step })` (GH77).
- `campaign.js` : `campaignTimeline(campaign, runs, { from, to, step })` (état de chaque entrée à
  chaque date, règle de repli GH73 §6.2 pour les données antérieures), `entryStep(entry, data)`
  (ex-règle GH71 `campaign-progress`, sur les faits bruts : statut d'entrée, `snapshot`, test live,
  `resyncable`, `isApproval`), `lastResult(testId, data)` (#70).
- `maturity.js` : `maturity(requirement, data)` (5 critères de SPEC-DASHBOARDS §5.2, mêmes règles).
- `polenta.d.ts` (§1.3).

Chaque fichier livré commence par un en-tête `// @polenta-lib <id> <version>` ; les fonctions
exportées sont documentées en JSDoc typé (vérifiables par `checkJs`).

**Écrite pour la performance** (QuickJS est 5 à 30 fois plus lent que V8, #78 §3.3) : balayage
unique des événements triés, sans rescanner le graphe par date ni par campagne. Repère : une
première version de la timeline prenait 1 290 ms sur ×50, la version à balayage unique 160 ms.
Testée sur le jeu ×50 du corpus (§12).

### 6.2 Seed de la bibliothèque

Au premier accès à Suivi sur un repo inscriptible (même garde de branche que le seed Status), si
`dashboards/lib/` est absent : copie du contenu de départ, comme une modification normale à publier.
Un fichier supprimé par le projet n'est jamais recréé (marqueur `dashboards/.seeded.yaml`, étendu).

### 6.3 Propositions de mise à jour

- Polenta embarque, pour chaque fichier livré (bibliothèque, `polenta.d.ts`, `jsconfig.json`,
  modèles des seeds §8), la liste des empreintes (SHA-256 du contenu normalisé en fins de ligne LF)
  de **toutes** ses versions livrées.
- Fichier du repo dont l'empreinte est celle d'une version livrée **antérieure** → mise à jour
  disponible. Empreinte inconnue (modifié par le projet) ou fichier absent → jamais proposé.
- **Bandeau** en tête du panneau Suivi : « Mises à jour disponibles (N) » → liste (fichier, version
  actuelle → nouvelle, résumé du changement) avec cases à cocher → « Appliquer ». Écriture normale,
  à publier. « Ignorer » masque cette version pour l'utilisateur (`.pref`).
- Sur une branche en lecture seule : bandeau affiché sans bouton « Appliquer ».

## 7. Modèles

Un modèle génère du code à partir d'un formulaire ; le client non technique ne voit pas de code.

- **Modèles de script** : « Liste filtrée » (reprend le builder : type d'objet, composant,
  conditions `= != > < contient dans`, ET / OU, regroupement → comptage), « Entrées de campagne »
  (une ligne par entrée, filtres statut de campagne / campagne), « Avancement dans le temps »
  (`campaignTimeline` : une ligne par date × statut d'entrée, campagne(s), pas `jour` / `semaine`).
- **Modèles de widget** — chacun génère une **transformation** (regroupement, union des `_ids`) et
  une **spec** : barres (groupées / empilées), camembert, courbe, KPI, table (colonnes), matrice
  (heatmap : lignes, colonnes, valeur ; « pire statut » selon `schema.entryStatuses[].severity`,
  mêmes couleurs que la page campagne), **aire empilée temporelle** (date × série, avec une couche
  de marques quasi transparentes au-dessus des aires pour rendre chaque point cliquable — une aire
  est une seule marque Vega, #78 §5 — et gestion de `polenta.drill`). Mesures proposées : nombre,
  somme, min, max, valeurs distinctes, pire statut. Le formulaire propose les colonnes des lignes du
  script choisi (comme le mapping actuel). Couleurs par jetons `var(--…)` (§3).
- Stockage : `template: { id, version, params, hash }`, `hash` = empreinte du code généré
  (script, ou transformation + spec pour un widget).
- Code ≠ `hash` → **personnalisé** : la popup n'affiche que le code (éditeur JS / JSON), mention
  « Personnalisé — le formulaire du modèle ne s'applique plus », action « Revenir au modèle »
  (confirmation : les modifications sont perdues) qui régénère depuis `params`.
- Un objet créé sans modèle (« Script vide », « Spec vide ») est personnalisé d'emblée.
- Une nouvelle version d'un modèle ne touche jamais un objet existant non personnalisé sans action :
  proposée via le bandeau (§6.3) pour les objets des seeds ; pour les autres, la popup indique
  « Nouvelle version du modèle disponible » et régénère à l'enregistrement.

## 8. Seeds

- **Status** (partagé) et **Campagnes** (privé, GH65) recréés en modèles (§7), mêmes widgets et
  mêmes règles de déclenchement / marqueurs. « Avancement par campagne » : barres empilées sur
  `entryStep` (bibliothèque) au lieu de `progress`.
- **Nouveau widget** au seed Campagnes : « Avancement dans le temps » (aire empilée, campagnes
  `in_progress`, pas journalier).
- Seeds existants : leurs requêtes et widgets, reconnus par leur contenu d'origine (SQL exact et
  mapping, comme la mise à niveau GH71), sont **réécrits** dans les nouvelles définitions au premier
  accès ; un objet modifié par l'utilisateur n'est pas touché (il tombe sous §5.3 : SQL non pris en
  charge). Le widget « Avancement dans le temps » est ajouté aux seeds Campagnes existants **via le
  bandeau** (proposition, pas d'ajout silencieux).
- La mise à niveau GH71 par comparaison de SQL (`upgrades`, `progressV2`) est retirée après cette
  réécriture.

## 9. Vue Requêtes, exports, impression

- `/query` : éditeur JS (CodeMirror, coloration JS) ou formulaire du modèle, bouton Exécuter, table des
  lignes, erreurs §2.4, sauvegarde, historique privé (texte du script). `QueryBuilder` et `SqlEditor`
  disparaissent.
- **Export Excel** : lignes produites par le script (colonnes §2.1, `_ids` exporté joint par « , »).
- Impression / PDF (`print.dashboard.tsx`) : rendu Vega en SVG, même grille.
- Export docx du dashboard (direct et gabarit) : un tableau des lignes du script de chaque widget
  (inchangé dans le principe).

## 10. Outils MCP

- `list_queries`, `run_query` (script enregistré → lignes ou erreur §2.4), `create_query` /
  `update_query` (titre, script, ou modèle + paramètres), `delete_query` : adaptés.
- `add_widget` / `update_widget` : transformation + spec Vega-Lite, ou modèle + paramètres ; autres
  outils dashboards inchangés dans leur rôle.
- **Nouveaux** : `get_data_contract` (types `.d.ts` + documentation du graphe, conventions `_ids`,
  agrégation en JS, `polenta.drill`, jetons de couleur), `test_script` (exécute un script non
  enregistré — ou un script enregistré suivi d'une transformation non enregistrée — sur les données
  réelles → lignes tronquées à 200 + nombre total, ou erreur avec fichier et ligne), `list_templates` (modèles et leurs paramètres), `list_library` / `read_library_module` /
  `write_library_module` (fichiers de `dashboards/lib/`, repo ouvert seulement).
- Validations MCP (`suivi-validation.util.ts`) : script exécuté à l'enregistrement, avertissement si
  erreur (l'enregistrement n'est pas bloqué), spec compilée par `vega-lite` (avertissement si
  `aggregate`). Vega 6 est ESM seul avec un `await` de premier niveau : il ne se bundle pas dans le
  serveur MCP actuel (CJS) → `import()` dynamique d'un module externe ou bundle MCP en ESM (Design).

## 12. Compatibilité et non-régression

- Contrat versionné (§1.2), format versionné avec migrations à la lecture et lecture seule (§5.3),
  erreurs visibles (§2.4, §3), bibliothèque et modèles versionnés par empreinte (§6.3).
- **Corpus de non-régression en CI** : repos fixtures (dont `scripts/demo-lave-linge` et un projet
  minimal, plus un jeu gonflé ×50 généré comme dans #78 pour la bibliothèque) + dashboards du seed ;
  chaque widget est exécuté (script + transformation) et ses lignes comparées à une référence JSON
  versionnée. Toute évolution du contrat ou d'un modèle apparaît dans le diff des références.
- **Budgets de performance** (vérifiés par le corpus, machine de CI) : avancement d'une campagne
  < 200 ms sur la démo et < 1 s sur ×50, contexte en cache (mesuré par #78 : 1,3 ms et 3,3 ms).
- Suppression de SQL sans migration des requêtes SQL (seul déploiement : 3 utilisateurs, aucune
  requête client). AlaSQL retiré des dépendances.

## Cas d'usage et comportements attendus

1. **Utilisateur non technique** crée un widget : choisit le modèle « Entrées de campagne » puis
   « Barres empilées » (catégorie campagne, série statut) → graphe sans voir de code.
2. **IA via MCP** : lit `get_data_contract`, écrit un script avec `test_script` jusqu'à obtenir les
   lignes voulues, crée la requête et le widget Vega-Lite.
3. **Vue temporelle** : widget « Avancement dans le temps » sur une campagne en cours → aire empilée
   pending / PASS / FAIL / BLOCKED / INCOMPLETE par jour depuis la création ; clic sur une couche à une
   date → popup des entrées concernées.
4. **Script en erreur** (champ renommé, exception) → le widget affiche le message et la ligne.
5. **Collègue avec une app plus ancienne** ouvre un dashboard `formatVersion: 2` → lecture seule
   avec message, fichier intact.
6. **Projet personnalise `campaign.js`** → aucune mise à jour proposée pour ce fichier ; les fichiers
   intacts restent proposés.
7. **Produit à composants** : un script importe `moteur::lib/mesures.js` du composant `moteur`.

## Critères d'acceptation

- [ ] AlaSQL, `QueryBuilder`, `SqlEditor`, le mode `sql` / `builder` d'exécution et la réécriture
      d'AST sont retirés ; aucune dépendance `alasql` dans `package.json`.
- [ ] Le graphe v1 contient les collections et champs de §1.1, sans colonne `maturity*` ni `progress*` ;
      `coverageStatus` d'une exigence est identique à la matrice de traçabilité sur le jeu de démo.
- [ ] `polenta.d.ts` + `jsconfig.json` permettent à `tsc --noEmit -p dashboards/jsconfig.json` de
      vérifier les scripts et la bibliothèque du seed sans erreur.
- [ ] Un script accédant à `fetch`, `require`, `process`, `setTimeout` ou un fichier échoue avec un
      message explicite ; une boucle infinie est interrompue en ~2 s ; une allocation massive
      échoue sans que la mémoire wasm dépasse 128 Mo ; une récursion infinie lève « pile dépassée »
      sans faire avorter le module ; pendant ces sondes, l'IPC et le serveur web restent réactifs
      (exécution hors du thread principal).
- [ ] Une variable globale ou un prototype modifié par un widget n'est pas visible du widget suivant
      (contexte durci) ; modifier `dashboards/lib/` ou une donnée invalide le contexte en cache.
- [ ] Une erreur de script ou de spec s'affiche dans le widget avec message et ligne (jamais vide).
- [ ] Les 6 types de widget actuels + l'aire empilée temporelle existent comme modèles ; les seeds
      Status et Campagnes affichent les mêmes informations qu'avant (sur `entryStep` pour l'avancement).
- [ ] Deux widgets différents (barres par statut, matrice test × campagne) partagent un même script
      d'entrées de campagne, chacun avec sa transformation ; le script n'est exécuté qu'une fois.
- [ ] Les couleurs `var(--…)` d'une spec suivent le thème clair / sombre.
- [ ] Un widget issu d'un modèle puis modifié à la main passe « personnalisé » ; « Revenir au modèle »
      régénère le code d'origine.
- [ ] Le drill-down (§4) ouvre les objets d'une marque portant `_ids`, et ceux d'un point de série temporelle par relance `polenta.drill`.
- [ ] Une requête builder historique s'ouvre convertie et donne les mêmes lignes ; une requête SQL
      historique affiche « non prise en charge » sans planter le listing.
- [ ] Un `dashboard.yaml` de `formatVersion` supérieure s'affiche en lecture seule et n'est jamais réécrit.
- [ ] Une ancienne version d'un fichier de bibliothèque est proposée dans le bandeau ; un fichier
      modifié ne l'est pas ; « Appliquer » produit une modification à publier.
- [ ] Import `<composant>::lib/x.js` fonctionne ; composant inconnu → erreur d'import nommée.
- [ ] Outils MCP §10 disponibles et documentés (SPEC-MCP-SERVER, AGENTS.md régénéré).
- [ ] Page campagne : pastilles par statut brut, plus de paramètre `progress` ; « Non approuvé » conservé.
- [ ] Export Excel et docx d'un widget / d'une requête portent les lignes du script ; l'impression PDF
      rend les graphes Vega.
- [ ] Corpus de non-régression exécuté en CI (`pnpm test`), références JSON versionnées.
- [ ] Fonctionne à l'identique dans l'app desktop et le client web (e2e web : remplacement des specs
      GH65 / GH69 par des scénarios GH74).
