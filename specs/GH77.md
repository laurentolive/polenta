# GH77 — Schéma : historique configurable des champs (statut suivi par défaut)

## Contexte

On veut suivre dans le temps la valeur de certains champs des objets (exigences, tests,
campagnes). Premier besoin : le statut, pour l'historique des campagnes (#73) et l'avancement de la
préparation des tests dans le temps. D'autres suivront côté exigences (statut, priorité…). #74
exposera `history` tel quel dans le graphe de données ; les fonctions qui l'exploitent
(`valueAt`, `timeline`, étapes de préparation ex-#71) sont des scripts de la **bibliothèque projet**
livrée par #74, pas du code de Polenta.

### Principe « données brutes » (décision du 2026-10-13, #79)

`history` est une **donnée brute** : Polenta l'enregistre, le fusionne et l'affiche tel quel. Il
n'en calcule aucun indicateur (état à une date, durée dans un statut, courbe…) : ce n'est utile à
aucune fonction de Polenta, donc c'est côté projet. La seule règle que Polenta applique est la
cohérence de la donnée elle-même : la valeur courante fait foi (§7).

Plutôt qu'un historique propre au statut, on ajoute un **mécanisme générique configuré dans le
schéma** : le client choisit les champs suivis, le statut l'est par défaut.

L'historique ne se reconstruit pas après coup (sauf reprise approximative depuis git) : à livrer tôt.

### État du code

- **Écritures d'objet**, toutes par `GitService.writeYaml` sur l'objet complet :
  - `RequirementsService` : `create`, `update`, `openDraft`, `transition`, `retargetObjectTypeRef` ;
  - `TestsService` : `create`, `update` (dont changement de statut direct), `openDraft` ;
  - `CampaignsService` : `create`, `update`, `updateRun` (passage auto `planned` → `in_progress`),
    `close`, et les autres mutations des entrées (`runs`) ;
  - `RevalidationService` : pose et retrait de `needsRevalidation` ;
  - serveur MCP (`bulk-import.tools.ts`) : passe par `requirements.create`, `tests.create`,
    `campaigns.create` ;
  - fusion de branches (`merge-core` `mergeObject`, `MergeResolutionService`) : écrit le résultat
    fusionné ;
  - les revues (`ReviewsService`) n'écrivent que `reviews/<id>.yaml`, jamais l'objet revu ;
  - pas d'import Excel d'exigences ou de tests ; l'import du classeur d'exécution (GH36) passe par
    `CampaignsService.updateRun`.
- **Identité** : `AuthService.projectUsername(repoPath)` (login du compte forge, sinon `local`) ;
  client web : login de la session ; MCP : `--user` / `POLENTA_USER` (`resolveUser`).
- **Champs système** : `needsRevalidation` (T172) est le précédent d'un champ posé par
  l'application seule ; `merge-core` `mergeUnit` le réconcilie sans conflit.
- **Campagnes** : statuts fixes (`planned`, `in_progress`, `completed`, `abandoned`) ; les
  `statuses` du schéma sont ignorés pour cette catégorie. Champs personnalisés dans `fields`.
- **Renommage d'un champ dans l'éditeur de schéma** : rien ne migre les objets. La valeur reste
  sous l'ancien nom, orpheline, et n'est plus affichée.
- **`scripts/check.py`** : référencé par `CLAUDE.md` et par le template, mais **absent de ce repo**.
  Il n'y a donc pas de script à modifier ici (cf. §8).

## Comportements attendus

### 1. Configuration dans `schema.yaml`

1. `ObjectTypeDefinition.trackStatusHistory?: boolean` — absent = `true`. Vaut pour les trois
   catégories, campagnes comprises (même si leurs statuts ne viennent pas du schéma).
2. `SchemaField.trackHistory?: boolean` — absent = `false`.
3. L'éditeur de schéma (`objectTypeEditor`) propose :
   - une case « Historiser le statut » sur le type, cochée par défaut ;
   - une case « Historiser » sur un champ, **seulement pour les types qui l'acceptent** (§3).
     Si le type d'un champ suivi devient incompatible, la case disparaît et `trackHistory` n'est
     plus écrit.
4. Écriture compacte : `trackStatusHistory` n'est écrit que s'il vaut `false`, `trackHistory`
   seulement s'il vaut `true` (même convention que `needsRevalidation`).

### 2. Format stocké

```yaml
history:
  status:
    - { value: draft,  at: 2026-09-02T08:10:00Z, by: lolive }
    - { value: review, at: 2026-09-20T14:02:00Z, by: lolive }
  priority:
    - { value: high, at: 2026-10-01T09:30:00Z, by: mdupont, source: mcp }
  statement:
    - { at: 2026-10-02T11:00:00Z, by: lolive }
```

1. `history` est un champ système **facultatif** au niveau racine de l'objet (à côté de `status`,
   `needsRevalidation`), absent tant qu'aucune entrée n'existe. Posé par l'application seule.
2. Clés : `status` pour le statut, `<nom du champ>` pour un champ de `fields`. Pas de collision
   possible avec un champ nommé `status`, qui vit dans `fields`.
3. Entrée :
   - `at` : date ISO 8601 UTC, à la seconde ;
   - `by` : login (§5) ;
   - `value` : **clé technique** (nom de statut, valeur d'enum, valeur brute), absent pour un type
     « événement seul » ;
   - `source` (facultatif) : `mcp`, `git` (reprise, §9), `schema` (démarrage du suivi, §6.1). Absent
     = saisie dans l'application.
4. Chaque liste est triée par `at` croissant.

### 3. Valeur ou événement selon le type du champ

| Type de champ | Entrée |
|---------------|--------|
| `text`, `number`, `enum`, `multi_enum`, `boolean`, `date`, `datetime`, `user` | valeur |
| `textarea`, `richtext`, `drawio` | événement seul (`at`, `by`) — le contenu est dans git |
| statut | valeur |

`multi_enum` : la valeur est stockée telle qu'elle est dans `fields` (chaîne CSV) ; deux
valeurs ne diffèrent que si leurs ensembles diffèrent (l'ordre ne compte pas).

### 4. Alimentation par comparaison à l'écriture

1. Une fonction unique `applyHistory(before, after, typeDef, ctx)` compare l'objet avant et après,
   et ajoute une entrée par champ suivi dont la valeur a changé. Elle est appelée par **toutes** les
   écritures d'exigence, de test et de campagne, sans branchement action par action.
2. **Création** : une entrée par champ suivi ayant une valeur (le statut initial compris : `draft`
   pour une exigence, `planned` pour une campagne…).
3. **Changement** : comparaison par valeur (`deepEqual`, ensembles pour `multi_enum`). Vider un
   champ est un changement : entrée avec `value: null` (ou événement seul).
4. **Pas de changement** : aucune entrée. Une sauvegarde automatique sans modification n'écrit rien.
5. Plusieurs changements dans une même écriture : une entrée par champ, toutes au même `at`.
6. Changements système sans valeur suivie modifiée (pose de `needsRevalidation`, réécriture de
   `objectTypeRef`, mutations des entrées de campagne) : aucune entrée, sauf si elles changent un
   champ suivi — ex. `updateRun` fait passer la campagne de `planned` à `in_progress` : entrée sur
   `status`.
7. Champ non suivi : on n'alimente pas, on ne supprime rien de l'historique existant.
8. **Valeurs retirées du schéma** : l'historique garde la clé ; l'affichage la montre telle quelle
   (pas de libellé).

### 5. Identité `by`

| Écriture | `by` | `source` |
|----------|------|----------|
| Application desktop | `AuthService.projectUsername(repoPath)` (login forge, sinon `local`) | — |
| Client web | login de la session | — |
| Serveur MCP | `--user` / `POLENTA_USER`, sinon `local` | `mcp` |
| Fusion de branches | les entrées viennent des branches, aucune n'est créée | — |
| Reprise git (§9) | auteur du commit | `git` |

### 6. Évolution du schéma

1. **Activer le suivi** d'un champ (ou réactiver le statut) : l'historique démarre avec la valeur
   courante, à la première écriture de l'objet — l'entrée implicite (§7) est alors écrite avec
   `source: schema`. Aucune réécriture de masse des fichiers à l'activation.
2. **Désactiver** : on cesse d'alimenter, rien n'est supprimé.
3. **Renommer un champ** (sprint dédié) : à l'enregistrement du schéma, pour chaque objet du type
   concerné (dans le repo du type, composants compris) :
   - `fields.<ancien>` → `fields.<nouveau>` ;
   - `history.<ancien>` → `history.<nouveau>` ;
   - aucune entrée d'historique créée (le nom change, pas la valeur).

   Détection du renommage : l'éditeur mémorise le nom d'origine de chaque champ chargé. Un champ
   supprimé puis recréé n'est pas un renommage.

   Conflit : si l'objet a déjà une donnée sous le nouveau nom (valeur orpheline d'un ancien champ),
   l'objet n'est pas modifié et il est listé dans le compte rendu affiché après l'enregistrement
   (« N objets non migrés : … »). Même comportement « au mieux par fichier » que
   `retargetObjectTypeRef` : un fichier illisible ne bloque pas les autres.

   Les fichiers modifiés sont publiés comme toute modification (Publier).
4. Le renommage d'une **valeur** d'enum ou d'un **statut** n'est pas migré (hors scope, #82).
   L'historique garde l'ancienne clé, affichée telle quelle.

### 7. La valeur courante fait foi

1. Si la valeur courante d'un champ suivi diffère de la dernière entrée de son historique (ou s'il
   n'y a pas d'historique) — ancienne version de l'app, YAML modifié à la main, `git revert` — la
   **lecture** (index des exigences / tests, lecture d'une campagne) ajoute une **entrée implicite** :
   `value` = valeur courante, `at` / `by` = `updatedAt` / `updatedBy` (dernier commit du fichier),
   `implicit: true`. Fichier jamais commité : `at` = date de lecture, `by` absent.
2. L'entrée implicite n'est pas écrite sur disque à la lecture. Elle l'est à la prochaine écriture
   de l'objet (sans `implicit`, avec `source: schema` si §6.1), ce qui comble le trou.
   Les lectures exposées ailleurs (graphe de données #74, MCP) livrent l'entrée implicite avec
   `implicit: true` : c'est un fait brut (« valeur constatée, date de changement inconnue »), à
   interpréter par le script du projet.
   Une écriture qui n'est pas une action de l'utilisateur sur l'objet écrit aussi l'entrée
   implicite — en particulier la resynchronisation des copies GH68 sur une simple consultation.
   Ça n'ajoute pas de fichier modifié de plus que ce que #81 décrit déjà, et disparaît si #81
   retient l'option 2.
3. Pour un champ « événement seul », il n'y a rien à comparer : aucune entrée implicite.
4. Signalement : il n'y a pas de `check.py` dans ce repo (cf. Contexte). La règle est ajoutée aux
   règles de cohérence de `CLAUDE.md` et à `AGENTS.md` ; dans l'application, l'entrée implicite est
   visible dans l'historique (§10, mention « déduite »).

### 8. Fusion de branches

1. `merge-core` `mergeUnit('history', …)` ne lève **jamais de conflit** : pour chaque champ, union
   des entrées des deux côtés, dédoublonnées (même `at`, `by`, `value`, `source`), triées par `at`.
2. La valeur courante issue de la fusion peut différer de la dernière entrée fusionnée : la règle
   §7 s'applique.

### 9. Reprise depuis `git log` (dernier sprint)

1. Action manuelle « Reconstruire l'historique depuis git » dans le panneau Projet, par repo.
2. Pour chaque exigence / test / campagne du repo et chaque champ suivi à valeur : parcourt les
   versions du fichier dans `git log` (branche courante), et produit une entrée à chaque changement
   de valeur, `at` = date du commit, `by` = auteur, `source: git`.
3. Fusion avec l'historique existant selon §8 (union, tri) ; une entrée `git` n'est pas ajoutée si
   une entrée de même valeur existe déjà dans la fenêtre du même commit (pas de doublon avec ce que
   l'application a déjà noté).
4. Champs « événement seul » : une entrée par commit qui modifie le champ.
5. Résultat : fichiers modifiés dans le working tree, publiés comme toute modification. Une barre de
   progression et un compte rendu (objets traités, entrées ajoutées, erreurs) sont affichés.
6. Rejouable : relancer ne crée pas de doublon.
7. Coût mesuré sur le repo de démo et sur un repo de 2 000 objets × 200 commits ; le design fixe
   une borne si besoin (ex. `git log` limité au fichier, pas de parcours de tout l'historique du
   repo par objet).

### 10. Affichage

Section repliable « Historique » en lecture seule dans le détail d'une exigence, d'un test et d'une
campagne : une liste par champ suivi, entrées les plus récentes en premier, avec libellé (statut /
valeur d'enum retrouvé dans le schéma, valeur brute sinon), date, auteur, et une mention pour
`source` (`MCP`, `git`, `schema`) et pour l'entrée implicite (« déduite »). Pas d'édition.

Affichage de la donnée brute uniquement (principe #79) : pas de durée par statut, de graphe ni de
synthèse. Ces vues relèvent des dashboards du projet (#74).

### 11. Copies figées des campagnes (`testSnapshot`)

`history` est retiré de la copie du test à la création de l'entrée et à sa resynchronisation (GH68).

  courante d'un champ suivi est la dernière entrée de son historique ».

## Critères d'acceptation

1. Une exigence créée (UI ou MCP) a `history.status: [{ value: draft, at, by }]` (+ `source: mcp`
   pour le MCP).
2. Changer le statut d'une exigence / d'un test par chacun des chemins (bouton de transition,
   colonne Statut de la vue Tableau, « Rouvrir en brouillon ») ajoute exactement une entrée.
3. Éditer un champ `enum` suivi ajoute une entrée avec la nouvelle valeur ; éditer un champ
   `richtext` suivi ajoute une entrée sans `value` ; éditer un champ non suivi n'ajoute rien.
4. Une sauvegarde sans changement n'ajoute aucune entrée.
5. Une campagne qui reçoit son premier résultat a une entrée `in_progress` ; sa clôture une entrée
   `completed` / `abandoned`.
6. `trackStatusHistory: false` sur un type : aucune entrée de statut n'est ajoutée ; l'historique
   existant est conservé.
7. Un objet dont le `status` a été modifié à la main dans le YAML montre une entrée implicite à la
   lecture ; elle est écrite à la prochaine sauvegarde.
8. Fusion de deux branches ayant chacune changé le statut d'un même objet : pas de conflit sur
   `history`, union triée des entrées.
9. `testSnapshot` ne contient jamais `history`.
10. Renommer un champ suivi dans l'éditeur migre valeur et historique de tous les objets du type ;
    un objet ayant déjà une donnée sous le nouveau nom est listé, non modifié.
11. La reprise git sur le repo de démo produit des entrées `source: git` cohérentes avec
    `git log`, et une seconde exécution n'ajoute rien.
12. Un fichier sans `history` (ancienne version) se lit et s'écrit sans erreur.
