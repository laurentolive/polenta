# GH81 — Campagnes : plus d'écriture du fichier de campagne sur une simple consultation

Issue : #81 (règle aussi #75).

## Contexte

Depuis GH68, la copie `testSnapshot` d'une instance **resynchronisable** (instance `pending` d'une
campagne ouverte, dont la copie n'est pas dans un statut d'approbation) est remplacée par l'état
actuel du test et **écrite** dans `campaigns/<id>.yaml` par `CampaignsService.refreshEntries()`,
appelée :
- à l'ouverture de la page d'exécution (`campaign.$campaignId_.execute.$testId.tsx`, mutation
  `refreshEntries`) ;
- à l'export du classeur Excel d'exécution (`CampaignExecutionService.exportSheet`).

Ces deux actions ressemblent à des lectures pour l'utilisateur : un relecteur qui ouvre la page
d'exécution d'un brouillon modifié puis repart sans rien saisir laisse une modification non
commitée du fichier de campagne.

#75 en est un effet de bord : une resynchronisation entre l'export et l'import d'un classeur
fait enregistrer les verdicts contre une version du test plus récente que celle remise aux
testeurs, sans aucune détection (`validateExecutionImport` ne compare que les ordres d'étapes du
classeur).

## Décisions de cadrage

| # | Question | Décision |
|---|----------|----------|
| D1 | Option retenue (issue) | **Option 2** : resynchroniser à la saisie, avec contrôle de version. Plus aucune écriture sur une consultation ni sur un export. |
| D2 | Détection « le test a changé » | **Empreinte du contenu** de la copie (pas le numéro `version`) : robuste aux modifications hors application (édition à la main, `git revert`, changement de branche). |
| D3 | Test modifié entre l'affichage et la saisie (page d'exécution) | **Figer la version affichée** : la saisie n'est pas refusée ; c'est la version que le testeur a vue qui est enregistrée. |
| D4 | Test modifié entre l'export et l'import (classeur) | **Instance refusée** (erreur propre à l'instance, les autres importées) : « le test a changé depuis l'export ». Le classeur ne contient pas le test complet, la version exportée ne peut pas être reconstituée — c'est la piste de #75. |

## Définitions

- **Instance resynchronisable** : inchangé par rapport à GH68 — `CampaignTestRun` `pending`, avec
  `testSnapshot`, campagne `planned` ou `in_progress`, copie hors statut d'approbation
  (`isApprovalStatus`). Une instance ajoutée approuvée, une entrée pré-T49 (sans copie), une
  instance déjà exécutée ou une campagne clôturée ne le sont pas.
- **Version effective** d'une instance : pour une instance resynchronisable, l'état actuel du test
  (copie live, sans `history`, paramètres de l'instance non recalculés — mêmes règles que
  `refreshEntries`) ; sinon sa copie `testSnapshot` (ou le test live pour une entrée pré-T49,
  comme aujourd'hui). Test source supprimé : la copie existante.
- **Empreinte** : condensat déterministe de la version effective (forme sérialisée, sans `history`,
  clés `undefined` exclues, ordre des clés stable). Deux versions de contenu identique ont la même
  empreinte, quel que soit le numéro `version`.

## Comportements attendus

### 1. Consultation — aucune écriture

1. Ouvrir la page d'exécution d'une instance n'écrit **rien** dans le repo, quel que soit le statut
   de l'instance ou du test. La page affiche la version effective (live pour une instance
   resynchronisable, copie sinon).
2. Les autres lectures (liste de la campagne, relecture d'un run, exports plan/rapport
   xlsx/docx/pdf, tableaux de bord) gardent leur comportement actuel et n'écrivent rien.
3. Le bandeau « Non approuvé » et la confirmation « Exécuter quand même » de la page d'exécution
   (GH68) sont inchangés ; ils portent sur la version affichée.
4. Session figée (GH71) inchangée : la version affichée est fixée à l'ouverture ; si la version
   effective change pendant la saisie (test modifié ailleurs, autre onglet, autre utilisateur),
   la saisie n'est pas réinitialisée ; le bandeau existant le signale et propose d'afficher la
   nouvelle version (ce qui efface la saisie).

### 2. Saisie d'un résultat dans la page d'exécution — la version affichée est figée

1. À la saisie (enregistrement d'un résultat), la page envoie au main, en plus du résultat, la
   **version affichée** du test (contenu complet de la copie affichée).
2. Si l'instance est resynchronisable au moment de l'enregistrement, le main remplace sa copie par
   la version affichée, puis enregistre le résultat — en **une seule écriture** du fichier de
   campagne. C'est vrai même si le test a changé depuis l'affichage (D3).
3. Si l'instance n'est plus resynchronisable (déjà exécutée entre-temps, copie approuvée,
   campagne clôturée), la version envoyée est ignorée : la copie existante n'est pas modifiée et
   le résultat est enregistré selon les règles actuelles (refus sur campagne clôturée inchangé).
4. Contrôles du main sur la version envoyée : son `id` est celui du test de l'instance
   (`testCaseId`), sinon la saisie est refusée avec une erreur explicite ; `history` éventuel est
   retiré (GH77 : une copie ne porte jamais `history`).
5. Ré-exécution d'une instance déjà exécutée : inchangée (copie figée conservée).

### 3. Export du classeur d'exécution — aucune écriture, empreinte enregistrée

1. L'export n'écrit plus rien dans le repo : le classeur est construit sur la **version
   effective** de chaque instance (live pour une instance resynchronisable).
2. La feuille `_polenta` enregistre, par instance, l'**empreinte** de la version exportée. Le
   numéro de format du classeur (`EXECUTION_SHEET_FORMAT_VERSION`) est incrémenté.
3. La feuille de saisie (colonnes, protection, ordres d'étapes) est inchangée.

### 4. Import du classeur — la version exportée est figée, ou l'instance est refusée

1. Pour chaque instance importable, le main recalcule l'empreinte de sa version effective et la
   compare à l'empreinte enregistrée dans le classeur :
   - **identique** → à l'enregistrement, une instance resynchronisable voit sa copie remplacée
     par la version effective (= la version exportée), puis le résultat est enregistré, en une
     seule écriture de la campagne ; une instance non resynchronisable garde sa copie ;
   - **différente** → **erreur propre à l'instance** (exclue, les autres importées), nouveau code
     d'erreur (ex. `test_changed_since_export`), message « Le test a changé depuis l'export du
     classeur — réexportez le classeur pour cette instance. » visible dans l'aperçu.
2. Classeur d'un format antérieur (sans empreinte) : comportement GH68 conservé — pas de
   comparaison, la copie actuelle est figée sans resynchronisation (ces classeurs ont été produits
   par un export qui avait déjà écrit la copie).
3. L'avertissement `test_not_approved` (GH68) est conservé ; il porte sur la version figée.
4. Les autres règles d'import (§4.5 : refus global, erreurs par instance, `executedBy`, passage
   `planned` → `in_progress`, écriture séquentielle) sont inchangées.

### 5. Client web

Mêmes comportements : aucune écriture à l'ouverture de la page d'exécution ni au téléchargement du
classeur, quel que soit le rôle. Le channel IPC de resynchronisation à la consultation, s'il est
supprimé ou renommé, est retiré de la liste blanche du serveur web (`channel-policy.ts`).

## Critères d'acceptation

- CA1 — Ouvrir puis quitter la page d'exécution d'une instance resynchronisable dont le test a
  changé : `git status` du repo ne montre aucune modification de `campaigns/<id>.yaml`.
- CA2 — Exporter le classeur d'exécution d'une campagne contenant des instances
  resynchronisables dont le test a changé : aucune modification du repo ; le classeur montre
  l'état actuel du test.
- CA3 — Ouvrir la page d'exécution (version V1), modifier le test (V2) ailleurs, saisir le
  résultat : la copie enregistrée est V1 (contenu affiché), le résultat est enregistré ; une
  seule écriture de la campagne.
- CA4 — Instance resynchronisable, test inchangé : la saisie fige la version live ; le fichier de
  campagne n'est écrit qu'une fois (copie + résultat).
- CA5 — Exporter (V1), modifier le test (V2), importer : l'instance est en erreur
  `test_changed_since_export` dans l'aperçu, non importée ; les autres instances sont importées.
  Cas #75 (étape insérée en position 2) détecté.
- CA6 — Exporter (V1), importer sans modification du test : l'instance est importée et sa copie
  vaut V1.
- CA7 — Modification du test hors application (YAML édité à la main sans changer `version`) entre
  l'export et l'import : détectée (CA5).
- CA8 — Classeur exporté avant GH81 (sans empreinte) : importé comme avant GH68/GH81, sans erreur
  de format.
- CA9 — Instance approuvée, instance déjà exécutée, campagne clôturée : comportements actuels
  inchangés (copie jamais modifiée par la saisie ni l'import).
- CA10 — Saisie envoyant une version dont l'`id` ne correspond pas au test de l'instance : refusée,
  rien d'écrit.

## Hors scope

- Resynchronisation des copies pour les exports plan/rapport (xlsx/docx/pdf) ou la liste de la
  campagne : ils continuent de lire la copie (les pastilles « Non approuvé » restent jugées sur
  l'état live pour une campagne ouverte, GH71).
- Enregistrer le test complet dans le classeur pour figer la version exportée malgré un changement
  (rejeté, D4).
- Bouton « mettre à jour la copie » manuel, migration des campagnes existantes.
- Indicateur nouveau : aucun (comportement de gestion des copies, relève de Polenta — principe
  GH79).
