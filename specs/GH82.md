# GH82 — Schéma : renommer un statut ou une valeur d'enum migre les objets et leur historique

## Contexte

Dans l'éditeur de schéma, renommer un **statut** ou une **valeur d'enum** (`enum`, `multi_enum`)
laisse les objets existants sur l'ancienne clé. La valeur devient orpheline : plus de libellé ni de
couleur, et elle n'est plus reconnue par les filtres, l'approbation (`isApproval`) ou la
resynchronisation GH68. GH77 a traité le renommage d'un **champ** (migration de `fields` et
`history`) ; ce ticket l'étend au renommage d'une **valeur**.

### État du code (après GH77 / GH86)

- `objectTypeEditor.tsx` :
  - statuts édités ligne par ligne (`StatusesTable`) ;
  - valeurs d'enum saisies en texte `"a, b, c"` (`EditableField.values`) ;
  - nom d'origine des champs mémorisé (`originalName`, GH77) ;
  - clés hors éditeur conservées (GH86).
- Renommage de champ (GH77) :
  - `renameFieldKeys` (logique pure, `@polenta/types`) ;
  - méthodes `renameFieldKeys` des services exigences / tests / campagnes, avec écriture brute
    (`persist(…, { raw: true })`, sans entrée d'historique) ;
  - `FieldRenameService`, canal `schema:rename-fields`, bannière de compte rendu dans l'onglet
    Structure.
- Où vit une clé de statut ou de valeur d'enum :
  - `status` de l'objet ;
  - `fields.<champ>` : chaîne pour `enum`, CSV pour `multi_enum` ;
  - `history.status` et `history.<champ>` (`value`) ;
  - copies `testSnapshot` des entrées de campagne (`status`, `fields`) ;
  - `default` du champ dans le schéma ;
  - requêtes et dashboards du Suivi (conditions du builder, SQL), **hors scope**.
- Les statuts des campagnes sont fixes (`planned`…) : non concernés. Leurs champs `enum` le sont.

## Décisions de cadrage

| # | Question | Décision |
|---|----------|----------|
| D1 | Copies `testSnapshot` | **Clés migrées** : seule la clé change, pas le sens. Sinon un statut d'approbation renommé n'est plus reconnu (GH68) |
| D2 | Détection d'un renommage de valeur d'enum | **Par position + confirmation** : même nombre de valeurs, et une valeur différente à la même position = renommage proposé |
| D3 | Requêtes / dashboards du Suivi | **Hors scope** (#74 les remplace) ; la confirmation le signale |
| D4 | Renommer vers une valeur déjà portée par des objets | **Autorisé avec avertissement** : les deux populations fusionnent ; la confirmation donne le nombre d'objets concernés |

## Comportements attendus

### 1. Détection dans l'éditeur

1. **Statut** : chaque ligne de `StatusesTable` mémorise son nom d'origine au chargement (non
   persisté), comme `originalName` des champs. Un nom différent à l'enregistrement est un renommage.
   Un statut supprimé puis recréé n'en est pas un.
2. **Valeur d'enum** (`enum`, `multi_enum`) : quand un champ existant (nom d'origine connu) garde le
   **même nombre** de valeurs, chaque position dont la valeur change est un renommage proposé
   (`a, b, c` → `a, bb, c` : `b → bb`). Si le nombre change (ajout ou retrait), rien n'est proposé
   pour ce champ : la saisie est ambiguë.
3. Un champ renommé et l'une de ses valeurs renommée dans la même édition sont tous deux migrés :
   le champ d'abord, puis la valeur sous le nouveau nom du champ.
4. Le `default` du champ égal à l'ancienne valeur est mis à jour dans le schéma.

### 2. Confirmation avant migration

À l'enregistrement d'un type, si au moins un renommage de statut ou de valeur est détecté, une fenêtre
de confirmation s'ouvre **avant** l'écriture du schéma :
- une ligne par renommage, « Statut : `review` → `en-revue` » ou « Champ Priorité : `haute` →
  `high` », **cochée par défaut, décochable** ;
- pour chaque ligne, le nombre d'objets du type qui portent l'ancienne valeur, et l'avertissement
  « N objet(s) portent déjà `<nouvelle>` : les deux seront confondus » si c'est le cas (D4) ;
- la mention « Les requêtes et dashboards du Suivi ne sont pas modifiés » ;
- [Enregistrer et migrer] / [Annuler].

Une ligne décochée n'est pas migrée, mais le schéma est enregistré tel quel : c'est la saisie de
l'utilisateur, et les objets gardent alors l'ancienne valeur, orpheline, comme aujourd'hui.

Les comptes viennent d'un aperçu calculé dans le main, sans écriture.

### 3. Migration

Après l'enregistrement du schéma (même philosophie que GH77 §6.3 : pas de retour arrière, au mieux
par fichier), pour chaque objet du type dans le repo du type (exigences, tests, campagnes) :

- **statut** `ancien → nouveau` :
  - `status` de l'objet ;
  - valeurs de `history.status` ;
  - `status` des copies `testSnapshot` des campagnes du repo dont le test est de ce type.
- **valeur d'enum** `ancien → nouveau` du champ `f` :
  - `fields.f` (pour `multi_enum`, l'élément concerné de la liste CSV, ordre et séparateur
    conservés) ;
  - valeurs de `history.f` ;
  - `fields.f` des copies `testSnapshot` dont le test est de ce type.
- Plusieurs renommages sont appliqués d'un coup (échange `a ↔ b` correct).
- Écriture brute : aucune entrée d'historique (la valeur ne change pas, seul son nom change), aucun
  déclenchement de revalidation (T172) ni de changement de `version`.
- Compte rendu dans la bannière de l'onglet Structure, commune avec le renommage de champ :
  objets migrés, copies de campagne migrées, échecs.

### 4. Hors scope

- Requêtes et dashboards du Suivi (conditions du builder, SQL) : D3, #74.
- Statuts des campagnes (fixes).
- Valeurs citées dans du texte (`richtext`, étapes de test, paramètres `{req.<champ>}`).
- Renommage par le serveur MCP (pas de tool de renommage) ou par édition manuelle de `schema.yaml`.
- Saisie d'un `validator` dans l'éditeur (relevé en GH86).

## Critères d'acceptation

1. Renommer un statut `review` → `en-revue` d'un type d'exigence :
   - toutes les exigences du type en `review` passent en `en-revue` ;
   - leurs `history.status` sont réécrits ;
   - aucune nouvelle entrée d'historique, aucun `needsRevalidation` posé.
2. Renommer le statut d'approbation d'un type de test : les copies `testSnapshot` des campagnes sont
   migrées, et la pastille « Non approuvé » (GH68) ne s'affiche pas à tort.
3. `enum` `haute, moyenne` → `high, moyenne` : les objets `haute` passent en `high`, ceux en
   `moyenne` sont inchangés, `history.<champ>` est réécrit.
4. `multi_enum` `"haute, basse"` avec `haute → high` : `"high, basse"`.
5. Ajout ou retrait d'une valeur dans la même édition : aucun renommage proposé pour ce champ.
6. Échange `a ↔ b` dans une même édition : les objets `a` passent en `b` et inversement.
7. Une ligne décochée dans la confirmation : schéma enregistré, objets non migrés pour cette ligne.
8. Renommer vers une valeur déjà portée : avertissement avec le nombre d'objets, migration effectuée.
9. Annuler dans la confirmation : rien n'est enregistré.
10. Le `default` égal à l'ancienne valeur est mis à jour.
11. Un fichier en échec n'empêche pas les autres et figure dans le compte rendu.
