Type : bug (`type:bug`). Milestone B — Déploiement serveur. Branche `milestone-B` (pas de branche ni de worktree par ticket).
Issue d'origine : compte rendu des tests sur hôte de #61 (2026-10-13, Debian 13, `CADDY_MODE=external`).

L'issue décrit quatre constats. Trois d'entre eux étaient déjà corrigés sur `origin/main` (db4559b) par des commits GH61
postérieurs au compte rendu ; le ticket ne reprend donc que ce qui restait ouvert. Chaque ligne a été vérifiée dans le code,
pas seulement d'après l'issue.

| # | Constat (issue) | État à la reprise | Traitement |
|---|---|---|---|
| 1 | `instance add` external échoue : « API GET /user → HTTP 000 » | Corrigé par `eaf04d8` (2026-10-16) : `api_target` joint la forge sur `EDGE_NETWORK` (HTTP, port 3000) en external | Aucune modification. Reste à reconfirmer sur un hôte réel (voir « Comment vérifier ») |

## Cause (points 3 et 4)

- **3** — `tests/acceptance-external.sh`, fonction `cleanup` (trap EXIT) : `instance remove … >/dev/null 2>&1` sans
  contrôle du code de sortie, puis le message « instance de test nettoyée » est affiché dès que le scénario a échoué.
  Rien ne vérifie que l'instance, son dossier, son conteneur et son bloc Caddy ont disparu. Le même patron que
  le résidu de #85.2 (remove d'une instance incomplète) passe donc inaperçu.
- **4a** — `check "réseau $EDGE présent" docker network inspect "$EDGE"` : `check` exécute la commande telle quelle, sa
  sortie JSON va dans le journal.
- **4b** — `polenta-host.sh`, contrôle de `host.env` : l'avertissement `ACME_EMAIL vide` ne tient pas compte du mode.
  En external, `caddy_write_compose` retourne avant d'écrire le Caddyfile (`lib/caddy.sh`), donc `ACME_EMAIL` n'est
  jamais lu.

## Correctif appliqué

- `deploy/tests/acceptance-external.sh`
  - `net_exists` (helper) remplace `docker network inspect` dans `check`.
  - `cleanup` : contrôle le `instance remove` (journal conservé, dernières lignes affichées) et vérifie ce qui reste
    (`$ROOT/instances/$NAME`, conteneur `forgejo-$NAME`, bloc `$SITES/$NAME.caddy`). Si quelque chose reste : message
    « Instance de test « … » NON nettoyée » avec la liste, commande de reprise, sortie non nulle. Le message « nettoyée »
    n'est plus affiché que si le nettoyage est réellement complet.
- `deploy/polenta-host.sh` (contrôle de `host.env`) : l'avertissement `ACME_EMAIL vide` n'est plus émis en `CADDY_MODE=external`.

Rien d'autre n'est modifié : pas de changement de `api_target` (point 1) ni du script de sonde (point 2).

## Risque résiduel (non traité, à noter)

- `api_target` (`deploy/lib/forgejo-api.sh`) : si `docker inspect` ne renvoie pas d'IP sur `EDGE_NETWORK`, l'appel retombe
  silencieusement sur `https://<domaine>` (le chemin en échec du constat 1). `wait_front` vérifie déjà la jonction au
  réseau avant tout appel API ; ce cas n'a pas été reproduit ici, donc pas de correctif.

## Comment vérifier

Vérifié ici (sans Docker, banc Git Bash) — `bash -n` et shellcheck sur les deux scripts : aucun avertissement de plus que
sur `origin/main`. Banc `harness` (doublures de `docker`, `inst_compose`, `polenta-host` ; cas `cleanup-fail` et `cleanup-ok`) :

| Cas | `origin/main` | Ce ticket |
|---|---|---|
| remove en échec, dossier et bloc restants | « instance de test nettoyée » (faux) | « NON nettoyée », dossier et bloc listés, sortie 1 |
| remove réussi | pas de message | pas de message |

Non lancé ici, à faire sur un hôte external réel (VM ou VPS de test, pas un hôte qui porte un client) :

1. `sudo deploy/tests/acceptance-external.sh <domaine neuf>` → doit sortir 0, aucun `docker events` résiduel.
2. Vérifier le chemin d'échec du nettoyage : `sudo POLENTA_HOST_BIN=/bin/false deploy/tests/acceptance-external.sh <domaine> --no-setup`
   → l'`instance add` échoue, le `remove` aussi : le message doit dire « NON nettoyée. instance remove en échec. »
   (et non « nettoyée »).
3. `sudo polenta-host setup` en external sur un `host.env` sans `ACME_EMAIL` → plus d'avertissement ACME.
