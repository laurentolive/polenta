## Causes

- **2** — `cmd_instance_export` : le dump de la forge est obligatoire. Une instance qui n'a jamais terminé `instance add`
  (pas de `.add-complete`) n'a pas encore de dépôt : `forgejo dump` échoue, l'export s'arrête, donc `remove` refuse
  (« rien n'a été supprimé »). Aucune issue de contournement dans le kit.
- **3a** — `cmd_instance_restore` : le domaine est lu dans `instance.env` **après** restauration du snapshot ; le snapshot
  de la source contient le domaine de la source. Une copie sous un autre nom reprend donc le domaine d'une instance vivante.
  Le RUNBOOK A5 annonce pourtant « un autre domaine » et le test trimestriel utilise `<nom>-test.<BASE_DOMAIN>`.
- **3b** — rien à corriger côté code : `--yes` et `--confirm` sont déjà pris en compte. Le RUNBOOK ne documente que la forme interactive.
- **4** — documentation incomplète sur les trois points ; le compose du kit (`lib/caddy.sh`) ne déclare pas `polenta-edge` externe.

## Correctif appliqué

- `deploy/polenta-host.sh`, `cmd_instance_export` : le dump de la forge peut être ignoré **uniquement** si l'instance n'est pas
  complète (`.add-complete` absent) **et** qu'il n'existe pas de `/data/git/repositories` dans le conteneur. Dans ce cas :
  avertissement, export des données brutes (`data.tar.gz`, `forge.env`, `instance.env`) comme d'habitude, et `LISEZMOI.md`
  indique l'absence de `forge-dump.tar.gz`. Tout autre échec de dump arrête l'export, comme avant.
- `deploy/polenta-host.sh`, `cmd_instance_restore` : sans `--domain` et avec `--source` ≠ `<nom>`, le domaine est
  `<nom>.<BASE_DOMAIN>` (même règle qu'`instance add`). Si `BASE_DOMAIN` est vide : arrêt immédiat, code d'usage, avant toute
  confirmation et toute écriture dans le dossier de l'instance. Sans `--source` (ou `--source` = `<nom>`) : domaine de la
  sauvegarde, inchangé.
- `deploy/RUNBOOK.md`
  - A2 : copie depuis Windows → `chmod +x …` ou `sudo bash ./polenta-host.sh setup`.
  - A5 : copie de contrôle « domaine `<nom>.<BASE_DOMAIN>` (`--domain` pour un autre) » ; `--force --yes` (ou `--confirm <nom>`)
    dans un exemple de script.
  - A16, migration `managed` → `external` : option de réutilisation des certificats (copie du volume `data` du Caddy du kit) ;
    note sur `polenta-edge`, retiré par `down` seulement s'il n'est plus utilisé.
  - A16, retour `external` → `managed` : report des `_*.caddy` de `CADDY_SITES_DIR` vers `/opt/polenta/caddy/etc/sites/`,
    option de réutilisation des certificats.

## Décisions à valider

1. **Constat 2 — tolérance ciblée plutôt qu'un drapeau.** Retenu : pas de `--no-export`, la tolérance ne vaut que pour une
   instance jamais mise en service sans dépôt. Alternative : un drapeau explicite `remove --no-export`, qui oblige l'exploitant
   à le dire mais ajoute une option pour un cas sans donnée client.
2. **Constat 3a — changement de comportement.** `restore --source acme acme-test` sans `--domain` vise désormais
   `acme-test.<BASE_DOMAIN>` et échoue tout de suite si `BASE_DOMAIN` est vide (avant, il reprenait le domaine de `acme`).
   Les appelants qui scriptaient l'ancien comportement doivent passer `--domain`.
3. **Constat 4, `polenta-edge` — documentation, pas code.** Déclarer le réseau `external` dans le compose généré obligerait
   `setup` managed à exiger un réseau créé à la main. Non retenu ; à revoir si l'on veut un réseau géré par le kit.

## Risque résiduel (non traité)

- `restore --source acme acme-test --domain acme.<BASE_DOMAIN>` (domaine de la source, donné à la main) reproduit le bloc Caddy
  en double. Le kit ne le détecte pas aujourd'hui (il faudrait lire le `DOMAIN` de la source sur l'hôte, qui peut ne pas s'y trouver).
