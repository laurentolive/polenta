# GH93 — Suivi : paramètres de tableau de bord choisis à l'affichage (ex. avancement d'une campagne)

## Contexte

Le widget **Avancement dans le temps** du seed Campagnes (requête modèle `campaign-timeline`,
filtre `campaignStatuses: ['in_progress']`) appelle `campaignsTimeline` (`dashboards/lib/campaign.js`),
qui **additionne** toutes les campagnes retenues : une seule série par statut d'entrée. On ne peut pas
suivre une campagne en particulier.

Contournement actuel : le paramètre « Campagnes » (`campaignIds`) des modèles `campaign-entries` /
`campaign-timeline` est **figé dans le code généré** → une requête et un widget par campagne, à
recréer pour chaque nouvelle campagne.

Ce ticket introduit des **paramètres de requête dont la valeur est choisie à l'affichage** : la
requête déclare ce qu'elle accepte, le tableau de bord affiche les sélecteurs correspondants, le
script lit la valeur dans `polenta.params`. La campagne est le premier cas ; le mécanisme est
générique.

### Principe « données brutes » (GH79, SPEC-TECH §1.1)

Aucun nouvel indicateur : Polenta fournit un **mécanisme générique** (déclaration, sélecteur,
transmission de la valeur) ; ce que chaque paramètre filtre ou change reste dans les scripts et la
bibliothèque du projet.

### État du code (vérifié sur `main` @ 8f23cbf)

- `PolentaHost` (`packages/types/src/graph.ts`) : `locale`, `timezone`, `timezoneOffsets`, `today`,
  `now`, `drill` — pas de valeur fournie par l'utilisateur.
- `ScriptRunRequest` (`script.ts`) : `queryId` / `script`, `dashboardId` / `widgetId`, `transform`,
  `drill`, `limit`.
- Partage d'exécution `ScriptEngineService` : clé = contexte + langue + fuseau + `drill` + script.
- Clé React Query des widgets : `useScriptRun.ts` (`widgetRunOptions`).
- `query.yaml` : `id`, `title`, `formatVersion`, `template?`, `createdBy`, `createdAt`.
- `.{user}.pref` : jamais commité (`*.pref` ignoré) ; porte déjà `savedQueries`, `dashboards`,
  `campaignsSeed`, `suiviIgnoredUpdates`.
- Formulaires de modèles : `TemplateForm` sait déjà proposer campagnes, composants, types d'objet,
  valeurs d'énumération.

## 1. Déclaration des paramètres (requête)

Une requête (partagée ou privée) peut déclarer une liste de **paramètres** :

| Propriété | Description |
|---|---|
| `name` | identifiant (lettres, chiffres, `_`, commence par une lettre), unique dans la requête ; clé dans `polenta.params` |
| `kind` | `campaign`, `component`, `objectType`, `enum`, `text`, `period` |
| `label` | libellé `{ fr, en }` (un seul texte accepté : utilisé pour les deux langues) |
| `values` | `enum` seulement : valeurs possibles `{ value, label }` |
| `default` | valeur par défaut facultative (format du §3) |
| `required` | facultatif ; vrai → pas de choix « Tous / Toutes », le widget attend une valeur |

- Stockage : dans la définition de la requête (`query.yaml` pour une requête partagée, l'objet de
  `savedQueries[]` pour une requête privée), **pas** dans le script : connue sans l'exécuter.
- Requête issue d'un modèle : déclaration **générée** par le modèle (§5). Modifier la déclaration
  d'une requête modèle la détache de son modèle, comme modifier son script (« personnalisé »).
- Requête personnalisée : déclaration éditée dans la vue `/query` (section « Paramètres » : ajouter,
  modifier, supprimer, réordonner) et via le MCP (§7).
- Déclaration invalide (nom dupliqué ou invalide, `kind` inconnu, `enum` sans valeurs, défaut hors
  format) : refus à l'enregistrement (app et MCP) avec message ; lue invalide depuis un fichier
  modifié à la main → la requête s'affiche en erreur (`kind: 'format'`), sans exécution.
- Requête en lecture seule (`legacy-sql`, `newer-format`) : pas de paramètres.

## 2. Valeurs reçues par le script

- Nouveau champ du contrat : `polenta.params` — objet **toujours présent** (vide si aucun
  paramètre), une clé par paramètre déclaré, gelé. Ajout dans le contrat v1 (on ne fait
  qu'ajouter) ; `polenta.d.ts` régénéré.
- Le script **et** la transformation du widget reçoivent le même `polenta.params`.
- Valeur absente (« Tous / Toutes », rien choisi, pas de défaut) → `null`. Une valeur n'est jamais
  `undefined` pour un paramètre déclaré.

## 3. Types de paramètres

| `kind` | Sélecteur | Valeur dans `polenta.params` |
|---|---|---|
| `campaign` | liste des campagnes du repo ouvert (`ID — titre`, statut affiché), + « Toutes » | ID de campagne ou `null` |
| `component` | composants du périmètre (comme le formulaire « Liste filtrée »), + « Tous » | nom du composant ou `null` |
| `objectType` | types d'objet du périmètre (libellé et composant affichés), + « Tous » | `objectTypeRef` ou `null` |
| `enum` | valeurs déclarées, + « Toutes » | `value` choisie ou `null` |
| `text` | champ de saisie libre (appliqué à la validation : Entrée ou perte du focus) | texte (espaces de début/fin retirés) ou `null` si vide |
| `period` | deux dates « du » / « au », chacune facultative | `{ from: 'AAAA-MM-JJ' \| null, to: 'AAAA-MM-JJ' \| null }`, ou `null` si les deux sont vides |

- Sélection **simple** pour tous les types (une campagne ou toutes) — pas de sélection multiple.
- `period` : `from > to` → refusé dans le sélecteur (message), la valeur précédente est conservée.
- **Valeur devenue invalide** (campagne supprimée, composant ou type retiré du workspace, valeur
  `enum` retirée de la déclaration) → traitée comme absente (`null`, ou défaut s'il est valide) et
  le sélecteur signale « Valeur introuvable : <valeur> ». La valeur mémorisée n'est pas effacée
  automatiquement (elle peut redevenir valide, ex. après changement de branche).
- Paramètre `required` sans valeur → les widgets qui en dépendent ne s'exécutent pas et affichent
  « Choisir <libellé> » (pas une erreur).

## 4. Barre de paramètres du tableau de bord

- Un dashboard dont au moins une requête de widget déclare des paramètres affiche, sous son titre,
  une **barre de sélecteurs**. Aucun paramètre → pas de barre (affichage inchangé).
- **Regroupement** : un sélecteur par couple (`name`, `kind`) ; deux requêtes qui déclarent le même
  couple partagent le sélecteur (choisir une campagne recentre tous les widgets concernés). Libellé
  et `values` : ceux de la première requête dans l'ordre des widgets ; pour `enum`, valeurs = union
  dans l'ordre d'apparition. Même `name` avec des `kind` différents → deux sélecteurs distincts.
- Ordre des sélecteurs : ordre de première apparition (widgets dans l'ordre du dashboard, puis
  ordre de déclaration).
- **Changement de valeur** → seuls les widgets dont la requête déclare ce paramètre se
  réexécutent.
- **Résolution de la valeur** d'un paramètre, par priorité :
  1. valeur choisie par l'utilisateur pour ce dashboard (**mémorisée par utilisateur** dans son
     `.pref`, clé par dashboard puis par sélecteur ; jamais commitée, rien à publier) ;
  2. `default` de la déclaration de la requête (le premier valide parmi les requêtes regroupées) ;
  3. `null`.
- Pas de valeur par défaut propre au dashboard : la barre n'écrit jamais dans le dashboard, donc
  jamais de modification à publier.
- Action de la barre : **Réinitialiser** (efface les choix de l'utilisateur pour ce dashboard →
  défauts des déclarations).
- Un sélecteur dont plus aucune requête ne déclare le couple disparaît ; les choix orphelins sont
  ignorés (nettoyés à la prochaine écriture du `.pref`).
- Dashboard en lecture seule (`newer-format`) ou branche en lecture seule : barre affichée et
  utilisable (choix mémorisés dans le `.pref`).

### Ailleurs que dans un dashboard

- **Vue `/query`** : barre des paramètres de la requête au-dessus du résultat ; valeurs initiales =
  défauts de la déclaration ; non mémorisées (perdues en quittant la vue). L'exécution et l'export
  Excel utilisent les valeurs affichées.
- **Popup de configuration de widget** : l'aperçu utilise les valeurs courantes du dashboard.
- **Drill-down** : la relance (`polenta.drill`) utilise les mêmes valeurs que le widget cliqué.
- **Impression / export docx du dashboard** : valeurs courantes de l'utilisateur ; elles sont
  rappelées en tête du document (« Campagne : CAMP-0003 — Validation lot 2 », « Période : du … au … »,
  « Toutes » pour une valeur absente).

## 5. Modèles

Les modèles de requête proposent, pour les paramètres concernés, un choix **« Fixé »** (valeur
figée dans le code, comportement actuel) ou **« Choisi à l'affichage »** :

| Modèle | Paramètre « choisi à l'affichage » | Comportement |
|---|---|---|
| `campaign-entries` | Campagne (`campaign`, `kind: campaign`) | campagne choisie → ses seules entrées, **les filtres de statut de campagne et la liste de campagnes fixée sont ignorés** ; « Toutes » → filtres du modèle appliqués (comportement actuel). Filtres de statut d'entrée toujours appliqués. |
| `campaign-timeline` | Campagne (idem) ; Période (`period`, `kind: period`) | période → `from` / `to` de `campaignsTimeline` (bornes absentes : comportement actuel) |
| `filtered-list` | Composant (`component`) ; Type d'objet (`objectType`) | valeur choisie → remplace le composant / type fixé ; « Tous » → valeur fixée du modèle si elle existe, sinon aucun filtre |

- La déclaration générée porte les libellés fr / en du modèle.
- Les paramètres d'un modèle ne fixent pas de `default` (« Toutes » / « Tous »).
- Pas de rétrocompatibilité à assurer avec les requêtes modèles créées avant GH93 (version GH74 non
  publiée) : le code généré et la version des modèles peuvent changer librement.
- Les modèles de widget (transformations) ne déclarent pas de paramètres.

## 6. Seed Campagnes

- Toutes les requêtes du seed Campagnes (Avancement par campagne, % exécuté,
  % PASS, Exécutions par jour, Entrées en échec, Avancement dans le temps) passent la campagne en
  « Choisi à l'affichage » → un seul sélecteur **Campagne** en tête du dashboard, « Toutes » par
  défaut : affichage initial identique à l'actuel.
- Seeds Campagnes déjà créés : aucune reprise ni proposition au bandeau (version GH74 non publiée,
  pas de rétrocompatibilité) ; seuls les nouveaux seeds portent le sélecteur.
- Seed Status : inchangé.

## 7. Serveur MCP et AGENTS.md

- `create_query` / `update_query` : propriété `parameters` (déclaration §1), validée comme dans
  l'app ; avec `template`, la déclaration est générée (une `parameters` fournie en plus → refus).
- `list_queries` / lecture d'une requête : déclaration incluse.
- `run_query`, `test_script` : propriété `params` (valeurs, format §3) ; paramètre déclaré non
  fourni → `default` de la déclaration, sinon `null` ; paramètre `required` sans valeur → erreur
  explicite ; clé non déclarée → refus.
- Les choix d'un utilisateur (`.pref`) ne sont pas accessibles par MCP.
- `get_data_contract`, AGENTS.md (section Suivi) : `polenta.params`, déclaration, exemple
  (avancement d'une seule campagne).

## 8. Cas limites

| Cas | Comportement attendu |
|---|---|
| Deux dashboards ouverts successivement avec le même widget de requête | valeurs propres à chaque dashboard ; résultats non mélangés (cache et partage d'exécution distinguent les valeurs) |
| Deux widgets de la même requête, même valeurs | script exécuté une fois (partage actuel conservé) |
| Requête déclarant un paramètre que son script ne lit pas | aucune erreur ; le sélecteur s'affiche quand même |
| Script lisant une clé non déclarée | `undefined` (comportement JS normal) |
| Campagne choisie puis supprimée / branche changée sans cette campagne | « Valeur introuvable », widgets en « Toutes » (ou défaut) |
| Campagne choisie terminée alors que le filtre du modèle est « en cours » | la campagne choisie est affichée (le filtre de statut ne s'applique qu'à « Toutes ») |
| Dashboard partagé, utilisateur sans droit d'écriture (branche en lecture seule) | sélecteurs utilisables, choix mémorisés dans son `.pref` |
| Requête privée d'un widget partagé | impossible (règle §7.0b inchangée) |
| Changement de la déclaration d'une requête (ex. `kind` modifié) | le couple (`name`, `kind`) change → nouveau sélecteur, l'ancien choix est ignoré |
| Valeur `text` contenant des caractères spéciaux / très longue | transmise telle quelle (texte, 1 000 caractères max, saisie bloquée au-delà) |
| Client web | même comportement (valeurs dans le `.pref` de l'utilisateur côté serveur) |

## 9. Critères d'acceptation

- [ ] Sur le seed Campagnes (nouveau), le dashboard affiche un sélecteur « Campagne » ; « Toutes »
      donne exactement les résultats actuels (corpus de non-régression inchangé).
- [ ] Choisir une campagne recentre les six widgets du seed sur elle seule, y compris « Avancement
      dans le temps » (aire empilée des seules entrées de cette campagne) ; une campagne terminée
      choisie est affichée malgré le filtre « en cours ».
- [ ] Le choix est retrouvé après fermeture / réouverture du dashboard et redémarrage de l'app ; il
      est propre à l'utilisateur et ne crée aucune modification à publier.
- [ ] « Réinitialiser » revient aux défauts des déclarations (« Toutes » sur le seed Campagnes).
- [ ] Changer la valeur d'un sélecteur ne réexécute que les widgets concernés.
- [ ] Les six types (`campaign`, `component`, `objectType`, `enum`, `text`, `period`) sont
      déclarables dans `/query` et via MCP, reçus dans `polenta.params` par le script et la
      transformation au format §3.
- [ ] `campaign-timeline` avec période choisie à l'affichage borne la série aux dates choisies.
- [ ] `filtered-list` avec composant / type choisi à l'affichage filtre selon la valeur choisie.
- [ ] Drill-down, aperçu de la popup, impression, export docx et export Excel utilisent les valeurs
      affichées ; impression et docx les rappellent en tête.
- [ ] Valeur invalide → « Valeur introuvable », widgets en défaut ; paramètre `required` sans
      valeur → « Choisir <libellé> » dans le widget.
- [ ] MCP : `run_query` / `test_script` avec `params` ; `create_query` / `update_query` avec
      `parameters` ; erreurs explicites (clé non déclarée, `required` manquant, déclaration
      invalide) ; `get_data_contract` documente `polenta.params`.
- [ ] Les erreurs de déclaration sont refusées à l'enregistrement et affichées en erreur de format
      si le fichier a été modifié à la main.

## 10. Hors scope

- Comparaison de campagnes (une courbe par campagne sur le même graphique).
- Intégration d'un widget dans la page d'une campagne, paramétré sur elle (ticket séparé).
- Sélection multiple dans un sélecteur.
- Paramètres déclarés par une transformation de widget ou par un widget seul (seule la requête
  déclare).
- Valeurs dépendantes entre sélecteurs (ex. liste des campagnes filtrée par le composant choisi).
- Paramètres dans l'URL / lien partageable vers un dashboard paramétré.
- Choix d'un autre utilisateur visible ou modifiable par MCP.
