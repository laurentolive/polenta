# T103 — bug : ajout de tests dans une campagne perd des tests, puis ajout/retrait bloqués

## Root cause

Toutes les méthodes de `CampaignsService` qui modifient une campagne (`addTests`,
`duplicateTest`, `removeEntries`, `updateRun`, `updateRunParams`, `close`, `update`)
suivent le même schéma : lire `campaigns/{id}.yaml` en entier via `get()`, modifier l'objet
en mémoire, réécrire le fichier en entier via `writeYaml()`. Aucune de ces méthodes ne
verrouille ni ne sérialise l'accès au fichier.

Le panneau "Ajouter des tests" (`campaign.$campaignId.tsx`, `handleConfirmAdd`) déclenche
plusieurs de ces mutations **en parallèle** via `Promise.all()` dès que la sélection mêle
des tests nouveaux et des tests déjà présents avec paramètres (un `addTestsMutation` +
un `duplicateTestMutation` par test dupliqué) — introduit par T97 sprint 2. Chaque appel
lit le même état de départ et la dernière écriture à se terminer écrase silencieusement
le résultat des autres ("lost update" classique) : les tests ajoutés par les mutations
"perdantes" disparaissent purement et simplement du fichier, sans erreur visible.

Plus l'utilisateur enchaîne les clics ajout/retrait rapidement, plus les lectures qui
démarrent avant qu'une écriture précédente ne soit terminée se basent sur un état obsolète
— chaque nouvelle mutation risque à son tour d'écraser le travail de la précédente, ce qui
donne l'impression qu'ajouter ou retirer un test "ne fait plus rien" passé un certain point.

Ce défaut était documenté comme limitation connue mais jugée théorique dans
`specs/T97-sprint2.md` (§Divergences, "absence de verrou/transaction sur l'écriture
concurrente") — le flux d'ajout groupé introduit par ce même sprint le rend en réalité
facilement reproductible, pas seulement théorique.

## Correctif appliqué

`apps/desktop/src/main/services/campaigns.service.ts` : ajout d'une file d'attente en
mémoire par campagne (`writeQueues: Map<string, Promise<unknown>>` + méthode privée
`enqueue()`), qui chaîne les mutations ciblant la même campagne (`repoPath::campaignId`)
les unes après les autres. Toutes les méthodes read-modify-write listées ci-dessus sont
désormais enveloppées dans `this.enqueue(repoPath, campaignId, async () => { ... })` —
chaque mutation ne démarre sa lecture qu'une fois l'écriture de la précédente terminée,
ce qui élimine les lost updates quel que soit le nombre d'appels IPC concurrents envoyés
par le renderer. Aucun changement côté UI ou IPC nécessaire : la sérialisation est
transparente pour les appelants.

Portée limitée à `CampaignsService` : c'est le seul service où plusieurs actions UI
distinctes ciblent délibérément le même fichier en parallèle (ajout groupé). Les autres
services (exigences, tests) écrivent un fichier par objet, donc ce scénario de collision
ne s'y présente pas de la même façon.

## Comment vérifier

1. Ouvrir une campagne active avec plusieurs tests disponibles à ajouter, dont au moins un
   avec paramètres déjà présent dans la campagne (pour déclencher `duplicateTest` en plus
   d'`addTests`).
2. Sélectionner plusieurs tests d'un coup (mélange nouveaux + dupliqués) et cliquer une
   seule fois sur "Ajouter" → tous les tests sélectionnés doivent apparaître dans la liste,
   aucun manquant.
3. Test de charge (fait pendant le debug, script jetable non conservé) : 12 appels
   `addTests` concurrents sur la même campagne — avant le correctif, 1 test sur 12
   survivait (11 perdus) ; après le correctif, 12/12 systématiquement. Combiné à des
   `duplicateTest`/`removeEntries` concurrents supplémentaires : comptes finaux corrects,
   aucun `entryId` dupliqué, `testCaseIds.length === runs.length` toujours vrai.
4. Enchaîner rapidement plusieurs clics ajout/retrait sur la même campagne → chaque action
   doit rester visible dans le résultat final, plus d'état qui semble "se figer".
