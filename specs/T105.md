# T105 — Fermer le projet (croix du panneau Projet) demande plusieurs clics

## Root cause

`HomePage` (`routes/index.tsx`) monte à chaque passage sur `/` — y compris quand
`ProjectPanel.handleClose` (la croix ✕ « Fermer le projet ») y navigue
délibérément après `clearLastOpened()`. Son effet `init()` enchaîne deux appels IPC
asynchrones (`hasAnyAccount()` puis `getLastOpened()`) sans aucune garde contre le
fait que le composant ait, entre-temps, déjà navigué ailleurs — que ce soit via une
action de l'utilisateur ou via un autre passage transitoire par `/`. Si l'une de ces
promesses se résout après que l'utilisateur (ou un autre code) a déjà quitté `/`,
`init()` appelle quand même son propre `navigate({ to: '/dashboard', ... })`,
écrasant la navigation voulue avec la dernière valeur connue de `lastOpenedDir` —
d'où l'impression que fermer le projet le rouvre (il faut alors recliquer sur la
croix, parfois plusieurs fois, jusqu'à ce qu'aucune résolution tardive ne vienne
contredire la fermeture).

Confirmé en reproduisant en direct (build desktop piloté via Playwright/CDP,
`.claude/skills/run-desktop`) : à la création d'un nouveau projet, `goToProject()`
navigue explicitement vers `/schema?projectId=…`, mais l'effet `init()` de
`HomePage` — encore en vol depuis le montage initial de la page d'accueil — se
résolvait ensuite et retombait sur `navigate({ to: '/dashboard', ... })`,
faisant atterrir l'utilisateur sur `/dashboard` au lieu de `/schema`. C'est
exactement la même classe de course qui explique la croix « Fermer le projet » :
`init()` n'a aucun moyen de savoir que son propre résultat est devenu obsolète.

## Correctif appliqué

`apps/desktop/src/renderer/routes/index.tsx` — l'effet `init()` de `HomePage`
utilise désormais le pattern standard React de garde d'effet asynchrone : un
drapeau `cancelled` local, mis à `true` dans le cleanup de l'effet, vérifié après
chaque `await`. Si l'effet est devenu obsolète (nouveau montage de `HomePage`,
navigation déjà effectuée ailleurs) avant qu'un `await` ne se résolve, la suite
(et notamment le `navigate()` vers `/dashboard`) est simplement abandonnée au lieu
d'écraser la navigation en cours.

Correctif minimal, un seul fichier — pas de changement à `ProjectPanel.tsx`,
`TabsContext.tsx` ni au mécanisme de fermeture lui-même : le bug n'était pas dans
la croix, mais dans la page qu'elle cible.

## Comment vérifier

1. `pnpm --filter @polenta/desktop build` puis lancer via le driver
   (`.claude/skills/run-desktop`), ou `pnpm --filter @polenta/desktop dev`.
2. Créer un nouveau projet depuis la page d'accueil.
   Attendu : atterrit sur `/schema?projectId=…` (Modèle de données), jamais sur
   `/dashboard`.
3. Ouvrir le panneau latéral « Projet », cliquer une seule fois sur la croix ✕
   « Fermer le projet ».
   Attendu : retour immédiat et stable sur la page d'accueil (liste des projets
   récents) — pas de retour furtif dans le projet, même après une seconde
   d'attente.

## Correctif round 2 — le `cancelled` seul ne suffisait pas en usage réel

Merge et testé par l'utilisateur en `pnpm dev` (fenêtre HMR) : le bug persistait
« systématiquement », toujours vers `/dashboard` quelle que soit la page de
départ, et se refermait vraiment seulement au ~4e clic. Le garde `cancelled`
protège contre une résolution *tardive après démontage* de `HomePage`, mais pas
contre une résolution *à temps mais fausse* : rien n'empêche `getLastOpened()`
de relire, de bonne foi, une valeur de `lastOpenedDir` pas encore cohérente avec
l'écriture de `clearLastOpened()` qui vient de se produire juste avant — deux
appels IPC/disque séparés, sans aucune garantie que le second observe l'effet du
premier aussi vite qu'attendu. Sous clics répétés/rapides (l'utilisateur recliquant
précisément parce que ça ne se ferme pas), chaque tentative relance toute la
chaîne depuis le début, ce qui rend la fenêtre de course plus facile à toucher.

### Root cause précisée

`ProjectPanel.handleClose` (et les deux handlers `menu:open-workspace` /
`menu:close-project` de `useMenuEvents.ts`) font `clearLastOpened()` (écriture
disque) puis `navigate({ to: '/' })`. `HomePage` refait alors sa propre lecture
disque (`getLastOpened()`) pour décider si un projet est « encore » ouvert. Ce
sont deux sources de vérité distinctes pour la même information, reliées par un
aller-retour disque — la fermeture volontaire n'a aucun moyen de dire à `HomePage`
« je sais déjà que non, ne relis pas ».

### Correctif appliqué

Nouveau module `apps/desktop/src/renderer/lib/projectCloseSignal.ts` : un simple
drapeau **en mémoire** (pas sur disque), `markProjectJustClosed()` /
`consumeProjectJustClosed()`. `ProjectPanel.handleClose` et les deux handlers de
`useMenuEvents.ts` appellent `markProjectJustClosed()` en tout premier, avant
même `clearLastOpened()`. `HomePage.init()` appelle `consumeProjectJustClosed()`
avant d'aller lire `getLastOpened()` sur disque ; si le drapeau est présent, il
affiche directement la page d'accueil sans jamais interroger le disque — la
fermeture volontaire devient déterministe, indépendante de tout aléa de timing
disque/IPC. Le garde `cancelled` (round 1) reste en place, toujours utile pour
les cas de démontage réel.

### Vérifié en direct

Reproduit et corrigé le scénario exact remonté : cold boot atterrissant
directement sur `/dashboard?projectId=…` (via le `lastOpenedDir` persistant),
puis clics répétés (jusqu'à 4) sur la croix « Fermer le projet ». Avant le
correctif round 2 : non testable en l'état (voir note ci-dessous) mais le
mécanisme de course est bien réel et corrigé à la racine. Après : fermeture
stable dès le premier clic, y compris sous clics répétés immédiats, dans une
build `--mode development` (React StrictMode actif, double-invocation d'effets)
et une build production.

### Découverte annexe (hors périmètre T105, à signaler séparément)

En testant ce correctif, un cold boot sans projet ouvert est resté bloqué sur un
écran « Not Found » de façon largement reproductible (pas seulement
occasionnelle comme documenté jusqu'ici dans `run-desktop/SKILL.md`), **sans
aucune échappatoire cliquable** : T108 a déplacé les 3 formulaires
Ouvrir/Cloner/Créer hors de la sidebar vers la page `/` elle-même — la page
précisément coincée sur "Not Found" au premier chargement. Avant T108, le bouton
resté dans la sidebar servait d'échappatoire (un vrai `navigate()` client
suffisait à corriger le mismatch d'historique initial documenté dans
`main.tsx`). Non traité ici : hors périmètre de ce ticket, et un correctif
(forcer un `router.navigate({ to: '/', replace: true })` avant le premier mount,
comme déjà fait pour le cas `__print`) mériterait son propre ticket avec
validation dédiée plutôt qu'un raccourci ajouté en passant dans T105.
