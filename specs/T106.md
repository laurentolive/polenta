# T106 — AGENTS.md généré à la création d'un projet Polenta

## Contexte

Les utilisateurs finaux de Polenta n'ont accès qu'à l'exécutable (apps/desktop) — pas
au code source de l'outil ni à ses specs internes (`SPEC*.md`, `CLAUDE.md`,
`WORKFLOW.md`, qui documentent le développement de Polenta lui-même). Pourtant, une
fois un projet créé, il est probable qu'ils utilisent une IA (Claude Code, Cursor,
Codex, Copilot, Gemini CLI…) pour faire du "system engineering assisté par IA" sur
leurs propres exigences/tests : review d'exigence, review de test, construction
d'indicateurs (requêtes/dashboards), vérification des liens de traçabilité.

Sans documentation embarquée dans le projet, l'IA choisie par l'utilisateur ne connaît
ni le format des fichiers (frontmatter YAML + Markdown), ni le schéma configurable
(`.polenta/schema.yaml`), ni les invariants (`tree.yaml` généré, IDs jamais réutilisés,
liens `needsRevalidation`, etc.), ni le moteur de requête des dashboards.

## Décisions (validées avec l'utilisateur)

1. **Nom de fichier : `AGENTS.md`** — convention émergente cross-outils pour les
   instructions destinées à un agent IA (Codex, Cursor, Claude Code la reconnaissent
   nativement), par opposition à `README.md` qui reste orienté lecture humaine.
2. **Injection automatique à la création du projet** — le fichier est écrit à la
   racine du repo git au moment de `WorkspaceService.createNewProject()`, au même
   titre que `.gitignore`, et commité dans le commit initial `init: create project`.
3. **Contenu générique, indépendant du domaine métier** — ce fichier documente les
   *mécanismes* de Polenta (format de fichier, schéma, liens, requêtes, traçabilité),
   pas une convention métier particulière (EARS, électroménager…). Un projet créé
   sans template n'a qu'un nœud `root` vide — le contenu doit rester valable dans ce
   cas comme dans le cas d'un schéma déjà enrichi. Il renvoie vers
   `.polenta/schema.yaml` comme source de vérité pour les spécificités du projet
   (types d'objets, champs, statuts, validateurs).

## Hors scope

- Pas de sélection de template à la création (`api.workspace.createNew` ne prend
  aujourd'hui que `containerDir`/`name` — cf. `SPEC-TEMPLATES.md`, non implémenté).
  `AGENTS.md` est donc un contenu fixe, pas généré depuis un template YAML.
- Pas de mise à jour rétroactive des projets existants (pas de migration) — un projet
  déjà créé avant ce ticket n'aura pas le fichier tant qu'il n'est pas ajouté à la
  main par l'utilisateur.
- Pas d'ajout dans `createFromClone` — un projet cloné a déjà son propre historique
  et peut déjà contenir un `AGENTS.md` (ou volontairement pas) ; on ne force pas
  l'écriture sur un repo existant.
- Pas de changement au repo `c:\Dev\polenta` lui-même (outil source) — celui-ci garde
  son `CLAUDE.md` propre au développement de l'outil.

## Contenu du fichier (sections)

1. Ce qu'est Polenta en une phrase (ALM fichiers-first, sans base de données)
2. Format d'un objet (exigence/test/campagne) : frontmatter YAML + corps Markdown,
   champs fixes (`id`, `objectTypeRef`, `status`) vs `fields{}` custom définis par
   `.polenta/schema.yaml`
3. `objectTypeRef` = `<nœud>::<type>`, `prefix` unique et jamais réutilisé
4. Où lire les règles du projet courant : `.polenta/schema.yaml` (types, champs,
   statuts, `isApproval`/`isTerminal`, validateur `EARS`/`regex:`)
5. Liens entre objets (ObjectLink) : `linkTypes`, `sourceRefs`/`targetRefs`,
   `needsRevalidation`
6. `tree.yaml` toujours généré — ne jamais éditer à la main
7. Les 4 activités "system engineering assisté par IA" visées par le ticket :
   - Review d'exigence (statut, critères d'acceptance mesurables, cohérence avec les
     exigences liées)
   - Review de test (couverture, exécution, campagnes)
   - Construction d'indicateurs : moteur de requête SQL en lecture seule
     (`requirements`/`tests`/`links`) utilisé par les dashboards
   - Vérification des liens : matrice de couverture, `coverageStatus`
     (`not_covered`/`covered`/`validated`/`failing`/`needs_revalidation`)
8. Rappel : l'utilisateur peut lancer l'IA de son choix (aucune dépendance à un outil
   particulier) — le fichier ne contient aucune instruction propriétaire à un agent.

## Critères d'acceptation

- [ ] `AGENTS.md` présent à la racine de tout projet créé via "Créer un nouveau
  projet" (`createNewProject`), commité dans le commit initial.
- [ ] Contenu indépendant de tout domaine métier (pas de mention "aspirateur",
  "batterie", EARS présenté comme optionnel/dépendant du schéma).
- [ ] `createFromClone` n'est pas modifié.
- [ ] Aucune régression TypeScript/lint sur `workspace.service.ts`.
