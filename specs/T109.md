# T109 — Suivi/Dashboard : afficher le premier dashboard par défaut

## Contexte / constat

Sur la route `/dashboard?projectId=…`, quand `dashboardId` est absent de l'URL,
`DashboardPage` (`apps/desktop/src/renderer/routes/dashboard.tsx:141-148`) affiche
un message d'invite (« Sélectionnez un dashboard dans le panneau latéral, ou
créez-en un avec le bouton "+" ») au lieu d'ouvrir un dashboard existant.

Deux points d'entrée atterrissent aujourd'hui sur cet état "sans id", alors qu'un
dashboard existe déjà dans la plupart des cas :

1. **Démarrage de l'app** (T102) — `routes/index.tsx:51` navigue vers
   `/dashboard?projectId=…&dashboardId=undefined` dès qu'un `lastOpenedId` est
   connu. C'est le flux normal d'ouverture directe du dernier projet
   (SPEC-ELECTRON-DESKTOP.md §16.1/§16.3, qui référence explicitement ce ticket
   en note à la ligne du tableau §16.3).
2. **Suppression du dashboard actif** — `DashboardPanel.tsx:132`
   (`deleteDashboardMutation.onSuccess`) navigue vers `dashboardId: undefined`
   quand le dashboard supprimé était celui affiché, même s'il en reste d'autres
   dans la liste.

Dans les deux cas, l'utilisateur doit aujourd'hui cliquer manuellement sur un
dashboard dans le panneau latéral pour voir du contenu, alors qu'un choix par
défaut raisonnable (le premier de la liste, tel qu'affiché dans le panneau
latéral) existe déjà.

Le panneau latéral (`DashboardPanel.tsx`) affiche déjà l'onglet "Dashboards" par
défaut (`activeTab` initial = `'dashboards'` sauf `queryId` actif dans l'URL) —
ce comportement-là ne change pas.

## Comportement attendu

Sur `/dashboard?projectId=…` avec `dashboardId` absent :

- **Au moins un dashboard existe** (liste `api.dashboards.list` non vide, pour le
  projet/utilisateur courant, privé + partagé confondus comme aujourd'hui) →
  redirection automatique (`navigate(..., replace: true)`) vers
  `/dashboard?projectId=…&dashboardId=<premier id>`, où "premier" suit exactement
  l'ordre déjà utilisé par le panneau latéral : `orderItems(dashboards,
  dashboardsOrder)[0]` (helper déjà exporté par `ReorderableSidebarSection.tsx`,
  ordre persisté `dashboards.getOrder` avec les ids inconnus ajoutés en fin de
  liste). Le dashboard affiché est donc toujours celui visuellement en tête du
  panneau latéral.
- **Aucun dashboard n'existe** (liste vide) → comportement inchangé : message
  d'invite dans la zone de contenu principale. Le panneau latéral propose déjà
  "Créer le premier" dans ce cas (`ReorderableSidebarSection`, `emptyMessage`/
  `addFirstLabel`), inchangé.
- **Chargement en cours** (liste et/ou ordre des dashboards pas encore résolus)
  → ne pas afficher le message d'invite prématurément (il ne doit pas
  "flasher" avant la redirection) ; état de chargement discret le temps que les
  deux requêtes (`dashboards`, `dashboards-order`) soient résolues.
- La redirection utilise `replace: true` (pas d'entrée d'historique
  intermédiaire sur l'état "sans id" — cohérent avec le pattern déjà utilisé pour
  le changement de scope, `dashboard.tsx:106`).
- Une fois `dashboardId` présent dans l'URL (redirection effectuée, ou id déjà
  fourni par un clic explicite dans le panneau), le comportement de la page est
  entièrement inchangé.

### Cas particulier — suppression du dashboard actif

`DashboardPanel.tsx:132` continue de naviguer avec `dashboardId: undefined`
quand le dashboard actif est supprimé. Avec ce ticket, cette navigation aboutit
désormais automatiquement sur le nouveau premier dashboard restant (s'il y en a
un), au lieu de rester sur l'état "sans id" — sans changement nécessaire dans
`DashboardPanel.tsx` lui-même, la redirection étant portée par `dashboard.tsx`.

### Extension — clic sur l'icône "Suivi" (ajouté après retour utilisateur en sprint 1)

Constat en validant le sprint 1 : `AppLayout.tsx` (`handleSelectPanel`, case
`'dashboard'`) navigue inconditionnellement vers `/query` (vue Requêtes vide)
au clic sur l'icône "Suivi", quel que soit ce qui était affiché avant —
y compris un dashboard qui venait de se charger correctement grâce au sprint 1.
Résultat observé : sortir de Suivi puis y revenir affiche la vue Requêtes vide
dans le contenu principal alors que le panneau latéral reste sur l'onglet
"Dashboards". Repris dans le périmètre de ce ticket (initialement noté hors
scope, ré-ouvert sur demande explicite) plutôt que d'ouvrir un ticket séparé.

Comportement ajouté : même mécanisme que `lastVersionRoute` (panneau
"Version", déjà existant dans `AppLayout.tsx`) — un `lastDashboardRoute` mémorise
la dernière sous-vue (`/dashboard?dashboardId=…` ou `/query?queryId=…`)
affichée sous le panneau "Suivi", et le clic sur l'icône restaure cette
sous-vue plutôt que de toujours retomber sur `/query`. Sans sous-vue connue
(première visite du projet), le nouveau défaut est `/dashboard` (dashboardId
undefined — qui bénéficie du redirect vers le premier dashboard ajouté par ce
même ticket), plus jamais `/query`.

## Hors scope

- Aucune notion de "dashboard par défaut" épinglé/marqué explicitement par
  l'utilisateur — le "premier" reste purement positionnel (ordre du panneau
  latéral), pas un champ persisté sur le dashboard.
- Pas de changement au tri/à la persistance de `dashboardsOrder` lui-même.
- Pas de changement pour la vue Requêtes (`/query`), qui garde son propre état
  vide quand `queryId` est absent.

## Critères d'acceptation

- [ ] Démarrage de l'app avec un `lastOpenedId` connu et au moins un dashboard
  existant dans le projet → la page Suivi/Dashboard affiche directement le
  premier dashboard du panneau latéral (widgets chargés), sans clic
  supplémentaire.
- [ ] Projet sans aucun dashboard → message d'invite inchangé, pas d'erreur, pas
  de boucle de redirection.
- [ ] Suppression du dashboard actuellement affiché alors qu'il en reste
  d'autres → la page bascule automatiquement sur le nouveau premier dashboard
  restant.
- [ ] Suppression du seul dashboard existant → retour au message d'invite
  (comportement inchangé).
- [ ] Réordonner les dashboards dans le panneau latéral puis revenir sur
  `/dashboard` sans id (ex. relancer l'app) → c'est bien le nouveau premier de
  la liste réordonnée qui s'affiche.
- [ ] Aucune régression sur la navigation explicite (clic sur un dashboard
  précis dans le panneau, changement de scope privé/partagé) ni sur la vue
  Requêtes.
- [ ] Cliquer sur l'icône "Suivi" alors qu'un dashboard précis (pas
  nécessairement le premier) était affiché, naviguer vers un autre panneau puis
  revenir sur "Suivi" → le même dashboard est restauré (contenu principal ET
  onglet du panneau latéral cohérents), pas de retour à `/query`.
- [ ] Même test en étant parti d'une requête (`/query?queryId=…`) plutôt que
  d'un dashboard → la requête est restaurée à l'identique.
- [ ] Aucune erreur TypeScript/lint nouvelle.
