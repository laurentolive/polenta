## Description

Dans l'éditeur de modèle de données (`/schema`), l'onglet **Interfaces** (`InterfacesTab`, `apps/desktop/src/renderer/routes/schema.tsx:195-360`) est supprimé. Ses fonctions sont relocalisées dans l'onglet **Structure** (`StructureTab.tsx`), et le concept de « rôle » devient **une seule source de vérité** réutilisée aux trois endroits qui en dépendent, au lieu de trois listes indépendantes non reliées comme aujourd'hui.

### Constat (analyse de code, confirmée avant rédaction de cette spec)

Le mot « rôle » apparaît aujourd'hui à trois endroits distincts, **sans lien structurel entre eux** :

| # | Endroit | Stockage | État actuel |
|---|---------|----------|--------------|
| 1 | Catalogue de rôles d'un repo interface | `schema.roles: RoleDefinition[]` (`.polenta/schema.yaml` du repo **interface**) | Seule vraie déclaration. Détermine aussi `node.isInterface` (`workspace-tree.service.ts:469-471` : `s.roles.length > 0`). Aujourd'hui éditable uniquement via l'onglet Interfaces, section « Rôles (repo interface) ». |
| 2 | Rôles joués par un composant qui implémente l'interface | `schema.implements[].roles: string[]` (`.polenta/schema.yaml` du repo **composant**) | Texte libre, aucune validation contre le catalogue (1). Éditable via l'onglet Interfaces (section « Implémentations ») **et déjà** via `StructureTab.tsx:670-693` + `updateInterfaceRoles` (`workspaceActions.ts:90-100`) en éditant le nœud interface dans l'arbre. |
| 3 | Rôles tagués sur une exigence du repo interface | `SchemaField` de type `multi_enum`, nommé `roles`, avec `values: [...]` codé en dur dans l'`ObjectTypeDefinition` (même repo que (1)) | Champ générique standard (`EditView.tsx` case `'multi_enum'`, `field.values ?? []`), sans lien avec (1). Consommé tel quel par `interface-compliance.service.ts` (`req.fields['roles']`) pour le calcul de la matrice de conformité. |

Le point (2) sert réellement — il pilote le filtrage d'applicabilité de la matrice de conformité (`interface-compliance.service.ts:186-231`, `isRequirementApplicable:247-251`) : une exigence taguée `controller` (3) n'est applicable qu'aux composants qui déclarent jouer ce rôle (2). Mais rien aujourd'hui n'empêche une faute de frappe entre (1), (2) et (3) — chacun est une saisie libre indépendante.

Le catalogue (1) lui-même n'est presque jamais lu : à part `getInterfaceFlag`, la seule autre lecture (`interface-compliance.service.ts:159`, `interfaceRoles = interfaceSchema?.roles?.map(...)`) est une variable calculée puis jamais utilisée — code mort. C'est le signe que (1) existe aujourd'hui sans être réellement la source de vérité qu'il devrait être pour (2) et (3).

## Décisions (validées par l'humain le 2026-07-17)

- **Source unique** : le catalogue de rôles (1) devient la seule liste saisie librement (nom + label). (2) et (3) deviennent des **sélections** parmi ce catalogue, plus jamais du texte libre ni des `values:` codées en dur.
- (1) est saisi dans une nouvelle section, présente dans la popup d'édition de **tout** nœud dépendance dans Structure — pas seulement ceux déjà marqués interface, sinon aucun nouveau repo ne pourrait jamais le devenir (« Rôles exposés par ce repo »), écrite dans `schema.roles` du repo édité (`node.repoPath`).
- (2) reste éditable en deux endroits, cohérents avec (1), tous deux présents dans la popup d'édition de n'importe quel nœud (les deux notions — exposer son propre catalogue et implémenter d'autres interfaces — sont indépendantes, un même repo peut faire les deux) :
  - Section existante « Rôles joués par [parent] » (actuellement en texte libre) — devient une sélection multiple parmi le catalogue du nœud édité, défini juste au-dessus dans la même popup.
  - Nouvelle section « Interfaces implémentées » — liste toutes les `implements[]` du nœud édité ; le champ rôles de chaque ligne est une sélection multiple parmi le catalogue de l'interface choisie sur cette ligne (résolu via `api.schema.get` sur le repo de l'interface ciblée).
- (3) : le rendu du champ `roles` d'une exigence dans `EditView.tsx` (`FieldControl`, case `'multi_enum'`) source ses options depuis le catalogue `schema.roles` du repo courant (même `repoPath` que l'objet édité — pas de résolution cross-repo) au lieu de `field.values`, uniquement quand `field.name === 'roles'` **et** que le repo courant a un catalogue non vide. Fallback sur `field.values` si le catalogue est vide (rétrocompatibilité avec un projet existant qui n'a pas encore de catalogue).
- L'onglet Interfaces (`InterfacesTab`, `TABS` dans `schema.tsx`) est supprimé une fois les sections Structure opérationnelles — pas avant.

## Comportements attendus

### Cas 1 — Éditer n'importe quel nœud dans l'arbre Structure : catalogue + rôles joués

Ces deux sections sont visibles dans la popup d'édition de **tout** nœud dépendance (pas seulement ceux déjà marqués `node.isInterface === true`) — sinon un repo jamais encore marqué interface ne pourrait jamais le devenir via l'UI (problème d'œuf et de poule : pas de section catalogue tant qu'il n'y a pas de rôles, pas de rôles tant qu'il n'y a pas de section catalogue).

- **« Rôles exposés par ce repo »** : liste éditable (nom + label), écrite dans `schema.roles` du repo édité lui-même (`node.repoPath`) à la sauvegarde. Vide au départ pour un repo qui n'est pas encore une interface — le remplir le fait devenir une interface (badge `isInterface` recalculé au prochain rechargement de l'arbre).
- **« Rôles joués par [parent] »** : sélection multiple (cases à cocher) parmi les rôles définis juste au-dessus dans la même popup (pas de texte libre), écrite dans `schema.implements` du parent qui monte ce nœud. Si le catalogue est vide **et** qu'aucun rôle n'était déjà déclaré côté parent, cette section est masquée (rien à sélectionner, rien à préserver). Si un rôle précédemment saisi en texte libre (avant T110) ne correspond à aucune entrée du catalogue (y compris si le catalogue est aujourd'hui vide), il reste affiché — séparément, comme « rôle hérité, hors catalogue » — avec une case à cocher pour le retirer explicitement ; jamais purgé silencieusement.
- Sauvegarde : deux écritures `api.schema.save`, une par repo cible (comme c'est déjà le cas pour la logique existante côté parent).

### Cas 2 — Éditer n'importe quel nœud : interfaces implémentées

Section visible dans la popup d'édition de **tout** nœud dépendance également (un repo peut simultanément exposer son propre catalogue de rôles ET implémenter d'autres interfaces qu'il monte lui-même en dessous de lui — les deux notions sont indépendantes).

- Nouvelle section **« Interfaces implémentées »** : tableau de lignes `{ interface (nom de montage), rôles joués }`, pré-rempli depuis `schema.implements` du nœud édité, ajout/suppression de lignes — reprise de la section « Implémentations » de l'ancien onglet Interfaces (schema.tsx:293-357), sans le champ « Version implémentée » en lecture seule (conservé, résolu via `useWorkspaceStructure` comme aujourd'hui).
- Le sélecteur de rôles de chaque ligne charge le catalogue de l'interface nommée sur cette ligne (`api.schema.get(interfaceRepoPath)`) et affiche des cases à cocher au lieu d'un champ texte libre. Si le catalogue n'est pas résolvable (interface non montée localement), fallback sur un champ texte libre (comportement actuel), pour ne pas bloquer la saisie.
- Sauvegarde écrit `schema.implements` du nœud édité.

### Cas 3 — Champ `roles` d'une exigence d'interface (EditView)
- Pour un objet dont le `SchemaField` s'appelle `roles` et est de type `multi_enum` : les options affichées (cases à cocher) viennent de `schema.roles` du repo courant (`repoPath` de l'objet édité) si ce catalogue est non vide, sinon de `field.values` (comportement actuel, rétrocompatibilité).
- Aucun changement pour tout champ `multi_enum` qui ne s'appelle pas `roles` — comportement générique inchangé.

### Cas 4 — Suppression de l'onglet Interfaces
- `TABS` dans `schema.tsx` ne contient plus `interfaces`.
- `InterfacesTab` et son UI dédiée sont supprimés du fichier.
- `EditorState.roles` / `EditorState.implements` restent nécessaires comme champs de données (toujours lus/écrits par `editableToSchema`) — seule l'UI dédiée disparaît, remplacée par les popups Structure et le champ `roles` dans EditView.

## Hors scope

- Pas de changement de forme du modèle de données (`ProjectSchema.roles`, `ProjectSchema.implements`, `SchemaField` gardent leurs types actuels — pas de nouveau `SchemaFieldType` dédié).
- Pas de migration automatique des projets existants dont le champ `roles` d'une exigence a des `values:` divergentes du catalogue — le fallback (Cas 3) couvre la transition, aucune réécriture de fichiers existants.
- Pas de validation stricte qui empêcherait de sauvegarder un rôle hors catalogue (le mode « rôle hérité, hors catalogue » du Cas 1 couvre ce cas sans bloquer).
- Pas de changement de la logique `+ Interface` / `addInterfaceImplementation` (ajout d'une nouvelle dépendance interface) — seule l'édition d'un nœud existant et le rendu du champ `roles` d'exigence sont concernés.
- Pas de changement des badges / de la détection `node.isInterface` elle-même (reste basée sur `schema.roles` non vide).

## Critères d'acceptation

1. Éditer n'importe quel nœud dans Structure permet de saisir/modifier son propre catalogue de rôles (persisté dans son `schema.yaml`) et de sélectionner (cases à cocher, plus de texte libre) les rôles que le parent joue pour ce nœud (persisté dans le `schema.yaml` du parent).
2. Éditer n'importe quel nœud dans Structure permet de voir, ajouter, modifier et supprimer toutes ses propres déclarations `implements`, avec sélection de rôles par cases à cocher sourcées depuis le catalogue de l'interface ciblée sur chaque ligne.
3. Un nouveau repo, jamais marqué interface auparavant, peut le devenir en lui ajoutant un premier rôle via la popup d'édition de son mount dans Structure — exclusivement via Structure, sans onglet Interfaces.
4. Le champ `roles` d'une exigence d'un repo interface affiche, en édition, les rôles du catalogue de ce même repo (pas une liste statique divergente) dès que le catalogue est renseigné.
5. Un projet existant dont le champ `roles` d'exigence a encore des `values:` codées en dur mais aucun catalogue (`schema.roles` vide) continue de fonctionner à l'identique (fallback).
6. L'onglet « Interfaces » n'apparaît plus dans la barre d'onglets de `/schema`.
7. Aucune régression TypeScript / lint sur `apps/desktop`.
