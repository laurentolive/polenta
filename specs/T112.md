# T112 — Supprimer createdAt/createdBy/updatedAt/updatedBy des YAML, dériver de git

## Contexte

En creusant T104 (l'affichage d'un champ pouvait modifier `updatedAt` sans intervention
de l'utilisateur — deux bugs distincts déjà corrigés : autosave des steps de test, et
`onUpdate` de l'éditeur richtext qui se déclenchait sur une transaction non liée à une
vraie édition), le constat de fond est que ces quatre champs sont redondants avec
l'historique git : chaque fichier YAML (`requirements/*.yaml`, `tests/*.yaml`) est déjà
versionné, donc "qui/quand a créé" et "qui/quand a modifié en dernier" sont dérivables du
`git log` de ce fichier plutôt que maintenus à la main dans le contenu du fichier
lui-même. Les stocker en dur crée toute une classe de bugs (n'importe quelle écriture
accidentelle pollue ces champs et le diff git) pour une info que git connaît déjà de
façon fiable.

## Comportement attendu

- Les fichiers YAML `requirements/*.yaml` et `tests/*.yaml` n'écrivent plus jamais les
  clés `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.
- À la lecture (liste ou détail), ces 4 valeurs sont dérivées du `git log` filtré sur le
  chemin du fichier : le commit le plus ancien = créé le/par, le plus récent = modifié
  le/par.
- Un fichier jamais commité (juste créé, ou en attente de premier commit) affiche ces 4
  champs comme absents (`null` → "—" côté UI), pas une valeur inventée.
- Un fichier avec des modifications non commitées garde l'`updatedAt`/`updatedBy` de son
  **dernier commit** — pas de rafraîchissement à chaque sauvegarde disque. Le panel
  Version (liste des fichiers modifiés) reste le signal pour "pas encore commité" ; pas
  de badge supplémentaire à ajouter pour ce ticket.
- Après un commit touchant un fichier, `createdAt`/`updatedAt` se mettent à jour pour
  refléter ce nouveau commit, sans nécessiter un redémarrage de l'app.

## Hors scope explicite

- `apps/api/` (NestJS) — copie parallèle de cette logique, mais dormante (non touchée
  depuis le ticket T63) ; non modifiée dans ce ticket.
- `ObjectLink.createdAt/createdBy` — tous les liens d'un repo vivent dans un seul
  `links/links.yaml` partagé, pas un mapping 1:1 propre avec l'historique git par entrée.
- Les autres types ayant leurs propres `createdAt/createdBy` sans rapport (`baseline.ts`,
  `branch.ts`, `campaign.ts`, `dashboard.ts`, `impact-analysis.ts`, `project.ts`,
  `review.ts`) — objets métier différents.
- `TestRun.executedAt/executedBy` — donnée métier (quand un test a été exécuté), pas une
  métadonnée de fichier.
- Pas de script de migration des fichiers YAML existants — la lecture écrase sans
  condition ces 4 champs après parsing, donc d'éventuelles clés obsolètes dans de vieux
  fichiers sont mortes à la lecture et disparaîtront naturellement au prochain
  enregistrement réel de chaque fichier.

## Critères d'acceptation

- [ ] Créer une exigence ou un test → le fichier YAML sur disque ne contient aucun des 4
      champs ; l'UI affiche "—" pour Créé le/Modifié le tant que non commité.
- [ ] Commiter ce fichier → rouvrir l'objet affiche des dates/auteurs cohérents avec le
      commit.
- [ ] Éditer sans commiter → `updatedAt` reste figé sur le dernier commit.
- [ ] Commiter l'édition → `updatedAt` se met à jour sans redémarrage de l'app.
- [ ] `pnpm typecheck` propre sur `@polenta/desktop`.
