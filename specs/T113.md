# T113 — Sous-composants locaux (même repo) comme pattern de premier ordre

## Contexte

Un projet Polenta peut aujourd'hui définir plusieurs `SystemNode` dans `.polenta/schema.yaml`
(`nodes: [...]`). D'après `SPEC-TEMPLATES.md` §3, un `SystemNode` "représente un composant du
système (local)" — rien dans la spec ne réserve ce pattern au seul nœud `root`.

Dans l'implémentation actuelle (`StructureTab.tsx`), c'est pourtant le cas : tout nœud dont le
`name !== 'root'` et qui n'a pas de correspondance dans l'arbre workspace (résolu depuis
`polenta-repo.yaml`, cf. T69/T70) est affiché avec un badge "⚠ non associé à un repo" et un
bouton "Supprimer" au survol (`handleDeleteOrphanNode`, cf. commentaire "légacy SystemNode sans
repo associé, cf. T70 §4.5"). Ses éléments restent lisibles/éditables (le nœud est toujours dans
`schema.yaml`), mais rien dans l'UI ne permet de **créer intentionnellement** un tel nœud : le
menu "+ Composant" (`AddMenu` → `onAddComponent`) déclenche systématiquement le flow d'ajout
d'une dépendance (`addDependency`, repo séparé/submodule) — jamais la simple création d'un
`SystemNode` local dans le `schema.yaml` du repo courant.

Résultat : le seul moyen d'avoir "plusieurs sous-composants" aujourd'hui dans l'UI est de créer
un repo git séparé par sous-composant, même quand l'équipe n'a besoin que d'un regroupement
logique interne (même cycle de vie, même équipe, pas de raison de gestion de configuration de
séparer les repos). C'est un cas d'usage réel et valide, laissé volontairement de côté par T70
(cf. son design §4.5 : "affichage de compatibilité, pas une nouvelle fonctionnalité de
migration") au profit du modèle "un composant = un repo" introduit par T69.

Un sous-composant local n'est en rien "hors du contrôle de version" — il vit dans le même repo
git que `root`, versionné par le même historique de commits. La question de lui donner son
propre repo (submodule) reste une décision distincte et volontaire de l'utilisateur, motivée par
ses contraintes de gestion de configuration (équipe séparée, réutilisation inter-projets,
versionnement indépendant) — pas une obligation dès qu'on veut plus d'un composant.

## Comportement attendu

1. **Création d'un sous-composant local depuis l'UI** : le menu "+ Composant" (`StructureTab`,
   niveau `root`) propose explicitement deux chemins distincts :
   - ajouter un **sous-composant local** — un nom (+ label optionnel) suffit ; le nœud est ajouté
     à `nodes[]` dans le `.polenta/schema.yaml` du repo courant (pas de nouveau repo git créé,
     pas d'entrée dans `polenta-repo.yaml`), avec `objectTypes: []` à configurer ensuite comme
     n'importe quel nœud ;
   - ajouter un **composant dans un repo séparé** — comportement actuel inchangé (`addDependency`).
   L'utilisateur choisit explicitement l'un ou l'autre à la création ; aucun des deux n'est
   présenté comme le choix "par défaut/recommandé" au détriment de l'autre.
2. **Un sous-composant local n'est plus jamais traité comme une erreur.** Un nœud non-root sans
   entrée correspondante dans `polenta-repo.yaml` (jamais déclaré comme dépendance) s'affiche
   normalement dans l'arbre, au même niveau que les composants repo-séparé, sans badge
   d'avertissement ni bouton "Supprimer" forcé.
3. **Le badge d'avertissement est conservé pour le vrai cas d'erreur** : un nœud non-root dont le
   nom correspond à une entrée de `polenta-repo.yaml` (dépendance déclarée) mais qui n'est pas
   résolu dans l'arbre workspace (repo non cloné/introuvable/erreur réseau) continue d'afficher un
   avertissement — le libellé est ajusté pour refléter précisément ce cas ("dépendance déclarée
   introuvable", pas "non associé à un repo") et reste actionnable (au minimum : toujours
   possible de retirer la dépendance/le nœud).
4. **Édition normale.** Un sous-composant local se configure exactement comme `root` aujourd'hui :
   ajout/édition/suppression de ses `objectTypes`, champs, statuts, via les mêmes formulaires que
   `StructureTab` propose déjà pour les nœuds résolus.
5. **Suppression volontaire.** Un sous-composant local reste supprimable à tout moment par
   l'utilisateur (action explicite, avec confirmation) — ce n'est plus présenté comme la
   correction d'une erreur, juste une suppression de composant comme une autre.
6. **Création/édition d'objets.** Créer une exigence (ou tout autre objet) dont l'`objectTypeRef`
   pointe vers un sous-composant local doit fonctionner de bout en bout depuis l'UI (formulaire de
   création, sauvegarde, apparition dans les listes/dashboards/requêtes) — pas seulement en
   lecture. C'est déjà le comportement de `resolveComponentRepoPath` (retombe sur le repo courant
   quand le nœud n'est pas dans l'arbre workspace) : ce point est une vérification de non-
   régression, pas un changement de service attendu.

## Hors scope

- Pas de migration automatique des anciens "SystemNode orphelins" existants (projets créés avant
  T69) — ils bénéficient simplement du même traitement que les nouveaux sous-composants locaux
  (plus de badge d'erreur), sans distinction à faire dans les données ni script de migration.
- Pas de changement au modèle "composant = repo séparé" (`polenta-repo.yaml`, `addDependency`,
  T69/T70) — les deux modes coexistent, ce ticket ne fait qu'ouvrir un second chemin de création.
- Pas de possibilité de convertir après coup un sous-composant local en repo séparé (ou
  inversement) depuis l'UI — l'utilisateur choisit à la création ; une conversion ultérieure est
  hors scope (ticket dédié si besoin identifié).
- Pas de changement à `Conformité interfaces` / `interface-compliance.service.ts` au-delà de ce
  qui est strictement nécessaire pour ne pas régresser sur les composants repo-séparé existants —
  un sous-composant local n'implémente/n'expose pas d'interface dans ce ticket (`roles`/
  `implements` restent réservés aux repos séparés, cf. `SPEC-TEMPLATES.md` §3a-3b).
- Pas de changement au format `schema.yaml` lui-même (`SystemNode` a déjà tous les champs
  nécessaires : `name`, `label`, `description?`, `readonly`, `objectTypes?`) — uniquement le
  comportement de l'UI (`StructureTab`) et, si nécessaire, la détection de dépendance déclarée-
  mais-non-résolue.

## Critères d'acceptation

- [ ] Depuis "+ Composant" (niveau `root`), un choix explicite "sous-composant local" vs
  "composant dans un repo séparé" est proposé.
- [ ] Créer un sous-composant local avec un nom ajoute un `SystemNode` à `nodes[]` dans
  `.polenta/schema.yaml` du repo courant — aucun repo git créé, `polenta-repo.yaml` inchangé.
- [ ] Le nouveau sous-composant local apparaît immédiatement dans l'arbre `StructureTab`, sans
  badge d'avertissement, avec la possibilité d'y ajouter des `objectTypes` (champs/statuts) comme
  pour `root`.
- [ ] Un projet contenant un `SystemNode` local historique (créé avant T113, jamais dans
  `polenta-repo.yaml`) ne montre plus de badge "non associé à un repo" ni de bouton "Supprimer"
  forcé après ce ticket — mêmes données, aucune migration nécessaire.
- [ ] Un projet dont `polenta-repo.yaml` déclare une dépendance dont le repo n'est pas résolu dans
  l'arbre workspace (ex. clone échoué) affiche toujours un avertissement actionnable, avec un
  libellé qui décrit une dépendance manquante (pas "non associé à un repo").
- [ ] Créer une exigence dont l'`objectTypeRef` cible un sous-composant local fonctionne de bout
  en bout (formulaire de création UI → fichier écrit dans `requirements/` du repo courant →
  visible dans la liste des exigences, les dashboards et les requêtes SQL).
- [ ] TypeScript/lint : zéro nouvelle erreur.

## Fichiers concernés (à confirmer en Design)

- `apps/desktop/src/renderer/components/schema/StructureTab.tsx` — logique d'affichage du badge
  "orphelin", menu "+ Composant", flow de création.
- `apps/desktop/src/renderer/hooks/useWorkspaceStructure.ts` / `apps/desktop/src/renderer/lib/workspaceActions.ts`
  — actions liées à l'arbre workspace, probablement à étendre pour la création d'un `SystemNode`
  local (distincte de `addDependency`).
- `apps/desktop/src/main/services/schema.service.ts` — `resolveComponentRepoPath` (vérification
  de non-régression uniquement, cf. Comportement attendu §6).
- `apps/desktop/src/main/services/polenta-repo.service.ts` — lecture des dépendances déclarées,
  utile pour distinguer "jamais déclaré" (silence) de "déclaré mais non résolu" (avertissement).

  `SystemNode` est par nature "un composant du système (local)", sans restriction au seul nœud
  `root` ; à mettre à jour en fin de ticket pour documenter explicitement le flow de création
  multi-composants locaux.
- `SPEC-FORKS-BRANCHES-BASELINES.md` §4 (Composants) — modèle `components.yaml`/`sourceRef`
  explicitement marqué caduc (§4.3) depuis T87 au profit des submodules git plats (T30/T69) ; ce
  ticket ne le concerne pas, mais clarifie que "sous-composant" a bien deux sens légitimes
  (repo séparé **ou** regroupement local) — à noter dans cette section pour éviter la confusion
  qui a motivé ce ticket.
