# T115 — Inventaire et uniformisation du style des boutons

## Contexte

Un design system de boutons existe déjà dans
`apps/desktop/src/renderer/index.css` (`@layer components`) : `.btn-primary`,
`.btn-secondary`, `.btn-danger`, `.btn-sm`. Il n'est cependant pas appliqué de
façon systématique — l'audit du code actuel (117 fichiers `.tsx`, ~90+
boutons) montre :

- Les classes `.btn-primary`/`.btn-secondary` sont majoritairement utilisées
  (65 occurrences), mais souvent avec des **overrides de taille/padding** qui
  contredisent la définition de base (ex. `ModificationControl.tsx` — bouton
  "Publier" — force `text-xs px-3 py-1.5 shadow` au lieu de `text-sm px-4
  py-2` défini par `.btn-primary`).
- Une quinzaine de boutons redéfinissent intégralement en Tailwind inline un
  style quasi identique à `.btn-secondary` (variantes de padding/hover
  différentes selon le fichier), notamment dans les modales (`AddDependencyModal.tsx`,
  `ElementConfigModal.tsx`, `RemoveDependencyModal.tsx`, `RequirementEditModal.tsx`,
  `TestCaseEditModal.tsx`, `StructureTab.tsx`, `ExcelView.tsx`, `baseline.tsx`…).
- `.btn-danger` (style *outline*, `border-red-300 text-red-600`) n'est **jamais
  utilisée** dans le code : tous les boutons de suppression/danger existants
  emploient un style plein rouge ad-hoc (`bg-red-500`/`bg-red-600
  hover:bg-red-600/700 text-white`), avec des paddings et tailles de texte
  qui varient d'un fichier à l'autre.
- De nombreux petits boutons icône (undo/redo, fermer, ajouter une ligne,
  toggle…) utilisent des variantes non standardisées de `p-1 rounded
  hover:bg-hover`.
- Quelques liens stylés comme actions secondaires utilisent une couleur
  bleue hardcodée (`text-blue-600 hover:underline`) au lieu des tokens du
  thème.

Le ticket demande (a) de produire la liste de ces boutons/styles, et (b) de
les uniformiser en prenant pour référence le bouton "Publier"
(`ModificationControl.tsx`) — qui s'avère lui-même, à l'audit, être une
déviation du design system existant plutôt qu'un modèle stable.

## Décisions issues du cadrage humain

- **(Amendement post-Design)** La taille des boutons doit dépendre du
  contexte : les endroits exigus (barre de titre de vue `ViewHeader`,
  popovers, actions en ligne dans une liste/tableau) ont *besoin* de boutons
  plus petits — on ne force pas tout vers une taille unique "standard". En
  contrepartie, le nombre de profils doit rester limité et cohérent : **2
  tailles** (`standard` et `compact`) déclinées sur les **3 couleurs**
  sémantiques déjà actées (`primary`/`secondary`/`danger`), pas une taille
  par bouton. "Publier" garde donc sa taille compacte (`text-xs px-3
  py-1.5`), mais celle-ci devient un profil nommé et partagé
  (`.btn-primary-sm`) plutôt qu'un override local isolé — la distinction
  n'est plus "Publier a un style à lui", mais "Publier est dans un contexte
  compact comme d'autres boutons de `ViewHeader`/popovers". Le détail du
  mapping contexte → profil est du ressort du Design (`T115-design.md`).
- **Le style "danger" (plein rouge, voir ci-dessous) est la réponse au
  besoin de "visuel différent" pour les actions à risque de perte de
  données** : ce n'est pas une taille qui rend une action destructive
  reconnaissable, c'est sa couleur/son style — solide et rouge, par
  opposition à `primary`/`secondary`. Ce style est décliné dans les deux
  tailles (`standard`/`compact`) pour rester reconnaissable même dans un
  popover de confirmation exigu. Pas de 3ᵉ palier de gravité au-delà de
  `danger` : la distinction se fait par la couleur, pas par une escalade de
  styles supplémentaires (cohérent avec l'exigence de nombre de profils
  limité).
- **Style "danger" de référence = plein rouge** (`bg-red-600 hover:bg-red-700
  text-white`, avec variante dark mode), pas le style outline actuellement
  défini par `.btn-danger` dans `index.css`. La classe `.btn-danger` est donc
  **redéfinie** pour matcher le pattern déjà majoritaire dans le code plutôt
  que l'inverse — pas de changement visuel sur les boutons danger existants
  qui suivaient déjà ce pattern, seulement une consolidation vers une classe
  partagée unique (padding/taille de texte unifiés).
- **Périmètre : spec + implémentation complète**, pas seulement l'inventaire.
  Ce ticket couvre l'ajustement des classes du design system ET la migration
  de l'ensemble des boutons du renderer vers ces classes partagées — pas de
  bouton laissé en style ad-hoc dupliqué à l'issue du ticket (hors exceptions
  listées en Hors scope). Le découpage en sprints (par famille de boutons,
  par zone de l'app…) est laissé à la phase Design.

Cet inventaire est une base pour la phase Design (liste des fichiers
identifiée par famille, pas exhaustive ligne à ligne) — le Design précise la
liste complète des fichiers à traiter par sprint.

### 2. Comportement attendu après uniformisation

- Tout élément interactif de type bouton (déclenche une action, pas une
  simple navigation de lien texte) utilise une classe partagée du design
  system — les 3 couleurs (`primary`/`secondary`/`danger`) déclinées en 2
  tailles (`standard`/`compact`, cf. amendement ci-dessus), plus `.btn-sm`,
  `.btn-icon`, `.btn-close` pour les familles hors couleur sémantique — et
  jamais une redéfinition Tailwind inline dupliquant un profil existant. Le
  choix standard/compact dépend du contexte (espace disponible), pas d'une
  préférence par fichier.
- Le bouton "Publier" (`ModificationControl.tsx`) utilise `.btn-primary` sans
  override de padding/taille de police/ombre.
- Tous les boutons de suppression/action destructive utilisent la classe
  `.btn-danger` redéfinie (plein rouge), avec un unique jeu de
  padding/taille de texte cohérent avec les autres boutons de même contexte
  (modale vs. inline vs. compact).
- L'apparence claire/sombre (dark mode) reste correcte pour toutes les
  familles après migration — aucune régression de contraste.
- Les combos `disabled:opacity-*` et `transition-colors`/`transition-opacity`
  restent présents partout où ils existaient déjà (pas de régression de
  feedback visuel).

## Hors scope

- Les badges de statut non cliquables (`rounded-full` coloré selon statut,
  pas de `onClick`) — ce ne sont pas des boutons, aucune action visée ici
  (cf. `STATUS_CLASSES`/`RUN_STATUS_CLASS`/`GLOBAL_RESULT_CLASS` dans
  `routes/requirements.tsx`, `components/impact/RequirementEditModal.tsx`,
  `components/sidebar/SystemPanel.tsx`, etc.).
- Les champs de formulaire (`.input-field`, `select`) — uniquement les
  éléments de type bouton/action.
- Refonte des tokens de couleur ou du dark mode lui-même — seule
  l'application cohérente des classes existantes (et de leurs éventuelles
  nouvelles variantes) est visée, pas une nouvelle palette.
- Ajout d'une bibliothèque de composants UI tierce (headlessui, radix…) pour
  remplacer les `<button>` natifs — hors périmètre, uniformisation par
  classes CSS Tailwind uniquement, cohérent avec l'existant.
- `RichTextToolbar` et les contrôles de l'éditeur riche (TipTap) — surface
  très spécifique avec ses propres contraintes d'intégration, à traiter
  séparément si besoin (non mentionné dans le ticket).

## Points ouverts pour la phase Design

- Liste exhaustive fichier par fichier des boutons à migrer (l'inventaire
  ci-dessus donne les familles et des exemples représentatifs, pas la liste
  complète des ~90+ occurrences).
- Faut-il introduire de nouvelles classes partagées pour "icône seule",
  "élément de menu déroulant" et "lien-action", ou ces cas restent-ils
  volontairement en dehors du système à 4 classes existant (avec une
  convention documentée mais non factorée en classe CSS) ? L'audit suggère
  que ces trois familles sont suffisamment répétées (18, 4+, 3 occurrences)
  pour justifier une classe, mais c'est un arbitrage Design (risque de
  sur-abstraction si les usages divergent trop en pratique).
- Découpage en sprints (ex. : sprint 1 = ajustement `.btn-danger`/retrait des
  overrides `.btn-primary`/`.btn-secondary` + migration des modales ; sprint
  2 = boutons icône/menu/lien restants).
- Faut-il un script/lint (ex. règle ESLint ou grep de CI) empêchant la
  réintroduction de styles de bouton ad-hoc dupliqués à l'avenir, ou
  uniquement une revue manuelle pour ce ticket ? Non demandé explicitement
  par le ticket — à trancher en Design plutôt que supposé.

## Critères d'acceptation

1. `apps/desktop/src/renderer/index.css` : `.btn-danger` est redéfinie en
   style plein rouge (`bg-red-600 hover:bg-red-700 text-white` + variante
   dark mode), `.btn-primary`/`.btn-secondary`/`.btn-sm` conservent leurs
   tailles/paddings actuels (aucune régression visuelle sur les usages déjà
   conformes).
2. Le bouton "Publier" (`ModificationControl.tsx`) utilise un profil de
   bouton partagé et nommé (`.btn-primary` ou son profil compact
   `.btn-primary-sm` — cf. `T115-design.md`), sans override local de
   `text-*`/`px-*`/`py-*`/`shadow` non couvert par ce profil.
3. Aucun bouton de suppression/action destructive du renderer ne reste en
   style rouge ad-hoc dupliqué — tous utilisent `.btn-danger`.
4. Aucune redéfinition Tailwind inline dupliquant `.btn-secondary` (le
   pattern `border border-edge rounded ... text-ink-2 hover:...`) ne subsiste
   dans les modales/panneaux identifiés dans l'inventaire — ils utilisent
   `.btn-secondary`.
5. `git grep` (ou équivalent) sur les paddings caractéristiques des patterns
   ad-hoc recensés (ex. `px-4 py-1.5.*border.*border-edge.*rounded.*text-ink-2`,
   `bg-red-500 hover:bg-red-600`, `bg-red-600 hover:bg-red-700` en dehors de
   `.btn-danger`) ne retourne plus de résultat dans `apps/desktop/src/renderer`.
6. Le thème clair et le thème sombre restent corrects (contraste, couleurs
   de fond/texte/bordure) pour chaque famille de bouton migrée — vérifié
   visuellement sur au moins un représentant de chaque famille dans les deux
   thèmes.
7. Aucune régression fonctionnelle : tous les boutons migrés déclenchent
   toujours la même action, respectent leur état `disabled` existant le cas
   échéant.
8. La liste des familles de boutons et leur classe de référence (produite
   dans ce document, §1) est cohérente avec l'état réel du code à l'issue du
   dernier sprint — mise à jour si l'implémentation diverge de l'inventaire
   initial.
