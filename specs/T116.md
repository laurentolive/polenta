# T116 — Centralisation et uniformisation du thème (dark/clair)

## Contexte

Le thème dark/clair de l'application desktop repose aujourd'hui sur deux sources semi-dupliquées :
- `apps/desktop/src/renderer/index.css` — variables CSS (`--canvas`, `--surface`, `--ink`, `--edge`, `--prim`, `--chart-series-1..8`) déclarées séparément pour `:root` (clair) et `.dark` (sombre)
- `apps/desktop/tailwind.config.js` — mapping manuel de ces variables vers des classes utilitaires Tailwind (`bg-canvas`, `text-ink`, `border-edge`, `bg-hover`...)

Un audit du code (`apps/desktop/src/renderer`) montre que **69 fichiers `.tsx` sur 117 (~59%)** contournent ce système de tokens en utilisant des couleurs Tailwind brutes de la palette par défaut (`slate-`, `red-`, `blue-`, `green-`, `gray-`, `white`, `black`...), notamment pour :
- les états d'erreur (`text-red-500`, `bg-red-50/500`, `border-red-300`...)
- les états de succès (`green-500/600`...)
- les liens et accents (`text-blue-600`, `bg-blue-50`...)
- la barre d'activité (`ActivityBar.tsx`) — toujours `slate-900/800/700/400` quel que soit le thème
- les vues d'impression (routes `print.*.tsx`, ~8 fichiers) — toujours `bg-white text-slate-900`

Aucun token sémantique n'existe aujourd'hui pour erreur/succès/avertissement/lien — d'où le recours systématique à la palette Tailwind brute.

## Description fonctionnelle

T116 consiste à :

1. Remplacer les deux sources actuelles (`index.css` + `tailwind.config.js`, dupliquées et éditées à la main indépendamment) par un fichier de config TypeScript unique — `theme.config.ts` — qui devient la seule source de vérité pour tous les tokens de couleur (existants + nouveaux), pour les deux thèmes clair/sombre.
2. Ajouter les tokens sémantiques manquants : `error`/`error-fg`, `success`/`success-fg`, `warning`/`warning-fg`, `link` (au minimum), avec leurs déclinaisons hover/border si besoin, pour couvrir les usages actuels de `red-`/`green-`/`blue-` observés dans l'audit.
3. Ajouter des tokens dédiés pour les deux familles d'exceptions actuelles (choix validé : elles restent des exceptions visuelles figées, mais pilotées par token plutôt que par classe Tailwind brute) :
   - **ActivityBar** : tokens `activity-bg`, `activity-fg`, `activity-fg-active`, `activity-bg-active`, `activity-fg-disabled` (valeurs fixes, identiques dans les deux thèmes puisque la barre reste volontairement sombre).
   - **Impression** : tokens `print-bg`, `print-ink` (valeurs fixes claires dans les deux thèmes, pour les rendus imprimables/export).
4. Migrer les 69 fichiers identifiés (`ActivityBar.tsx` compris) pour qu'ils utilisent exclusivement les classes Tailwind générées à partir des tokens — plus aucune couleur brute de la palette Tailwind par défaut (`slate-`, `gray-`, `zinc-`, `neutral-`, `stone-`, `red-`, `blue-`, `green-`, `yellow-`, `indigo-`, `purple-`, `pink-`, `white`, `black`) dans le code applicatif, y compris dans les routes `print.*.tsx` (migrées vers `print-bg`/`print-ink`).
5. `index.css` et `tailwind.config.js` sont régénérés/dérivés depuis `theme.config.ts` (mécanisme précis — génération au build, script à lancer manuellement, ou import direct des valeurs JS dans `tailwind.config.js` — à trancher en phase Design).

## Comportements attendus par cas d'usage

- **Bascule clair → sombre (ou inverse)** via `ThemeContext` : tous les écrans de l'app (hors ActivityBar et vues d'impression, volontairement fixes) changent de palette sans qu'aucune zone ne reste bloquée sur l'ancienne palette.
- **Nouvel écran** : un développeur ajoutant un composant ne doit avoir besoin d'aucune couleur Tailwind brute — le token sémantique adapté couvre son besoin (fond, texte, bordure, état interactif, erreur, succès, avertissement, lien).
- **ActivityBar** : reste visuellement identique à aujourd'hui (fond `slate-900`) dans les deux thèmes, mais sa couleur est désormais définie via un token nommé, pas une classe Tailwind brute dans le composant.
- **Impression/export** : les vues restent en rendu clair fixe (fond blanc, texte foncé) indépendamment du thème actif, via leurs propres tokens.
- **Dashboards** : les séries de graphiques (`chart-series-1..8`, déjà tokenisées depuis T77) ne sont pas affectées fonctionnellement par ce ticket (seul leur emplacement de déclaration peut changer si elles migrent dans `theme.config.ts`).

## Critères d'acceptation mesurables

1. `theme.config.ts` existe, déclare l'ensemble des tokens (existants + nouveaux) avec leur valeur clair et sombre, et sert de source unique alimentant `index.css` et `tailwind.config.js`.
2. Recherche de `(bg|text|border|ring|divide|from|to|via)-(slate|gray|zinc|neutral|stone|red|blue|green|yellow|indigo|purple|pink)-[0-9]` et de `\b(bg|text|border)-(white|black)\b` sur `apps/desktop/src/renderer/**/*.tsx` : zéro résultat, y compris dans les routes `print.*.tsx` (hors exceptions listées ci-dessous).
3. Nouveaux tokens `error`/`success`/`warning`/`link` disponibles comme classes Tailwind (ex: `bg-error`, `text-error`, `text-link`, `bg-success`...) et couvrant les usages fonctionnels recensés dans l'audit (messages d'erreur, badges de statut, liens, confirmations).
4. `ActivityBar.tsx` n'a plus de classe Tailwind brute — utilise les tokens `activity-*`.
5. Aucune régression visuelle involontaire : les couleurs actuelles (valeurs hex) sont préservées à l'identique lors du passage aux tokens, sauf harmonisation explicitement décidée en Design (ex: unifier des variantes de rouge `red-500` vs `red-600` utilisées de façon incohérente selon les fichiers vers une seule valeur `--error`).
6. Build + lint TypeScript sans nouvelle erreur.

## Hors scope explicite

- Ajout d'un 3ᵉ thème (contraste élevé, thèmes personnalisés par projet/utilisateur) — T116 couvre uniquement clair/sombre.
- Chargement runtime d'un thème externe (JSON/YAML modifiable par l'utilisateur sans rebuild) — le fichier de config reste un fichier TypeScript du dépôt, pas une préférence utilisateur éditable depuis l'UI.
- Composants tiers dont le style est piloté par une lib externe non Tailwind (ex: rendu interne de `drawio-viewer.min.js`) — non concernés par la vérification de conformité du critère 2.
- Mise en page/pagination des vues d'impression au-delà de leur palette — hors sujet.
