# T118 — Collision d'ID sur les objets à compteur (campagnes, exigences, tests)

## Root cause

`nextCampaignId()` (`campaigns.service.ts`), `nextId()` (`requirements.service.ts`) et
`nextTestId()` (`tests.service.ts`) faisaient chacun un read-modify-write indépendant sur
`config/counters.yaml` :

1. **Pas de verrou** : `create()` n'était pas sérialisé (contrairement à `update()` /
   `addTests()` / etc. dans `campaigns.service.ts`, qui passent par `enqueue()` par ID
   d'objet). Deux créations proches dans le temps pouvaient lire la même valeur de compteur
   avant que l'une des deux n'ait écrit sa mise à jour, produire le même ID, et la seconde
   écriture (`writeYaml` sur `campaigns/<ID>.yaml`) écrasait silencieusement la première
   — pas d'erreur visible, perte de données.
2. **Compteur non recalé sur l'état réel du dossier** : le compteur `config/counters.yaml`
   n'était jamais reconstruit à partir des fichiers `<PREFIX>-XXXX.yaml` existants. Des
   fichiers écrits hors de ce chemin (données seed, édition manuelle) laissaient le compteur
   en retard, prêt à régénérer un ID déjà pris.

**Repro confirmée** dans `C:\Dev\polenta-demo\aspirateur-demo` :
`config/counters.yaml` était resté à `CAMP: 1` alors que `campaigns/CAMP-0001.yaml` à
`CAMP-0004.yaml` existaient déjà (seed jamais passée par le compteur). Une première création
via l'UI ("test sprint") avait déjà régénéré `CAMP-0001` et écrasé le seed correspondant
(`Campagne validation démarrage & sécurité système`) — voir commit `4d1d753 test update`
dans l'historique de ce repo produit. Rejoué à l'identique aujourd'hui : la création
successive de 3 campagnes ("test 1", "test 2", "test 3") n'a produit que 2 fichiers propres
(`CAMP-0002`, `CAMP-0003`) ; la 3e a été absorbée dans `CAMP-0001` existant.

## Correctif appliqué

Nouveau helper partagé `apps/desktop/src/main/services/id-counter.util.ts` — `nextCounterId(git, repoPath, prefix, dir)` :

- **Sérialise** chaque lecture+écriture de `counters.yaml` par `repoPath` via une file de
  promesses en mémoire (même pattern que `CampaignsService.enqueue`), pour éliminer la
  course entre créations concurrentes dans le même process.
- **Recale le compteur** au démarrage de chaque calcul : le prochain numéro est
  `max(compteur stocké, plus grand <PREFIX>-NNNN présent dans dir) + 1`. Un compteur en
  retard s'auto-corrige au lieu de collisionner avec un fichier déjà présent.

`campaigns.service.ts`, `requirements.service.ts` et `tests.service.ts` délèguent maintenant
à ce helper au lieu de dupliquer chacun leur propre logique read-modify-write.

Portée volontairement limitée à ces trois services (ceux vérifiés comme partageant le
pattern défaillant) — `saved-queries.service.ts` / `dashboards.service.ts` (compteurs
`QUERY`/`DASHBOARD`) n'ont pas été touchés, hors périmètre de ce ticket.

## Comment vérifier

1. `pnpm typecheck` dans `apps/desktop` — zéro erreur (déjà validé).
2. Script de sanity manuel (pas d'infra de test unitaire existante sur ces services) :
   reconstitue l'état réel de `polenta-demo` (compteur `CAMP: 1`, fichiers jusqu'à
   `CAMP-0004`) puis lance 3 créations concurrentes → produit `CAMP-0005`, `CAMP-0006`,
   `CAMP-0007`, tous uniques, aucune collision avec les fichiers existants.
3. Manuellement dans l'app : ouvrir un repo produit, créer plusieurs campagnes/exigences/
   tests à la suite rapidement → chacun doit obtenir un ID distinct, aucun ne doit écraser
   un objet existant.

## Suite

Les données de `C:\Dev\polenta-demo\aspirateur-demo` restent polluées par les collisions
passées (`CAMP-0001` mélange "test sprint" + le run destiné à "test 2" ; "test 2" n'a jamais
eu son propre fichier). C'est un repo produit séparé (pas ce repo outil) — nettoyage à traiter
à part, pas inclus dans ce ticket.
