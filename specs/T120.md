# T120 — Suppression du niveau "Sous-composant" (Vue Système + Structure)

## Contexte

T113 a introduit la possibilité de définir plusieurs `SystemNode` locaux dans le `schema.yaml`
d'un même repo (`root` + sous-composants locaux, sans repo git séparé). Pour permettre de choisir
lequel parcourir, T113 a ajouté un second combobox **"Sous-composant"** dans la Vue Système
(`SystemPanel.tsx` l.335-353), en cascade sous le combobox **"Composant"** existant (T72, un par
repo du workspace) — masqué uniquement quand le repo n'a qu'un seul `SystemNode` (`root`).

Ce second niveau de sélection est perturbant pour l'utilisateur : un sous-composant local (même
repo, même historique git) et un composant en repo séparé (submodule) sont conceptuellement du
même ordre — "un composant du système" (cf. `SPEC-TEMPLATES.md` §3) — mais seul le second obtient
aujourd'hui une entrée directe dans "Composant", le premier étant relégué à un niveau de navigation
supplémentaire. Rien dans le modèle de données ne justifie cette hiérarchie à deux étages : elle
est un artefact de l'implémentation (deux structures de données distinctes — `flatNodes`/
`repoOptions` au niveau workspace, `schema.nodes` au niveau repo — cf. exploration ci-dessous),
pas une distinction que l'utilisateur doit percevoir.

Même remarque, dans une moindre mesure, dans l'onglet Structure (Modèle de données) : un
sous-composant local y est déjà traité sans badge d'erreur ni distinction de droits depuis T113,
mais son rendu (ligne texte simple, sans icône, en retrait) reste visuellement plus discret qu'un
repo (`RepoRow` : icône `FolderGit2`/`GitFork`, sélecteur de branche, poids visuel de "composant").

**Un composant local ou en repo séparé doit être vu de la même manière comme un composant** — la
notion de "sous-composant" comme niveau de navigation ou de présentation distinct n'a pas de raison
d'exister côté UI. Elle reste une distinction purement technique (présence ou non d'un repo git
séparé), pertinente uniquement là où l'action de l'utilisateur en dépend réellement (ex. le choix
"Composant local" vs "repo séparé" à la création, `AddDependencyModal`, inchangé par ce ticket).

## Comportement attendu

### 1. Vue Système — combobox unique "Composant"

- Le combobox **"Sous-composant"** est supprimé. Le combobox **"Composant"** devient la seule
  étape de sélection entre le repo/`SystemNode` et le type d'élément.
- Il liste, à plat, une entrée par `SystemNode` de chaque repo du workspace (root + sous-composants
  locaux), au lieu d'une entrée par repo comme aujourd'hui.
- **Repo à un seul `SystemNode` (`root`)** — cas le plus courant : une seule entrée, libellée
  exactement comme l'entrée "Composant" actuelle (mount name, suffixé du `label` du node si
  présent). **Aucun changement visuel ni de comportement** pour un projet qui n'utilise pas de
  sous-composants locaux (même principe de non-régression que T113).
- **Repo à plusieurs `SystemNode`** — un séparateur visuel (groupe/optgroup, non sélectionnable)
  identifie le repo d'origine ; en dessous, une entrée par `SystemNode` de ce repo (root inclus),
  libellée par son propre `label` (repli sur `name`). Choisir n'importe quelle entrée sélectionne
  en une seule action le repo et le `SystemNode` correspondants (plus de sélection en cascade).
- Sélectionner une entrée recharge tout le contexte (schéma, arbre, index, combobox Élément réduit
  au premier type du node choisi) — comportement identique à aujourd'hui pour un changement de
  Composant ou de Sous-composant (les deux se fondent en une seule transition).
- Aucun changement du combobox **"Élément"** : il continue de lister les types du `SystemNode`
  sélectionné.

### 2. Persistance / URL — inchangé dans son format

- Les search params `repo`+`node` (`/product`) et `repo`+`component` (`/components`) sont conservés
  tels quels : ils encodaient déjà la paire (repo, `SystemNode`) nécessaire, uniquement pilotée
  jusqu'ici par deux comboboxes distincts. Un lien existant reste valide sans migration.
- La restauration de dernière sélection (T52, `localStorage` par projet) continue de fonctionner
  à l'identique — elle stocke déjà la paire (repo, node), pas les comboboxes eux-mêmes.

### 3. Structure (Modèle de données) — parité visuelle

- Un sous-composant local est présenté dans l'arbre avec le même poids visuel qu'un composant en
  repo séparé (icône dédiée au lieu d'une simple ligne de texte, même style de libellé) — tout en
  restant imbriqué sous le repo qui le contient physiquement (il vit dans le `schema.yaml` de ce
  repo ; ce n'est pas une hiérarchie de navigation mais une contrainte de stockage, cf. Contexte).
- Aucune régression sur les actions déjà en place pour un sous-composant local (`+ élément`,
  renommer, supprimer) ni sur le sélecteur de branche (qui reste propre aux repos séparés, un
  sous-composant local n'ayant pas de branche propre).
- Le vocabulaire "sous-composant" peut rester dans le code/les commentaires techniques (il décrit
  une réalité de stockage réelle) mais ne doit plus apparaître comme un **libellé visible par
  l'utilisateur** dans l'UI (tooltips, titres de modale, textes d'aide compris).

## Hors scope

- Pas de changement du modèle de données (`SystemNode`, `schema.yaml`, `WorkspaceTreeNode`) — la
  distinction technique repo séparé / sous-composant local reste portée par les mêmes structures
  (cf. exploration : un `SystemNode` n'a toujours pas de champ `url`, un `WorkspaceTreeNode` reste
  la seule entité avec `url`/`pin`). Ce ticket ne fusionne que la présentation, pas la donnée.
- Pas de changement à `AddDependencyModal`/`StructureTab` : le choix explicite "Composant local"
  vs "repo séparé" à la **création** (T113) reste nécessaire et inchangé — c'est le seul endroit où
  la distinction technique doit rester visible, puisque l'utilisateur y fait un choix réel de
  gestion de configuration.
- Pas de renommage des search params d'URL (`node`/`component` restent tels quels).
- Pas de changement à `Conformité interfaces` / `interface-compliance.service.ts` — les rôles/
  `implements` restent réservés aux repos séparés (cf. `SPEC-TEMPLATES.md` §3a-3b), un
  sous-composant local n'en a jamais eu.
- Pas de migration de données existantes — un projet avec des sous-composants locaux créés avant
  ce ticket bénéficie du nouveau rendu sans script ni changement de fichier.

## Critères d'acceptation

- [ ] Le combobox "Sous-composant" n'existe plus dans `SystemPanel.tsx` ; un seul combobox
  "Composant" reste visible.
- [ ] Un projet sans sous-composant local (un seul `SystemNode` par repo) affiche exactement la
  même liste "Composant" qu'avant ce ticket — aucune régression visuelle ni fonctionnelle.
- [ ] Un projet avec un repo à plusieurs `SystemNode` affiche, dans le combobox "Composant", un
  séparateur par repo et une entrée par `SystemNode` (root inclus) sous ce séparateur.
- [ ] Sélectionner un `SystemNode` local depuis ce combobox recharge correctement le combobox
  Élément et l'arbre sur ce node, en une seule interaction utilisateur.
- [ ] Un lien direct existant (`?repo=...&node=...` ou `?repo=...&component=...`) continue de
  résoudre exactement le même composant qu'avant ce ticket.
- [ ] La restauration de dernière sélection (T52) fonctionne à l'identique après ce ticket.
- [ ] Dans l'onglet Structure, un sous-composant local a une icône dédiée et un poids visuel de
  ligne comparable à un repo, tout en restant imbriqué sous son repo conteneur.
- [ ] Aucun libellé visible par l'utilisateur ne contient le mot "sous-composant" (tooltips,
  titres de modale compris) dans la Vue Système et l'onglet Structure.
- [ ] TypeScript/lint : zéro nouvelle erreur.
