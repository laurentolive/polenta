# T123 — Un composant local a les mêmes capacités qu'un composant avec repo (imbrication + interfaces)

## Contexte

T113 a introduit les **sous-composants locaux** : un repo peut définir plusieurs `SystemNode` dans
`nodes[]` de son `schema.yaml`, en plus de `root`, sans passer par un repo séparé
(`polenta-repo.yaml`). Mais T113 les a traités comme une catégorie à part, avec des capacités
volontairement réduites par rapport à un composant en repo séparé :

- **Pas d'imbrication** : un sous-composant local ne peut pas lui-même contenir d'autre
  sous-composant. `SystemNode` (`packages/types/src/schema.ts:59-65`) est un tableau plat,
  `root` et tous les sous-composants locaux sont des frères sans relation parent/enfant. Dans
  `StructureTab.tsx`, la ligne d'un nœud local n'offre que `AddElementMenu` (+ exigence/test/
  campagne, lignes 179-202) — jamais `AddMenu` (+ Composant/+ Interface, lignes 140-177), qui n'est
  rendu que sur `RepoRow` (repo racine ou dépendance séparée).
- **Pas d'interfaces** : `roles`/`implements` (le mécanisme d'interface, `SPEC-TEMPLATES.md`
  §3a-3b) sont déclarés au niveau **racine du fichier `schema.yaml`**
  (`ProjectSchema.roles`/`ProjectSchema.implements`, `schema.ts:119-129`), donc décrivent **le
  repo entier**, jamais un `SystemNode` précis. Un sous-composant local n'a aucun moyen d'exposer
  un rôle ou d'implémenter une interface — T113 l'excluait explicitement ("un sous-composant local
  n'implémente/n'expose pas d'interface dans ce ticket").

**Correction de cadrage (retour utilisateur)** : cette distinction "composant" / "sous-composant"
n'a pas de raison d'être. **Il n'existe qu'une seule notion : le composant.** Un composant est
local (vit dans le `schema.yaml` du repo courant, versionné avec lui) ou a son propre repo
(dépendance déclarée dans `polenta-repo.yaml`) — c'est un simple attribut d'implémentation, pas
deux catégories fonctionnelles différentes. Un composant local doit pouvoir :
- contenir d'autres composants (locaux), à n'importe quelle profondeur ;
- avoir ses propres éléments (exigences/tests/campagnes) et des liens vers/depuis d'autres
  éléments — **déjà le cas aujourd'hui**, `sourceRefs`/`targetRefs` (`schema.ts:96-105`) référencent
  un composant par nom (`composant::type`) ou par catégorie, sans distinction locale/repo séparé ;
  aucun changement nécessaire sur ce point, seulement une vérification de non-régression ;
- exposer des rôles et/ou implémenter des interfaces — **actuellement impossible**, à corriger ici.

Ce ticket fusionne donc l'ancien **T124** (interfaces sur composant local, retiré de `TICKETS.md`,
absorbé ici) avec l'imbrication : les deux ne sont que deux facettes de la même correction
("un composant local = un composant, point").

Pour l'imbrication, le pattern à suivre existe déjà dans le code, côté **repos** :
`WorkspaceTreeNode.children: WorkspaceTreeNode[]` (`packages/types/src/polenta-workspace.ts:36-56`)
et `dfsCollect`/`buildWorkspaceTree` (`apps/desktop/src/main/services/workspace-tree.service.ts`)
font déjà une descente récursive à profondeur illimitée pour les dépendances de dépendances. Ce
ticket applique le même principe à l'intérieur d'un même repo, entre `SystemNode` locaux.

**Décisions d'architecture validées avec l'utilisateur avant rédaction de cette spec :**

1. **Unicité du nom** : un `name` de `SystemNode` reste unique sur l'ensemble de l'arbre local d'un
   repo, quelle que soit sa profondeur. **Aucun changement au format `objectTypeRef`**
   (`nodeName::typeName`, résolu par `findObjectTypeDef`) : l'imbrication est un regroupement
   organisationnel, elle ne devient jamais un chemin dans les refs.
2. **Libellé du combobox Composant (Vue Système, T120)** : reste à plat (T120 a volontairement
   supprimé toute notion de sous-composant dans cette liste), mais le label d'une entrée
   profondément imbriquée devient le **chemin complet des ancêtres locaux** jusqu'au nœud, séparés
   par `›` (ex. `Boîtier › Capteurs`), sous le `groupLabel` du repo inchangé.
3. **Reparenting** : hors scope pour ce ticket — même logique que T113 avait exclu la conversion
   local ↔ repo séparé après coup. On choisit l'emplacement d'un composant à la création.
4. **`roles`/`implements` migrent du niveau racine du `schema.yaml` vers le `SystemNode`
   lui-même** (`root` compris). Chaque composant — local, avec repo séparé, imbriqué ou non — porte
   ses propres `roles?`/`implements?`. Ce qui était `ProjectSchema.roles`/`ProjectSchema.implements`
   (décrivant "ce repo est une interface"/"ce repo implémente X") devient
   `SystemNode.roles`/`SystemNode.implements` du node `root` de ce repo — migration mécanique,
   sémantique inchangée pour le cas repo-séparé existant.
5. **MCP `add_component`** (T122) : gagne un paramètre optionnel `parentName`, pour rester
   cohérent avec `SPEC-TEMPLATES.md` §3 qui documente déjà ce tool comme suivant "strictement le
   pattern sous-composant local" de l'UI.

## Comportement attendu

### Imbrication

1. **Modèle de données.** `SystemNode` gagne un champ `children?: SystemNode[]` (tableau
   récursif, même principe que `WorkspaceTreeNode.children`). `root` et les composants locaux de
   premier niveau restent au niveau `schema.nodes[]` actuel ; un composant local peut désormais
   porter ses propres `children[]`, récursivement, sans limite de profondeur a priori.
2. **Création d'un composant local imbriqué depuis l'UI.** La ligne d'un composant local dans
   `StructureTab` gagne une action **"+ Composant local"**, en plus de `AddElementMenu` existant
   (+ exigence/test/campagne) — même flow que "+ Composant" → case "Composant local" au niveau
   `root`/repo (T113), mais ajoute le nouveau `SystemNode` dans `children[]` du nœud ciblé plutôt
   qu'au niveau racine de `schema.nodes[]`.
3. **Un composant en repo séparé ne peut jamais être imbriqué sous un composant local** — cette
   limite est **technique**, pas fonctionnelle : un composant en repo séparé est un git submodule
   déclaré dans `polenta-repo.yaml`, un fichier par repo, résolu au niveau du repo lui-même, pas
   au niveau d'un `SystemNode` particulier à l'intérieur d'un `schema.yaml`. Ce n'est donc pas une
   capacité manquante à donner au composant local (contrairement aux interfaces, cf. ci-dessous) :
   la ligne d'un composant local n'offre jamais "+ Composant (repo séparé)", uniquement
   "+ Composant local" ; seules les lignes de repo (`RepoRow`) gardent cette option.
4. **Affichage récursif dans l'arbre Structure.** Un composant local imbriqué s'affiche sous son
   parent avec un indent croissant, comme `RepoRow` le fait déjà pour `WorkspaceTreeNode.children`
   — même profondeur non limitée, même comportement d'expand/collapse.
5. **Suppression en cascade.** Supprimer un composant local qui a des `children[]` supprime tout le
   sous-arbre — confirmation explicite mentionnant le nombre de sous-composants et d'éléments qui
   seront supprimés, cohérent avec "Dossier non vide : confirmation explicite" déjà en vigueur pour
   l'arbre de la Vue Système.
6. **Combobox "Composant" (Vue Système).** Une entrée correspondant à un composant local imbriqué
   affiche le chemin complet de ses ancêtres locaux, séparés par `›`, sous le `groupLabel` du repo.

### Interfaces sur n'importe quel composant

7. **`roles`/`implements` deviennent des champs de `SystemNode`.** N'importe quel composant —
   `root`, local, imbriqué à n'importe quelle profondeur, ou avec repo séparé — peut déclarer
   `roles?: RoleDefinition[]` (il expose un contrat) et/ou `implements?: ImplementsDeclaration[]`
   (il implémente une ou plusieurs interfaces avec certains rôles). `ProjectSchema.roles`/
   `ProjectSchema.implements` (niveau fichier) sont retirés au profit de ces champs sur `root`.
8. **Migration.** À la lecture d'un `schema.yaml` existant avec `roles`/`implements` au niveau
   racine, ces valeurs sont relues comme celles du node `root` (migration transparente à la
   sauvegarde suivante — pas de script de migration séparé nécessaire, `SchemaService` absorbe la
   conversion à la lecture/écriture).
9. **Badge "Interface".** Le badge violet "Interface" (`StructureTab.tsx`, aujourd'hui posé sur
   une ligne de repo via `WorkspaceTreeNode.isInterface`, dérivé de `schema.roles.length > 0` au
   niveau fichier) doit :
   - pour une ligne de repo (`RepoRow`) : continuer de se dériver du node `root` de ce repo
     (`schema.nodes.find(n => n.name === 'root')?.roles`) — comportement visuellement inchangé
     pour le cas déjà existant ;
   - pour un composant local (imbriqué ou non) : s'afficher directement si ce `SystemNode` a des
     `roles` non vides — nouveau, puisque ce cas n'existait pas avant ce ticket.
10. **Édition roles/implements pour un composant local.** La popup d'édition d'un composant local
    (`StructureTab.tsx`/`AddDependencyModal.tsx` réutilisé ou étendu) gagne les mêmes sections que
    la popup d'édition d'un nœud dépendance aujourd'hui (T110) : "Rôles exposés par ce composant"
    (catalogue `roles`) et "Interfaces implémentées" (`implements[]`, une ligne par
    `{interface, roles}`) — mêmes composants d'édition, réutilisés tels quels.
11. **Matrice de conformité (`interface-compliance.service.ts`).** `getComplianceMatrix` itère
    aujourd'hui `tree.nodes` (un `WorkspaceTreeNode` par repo) et filtre `node.isInterface` — doit
    devenir un parcours récursif de **tous les `SystemNode`** de tous les repos (root + composants
    locaux à toute profondeur), pas seulement les racines de repo. Un composant local avec `roles`
    non vides apparaît comme interface dans la matrice ; un composant local avec `implements` non
    vide est compté dans la couverture par rôle, exactement comme un composant avec repo séparé
    aujourd'hui.
12. **Élément/lien sur un composant local** — vérification de non-régression uniquement (déjà
    fonctionnel depuis T113) : créer une exigence taguée par rôle (champ `multi_enum` `roles`,
    `SPEC-REQ-requirements.md` §3) sur un composant local dont le parent (ou lui-même) expose des
    `roles` doit sourcer ses options depuis ce catalogue, exactement comme pour un composant avec
    repo séparé.

### MCP

13. **`add_component`** gagne un paramètre optionnel `parentName` (nom d'un `SystemNode` existant
    dans le même repo). Absent → comportement actuel inchangé (ajout au niveau racine de
    `schema.nodes[]`). Présent mais introuvable → erreur explicite.
14. `SPEC-MCP-SERVER.md` à mettre à jour en fin de ticket ; envisager si `add_component`/un tool
    dédié doit aussi permettre de déclarer `roles`/`implements` sur un composant local existant
    (à confirmer en Design — pas un pré-requis bloquant si le volume de travail est trop important
    pour un seul ticket, auquel cas documenter la limitation).

## Hors scope

- **Reparenting** : pas de possibilité de déplacer après coup un composant local existant pour le
  faire changer de parent. Le choix du parent se fait à la création uniquement. Réorganiser après
  coup = supprimer et recréer (le réordonnancement ↑/↓ entre frères continue de fonctionner).
- **Conversion local ↔ repo séparé** après coup — déjà hors scope depuis T113, inchangé.
- **Imbriquer un composant en repo séparé sous un composant local** — exclu pour une raison
  technique (cf. Comportement attendu §3), pas une limitation fonctionnelle à lever.
- **Limite de profondeur codée en dur** — non prévue a priori, sauf si le Design ou les tests
  manuels révèlent un problème de performance/ergonomie concret nécessitant un garde-fou ; dans ce
  cas, le documenter comme divergence plutôt que comme pré-requis de cette spec.
- **Drag & drop dans l'arbre Structure** pour réorganiser les composants — hors scope, cf.
  Reparenting.

## Critères d'acceptation

- [ ] Depuis la ligne d'un composant local dans `StructureTab`, une action "+ Composant local"
  crée un nouveau `SystemNode` enfant (dans `children[]`), avec le même formulaire minimal (Nom).
- [ ] Le nouveau composant local imbriqué apparaît immédiatement dans l'arbre Structure, indenté
  sous son parent, avec les mêmes actions qu'un composant local non imbriqué.
- [ ] Imbriquer sur au moins 3 niveaux de profondeur fonctionne sans erreur.
- [ ] La ligne d'un composant local, imbriqué ou non, n'offre jamais "+ Composant (repo séparé)" —
  uniquement sur les lignes de repo (`RepoRow`).
- [ ] Un composant local (imbriqué ou non) peut déclarer des `roles` (catalogue de rôles exposés)
  et/ou des `implements` (interfaces implémentées) depuis la même popup d'édition qu'un composant
  avec repo séparé aujourd'hui.
- [ ] Un composant local avec `roles` non vides affiche le badge "Interface", identique
  visuellement à celui d'un repo interface.
- [ ] La matrice de conformité (Dashboards ou vue dédiée) inclut les composants locaux ayant des
  `roles`/`implements`, avec la même logique de couverture par rôle qu'un composant repo séparé.
- [ ] Une exigence taguée par rôle sur un composant local source correctement ses options
  `roles` depuis le catalogue du composant/de son ancêtre concerné.
- [ ] Créer une exigence dont l'`objectTypeRef` cible un composant local imbriqué à profondeur ≥ 2
  fonctionne de bout en bout (formulaire UI → fichier → listes/dashboards/requêtes SQL), avec le
  bon préfixe d'ID.
- [ ] Le combobox "Composant" de la Vue Système affiche le chemin `Parent › Enfant` pour un
  composant local imbriqué, sous le bon `groupLabel` de repo.
- [ ] Supprimer un composant local ayant des enfants déclenche une confirmation explicite
  mentionnant le nombre de sous-composants/éléments supprimés, puis supprime tout le sous-arbre.
- [ ] Un `schema.yaml` existant avec `roles`/`implements` au niveau racine (ancien format) continue
  de fonctionner à l'identique après migration transparente vers le node `root`.
- [ ] Le tool MCP `add_component` accepte un `parentName` optionnel ; un `parentName` introuvable
  renvoie une erreur explicite.
- [ ] `findNodeUsingPrefix` (unicité de préfixe projet) et la validation de nom unique couvrent
  tout l'arbre imbriqué, pas seulement le premier niveau.
- [ ] TypeScript/lint : zéro nouvelle erreur.
