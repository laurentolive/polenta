# T125 — Bug : curseur qui saute dans l'édition richtext de la Vue Excel (après collage)

## Reproduction rapportée

Dans la Vue Excel (`ExcelView.tsx`), ouvrir le popover d'édition d'une cellule richtext
(clic sur une cellule dont le champ est de type `richtext`), puis coller du contenu
(Ctrl+V) dans l'éditeur : le curseur saute de manière inopinée à une position inattendue
(typiquement le début du document) peu après le collage, alors que l'utilisateur
s'attend à ce qu'il reste à l'endroit où le contenu vient d'être inséré.

## Root cause

`RichTextField.tsx` maintient un effet de « resynchronisation externe » qui réagit à
tout changement de la prop `value` (ex. rechargement depuis le serveur, changement
d'objet édité) :

```ts
useEffect(() => {
  if (isInitialSyncRef.current) { isInitialSyncRef.current = false; return }
  if (!editor) return
  const current = (editor.storage.markdown as MarkdownStorage).getMarkdown()
  if (current !== value) {
    editor.commands.setContent(value, false)   // ← replace le curseur en tête de doc
    setRawValue(value)
  }
}, [value])
```

Or, dans le flux normal d'édition (`ExcelView` → `SystemView`/`SystemViewContext`), la
prop `value` reçue par `RichTextField` n'est pas uniquement mise à jour par des sources
externes : chaque frappe/collage déclenche `onUpdate` → `onChange(md)` →
`handleAutoInlineEdit` → `setPendingEdits` (synchrone), ce qui fait redescendre le
*même* markdown comme nouvelle prop `value` dès le rendu suivant — un simple écho de
l'édition que le champ vient lui-même de produire, pas un changement externe.

Le code comparait cet écho à un `getMarkdown()` recalculé (`current`) plutôt qu'à la
chaîne réellement émise. Cette comparaison est fragile car le round-trip
parse→sérialisation de `tiptap-markdown` n'est pas toujours une identité stricte (le
fichier documente déjà ce phénomène pour le cas du montage initial : un `\n` brut dans
un paragraphe ne survit pas au round-trip). Un collage y est particulièrement exposé
(tableaux insérés via `insertTable`/`fillPastedTable`, images, ponctuation échappée par
le sérialiseur…) : le moindre mismatch entre `current` et l'écho `value` déclenchait un
`setContent(value, false)` inutile, qui réinitialise la sélection ProseMirror — d'où le
saut de curseur observé juste après un Ctrl+V.

## Correctif appliqué

`apps/desktop/src/renderer/components/RichTextField.tsx` :

- Ajout d'un ref `lastEmittedValueRef`, mis à jour dans `onUpdate` avec le markdown que
  le champ vient lui-même de calculer et de transmettre via `onChange`.
- L'effet de resynchronisation externe compare désormais la prop `value` entrante à ce
  ref *avant* toute autre chose : si elle correspond exactement à ce que le champ vient
  d'émettre, c'est un écho de sa propre édition — l'effet retourne sans toucher à
  l'éditeur ni à sa sélection.
- Le `getMarkdown()` recalculé (`current`) et `setContent` restent utilisés uniquement
  pour les changements réellement externes (ex. bascule de champ/objet édité, valeur
  rechargée depuis le serveur différente de la dernière édition locale).

Correctif minimal, ciblé sur `RichTextField.tsx` — aucune modification de
`ExcelView.tsx`/`SystemViewContext.tsx` (le flux pendingEdits/autosave existant reste
inchangé).

## Comment vérifier

1. Ouvrir un objet avec un champ richtext dans la Vue Excel, cliquer sur la cellule pour
   ouvrir le popover d'édition.
2. Placer le curseur au milieu d'un paragraphe existant et coller (Ctrl+V) :
   - du texte simple depuis une autre application,
   - un tableau copié depuis Excel (chemin `handlePaste` → `extractTableRows`/
     `fillPastedTable`),
   - une image (chemin `handlePaste` → `api.image.writePaste`).
3. Dans les trois cas, vérifier que le curseur reste positionné juste après le contenu
   collé (pas de saut au début du document) et que l'on peut continuer à taper
   immédiatement à cet endroit.
4. Vérifier la non-régression : changer de cellule/objet édité (popover fermé puis
   rouvert sur un autre champ) affiche bien le contenu correct — la resynchronisation
   externe fonctionne toujours pour un changement réel de valeur.
5. `npx tsc --noEmit` sur `apps/desktop` : aucune nouvelle erreur (vérifié).
