# T128 — Bug : contenu de fin de richtext tronqué ~1s après édition d'une liste

## Reproduction rapportée

Dans la Vue Excel (`ExcelView.tsx`), ouvrir le popover d'édition d'une cellule
richtext, ajouter une ligne dans une liste (ex. sortir de la liste en tapant
Entrée deux fois, ce qui crée un paragraphe vide après la liste) : environ une
seconde plus tard, le curseur est déplacé en fin de document et le contenu
vide de fin (paragraphe/ligne qui vient d'être ajouté) a disparu.

## Root cause

`autoSaveMutation` (`SystemView.tsx`, sauvegarde debattue à 800 ms d'un champ
édité inline) :

```ts
onSuccess: (_, variables) => {
  qc.invalidateQueries({ queryKey: ['objects', ...] })   // pas attendu
  qc.invalidateQueries({ queryKey: ['object', ...] })     // pas attendu
  clearPendingEditsFor(variables.objectId, variables.field, variables.value)
},
```

`invalidateQueries` déclenche un refetch réseau/IPC (asynchrone) mais n'est pas
attendu : `clearPendingEditsFor` s'exécute juste après, dans le même tick,
avant que ce refetch n'ait eu le temps d'aboutir. Or `objects`
(`SystemView.tsx`) ne masque la donnée serveur que via `pendingEdits` :

```ts
const objects = useMemo(() => rawObjects.map(o => {
  const edits = pendingEdits[normalized.id]
  return edits ? { ...normalized, ...edits } : normalized
}), [rawObjects, pendingEdits])
```

Pendant la fenêtre entre la synchronisation de `clearPendingEditsFor` (qui
retire l'override local) et l'arrivée effective du refetch, `objects` retombe
sur `rawObjects` tel qu'il était **avant** la sauvegarde — l'ancienne valeur,
sans la ligne qui vient d'être ajoutée. Ce changement de prop `value` atteint
`RichTextField.tsx`, dont l'effet de resynchronisation externe (voir T125 —
protégé contre l'écho de sa propre édition via `lastEmittedValueRef`, mais pas
contre un changement réellement différent) le traite comme un changement
légitime et appelle `editor.commands.setContent(value, false)` : le document
revient à cet état antérieur. Un paragraphe vide en fin de document n'ayant
aucune représentation possible en markdown (contrairement à un item de liste
vide, qui lui survit au round-trip grâce à son marqueur `-`/`1.` explicite),
il est structurellement absent de cette valeur antérieure — d'où sa
disparition visible, et le saut du curseur (position par défaut de
`setContent`).

Confirmé par test : reproduit de façon intermittente sur le code d'avant
correctif (le délai exact entre la dernière frappe et la vérification change
si la fenêtre de la course est atteinte ou non), jamais reproduit après
correctif sur plusieurs essais avec le même scénario/timing.

## Correctif appliqué

`apps/desktop/src/renderer/components/system/SystemView.tsx`,
`autoSaveMutation.onSuccess` : les deux `invalidateQueries` sont désormais
attendus (`await Promise.all([...])`) avant l'appel à
`clearPendingEditsFor`. Le cache est ainsi à jour avec la valeur réellement
sauvegardée avant que le filet de sécurité local (`pendingEdits`) ne soit
retiré — plus de fenêtre où `objects` peut refléter une donnée pré-sauvegarde
pendant que `pendingEdits` ne la masque plus.

Correctif minimal, localisé à ce seul `onSuccess`. Le même motif
(`invalidateQueries` non attendu suivi d'un clear de pending state) existe
aussi dans la mutation de transition de statut un peu plus bas dans
`SystemView.tsx` (`clearPendingEditsFor(objectId, 'status')`) — non corrigé
ici car le champ `status` n'est pas édité via `RichTextField` (pas de perte de
curseur/contenu observable de la même façon) et le correctif doit rester
limité au périmètre du bug signalé ; à traiter séparément si un symptôme
similaire y est constaté.

## Comment vérifier

1. Ouvrir un objet avec un champ richtext dans la Vue Excel, ouvrir le
   popover d'édition.
2. Créer une liste à puces avec un item, appuyer deux fois sur Entrée pour
   sortir de la liste (crée un paragraphe vide en fin de document).
3. Attendre au moins 1,5 s sans autre interaction, puis taper un caractère :
   il doit atterrir dans ce paragraphe vide (pas de saut de curseur, pas de
   perte de contenu).
4. Répéter plusieurs fois — le bug d'avant correctif était intermittent
   (dépendant du timing exact du round-trip réseau/IPC), donc un seul essai
   sans reproduction ne suffit pas à valider la non-régression du cas
   contraire.
5. `npx tsc --noEmit` sur `apps/desktop` : aucune nouvelle erreur (vérifié).
