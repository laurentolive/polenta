# T129 — Vue Système : fusionner les comboboxes "Composant" et "Élément" en un seul combobox filtrable

## Contexte

Le panel Système (`SystemPanel.tsx`) fixe aujourd'hui le contexte d'édition (quel `SystemNode` +
quel type d'élément) en **deux actions obligatoires et séquentielles** :

1. Combobox **Composant** (`SystemPanel.tsx:359-372`) — liste plate `flattenSystemNodes` de tous
   les `SystemNode` du workspace (racine + dépendances + composants locaux imbriqués à toute
   profondeur, T120/T123), groupée par repo (`<optgroup>`) quand le workspace a plusieurs repos.
   Un composant imbriqué est libellé par le chemin de ses ancêtres locaux séparés par `›`
   (`SystemViewContext.tsx:224-246`).
2. Combobox **Élément** (`SystemPanel.tsx:381-400`) — liste les `ObjectTypeDefinition` du
   `SystemNode` choisi à l'étape 1. **Aucune valeur par défaut** tant que l'étape 1 n'a pas eu
   lieu et que l'étape 2 n'a pas été faite explicitement une première fois par l'utilisateur
   (`selectedTypeId = urlType ?? ''`, `SystemViewContext.tsx:260`) — donc choisir un composant
   sans choisir ensuite un type ne mène à rien d'exploitable dans l'arbre/la vue document.

Ce ticket fusionne les deux en **un seul combobox filtrable par texte libre**, une entrée =
une paire (`SystemNode`, `ObjectTypeDefinition`), sélectionnable en une seule action.

**Décisions validées avec l'utilisateur avant rédaction de cette spec :**

1. **Pas de chemin hiérarchique façon explorateur de fichiers** pour la partie inter-repo du
   libellé : le workspace autorise des dépendances diamant (`DiamondConflict`,
   `polenta-workspace.ts:70-76` — un repo peut être requis par plusieurs parents avec
   `requiredBy: string[]`), donc un composant partagé entre repos n'a pas de chemin canonique
   unique. Le combobox Composant actuel contourne déjà ce problème en utilisant `flatNodes`
   (liste plate dédupliquée par repo, `useWorkspaceStructure.ts`) plutôt que `tree`/`logicalTree`
   — ce choix est conservé. Le chemin `›` (T123) reste utilisé, lui, pour l'imbrication **locale**
   (même repo, `SystemNode.children`), qui est un arbre strict sans ambiguïté de parent.
2. **Groupement par repo conservé** : le combobox fusionné garde le séparateur visuel par repo
   (identique à T120) quand le workspace a plusieurs repos ; le type d'élément s'ajoute comme
   dernier segment du libellé de chaque entrée (ex. `Boîtier › Capteurs / Exigence Système`).
3. **Un `SystemNode` sans aucun type configuré n'a aucune entrée dans le combobox fusionné**
   (produit cartésien nœud × type = 0 entrée pour ce nœud) et devient donc invisible depuis la
   Vue Système. Ce cas se configure/se gère via l'onglet Structure, pas depuis ce combobox —
   régression assumée par rapport à l'affichage actuel ("Composant sans type configuré" restait
   sélectionnable), décision explicite de l'utilisateur plutôt qu'un oubli.
4. **Filtrage texte substring** requis (pas seulement un "jump to" comme le `<select>` natif) —
   implique de remplacer les deux `<select>` HTML natifs par un composant combobox custom
   filtrable (ex. Radix/Headless UI `Combobox`), avec les groupes de repo rendus comme en-têtes
   de section dans la liste déroulante plutôt qu'en `<optgroup>` natif.
5. **Hors scope explicite** : recherche/navigation directe vers un **document** existant (type
   "aller à…", commande palette globale sur les éléments eux-mêmes) — besoin différent, identifié
   puis explicitement écarté en conversation avec l'utilisateur. Ce ticket ne touche que la
   sélection de **contexte** (nœud + type), pas la navigation vers un élément précis. `ElementTree`
   et sa `FilterBar` de texte existante (filtrage des éléments *dans* le contexte sélectionné,
   `SystemPanel.tsx` `FilterBar`) restent inchangés et distincts de ce nouveau combobox.

## Comportement attendu

1. **Modèle des entrées.** Pour chaque `ComponentOption` produit aujourd'hui par
   `componentOptions` (`SystemViewContext.tsx:224-246`), et pour chaque `ObjectTypeDefinition` du
   `SystemNode` correspondant (`schema.nodes[...].objectTypes`), une entrée
   `{ repoName, nodeId, typeId, label, groupLabel? }` où `label` = libellé actuel du
   `ComponentOption` (chemin `›` inclus le cas échéant) + `" / "` + `objectType.label || .name`.
   Un `SystemNode` à `objectTypes` vide ne produit aucune entrée (cf. décision 3 ci-dessus).
2. **Rendu.** Un seul combobox, libellé **"Composant / Élément"** (ou libellé à trancher en
   Design — le texte actuel "Composant" et "Élément" disparaissent comme labels de champs
   séparés). Liste groupée par repo comme aujourd'hui quand le workspace a plusieurs repos
   (décision 2) ; en mono-repo, liste plate sans en-tête (cohérent avec le comportement actuel du
   combobox Composant en mono-repo, `SPEC-SYSTEM-VIEW.md:61-64`).
3. **Filtrage texte.** Taper du texte réduit la liste aux entrées dont le libellé complet
   (repo + chemin + type) contient la chaîne tapée, insensible à la casse. Pas d'exigence de
   pondération/tri par pertinence au-delà d'un filtrage substring simple — à confirmer/affiner en
   Design si le volume d'entrées réel le justifie.
4. **Sélection.** Choisir une entrée recharge en une seule action tout le contexte (schéma, arbre,
   index) — remplace l'actuel `handleComponentChange` (`SystemViewContext.tsx:374-383`, qui
   recalcule un `firstType` puis appelle `navigateWith`) par un seul handler recevant directement
   `(repoName, nodeId, typeId)` et appelant `navigateWith` une fois, sans étape intermédiaire de
   "premier type disponible".
5. **Persistance URL et dernière sélection (T52).** Format d'URL inchangé (`repo`+`node`/
   `component`+`type`/`level`, `SystemViewContext.tsx:197-199`) — seule la présentation en un
   combobox unique change, comme T120 l'avait déjà fait pour Composant seul
   (`SPEC-SYSTEM-VIEW.md:73-74`). La restauration de la dernière sélection (T52) continue de
   fonctionner sans changement de mécanisme, puisqu'elle restaure déjà les trois valeurs
   `repo`/`node`/`type` ensemble.
6. **État initial.** Au premier chargement, l'entrée correspondant au composant racine + son
   premier type disponible est présélectionnée (comportement identique à aujourd'hui,
   `SPEC-SYSTEM-VIEW.md:36-37`).
7. **Titre contextuel (`ViewHeader`).** Le texte `"Composant X / Élément Y"` actuellement affiché
   dans la barre de titre de la vue document (`SPEC-SYSTEM-VIEW.md:218-223`) reste inchangé dans
   sa forme — il continue de refléter la sélection courante, désormais pilotée par un seul
   combobox au lieu de deux.
8. **Lecture seule / repo figé.** Le bandeau "lecture seule" pour un repo en HEAD détaché
   (`SPEC-SYSTEM-VIEW.md:70-72`) reste affiché après sélection d'une entrée pointant vers un tel
   repo — comportement inchangé, juste rebranché sur le nouveau combobox.
9. **État "aucune entrée".** Si le workspace entier n'a aucun `SystemNode` avec au moins un type
   configuré, le combobox affiche un état vide explicite (texte à définir en Design, ex. reprise
   de `sidebar.system.noComponentConfigured`).

## Hors scope

- Recherche/navigation directe vers un **document** existant (commande "aller à…" sur les
  éléments eux-mêmes plutôt que sur le contexte nœud+type) — cf. décision 5.
- Rendre visible/sélectionnable un `SystemNode` sans type configuré (cf. décision 3) — géré via
  l'onglet Structure.
- Tout changement au format de persistance URL (`repo`/`node`/`type`) — inchangé.
- Raccourci clavier dédié pour ouvrir/focaliser ce combobox — non demandé, à ne pas ajouter sauf
  demande explicite ultérieure.
- Tri/pondération de pertinence avancée du filtrage texte (au-delà d'un substring simple) — sauf
  si le Design constate un besoin concret.

## Critères d'acceptation

- [ ] Un seul combobox dans `SystemPanel.tsx` remplace les deux `<select>` "Composant" et
  "Élément" actuels.
- [ ] Taper du texte dans le combobox filtre la liste par substring insensible à la casse sur le
  libellé complet (repo + chemin composant + type).
- [ ] Sélectionner une entrée recharge le contexte (arbre, vue document) en une seule action,
  sans état intermédiaire "type non sélectionné".
- [ ] Un `SystemNode` imbriqué (T123) apparaît avec son chemin `›` complet suivi du type, sous le
  bon groupe de repo.
- [ ] En mono-repo, aucun en-tête de groupe n'apparaît (cohérent avec le combobox Composant
  actuel).
- [ ] Un `SystemNode` sans type configuré n'apparaît dans aucune entrée du combobox fusionné.
- [ ] L'URL (`repo`/`node`/`type` ou `component`/`level`) reste au même format qu'avant ce ticket.
- [ ] La restauration de la dernière sélection (T52) fonctionne à l'identique après rechargement
  de l'application.
- [ ] Le titre contextuel `ViewHeader` ("Composant X / Élément Y") reste correct après sélection
  via le nouveau combobox.
- [ ] La `FilterBar` de filtrage des éléments dans l'arbre (sous le nouveau combobox) continue de
  fonctionner sans changement.
- [ ] TypeScript/lint : zéro nouvelle erreur.
