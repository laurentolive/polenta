# T130 — Revue complète de la doc de format/architecture

## Contexte

Préparation de l'open-sourcing du projet (page de présentation + repo d'exemple). Un premier
passage ad hoc (commit `62c7bce`, hors workflow formel) avait déjà corrigé 3 écarts confirmés en
ouvrant un projet d'exemple dans l'app (Playwright + Electron) : format de stockage des exigences/
tests (YAML pur vs frontmatter Markdown documenté), localisation de l'arbre d'affichage
(`.polenta/trees/<nœud>/<type>.yaml` vs `tree.yaml` unique documenté), et le sens du lien de
couverture test↔exigence. Ce ticket formalise la suite : audit de tous les `specs/SPEC-*.md`
restants contre le code actuel, plus les 2 écarts lourds déjà identifiés mais non corrigés
(template obsolète, section submodules périmée).

**Décisions de périmètre (validées avec l'humain avant rédaction de ce spec) :**
- Les 2 écarts lourds (template `electro-domestic-battery.yaml`, §22 submodules de
  `SPEC-ELECTRON-DESKTOP.md`) **sont dans le périmètre de T130**, pas des tickets séparés.
- Méthode d'audit par défaut : **lecture de code ciblée** (comparaison directe doc ↔ source),
  pas de repro live systématique — sauf pour les 3 écarts déjà vérifiés par ouverture réelle du
  projet d'exemple lors du premier passage.

**Décision finale (post-validation de la spec)** : **aucune correction de code** — l'application
actuelle est jugée prête pour une première version. Ce ticket met à jour la documentation
systématiquement pour refléter le code tel qu'il est, y compris les 3 items listés plus bas en
§"Écarts nécessitant une décision produit" : ils sont traités comme des corrections directes de
`SPEC-REVIEWS.md` (aligner le texte sur le comportement réel), pas comme des items à consigner dans
`SPEC-AUDIT.md` en attente d'un ticket séparé. Idem pour l'item 18 (menu natif désactivé) : documenter
l'état réel, sans enquête sur l'intention.

## Méthode

Audit mené en 9 passes parallèles (subagents `haiku`, cf. CLAUDE.md §délégation) couvrant les 15
fichiers `specs/SPEC-*.md` restants + 2 passes personnelles sur les 2 écarts lourds déjà repérés.
Chaque passe compare les affirmations de la doc au code source réel et ne remonte que les écarts
confirmés par lecture directe (fichier:ligne cité des deux côtés).

**Découverte importante en cours d'audit** : `specs/SPEC-AUDIT.md` existe déjà (généré 2026-06-24,
non référencé dans `SPEC-INDEX.md`) et documente en détail les écarts de `SPEC-TESTS.md §4+`,
`SPEC-TRACEABILITY.md §3+`, `SPEC-SYSTEM-VIEW.md` et une partie de `SPEC-FORKS-BRANCHES-BASELINES.md
§5` (baselines). Les passes d'audit sur ces fichiers ont largement re-confirmé son contenu (aucune
contradiction sauf une, voir §"SPEC-AUDIT.md lui-même" plus bas) — ce fichier est traité comme la
source de vérité pour ces domaines plutôt que dupliqué ici.

## Comportements attendus

### Cas d'usage 1 — Correction des écarts de documentation pure ("la doc a tort")

Pour chaque écart listé en §"Écarts confirmés — correction directe" ci-dessous : le texte du
fichier `specs/SPEC-*.md` concerné est mis à jour pour refléter fidèlement le comportement/format
réel du code, sans changer le code. C'est le gros du volume de ce ticket.

### Cas d'usage 2 — Réécriture complète (les 2 écarts lourds)

- `templates/electro-domestic-battery.yaml` réécrit intégralement au format actuel de
  `packages/types/src/schema.ts` (`nodes[].objectTypes[]`, `linkTypes[].sourceRefs/targetRefs`,
  `statuses[].isApproval/isTerminal`, etc. — voir `SPEC-TEMPLATES.md` §2-4, déjà à jour).
- `SPEC-ELECTRON-DESKTOP.md` §20 (format `.polenta/schema.yaml`) et §22 (architecture
  multi-composants) réécrits pour décrire le mécanisme réel : `SystemNode`/`ObjectTypeDefinition`/
  `LinkTypeDefinition`, composants en repo séparé découverts via `polenta-repo.yaml` (T69, workspace
  plat), imbrication de composants locaux à profondeur illimitée (`children`, T123), arbre de
  traçabilité maintenu par l'app dans `.polenta/trees/<nœud>/<type>.yaml` (pas de `tree.yaml`
  unique, pas de script Python, pas de hook pre-commit). Détail complet en §"Écart lourd A" et
  §"Écart lourd B" ci-dessous.

### Cas d'usage 3 — Écarts qui ne sont PAS des corrections de doc ("le code a peut-être tort")

Certains écarts trouvés ne sont pas de la dérive documentaire mais des fonctionnalités documentées
et jamais implémentées, ou des pertes de données suspectes. Pour ceux-ci, **ne pas réécrire la doc
pour la faire correspondre au code** — les lister comme "connu, non implémenté" (nouvelle entrée
dans `SPEC-AUDIT.md`, même format que l'existant) et laisser la décision spec-vs-code à un ticket
séparé. Voir §"Écarts nécessitant une décision produit" ci-dessous.

### `SPEC-ELECTRON-DESKTOP.md` §20 (schéma) — **écart majeur, nouvellement découvert**

Le modèle de données décrit en §20.1-20.4 (`requirementTypes`/`testTypes`/`RequirementTypeDefinition`/
`TestTypeDefinition`/`ComponentDefinition{url,branch,readonly}`/`LevelDefinition`, génération de
`.gitmodules` depuis `schema.components`) **ne correspond à rien dans le code actuel**. Confirmé par
lecture directe de `packages/types/src/schema.ts` et `apps/desktop/src/main/services/schema.service.ts` :
le modèle réel est `SystemNode` (imbrication `children` à profondeur illimitée, `roles`/`implements`
portés par le nœud) / `ObjectTypeDefinition{category: requirement|test|campaign}` / `LinkTypeDefinition
{sourceRefs, targetRefs}` / `ProjectPreferences`. Aucune occurrence de `.gitmodules` dans tout le
code (`grep -r gitmodules` → 0 résultat) : le mécanisme submodule-via-schema décrit ici n'existe
tout simplement pas.

Par ailleurs §20.2 documente `packages/types/src/config.ts` comme "Modèle avancé (cible future)"
vers lequel `schema.ts` migrerait. **Le sens est inversé** : l'en-tête réel du fichier dit
`// SUPERSEDED — remplacé par ProjectSchema dans schema.ts. À supprimer…` — c'est du code mort en
attente de suppression, pas une cible. Cette sous-section doit être retirée ou entièrement
recadrée, pas juste corrigée en détail.

Ce fichier étant déjà à jour et détaillé sur ce même modèle (`SPEC-TEMPLATES.md` §2-3, corrigé lors
du premier passage), la réécriture de §20 peut s'appuyer dessus plutôt que repartir de zéro.

§20.5 : liste des types de champ incomplète (`text|textarea|number|enum|boolean|date`) — il manque
`multi_enum`, `richtext`, `user`, `drawio`, `datetime` (cf. `SchemaFieldType` réel).

### Écart lourd A — Template `templates/electro-domestic-battery.yaml`

Confirmé : format entièrement obsolète (`requirementTypes[].id` au lieu de
`nodes[].objectTypes[].name`, `type: RICHTEXT/ENUM/TEXT/MULTI_ENUM` majuscules au lieu des valeurs
`SchemaFieldType` minuscules, `options:[{value,label,color}]` au lieu de `values:[...]`, bloc
`transitions:` sans équivalent dans `SchemaStatus`, `linkTypes[].id/allowedFrom/allowedTo` au lieu
de `name/sourceRefs/targetRefs`, `roles[].id/description` au lieu de `name/label`). Nécessite
réécriture complète vers le format `SPEC-TEMPLATES.md` §2-4.

**Découverte en cours d'audit, change la nature du problème** : il n'existe **aucun mécanisme
applicatif** pour appliquer un template aujourd'hui.
- Aucun channel IPC `templates:*` (recherché dans tout `apps/desktop/src/main`).
- Aucune référence à un sélecteur de template dans le renderer (recherche `template` dans
  `apps/desktop/src/renderer` → 3 résultats, tous sans rapport : TableSizePicker, un vendor JS,
  un commentaire dans SystemViewContext).
- `templates/` ne contient **qu'un seul fichier** (`electro-domestic-battery.yaml`) — le template
  `generic` listé dans `SPEC-TEMPLATES.md` §6 n'existe pas non plus.

Autrement dit, `SPEC-TEMPLATES.md` §5 ("Application d'un template" — sélection à la création de
projet, import custom, export depuis un projet existant, diff/merge à la mise à jour) décrit une
fonctionnalité qui n'a jamais été construite, pas un comportement qui a dérivé. Recommandation pour
Agent Design : réécrire le template au format actuel (contenu prêt pour quand la fonctionnalité
existera) **et** marquer §5 comme "non implémenté" plutôt que de le décrire au présent — à confirmer
au moment de la validation de ce spec. Le template `generic` mentionné en §6 doit soit être créé,
soit retiré du tableau.

   `specs/`, `templates/`.
