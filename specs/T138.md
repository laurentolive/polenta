# T138 — Afficher le statut de couverture de test dans les vues Word, Excel, Édition

## Contexte

`coverageStatus` (calculé par exigence — cf. [SPEC-TRACEABILITY.md](SPEC-TRACEABILITY.md) §2.2 et
`computeCoverageStatus()`/`computeCoverage()` dans `apps/desktop/src/main/services/traceability.service.ts`)
n'est aujourd'hui visible que de façon agrégée : dashboard "Couverture" (camembert par statut,
taux par composant — cf. `dashboard-seed.service.ts`) ou requête SQL brute dans le Query Builder
(`coverageStatus` exposé comme colonne dérivée du dataset `requirements`, cf.
`query-engine.service.ts`).

Aucune des 3 vues de consultation/édition d'une exigence (Vue Système : Document/`WordView.tsx`,
Tableau/`ExcelView.tsx`, formulaire/`EditView.tsx`, toutes trois sous
`apps/desktop/src/renderer/components/system/`) n'affiche ce statut par exigence individuelle.
Un utilisateur qui parcourt ses exigences dans ces vues n'a aucun signal visuel de leur couverture
sans changer de panneau.

## Description fonctionnelle

**Correction en cours de spec** : ce n'est pas une icône ajoutée en dur à côté du titre, ni une
préférence globale de type `schema.yaml` `preferences: {}` — c'est un **nouveau champ système**,
au même titre que `section`/`name`/`id`/`status`/`version` (`SystemView.tsx:104`,
`const systemFields = ['section', 'name', 'id', 'status', 'version', 'createdAt', 'author']`).

Le mécanisme d'activation existe déjà dans l'app pour exactement ce cas d'usage : le panneau
**⚙️ Configuration des champs visibles** (cf. [SPEC-SYSTEM-VIEW.md](SPEC-SYSTEM-VIEW.md) §224,
`SystemView.tsx` l. 99-241) où l'utilisateur coche/décoche, par vue et par type d'objet, les champs
(système + personnalisés) à afficher. Chaque vue a son propre tableau `visibleFields`
(`visibleFieldsExcel`/`visibleFieldsWord`/`visibleFieldsEdit`, persistés par utilisateur via
`api.pref.setFieldVisibility(repoPath, username, typeKey, views)`).

Donc, concrètement :

- Ajouter `'coverageStatus'` à `systemFields` (`SystemView.tsx:104`) avec son libellé
  (nouvelle clé i18n, ex. `system.fieldConfig.colCoverage`), à côté de `status` dans le panneau de
  configuration des champs visibles (`allFields`, l. 111-121).
- **Ne pas** l'ajouter aux tableaux `visibleFieldsExcel`/`visibleFieldsWord`/`visibleFieldsEdit` par
  défaut (`['section', 'name', 'id', 'status']`, `SystemView.tsx:570-572`) — c'est l'"option" dont on
  a parlé : le champ existe, désactivé par défaut, l'utilisateur l'active lui-même via le panneau
  ⚙️, exactement comme il le ferait pour tout autre champ qu'il veut voir apparaître dans une vue.
- Pas de nouvelle préférence `schema.yaml`, pas de nouvelle page — on branche sur le mécanisme de
  visibilité de champ déjà existant.

**Point à trancher en phase Design — écart déjà documenté (`specs/SPEC-AUDIT.md` §"Configuration
des champs ⚙️", ligne 200-203)** : seuls les onglets **Excel** et **Word** de `FieldConfigModal`
sont configurables aujourd'hui ; `visibleFieldsEdit` est persisté mais **aucun onglet "Édition"
n'existe** dans la modale pour le faire varier — c'est un `[ABSENT]` déjà relevé, indépendant de ce
ticket. Deux options pour que `coverageStatus` soit malgré tout "activable" en vue Édition, à
trancher en Design :
1. Combler l'écart en ajoutant l'onglet "Édition" manquant à `FieldConfigModal` (élargit le
   périmètre du ticket au-delà de `coverageStatus` seul) ;
2. Se contenter d'Excel et Word pour l'activation par champ, et pour la vue Édition ajouter
   `coverageStatus` au tableau par défaut `visibleFieldsEdit` (`SystemView.tsx:572`) — visible en
   permanence dans cette vue précise, non désactivable tant que l'onglet manquant n'est pas comblé.

### Champ non éditable

`coverageStatus` est un champ **calculé et en lecture seule** (contrairement à `status`, qui est un
champ système mais éditable — enum piloté par `typeDef.statuses`, cf. `WordView.tsx:520-522`,
`ExcelView.tsx:1351-1353`, `EditView.tsx:456-459`). Le rendu de `coverageStatus` doit suivre le même
principe d'emplacement (colonne/ligne de champ) que `status`, mais sans dropdown ni édition inline
dans aucune des 3 vues — même en mode édition, même si le composant n'est pas `readonly`.

Les cas de test (`TestCase`) n'ont pas de `coverageStatus` : le champ, une fois coché comme visible,
n'affiche simplement rien (ou une valeur neutre) sur les lignes/objets de type `test`.

### Icônes et libellés (repris tels quels de SPEC-TRACEABILITY.md §2.2)

| Statut | Icône | Condition |
|--------|-------|-----------|
| `not_covered` | ○ | Aucun test lié |
| `covered` | ◑ | Au moins un test lié, aucun run PASS (au moins un `not_run`) |
| `validated` | ✓ | Tous les tests liés (hors fail/revalidation) ont un run PASS |
| `failing` | ✗ | Au moins un test lié en échec ou bloqué |
| `needs_revalidation` | ⚠ | Au moins un lien de couverture marqué à revalider |

Priorité de calcul en cas de statuts multiples (déjà implémentée, ne pas dupliquer la logique) :
`needs_revalidation` > `failing` > `covered` > `validated` > `not_covered`.

Réutiliser la palette d'icônes déjà en place dans `ComplianceMatrix.tsx` (`CheckCircle2`,
`AlertCircle`, `XCircle` de `lucide-react`, classes `text-status-success`/`text-status-warning`/
`text-status-danger`) plutôt que d'introduire un nouveau jeu d'icônes — `covered` et `not_covered`
n'ont pas d'équivalent direct dans ce fichier, un choix cohérent avec le design system existant est
à trancher en phase Design (ex. neutre pour `not_covered`, variante de warning pour `covered`).

### Tooltip

Au survol de la valeur du champ : liste des tests liés à l'exigence, avec pour chacun son ID, son
titre, et son dernier statut d'exécution (`not_run` / `pass` / `fail` / `blocked` / à revalider —
cf. SPEC-TRACEABILITY.md §2.3). Pas de nouveau panneau, pas de navigation depuis le tooltip (hors
scope — cf. ci-dessous).

## Comportements attendus par cas d'usage

1. **Champ `coverageStatus` non coché dans le panneau ⚙️ d'une vue (défaut)** → cette vue ne montre
   rien de plus qu'aujourd'hui — comportement actuel inchangé à l'octet près, pour cette vue.
2. **Champ coché pour Excel et/ou Word, exigence non liée à un test** → icône `not_covered` (○),
   tooltip "Aucun test lié".
3. **Champ coché, exigence liée à un test jamais exécuté** → icône `covered` (◑), tooltip listant
   le(s) test(s) en `not_run`.
4. **Champ coché, exigence liée à un ou plusieurs tests, tous en dernier run PASS** → icône
   `validated` (✓).
5. **Champ coché, exigence liée à un test dont le dernier run est FAIL ou BLOCKED** → icône
   `failing` (✗), même si d'autres tests liés sont PASS — priorité de calcul.
6. **Lien marqué `needsRevalidation: true`** → icône `needs_revalidation` (⚠), priorité maximale
   même sur un `failing`.
7. **Changement de statut en direct** : si l'utilisateur exécute un test ou modifie un lien pendant
   qu'une des 3 vues est ouverte avec le champ coché, l'icône se met à jour sans rechargement manuel
   (même fraîcheur que les autres données déjà réactives dans `SystemView.tsx`, ex.
   `linksByObjectId`) — pas de bouton "actualiser" dédié à cette info.
8. **Exigence en lecture seule** (composant `readonly: true`) : l'icône s'affiche identiquement si le
   champ est coché ; aucune interaction d'écriture n'est ajoutée par cette évolution.
9. **Activation/désactivation via le panneau ⚙️** : cocher/décocher `coverageStatus` dans
   "Configuration des champs visibles" pour Excel ou Word fait apparaître/disparaître la colonne
   immédiatement, persisté par utilisateur (`api.pref.setFieldVisibility`) — même comportement que
   pour tout autre champ système ou personnalisé aujourd'hui.
10. **Vue Édition** : selon l'option retenue en Design pour l'écart `FieldConfigModal` (voir
    ci-dessus) — soit activable via un onglet "Édition" ajouté à la modale, soit toujours visible par
    défaut dans cette vue en attendant que cet écart soit comblé ailleurs.

## Critères d'acceptation

- [ ] `'coverageStatus'` fait partie de `systemFields` (`SystemView.tsx`), avec un libellé i18n
  FR/EN dédié, et apparaît dans le panneau ⚙️ "Configuration des champs visibles" pour Excel et Word,
  aux côtés de `status`.
- [ ] Non coché (défaut) : `WordView` et `ExcelView` rendent les exigences à l'identique de
  l'existant — aucune icône, aucun tooltip, aucune colonne supplémentaire.
- [ ] Coché : dans `WordView` et `ExcelView`, chaque exigence affichée porte l'icône correspondant à
  son `coverageStatus`, avec les 5 valeurs de la table ci-dessus correctement distinguées
  visuellement (icône + couleur) ; les `TestCase` n'affichent rien pour ce champ.
- [ ] `EditView` traite `coverageStatus` selon l'option tranchée en Design (onglet dédié dans
  `FieldConfigModal`, ou champ par défaut non désactivable) — documenté explicitement dans
  `specs/T138-design.md`.
- [ ] Le champ est **non éditable** dans les 3 vues : pas de dropdown, pas d'édition inline, quel que
  soit l'état `readonly` du composant.
- [ ] Le tooltip au survol liste les tests liés (ID, titre, dernier statut d'exécution) ; une
  exigence sans test lié affiche un tooltip explicite ("aucun test lié") plutôt qu'un tooltip vide.
- [ ] Le calcul du statut réutilise `computeCoverageStatus()`/`computeCoverage()` existant
  (`traceability.service.ts`) — aucune réimplémentation de cette logique côté renderer.
- [ ] Aucune régression sur le rendu existant des exigences dans les 3 vues (titre, champs, liens,
  statut de cycle de vie draft/review/approved/obsolete restent inchangés et visibles).
- [ ] Le choix d'affichage (champ coché ou non) se persiste par utilisateur et par vue, et survit à
  un redémarrage de l'app (déjà garanti par `api.pref.setFieldVisibility`/`getFieldVisibility`,
  aucune régression attendue sur ce mécanisme).
- [ ] TypeScript/lint : zéro nouvelle erreur.

## Hors scope explicite

- Vue matrice de traçabilité dédiée (`traceability:matrix`, endpoint déjà présent côté backend mais
  non branché à une page renderer) — signalé lors de la discussion précédente comme un manque
  potentiellement plus large, mais ticket distinct si besoin.
- Navigation/clic depuis l'icône ou le tooltip vers le test lié ou vers un panneau de détail —
  seulement de la consultation passive dans cette évolution.
- Affichage de l'info de couverture dans le 4ᵉ endroit d'édition identifié par T126
  (`DynamicField`, formulaires détail/création req/test/campagne — `req.$reqId.tsx` etc.) : la
  demande porte explicitement sur les 3 vues de la Vue Système (Word/Excel/Édition).
- Filtrage/tri par statut de couverture dans `ExcelView` au-delà de ce qu'apporte gratuitement le
  filtre de colonne générique déjà existant (SPEC-SYSTEM-VIEW.md §Filtre par colonne) — pas de
  filtre spécifique "par statut de couverture" à développer ici.
- Combler entièrement l'écart `[ABSENT]` "onglet Édition" de `FieldConfigModal` si l'option 2 est
  retenue en Design (champ par défaut non désactivable en vue Édition) — combler cet écart pour
  de bon (onglet générique, pas seulement pour `coverageStatus`) resterait un ticket séparé.

**Correction (revue architecture en phase Design)** : `ExcelView` traite chaque champ visible comme
sa propre colonne (`<td>` par `col` dans `visibleFields`, cf. le rendu déjà en place pour `version`,
`createdAt`, etc.) — il n'y a pas d'endroit "cellule ID/titre" où fusionner l'icône sans casser ce
modèle. `coverageStatus` apparaît donc comme **une colonne à part entière** dans `ExcelView`, au même
titre que tout autre champ système cochable, et non fusionné dans une colonne existante. La phrase
"sans ajouter de colonne dédiée" plus haut dans ce document est corrigée par ce paragraphe.
