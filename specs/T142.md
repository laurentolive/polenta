# T142 — Indexation exigences/tests lente : `git log` par fichier au lieu d'un seul passage

## Root cause

`RequirementsIndexService.build()` et `TestsIndexService.build()` — déclenchés paresseusement au
premier accès (typiquement dès l'ouverture d'un projet, T137/`getOrBuild`) et à chaque
invalidation d'index (n'importe quelle modif de fichier sous `requirements/`/`tests/`, ou tout
mouvement de HEAD — `RepoWatcherService`) — appelaient `GitService.fileHistory(repoPath, file)`
**une fois par fichier** pour dériver `createdAt`/`createdBy`/`updatedAt`/`updatedBy` (T112).

`fileHistory()` s'appuie sur `isomorphic-git`'s `git.log({ filepath })`, qui **rejoue tout
l'historique de commits accessibles depuis HEAD à chaque appel** (implémentation `_log` :
traversée topologique complète, résolution de l'oid du fichier à chaque commit visité) — coût
O(commits) par appel. Multiplié par un appel par fichier : coût total **O(fichiers × commits)**.
Plus un projet accumule d'exigences/tests ET de commits, plus chaque ouverture ralentit — les
deux facteurs grossissent avec la vie normale du projet.

Mesuré sur le dossier `specs/` de ce repo lui-même (280 fichiers, 536 commits, choisi comme banc
d'essai réaliste faute de `requirements/`/`tests/` dans ce repo) : **~300 secondes** pour la
boucle par-fichier actuelle.

## Correctif

Nouvelle méthode `GitService.fileHistoryMap(repoPath, prefix)` — un seul `git.log()` (sans
`filepath`) pour obtenir la liste des commits, puis pour chaque commit un diff d'arbre **scopé à
`prefix`** contre son premier parent (`readSubtreeOid` + `diffSubtrees`, récursif, élagué dès
qu'un sous-arbre a le même oid des deux côtés — jamais de balayage du reste du repo). Coût
ramené à O(commits), plus plusieurs ordres de grandeur en dessous de O(fichiers × commits) dès
qu'il y a plus qu'une poignée de fichiers.

`RequirementsIndexService.build()`/`TestsIndexService.build()` appellent désormais
`fileHistoryMap()` une fois avant leur `Promise.all`, et font un `Map.get(file)` au lieu d'un
`fileHistory()` par fichier. `GitService.fileHistory()` (par-fichier) reste disponible telle
quelle — toujours référencée par ailleurs (commentaires `requirements.service.ts`/
`tests.service.ts`) et pas fausse en elle-même pour un usage ponctuel.

## Effet de bord découvert en vérifiant : `fileHistory()` avait un bug sur les merges

En comparant les deux implémentations sur `specs/` (qui a de vrais commits de merge — modèle
par-ticket-branche de WORKFLOW.md), **158 fichiers sur 280 divergent** entre l'ancien
`fileHistory()` et le nouveau `fileHistoryMap()`. Vérifié à la main contre `git log -- <path>`
sur plusieurs cas (`specs/T98.md`, `specs/T50.md`, `specs/T110.md`, `specs/SPEC-ACCOUNTS-AUTH.md`,
`specs/SPEC-INDEX.md`) : dans tous les cas vérifiés, **c'est l'ancien `fileHistory()` qui est
faux** — il rapporte un `updatedAt` qui ne correspond à AUCUN commit touchant réellement le
fichier (ex. `T98.md` : un seul commit dans toute son histoire d'après `git log`, mais l'ancien
code rapportait un `updatedAt` un jour plus tard). Le nouveau `fileHistoryMap()` (diff contre le
premier parent) est cohérent avec `git log -- <path>` et `git log --full-history -- <path>` sur
tous les cas vérifiés.

Root cause probable côté `isomorphic-git` : son algorithme par-fichier compare l'oid du fichier
entre commits **dans l'ordre de traversée topologique** (pas un diff parent↔enfant explicite),
ce qui semble se dérégler sur des commits de merge. Pas creusé plus loin côté lib elle-même —
hors périmètre de ce ticket, et non bloquant puisque `fileHistoryMap()` n'a pas ce problème.

Conséquence pratique : après ce correctif, certaines dates "dernière modification" affichées
dans l'UI pour des exigences/tests existants vont légitimement changer (vers une date plus
ancienne et correcte) au premier rebuild d'index qui suit le déploiement — attendu, pas une
régression.

## Vérification

- `pnpm --filter @polenta/desktop run typecheck` : propre.
- Comparaison ancien/nouveau sur `specs/` (280 fichiers, 536 commits) via un script jetable
  (supprimé, pas commité) qui instancie le vrai `GitService` :
  - `fileHistory()` par fichier : ~300s
  - `fileHistoryMap()` batché : ~19s (~16×)
  - Écarts (158/280 fichiers) spot-vérifiés à la main contre `git log -- <path>` /
    `git log --full-history -- <path>` sur 5 fichiers représentatifs — le nouveau code est
    systématiquement celui qui correspond à l'historique réel.
- Non vérifié en usage interactif (pas d'affichage Electron attachable dans cette session) — à
  confirmer avant merge : ouvrir un projet avec un nombre significatif d'exigences/tests et un
  historique git non trivial, comparer le temps d'ouverture avant/après, et vérifier que les
  dates créé/modifié affichées dans l'UI (fiche exigence, colonnes Excel) sont cohérentes avec
  `git log` sur les fichiers correspondants.

## Comment tester manuellement

1. Sur un repo avec plusieurs dizaines d'exigences/tests et un historique de plusieurs centaines
   de commits (idéalement avec des merges), ouvrir le projet et chronométrer le temps jusqu'à
   l'affichage de la liste des exigences.
2. Modifier un fichier sous `requirements/` (ou `tests/`) pour déclencher une invalidation
   d'index (`RepoWatcherService`), rouvrir la liste, vérifier que `createdAt`/`updatedAt`
   restent corrects pour ce fichier et les autres.
3. Pour un fichier ayant traversé un merge dans son historique, comparer la date "dernière
   modification" affichée dans l'UI à `git log --full-history -- <chemin>`.
