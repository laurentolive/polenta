# T152 — Bug : ECONNRESET au clone d'un repo distant derrière un proxy d'entreprise

## Root cause

Le commit `7701f1f` (« organization proxy support ») a introduit
`net-proxy.ts::resolveProxyDispatcher` — résout le proxy système (WPAD/PAC ou poste par
poste, via `session.defaultSession.resolveProxy` d'Electron, avec repli sur
`HTTP(S)_PROXY`) et produit un `Dispatcher` undici à passer aux appels `fetch`. Ce
mécanisme n'a été branché que dans `auth.service.ts` (login GitHub Device Flow, appels
à `api.github.com`) — pas dans le transport git.

Le clone/fetch/push/pull passait par `isomorphic-git/http/node`, qui s'appuie sur
`simple-get` → les modules `http`/`https` natifs de Node, **sans aucune connaissance du
proxy** (ni variables d'environnement, ni résolution système). Sur un poste où le proxy
n'est configuré qu'au niveau système (pas de `HTTP_PROXY`/`HTTPS_PROXY` en variable
d'environnement — le cas courant en entreprise), ce transport tente une connexion
directe vers `github.com`, que le pare-feu de l'entreprise coupe (`ECONNRESET`) — alors
que le login, lui, passe par `resolveProxyDispatcher` et fonctionne.

## Correctif appliqué

Nouveau fichier `apps/desktop/src/main/services/git-http.ts` : réimplémente le contrat
`HttpClient` d'isomorphic-git (`request({ url, method, headers, body }) → { url, method,
statusCode, statusMessage, headers, body }`) au-dessus d'`undici.request`, en résolvant
le dispatcher via `resolveProxyDispatcher` (déjà utilisé par `auth.service.ts`) — donc la
même détection de proxy pour le login et pour toutes les opérations git.

`sync.service.ts` : seul changement, l'import
```ts
import http from 'isomorphic-git/http/node'
```
devient
```ts
import http from './git-http'
```
Les 6 sites d'appel (`clone`, `fetch`, `push` ×3, `pull`) ne changent pas — ils utilisent
déjà `http` en tant que variable, sans référence directe au module d'origine.

`onProgress` n'est pas branché dans le nouveau client, à l'identique de
`isomorphic-git/http/node` (qui destructure le paramètre sans jamais l'appeler) — la
progression affichée à l'utilisateur pendant le clone provient du mécanisme interne
d'isomorphic-git (comptage d'objets pendant la négociation du pack), indépendant du
transport HTTP, donc non affecté.

Portée volontairement limitée au transport HTTP (aucun changement de
`auth.service.ts`/`net-proxy.ts`, aucune dépendance ajoutée — `undici` était déjà une
dépendance directe d'`@polenta/desktop`).

## Comment vérifier

1. Sur le poste d'entreprise où l'erreur a été observée : relancer un clone d'un projet
   distant après mise à jour — doit aboutir sans `ECONNRESET`.
2. Sur un poste sans proxy (golden path, non régressif) : clone, fetch, push, pull d'un
   repo distant restent fonctionnels.
3. Vérifier qu'un poste avec proxy configuré uniquement via `HTTP_PROXY`/`HTTPS_PROXY`
   (repli de `resolveProxyDispatcher`) fonctionne aussi.

## Vérifications techniques

- `pnpm --filter @polenta/desktop typecheck` (`tsc --noEmit`) : OK, aucune erreur.
- `@polenta/desktop` ne déclare pas de script `lint` — pas de vérification lint pour ce
  paquet (comportement préexistant, cf. T150).
- Pas de suite de tests automatisés pour `apps/desktop/src/main/services/` — vérification
  manuelle : clone direct (sans proxy) d'un petit repo public GitHub
  (`octocat/Hello-World`) via le nouveau transport `git-http.ts` (dispatcher `undefined`,
  connexion directe) — clone réussi, fichiers récupérés correctement. Confirme l'absence
  de régression sur le golden path avant de livrer le correctif proxy, qui ne peut être
  vérifié de bout en bout que sur un poste effectivement derrière un proxy d'entreprise
  (hors de cet environnement de dev).
