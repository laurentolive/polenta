# T153 — Bouton "Rafraîchir" (git pull) dans le panneau Version

## Description fonctionnelle

Dans le panneau Version (`VersionRepoFolder.tsx`), chaque repo du workspace (root, composant,
intégration) affiche déjà son statut git (branche courante, fichiers stagés/modifiés, bouton
Push si `ahead > 0`). Il manque la capacité de récupérer les changements distants : `pull` est
implémenté côté backend (`SyncService.pull`, `sync.service.ts:291-309`) et exposé jusqu'au
client (`api.sync.pull(repoPath)`), mais aucun appelant ne l'utilise dans le renderer.

Ajout d'un bouton icône "Rafraîchir" placé dans la ligne d'en-tête du repo, à côté du sélecteur
de branche (`BranchCombobox`) — visible en permanence (pas seulement quand le repo est en retard
sur son remote), au même niveau que le nom du repo.

## Comportement attendu par cas d'usage

1. **Repo propre (`isDirty === false`)** : le bouton est actif. Un clic déclenche
   `api.sync.pull(repoPath)`. Pendant l'appel, le bouton affiche un état "en cours" (icône en
   rotation / disabled). En cas de succès, la query `sync:status` (et `sync:graph`, si affiché
   ailleurs pour ce repo) est invalidée pour refléter le nouvel état immédiatement.
2. **Repo avec modifications en attente (`isDirty === true`, staged ou non-staged)** : le bouton
   est désactivé (`disabled`), avec un `title`/tooltip expliquant qu'il faut d'abord committer ou
   annuler les modifications en cours. Aucun appel réseau n'est déclenché.
3. **Échec du pull** (conflit de merge, réseau, auth) : un message d'erreur s'affiche sous le
   bouton, sur le même modèle que `pushMutation.isError` existant. Pas de traitement spécial de
   `MergeConflictError` dans ce ticket (cf. Hors scope) — le message générique de l'erreur
   remontée suffit.
4. **Repo en detached HEAD** : le pull reste possible tant que le tree est propre (le detached
   HEAD bloque déjà l'édition ailleurs dans l'app, pas cette action en particulier) — pas de garde
   supplémentaire ajoutée ici.

## Critères d'acceptation

- [ ] Le bouton "Rafraîchir" est visible dans l'en-tête de chaque `VersionRepoFolder`, quel que
      soit l'état `ahead`/`behind` du repo.
- [ ] Cliquer sur le bouton avec un repo propre déclenche `api.sync.pull` et rafraîchit le statut
      affiché (staged/unstaged/ahead/behind, branche) sans rechargement manuel.
- [ ] Le bouton est désactivé dès qu'il y a au moins un fichier stagé ou non-stagé, avec un
      tooltip explicite.
- [ ] Une erreur de pull est affichée à l'utilisateur (pas de `catch` silencieux).
- [ ] Aucune régression sur le bouton Push existant ni sur le calcul `isDirty` partagé.

## Hors scope

- Affichage du compteur "N commits derrière" (`behind`, déjà calculé côté service mais jamais
  exposé côté UI) — pourrait justifier un ticket dédié pour décider si on veut gater la
  visibilité du bouton sur `behind > 0` comme c'est le cas pour Push/`ahead`. Ici le bouton est
  toujours visible, sur demande explicite ("bouton rafraîchir à côté du repo").
- Gestion dédiée de `MergeConflictError` après pull (navigation vers `/version-diff` comme pour
  "Publier", cf. `SPEC-FORKS-BRANCHES-BASELINES.md` §2.4) — le pull échoue avec un message
  générique, résolution manuelle hors de ce ticket.
- Pull en cascade sur les repos enfants (composants) déclenché automatiquement — chaque repo
  garde son bouton propre, un clic = un repo.
