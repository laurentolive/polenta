# T154 — Sécuriser "Publier" : intégration à jour avant merge, échec réseau explicite

## Contexte

Suite à T153 (bouton "Rafraîchir"/git pull dans le panneau Version) : un utilisateur non
git-initié ne comprend pas pourquoi il devrait déclencher un pull manuellement. La cible est un
auto-pull périodique (T155), mais un auto-pull n'est sûr que si la branche d'intégration ne peut
jamais diverger silencieusement de `origin` — sinon un pull automatique en tâche de fond peut
tomber sur un vrai conflit de merge, sans que l'utilisateur comprenne pourquoi.

Audit de `ModificationControl.tsx` (`publishMutation.mutationFn`, workflow "Publier",
`SPEC-FORKS-BRANCHES-BASELINES.md` §2.1) : le merge (`api.sync.mergeInto`) se fait sur la branche
d'intégration **locale**, sans `fetch` préalable. Le push final (`api.sync.pushBranch`) est
best-effort, non attendu (`.then()/.catch()`) — s'il échoue (quelqu'un d'autre a publié entre
temps), le merge local a déjà réussi : l'intégration locale diverge silencieusement de `origin`,
seul un toast discret (`pushError`) le signale. C'est cette divergence silencieuse qui rendrait un
futur auto-pull dangereux.

## Description fonctionnelle

Avant de merger le travail de l'utilisateur dans la branche d'intégration, "Publier" doit :

1. **Vérifier le réseau tôt, avant de toucher quoi que ce soit** (avant de créer la branche
   éphémère, avant tout commit) : un `fetch` du remote. Si ce fetch échoue (réseau indisponible,
   proxy, auth), la publication est bloquée avec un message clair et dédié ("réseau indisponible"),
   distinct du message générique actuel et du message de conflit de merge. Aucune branche créée,
   aucun commit fait — l'utilisateur retrouve exactement l'état d'avant son clic, ses modifications
   non committées intactes, et peut réessayer plus tard.
2. **Fast-forward la branche d'intégration locale vers `origin` si c'est un simple retard** (local
   strictement en arrière, aucun commit local non poussé) — mise à jour de la seule référence
   `refs/heads/<intégration>`, jamais du working directory, et donc jamais effectuée pendant qu'on
   est checkouté dessus (voir Design ci-dessous pour l'invariant d'ordonnancement).
3. **Si la branche d'intégration locale a divergé** (commits locaux non poussés ET commits distants
   absents localement — signe d'un push précédent resté en échec, cas préexistant hors scope ici) :
   ne rien forcer, laisser le comportement actuel (`mergeInto` fait un vrai merge, le push peut
   échouer à nouveau avec le même toast qu'aujourd'hui). Pas de nouvelle UI pour ce cas dans ce
   ticket.

Il est acceptable, et même préférable, qu'une publication échoue clairement faute de réseau
plutôt que de réussir en silence sur une intégration locale potentiellement obsolète.

## Comportement attendu par cas d'usage

1. **Réseau disponible, intégration à jour** : aucun changement de comportement perceptible —
   fetch rapide, rien à fast-forwarder, publication comme avant.
2. **Réseau disponible, intégration en retard (cas nominal du problème)** : fast-forward
   silencieux de l'intégration locale avant le merge — la publication réussit sur une base à jour,
   le push final a beaucoup moins de chances d'échouer par race.
3. **Réseau indisponible** : popup de publication se ferme comme aujourd'hui, message d'erreur
   dédié et explicite ("Publication impossible : réseau indisponible. Vos modifications restent
   en attente, réessayez une fois connecté."), aucune branche/commit créé.
4. **Intégration locale divergée (cas préexistant rare)** : comportement inchangé par rapport à
   aujourd'hui (hors scope, cf. ci-dessus).

## Critères d'acceptation

- [ ] Un échec de `fetch` en tout début de `publishMutation` produit un message dédié
      (`publishError.kind === 'network'`), pas le message générique actuel.
- [ ] Après un échec réseau, aucune branche éphémère n'a été créée et aucun commit n'a été fait —
      l'utilisateur reste sur sa branche de départ avec ses modifications non committées intactes.
- [ ] Quand l'intégration locale est strictement en retard sur `origin`, elle est fast-forwardée
      avant le merge — vérifiable via `sync:status`/`ahead`/`behind` qui retombe à `behind: 0`
      juste avant le merge (pas testable directement dans l'UI sans instrumentation ; vérifié par
      lecture de code + test ciblé du service).
- [ ] Le fast-forward ne modifie jamais le working directory ni ne s'exécute jamais pendant que la
      branche d'intégration est la branche courante checkoutée (invariant d'implémentation).
- [ ] Aucune régression sur le flux "Publier" existant (nominal, avancé, conflit de merge réel,
      push best-effort en cas de race résiduelle).

## Hors scope

- Résolution automatique ou UI dédiée pour le cas "intégration locale divergée" (déjà un push
  précédent resté en échec) — comportement inchangé, cf. ci-dessus.
- L'auto-pull périodique lui-même — objet de T155, qui dépend de ce ticket.
- Le bouton "Rafraîchir" (T153) n'est pas modifié par ce ticket.
