# T155 — Auto-pull périodique en tâche de fond

## Contexte

Suite à T153 (bouton "Rafraîchir") et T154 (sécurisation de "Publier") : un utilisateur non
git-initié ne devrait jamais avoir à comprendre qu'un pull existe, ni à cliquer dessus. Décisions
prises avec l'utilisateur avant implémentation :
- Portée : **global**, tourne tant qu'un projet est ouvert, indépendamment de l'onglet actif — pas
  seulement quand le panneau Version est ouvert (l'utilisateur ciblé ne l'ouvre justement jamais).
- Intervalle : **5 minutes**.
- Pas de pull au démarrage/à l'ouverture du projet — l'ouverture fait déjà sa propre résolution
  réseau (clone/fetch des dépendances manquantes, cf. `WorkspaceTreeService`), déjà lente.

## Description fonctionnelle

Un hook `useAutoPull(currentProjectId)`, monté une fois au niveau du layout applicatif
(`AppLayout.tsx`, à côté de `VersioningProvider`), qui toutes les 5 minutes :
1. Énumère tous les repos du workspace (root + composants/interfaces, via `useWorkspaceStructure`).
2. Pour chacun, vérifie `sync:status` : s'il y a le moindre fichier stagé ou non stagé, le repo est
   ignoré pour ce tick (même garde que le bouton Rafraîchir de T153).
3. Sinon, tente un **fast-forward-only** (nouvelle méthode `SyncService.pullFastForwardOnly`, PAS
   `SyncService.pull`) — jamais de vrai merge à trois voies en tâche de fond : une opération que
   l'utilisateur n'a pas demandée ne doit jamais pouvoir écrire des marqueurs de conflit dans ses
   fichiers pendant qu'il travaille sur autre chose. Si le repo a divergé (commits locaux non
   poussés — cas préexistant rare, cf. T154), l'échec est silencieux, journalisé (`console.warn`),
   retenté au prochain tick.
4. En cas de succès, invalide la query `sync:status` du repo concerné pour que l'UI (si affichée)
   se rafraîchisse sans action de l'utilisateur.

Aucune notification, aucune UI dédiée : succès invisible, échec silencieux — un utilisateur qui
n'a rien demandé ne doit jamais voir une erreur technique git.

## Nouveau : `SyncService.pullFastForwardOnly`

Ajouté à côté de `pull()` existant (lui-même inchangé, toujours utilisé par le bouton manuel
Rafraîchir de T153, qui peut légitimement tenter un vrai merge puisque l'utilisateur a cliqué
explicitement). Route les remotes non-http vers `git pull --ff-only`, sinon
`git.pull({ fastForwardOnly: true, ... })` côté isomorphic-git. Un repo sans remote configuré est
un no-op (même logique que `fetch()` en T154).

## Découverte pendant les tests (hors périmètre de ce ticket, à signaler)

`WorkspaceTreeService.writeCache` (`workspace-tree.service.ts`) écrit
`<workspaceDir>/.polenta/tree.cache.yaml` avec un champ `generatedAt: new Date().toISOString()`
recalculé à **chaque** régénération de l'arbre (typiquement à chaque ouverture de projet). Ce
fichier est suivi par git (pas de `.gitignore`), donc le repo apparaît quasi systématiquement
"modifié" (au moins ce fichier) peu après l'ouverture — ce qui bloque la garde `isDirty` utilisée
aussi bien par le bouton Rafraîchir (T153) que par cet auto-pull (T155), jusqu'à ce que l'utilisateur
committe ou annule ce changement. Constaté en conditions réelles pendant les tests de ce ticket
(cf. `T155-sprint1.md`). **Non corrigé ici** — cause racine différente (persistance du cache de
l'arbre workspace, sans rapport avec le pull), mérite son propre ticket. Deux pistes possibles pour
ce futur ticket : ne pas versionner ce fichier (`.gitignore`), ou ne le réécrire que si le contenu
utile (hors `generatedAt`) a effectivement changé.

## Hors scope

- Corriger `tree.cache.yaml` (cf. ci-dessus — futur ticket dédié).
- Toute UI de notification/statut de synchronisation ("dernière synchro il y a Xmin", badge, etc.).
- Gestion dédiée du cas divergé — reste un échec silencieux comme documenté ci-dessus.
- Rendre l'intervalle configurable par l'utilisateur.

## Critères d'acceptation

- [ ] `useAutoPull` ne déclenche aucun appel réseau à l'ouverture du projet (seulement après le
      premier intervalle écoulé).
- [ ] Tourne indépendamment de l'onglet actif (vérifié : hook monté dans `AppLayout`, pas dans un
      composant scoped au panneau Version).
- [ ] Un repo avec des modifications en attente est ignoré pour le tick courant, sans erreur visible.
- [ ] `pullFastForwardOnly` ne réalise jamais de merge à trois voies — vérifié directement contre
      le service (cf. sprint 1).
- [ ] Le bouton Rafraîchir (T153, `pull()` classique) n'est pas affecté par ce ticket.
