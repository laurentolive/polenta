# T158 — Évolution : Ctrl+Entrée valide la saisie dans un champ richtext

## Contexte / problème

Dans un champ `richtext` (`RichTextField.tsx`, éditeur TipTap), `Ctrl+Entrée`
(`Cmd+Entrée` sur macOS) n'a aujourd'hui aucun effet « métier » : l'extension
`HardBreak` de `@tiptap/starter-kit` mappe `Mod-Enter` (et `Shift-Enter`) sur
`setHardBreak`, insère donc un saut de ligne et **consomme l'évènement** avant qu'il
ne remonte vers un handler de validation.

Conséquences :

- Vue Tableau (`ExcelView`) — le popover d'édition richtext écoute déjà
  `e.ctrlKey && e.key === 'Enter'` pour se fermer (`ExcelView.tsx:1826`), mais le
  raccourci ne fonctionne pas : TipTap intercepte la frappe.
- Vue Document (`WordView`), formulaires détail/création (`req.$reqId`, `test.$testId`,
  `req.new`, `test.new`, `campaign.new`), `EditView`, `StepsTable` — aucun moyen au
  clavier de valider depuis l'intérieur d'un champ richtext ; il faut sortir du champ à
  la souris puis cliquer sur le bouton d'action.
- `useModalHotkeys` ignore explicitement `Enter` quand le focus est dans une zone
  `contentEditable` (commentaire du hook) — les modales ne rattrapent donc rien.

## Description fonctionnelle

Dans **tout champ richtext en édition**, `Ctrl+Entrée` (et `Cmd+Entrée` sur macOS)
**valide la saisie du contexte d'édition courant**, au lieu d'insérer un saut de ligne.

- `Maj+Entrée` reste le saut de ligne « dur » (inchangé) — l'utilisateur qui veut
  forcer un retour à la ligne garde ce raccourci.
- `Entrée` seul reste inchangé (nouveau paragraphe / nouvel item de liste).
- « Valider la saisie » = déclencher l'action primaire du conteneur qui affiche le
  champ (voir tableau ci-dessous). Le contenu en cours de frappe est pris en compte
  (la dernière frappe est incluse dans la valeur validée).

### Comportement attendu par contexte d'édition

| Contexte | Composant | Effet de Ctrl+Entrée |
|---|---|---|
| Popover richtext, Vue Tableau | `ExcelView.tsx` (`activeRichtextPopover`) | Ferme le popover en conservant la saisie (comportement déjà voulu, aujourd'hui cassé) |
| Champ inline, Vue Document | `WordView.tsx` (`EditableRichField`) | `commit()` : enregistre la valeur et sort du mode édition |
| Formulaire d'édition (Vue Système) | `EditView.tsx` | Valide/flush le champ actif (équivaut au handler `window` `Ctrl+Enter` existant `EditView.tsx:432`, aujourd'hui inefficace depuis l'éditeur) |
| Formulaires de création | `req.new`, `test.new`, `campaign.new` | Soumet le formulaire (même chemin que le bouton primaire `handleSubmit`) — la validation de champs requis s'applique normalement |
| Pages détail req/test | `req.$reqId`, `test.$testId` | Déclenche « Enregistrer » (`saveMutation` / `handleSave`) si des modifications existent ; sans modification, no-op |
| Tableau des étapes de test | `StepsTable.tsx` | Valide/sort le champ de la cellule (blur) — **n'ajoute pas** de nouvelle étape |

### Contextes explicitement inchangés

- Champs richtext **en lecture seule** (`disabled` / `TestCaseEditModal`,
  `RequirementEditModal`, viewers, `campaign.$campaignId_.execute.$testId` en
  consultation) : aucun effet, aucun changement.
- Mode « Raw » d'un champ richtext (`<textarea>`) : c'est un vrai `<textarea>`,
  `Ctrl+Entrée` y suit le comportement natif du navigateur — hors périmètre.

## Décision d'implémentation (validée avec l'humain)

- `RichTextField` expose une nouvelle prop optionnelle `onSubmit?: () => void`.
- Une petite extension TipTap locale capte `Mod-Enter` :
  - si un `onSubmit` est fourni → l'appelle et renvoie `true` (évènement consommé,
    pas de saut de ligne) ;
  - sinon → renvoie `false` (comportement `HardBreak` actuel préservé pour tout
    champ non câblé, notamment lecture seule).
- Chaque conteneur qui édite un champ richtext câble `onSubmit` sur son action
  primaire selon le tableau ci-dessus. Le passage se fait via `DynamicField`
  (nouvelle prop passe-plat `onSubmit`) et directement dans `WordView`/`ExcelView`/
  `EditView`/`StepsTable`.

## Hors scope

- Pas de nouvelle indication visuelle du raccourci (pas de hint « Ctrl+Entrée pour
  valider » dans l'UI) — cohérent avec les autres raccourcis non affichés.
- Pas de changement du raccourci `Maj+Entrée` (saut de ligne).
- Pas de raccourci « valider » pour les champs non-richtext (déjà couverts par
  `useModalHotkeys` / `Enter` natif).
- Pas de traitement du cas « curseur dans un bloc de code » : `Mod-Enter` y sert
  aujourd'hui à sortir du bloc de code (`CodeBlock` de starter-kit) ; ce raccourci
  passe désormais à « valider ». Sortie de bloc de code = flèche bas (tradeoff
  accepté, `Maj+Entrée` reste disponible pour un saut de ligne).

## Critères d'acceptation

1. Vue Tableau : ouvrir le popover d'édition d'un champ richtext, taper du texte,
   `Ctrl+Entrée` → le popover se ferme, la valeur (dernière frappe incluse) est
   enregistrée sur la/les ligne(s) sélectionnée(s).
2. Vue Document : cliquer un champ richtext pour l'éditer, `Ctrl+Entrée` → le champ
   repasse en lecture, la valeur est enregistrée.
3. Formulaire de création d'exigence : focus dans le champ `statement`,
   `Ctrl+Entrée` → l'exigence est créée (ou l'erreur « titre requis » s'affiche si le
   titre est vide), comme un clic sur « Créer ».
4. Page détail exigence : modifier le champ `statement`, `Ctrl+Entrée` → « Enregistrer »
   se déclenche ; le contenu est persisté.
5. `EditView` : éditer un champ richtext, `Ctrl+Entrée` → le champ est validé/flush
   (pas de perte de la dernière frappe).
6. `StepsTable` : éditer la cellule « Action » d'une étape, `Ctrl+Entrée` → le focus
   sort du champ, aucune étape supplémentaire n'est ajoutée.
7. Dans tous les cas : `Maj+Entrée` insère toujours un saut de ligne ; `Entrée` seul
   crée toujours un nouveau paragraphe / item de liste.
8. Champ richtext en lecture seule (`TestCaseEditModal`) : `Ctrl+Entrée` sans effet,
   pas d'erreur console.
9. Aucune régression TypeScript / lint.
