# T159 — Bug : modifs d'un champ richtext perdues en vue Édition quand on quitte sans blur

## Reproduction rapportée

En vue Édition (`viewMode === 'edit'`, `EditView`), modifier le contenu d'un champ
`richtext` puis « aller dans une autre vue » sans repasser par le bouton « Retour » :
la modification est perdue, jamais persistée. Risque de perte de données.

Cas confirmé par l'utilisateur : navigation via la **barre latérale**. L'utilisateur
signale qu'il y a probablement d'autres chemins, et demande si une sauvegarde
« sur perte de focus fenêtre » serait pertinente.

## Rappel : T127 a déjà traité une variante de ce bug

`specs/T127.md` (commit `5ee8c40`) a corrigé exactement le cas « éditer un richtext
puis cliquer sur une icône de l'**ActivityBar** » en ajoutant un *cleanup* de démontage
dans `EditView` :

```ts
// EditView.tsx ~L420
const onFlushValuesRef = useRef(onFlushValues)
useEffect(() => { onFlushValuesRef.current = onFlushValues }, [onFlushValues])
useEffect(() => {
  return () => { onFlushValuesRef.current(localValuesRef.current) }
}, [])
```

T127 a **explicitement laissé hors scope** (sa section « Hors scope ») le cas où
`EditView` **reste monté** et où seul `editingNodeId` change — précisément le cas ici.

## Root cause

### Fait structurant : le champ `richtext` n'a AUCUN autosave en vue Édition

Dans `EditView.tsx` / `FieldControl`, tous les types de champ sauf `richtext` câblent un
`onBlur` → `onBlurField` → `handleEditBlurField` → `autoSaveMutation` (sauvegarde
immédiate). Le cas `case 'richtext':` ne câble **ni `onBlur`, ni autosave debouncé**
(contrairement aux vues Excel/Word qui, elles, passent par `handleAutoInlineEdit`,
debounce 800 ms). Cf. commentaire déjà présent `EditView.tsx:413-419`.

Chaque frappe dans le richtext ne fait que mettre à jour un **miroir local** :

```
RichTextField.onUpdate → onChange(md)
  → FieldControl.set(md) → setLocalVal(md) + onChange(md)
    → FieldRow.onChange → EditView: localValuesRef.current[field] = md
```

`localValuesRef` n'est **jamais** envoyé au serveur tant qu'un *flush* explicite n'a pas
lieu. Les seuls déclencheurs de flush sont :

| Déclencheur | Chemin |
|---|---|
| Bouton « Retour » du header | `ViewHeader` → `editViewRef.triggerBack()` → `handleBack` → `onFlushValues()` puis `onBack()` |
| Touche `Échap` | `EditView` keydown handler → `handleBack` |
| Démontage d'`EditView` (T127) | cleanup `useEffect([])` → `onFlushValuesRef.current(localValuesRef.current)` |

### Le trou : `editingNodeId` change alors qu'`EditView` reste monté

`EditView` synchronise son miroir sur l'objet chargé :

```ts
// EditView.tsx:399-403
useEffect(() => {
  if (objectData) {
    localValuesRef.current = { ...objectData }   // ← ÉCRASE le miroir
  }
}, [objectData])
```

Quand l'utilisateur **double-clique sur un autre élément de l'arbre** dans la barre
latérale (`SystemPanel.tsx:297-300` → `handleDoubleClick` → `setEditingNodeId(nodeId)`) :

1. `viewMode` reste `'edit'` → `EditView` **ne se démonte pas** → le cleanup T127 ne
   s'exécute pas.
2. `editingNodeId` change → `editingTreeNode` → `editingObjectId` change →
   nouvelle query `['object', …, editingObjectId]` → nouveau `loadedObject` → nouveau
   `objectData` (nouvelle identité).
3. L'effet `[objectData]` ci-dessus **remplace `localValuesRef.current`** par les données
   du nouvel objet. Les modifs non sauvegardées du premier objet sont perdues sans
   qu'aucun flush n'ait eu lieu. En parallèle, l'effet `[value]` de `FieldControl`
   (`setLocalVal(value); onChange(value)`) réinitialise aussi `localVal`.

Même mécanisme pour la **navigation vers un objet lié** (`LinksSection` →
`onNavigateToObject` → `navigateToObject` / `handleGoBack` sur une entrée `'edit'`) :
`EditView` reste monté, `editingNodeId` change, miroir écrasé. (Déjà pointé en « Hors
scope » de T127.)

### Vecteur additionnel : invalidation / refetch de `['object']` pendant l'édition

Tout ce qui fait changer l'identité de `objectData` **pendant** qu'un richtext est en
cours d'édition déclenche le même écrasement via l'effet `[objectData]` :

- **Blur d'un autre champ** du formulaire (titre, statut, champ texte…) →
  `autoSaveMutation.onSuccess` → `qc.invalidateQueries(['object', …])` → refetch → si la
  valeur serveur a réellement changé, nouveau `loadedObject` → `objectData` change →
  miroir richtext écrasé (le champ richtext n'ayant jamais été blurré, sa valeur n'est
  que dans `localValuesRef`). Non temporisé.
- **Retour de focus fenêtre** (`refetchOnWindowFocus`, activé par défaut) après
  `staleTime` (60 s, `main.tsx:10`) → refetch de `['object']`. Ici react-query v5 fait du
  *structural sharing* : un refetch **identique** garde la même référence et ne
  déclenche donc PAS l'effet (cas bénin). Le problème n'apparaît que si le contenu
  serveur diffère réellement.

Donc « sauver sur perte de focus » ne serait qu'un pansement : la cause commune est
l'absence d'autosave du richtext + l'écrasement inconditionnel de `localValuesRef` par
l'effet `[objectData]`.

## Chemins de navigation — état des lieux

| Chemin | `EditView` démonté ? | Flush aujourd'hui ? |
|---|---|---|
| Bouton « Retour » header | oui (après flush) | ✅ `handleBack` |
| Touche Échap | oui (après flush) | ✅ `handleBack` |
| Onglet Tableau / Document (`setEditingNodeId(null); setViewMode(mode)`) | oui | ✅ cleanup T127 |
| Icône ActivityBar → route différente (`/dashboard`, `/schema`…) | oui | ✅ cleanup T127 |
| Icône ActivityBar → Exigences/Tests/Campagnes (même route `/product`, params) | **non** (même route ; `effectiveType` change) | ❌ |
| **Double-clic autre élément de l'arbre** (barre latérale) | **non** | ❌ |
| **Navigation vers objet lié** (`onNavigateToObject`, viewMode reste `edit`) | **non** | ❌ |
| Blur d'un autre champ pendant édition richtext | non | ❌ (écrasement par refetch) |
| Fermeture d'onglet (`attemptCloseTab`) | oui | ✅ cleanup T127 (le blur programmé ne touche pas le richtext, mais le démontage flush) |
| Retour de focus fenêtre > 60 s, contenu serveur modifié | non | ❌ |

## Périmètre du correctif — options examinées (décision : A + sérialisation main + absorption T161)

### Option A — Autosave debouncé du richtext en vue Édition *(recommandée)*

Brancher le `onChange` des champs d'`EditView` (au minimum `richtext`) sur un autosave
temporisé, sur le modèle exact de `handleAutoInlineEdit` d'Excel/Word (debounce ~800 ms,
map de timers par `objectId:field`, même `autoSaveMutation`). Le flush à la navigation
(handleBack + cleanup T127) devient un simple filet de sécurité.

- **Couvre tous les chemins du tableau ci-dessus** d'un coup, y compris crash appli et
  perte de focus.
- Aligne `EditView` sur le comportement déjà éprouvé des deux autres vues.
- Légèrement au-delà du « correctif minimal » (`WORKFLOW.md`), mais réduit la surface de
  code fragile au lieu de l'augmenter.
- Points d'attention : au changement d'`editingNodeId`, *flusher le timer en attente*
  avant qu'il ne parte avec le mauvais `objectId` ; ne pas ré-émettre au montage
  (`FieldControl` effet `[value]` appelle déjà `onChange(value)` — à filtrer).

### Option B — Correctif minimal ciblé (rester en flush-only)

1. Dans `EditView`, avant que l'effet `[objectData]` n'écrase `localValuesRef`, *flusher*
   l'ancien miroir si `editingObjectId` a changé (garder l'`objectId` précédent dans un
   ref ; appeler `onFlushValues` avec les anciennes valeurs + l'ancien id).
2. Rendre `handleFlushEditValues` capable de cibler un `objectId` explicite (aujourd'hui
   il lit `editingObjectId`/`objectData` du closure courant — déjà changés au moment où
   le flush partirait).
3. Neutraliser `refetchOnWindowFocus` (et/ou les invalidations de `['object']`) tant
   qu'une édition richtext est en cours, ou garder l'effet `[objectData]` de ne pas
   écraser les champs localement divergents.

Plus petit diff apparent mais multiplie les cas particuliers et les refs de
synchronisation — le point 2 touche la signature du flush, le point 3 est délicat à
cadrer proprement.

### Option C — Diagnostic seulement (état actuel)

Ce fichier. Pas de code.

## Correctif appliqué (Option A + sérialisation main + T161 absorbé)

Principe : **un seul écrivain par objet**, write bulk, ciblé sur un `objectId` explicite.
Autosave debouncé et flushs explicites (démontage, changement d'objet) coordonnés par
`cancelAutosave()` + un flag `dirty` pour ne jamais émettre deux `update` concurrents pour
le même fichier.

### `SystemView.tsx` — `handleFlushEditValues(values, target?): Promise<boolean>`

- Devient `async`, renvoie `false` si l'écriture a échoué → EditView ré-arme son flag
  `dirty` et retentera (au lieu de perdre l'édition sur un échec IPC / validation EARS).
- 2e paramètre optionnel `target = { objectId, category, baseline }` : cible un objet + sa
  baseline serveur au lieu de l'objet couramment édité — indispensable car un changement
  d'objet à `EditView` monté repointe déjà `editingObjectId`/`objectData`.
- `cat = target?.category || effectiveType?.category` (`||`, pas `??` : une category vide
  doit retomber sur le fallback). Corrige aussi le routage requirement/test.
- Un seul `api.*.update` par appel. Pas de création d'objet quand `target` est fourni.

### `EditView.tsx`

- **Autosave debouncé** (`scheduleAutosave` / `cancelAutosave`, 800 ms) : un seul timer.
  Le cas `richtext` de `FieldControl` l'arme via `onEdit` (distinct de `onChange` = miroir).
  Les champs simples gardent leur `onBlur` → `onBlurField` immédiat, **mais** ce `onBlur`
  fait d'abord `cancelAutosave()` (le richtext reste `dirty`, flushé au prochain
  déclencheur) → un seul write en vol.
- `flushMirror(objectId, category, baseline)` : gardé par `dirtyRef` (l'utilisateur a-t-il
  changé un champ depuis le dernier flush émis ?). Évite qu'un switch/démontage suivant de
  près un autosave déjà parti n'émette un `update` dupliqué.
- `FieldControl` : l'effet `[value]` ne touche plus **que l'affichage** (`setLocalVal`), et
  seulement si le tampon n'a pas de divergence non sauvegardée (`localValRef ===
  syncedValRef`). Le miroir `localValuesRef` est la propriété **exclusive** de l'effet
  `[objectData]` d'EditView → il n'est plus écrasé par un refetch en arrière-plan ni par le
  remount de la liste des champs.
- Effet `[objectData]` (owner du miroir) :
  - **changement d'objet** (`prev.id !== id`, EditView monté) → `cancelAutosave()` +
    `flushMirror(objet sortant, baseline = serverSnapshotRef)` + reseed du miroir. `prev`
    vient de `prevObjectDataRef` (mis à jour dans l'effet, pas en rendu). Couvre double-clic
    arbre, nav objet lié, bascule Exigences/Tests.
  - **sinon** (1er montage, refetch même objet, objet créé) → adopte chaque champ serveur
    *sauf* divergence locale non sauvegardée.
  - **garde orphelin** : si le nœud d'arbre change et que le miroir est encore `dirty` d'un
    nœud dont l'objet n'a jamais été persisté (`prev` null), le contenu est jeté — sinon il
    serait écrit sur l'objet suivant.
- `objectLoading` (prop, `!!editingObjectId && !objectData`) : « Chargement… » au lieu de
  champs vides éditables pendant que l'objet du nouvel élément se charge — sinon une frappe
  atterrit dans le mauvais objet.
- Liste des champs `key`ée sur `nodeId` : remonte les `FieldControl` au changement
  d'élément, mais pas à la création (null → id) — contenu pré-titre préservé.
- `handleBack` ne flushe plus (évite le double write avec le cleanup de démontage) : le
  flush passe par la branche switch de `[objectData]` (nav objet lié) ou le cleanup de
  démontage (Retour/Échap → viewMode quitte 'edit').

### Sérialisation des écritures (main) — `withKeyLock`

`RequirementsService` / `TestsService` `.update` / `.openDraft` / `.transition` font un
read-modify-write non verrouillé du YAML (`findById` → merge → `writeYaml`). Deux mutations
concurrentes du même objet pouvaient s'interleaver et perdre un champ — course désormais
**réelle** avec l'autosave debouncé, et **pré-existante** pour l'autosave par champ des
vues Excel/Word.

`serialize-writes.util.ts` — `withKeyLock(key, fn)` : file d'attente par clé
(`${repoPath}::requirements/${id}` etc.). Les mutations d'un même objet passent l'une après
l'autre ; les objets distincts restent parallèles. Ferme la classe de perte sur write
concurrent (autosave vs transition de statut, autosave vs rename, Excel/Word).

### Limites connues

- Bascule Exigences/Tests de l'ActivityBar sans rouvrir d'élément : modifs persistées, mais
  les `FieldControl` restés montés affichent l'ancien contenu jusqu'à l'ouverture d'un
  élément (`key` = `nodeId` inchangé). Pas de perte de données.
- `execute()` (exécution d'un cas de test → fichier de run distinct) n'est pas passé sous
  `withKeyLock` — pas de RMW concurrent sur le fichier du cas de test lui-même.

## T161 absorbé dans T159

T161 (« exigence créée depuis l'arbre — titre figé sur "Sans titre" / description perdue »,
signalé sur `handstickProduct` / `VE22D`) partageait la **root cause #2** de T159 (miroir
richtext écrasé par le refetch de `['object']`). Décision humaine : **fusionner dans T159**.

- **Défaut 2 de T161** (description perdue) → couvert par le correctif principal T159
  (miroir protégé + autosave). Le cas « objet fraîchement créé » (`fields: {}` → la
  description n'a pas de clé dans `objectData`, donc jamais adoptée par le merge, donc
  préservée dans le miroir jusqu'au flush) fonctionne avec la logique T159.
- **Défaut 1 de T161** (titre figé) → repris tel quel :
  - `ElementTree` : prop `onItemRenamed`, appelée au commit du renommage inline quand le
    nœud porte déjà un `objectId`.
  - `SystemPanel.handleItemRenamed` → `api.*.update { title }` + invalidations (miroir de
    `SystemView.handleRenameNode`).
  - `SystemViewContext.createItemObject` : capture le nom du nœud avant la création async ;
    si renommé pendant l'`await`, pousse le nouveau nom comme `title` (ignoré si
    copier-coller).
- Entrée d'arbre orpheline (`VE22D_REQ-0001` — objet jamais écrit) : nettoyage manuel,
  hors scope (cf. T161 §Hors scope).

Le ticket T161 est fusionné dans l'entrée T159 de `TICKETS.md` ; le worktree
`../polenta-T161` et sa branche sont supprimés après merge.

## Comment vérifier

1. Éditer un richtext en vue Édition, cliquer **Dashboard** dans l'ActivityBar → rouvrir :
   modif présente.
2. Éditer un richtext, **double-clic sur un autre élément de l'arbre** → rouvrir le 1er :
   modif présente. Idem via un lien (`LinksSection`), idem bascule Exigences/Tests.
3. Éditer un richtext puis changer le **statut** sans blur du richtext → rouvrir : modif
   présente (et pas de champ perdu — `withKeyLock`).
4. **T161** : `+` → créer un élément, le nommer, ouvrir en Édition, saisir une description,
   quitter (clic Version) → rouvrir : titre = nom du nœud, description enregistrée.
5. **T161 non-régression** : renommer un élément existant depuis l'arbre latéral → titre à
   jour en Vue Tableau + sélecteur de liens. Copier-coller un élément → titre = source.
6. Non-régression T127 : bouton Retour, Échap, onglet Tableau/Document.
7. `cd apps/desktop && npx tsc --noEmit -p tsconfig.json` → 0 erreur.
