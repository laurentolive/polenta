# T163 — Vue Word : afficher les diagrammes draw.io des richtext en lecture (rendu paresseux)

## Contexte

Dans la **Vue Word** (`SystemView`, onglet Document), chaque champ `richtext` d'un
élément est rendu en lecture par `StaticRichTextViewer`
([staticRichText.tsx](../apps/desktop/src/renderer/lib/staticRichText.tsx)), via
`RichTextInlineField` ([WordView.tsx:178-244](../apps/desktop/src/renderer/components/system/WordView.tsx#L178-L244)).

`StaticRichTextViewer` rend le markdown avec `markdown-it` seul (pas d'éditeur
Tiptap/ProseMirror) — choix délibéré de perf : la Vue Word monte **tous** les
éléments du document d'un coup, et un éditeur Tiptap par champ × N éléments gelait
l'onglet « Exigences » sur un projet de la taille de PL/Product (281 items × 3
champs richtext, confirmé au profiling — cf. en-tête du fichier).

Conséquence : la règle de *fence* `drawio` de ce viewer
([staticRichText.tsx:50-59](../apps/desktop/src/renderer/lib/staticRichText.tsx#L50-L59))
remplace chaque diagramme par une **étiquette texte** `📐 nom-de-fichier`. Le
diagramme réel n'apparaît qu'en passant le champ en édition : `RichTextInlineField`
bascule alors sur `RichTextField` → extension `DrawioEmbed` → `DrawioEmbedView` →
viewer mxGraph vendoré.

Les images, elles, **sont** rendues en lecture (balise `<img>` simple, résolution
du chemin repo en `data:` via `api.image.read`) — seul draw.io est réduit à une
étiquette, car son rendu coûte un viewer canvas par occurrence.

### Divergence SPEC

`SPEC-REQ-requirements.md §3.2a` (« Affichage : rendu via le viewer officiel
draw.io vendoré ») ne distingue pas la Vue Word des autres rendus. Le
comportement actuel (étiquette seule en Vue Word lecture) est donc une
**divergence non documentée** introduite par le correctif de perf de
`StaticRichTextViewer`. T163 réaligne l'implémentation sur la SPEC.

`§3.2b` (« redimensionnables, rognables… uniquement en édition, jamais dans le
rendu lecture seule ») ne concerne que **l'interactivité d'édition** (poignées,
rognage, menu contextuel), pas la présence du diagramme.

## Objectif

En Vue Word lecture, afficher le vrai diagramme draw.io de chaque bloc `drawio`
d'un champ `richtext`, **sans régression de perf** : le rendu d'un diagramme n'est
déclenché que lorsqu'il entre (ou approche) le viewport, via un
`IntersectionObserver`. Le coût reste borné aux diagrammes réellement visibles à
l'écran, pas aux centaines d'éléments de la liste.

## Périmètre

**Dans le périmètre**
- `StaticRichTextViewer` uniquement (`apps/desktop/src/renderer/lib/staticRichText.tsx`).
  C'est son seul consommateur : la Vue Word. Toute autre vue qui l'adopterait
  plus tard bénéficierait automatiquement du même rendu.

**Hors périmètre**
- Vue Tableau (`ExcelView`) : une cellule `richtext` n'affiche qu'un aperçu
  tronqué d'une ligne ([ExcelView.tsx:203-233](../apps/desktop/src/renderer/components/system/ExcelView.tsx#L203-L233)) — aucun rendu de diagramme attendu.
- Routes campagne (`campaign.*`) : utilisent déjà le `RichTextViewer` live
  (Tiptap lecture seule), qui rend déjà les diagrammes via `DrawioEmbedView`.
- Vue Édition / `EditView` : édition, `RichTextField` complet, déjà fonctionnel.
- Aucune interactivité d'édition sur le diagramme en Vue Word lecture (pas de
  poignées, pas de rognage interactif, pas de menu contextuel) — inchangé par
  rapport à `§3.2b`.
- `RichTextViewer` (composant Tiptap) : inchangé.

## Comportement attendu

### R1 — Placeholder au lieu de l'étiquette

La règle de *fence* `drawio` de `getMarkdownIt()` émet, au lieu du `<span>`
étiquette actuel, un élément placeholder portant les données du bloc, p. ex. :

```html
<div class="static-drawio"
     data-drawio-path="diagrams/foo.drawio"
     data-drawio-node-id="node-PWR-001"
     data-drawio-width="320"
     data-drawio-height="180"
     data-drawio-crop='{"x":10,"y":0,"width":300,"height":180}'>
  <span class="…">📐 foo.drawio</span>
</div>
```

- `data-drawio-node-id`, `data-drawio-width`, `data-drawio-height`,
  `data-drawio-crop` ne sont émis que s'ils sont présents dans le payload JSON du
  bloc (mêmes clés que `DrawioEmbedExtension` : `path`, `nodeId`, `width`,
  `height`, `crop`).
- Le `<span>📐 label</span>` interne reste comme **contenu de repli** : affiché
  tant que le diagramme n'est pas rendu, et définitivement si `repoPath` est
  absent (rien à résoudre) ou en cas d'erreur (R6).
- Payload JSON illisible → repli sur `path` = contenu brut, `📐 label` seul, comme
  aujourd'hui (`catch`).

### R2 — Observation paresseuse

Le `useEffect` de `StaticRichTextViewer` (qui balaie déjà `containerRef` en
`querySelectorAll` pour résoudre les `<img data-static-img-src>`) balaie aussi les
`.static-drawio` et attache un **`IntersectionObserver`** :

- `root: null` (viewport), `rootMargin` d'anticipation (~`200px`) pour lancer le
  rendu juste avant que le diagramme n'entre à l'écran.
- À la **première** intersection d'un placeholder : déclenche le rendu (R3), puis
  `observer.unobserve(el)` — **un diagramme n'est rendu qu'une fois** (pas de
  re-rendu au scroll, pas de rechargement au retour de focus fenêtre,
  contrairement à `DrawioEmbedView`).
- Si `repoPath` est absent : ne pas observer, laisser le repli `📐 label`.

### R3 — Rendu d'un diagramme

À l'entrée dans le viewport, pour un placeholder donné :

1. `const pages = await api.drawio.read(repoPath, path)` — si `null`/vide → R6.
2. `const target = resolveDrawioTarget(pages, nodeId)` (réutilisé tel quel depuis
   `lib/drawioRender.ts`) ; `page = pages[target.pageIndex]` ; si `page.xml`
   absent → R6.
3. `await loadDrawioViewer()` (singleton, réutilisé tel quel) ; échec → R6.
4. Construire la structure DOM du rendu **impérativement** (pas de React —
   cohérent avec la résolution d'images du même `useEffect`), en répliquant la
   géométrie non-éditable de `ResizableMediaFrame` (R4).
5. Sur le conteneur mxGraph : `className = 'mxgraph'` + `data-mxgraph` avec la
   **même config** que `DrawioEmbedView`
   ([DrawioEmbedView.tsx:93-112](../apps/desktop/src/renderer/tiptap/DrawioEmbedView.tsx#L93-L112))
   — `xml: page.xml`, `resize: true`, `nav: false`, `lightbox: 0`, **pas de clé
   `toolbar`**.
6. `window.GraphViewer.createViewerForElement(container, viewer => { … })`.
7. Dans le callback : mesurer la taille naturelle rendue par le viewer
   (`ResizeObserver` sur le conteneur, comme
   [DrawioEmbedView.tsx:150-162](../apps/desktop/src/renderer/tiptap/DrawioEmbedView.tsx#L150-L162)),
   puis appliquer l'échelle/le décalage de R4 une fois la taille stabilisée.
8. Surlignage de cellule (`target.highlightCellId`) : **best-effort**, même
   principe que le viewer live (overlay rectangle orange positionné depuis
   `graph.getView().getState(cell)`) ; une divergence d'API interne ne doit pas
   empêcher l'affichage du diagramme. *(Optionnel v1 — cf. Q ouverte QO1.)*

### R4 — Taille (`width`/`height`) et cadrage (`crop`) honorés

Le rendu lecture reproduit **fidèlement** la taille et le cadrage stockés, en
répliquant la géométrie de `ResizableMediaFrame` en mode non-cropping
([ResizableMediaFrame.tsx:179-203](../apps/desktop/src/renderer/tiptap/ResizableMediaFrame.tsx#L179-L203)) :

Soit `natural` = taille naturelle mesurée du viewer (`fallbackSize` du live),
`displayW = width ?? natural.width`, `displayH = height ?? natural.height` :

- **Sans `crop`** : conteneur externe `displayW × displayH`, `overflow: hidden` ;
  contenu interne rendu à `natural`, `transform: scale(displayW / natural.width)`,
  `transform-origin: 0 0`, `left: 0, top: 0`.
- **Avec `crop`** (unités du modèle mxGraph, mêmes que `cropBounds` = `natural`) :
  `contentScale = displayW / crop.width`,
  `offsetX = -crop.x * contentScale`, `offsetY = -crop.y * contentScale` ;
  conteneur externe `displayW × displayH`, `overflow: hidden` ; contenu interne à
  `natural`, `transform: scale(contentScale)`, positionné à `left/top = offsetX/offsetY`.

Comportement identique à celui du viewer live une fois la mesure `ResizeObserver`
stabilisée. `width`/`height`/`crop` absents → taille naturelle, pas de mise à
l'échelle.

### R5 — Clic = édition du champ (pas d'interaction viewer)

Un clic (simple ou double) sur le diagramme rendu se comporte **exactement comme
un clic ailleurs dans le champ** : il passe `RichTextInlineField` en mode édition
([WordView.tsx:229-233](../apps/desktop/src/renderer/components/system/WordView.tsx#L229-L233)),
où le `DrawioEmbedView` interactif complet prend alors le relais.

- Le rendu du diagramme ne doit **pas** capturer/consommer le clic : `pointer-events`
  neutralisé sur le sous-arbre du viewer + overlay transparent au-dessus **sans
  gestionnaire** (mêmes raisons que
  [DrawioEmbedView.tsx:249-261](../apps/desktop/src/renderer/tiptap/DrawioEmbedView.tsx#L249-L261) :
  les formes SVG du viewer posent leur propre `pointer-events`), l'évènement
  `click` remontant naturellement jusqu'au `onClick` du conteneur de champ.
- Pas de `showLightbox()`, pas d'« Ouvrir dans draw.io », pas de menu contextuel
  en Vue Word lecture.

### R6 — Erreurs

- `repoPath` absent → repli `📐 label` (inchangé).
- Fichier introuvable / vide / XML invalide / échec de chargement du viewer →
  remplacer le contenu du placeholder par un état d'erreur inline discret
  (p. ex. `⚠ Diagramme introuvable : <path>`), cohérent avec `§3.2a` (« état
  d'erreur explicite inline, jamais de crash »). Jamais d'exception propagée.

### R7 — Nettoyage

- `observer.disconnect()` au démontage du composant et à tout changement de
  `html` (nouvelle valeur du champ) — comme l'effet de résolution d'images.
- Les viewers rendus dans un sous-arbre remplacé par React (`dangerouslySetInnerHTML`
  ré-évalué) sont abandonnés en vidant/laissant remplacer le conteneur — même
  teardown que `DrawioEmbedView` (`container.innerHTML = ''`, abandon de la
  référence) ; l'API vendorée telle qu'utilisée aujourd'hui n'expose pas de
  `destroy()` explicite.

## Critères d'acceptation

1. Vue Word lecture, projet avec repo : un champ `richtext` contenant un bloc
   `drawio` valide affiche le **diagramme rendu** (moteur mxGraph, fidélité
   identique à l'éditeur) une fois scrollé à l'écran, sans passer en édition.
2. Un diagramme hors viewport n'est **pas** rendu : aucune lecture de fichier
   `.drawio`, aucun viewer créé tant que le placeholder n'approche pas l'écran
   (vérifiable au profiling / via un compteur d'appels `api.drawio.read`).
3. Ouvrir l'onglet Document d'un projet à ~280 éléments avec des diagrammes
   répartis : pas de gel perceptible, temps d'affichage initial comparable à
   l'état actuel (étiquettes) — seuls les ~diagrammes visibles sont rendus.
4. Un bloc `drawio` avec `width`/`height` stockés s'affiche à cette taille ; avec
   `crop` stocké, le cadrage (pan/zoom) est appliqué — rendu visuellement
   identique à celui de la Vue Édition pour le même bloc.
5. Une ancre `nodeId` pointant vers une page affiche cette page ; pointant vers
   une cellule, affiche la page contenante (surlignage best-effort si implémenté).
6. Clic sur le diagramme rendu → le champ passe en édition et le `DrawioEmbedView`
   interactif apparaît (poignées au survol/sélection, menu contextuel clic
   droit). Aucune lightbox ni ouverture externe déclenchée depuis la lecture.
7. Fichier `.drawio` référencé absent → message d'erreur inline discret, pas de
   crash, le reste du champ (texte, images, autres diagrammes) s'affiche
   normalement.
8. `repoPath` absent (cas résiduel) → repli `📐 nom-de-fichier`, comme aujourd'hui.
9. Naviguer hors de la Vue Word puis y revenir, ou modifier un champ : pas de
   fuite d'`IntersectionObserver` ni de viewers orphelins accumulés.
10. Aucune régression TypeScript / lint. `RichTextViewer`, `DrawioEmbedView`,
    `ResizableMediaFrame`, `EditView`, routes campagne : inchangés.

## Questions ouvertes (pour la phase Design)

- **QO1** — Surlignage de cellule (`highlightCellId`) en lecture Vue Word :
  l'implémenter en v1 (réplique de l'overlay du viewer live) ou le remettre à
  plus tard (page correcte affichée, sans encadré orange) ? *Proposition : v1
  minimal sans surlignage, la page contenante suffit ; à rediscuter si gênant.*
- **QO2** — Plafond de rendus concurrents : faut-il une file limitant le nombre
  de `createViewerForElement` simultanés (cas « Tout déplier » d'un gros
  document faisant entrer beaucoup de diagrammes d'un coup) ? *Proposition :
  aucun plafond en v1 — `IntersectionObserver` + `rootMargin` borne déjà, et
  `loadDrawioViewer()` charge le script une seule fois ; ajouter une file si le
  profiling montre un à-coup réel.*
- **QO3** — `rootMargin` exact et `root` : viewport (`null`) suffit-il, ou faut-il
  cibler explicitement le conteneur scrollable de la Vue Word
  ([WordView.tsx:833](../apps/desktop/src/renderer/components/system/WordView.tsx#L833)) ?
  *Proposition : viewport, plus simple et robuste ; `rootMargin` ~200 px.*
- **QO4** — Observer partagé au niveau module vs un par instance de
  `StaticRichTextViewer`. *Proposition : un par instance, nettoyage plus simple ;
  mutualisation possible plus tard.*
