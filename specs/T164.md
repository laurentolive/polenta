# T164 — Clic simple sur un élément de l'arbre → *goto* dans la vue de droite

## Contexte

Dans la Vue Système (onglets Exigences et Tests), le panneau latéral affiche l'arbre
`ElementTree`. Aujourd'hui :

| Geste sur un élément | Effet actuel |
|---|---|
| Clic simple | Sélection locale dans l'arbre uniquement (`onSelect` → `selectedIds`). **Aucun effet sur la vue de droite.** |
| Double-clic | Ouvre la Vue Édition (`onDoubleClick` → `setEditingNodeId` → `viewMode: 'edit'`). |
| Drag & drop | Réorganise l'arbre. Aucun effet sur la vue de droite. |

La spec actuelle (`SPEC-SYSTEM-VIEW.md`) précise explicitement : « La sélection dans l'arbre
n'a **aucun impact** sur le contenu de la vue document. » Ce ticket revient sur ce choix pour
le seul aspect *navigation* (pas *contenu*) : la vue de droite continue d'afficher tous les
éléments (ou les résultats filtrés) ; le clic simple ne fait que **faire défiler jusqu'à**
l'élément et le **marquer**.

Il n'existe aucun mécanisme de *scroll-to-object* dans `WordView` / `ExcelView`. Le voisin le
plus proche, `navigateToObject` (T37, `SystemView.tsx:660`), bascule en `viewMode: 'edit'` —
trop lourd pour ce besoin.

## Objectif

Au **clic simple** sur un élément de l'arbre, exécuter un ***goto*** dans la vue de droite
**déjà affichée** :

1. faire défiler la vue pour amener l'élément dans le viewport (`scrollIntoView`, aligné au
   plus proche, défilement fluide) ;
2. appliquer un **contour persistant** sur la ligne (Excel) ou la carte (Word) de l'élément.

Le *goto* **ne change jamais** le `viewMode`, ne recharge pas le contexte (schéma / arbre /
index), n'ouvre aucune nouvelle vue ni onglet.

## Comportements attendus par cas d'usage

### CU1 — Clic simple, vue Word ou Excel, sélection simple
- La vue de droite défile jusqu'à l'élément correspondant au `nodeId` cliqué.
- La ligne / carte de cet élément reçoit un contour persistant (« élément courant »).
- Le contour précédent (s'il y en avait un) est retiré — un seul élément marqué à la fois.
- Aucun changement de `viewMode`, aucune ouverture d'éditeur.

### CU2 — Clic simple, vue Édition (`viewMode: 'edit'`)
- **No-op.** Le *goto* ne s'applique pas. La sélection dans l'arbre se met à jour normalement
  (comportement inchangé). Seul le double-clic (ou l'icône Éditer) change l'élément édité.

### CU3 — Double-clic
- **Inchangé** : ouvre la Vue Édition sur l'élément (sélection simple uniquement).
- Le double-clic est précédé d'un `click` : le *goto* de CU1 peut se déclencher juste avant la
  bascule en Édition — acceptable (la vue Word/Excel est alors remplacée). Pas de traitement
  particulier requis.

### CU4 — Sélection multiple (Shift+clic, Ctrl+clic)
- Dès que `selectedIds.length > 1`, **aucun *goto*** n'est déclenché, quel que soit le
  `viewMode`.
- Un Ctrl+clic qui *réduit* la sélection à un seul élément ne déclenche pas de *goto* non plus
  (règle simple : *goto* uniquement sur un clic simple sans modificateur — `!e.shiftKey &&
  !e.ctrlKey && !e.metaKey`).

### CU5 — Clic sur un dossier
- *Goto* **sur le dossier lui-même** : scroll + contour persistant sur l'en-tête de section
  (Word) / la ligne de groupe (Excel) du dossier.
- Les dossiers sont rendus dans les deux vues avec un élément keyé par `node.id`
  (`<HeadingTag key={node.id}>` dans `WordView.renderNodes`, `<tr key={node.id}>` de ligne de
  groupe dans `ExcelView`) — le même mécanisme `data-node-id` + `scrollIntoView` s'applique,
  sans traitement particulier.
- Fonctionne y compris pour un dossier vide (la cible existe tant que le dossier est affiché,
  c.-à-d. hors filtre qui le masquerait — cf. CU7).
- Le clic simple / double-clic sur un dossier conserve par ailleurs son rôle actuel
  (sélection, expand-collapse au double-clic).

### CU6 — Drag & drop de réorganisation
- Au `drop` (fin de `handleDrop` dans `ElementTree`), déclencher un *goto* sur l'élément
  déplacé :
  - si un seul nœud déplacé et que c'est un `item` → *goto* sur ce nœud ;
  - si plusieurs nœuds ou un `folder` → *goto* sur le premier `item` de la sélection déplacée,
    ou no-op si aucun.
- But : la vue de droite (qui se ré-ordonne suite au changement d'arbre) se recale sur
  l'élément que l'utilisateur vient de bouger.
- En `viewMode: 'edit'` → no-op (cohérent avec CU2).

### CU7 — Élément introuvable dans la vue de droite
- Si aucune ligne / carte ne correspond au `nodeId` (élément masqué par un filtre, objet
  backend pas encore monté, incohérence transitoire) → **no-op silencieux** (pas d'erreur,
  pas de scroll). Le filtre global du panneau et celui de la vue document étant le même, ce
  cas ne devrait pas se produire pour un élément visible et cliquable dans l'arbre.

### CU8 — Cycle de vie du marquage « élément courant »
Le contour persistant est retiré quand :
- un autre *goto* le déplace sur un autre élément ;
- l'utilisateur clique dans le vide de l'arbre (désélection totale, `onSelect([])`) ;
- le contexte change (composant/type sélectionné dans le combobox) ;
- la vue passe en Édition puis revient (l'état *goto* n'est pas restauré — repartir de zéro).

Le contour n'est **pas** synchronisé en continu avec `selectedIds` : c'est un état distinct
(« dernière cible de *goto* »), posé par le clic simple / le drop, et seulement retiré selon
les règles ci-dessus.

## Conception indicative (à confirmer en phase Design)

- **Canal de données** : nouvel état `gotoNodeId: string | null` dans `SystemView`
  (ou le contexte `SystemViewContext`). L'arbre remonte le `nodeId` via un nouveau callback
  `onGoto?(nodeId: string)` passé à `ElementTree` par `SystemPanel`.
- **`ElementTree`** :
  - dans `handleSelect`, après `onSelect([nodeId])`, sans modificateur clavier
    (`!e.shiftKey && !e.ctrlKey && !e.metaKey`) → `onGoto?.(nodeId)` — pour un `item` comme
    pour un `folder` ;
  - dans `handleDrop`, après `onRootChange(newRoot)` → `onGoto?.(<item déplacé>)` ;
  - `handleClickEmpty` → `onGoto?.(null)` (ou un `onGotoClear`).
- **`SystemView`** : ne transmet `gotoNodeId` à `WordView` / `ExcelView` que si
  `viewMode !== 'edit'` (sinon `undefined`). Réinitialise `gotoNodeId` sur changement de
  `effectiveNodeId` / `effectiveTypeId`.
- **`WordView` / `ExcelView`** :
  - marquer chaque ligne/carte d'élément **et chaque en-tête de dossier** d'un attribut
    `data-node-id={node.id}` (`<tr>` élément ~1579 et `<tr>` de groupe ~1538/1578 dans
    `ExcelView` ; `<div>` racine de `ItemCard` ~433 et `<HeadingTag>` ~772 dans `WordView`) ;
  - `useEffect([gotoNodeId])` : `containerRef.current?.querySelector('[data-node-id="…"]')`
    → `scrollIntoView({ block: 'nearest', behavior: 'smooth' })` ;
  - classe de contour conditionnée par `gotoNodeId === node.id`. Le style doit être un
    **contour** (ex. `ring-2 ring-status-info` / `outline`) visuellement **distinct** de la
    sélection de ligne existante d'Excel (fond plein `bg-status-info-solid`).
- **Dossiers Word/Excel repliés** : l'en-tête / la ligne de groupe d'un dossier est toujours
  rendue même repliée → un *goto* sur un dossier fonctionne quel que soit son état plié/déplié
  dans la vue de droite. En revanche, si l'élément **cible est un `item` contenu dans un
  dossier replié**, tenter de déplier avant le scroll est un *plus* non requis pour la v1 —
  sinon no-op (CU7).

## Critères d'acceptation

- [ ] Vue Excel, filtre inactif : clic simple sur un élément bas de liste → la vue défile,
      la ligne devient visible et porte un contour distinct de la surbrillance de sélection.
- [ ] Vue Word : idem avec la carte de l'élément.
- [ ] Un second clic simple sur un autre élément déplace le contour ; l'ancien n'a plus de
      contour.
- [ ] `viewMode: 'edit'` : clic simple sur un élément de l'arbre ne fait rien de visible dans
      la vue (pas de rechargement, pas de scroll) ; double-clic ouvre toujours l'édition.
- [ ] Shift+clic / Ctrl+clic (multi-sélection) : aucun scroll, aucun contour posé.
- [ ] Clic sur un dossier : la vue défile jusqu'à l'en-tête de section (Word) / la ligne de
      groupe (Excel) du dossier, qui porte le contour ; fonctionne pour un dossier vide.
- [ ] Drag & drop d'un élément à une nouvelle position (même niveau) : après le dépôt, la vue
      de droite est défilée sur l'élément déplacé, qui porte le contour.
- [ ] Clic dans le vide de l'arbre : le contour « élément courant » disparaît.
- [ ] Changement de composant/type dans le combobox : pas de contour résiduel.
- [ ] Aucune régression : double-clic, menu contextuel, navigation clavier ↑/↓/Entrée, undo/redo,
      création/suppression, `navigateToObject` (clic sur un lien) fonctionnent comme avant.
- [ ] `pnpm -C apps/desktop typecheck` sans erreur nouvelle.

## Hors scope

- **Vue Recherche** (`SearchPanel`) : le clic simple ouvre déjà la page détail autonome
  (`/req/$id`, `/test/$id`, `/campaign/$id`) — comportement conservé tel quel.
- **Vue Campagnes** (`CampaignNavList`) : le clic simple ouvre déjà la campagne dans la vue de
  droite — comportement conservé tel quel (pas d'harmonisation du style de marquage avec
  Word/Excel dans ce ticket).
- **Navigation clavier** (↑/↓ dans l'arbre) : ne déclenche pas de *goto* dans cette version
  (seul le clic souris et le drop). À rouvrir si une parité clavier est souhaitée.
- **Dépliage automatique** d'un dossier replié dans la vue Word/Excel pour atteindre la cible.
- **Persistance** du marquage « élément courant » (URL, `localStorage`, restauration T52).
- Modification du contenu affiché par la vue document (toujours piloté par le seul filtre
  global).
