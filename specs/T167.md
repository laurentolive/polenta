# T167 — Vue Recherche : liste des résultats (style Vue Word) dans la zone principale

## Contexte

La Vue Recherche (`/search`, activité « Recherche » de la barre latérale) est
composée de deux zones :

- **Panneau latéral** (`SearchPanel.tsx`) — champ de recherche, options
  (casse / mot entier / regex), remplacement, filtres de type (Exig. / Tests /
  Camp.), et la liste hiérarchique des résultats (élément → occurrences avec
  extrait surligné). **Fonctionne bien**, non remis en cause par ce ticket sauf
  sur le comportement du clic (voir plus bas).
- **Zone principale** (`routes/search.tsx`) — depuis T107, une simple page vide
  avec une icône loupe et un message d'invitation. **Rien ne s'y passe** quand une
  recherche est lancée.

T167 remplit cette zone principale : elle affiche la **liste des éléments
résultats sous forme de document (style Vue Word)**, avec navigation au clic
simple et édition au double-clic — sans jamais quitter la Vue Recherche.

## Description fonctionnelle

### 1. Liste des résultats en zone principale (style Vue Word)

Tant qu'aucune recherche n'est active (champ vide, ou regex invalide), la zone
principale garde l'état vide actuel (icône + message d'invitation).

Dès qu'une recherche produit au moins un résultat, la zone principale affiche
**une carte par élément résultat**, dans le même ordre que le panneau latéral
(exigences, puis tests, puis campagnes ; ordre interne = ordre de la liste
`api.*.list`, comme aujourd'hui dans `SearchPanel`).

Chaque carte reprend la présentation d'une carte de la **Vue Word**
(`WordView.ItemCard`), en **lecture seule** :

- **En-tête** : badge de catégorie (EX / TC / CA, mêmes couleurs
  `CATEGORY_CHART_BG` que le panneau latéral), identifiant (`id`), titre, badge
  de statut (`getStatusClass`), numéro de version le cas échéant.
- **Corps** : **tous les champs** de l'élément rendus en lecture, y compris les
  champs `richtext` (via `StaticRichTextViewer`, comme la Vue Word — diagrammes
  draw.io rendus paresseusement T163). Pour un test : la table des étapes.
- **Pas d'édition inline** dans la carte (ni champ, ni statut, ni lien, ni
  étape). Toute modification passe par le double-clic (§3). C'est la différence
  assumée avec `WordView` en Vue Système.
- **Pas de vue Tableau / Excel** : les résultats sont de types hétérogènes
  (exigence + test + campagne mélangés), une grille à colonnes fixes n'a pas de
  sens. La zone principale n'a donc qu'un seul mode d'affichage.
- **Pas de dossiers / sections / numérotation** : les résultats sont une liste
  plate transverse à l'arborescence. Pas de titres `Hn`.

Le type de chaque carte (et donc son `typeDef` : libellés de champs, ordre des
champs, statuts) est résolu depuis le schéma du repo courant via
`objectTypeRef` de l'élément (`useProjectSchema` + helpers `getReqTypeDef` /
équivalent test). Un élément dont le type n'est pas résolvable reste affiché
avec ses champs bruts (repli, comme `req.$reqId.tsx`).

#### Surbrillance des occurrences

Dans le corps de la carte, les occurrences du terme recherché sont **surlignées**
(`<mark>`, même style `bg-status-warning-solid/70` que l'extrait du panneau
latéral) dans les champs texte / richtext où elles apparaissent. Pour un champ
`richtext`, la surbrillance porte sur le rendu lecture ; une implémentation
« best effort » est acceptable (surligner les nœuds texte correspondant au
`buildRegex` courant). Aucune surbrillance = acceptable en repli si le champ est
un richtext complexe, mais le champ concerné doit rester visible.

### 2. Clic simple sur un résultat — « goto »

Le clic simple (sans modificateur) sur un résultat — **dans le panneau latéral
comme dans la liste de droite** — a le **même comportement que le clic simple
dans l'arbre des vues Exigences / Tests** (T164, `SPEC-SYSTEM-VIEW` §goto) :

- la zone principale **défile** jusqu'à la carte correspondante
  (`useScrollToNode`, attribut `data-node-id` = `id` de l'élément) ;
- la carte reçoit un **contour bleu persistant** (`ring-2 ring-inset
  ring-status-info-solid`, constante `GOTO_OUTLINE_CLASS`) jusqu'au prochain
  goto / clic dans le vide.

Ce comportement **remplace** la navigation actuelle du panneau latéral (qui
ouvrait la page détail `/req/$id` ou `/test/$id` et quittait la Vue Recherche).
Le clic simple ne quitte plus jamais `/search`.

Clic dans le vide de la liste de droite = efface le contour goto (comme
`handleClickEmpty` de l'arbre).

### 3. Double-clic sur un résultat — édition inline

Le double-clic sur une carte (ou sur une ligne de résultat du panneau latéral)
ouvre l'**édition de l'élément dans la zone principale**, **sans quitter
`/search`** (aucune navigation routeur — un simple état local de la route, comme
le `viewMode === 'edit'` de `SystemView`).

- L'interface d'édition est le **composant `EditView` complet** (le même que le
  double-clic dans les vues Exigences / Tests) : autosave par champ, section
  Liens, table des Étapes pour un test, badge de couverture pour une exigence,
  `Ctrl/Cmd+Entrée` = valider, `Échap` = retour.
- Un bouton **« Retour aux résultats »** (dans le `ViewHeader` de la zone
  principale) referme l'édition et réaffiche la liste des résultats, **inchangée**
  (même recherche, même scroll, même contour goto). Le flush des champs non
  sauvegardés suit le mécanisme T159 d'`EditView` (autosave debouncé + flush au
  changement d'élément / démontage).
- L'en-tête affiche le libellé du type + l'`id` de l'élément édité, comme en Vue
  Système.
- Après retour, la carte de l'élément édité reflète les modifications
  (invalidation des queries `requirements` / `tests` déjà utilisées par
  `SearchPanel`, donc la recherche est recalculée ; un élément qui ne matche
  plus disparaît de la liste — comportement acceptable et cohérent).
- **Navigation vers un objet lié** depuis la section Liens d'`EditView` : ouvre
  l'objet cible **dans un nouvel onglet** (`openTab`, `/req/$id` ou `/test/$id`).
  Pas de navigation « en place » dans la Vue Recherche (l'arbre de la Vue
  Système n'existe pas ici). Le retour arrière multi-niveaux d'`EditView` en Vue
  Système (`backHistory`) est **hors scope**.

#### Cas des campagnes

Une campagne n'a pas d'endpoint d'édition générique (`api.campaigns` n'expose
pas de `update`). Le double-clic sur une carte campagne **navigue vers la page
campagne dédiée** `/campaign/$id` (quitte la Vue Recherche) — même comportement
que le clic actuel du panneau latéral pour ce type. La carte campagne reste
affichée en lecture seule dans la liste comme les autres.

### 4. Remplacement (inchangé)

Le remplacement (`Remplacer` / `Tout remplacer`) reste piloté depuis le panneau
latéral, inchangé. Après un remplacement, les cartes de la zone principale se
mettent à jour via l'invalidation des queries (déjà en place).

### 5. Partage d'état panneau ↔ zone principale

`SearchPanel` (sidebar) et `routes/search.tsx` (zone principale) sont dans deux
sous-arbres React distincts (Sidebar vs `<Outlet/>`). L'état de recherche
(requête, options, filtres de type, résultats calculés, cible goto, élément en
édition) doit être **partagé** — via un contexte `SearchProvider` monté dans
`AppLayout` (au même niveau que `SystemViewProvider` / `VersioningProvider`,
dans la branche `currentProjectId`).

- Les requêtes de liste (`requirements` / `tests` / `campaigns`) et le calcul des
  résultats migrent du composant `SearchPanel` vers le provider (ou un hook
  qu'il utilise). `enabled: !!regex` est conservé : **aucun fetch tant qu'aucune
  recherche n'est saisie** — le provider est inerte au repos.
- Effet de bord assumé et souhaitable : la requête de recherche **survit
  désormais** à une navigation hors de la Vue Recherche puis au retour (le
  provider reste monté tant qu'un projet est ouvert), au lieu d'être perdue à
  chaque démontage de `SearchPanel`.

## Critères d'acceptation mesurables

1. Avec une recherche active produisant N résultats (exigences + tests +
   campagnes), la zone principale affiche exactement N cartes, une par élément,
   dans le même ordre que le panneau latéral.
2. Chaque carte affiche id, titre, statut, et tous les champs de l'élément en
   lecture (richtext inclus, rendu sans éditeur TipTap).
3. Le clic simple sur un résultat (panneau OU carte) fait défiler la zone
   principale jusqu'à la carte et lui applique le contour `GOTO_OUTLINE_CLASS` ;
   aucune navigation routeur ne se produit (`location.pathname` reste `/search`).
4. Le double-clic sur une carte exigence ou test affiche `EditView` dans la zone
   principale avec un bouton de retour ; `location.pathname` reste `/search`.
5. « Retour aux résultats » réaffiche la liste sans perte de la recherche en
   cours ni du contour goto.
6. Le double-clic sur une carte campagne navigue vers `/campaign/$id`.
7. Une modification faite dans `EditView` (search) est persistée sur disque
   (fichier YAML de l'élément) et visible après retour à la liste.
8. Aucune régression TypeScript (`npx tsc --noEmit` dans `apps/desktop`).
9. Le panneau latéral reste fonctionnel : options, filtres de type,
   remplacement, liste hiérarchique d'occurrences — inchangés hormis le
   comportement du clic (goto au lieu de navigation).
10. Aucun fetch de liste (`requirements`/`tests`/`campaigns`) déclenché tant
    qu'aucune recherche n'est saisie.

## Hors scope (explicite)

- **Vue Tableau / Excel** des résultats — exclue par nature (types hétérogènes).
- **Édition inline dans la carte** (champs, statut, liens, étapes directement
  dans la liste) — toute édition passe par le double-clic → `EditView`.
- **Édition inline d'une campagne** — pas d'endpoint ; double-clic = navigation
  vers la page campagne.
- **Retour arrière multi-niveaux** (`backHistory` d'`EditView` en Vue Système)
  et navigation « en place » vers objets liés — remplacés par « ouvrir dans un
  nouvel onglet ».
- **Recherche multi-repo / cross-composant** — la Vue Recherche reste sur le
  repo racine, comme aujourd'hui.
- **Surbrillance parfaite des occurrences dans un richtext complexe** (tableaux,
  diagrammes) — best effort, repli = pas de surbrillance mais champ visible.
- **Persistance disque de la requête de recherche** entre deux sessions de
  l'app — le partage d'état vaut pour la session courante uniquement.
- **Roue crantée ⚙️ / champs visibles configurables** pour la liste de résultats
  — la carte affiche tous les champs, pas de configuration par vue.
