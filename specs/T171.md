# T171 — Base de paramètres partagés entre exigences et tests

## Contexte

Un même cas de test est souvent **générique** : il est réutilisé sur plusieurs produits. Les
valeurs dont il a besoin (seuils, modes, puissances) dépendent pourtant du produit. Elles
figurent aujourd'hui dans les exigences, par exemple dans une colonne « objectifs » que la
qualité remplit, et le testeur les recopie à la main. Une même information, comme la liste des
modes d'aspiration et leur puissance, sert souvent à plusieurs tests et à plusieurs exigences.
Elle est alors dupliquée, avec un risque d'incohérence.

T97 a introduit des paramètres `{label}` dans le texte d'un test (SPEC-TESTS §2.4a), dont la
valeur est **saisie à la main** à l'ajout du test en campagne.

T171 introduit une **base de paramètres**. Un paramètre est un objet à part entière (nom et
valeur), défini une fois, et référencé par son nom dans le texte des exigences et des tests. Le
paramètre ne dépend pas des liens de traçabilité : une exigence et un test qui utilisent le même
paramètre n'ont pas besoin d'être liés.

*Historique de cadrage : une première version de cette spec proposait de référencer un champ de
l'exigence vérifiée (`{req.<champ>}`, résolu via le lien de vérification). Elle a été abandonnée
au profit de la base de paramètres, pour n'avoir qu'une seule mécanique, indépendante des liens.*

**Dépendance : T172** (livré — revalidation). T171 appelle le point d'entrée de T172,
`RevalidationService.markImpactedBy`, pour marquer `needsRevalidation` les éléments impactés
par la modification d'un paramètre (§9). Depuis T172, le flag est porté par les **éléments**
(exigences, tests), pas par les liens (SPEC-REQ §5.3).

## Principes

1. **Une seule mécanique.** Les exigences et les tests utilisent la même syntaxe `{nom}`. Les
   paramètres T97 saisis à la main sont unifiés avec la base (§6).
2. **Le nom est le contrat, la valeur appartient au repo.** Un test générique référence
   `{puissance_turbo}`, et chaque repo définit la valeur dans sa propre base.
3. **Chaque composant porte ses paramètres.** Le repo produit et chaque repo composant ont leur
   propre base (§1).
4. **Les variantes passent par les branches git.** Deux jeux de valeurs pour un même composant
   (par exemple deux niveaux de puissance) correspondent à deux branches du composant. Chaque
   produit épingle la branche qui lui correspond. T171 n'ajoute aucune notion de variante : la
   base utilisée est celle de la branche ou du commit extrait.
5. **Les valeurs sont figées en campagne**, comme le contenu du test (T49).

## Description fonctionnelle

### 1. Stockage : un fichier unique par repo

Chaque repo Polenta (produit ou composant) peut contenir un fichier
`parameters/parameters.yaml` qui regroupe **tous** les paramètres du repo. C'est le même
principe que `links/links.yaml` pour les liens.

```yaml
# parameters/parameters.yaml
parameters:
  puissance_eco:
    value: "150"
    unit: W
    description: Puissance d'aspiration en mode Eco
  puissance_turbo:
    value: "450"
    unit: W
    description: Puissance d'aspiration en mode Turbo
  tension_nominale:
    value: "14.4"
    unit: V
```

| Élément | Obligatoire | Description |
|---|---|---|
| clé (`puissance_turbo`) | oui | Nom du paramètre, et donc son identifiant. Grammaire : `[A-Za-z0-9_-]+`, la même que les labels T97. L'unicité dans le repo est garantie par la structure en dictionnaire. Non modifiable après création (§9). |
| `value` | oui | Valeur, **toujours une chaîne**. Peut être vide (§5). |
| `unit` | non | Unité, ajoutée à la valeur lors de la substitution (§5). |
| `description` | non | Texte libre, affiché dans la vue Paramètres et dans le sélecteur d'insertion. |

**Règles d'écriture :**
- Les clés sont **triées par nom** à chaque écriture, pour que les diffs soient stables et que
  deux modifications concurrentes de paramètres différents fusionnent sans conflit git dans la
  majorité des cas.
- Les écritures sont sérialisées par repo, avec le même verrou par clé que les autres écritures
  (`serialize-writes.util.ts`).
- Absence du fichier ou dictionnaire vide : la base du repo est vide.

Le fichier est versionné dans git comme les exigences et les tests. La base suit donc les
branches et les baselines, et une baseline se lit en une seule lecture au tag.

**Choix du fichier unique plutôt qu'un fichier par paramètre :**
- vue d'ensemble immédiate et diff lisible ;
- lecture au tag triviale ;
- cohérent avec `links/links.yaml`.

Ce qu'on perd : l'historique `git log` par paramètre. Les champs dérivés `createdBy`/`updatedBy`
ne sont donc pas calculés par paramètre.

### 2. Syntaxe de référence

| Forme | Désigne |
|---|---|
| `{nom}` | Le paramètre `nom` du **repo qui contient l'objet** (exigence ou test) où la référence est écrite. |
| `{<nœud>::nom}` | Le paramètre `nom` du composant `<nœud>`, c'est-à-dire le nom du nœud submodule dans le schéma. C'est la même convention que `objectTypeRef`. |

- Un test d'un composant écrit `{puissance_turbo}`. Il est résolu dans la base de **ce
  composant**, même quand on l'exécute depuis une campagne du repo produit.
- Une exigence du repo produit qui veut la valeur d'un composant écrit
  `{motor-control::courant_max}`.
- La forme `{<nœud>::nom}` n'est valide que vers un nœud visible depuis le repo de l'objet, à
  savoir les composants déclarés dans son schéma. Un repo composant ne référence pas de
  paramètre cross-composant (même règle que CLAUDE.md, règle 8).

### 3. Où une référence est reconnue

- **Tests** : les mêmes champs que les paramètres T97, soit `preconditions`, `action` et
  `expectedResult` de chaque étape, et `postconditions`, dans l'ordre de
  `extractTestParameters`. `TestStep.notes` et les champs personnalisés du test ne sont pas
  scannés.
- **Exigences** : tous les champs de `fields` de type `text`, `textarea` et `richtext`, dont
  `statement`. Le `title` n'est pas scanné.

Ailleurs, le texte `{…}` reste littéral.

### 4. Affichage d'une référence

Une référence de paramètre a toujours un **style dédié**, visuellement distinct du texte saisi
(pastille, couleur ou soulignement : c'est au design de le définir). Le même style est utilisé
partout.

| Contexte | Texte affiché | Au survol | Double-clic |
|---|---|---|---|
| Exigence ou test, en lecture : fiche exigence, fiche de définition du test, vue Word, vue Excel, résultats de recherche | **Valeur** (`450 W`), lue sur l'état courant du repo de l'élément | Nom du paramètre (`puissance_turbo`, ou `motor-control::courant_max`), et sa description | Ouvre l'**édition du paramètre** (§8). Lecture seule si le nœud qui le porte est `readonly`. Possible aussi depuis un élément approuvé (verrouillé) : la modification suit alors le §9. |
| Campagne : exécution et relecture | **Valeur figée** de l'instance (§7) | Nom du paramètre, et origine : base ou saisie manuelle | Aucune action : la valeur est figée |
| Éditeur (`RichTextField`), en édition d'une exigence ou d'un test | La référence `{nom}`, avec le style dédié | Valeur courante | Ouvre l'édition du paramètre |

Exigences et tests se comportent donc de la même façon. Sur la fiche d'un test générique, la
valeur affichée est celle de la base courante. La valeur réellement utilisée à l'exécution est
celle figée en campagne (§7).

Une **référence non résolue** (§5) est affichée littéralement, avec une variante « non résolue »
du style (par exemple barrée ou en couleur d'alerte), pour rendre l'incohérence visible. Le
double-clic sur une référence non résolue locale propose de **créer** le paramètre, avec le nom
pré-rempli.

### 5. Règles de substitution

- Le texte substitué est `value`, suivi de ` <unit>` quand `unit` est renseigné (par exemple
  `450 W`).
- **Référence non résolue : la référence reste affichée littéralement**, `{nom}`, sans bloquer.
  C'est la même règle que pour un paramètre T97 sans valeur (`substituteParams`). Cas concernés :
  - paramètre inexistant dans la base visée ;
  - nœud inconnu ou non visible ;
  - paramètre existant, mais dont `value` est vide. C'est une incohérence : le texte attend une
    valeur que la base ne fournit pas.
- La valeur est insérée en texte brut dans le Markdown du champ, rendu ensuite par
  `RichTextViewer` (`html: false`), comme en T97.

### 6. Unification avec les paramètres T97

La syntaxe `{nom}` de T97 et celle de T171 sont **la même**. À l'ajout d'un test en campagne,
pour chaque référence détectée :

1. **Référence présente dans la base** avec une valeur non vide, à la source de résolution (§7) :
   elle est lue automatiquement, figée, et **non modifiable**.
2. **Référence locale `{nom}` absente de la base** : elle devient un **paramètre à saisir à la
   main**, exactement comme en T97. C'est utile pour les valeurs propres au banc ou à la
   session (numéro de série, température ambiante). Elle reste modifiable ensuite
   (`updateRunParams`).
3. **Référence cross-composant `{<nœud>::nom}` non résolue** : elle n'est **jamais** proposée à
   la saisie et reste littérale.

Les tests et campagnes T97 existants fonctionnent sans changement tant qu'aucun paramètre du
même nom n'existe dans la base. Si un paramètre de la base porte le même nom qu'un label T97
existant, ce label est désormais résolu automatiquement à l'ajout. C'est le comportement voulu,
qui permet d'adopter progressivement la base. Les campagnes déjà créées ne changent pas, car
leurs valeurs sont figées.

La règle « un test sans paramètre ne peut être inclus qu'une fois » (T97 sprint 2) ne compte que
les références **à saisir**. Un test dont toutes les références sont résolues depuis la base se
comporte comme un test sans paramètre : une seule instance, pas de « Dupliquer ».

### 7. Résolution en campagne

La résolution a lieu **à l'ajout du test dans la campagne**, sur tous les chemins d'ajout :
`create` (y compris depuis l'analyse d'impact), `addTests` et « Dupliquer ». Les valeurs sont
figées dans l'instance (§10). Une modification ultérieure de la base ne change pas une campagne
existante.

**Source de résolution :**

- **Campagne avec `baselineRef`.** Les paramètres sont **toujours** lus au tag, jamais sur
  l'état courant. Une baseline pose le même tag sur le repo produit et sur chaque composant
  (SPEC-FORKS-BRANCHES-BASELINES §5.3) : chaque paramètre est lu dans
  `parameters/parameters.yaml`, au tag du même nom, dans le repo qui le porte. On réutilise la
  lecture à un ref git de l'analyse d'impact (T46, `git.readYamlRef`).
- **Campagne sans `baselineRef`.** Les paramètres sont lus sur l'état courant : la branche
  extraite du repo produit, et le commit épinglé et extrait de chaque composant.

**Tag introuvable.** Le champ `baselineRef` est aujourd'hui une saisie libre, avec une liste de
suggestions des tags existants. Il peut donc contenir un texte qui ne correspond à aucun tag
(faute de frappe, tag supprimé depuis, ou tag absent sur un composant). Dans ce cas, les
paramètres de ce repo ne peuvent pas être lus à la baseline, et on **ne se replie pas sur l'état
courant** :

- l'ajout du test est **autorisé** ;
- les références vers un repo où le tag est introuvable ne sont **pas remplacées** : elles
  restent littérales, avec le style « non résolue » (§4) ;
- elles ne sont pas non plus proposées en saisie à la main, puisque ce sont des paramètres de la
  base qu'on n'a pas pu lire ;
- l'utilisateur est **notifié** (voir ci-dessous).

**Notification des références non résolues.** Une référence peut rester non résolue à l'ajout :
tag introuvable, paramètre absent au tag ou de l'état courant, valeur vide, nœud inconnu. Dans
tous ces cas, elle est enregistrée dans l'instance (`unresolvedParams`, §11) et signalée :

- **avant validation**, dans le panneau d'ajout et dans le formulaire de création de campagne :
  pour chaque test, la liste des références qui ne pourront pas être résolues, avec la raison
  (« baseline `<ref>` introuvable dans `<repo>` », « paramètre absent », « valeur vide ») ;
- **après l'ajout**, par une notification qui récapitule les tests ajoutés avec des références
  non résolues ;
- **dans la campagne** : un indicateur sur l'instance dans la liste des tests, et un bandeau en
  tête des pages d'exécution et de relecture qui liste les références non résolues.

Les références locales absentes de la base, qui passent en saisie manuelle (§6, cas 2), ne sont
pas concernées : elles ont une valeur saisie.

Le **contenu du test** (`testSnapshot`) reste pris sur l'état courant du test : la règle T49 est
inchangée.

**Panneau d'ajout et formulaire de création de campagne.** Pour chaque test sélectionné :
- les références résolues depuis la base sont affichées en lecture seule, avec leur valeur ;
- seules les références à saisir sont demandées ;
- la complétude (`isParamsComplete`) ne porte que sur ces dernières.

**Exécution et relecture** (`campaign.$campaignId_.execute.$testId`,
`campaign.$campaignId_.run.$testId`) :
- chaque référence est remplacée par la valeur figée de l'instance, qu'elle vienne de la base ou
  d'une saisie, avec le style du §4 ;
- l'en-tête indique la source de résolution : le tag, ou « état courant ».

**Liste des tests de la campagne.** Les valeurs saisies à la main restent affichées à côté du
titre, comme en T97. Les valeurs issues de la base n'y sont pas listées, pour ne pas surcharger
la liste.

### 8. Vue Paramètres et édition d'un paramètre

Une nouvelle vue, accessible depuis la navigation principale comme Exigences et Tests, liste les
paramètres :

- **Regroupement par repo** : le produit, puis chaque composant du workspace.
- **Pour chaque paramètre** : nom, valeur, unité, description, et nombre d'utilisations.
- **« Utilisé par »** : la liste des exigences et des tests qui référencent le paramètre, en
  références directes et cross-composant. Chaque entrée est un **lien qui ouvre l'élément**
  (fiche exigence ou fiche test). Les éléments en statut terminal sont affichés grisés et ne
  bloquent pas la suppression (§9).
- **Création et modification** sur les repos modifiables. Les paramètres d'un nœud
  `readonly: true` sont en lecture seule, comme ses exigences et ses tests.
- **Recherche** par nom, valeur ou description.

L'**édition d'un paramètre** (valeur, unité, description) se fait dans une boîte de dialogue.
C'est la même boîte, qu'elle soit ouverte depuis la vue Paramètres ou par double-clic sur une
référence (§4). Elle affiche aussi la liste « Utilisé par ».

L'écriture passe par le même workflow git que les exigences et les tests : modifications en
attente, puis « Publier ».

### 9. Insertion, suppression, modification

**Insertion depuis l'éditeur.** Dans l'éditeur riche (`RichTextField`), pour les champs
d'exigence et de test où une référence est reconnue (§3) :

- **Déclenchement** : une action « Insérer un paramètre » dans la barre d'outils, ou la saisie
  de `{`, qui ouvre la même liste en autocomplétion.
- **Sélecteur** : recherche parmi les paramètres du repo courant et des composants visibles,
  avec pour chacun le nom, la valeur, l'unité et le repo.
- **Paramètre existant** : le choisir insère `{nom}`, ou `{<nœud>::nom}` s'il vient d'un
  composant.
- **Nouveau paramètre** : « Créer un paramètre » demande le nom, la valeur, l'unité et la
  description, ajoute l'entrée dans `parameters/parameters.yaml` du repo courant, puis insère
  `{nom}`. Le nom doit respecter la grammaire du §1 et ne pas exister déjà.
- **Saisie manuelle** : taper `{nom}` à la main reste possible partout, y compris dans les
  champs `text` et `textarea` non riches.

**Renommage.** Il n'est pas possible dans T171 : le nom est l'identifiant et les références sont
du texte.

**Suppression.** Elle est **refusée tant que le paramètre est utilisé** par au moins une exigence
ou un test, dans le repo du paramètre ou dans un repo qui le référence en cross-composant. Le
refus affiche la liste « Utilisé par », avec des liens qui ouvrent directement chaque élément,
pour que l'utilisateur retire les références avant de réessayer. Un paramètre inutilisé est
supprimé après une simple confirmation.

Les références déjà figées dans des campagnes (`resolvedParams`) ne comptent pas comme des
utilisations : la campagne garde sa valeur. Les éléments en statut terminal (`isTerminal`, ex.
`obsolete`) ne comptent pas non plus pour le refus de suppression ; ils restent listés, grisés,
dans « Utilisé par », et leur référence devient non résolue (§5) après la suppression.

**Modification d'un paramètre utilisé par un élément `approved`** (exigence ou test ; « approuvé »
= statut `isApproval` de son type, comme en T172) :

Est une modification, au sens de ce paragraphe, tout changement qui modifie le **texte affiché**
d'un élément (§5) : changement de `value` ou de `unit`, et **création** d'un paramètre dont le
nom résout des références jusque-là non résolues. Un changement de `description` seule ne
modifie aucun texte affiché et ne déclenche rien. Les éléments concernés sont les utilisateurs
du paramètre au sens de « Utilisé par » (§8), références cross-composant comprises.

1. une confirmation liste les éléments approuvés concernés ;
2. une fois confirmée, elle est traitée comme une **modification de chacun de ces éléments** au
   sens de T172 (SPEC-REQ §5.3) : `RevalidationService.markImpactedBy` est appelé pour chacun ;
3. les **éléments liés** à chacun d'eux, quel que soit le sens et le type du lien, passent à
   `needsRevalidation: true`, avec les mêmes exclusions qu'en T172 (terminaux, readonly,
   orphelins) ; les liens eux-mêmes ne sont pas modifiés ;
4. l'élément approuvé qui utilise le paramètre est **lui aussi** marqué (décision validée) : son
   texte affiché a changé sans passer par un brouillon ni une relecture. C'est la différence avec
   T172, où l'élément rouvert n'est pas marqué parce qu'il repasse par la relecture avant d'être
   réapprouvé. Mêmes exclusions qu'en T172 pour lui (readonly, terminal) ;
5. le statut des éléments n'est **pas** modifié : pas de retour en `draft`. Les éléments marqués
   affichent l'icône ⚠ « Impact à vérifier » ; le flag est levé depuis l'analyse d'impact (T173).

Les éléments non approuvés qui utilisent le paramètre ne déclenchent aucun marquage, comme en
T172 (l'édition d'un élément non approuvé ne marque rien).

Seule une modification faite **par l'application** (vue Paramètres, dialogue d'édition, création
depuis l'éditeur) déclenche le marquage. Un changement de valeurs arrivé par git (changement de
branche d'un composant, pull, merge de `parameters/parameters.yaml`) change les valeurs affichées
(critère 12) sans rien marquer : c'est hors scope, comme pour les autres objets en T172.

### 10. Exports

Les exports **résolvent les paramètres**, aussi bien pour les exigences que pour les tests.

| Export | Source des valeurs |
|---|---|
| Exigences : `requirements.docx.ts`, `requirements.xlsx.ts`, PDF `print.requirements` | Base courante du repo de chaque exigence, comme à l'affichage (§4) |
| Définitions de tests : `tests.docx.ts`, `tests.xlsx.ts`, PDF `print.tests` | Base courante du repo de chaque test, comme à l'affichage (§4) |
| Campagne, plan et rapport : `campaign.docx.ts`, `campaign.xlsx.ts`, PDF `print.campaign-plan` et `print.campaign-report` | Valeurs figées de chaque instance : `resolvedParams`, puis `paramValues`. Les paramètres T97 saisis à la main sont donc aussi substitués, ce qu'ils n'étaient pas avant T171. |

Une référence non résolue reste littérale dans l'export (§5). Le style dédié du §4 n'est pas
exigé dans les exports.

### 11. Modèle de données

**Nouveau type `Parameter`** (`packages/types`), et format du fichier :

```ts
interface Parameter {
  name: string          // clé dans parameters.yaml
  value: string
  unit?: string
  description?: string
}

interface ParametersFile {
  parameters: Record<string, Omit<Parameter, 'name'>>
}
```

**`CampaignTestRun`** (`packages/types/src/campaign.ts`) reçoit trois champs optionnels :

| Champ | Type | Description |
|---|---|---|
| `resolvedParams` | `Record<string, string>` | Valeurs lues dans la base et figées à l'ajout. La clé est la référence telle qu'écrite dans le test (`puissance_turbo`, `motor-control::courant_max`). La valeur est déjà mise en forme (`value` + unité, §5). Seules les références résolues avec une valeur non vide y figurent. Aucune API ne modifie ce champ après l'ajout. |
| `paramSourceRef` | `string` | Tag git auquel les paramètres ont été lus. Égal au `baselineRef` de la campagne quand il y en a un, absent sinon (état courant). |
| `unresolvedParams` | `{ ref: string; reason: 'tag_not_found' \| 'missing' \| 'empty' \| 'unknown_node' }[]` | Références de base non résolues à l'ajout, avec leur raison (§7). Absent ou vide si tout est résolu. Sert à la notification dans la campagne. |

`paramValues` (T97) garde son rôle : valeurs **saisies à la main**, modifiables. Une même
référence ne peut pas figurer dans les deux.

**Substitution à l'affichage et à l'export** : pour chaque référence, on prend d'abord
`resolvedParams`, puis `paramValues`. À défaut, la référence est affichée littéralement.

**Exemple (`campaigns/CAMP-0003.yaml`) :**

```yaml
baselineRef: baseline/v1.0
runs:
  - entryId: TEST-0042-1
    testCaseId: TEST-0042
    testSnapshot: { ... }            # inchangé (T49)
    status: pending
    paramValues:                     # inchangé (T97) : saisi à la main
      numero_serie: SN-2026-0412
    resolvedParams:                  # nouveau (T171) : lu dans la base, figé
      puissance_turbo: 450 W
      motor-control::courant_max: 12 A
    paramSourceRef: baseline/v1.0    # nouveau (T171)
    unresolvedParams:                # nouveau (T171)
      - ref: tension_nominale
        reason: missing              # absent de la base au tag baseline/v1.0
```

**Compatibilité ascendante.**
- Les trois champs sont optionnels : les campagnes existantes se lisent sans migration ni
  réécriture.
- Un repo sans `parameters/parameters.yaml` a une base vide : tout se comporte comme en T97, à
  une exception près, la substitution des paramètres T97 dans les exports de campagne (§10).

**DTO et IPC.**
- `CreateCampaignDto`, `addTests` et `duplicateTest` ne changent pas de signature.
- La résolution se fait côté main process (`campaigns.service.ts`) : le renderer ne fournit que
  les valeurs saisies à la main.
- Pour la notification **avant validation**, un canal IPC de prévisualisation calcule, pour une
  campagne (ou un `baselineRef` à la création) et une sélection de tests, les références
  résolues, à saisir et non résolues, sans rien écrire.
- De nouveaux canaux IPC couvrent la base : lister, lire, créer, modifier, supprimer (avec refus
  si utilisé), et « utilisé par ».

## Critères d'acceptation

1. Soit le paramètre `puissance_turbo` (valeur `450`, unité `W`) dans le repo produit. Une
   exigence dont le `statement` contient `SHALL deliver {puissance_turbo}` s'affiche, en
   lecture, « SHALL deliver 450 W ». La valeur a le style dédié, et le survol affiche
   `puissance_turbo`.
2. Un double-clic sur cette valeur ouvre l'édition du paramètre. Après modification, l'exigence
   affiche la nouvelle valeur.
3. Un test du même repo qui contient `{puissance_turbo}` dans un `expectedResult`, ajouté à une
   campagne sans baseline, affiche « 450 W » à l'exécution. Aucune saisie n'est demandée pour
   ce paramètre à l'ajout.
4. Après l'ajout, passer la valeur à `400` ne change pas la campagne existante. Un nouvel ajout,
   dans une autre campagne, affiche « 400 W ».
5. Un test du composant `motor-control` qui contient `{courant_max}`, ajouté à une campagne du
   repo `motor-control`, est résolu dans la base de `motor-control`. (Reformulé au design : les
   campagnes ne contiennent aujourd'hui que les tests de leur propre repo ; la résolution
   utilise le repo du test, et couvrira donc des campagnes inter-repos si elles apparaissent.)
6. Une exigence du produit qui contient `{motor-control::courant_max}` affiche la valeur du
   composant.
7. Soit une campagne avec `baselineRef: baseline/v1.0`, où `puissance_turbo` valait `450` au tag
   et vaut `400` dans l'état courant. L'instance affiche « 450 W », et `paramSourceRef` vaut
   `baseline/v1.0`.
8. Soit une campagne dont le `baselineRef` ne correspond à aucun tag. Un test qui contient
   `{puissance_turbo}` est ajouté. La référence reste littérale, avec le style « non résolue »,
   et n'est pas proposée en saisie. Le problème est signalé avant validation, notifié après
   l'ajout, et visible sur l'instance (indicateur dans la liste, bandeau à l'exécution).
   `unresolvedParams` contient `{ ref: puissance_turbo, reason: tag_not_found }`.
9. `{inconnu}` dans un test est demandé en saisie à la main à l'ajout, comme en T97.
   `{motor-control::inconnu}` n'est pas demandé et reste littéral, avec le style « non
   résolue ».
10. Un paramètre dont `value` est vide laisse la référence littérale, dans l'exigence comme en
    campagne.
11. Un test dont toutes les références sont résolues depuis la base ne propose pas
    « Dupliquer ».
12. Changer de branche sur un composant, pour une autre variante, change les valeurs affichées
    dans les exigences, et celles résolues aux ajouts suivants en campagne.
13. La vue Paramètres liste les paramètres par repo, permet la création et la modification sur
    un repo modifiable, et les interdit sur un nœud `readonly`. « Utilisé par » liste les
    exigences et les tests qui référencent le paramètre, et chaque entrée ouvre l'élément.
14. La suppression d'un paramètre utilisé est refusée. Le refus liste les éléments utilisateurs,
    avec des liens qui les ouvrent. Une fois les références retirées, la suppression réussit.
    Un paramètre utilisé uniquement par des éléments `obsolete` se supprime après confirmation.
15. Dans l'éditeur, « Insérer un paramètre », ou la saisie de `{`, propose les paramètres
    existants. Le choix insère la bonne forme de référence. « Créer un paramètre » ajoute
    l'entrée dans `parameters/parameters.yaml` et insère la référence.
16. Modifier un paramètre utilisé par une exigence ou un test `approved` affiche une
    confirmation qui liste ces éléments. Une fois confirmée, chacun de ces éléments et les
    éléments qui lui sont liés (quel que soit le sens du lien) passent à
    `needsRevalidation: true`. Leur statut reste `approved`, `links.yaml` n'est pas modifié et
    l'icône ⚠ apparaît à côté de leur statut. Modifier un paramètre utilisé uniquement par des
    éléments non approuvés, ou modifier seulement sa description, ne marque aucun élément.
17. La fiche de définition d'un test qui contient `{puissance_turbo}` affiche « 450 W » avec le
    style dédié. Le survol affiche le nom, et le double-clic édite le paramètre, comme pour une
    exigence.
18. Les exports des exigences et des définitions de tests (docx, xlsx, pdf) affichent les
    mêmes valeurs qu'à l'écran. Les exports de campagne affichent les valeurs
    figées, y compris les paramètres T97 saisis à la main.
19. `parameters/parameters.yaml` est réécrit avec ses clés triées par nom.
20. Les tests, campagnes et paramètres T97 existants, dans un repo sans base de paramètres, se
    comportent exactement comme avant T171 à l'écran.

## Hors scope

- **Valeurs structurées** (listes, dictionnaires, tables) et **itération** sur les lignes d'une
  table (une instance par ligne). C'est un ticket suivant, pour lequel la syntaxe et le stockage
  en chaînes de T171 sont prévus.
- **Surcharge** par le produit d'une valeur définie dans un composant : les variantes passent
  par les branches.
- **Renommage** d'un paramètre avec mise à jour des références.
- Retour automatique en `draft` d'un élément dont un paramètre est modifié : c'est remplacé par
  `needsRevalidation` (§9).
- Le **marquage** `needsRevalidation` lui-même : livré par T172, T171 ne fait que l'appeler.
  La **levée** du flag relève de l'analyse d'impact (T173).
- Intégration des modifications de paramètres à l'analyse d'impact entre baselines.
- Résolution des paramètres dans la **consultation d'une baseline** hors campagne.
- Outils MCP et import en masse (`bulk-import`) pour les paramètres.
- Contenu du test (`testSnapshot`) lu à la baseline : la règle T49 est inchangée.
- Validation du champ `baselineRef` à la création d'une campagne (liste fermée des tags) : un
  tag introuvable est seulement notifié à l'ajout des tests (§7).
- **Campagnes inter-repos** (tests d'un repo composant dans une campagne du repo produit) : non
  supportées aujourd'hui, non ajoutées par T171.
- Résolution *a posteriori* des références restées non résolues dans une instance, par exemple
  une fois le tag créé : on retire l'instance, puis on ajoute le test à nouveau.

## Décisions validées

- **Affichage** : style dédié, valeur affichée, nom au survol, double-clic pour éditer le
  paramètre. C'est identique pour les exigences et les tests (§4).
- **Suppression** : refusée tant que le paramètre est utilisé, avec la liste des éléments
  utilisateurs, chacun cliquable pour l'ouvrir (§9).
- **Modification** d'un paramètre utilisé par un élément `approved` : cet élément **et** les
  éléments qui lui sont liés sont marqués `needsRevalidation`, quel que soit le sens du lien, via
  le point d'entrée de T172 (§9). Réaligné sur T172 après sa livraison : le flag est porté par
  les éléments, pas par les liens. Déclencheurs : `value`, `unit`, création résolvant des
  références ; pas la `description`, ni les changements arrivés par git.
- **Exports** : ils affichent les mêmes valeurs qu'à l'écran, pour les exigences comme pour les
  tests. Les exports de campagne utilisent les valeurs figées (§10).
- **Campagne avec `baselineRef`** : la résolution se fait toujours à la baseline, sans repli sur
  l'état courant. Si le tag est introuvable, le test est quand même ajouté, la référence n'est
  pas remplacée, et l'utilisateur est notifié (§7).
- **Stockage** : un fichier unique `parameters/parameters.yaml` par repo (§1).
- **Éléments terminaux** : ne bloquent pas la suppression d'un paramètre, restent listés grisés
  dans « Utilisé par » (§8, §9).
- **Création** d'un paramètre résolvant des références d'éléments approuvés : déclenche le
  marquage comme une modification de valeur (§9).
