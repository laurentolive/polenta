# T173 — Analyse d'impact : lever le flag `needsRevalidation` des éléments

**Statut** : spec en validation
**Dépend de** : T172 (marquage `needsRevalidation`), T175 (analyse des modifications locales)
**Issue** : laurentolive/polenta#5

## 1. Contexte

T172 pose `needsRevalidation: true` sur les éléments (exigences, tests) liés à un élément qui
quitte l'approbation ; T171 le pose aussi sur les éléments utilisant un paramètre modifié (et
leurs pairs). Une icône ⚠ « Impact à vérifier » s'affiche à côté du statut. **Rien ne lève ce
flag** : il pèse indéfiniment sur la maturité (critère 5), le statut de couverture
(`needs_revalidation`), la matrice et la compliance d'interface.

T173 permet à l'utilisateur, depuis la vue **Analyse d'impact**, de constater qu'il a traité
l'impact sur un élément marqué et de **lever le flag** (clé `needsRevalidation` retirée du YAML).

Décisions validées en phase Spec :
- levée **dans les analyses existantes** (baseline §4.6, modifications locales §4.7), sur les
  nœuds marqués ;
- **liste de repli** « Impact à vérifier » pour les flags qu'aucune analyse n'atteint ;
- action **unitaire et multi-sélection** ;
- **aucune trace** au-delà de git (pas de commentaire, pas de fichier d'acquittement) ;
- **cause** non enregistrée : l'utilisateur la déduit du contexte (arbre d'analyse, ou éléments
  liés affichés dans la liste de repli).

## 2. Description fonctionnelle

### 2.1 Levée du flag — règle commune

Lever le flag d'un élément X :
- supprime la clé `needsRevalidation` du YAML de X (jamais `needsRevalidation: false`, cf.
  T172 CA8) ;
- ne modifie **ni** le statut, **ni** la `version`, **ni** aucun autre champ, **ni**
  `links/links.yaml` ;
- s'applique **quel que soit le statut** de X, y compris `approved` (verrouillé) : comme pour
  le marquage (T172 §2.1), le verrouillage `isApproval` ne s'applique pas à ce champ ;
- écrit dans le repo propriétaire de X (composant compris, même résolution que le marquage
  T172) ; refusée pour un élément d'un nœud `readonly` (qui ne peut d'ailleurs pas être marqué) ;
- est idempotente : lever le flag d'un élément non marqué ne fait rien et n'est pas une erreur ;
- n'est **pas commitée** : l'écriture va dans le working tree comme toute édition, et part avec
  « Publier ». Qui/quand = auteur/date du commit (`git log`), comme pour les autres champs.

Pas de dialogue de confirmation pour une levée unitaire (action réversible : il suffit de
rouvrir l'élément déclencheur pour re-marquer). Une levée multiple affiche une confirmation
« Lever le flag de N éléments ? ».

Après levée : invalidation des caches renderer concernés (listes d'exigences/tests, matrice,
maturité, liste de repli, analyse active) — l'icône ⚠ disparaît partout.

### 2.2 Dans les analyses (chemin principal)

S'applique aux analyses **baseline** (§4.6) et **modifications locales** (§4.7).

- Chaque nœud d'arbre (montant ou descendant) dont l'élément est **actuellement** marqué
  affiche l'icône ⚠ « Impact à vérifier » et un bouton **« Lever le flag »**.
- L'état du flag est lu **en direct** (index vivant, tous repos du workspace), pas depuis le
  snapshot de l'analyse : une analyse baseline figée reflète donc le flag courant. Un nœud dont
  l'élément n'existe plus dans le workspace n'affiche ni icône ni bouton.
- Un même élément peut apparaître sous plusieurs éléments changés / dans les deux arbres :
  lever le flag sur une occurrence le lève pour toutes.
- **Multi-sélection** : une case à cocher par nœud marqué, et un bouton « Lever le flag de la
  sélection (N) » en tête de l'analyse. La sélection est dédupliquée par élément. Elle est
  vidée au changement d'analyse active.
- Le contexte de l'arbre donne la cause : le nœud est rattaché à l'élément changé qui l'a
  vraisemblablement marqué.
- La levée du flag est **indépendante** du statut d'impact du nœud (enum à 8 valeurs, §4.6) :
  aucun des deux ne modifie l'autre.
- Dans l'analyse **locale**, lever un flag modifie le YAML de l'élément mais ne le fait pas
  apparaître comme « élément changé » (`needsRevalidation` n'est pas un champ comparé, §4.7) ;
  le recalcul live déclenché par `repo:file-changed` ne doit pas perdre la sélection en cours
  des autres nœuds.

### 2.3 Liste de repli « Impact à vérifier »

Certains flags ne sont atteints par aucune analyse : marquage par modification de paramètre
(T171 — `parameters/` n'est ni dans le diff baseline ni dans l'analyse locale), réouverture déjà
publiée sans nouvelle baseline, élément hors des arbres calculés.

- **Entrée** : dans le panneau Analyse d'impact, une entrée « Impact à vérifier (N) » en tête de
  la liste, au-dessus de « Modifications locales ». Affichée seulement si N > 0 (N = nombre
  d'éléments marqués dans le workspace). Même mécanique de sélection que l'entrée locale
  (valeur sentinelle dans `ImpactAnalysisContext.activeAnalysisId`), **sans** sélection
  automatique à l'ouverture de la vue.
- **Contenu** : **tous** les éléments marqués du workspace (repo racine + composants), source
  `getMissingLinks().revalidationItems` enrichie du repo. Par ligne : id, type (exigence/test),
  titre, statut, badge de repo si hors racine, case à cocher, bouton « Lever le flag ».
  Tri : exigences puis tests, par id.
- **Éléments liés** (aide à trouver la cause) : chaque ligne se déplie sur la liste de ses
  éléments liés (tous liens, sens indifférent, un niveau) avec id, titre, statut, `version` et
  type de lien. Les éléments liés dans un statut non-approbation sont mis en évidence (candidats
  « déclencheur » : un élément rouvert en brouillon). Un clic sur un id ouvre l'élément (même
  popup que les nœuds d'analyse).
- **Multi-sélection** : « Tout sélectionner » + « Lever le flag de la sélection (N) ».
- Lecture seule sinon : pas de persistance, pas d'export, pas de statut d'impact.
- Rafraîchissement : mêmes déclencheurs que l'analyse locale (`repo:file-changed` sur
  `requirements/`, `tests/`, `links/`, changement de ref, retour du focus). Quand N tombe à 0
  alors que l'entrée est active, la vue revient à « aucune analyse ».

### 2.4 Point d'entrée

Un service unique (ex. `RevalidationService.clear(repoPath, elementIds[], workspaceDir)`),
symétrique de `markImpactedBy` : même résolution des repos, même verrou par fichier
(`withKeyLock`), best-effort par élément. Il renvoie les éléments levés et ceux en échec (avec
motif : introuvable, readonly, erreur d'écriture). Un échec partiel est signalé à l'utilisateur
(bandeau d'erreur en tête de la vue listant les ids en échec et leur motif, fermable) sans annuler les levées réussies.

## 3. Cas d'usage

1. **Réouverture locale** : SYS-0001 `approved` rouverte en brouillon → TEST-0003 et SW-0010
   marqués. Analyse « Modifications locales » : SYS-0001 changée ; TEST-0003 et SW-0010 dans
   ses arbres avec ⚠. L'utilisateur vérifie TEST-0003, clique « Lever le flag » → clé retirée
   de `tests/TEST-0003.yaml`, TEST-0003 reste `approved` v1, ⚠ disparaît de toutes les vues ;
   SW-0010 garde son flag.
2. **Levée multiple** : 6 pairs marqués ; l'utilisateur coche 4 nœuds, confirme → 4 flags
   levés en une opération, 2 restent.
3. **Analyse baseline** : v1.0 → v1.1 ; un nœud marqué depuis affiche ⚠ bien que l'analyse soit
   figée ; levée possible.
4. **Paramètre modifié (T171)** : SW-0020 et ses pairs marqués ; aucune analyse ne les montre.
   Entrée « Impact à vérifier (3) » → les 3 éléments listés ; dépliage de SW-0020 → ses liens ;
   levée depuis la liste.
5. **Élément d'un composant** : flag levé dans le YAML du composant, pas du produit.
6. **Élément présent deux fois** dans une analyse : levée sur une occurrence → ⚠ disparaît sur
   les deux.
7. **Levée puis nouvelle réouverture** du déclencheur → pair re-marqué (T172 inchangé).

## 4. Critères d'acceptation

- CA1 — Après levée, le YAML de l'élément n'a plus de clé `needsRevalidation` ; statut,
  `version`, autres champs et `links/links.yaml` inchangés (diff limité à cette ligne).
- CA2 — La levée fonctionne sur un élément `approved`, et sur un élément d'un composant du
  workspace (écrit dans le repo du composant).
- CA3 — Dans une analyse baseline ou locale, un nœud dont l'élément est marqué affiche ⚠ et
  « Lever le flag » ; un nœud non marqué n'affiche ni l'un ni l'autre.
- CA4 — La multi-sélection lève le flag de tous les éléments cochés, dédupliqués, après
  confirmation ; un échec partiel est signalé sans annuler les levées réussies.
- CA5 — L'entrée « Impact à vérifier (N) » apparaît ssi au moins un élément du workspace est
  marqué ; N est exact ; elle liste tous les éléments marqués avec leurs éléments liés.
- CA6 — Après levée, l'icône ⚠ disparaît des vues Excel, Word, Édition, et la matrice, la
  maturité (critère 5) et le statut de couverture ne comptent plus l'élément comme à revalider,
  sans rechargement manuel.
- CA7 — Aucun commit, aucun fichier créé (`impact-acks/`, `impact-analyses/` inchangés).
- CA8 — Le statut d'impact d'un nœud d'analyse baseline n'est pas modifié par une levée, et
  inversement.
- CA9 — i18n FR/EN pour tous les nouveaux libellés.
- CA10 — `tsc` sans nouvelle erreur.

## 5. Hors scope

- Commentaire de levée, fichier d'acquittement, identité « levé par » autre que git.
- Enregistrement de la cause du marquage (ids déclencheurs dans le YAML) — T172 inchangé.
- Levée depuis l'icône ⚠ des vues Excel/Word/Édition.
- Pré-vérifications avant création de baseline (SPEC-AUDIT §5.2, dont les `needsRevalidation`
  restants) — ticket séparé si besoin.
- Flux élément-unique §4.1–4.5 (`getImpactReport`, `acknowledgeImpact`, `impact-acks/`) : reste
  non branché ; sa suppression ou son alignement relève d'un autre ticket.
- Outils MCP pour lire/lever le flag.
- Copie `apps/api` des services.

## 6. Points de vigilance pour le design

- Lecture du flag en direct pour les nœuds d'une analyse figée : une requête dédiée (ids marqués
  du workspace) plutôt que de recharger les listes complètes.
- `update` d'une exigence/d'un test merge `...existing` : un autosave concurrent ne doit pas
  réintroduire un flag levé (ou l'inverse) — verrou par fichier comme en T172 §6.
- Documentation à mettre à jour au sprint final : SPEC-TRACEABILITY §3.3 et §4 (nouvelle
  sous-section levée / liste de repli), SPEC-REQ §5.3, SPEC-AUDIT §3, SPEC-INDEX, textes agents
  (`agents-md.template.ts` : où lever le flag).
