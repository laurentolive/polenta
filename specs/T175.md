# T175 — Analyse d'impact par défaut sur les modifications locales non commitées

**Type** : Évolution — **Dépend de** : T174 (entrée « Analyse d'impact » dans la barre d'activité)

## 1. Contexte

Depuis T46 (SPEC-TRACEABILITY §4.6), l'analyse d'impact compare exclusivement **deux baselines**
figées ; le résultat est persisté (`impact-analyses/<id>.yaml`) avec un statut par élément impacté.
Pour mesurer l'impact d'une modification en cours, l'utilisateur doit aujourd'hui commiter puis poser
une baseline — ce qui est lourd pour le cas le plus fréquent : « je viens de modifier des exigences /
tests, qu'est-ce que ça touche ? ».

T175 ajoute une **analyse d'impact « live » des modifications locales** : l'état du working tree
(staged + unstaged + non suivis) comparé au dernier commit (`HEAD`), présentée par défaut quand des
modifications existent.

## 2. Description fonctionnelle

### 2.1 Entrée « Modifications locales » dans le panneau Analyse d'impact

- Le panneau latéral Analyse d'impact (`ImpactPanel` / `VersionImpactSelector`) affiche, **en tête de
  la liste des analyses**, une entrée spéciale « Modifications locales (vs HEAD) » **dès qu'au moins
  un repo du workspace a une modification locale portant sur un élément** (cf. §2.3).
- L'entrée est visuellement distincte des analyses enregistrées (libellé en italique ou icône
  dédiée, pas de date, pas de bouton supprimer) et affiche le nombre d'éléments changés.
- Sans modification locale pertinente, l'entrée n'apparaît pas : comportement actuel inchangé.
- Le sélecteur de baselines (« baseline la plus ancienne / la plus récente », bouton Analyser) et la
  liste des analyses enregistrées restent affichés et utilisables en toutes circonstances.

### 2.2 Sélection par défaut

- À l'ouverture de la vue Analyse d'impact **sans analyse active** (`activeAnalysisId === null`), si
  l'entrée « Modifications locales » existe, elle est **sélectionnée automatiquement** et la vue
  principale affiche son résultat.
- Si l'utilisateur a explicitement sélectionné une analyse enregistrée, elle reste active : la
  sélection automatique ne s'applique qu'à l'état « rien de sélectionné ».
- L'utilisateur peut revenir à tout moment à l'analyse locale en cliquant l'entrée, ou passer à une
  analyse enregistrée / en créer une entre baselines.
- Si l'analyse locale est active et que les modifications locales disparaissent (commit, publication,
  abandon des modifications), l'entrée disparaît et la vue revient à l'état « aucune analyse
  sélectionnée » (message d'invite actuel).

### 2.3 Périmètre des modifications prises en compte

**Repos** : le repo produit **et** tous ses composants (submodules) du workspace — même liste de repos
que celle utilisée ailleurs pour le workspace (`resolveWorkspaceRepoPaths`). Chaque repo est comparé à
**son propre** `HEAD`.

**Fichiers** : l'état du working tree (fichiers staged, unstaged et non suivis confondus) comparé à
`HEAD`, pour :

| Fichier | Rôle dans l'analyse |
|---------|---------------------|
| `requirements/**/*.yaml` | **Élément changé** (racine d'un arbre d'impact) : ajoutée / supprimée / modifiée |
| `tests/**/*.yaml` | **Élément changé** (racine d'un arbre d'impact) : ajouté / supprimé / modifié |
| `links/links.yaml` | Pas un élément changé : un lien ajouté/supprimé modifie seulement la construction des arbres |
| autres (`.polenta/`, `parameters/`, `impact-analyses/`, `diagrams/`…) | Ignorés : ne font pas apparaître l'entrée |

Un fichier élément dont le contenu YAML est identique champ à champ à `HEAD` (ex. reformatage) ne
compte pas comme modifié (même règle que `diffRequirementFields` en T46).

### 2.4 Contenu de l'analyse

Même présentation que les analyses entre baselines (vue principale `/impact-analysis`), avec :

- **En-tête** : « Modifications locales (vs HEAD) » à la place de « baseline A → baseline B ».
- **Éléments changés** : exigences **et tests**, triés par repo puis par id, chacun avec son type de
  changement (ajouté / supprimé / modifié) et, pour « modifié », la liste des champs changés
  (`status`, `title`, `fields.*` ; pour un test, `steps` compte comme un seul champ).
- **Arbres d'impact montant / descendant** : calculés comme en §4.6 (graphe complet, deux
  directions, anti-cycle par élément changé, tests couvrants rattachés à chaque nœud exigence) sur un
  **snapshot du working tree** (état courant, non commité) — et non sur `HEAD`. Pour un **test**
  changé : arbre montant = exigences qu'il couvre (puis leurs ascendants) ; arbre descendant vide.
- **Multi-repo** : le snapshot agrège les exigences, tests et liens de tous les repos du workspace,
  de sorte qu'un changement dans un composant fasse apparaître les éléments impactés du produit (et
  inversement) via les liens cross-composant. Chaque élément (changé ou impacté) indique le repo
  (nœud) auquel il appartient quand il n'est pas dans le repo racine.
- Un élément **supprimé** n'a pas d'arbre (comme en T46).

### 2.5 Nature « live » — non persistée

- L'analyse locale **n'est jamais écrite sur disque** (aucun fichier `impact-analyses/*.yaml`) : elle
  ne crée donc elle-même aucune modification locale.
- **Pas de statut par élément** : les sélecteurs de statut, commentaires, indicateur de complétude et
  bouton « Générer une campagne » sont masqués pour cette analyse. Les éléments restent cliquables
  (ouverture du popup lecture seule existant).
- **Recalcul** : l'analyse est recalculée à la sélection de l'entrée et à chaque changement des
  modifications locales (même signal que celui qui rafraîchit l'état staged/unstaged du panneau
  Version) ; un bouton « Rafraîchir » permet de forcer le recalcul.
- Pour conserver un instantané suivi (statuts, campagne), le chemin reste inchangé : commiter, poser
  une baseline et créer une analyse entre baselines (§4.6).

## 3. Cas d'usage et comportements attendus

| # | Situation | Comportement attendu |
|---|-----------|---------------------|
| U1 | Repo propre, ouverture de la vue | Pas d'entrée « Modifications locales » ; comportement actuel |
| U2 | `SYS-0003` modifiée (non commitée), ouverture de la vue sans analyse active | Entrée présente, sélectionnée automatiquement ; `SYS-0003` listée « modifiée » avec ses champs changés et ses arbres |
| U3 | Nouvelle exigence créée (fichier non suivi) | Listée « ajoutée », arbres construits depuis les liens du working tree |
| U4 | Exigence supprimée localement | Listée « supprimée », sans arbre |
| U5 | Test `TEST-0007` modifié | Listé « modifié » ; arbre montant = exigences qu'il couvre |
| U6 | Seul `links/links.yaml` modifié | Pas d'entrée (aucun élément changé) |
| U7 | Seul un fichier hors éléments modifié (`parameters/`, `.polenta/`…) | Pas d'entrée |
| U8 | Exigence modifiée dans le composant `motor-control` | Entrée présente ; l'exigence est listée avec son repo ; les éléments du produit liés apparaissent dans les arbres |
| U9 | Analyse enregistrée sélectionnée, puis une modification locale apparaît | L'analyse enregistrée reste affichée ; l'entrée locale apparaît en tête, non sélectionnée |
| U10 | Analyse locale active, l'utilisateur modifie un autre élément | L'analyse se met à jour et inclut le nouvel élément |
| U11 | Analyse locale active, l'utilisateur publie / commite tout | L'entrée disparaît ; la vue revient à « aucune analyse sélectionnée » |
| U12 | Création d'une analyse entre baselines alors que le repo est modifié | Fonctionne comme aujourd'hui (et le fichier `impact-analyses/*.yaml` écrit n'ajoute pas d'élément changé) |

## 4. Critères d'acceptation

1. CA1 — Avec au moins une exigence ou un test modifié/ajouté/supprimé localement dans un repo quelconque du workspace, l'entrée « Modifications locales (vs HEAD) » apparaît en tête de la liste dans le panneau Analyse d'impact.
2. CA2 — Ouvrir la vue sans analyse active sélectionne cette entrée automatiquement ; une analyse enregistrée choisie par l'utilisateur n'est jamais remplacée automatiquement.
3. CA3 — Les éléments changés listés correspondent exactement aux fichiers `requirements/**/*.yaml` et `tests/**/*.yaml` qui diffèrent de `HEAD` (staged, unstaged ou non suivis), tous repos confondus, sans les fichiers identiques champ à champ.
4. CA4 — Les arbres d'impact reflètent les liens du working tree (un lien ajouté localement apparaît dans les arbres, un lien supprimé localement n'y apparaît plus).
5. CA5 — Un changement dans un composant fait apparaître les éléments impactés du produit via les liens cross-composant.
6. CA6 — Aucun fichier n'est écrit pour l'analyse locale ; les contrôles de statut / commentaire / complétude / campagne n'y sont pas affichés.
7. CA7 — L'analyse se met à jour après une modification, un commit ou un abandon de modification, sans avoir à rouvrir la vue ; l'entrée disparaît quand il ne reste plus d'élément changé.
8. CA8 — Les analyses entre baselines (création, consultation, statuts, suppression, campagne) fonctionnent comme avant T175.
9. CA9 — Libellés FR/EN ajoutés dans les deux fichiers i18n.

## 5. Hors scope

- Persister, nommer ou attribuer des statuts à l'analyse locale (passer par une baseline).
- Comparer le working tree à autre chose que `HEAD` (branche, baseline, commit arbitraire).
- Considérer un lien ajouté/supprimé comme un élément changé à part entière.
- Changer l'analyse élément unique (`getImpactReport`, SPEC-TRACEABILITY §4.1–4.5) ou le flag
  `needsRevalidation` (T172/T173).
- Détecter les modifications de fichiers `.drawio` ou de paramètres (T171) comme source d'impact.
- Changer l'analyse entre baselines pour y inclure les tests (T46 reste « exigences seulement »).

## 6. Points ouverts pour le Design

- Réutiliser `diffRequirementsBetweenRefs` / `buildImpactTreesFromSnapshot` en les généralisant
  (ref vs working tree, exigences + tests, snapshot multi-repo) plutôt que de dupliquer.
- Clés des nœuds multi-repo : un même id ne peut pas exister dans deux repos (préfixes uniques,
  CLAUDE.md règle 10), ce qui permet de garder des ids simples dans le snapshot agrégé.
- Signal de rafraîchissement : réutiliser l'invalidation de requête existante du statut git plutôt
  qu'un watcher dédié.
