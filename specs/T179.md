# T179 — Références aux champs de l'exigence liée dans les tests (`{req.<champ>}`), une instance par exigence

## Contexte

T171 a introduit la base de paramètres (`{nom}` / `{<nœud>::nom}`), indépendante des liens. Au
cadrage de T171, une première piste `{req.<champ>}` (valeur lue dans l'exigence vérifiée) avait
été écartée pour n'avoir qu'une seule mécanique.

Le besoin revient : un test générique vérifie souvent **plusieurs exigences de même forme**
(ex. une exigence d'autonomie par mode : Eco, Normal, Turbo), chacune portant sa propre valeur
cible dans un champ (ex. `target`). Créer un paramètre de base par exigence duplique
l'information déjà présente dans l'exigence. On veut écrire une fois le test :

> Mesurer l'autonomie en mode {req.mode}. Résultat attendu : ≥ {req.target}

et obtenir, en campagne, **une instance du test par exigence liée**, chacune avec les valeurs de
son exigence.

T179 **complète** T171 sans le remplacer : `{nom}` reste la base de paramètres, `{req.<champ>}` est
une seconde famille de références, résolue via les liens de couverture.

## Principes

1. **Le lien porte l'itération.** Un test qui référence `{req.…}` est instancié une fois par
   exigence liée (lien de couverture), à l'ajout en campagne.
2. **Même cycle de vie que T171** : résolu à l'ajout, figé dans l'instance, lu à la baseline de
   la campagne si elle existe.
3. **Un test sans `{req.…}` ne change pas**, même s'il est lié à plusieurs exigences : une seule
   instance, comme aujourd'hui.
4. **La couverture suit l'instance** : le résultat d'une instance générée pour une exigence ne
   compte que pour cette exigence.

## Description fonctionnelle

### 1. Syntaxe

| Forme | Désigne |
|---|---|
| `{req.<champ>}` | Le champ `<champ>` de l'exigence pour laquelle l'instance a été générée. |

- `<champ>` suit la grammaire des noms de paramètres (`[A-Za-z0-9_-]+`, `\_` toléré comme en
  T171).
- `<champ>` désigne **n'importe quel champ de l'exigence** :
  - tout champ personnalisé de `fields`, quel que soit son type (ex. `{req.target}`,
    `{req.statement}`) ;
  - tout champ système : `id`, `title`, `status`, `version`, `objectTypeRef`, `projectId`,
    `branchId`, `jiraLinks`, `needsRevalidation` ;
  - les champs dérivés de `git log` : `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.
- Un champ personnalisé qui porte le nom d'un champ système ou dérivé est masqué par celui-ci.
- Le préfixe `req.` est réservé ; la forme `{<nœud>::req.x}` n'existe pas. Le point ne fait pas
  partie de la grammaire des noms T171 : aucune référence existante ne change de sens.

### 2. Où la référence est reconnue

- **Tests uniquement**, dans les mêmes champs que T171 §3 : `preconditions`, `action` et
  `expectedResult` de chaque étape, `postconditions`. Hors code Markdown (même règle que T171).
- Dans une exigence, `{req.…}` reste littéral (pas d'exigence « liée » à une exigence).

### 3. Exigences liées

Les exigences liées à un test sont celles reliées par un **lien de couverture**, au sens du
moteur de traçabilité (`matchCoverageLink`) : tout lien entre le test et une exigence, **dans les
deux sens**, quel que soit son type. Sont exclues :

- les exigences en statut terminal (`isTerminal`, ex. `obsolete`) ;
- les liens orphelins (exigence introuvable).

Ordre : par ID d'exigence (tri naturel), pour un ordre d'instances stable.

### 4. Ajout en campagne : génération des instances

Sur tous les chemins d'ajout (`create`, y compris depuis l'analyse d'impact, `addTests`), pour
chaque test sélectionné :

| Cas | Résultat |
|---|---|
| Le test ne contient aucune `{req.…}` | Inchangé : une instance (règles T97/T171). |
| Le test contient au moins une `{req.…}` et est lié à N ≥ 1 exigences | **Une instance par exigence sélectionnée** (§5), chacune portant l'ID de son exigence (`requirementId`) et ses valeurs figées. |
| Le test contient au moins une `{req.…}` et n'est lié à aucune exigence | **Une instance**, sans `requirementId`. Les `{req.…}` restent littérales, style « non résolue », raison `no_linked_requirement`, avec notification (T171 §7). |

Au sein d'une instance générée pour une exigence, les références `{nom}` / `{<nœud>::nom}` de la
base (T171) sont résolues comme aujourd'hui ; les références à saisir à la main (T97) sont
demandées **par instance**.

**Déduplication.** `addTests` ne déduplique plus seulement par test mais par couple
(test, exigence) : un test déjà présent dans la campagne reste proposable à l'ajout tant qu'une
de ses exigences liées n'a pas d'instance (ex. lien créé depuis). Seules les instances manquantes
sont ajoutées.

**« Dupliquer »** (T97 sprint 2), sur une instance générée : crée une nouvelle instance **pour la
même exigence**, avec de nouvelles valeurs saisies. Proposé seulement si l'instance a des
références à saisir, comme aujourd'hui. Les références `{req.…}` résolues ne comptent pas comme
« à saisir ».

### 5. Panneau d'ajout et formulaire de création de campagne

Pour chaque test sélectionné qui contient des `{req.…}` :

- la liste des exigences liées est affichée (ID + titre), **toutes cochées par défaut** ;
  l'utilisateur peut en décocher ;
- pour chaque exigence cochée, les valeurs `{req.…}` résolues sont affichées en lecture seule ;
- les références non résolues sont signalées avant validation, avec leur raison (§6) ;
- décocher toutes les exigences équivaut à ne pas sélectionner le test.

La prévisualisation passe par le canal IPC existant (`campaigns:preview-params`), étendu.
`CreateCampaignDto` et `addTests` reçoivent, par test, la liste des exigences retenues
(optionnelle : absente → toutes les exigences liées).

### 6. Résolution d'une valeur

- **Source** : la même que T171 §7. Campagne avec `baselineRef` → le lien, l'exigence et ses
  champs sont lus **au tag**, sans repli sur l'état courant ; sans `baselineRef` → état courant.
- **Texte substitué** : la valeur stockée du champ, en texte brut :
  - `text`, `textarea`, `richtext` : le texte (Markdown pour `richtext`, inséré tel quel et
    rendu par le viewer, comme T171 §5) ;
  - `number` : sa représentation texte ;
  - `enum` : la valeur stockée ;
  - `multi_enum` : la chaîne CSV stockée ;
  - `status` : le nom du statut stocké ; `version` : le nombre ; `needsRevalidation` : `true`
    ou `false` (absent = `false`) ;
  - liste (ex. `jiraLinks`, `diagrams`, `tags`) : éléments joints par `, ` ;
  - dates dérivées (`createdAt`, `updatedAt`) : format ISO, lues sur l'historique git du fichier
    à la même source (tag ou état courant) ;
  - tout autre objet structuré : sérialisé en YAML sur une ligne.
- **Paramètres imbriqués** : si la valeur du champ contient des références `{nom}` /
  `{<nœud>::nom}`, elles sont résolues dans la base du **repo de l'exigence**, à la même source ;
  non résolues, elles restent littérales.
- **Non résolue** (la référence reste littérale, style « non résolue », enregistrée dans
  `unresolvedParams`, notifiée comme T171 §7) :
  - `no_linked_requirement` : aucune exigence liée (§4) ;
  - `missing` : le champ n'existe pas dans l'exigence ;
  - `empty` : le champ est vide ;
  - `tag_not_found` : tag introuvable dans le repo de l'exigence.
  Une `{req.…}` non résolue n'est **jamais** proposée à la saisie à la main.

### 7. Affichage

| Contexte | Rendu de `{req.<champ>}` |
|---|---|
| Fiche de définition du test, vue Word/Excel des tests, recherche | Référence littérale `{req.<champ>}` avec un style dédié « référence d'exigence » (variante du style T171). Au survol : la liste des exigences liées avec la valeur courante du champ pour chacune. Pas d'action au double-clic. |
| Éditeur (`RichTextField`) | Même style ; saisie à la main possible partout. L'insertion depuis le sélecteur de paramètres T171 propose une section « Champ de l'exigence liée » listant les champs système et dérivés, puis les champs personnalisés des types d'exigence du schéma. |
| Campagne : liste des tests | Chaque instance générée affiche l'ID de son exigence à côté du titre du test (ex. `TEST-0012 — Autonomie · SYS-0041`), avec un lien qui ouvre l'exigence. |
| Campagne : exécution et relecture | Valeur figée, style T171. L'en-tête rappelle l'exigence de l'instance (ID + titre). Au survol : `req.<champ>` et l'ID de l'exigence. |

### 8. Couverture et traçabilité

- Une instance générée porte `requirementId`. Le `TestRun` produit par son exécution est rattaché
  à cette instance (`campaignRunId`) ; le moteur de traçabilité en déduit l'exigence.
- Dans `computeCoverage`, pour une paire (test, exigence), le « dernier run » retenu est le plus
  récent parmi : les runs d'instances générées **pour cette exigence**, et les runs sans exigence
  (tests sans `{req.…}`, runs antérieurs à T179). Les runs d'instances générées pour **une autre**
  exigence sont ignorés pour cette paire.
- Conséquence : un FAIL sur l'instance « Turbo » ne dégrade que la couverture de l'exigence Turbo.

### 9. Exports

- Définitions de tests (docx, xlsx, pdf) : `{req.…}` reste littérale (plusieurs exigences
  possibles), comme à l'écran.
- Campagne (plan, rapport) : une ligne par instance, avec l'ID de l'exigence de l'instance ; les
  valeurs figées sont substituées (`resolvedParams`).

### 10. Modèle de données

**`CampaignTestRun`** reçoit un champ optionnel :

| Champ | Type | Description |
|---|---|---|
| `requirementId` | `string` | Exigence pour laquelle l'instance a été générée. Absent pour un test sans `{req.…}` ou sans exigence liée. |

Les valeurs `{req.…}` résolues sont figées dans `resolvedParams` (T171), avec la clé
`req.<champ>` ; les non résolues dans `unresolvedParams`. `UnresolvedParamReason` gagne la valeur
`no_linked_requirement`.

`entryId` reste `${testCaseId}-${n}` (n = rang parmi les instances du test dans la campagne).

**Exemple (`campaigns/CAMP-0004.yaml`) :**

```yaml
runs:
  - entryId: TEST-0012-1
    testCaseId: TEST-0012
    requirementId: SYS-0041
    status: pending
    resolvedParams:
      req.mode: Eco
      req.target: 45 min
  - entryId: TEST-0012-2
    testCaseId: TEST-0012
    requirementId: SYS-0042
    status: pending
    resolvedParams:
      req.mode: Turbo
      req.target: 12 min
```

**Compatibilité ascendante** : champ optionnel, campagnes existantes lues sans migration ;
aucune référence T97/T171 existante ne contient de point, donc aucune ne change de sens.

## Critères d'acceptation

1. Soit `TEST-0012` dont une étape contient `≥ {req.target}`, lié à `SYS-0041`
   (`target: 45 min`) et `SYS-0042` (`target: 12 min`). Ajouté à une campagne sans baseline, il
   produit deux instances, `requirementId` `SYS-0041` et `SYS-0042`, qui affichent à l'exécution
   « ≥ 45 min » et « ≥ 12 min ».
2. Le sens du lien (test → exigence ou exigence → test) et son type n'ont pas d'influence.
3. Une exigence liée en statut `obsolete` ne produit pas d'instance.
4. Dans le panneau d'ajout, décocher `SYS-0042` ne produit que l'instance `SYS-0041`. Rouvrir le
   panneau propose encore `TEST-0012`, pour `SYS-0042` seulement.
5. Un test sans `{req.…}` lié à trois exigences produit une seule instance, sans `requirementId`.
6. Un test avec `{req.target}` sans exigence liée produit une instance ; la référence reste
   littérale, style « non résolue », `unresolvedParams` contient
   `{ ref: req.target, reason: no_linked_requirement }`, et c'est signalé avant et après l'ajout.
7. `{req.inconnu}` → non résolue `missing` ; champ vide → `empty` ; jamais proposée à la saisie.
8. `{req.id}`, `{req.title}`, `{req.status}`, `{req.version}` et `{req.updatedBy}` affichent les
   valeurs correspondantes de l'exigence de l'instance ; `{req.statement}` affiche son énoncé
   rendu ; tout champ personnalisé du type est accessible.
9. Une exigence dont `target` vaut `{duree_turbo}` (paramètre de base à `12 min`) affiche
   « ≥ 12 min » dans l'instance.
10. Campagne avec `baselineRef` : la valeur de `target` affichée est celle au tag, même si
    l'exigence a changé depuis ; un lien créé après le tag ne produit pas d'instance.
11. Modifier `SYS-0041.target` après l'ajout ne change pas l'instance existante.
12. Un FAIL sur l'instance `SYS-0042` et un PASS sur `SYS-0041` : la matrice de traçabilité
    montre `fail` pour `SYS-0042` et `pass` pour `SYS-0041` sur la colonne `TEST-0012`.
13. Un test mélangeant `{req.target}`, `{puissance_turbo}` (base) et `{numero_serie}` (à saisir)
    produit une instance par exigence ; `numero_serie` est demandé pour chaque instance.
14. La fiche de définition du test affiche `{req.target}` avec le style dédié, et le survol liste
    `SYS-0041 : 45 min`, `SYS-0042 : 12 min`.
15. Les exports de campagne listent une ligne par instance avec l'ID de l'exigence et les
    valeurs figées.
16. Les campagnes, tests et paramètres existants se comportent exactement comme avant T179.

## Hors scope

- `{req.…}` dans les exigences ; désignation explicite d'une exigence (`{SYS-0041.target}`).
- Filtre des exigences liées par type d'exigence ou par type de lien.
- Affichage du label d'une valeur `enum` (la valeur stockée est utilisée).
- Resynchronisation automatique des instances d'une campagne existante quand un lien est
  ajouté ou retiré (on rouvre le panneau d'ajout, cf. déduplication §4 ; une instance dont le
  lien a été supprimé reste dans la campagne).
- Itération sur autre chose que les exigences liées (tables de valeurs : ticket suivant de T171).
- Outils MCP / import en masse.

## Décisions validées

- **Liens retenus** : liens de couverture, dans les deux sens, tout type (`matchCoverageLink`),
  exigences terminales exclues.
- **Test sans exigence liée** : une instance, références non résolues et notifiées.
- **Couverture** : le résultat d'une instance ne compte que pour son exigence.
- **Sélection à l'ajout** : exigences liées toutes cochées par défaut, décochables.
- **Champs accessibles** : tous les champs de l'exigence — personnalisés, système et dérivés
  (§1).

## Propositions à valider (défauts retenus par l'Agent Spec)

- Un champ personnalisé homonyme d'un champ système/dérivé est masqué par celui-ci.
- Source de résolution alignée sur T171 (baseline si `baselineRef`, liens compris).
- Paramètres de base imbriqués dans la valeur d'un champ d'exigence : résolus dans le repo de
  l'exigence.
- Définition du test : référence littérale stylée, valeurs au survol ; définitions exportées
  littérales.
- Déduplication par couple (test, exigence) ; « Dupliquer » reste attaché à la même exigence.
