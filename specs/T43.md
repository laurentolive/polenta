## Contexte

### Ce qui existe déjà

- **`ViewHeader`** (`apps/desktop/src/renderer/components/layout/ViewHeader.tsx`) : composant partagé
  (T92) avec un slot `actions` (JSX libre, rendu juste avant le bouton "Publier"/`ModificationControl`)
  déjà utilisé par `dashboard.tsx:165`, `impact-analysis.tsx:447`, `campaign.$campaignId.tsx:184`,
  `req.$reqId.tsx:129`, `test.$testId.tsx:152`. `requirements.tsx`, `tests.tsx` et `query.tsx` n'utilisent
  pas encore ce slot. Ajouter l'icône export = ajouter un élément JSX dans `actions` de chaque vue
  concernée, pas de nouvelle prop sur `ViewHeader`.
- **Pattern IPC "save as" déjà en place et réutilisable** : `queries:export-excel`
  (`apps/desktop/src/main/ipc/index.ts:563-572`) ouvre `dialog.showSaveDialog({defaultPath, filters})`
  côté main process, puis délègue l'écriture au service
  (`query-engine.service.ts:335-341`, `exportExcel` via `ExcelJS`), renvoie `{status:'ok'|'canceled',
  filePath}`. Câblage renderer en `useMutation` dans `query.tsx:217-219`, bouton `query.tsx:~280`. C'est le
  modèle à généraliser pour T43, plutôt que le pattern `traceability:export-csv`
  (`ipc/index.ts:273-274`) qui renvoie les données brutes au renderer sans écrire sur disque.
- **`api-client`** (`packages/api-client/src/ipc-client.ts:197-211`) : objet explicite écrit à la main
  (pas de proxy dynamique) — tout nouveau canal d'export doit y être ajouté explicitement, ainsi que dans
  les types associés.
- **`preload/index.ts`** : n'expose que `invoke/on/off` bruts (contextBridge) — aucun impact à prévoir
  côté preload, tout passe par `window.polenta.invoke`.
- **Filtres déjà en mémoire pour exigences/tests** : `requirements.tsx` et `tests.tsx` lisent `filter`
  (texte) et `type` (objectTypeRef) depuis `Route.useSearch()`, appliqués en local (`filtered`,
  `requirements.tsx:56`, `tests.tsx:58`) — c'est la variable "vue active" à réutiliser pour l'export, pas
  la collection complète du composant.
- **`ExcelView`** (`components/system/ExcelView.tsx`) : a un filtre texte global (`filter` prop, ligne 40,
  appliqué lignes 963-975) mais **pas** de filtre par colonne — T51 (filtre par colonne) n'est pas
  implémenté à ce jour. `ExcelView` n'est pas utilisé par `requirements.tsx`/`tests.tsx` (vues liste
  simples), seulement par `product.tsx`/`components.tsx`.
- **`campaign.$campaignId.tsx`** : la liste des tests d'une campagne vient directement de
  `campaign.testCaseIds` (ligne 137, 282), jointe à `tests` via `testMap` (ligne 134) et au statut de run
  (`getRunStatus`, ligne 146). Pas de filtre actif sur cette liste — "vue active" == liste complète des
  tests de la campagne.
- **`query.tsx`** : résultat de requête en state (`result`, ligne 80), déjà exporté en Excel (voir
  ci-dessus). Réutilisable tel quel comme source pour le nouvel export xlsx/pdf unifié.
- **`impact-analysis.tsx`** (T46) : `activeAnalysis` expose directement `fromBaseline.tag`/
  `toBaseline.tag` (ligne 443) — utile pour le nom de fichier `impactAnalisys-{baselineold}-{baselinenew}`.
  Le spec de T46 note d'ailleurs explicitement que l'export de ce rapport est renvoyé à T43.
- **`dashboard.tsx`** : pas de conteneur DOM racine identifiable aujourd'hui pour capturer le rendu — le
  rendu des widgets est délégué à `DashboardGrid.tsx`, à instrumenter (ex. `ref`/`id` sur le conteneur
  racine) pour permettre un export.

### Ce qui manque

- **Aucune génération Word (.docx) ni PDF n'existe** — seul `ExcelJS` est présent dans
  `apps/desktop/package.json`. Il faut ajouter une dépendance dédiée pour le docx (ex. `docx` npm — à
  confirmer en Design) et s'appuyer sur `webContents.printToPDF` natif d'Electron pour le PDF (décision
  utilisateur : pas de nouvelle dépendance PDF lourde de type `puppeteer`/`pdf-lib`).
- **Aucun canal IPC générique d'export** — seul `queries:export-excel` existe, ad hoc pour un seul type de
  contenu. T43 introduit potentiellement plusieurs types de contenu (7) × plusieurs formats — le Design
  doit trancher entre un canal générique paramétré (type de contenu + format + payload) et des canaux
  dédiés par type, en explicitant le compromis.
- **Aucune notion de "baseline ou commit courant" partagée entre les vues** — chaque vue porte sa propre
  logique (baseline explicite pour `impact-analysis.tsx`, rien pour `requirements.tsx`/`tests.tsx` qui
  lisent le working tree live). Pour ces dernières, `{baseline|commit}` du nom de fichier par défaut
  désigne le SHA court du commit HEAD courant du repo (pas de baseline sélectionnée dans ces vues
  aujourd'hui) — mécanisme de récupération à identifier en Design (probablement déjà exposé par
  `SyncService`/`status`).
- **Aucun conteneur DOM capturable sur `dashboard.tsx`** pour un export visuel — à ajouter.

## Description fonctionnelle

### 1. Icône export dans la barre de titre

Chaque vue concernée reçoit une icône "Export" (cohérente visuellement avec l'icône déjà utilisée dans
`query.tsx`, ex. `Download` de `lucide-react`) ajoutée au slot `actions` de son `ViewHeader`. Pour
`query.tsx`, qui a déjà un bouton d'export inline hors `ViewHeader`, ce bouton est migré vers le même
mécanisme unifié que les autres vues (même composant de popup, même canal IPC générique).

Cliquer sur l'icône ouvre une popup listant les formats disponibles pour cette vue (mapping ci-dessous,
sous forme d'icônes "Export Word" / "Export Excel" / "Export PDF" comme décrit dans le ticket). Choisir un
format déclenche immédiatement le dialogue natif "Enregistrer sous" (`dialog.showSaveDialog`, pattern
existant), pré-rempli avec le chemin/nom par défaut (§4). Annuler le dialogue n'écrit aucun fichier.

### 2. Mapping export → vue déclenchante → formats disponibles (décision utilisateur)

| Export | Vue déclenchante | Formats | Contenu |
|---|---|---|---|
| Cahier d'exigences | `requirements.tsx` | xlsx, docx, pdf | Exigences actuellement visibles (`filtered`) |
| Cahier de test | `tests.tsx` | xlsx, docx, pdf | Tests actuellement visibles (`filtered`) |
| Cahier de campagne de test | `campaign.$campaignId.tsx` | xlsx, docx, pdf | Plan de campagne (tests inclus, champs, sans statut d'exécution) |
| Rapport de campagne de test | `campaign.$campaignId.tsx` | docx, pdf | Résultats d'exécution (statut par test : pass/fail/blocked/skipped) |
| Rapport d'analyse d'impact | `impact-analysis.tsx` | xlsx, pdf | Diff + arbres d'impact + statuts de l'analyse ouverte |
| Résultats de requête | `query.tsx` | xlsx, pdf | `result` courant (xlsx = mécanisme déjà existant, pdf = nouveau) |
| Dashboard | `dashboard.tsx` | docx, pdf | Widgets actuellement affichés avec leurs données courantes |

`campaign.$campaignId.tsx` propose donc deux actions d'export distinctes (cahier vs rapport), pas une
seule — le rapport de campagne n'a de sens que si la campagne a au moins un run en cours ou terminé
(sinon aucun statut à rapporter) ; le cahier reste disponible dans tous les cas.

### 3. Périmètre exporté : la vue/filtre actif uniquement (décision utilisateur)

L'export ne porte jamais sur "toute la collection du composant" mais sur ce qui est effectivement
affiché à l'écran au moment du clic :

- `requirements.tsx` / `tests.tsx` : la variable `filtered` (filtre texte + type déjà appliqués)
- `campaign.$campaignId.tsx` : la totalité de `testCaseIds` — il n'existe aujourd'hui aucun filtre actif
  sur cette liste (T51 non implémenté ici), donc "vue active" correspond de facto à la liste complète
- `query.tsx` : le `result` courant
- `impact-analysis.tsx` : l'`activeAnalysis` ouverte, avec les statuts tels qu'affichés
- `dashboard.tsx` : le dashboard actuellement ouvert avec la configuration de widgets courante

Si un filtre par colonne (T51) est implémenté ultérieurement dans `ExcelView`, l'export réutilisera ce
filtre dès lors qu'une vue basée sur `ExcelView` devient concernée — hors scope tant que T51 n'existe
pas.

### 4. Nom de fichier par défaut

Suit le pattern donné par le ticket, appliqué par type :

| Export | Pattern |
|---|---|
| Cahier d'exigences | `{composant}-exigences-{baseline\|commit}.{ext}` |
| Cahier de test | `{composant}-tests-{baseline\|commit}.{ext}` |
| Cahier de campagne | `{composant}-campagne-{nomCampagne}-{baseline\|commit}.{ext}` |
| Rapport de campagne | `{composant}-rapport-campagne-{nomCampagne}-{baseline\|commit}.{ext}` |
| Rapport d'analyse d'impact | `impactAnalisys-{baselineold}-{baselinenew}.{ext}` |
| Résultats de requête | `request-{nomRequete}.{ext}` |
| Dashboard | `dashboard-{nomDashboard}.{ext}` |

`{baseline|commit}` : nom de la baseline (tag) si la vue est dans un contexte baseline (cas de
`impact-analysis.tsx`, déjà couvert par son propre pattern) ; sinon SHA court du commit HEAD courant du
repo affiché. `{composant}` : nom du nœud/repo (`schema.nodes[].name` ou label du repo courant).

*Note : les préfixes `request-`/`impactAnalisys-` reprennent le texte du ticket tel quel (anglicisme et
orthographe non standard inclus) — repris littéralement plutôt que "corrigés", à confirmer/amender à la
validation de cette spec si ce n'était pas intentionnel.*

L'utilisateur peut modifier chemin et nom dans le dialogue natif avant de confirmer — le nom ci-dessus
n'est qu'une valeur par défaut.

### 5. Génération PDF

Chaque export PDF construit une vue HTML imprimable (réutilisation du rendu existant de la vue quand
c'est pertinent — ex. dashboard, cahier riche — ou un template minimal généré côté main/service pour les
contenus tabulaires), puis le main process appelle `webContents.printToPDF` sur cette vue pour produire le
fichier. Pas de nouvelle dépendance PDF.

### 6. Génération Word (.docx)

Nouvelle dépendance à ajouter à `apps/desktop/package.json` (proposition : `docx` npm, à valider en
Design). Un exporteur dédié par type de contenu (cahier d'exigences, cahier de test, cahier de campagne,
rapport de campagne, dashboard) génère la structure docx (titres, tableaux, texte riche) à partir des
mêmes données que la vue affichée — pas de conversion HTML→docx générique.

### 7. Canal(aux) IPC

Généralisation du pattern `queries:export-excel` : le Design tranche entre un canal unique paramétré
(type de contenu + format + payload) et des canaux dédiés par couple (type, format), en gardant le même
contrat `dialog.showSaveDialog` côté main + écriture disque + retour `{status, filePath}`. Le canal
`queries:export-excel` existant est soit absorbé par ce mécanisme, soit conservé et aligné dessus — à
trancher en Design, mais pas de duplication ad hoc supplémentaire par vue.

## Hors scope

- **T51** (filtre par colonne dans `ExcelView`) — non traité ici ; l'export "vue active" pour les cahiers
  exigences/tests s'appuie sur le filtre existant (texte + type), pas un filtre par colonne
- Mise en page "papier" avancée (sommaire, pagination personnalisée, en-têtes/pieds de page avec logo) —
  `printToPDF` applique le rendu HTML tel quel, pas de moteur de mise en page dédié
- Export multi-composant agrégé en un seul document — un export porte toujours sur un seul repo/composant
  à la fois, comme les vues existantes
- Templates personnalisables (charte graphique, logo client) — mise en page fixe pour cette évolution
- Historique/audit des exports réalisés (qui a exporté quoi, quand) — aucune traçabilité de ce type
- Export automatique/programmé — action manuelle uniquement, déclenchée par l'icône
- Export du "cahier de campagne" ou "rapport" pour plusieurs campagnes à la fois — un export = une
  campagne ouverte
- Édition du contenu exporté avant sauvegarde (pas d'aperçu éditable) — le contenu généré reflète
  exactement ce qui est affiché au moment du clic

## Critères d'acceptation

1. Chaque vue du mapping (§2) affiche une icône export dans son `ViewHeader` (ou équivalent migré pour
   `query.tsx`), proposant uniquement les formats listés pour cette vue
2. Cliquer un format ouvre le dialogue natif "Enregistrer sous" pré-rempli avec le nom par défaut du §4 ;
   annuler le dialogue n'écrit aucun fichier et ne montre pas d'erreur
3. L'export xlsx/docx d'un cahier d'exigences ou de test contient exactement les éléments visibles dans
   `filtered` au moment du clic (filtre texte/type appliqué), pas la collection complète du composant si
   un filtre est actif
4. `campaign.$campaignId.tsx` propose deux exports distincts (cahier de campagne xlsx/docx/pdf, rapport de
   campagne docx/pdf) ; le rapport n'est proposé que si la campagne a au moins un run en cours ou terminé
5. L'export d'un rapport de campagne contient le statut d'exécution par test (pass/fail/blocked/skipped)
6. L'export xlsx/pdf d'une analyse d'impact contient le diff des exigences et les arbres d'impact avec les
   statuts tels qu'affichés dans l'analyse ouverte
7. L'export xlsx existant de `query.tsx` continue de fonctionner via le mécanisme unifié, et un export pdf
   est disponible en plus
8. L'export docx/pdf d'un dashboard capture les widgets actuellement affichés avec leurs données courantes
9. La génération PDF n'introduit aucune nouvelle dépendance lourde (`puppeteer`, `pdf-lib`) — utilise
   `webContents.printToPDF`
10. La génération docx utilise une seule dépendance dédiée, ajoutée uniquement à
    `apps/desktop/package.json`
11. Aucun nouveau canal IPC ad hoc dupliqué par vue — le mécanisme d'export (dialogue + écriture disque)
    est partagé entre tous les types de contenu
