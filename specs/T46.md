# T46 — Analyse d'impact entre deux baselines

## Contexte

### Ce qui existe déjà

- **Diff de fichiers brut entre deux refs git** (`sync.service.ts` `diffBetween(repoPath, sha1, sha2)` +
  `diffFileBetween(...)`, exposés dans `version-diff.tsx`) : liste les fichiers `A/M/D` entre deux SHA
  via `git.walk` sur les arbres, et lit le contenu ancien/nouveau d'un fichier via `git.readBlob`. C'est
  un diff **fichier texte**, pas un diff **exigence** — aucun parsing de frontmatter, aucune notion
  d'ID/statut/champ. Réutilisable tel quel comme brique bas niveau pour T46 (filtrer sur
  `requirements/**/*.md`, parser le frontmatter YAML de chaque contenu ancien/nouveau).
- **Sélecteur de ref générique** (`GitRefCombobox` dans `version-diff.tsx`) : branches locales/remote,
  tags, commits récents. **Non réutilisé tel quel pour T46** — décision ci-dessous : les deux bornes de
  l'analyse d'impact sont toujours des baselines, pas n'importe quelle branche/tag/commit.
- **Analyse d'impact élément-unique** (`TraceabilityService.getImpactReport(repoPath, reqId, depth)`,
  §4 de `SPEC-TRACEABILITY.md`) : déclenchée manuellement ou à l'édition d'un élément, calcule les
  `ImpactItem[]` liés en niveau 1 (tests couvrant l'exigence, exigences parent/enfant, liens
  sémantiques DERIVES_FROM/SATISFIES/REFINES) et les campagnes en cours qui utilisent ces tests. C'est
  la logique de traversée de liens que T46 réutilise pour chaque exigence modifiée — mais son
  acquittement (`ImpactAcknowledgement`, §4.5) est un booléen "vérifié/pas vérifié" par élément et par
  version déclenchante, **pas** le cycle de statut à 8 valeurs demandé ici. Ce mécanisme existant reste
  en place tel quel pour le cas d'usage "je viens d'éditer un élément, qu'est-ce qui est à revoir
  maintenant" — T46 ne le remplace pas, il ajoute un flux séparé et persistant pour le cas d'usage
  "comparer deux jalons figés".
- **Génération de plan de test** (`TraceabilityService.generateTestPlan`, §5) : à partir d'une liste
  d'IDs d'exigences, résout les TestCases approuvés qui les couvrent et produit un `TestCampaign`
  brouillon. Réutilisable directement pour le point 5 du ticket (construire une campagne à partir des
  éléments "à tester").
- **Baselines** (`BaselineService`, `.polenta/baselines.yaml`, `SPEC-FORKS-BRANCHES-BASELINES.md` §5) :
  un tag git posé sur un jalon, indexé avec sa date de création via `baseline.list(repoPath)`. §5.6 de
  cette spec décrit déjà un endpoint `GET /projects/:id/baselines/diff?from=v1.0&to=v2.0` — **non
  implémenté à ce jour** (aucune trace dans le code, seule une mention en commentaire dans
  `VersionPanel.tsx`). T46 est l'implémentation réelle de ce chaînon, étendue à l'analyse d'impact — et
  c'est cette liste de baselines, pas le `GitRefCombobox` générique, qui alimente les sélecteurs A/B de
  T46 (décision ci-dessous).
- **Création de baseline verrouillée à la branche d'intégration** (T79, `baseline.tsx`
  `readinessIssue()`) : aujourd'hui, créer une baseline est **bloqué** tant qu'un repo du workspace n'est
  pas exactement sur sa branche d'intégration configurée (`status.branch !== integrationBranch` → repo
  "en défaut", bouton de création désactivé). Ce verrou empêche de poser une baseline sur une branche de
  travail (`dev-*`) — **incompatible avec le besoin ci-dessous**, à assouplir.

### Ce qui manque

- Aucun diff **au niveau exigence** (ajoutée/supprimée/modifiée avec champs changés) n'existe — seul le
  diff fichier texte brut existe.
- Aucune entité persistée ne permet de suivre un statut par élément impacté dans le temps ; le seul
  mécanisme de suivi existant (`ImpactAcknowledgement`) est un acquittement ponctuel booléen, pas un
  cycle de statut à plusieurs valeurs.
- La création de baseline ne permet pas aujourd'hui de baseliner une branche de travail quelconque (cf.
  ci-dessus) — pré-requis pour l'usage "mesurer l'impact d'une modification avant de la livrer".

## Description fonctionnelle

### 1. Choisir deux baselines et voir les exigences modifiées

Nouvelle page (route `/impact-analysis`), accessible depuis le panneau Version. **Les deux bornes de la
comparaison sont toujours des baselines** — pas une branche, pas un commit arbitraire. Deux sélecteurs
alimentés par `baseline.list(repoPath)` (nom du tag + date de création), pas le `GitRefCombobox` générique
de `version-diff.tsx`.

**Décision (retour utilisateur) : si on veut comparer par rapport à l'état courant de l'intégration, il
faut d'abord poser une baseline sur cet état.** Une baseline est le seul objet git garanti immuable,
nommé, et retrouvable dans le temps — comparer contre une branche qui continue d'avancer donnerait une
analyse qui ne veut plus dire la même chose selon le moment où on la relit, ce qui est inacceptable pour
un usage de maîtrise des risques. Concrètement : si aucune baseline n'existe encore sur l'état actuel, le
sélecteur B propose une option "Créer une baseline sur l'état actuel…", qui ouvre le flux de création de
baseline déjà existant (`baseline.tsx`) ; une fois créée, la nouvelle baseline devient sélectionnable
normalement. Aucune comparaison n'est possible sans que les deux bornes soient des baselines effectivement
posées.

**Prérequis — baseliner n'importe quelle branche (retour utilisateur) :** l'usage principal de T46 est de
mesurer l'impact d'une modification **avant de la livrer** — donc de poser une baseline sur une branche de
travail (`dev-*`) en cours, pas seulement sur la branche d'intégration. Le verrou actuel de création de
baseline (§Contexte ci-dessus, T79) est trop strict pour ça et doit être assoupli : la seule condition
bloquante qui reste est **l'absence de modifications en attente** (staged/unstaged) sur chaque repo du
workspace — une baseline doit toujours refléter un état réellement committé, mais elle n'a plus besoin
d'être sur la branche d'intégration. Le repo affiche toujours sa branche courante dans le récapitulatif de
création (utile pour vérifier qu'on baseline la bonne branche), mais ce n'est plus une condition
bloquante, juste une information.

Au choix des deux baselines, calcul de la liste des exigences dont le fichier a changé entre A et B (via
`sync.diffBetween` filtré sur `requirements/**/*.md`, puis parsing frontmatter de chaque
`diffFileBetween` pour classer) :

- **Ajoutées** : fichier absent en A, présent en B
- **Supprimées** : fichier présent en A, absent en B
- **Modifiées** : fichier présent des deux côtés avec un contenu différent — la liste des champs
  changés (statut, champs `fields.*`, `statement`) est calculée par comparaison frontmatter A vs B et
  affichée sur chaque exigence modifiée (repli sur le diff texte brut si le parsing frontmatter échoue
  sur l'un des deux côtés)

Cette liste est affichée dans le panneau latéral, sous forme d'arbre (une entrée par exigence
ajoutée/modifiée/supprimée), conformément à la description d'origine du ticket. Chaque exigence modifiée
peut être dépliée pour révéler ses éléments impactés (point 2).

### 2. Éléments potentiellement impactés par modification

Pour chaque exigence **ajoutée ou modifiée** (une exigence supprimée n'a pas d'éléments "impactés" au
sens traçabilité — elle est listée mais sans sous-arbre), la liste des éléments impactés est calculée en
parcourant **tout le graphe de liens**, sans limite de profondeur — pas le niveau 1 seul utilisé
aujourd'hui par défaut dans `getImpactReport` (§4.4 de `SPEC-TRACEABILITY.md`). Un garde-fou anti-cycle
(ensemble des nœuds déjà visités) est nécessaire, comme c'est déjà le cas dans `getImpactReport`. Le
graphe complet reste borné en pratique par la taille du projet — cohérent avec le budget de perf déjà posé
en §6.2 de `SPEC-TRACEABILITY.md` ("analyse d'impact complet : <50ms sur 500 exigences/300 tests").

Le résultat est présenté comme **deux arbres distincts** partant de l'exigence modifiée :

- **Arbre descendant** : les exigences filles (décomposition), récursivement jusqu'aux feuilles — ce que
  `getImpactReport` calcule déjà en niveau 1, à étendre en profondeur illimitée
- **Arbre montant** : les exigences parentes (celles que l'exigence modifiée dérive/satisfait/affine),
  récursivement jusqu'à la racine — direction **non couverte aujourd'hui** par `getImpactReport`, qui ne
  suit que les liens entrants (`link.targetId === reqId`) et ne remonte donc jamais vers les parents

Contrairement à `getImpactReport` (qui ne récupère les tests couvrants que pour l'exigence déclenchante,
pas pour ses descendants), **chaque nœud des deux arbres** — l'exigence modifiée elle-même, chacune de ses
descendantes, chacune de ses ascendantes — porte la liste des tests qui la couvrent directement, comme
élément impacté rattaché à ce nœud. Un test ou une exigence rejoignable par les deux directions (cycle de
liens croisés) n'apparaît qu'une fois, dans l'arbre où il a été atteint en premier.

L'arbre montant n'est affiché **que s'il n'est pas vide** ("si besoin") — une exigence sans parent ne
montre que son arbre descendant.

**Le graphe de liens traversé est celui figé à la baseline B**, pas l'état courant du projet — cohérent
avec la décision du point 1 (les deux bornes sont des baselines immuables). Une analyse d'impact est donc
entièrement reproductible : la rouvrir dans un mois donne exactement les mêmes exigences changées et les
mêmes arbres, tant que les baselines A et B existent toujours (le seul contenu qui évolue après coup est
le statut posé sur chaque élément impacté, cf. point 4). Si le projet évolue après B (nouveaux liens,
nouveaux tests), ils n'apparaissent pas dans cette analyse — comparer l'évolution ultérieure nécessite de
poser une nouvelle baseline et de créer une nouvelle analyse à partir de B (ou d'une baseline plus
récente).

Chaque élément impacté apparaît sous l'exigence qui l'a déclenché, avec son type (exigence/test), le lien
qui le rattache, et son statut courant (point 3). Un même élément impacté par plusieurs exigences
modifiées apparaît sous chacune d'elles (pas de déduplication dans l'arbre — la déduplication n'a lieu
qu'à la génération de campagne, point 5).

Cliquer sur un élément impacté (ou sur l'exigence modifiée elle-même) l'ouvre dans la zone principale avec
les mêmes vues que partout ailleurs dans l'application (fiche édition, vue Système, Excel, Word) — pas de
vue dédiée à réinventer.

### 3. Statut par élément impacté

Chaque élément impacté a un champ `status`, une liste plate à 8 valeurs, modifiable librement sans
contrainte de transition (pas de machine à états — décision validée avec l'utilisateur) :

| Valeur | Sens |
|--------|------|
| `impact_non_verifie` | Valeur initiale à la création de l'analyse |
| `pas_d_impact_reel` | Analysé, aucune action requise |
| `impact_a_tester` | Le comportement existant doit être re-testé (pas de modification requise) |
| `impact_teste` | Le test de revérification a été exécuté |
| `modification_a_faire` | Une correction/évolution est nécessaire sur l'élément impacté |
| `modification_faite` | La modification a été appliquée |
| `modification_a_tester` | La modification doit être vérifiée par test |
| `modification_verifiee` | La modification a été vérifiée |

Changer le statut d'un élément met à jour `updatedAt`/`updatedBy` sur cet item ; un commentaire libre
optionnel peut être attaché à chaque changement de statut (traçabilité de la décision, ex. pourquoi "pas
d'impact réel").

### 4. Persistance et suivi dans le temps

Une analyse d'impact est un objet persisté en git, calculé **une seule fois à sa création** (diff +
arbres, tous deux figés sur les baselines A/B choisies, cf. point 2) — pas un calcul recalculé à chaque
ouverture de page. Seuls les statuts et commentaires évoluent après coup. Stockage : un fichier YAML par
analyse, `impact-analyses/<id>.yaml`, sur le modèle des fichiers `impact-acks/` déjà utilisés par le
mécanisme existant.

Contenu : les deux baselines (tag + SHA résolu de chacune), la liste complète des exigences changées et,
pour chacune, ses deux arbres d'impact avec, par élément, son statut, son commentaire, et l'historique de
modification.

Le panneau latéral liste les analyses d'impact existantes (par libellé "A → B", date de création) — on
peut rouvrir une analyse en cours pour continuer à faire avancer les statuts. Puisque les deux baselines
sont immuables, il n'y a pas de notion de "recalcul" du diff ou des arbres : si le projet a évolué depuis
B, l'utilisateur pose une nouvelle baseline et ouvre une nouvelle analyse à partir de là — chaque analyse
reste un instantané figé et daté, cohérent avec l'usage d'audit (point 6).

### 5. Génération de campagne de vérification

Depuis la page d'analyse, un bouton "Générer une campagne" collecte tous les éléments dont le statut est
`impact_a_tester` ou `modification_a_tester` :

- Les éléments de type `test_case` sont ajoutés directement à la liste de la campagne
- Les éléments de type `requirement` sont résolus vers leurs TestCases approuvés couvrants, en réutilisant
  `generateTestPlan` (déduplication déjà gérée par ce service si un TestCase couvre plusieurs exigences
  sélectionnées)

Le résumé pré-création (nombre de TestCases trouvés, exigences non couvertes) affiché par
`generateTestPlan` est repris tel quel. La campagne créée référence dans ses métadonnées l'analyse
d'impact d'origine (traçabilité "cette campagne vérifie l'impact de v1.0 → v1.1").

### 6. Vue d'ensemble / garantie de complétude

Un indicateur d'avancement en tête de page : nombre d'éléments impactés par statut, et un compte "ouverts"
vs "clos". Sont considérés **clos** : `pas_d_impact_reel`, `impact_teste`, `modification_verifiee`. Tous
les autres statuts sont **ouverts**. L'analyse est marquée "complète" quand zéro élément ouvert reste —
visuellement mis en avant (ex. bandeau vert "Analyse complète — tous les impacts sont maîtrisés") plutôt
qu'un blocage dur : rien n'empêche de laisser une analyse incomplète, elle reste juste visible comme telle
tant qu'il reste des éléments ouverts. *(Cette catégorisation clos/ouvert est une proposition à valider —
elle sert uniquement à l'indicateur de complétude, elle ne contraint pas les transitions de statut.)*

## Hors scope

- Limiter/configurer la profondeur de traversée (ex. "s'arrêter à N niveaux") — T46 parcourt toujours le
  graphe complet dans les deux directions, pas de réglage utilisateur sur la profondeur
- Diff de baseline multi-composant (comparer un composant dans le cadre d'un workspace avec submodules)
  — se limite au repo actuellement sélectionné, comme `version-diff.tsx` aujourd'hui
- Remplacement du mécanisme `ImpactAcknowledgement` existant (déclenché à l'édition d'un élément) — reste
  inchangé, coexiste avec T46
- Export PDF/Excel du rapport d'analyse d'impact (pourrait réutiliser l'export déjà prévu pour d'autres
  vues, cf. T43, mais non traité ici)
- Suppression d'une analyse d'impact persistée — pas demandé, à traiter en évolution séparée si besoin
- Notifications / assignation d'un élément impacté à une personne — le champ `updatedBy` suffit pour la
  traçabilité, pas de workflow d'assignation dans ce ticket
- Recalcul du diff/des arbres d'une analyse existante — une analyse est figée sur les deux baselines
  choisies à sa création ; suivre une évolution ultérieure passe par une nouvelle baseline puis une
  nouvelle analyse, pas par une mise à jour de l'existante
- Comparaison contre une branche ou un commit non baselisé — si l'utilisateur veut comparer contre l'état
  courant, il doit d'abord poser une baseline dessus (cf. point 1) ; T46 n'offre pas de raccourci qui
  contournerait cette contrainte

## Critères d'acceptation

1. Depuis le panneau Version, on peut ouvrir une page d'analyse d'impact, choisir deux baselines existantes
   sur le repo sélectionné (ou en créer une nouvelle sur l'état actuel si aucune n'existe encore pour ce
   qu'on veut comparer), et voir la liste des exigences ajoutées/supprimées/modifiées entre les deux, avec
   pour les modifiées le détail des champs changés
2. Chaque exigence modifiée ou ajoutée peut être dépliée pour voir ses éléments impactés sous forme de
   deux arbres — un arbre descendant (exigences filles et leurs tests, récursif jusqu'aux feuilles) et un
   arbre montant (exigences parentes et leurs tests, récursif jusqu'à la racine, affiché seulement s'il
   n'est pas vide) — chaque élément avec son type et le lien qui le rattache à son nœud parent dans
   l'arbre
3. Chaque élément impacté a un statut parmi les 8 valeurs définies, modifiable librement depuis la liste,
   avec commentaire optionnel
4. L'analyse est persistée : la fermer et la rouvrir plus tard restitue exactement le même diff, les mêmes
   arbres, et les statuts tels que laissés — rien ne change sauf ce que l'utilisateur modifie explicitement
   (statut, commentaire)
5. Un bouton génère une campagne de vérification pré-remplie à partir de tous les éléments en statut "à
   tester" (impact ou modification), avec déduplication des TestCases
6. Un indicateur affiche le nombre d'éléments ouverts/clos et signale visuellement quand l'analyse est
   complète (plus aucun élément ouvert)
7. Cliquer sur une exigence ou un élément impacté dans l'arbre l'ouvre dans la zone principale avec les
   vues existantes (édition, Système, Excel, Word) — aucune vue dédiée nouvelle pour l'affichage d'un
   élément
8. Le mécanisme d'acquittement d'impact existant (déclenché à l'édition d'un élément, §4 de
   `SPEC-TRACEABILITY.md`) continue de fonctionner sans changement
9. On peut créer une baseline alors que le repo est sur une branche de travail (`dev-*`) quelconque, pas
   uniquement sur sa branche d'intégration configurée — seule une modification en attente (staged ou
   unstaged) bloque encore la création, sur n'importe quelle branche
