# T47 — Ajouter draw.io dans richtext (affichage et édition)

## Contexte

Le type de champ `drawio` existe déjà dans le modèle de données (`SchemaField.type`,
`packages/types/src/schema.ts`) mais uniquement comme **champ autonome** : dans
`EditView.tsx` (`case 'drawio'`), c'est une simple saisie de chemin de fichier +
un bouton "Ouvrir dans Draw.io" qui appelle `window.electronAPI.openExternal(...)`.
Cet appel est du code mort — `electronAPI` n'existe pas dans le contract IPC réel
(`packages/api-client/src/types.ts`), il n'y a ni handler main-process, ni entrée
`dialog.openExternalFile` ou équivalent. Le bouton ne fait donc rien aujourd'hui.

Il n'existe aujourd'hui **aucun moyen d'insérer un diagramme draw.io à l'intérieur
d'un champ `richtext`** (`RichTextField.tsx` / `RichTextViewer.tsx`, éditeur TipTap).
Seules les images (upload fichier ou coller presse-papiers, base64 inline) sont
supportées comme contenu visuel inline.

Par ailleurs, `CONTEXT.md` (décision D4) établit que les diagrammes sont stockés en
fichiers `.drawio` (XML) versionnés dans `diagrams/`, référencés par un pointeur
`fichier.drawio#node-id` pour une traçabilité fine — jamais embarqués tels quels
dans le Markdown. Le format d'exigence documenté dans `CLAUDE.md` illustre déjà ce
pattern via un champ `diagrams: [...]` de frontmatter, mais ce champ n'est un exemple
documentaire : il n'est implémenté nulle part dans le code actuel.

## Décisions (validées avec l'humain avant rédaction de cette spec)

1. **Stockage** : un diagramme inséré dans un richtext est une **référence** à un
   fichier `.drawio` existant sous `diagrams/`, avec un pointeur optionnel vers un
   node-id précis (`diagrams/foo.drawio#node-PWR-001`), cohérent avec D4. Pas de XML
   embarqué inline dans le Markdown.
2. **Édition** : pas d'éditeur draw.io intégré (pas d'iframe `embed.diagrams.net`).
   Le flux est "ouverture externe + resynchronisation", sur le même principe que le
   champ `drawio` autonome : un bouton ouvre le fichier dans l'application draw.io
   installée sur le poste (application desktop draw.io, pas le service en ligne),
   et Polenta relit le fichier et rafraîchit l'aperçu quand l'utilisateur revient sur
   la fenêtre (ou sur détection de changement du fichier sur disque).
3. **Offline requis** : aucune fonctionnalité de T47 ne doit dépendre d'un accès
   réseau. L'affichage du diagramme dans le richtext doit être un rendu local
   (pas de chargement d'`embed.diagrams.net`).

Conséquence directe : le bug du bouton "Ouvrir dans Draw.io" cassé (`electronAPI`
inexistant) doit être corrigé dans le cadre de T47, puisque le même mécanisme
d'ouverture externe est réutilisé pour le nouvel embed richtext ET pour le champ
`drawio` autonome existant.

## Comportement attendu

### Insertion dans un richtext (édition)

1. Dans la barre d'outils richtext (`RichTextToolbar.tsx`, et le mode inline
   toolbar de `RichTextField.tsx` sans contexte), un nouveau bouton "Insérer un
   diagramme draw.io" ouvre un sélecteur de fichier `.drawio` (via une nouvelle
   méthode IPC `dialog.pickDrawioFile`, sur le modèle de `dialog.pickImageFile`),
   limité aux fichiers du repo (sous `diagrams/` ou plus largement le repo courant
   — à trancher en Design).
2. Après sélection, un diagramme n'ayant qu'un seul node racine s'insère directement.
   Si le fichier `.drawio` contient plusieurs diagrammes/pages, l'utilisateur choisit
   la page/le node-id ciblé avant insertion (liste des pages du fichier).
3. Le diagramme s'insère comme un bloc inline dans le document TipTap, au point du
   curseur — même logique de positionnement que l'insertion d'image.
4. Le document Markdown stocké (`richtext` field) sérialise ce bloc de façon stable
   et diffable en Git (ex. réutiliser la syntaxe image Markdown avec un marqueur
   dédié, ou une syntaxe custom — détail technique laissé à `T47-design.md`).

### Affichage (lecture et édition)

5. Dans `RichTextViewer.tsx` (lecture seule) et `RichTextField.tsx` (édition), un
   diagramme référencé est rendu **localement, sans réseau** : un aperçu visuel du
   diagramme (pas seulement une icône + nom de fichier), généré à partir du XML du
   fichier `.drawio` référencé.
6. Le rendu se limite à la page/au node-id référencé si un pointeur a été précisé,
   sinon à la première page du fichier.
7. Si le fichier référencé est introuvable (chemin invalide, fichier supprimé,
   submodule non résolu dans le workspace courant), afficher un état d'erreur
   explicite inline ("diagramme introuvable : diagrams/foo.drawio") plutôt qu'un
   rendu vide silencieux ou un crash de l'éditeur.
8. Un double-clic (ou un bouton dédié au survol) sur le diagramme rendu ouvre le
   fichier dans l'application draw.io externe installée sur le poste.
9. Au retour de focus sur la fenêtre Polenta après une édition externe (ou sur
   détection de changement du fichier sur disque), l'aperçu inline se rafraîchit
   automatiquement sans action supplémentaire de l'utilisateur.

### Champ `drawio` autonome (bug connexe corrigé dans ce ticket)

10. Le bouton "Ouvrir dans Draw.io" de `EditView.tsx` (`case 'drawio'`) utilise
    désormais le même mécanisme IPC réel que le nouvel embed richtext (au lieu de
    l'appel mort à `window.electronAPI.openExternal`) — il devient fonctionnel.

## Cas limites

- Diagramme référencé dans un composant submodule non cloné dans le workspace
  courant → état "introuvable", pas de résolution de chemin qui plante.
- Fichier `.drawio` invalide/corrompu (XML non parsable) → état d'erreur explicite,
  pas de crash de l'éditeur TipTap.
- Suppression du fichier `.drawio` référencé après insertion dans un richtext → le
  bloc reste dans le document (référence pointant vers un fichier absent), affichage
  en état d'erreur au prochain rendu (cf. point 7) ; pas de suppression automatique
  du bloc.
- Aucune application draw.io desktop installée sur le poste → l'ouverture externe
  échoue silencieusement côté OS (comportement standard `shell.openPath`) ; pas de
  détection préalable de la présence de l'app à la charge de Polenta.
- Copier-coller d'un bloc de richtext contenant un diagramme d'un champ à un autre
  (même objet ou objet différent) → la référence de fichier est copiée telle quelle
  (même fichier `.drawio` partagé), pas de duplication de fichier.

## Hors scope explicite

- Éditeur draw.io intégré (iframe / embed.diagrams.net) — explicitement écarté
  (offline requis).
- Création d'un nouveau fichier `.drawio` depuis le richtext (dessiner un nouveau
  diagramme sans passer par l'app externe) — seule l'insertion d'un fichier
  **existant** est couverte.
- Export Word/Excel (`T43`) du rendu inline des diagrammes dans les documents
  générés — à traiter dans le ticket d'export si besoin, pas ici.
- Résolution automatique de rétrocompatibilité ou de conflits quand deux richtext
  de composants différents référencent le même fichier `.drawio` avec des chemins
  relatifs différents — hors scope, cohérent avec le système de résolution de
  chemin existant (aucun mécanisme spécifique à ajouter).
- Historique de versions / diff visuel du contenu du diagramme (le diff Git du XML
  `.drawio` brut, déjà existant via `T59`, reste le mécanisme de diff).

## Critères d'acceptation

- [ ] Un bouton "Insérer un diagramme draw.io" est disponible dans la toolbar
      richtext (contexte `RichTextToolbar.tsx` et mode standalone `RichTextField.tsx`)
- [ ] La sélection d'un fichier `.drawio` (avec choix de page/node-id si plusieurs)
      insère une référence dans le document au point du curseur
- [ ] Le document Markdown stocké contient une représentation stable et diffable de
      la référence (chemin + node-id optionnel), pas de XML dupliqué inline
- [ ] `RichTextViewer.tsx` et `RichTextField.tsx` rendent visuellement le diagramme
      référencé localement, sans requête réseau
- [ ] Le rendu respecte le node-id/la page ciblée si précisé
- [ ] Un fichier référencé introuvable ou invalide affiche un état d'erreur inline
      explicite, sans crash
- [ ] Double-clic sur le diagramme rendu ouvre le fichier dans l'application draw.io
      externe du poste
- [ ] Le retour de focus sur Polenta après édition externe rafraîchit l'aperçu inline
      automatiquement
- [ ] Le bouton "Ouvrir dans Draw.io" du champ `drawio` autonome (`EditView.tsx`)
      est corrigé et fonctionnel (même mécanisme IPC que le point précédent)
- [ ] Aucune fonctionnalité livrée ne dépend d'une connexion internet
