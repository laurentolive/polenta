# T50 — Richtext dans la vue d'exécution des tests / description de campagne / étapes

## Contexte et clarification du périmètre

Le ticket original demandait du richtext à trois endroits : commentaires de la vue d'exécution,
description de campagne, étapes de test. L'investigation du code existant a montré que :

- `StepResult.comment` (commentaire par étape lors de l'exécution) et `TestRun.notes` (notes
  globales du run) sont **déjà** en richtext (`RichTextField` en édition, `RichTextViewer` en
  lecture) — voir `campaign.$campaignId.execute.$testId.tsx` et `campaign.$campaignId.run.$testId.tsx`.
- `TestCase.steps[].action` / `.expectedResult` (étapes de la **définition** du test) sont
  également déjà en richtext (`StepsTable.tsx`).
- Le seul champ réellement en texte brut est `TestCampaign.description`.

Décision validée avec l'utilisateur : plutôt que de rendre `description` en richtext directement,
ce champ système codé en dur est **supprimé**. La catégorie `campaign` gagne le même mécanisme
générique de champs personnalisés (`fields{}` + `objectTypeRef`) que `requirement`/`test`, déjà
prévu dans le modèle de schéma (`ObjectCategory` inclut `'campaign'`, `StructureTab.tsx` propose
déjà cette catégorie) mais jamais câblé côté `TestCampaign`. Un projet qui a besoin d'une
description de campagne l'ajoute alors comme champ personnalisé (type `richtext` ou autre) via
`schema.yaml`, exactement comme pour les exigences et les tests.

`TestStep.notes` (définition) et `preconditions`/`postconditions` du `TestCase` restent hors
scope (voir Hors scope).

## Comportements attendus

1. `TestCampaign` n'a plus de champ système `description` codé en dur. Il gagne :
   - `objectTypeRef?: string` — référence au type de campagne défini dans `schema.yaml`
     (format `component::typeName`, comme pour `Requirement`/`TestCase`)
   - `fields: Record<string, unknown>` — valeurs des champs personnalisés du type
2. `CreateCampaignDto` reflète les mêmes champs (`objectTypeRef`, `fields`) à la place de
   `description`. Un `UpdateCampaignDto` (nouveau) permet de modifier `title`, `objectTypeRef`,
   `fields` sur une campagne existante.
3. Formulaire de création (`campaign.new.tsx`) :
   - Si un ou plusieurs objectTypes `category: campaign` existent dans le schéma du nœud courant,
     l'utilisateur choisit le type (comme pour un test) et les champs personnalisés du type
     s'affichent via `DynamicField` (richtext rendu par `RichTextField`).
   - S'il n'y a aucun objectType/champ défini, aucune section "champs personnalisés" ne s'affiche
     — et il n'y a plus de champ "Description" par défaut.
4. Page de détail (`campaign.$campaignId.tsx`) :
   - Les champs personnalisés sont affichés (richtext via `RichTextViewer`) à la place du
     paragraphe `description` codé en dur actuel.
   - Un mode édition permet de modifier ces champs après création (nouvel appel
     `api.campaigns.update`).
5. Backend `campaigns.service.ts` :
   - `create()` stocke `objectTypeRef`/`fields` depuis le dto (au lieu de `description`).
   - Nouvelle méthode `update()` (mirroring `tests.service.ts`) pour modifier `title`,
     `objectTypeRef`, `fields` sur une campagne existante, avec merge des `fields` (comme
     `tests.service.ts:71`).
6. Aucune campagne existante en base (aucune donnée de production affectée à ce jour dans ce repo)
   — pas de migration nécessaire. Les campagnes déjà créées sans `fields`/`objectTypeRef`
   continuent de se charger (`fields` défaut `{}`).
7. L'éditeur de schéma (onglet "Modèle de données" / `StructureTab.tsx`) supporte déjà la
   catégorie `campaign` — aucun changement requis de ce côté.

## Critères d'acceptation

- [ ] `TestCampaign`, `CreateCampaignDto`, `UpdateCampaignDto` n'ont plus de `description` codé en
      dur ; ils exposent `objectTypeRef?` et `fields: Record<string, unknown>`.
- [ ] Un `schema.yaml` peut déclarer un objectType `category: campaign` avec un champ `description`
      de type `richtext` (ou tout autre champ), et ce champ apparaît dans le formulaire de création
      de campagne.
- [ ] Le formulaire de création de campagne n'affiche plus de champ "Description" codé en dur ;
      les champs personnalisés du type sélectionné s'affichent à la place (via `DynamicField`),
      y compris en richtext si le champ est typé ainsi.
- [ ] La page de détail de campagne affiche les champs personnalisés (richtext rendu via
      `RichTextViewer`) au lieu du paragraphe `description` codé en dur.
- [ ] Il est possible de modifier les champs personnalisés d'une campagne existante après création.
- [ ] Aucune régression sur les fonctionnalités existantes de la page campagne (ajout de tests,
      clôture, suppression, suivi des runs, filtres par `component`/`level`).
- [ ] TypeScript compile sans nouvelle erreur ; `/code-review` passé sur le diff.

## Hors scope

- Richtext pour `TestStep.notes` (définition du test) — champ non exposé dans l'UI actuellement,
  aucun éditeur n'existe (`test.new.tsx`/`test.$testId.tsx` le forcent à `null`).
- `preconditions`/`postconditions` du `TestCase` — actuellement en `<textarea>` brut malgré leur
  typage `RICHTEXT` dans `packages/types/src/test.ts` ; incohérence pré-existante non demandée
  par ce ticket.
- Migration automatique des anciennes valeurs `description` de campagnes existantes vers
  `fields.description` — aucune donnée de production affectée à ce jour.
- Ajout d'une interface de sélection de "campaign type" dans l'éditeur de schéma — déjà supporté
  (`StructureTab.tsx`), aucun changement nécessaire.
- Template par défaut (`templates/electro-domestic-battery.yaml`) ne déclare aujourd'hui aucun
  objectType `campaign` — en ajouter un par défaut n'est pas demandé (chaque projet configure
  selon son besoin).
