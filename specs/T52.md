# T52 — Restaurer la sélection composant/élément en revenant sur la vue Système

## Contexte

`SystemViewContext` pilote déjà la sélection courante (repo, composant/`node`, type/`élément`)
via les search params de l'URL (`repo`, `node`/`component`, `type`/`level` — voir
SPEC-SYSTEM-VIEW.md §Persistance de l'état). Ce mécanisme fonctionne pour partager un lien direct,
mais ne survit pas à une navigation vers un autre panneau puis un retour :

- `ActivityBar` → `AppLayout.handleSelectPanel('system')`
  (`apps/desktop/src/renderer/components/layout/AppLayout.tsx:116-118`) navigue vers `/product`
  en mettant **explicitement** `repo`/`node`/`type` à `undefined` à chaque clic, quelle que soit
  la sélection précédente.
- `SystemViewProvider` n'est monté que si le panneau actif est `system`
  (`AppLayout.tsx:142-150`) : en quittant la vue, tout état en mémoire est détruit, pas seulement
  réinitialisé.
- Avec une URL "bare", l'effet de défaut de `SystemViewContext`
  (`SystemViewContext.tsx:224-235`) retombe systématiquement sur `nodes[0]` / premier type.
- Rien n'est persisté sur disque pour repo/node/type : un redémarrage de l'app perd aussi la
  sélection (contrairement au mode de vue Excel/Word, déjà persisté via `localStorage`
  — `polenta:viewMode:${repoPath}`, `SystemView.tsx:299,308`).

Le ticket demande que la vue Système réaffiche **par défaut** le dernier composant et le dernier
élément consultés, aussi bien en revenant depuis un autre panneau qu'en rouvrant le projet.

## Comportements attendus

1. À chaque fois que la sélection effective (repo + composant + type d'élément) devient valide et
   stable dans `SystemViewContext` (c'est-à-dire correspond à une entrée réelle de `repoOptions` /
   `nodes` / `objectTypes`), elle est persistée dans `localStorage` sous la clé
   `polenta:lastSelection:${projectId}`, valeur JSON `{ repo, node, type }`.
2. Quand `SystemViewProvider` est monté avec une URL "bare" (`!urlRepo || !urlNode`, cas actuel de
   l'effet de défaut) :
   - Si une sélection est présente en `localStorage` pour ce `projectId`, et que `repo` existe
     dans `repoOptions`, `node` dans les `nodes` du schéma de ce repo, et `type` dans les
     `objectTypes` de ce `node`, la navigation initiale utilise cette sélection au lieu de
     `nodes[0]` / premier type.
   - Sinon (première visite, ou sélection sauvegardée invalide/obsolète — composant renommé,
     supprimé, type supprimé du schéma…), comportement inchangé : composant racine + premier
     élément.
3. `AppLayout.handleSelectPanel('system')` n'a pas besoin d'être modifié : il continue de
   naviguer vers `/product` avec des params vides — c'est l'effet de défaut de
   `SystemViewContext` (point 2) qui restaure la sélection à partir de `localStorage`. Ceci couvre
   uniformément tous les points d'entrée "bare" vers `/product` (activity bar, redémarrage de
   l'app, lien pré-T72 sans `repo`), pas seulement le clic sur l'icône Système.
4. La sélection est propre à chaque projet (clé indexée par `projectId`) : ouvrir un autre projet
   n'affiche pas la dernière sélection d'un projet différent.
5. Un changement explicite de composant ou d'élément via les comboboxes (déjà géré par
   `handleRepoChange`/`handleNodeChange`/`handleTypeChange`) met aussi à jour la sélection
   persistée, puisqu'il modifie l'URL et retombe donc sur le même effet de persistance (point 1).

## Hors scope

- La restauration ne couvre que composant (repo + `node`) et élément (`type`) — pas l'élément
  précis ouvert dans l'arbre/la vue Édition (`editingNodeId`), ni le filtre, ni le mode de vue
  Excel/Word (déjà géré séparément), ni la position de scroll ou l'historique undo/redo. La
  spec existante précise déjà que "la sélection dans l'arbre n'a aucun impact sur le contenu de
  la vue document" — ce ticket ne change pas cette règle.
- La route `/components` (onglet Structure, T70) partage la même faiblesse en théorie mais n'est
  actuellement jamais atteinte avec des params "bare" par `AppLayout` — non modifiée par ce
  ticket.
- Migration/nettoyage d'anciennes clés `localStorage` — aucune clé de ce type n'existe
  actuellement.
- Persistance multi-fenêtre/multi-utilisateur (fichier `.{githubaccount}.pref`, comme pour la
  config des champs visibles) : `localStorage` suffit puisque la sélection de navigation est un
  confort individuel, pas une donnée de projet partagée.

## Critères d'acceptation

- [ ] Sélectionner un composant B et un élément Y dans la vue Système, naviguer vers un autre
      panneau (ex. Version), puis revenir sur Système via la barre d'activité : B/Y sont réaffichés
      (pas le composant racine / premier élément).
- [ ] Même scénario après un redémarrage complet de l'application sur le même projet : B/Y sont
      réaffichés.
- [ ] Si le composant ou l'élément sauvegardé n'existe plus (schéma modifié entre-temps), retour
      silencieux au comportement par défaut (composant racine, premier élément), sans erreur.
- [ ] Deux projets différents ouverts successivement conservent chacun leur propre dernière
      sélection (pas de fuite entre projets).
- [ ] Un lien direct existant avec `repo`/`node`/`type` explicites dans l'URL continue de
      prévaloir sur la sélection persistée (l'URL reste la source de vérité quand elle est
      renseignée).
- [ ] Aucune régression sur le changement de composant/élément via les comboboxes, le mode de vue
      Excel/Word, ni sur `/components`.
- [ ] TypeScript compile sans nouvelle erreur ; `/code-review` passé sur le diff.
