# T61 — Sauvegarde dans le repo du composant

## Statut
Corrigé — branche `T61` (fix complet : API + desktop)

## Root cause (corrigée)

**Deux scopes touchés, fix initial incomplet.**

Le premier correctif ciblait uniquement `apps/api` (NestJS backend). Or l'app Electron desktop possède ses propres services dans `apps/desktop/src/main/services/` qui n'utilisent pas l'API pour les opérations fichiers. Le bug persistait donc dans le desktop.

### Root cause API (`apps/api`)

`GitService.writeAndCommit` utilisait toujours `this.repoPath(projectId)` (le repo produit) comme répertoire cible, sans jamais consulter le schéma `.polenta/schema.yaml`.

### Root cause Desktop (`apps/desktop`)

`RequirementsService` et `TestsService` appelaient `this.git.writeYaml(repoPath, ...)` avec le `repoPath` produit pour toutes les opérations (create, update, transition, execute). `SchemaService` existait dans le desktop mais n'était jamais consulté depuis ces services — aucune logique de routing vers le repo composant.

## Correctifs appliqués

### Correctif initial — API (`apps/api`)

#### 1. `apps/api/src/modules/git/schema.service.ts` (nouveau fichier)

`SchemaService` :
- Lit et met en cache `.polenta/schema.yaml` du repo produit.
- Expose `parseNodeName(objectTypeRef)` : extrait le nom du nœud avant `::`.
- Expose `repoPathForNode(projectId, nodeName)` : retourne le chemin du repo composant pour les nœuds avec `url`, ou le repo produit sinon.

#### 2. `apps/api/src/modules/git/git.module.ts`

Ajout de `SchemaService` dans `providers` et `exports`.

#### 3. `apps/api/src/modules/git/git.service.ts`

`writeAndCommit` accepte un paramètre optionnel `repoDir?: string` pour cibler un repo composant.

#### 4. `apps/api/src/modules/requirements/requirements.service.ts` et `tests.service.ts`

Injection de `SchemaService` + appel `resolveRepoDir(projectId, objectTypeRef)` avant chaque `writeAndCommit`.

---

### Correctif suite — Desktop (`apps/desktop`)

#### 5. `apps/desktop/src/main/services/schema.service.ts`

Ajout de la méthode :
```ts
async resolveComponentRepoPath(repoPath: string, objectTypeRef: string): Promise<string | null>
```
- Parse le node name depuis `objectTypeRef` (avant `::`).
- Si node name = `root` ou pas de `::` → retourne `null` (repo produit).
- Lit le schéma depuis le cache.
- Si le node a une `url` → retourne `path.join(repoPath, 'components', nodeName)`.
- Si `components/<name>` existe sans `.git`, initialise un nouveau repo git via `git.init()`.
- Sinon → retourne `null`.

#### 6. `apps/desktop/src/main/services/requirements.service.ts`

- Injecte `SchemaService` dans le constructeur (3ème argument).
- `create()`, `update()`, `openDraft()`, `transition()` : résolution du `targetRepo` via `schema.resolveComponentRepoPath()` avant chaque `git.writeYaml()`.
- L'index (`index.upsert`) continue de pointer vers le `repoPath` produit pour la recherche unifiée.

#### 7. `apps/desktop/src/main/services/tests.service.ts`

Mêmes changements : `create()`, `update()`, `execute()` routent les écritures vers `targetRepo`.
- `execute()` consulte d'abord `testsIndex.findById()` pour obtenir l'`objectTypeRef` du test case existant avant de résoudre le repo.
- `nextRunId()` est appelé avec `targetRepo` (les runs vivent dans le même repo que les tests).

#### 8. `apps/desktop/src/main/container.ts`

`SchemaService` instancié **avant** `RequirementsService` et `TestsService` (déplacé en début de `createContainer`), puis passé aux deux services.

## Convention chemin composant (desktop)

Les composants sont attendus sous :
```
<repoPath>/components/<nodeName>/
```
Identique à l'API. Si le répertoire existe sans `.git` (ex : submodule vide non initialisé), `resolveComponentRepoPath` appelle `git.init()` automatiquement.

## Comment vérifier le fix (desktop)

1. Ouvrir un projet produit dont `.polenta/schema.yaml` déclare un composant avec `url` (ex: `HMI`).
2. Créer une exigence avec `objectTypeRef: "HMI::exigence-ihm"` depuis l'UI desktop.
3. Vérifier que le fichier `requirements/<ID>.yaml` est créé dans `<repoPath>/components/HMI/` et non dans `<repoPath>/`.
4. Si `components/HMI` était vide (pas de `.git`), vérifier que le dossier a été initialisé (`components/HMI/.git` existe).
5. Pour un nœud local (`root::exigence-systeme`), l'écriture reste dans `<repoPath>/` — comportement inchangé.
