# T69 — Refonte architecture workspace & composants interface

## Contexte

La limite de ~10 submodules git posée en T30 n'est plus tenable dès qu'on introduit la notion d'interface versionnée. Un produit réaliste avec 6 domaines + interfaces entre composants dépasse facilement 20-30 repos. La gestion par git submodules devient un frein.

## Décisions d'architecture

### 1. Workspace plat géré par Polenta

Tous les repos sont clonés au même niveau dans un répertoire de travail choisi par l'utilisateur. Git redevient un outil de versioning simple — Polenta porte la composition.

```
workspace/                        ← répertoire choisi à la création
├── .polenta/                     ← marqueur local, NON versionné
│   ├── workspace.yaml            ← config locale (overrides de noms, etc.)
│   └── tree.cache.yaml           ← arbre calculé, régénéré à l'ouverture
├── product-aspirateur-v1/        ← repo root
├── comp-motor-control/           ← cloné automatiquement par Polenta
├── comp-bms/
├── iface-can-bus/                ← interface
└── can-bus-legacy/               ← iface-can-bus monté sous nom alternatif (conflit)
```

`.polenta/` dans le répertoire parent (hors de tout repo git) est le marqueur de workspace. Sa présence identifie la racine du workspace Polenta.

### 2. Déclaration des dépendances par repo

Chaque repo qui a des enfants déclare uniquement ses dépendances directes dans `polenta-repo.yaml` à sa racine :

```yaml
# product-aspirateur-v1/polenta-repo.yaml
dependencies:
  - name: comp-motor-control
    url: git@github.com:org/comp-motor-control.git
    pin: a3f8c21
  - name: comp-bms
    url: git@github.com:org/comp-bms.git
    pin: f2d1e80
  - name: iface-can-bus
    url: git@github.com:org/iface-can-bus.git
    pin: b7d2e90
```

- Chaque repo ne connaît que ses enfants directs, jamais ses parents.
- Le pin de version est géré par le parent (configuration management).
- Les repos sans enfants n'ont pas de `polenta-repo.yaml`.

### 3. Construction de l'arbre complet par parsing récursif

Polenta reconstruit l'arbre complet au runtime par parcours récursif des `polenta-repo.yaml`. Cet arbre est mis en cache dans `.polenta/tree.cache.yaml` (non versionné, régénéré à chaque ouverture).

Flow d'ouverture d'un repo root :
```
Ouvrir product-aspirateur-v1
  → parse polenta-repo.yaml
  → clone/checkout comp-motor-control @ a3f8c21  (si absent du workspace)
    → parse polenta-repo.yaml de motor-control
    → clone/checkout iface-can-bus @ b7d2e90     (si absent)
  → clone/checkout comp-bms @ f2d1e80
    → iface-can-bus déjà présent, même pin → OK
  → écrire .polenta/tree.cache.yaml
```

### 4. Gestion des dépendances en diamant

Quand deux composants dépendent de la même interface à des versions différentes avec le même nom de montage, Polenta détecte le conflit pendant le parsing et notifie l'utilisateur.

**Option A — Mise à jour** : l'utilisateur met à jour le pin d'un des composants pour converger vers une version commune.

**Option B — Coexistence** : deux versions coexistent dans le workspace. L'utilisateur choisit librement le nom de montage pour chaque version (nom métier, plutôt que version dans le nom).

```yaml
# .polenta/workspace.yaml  ← config locale du workspace
mount-overrides:
  - repo-url: git@github.com:org/iface-can-bus.git
    pin: b7d2e90
    mount-as: can-bus-next       # nom choisi par l'utilisateur
  - repo-url: git@github.com:org/iface-can-bus.git
    pin: 3a1d007
    mount-as: can-bus-legacy     # nom choisi par l'utilisateur
```

### 5. Interface versionnés

Une interface est un repo Polenta ordinaire, avec son propre `schema.yaml` et son arbre de versions. Il représente le contrat entre deux composants (protocole de communication, format d'échange, API matérielle).

Déclaration dans `schema.yaml` d'un composant implémenteur :

```yaml
# comp-motor-control/.polenta/schema.yaml
implements:
  - interface: iface-can-bus    # nom de montage dans le workspace
    version: "2.1"              # version sémantique de l'interface implémentée
```

Nouveau `linkType` dans le schéma produit pour la traçabilité :

```yaml
# product-aspirateur-v1/.polenta/schema.yaml
linkTypes:
  - name: implements-interface
    labelSourceToTarget: "implémente"
    labelTargetToSource: "est implémenté par"
    sourceRefs: [requirement]
    targetRefs: [requirement]
```

## Suppressions

- Les git submodules ne sont plus utilisés. `.gitmodules` disparaît.
- La limite arbitraire de 10 submodules est levée.
- `schema.nodes[].url` disparaît du schéma (remplacé par `polenta-repo.yaml`).

## Impact sur l'existant

| Élément | Changement |
|---|---|
| `schema.yaml` | Suppression de `nodes[].url` et `nodes[].branch` |
| `tree.yaml` | Remplacé par `.polenta/tree.cache.yaml` (hors repo) |
| `scripts/update-tree.py` | À adapter pour le parsing récursif |
| Vue système | Doit lire l'arbre depuis le cache workspace |
| CI/CD | Doit cloner le workspace avant de lancer les scripts |

## Phases de mise en œuvre

1. **Workspace local** — création, marqueur `.polenta/`, sélection du répertoire de clonage
2. **Parsing récursif** — lecture des `polenta-repo.yaml`, clone automatique, cache
3. **Détection de conflits** — diamond deps, notification, résolution (option A ou B)
4. **Interface** — nouveau type de repo, linkType `implements-interface`
5. **Migration** — outil de conversion depuis l'ancien modèle submodules

## Description fonctionnelle détaillée

### UC-1 — Créer un workspace

L'utilisateur choisit un répertoire sur son disque puis indique l'URL (ou chemin local) du repo root. Polenta initialise le workspace et clone le repo root en une seule opération.

**Comportement attendu :**
- Si le répertoire contient déjà `.polenta/`, Polenta propose de l'ouvrir au lieu d'en créer un nouveau.
- Sinon, Polenta initialise `.polenta/workspace.yaml`, demande à l'utilisateur de configurer le repo root et Polenta le clone dans le répertoire workspace, puis lance le parsing récursif (UC-4) pour cloner automatiquement toutes les dépendances.
- Le `WorkspaceService` actuel (`workspace.json` dans `app.getPath('userData')`) est remplacé ou complété par ce nouveau marqueur de workspace par répertoire.

### UC-2 — Ouvrir un workspace existant

L'utilisateur sélectionne un répertoire. Polenta cherche `.polenta/workspace.yaml` à sa racine. Si trouvé → workspace reconnu. Polenta liste les repos présents dans le répertoire et reconstruit l'arbre.

**Comportement attendu :**
- Polenta lit `tree.cache.yaml` si présent et récent (même commit HEAD du repo root que lors du dernier cache).
- Si le cache est absent ou périmé, Polenta lance le parsing récursif (UC-4).
- Les repos présents dans le répertoire mais non référencés dans aucun `polenta-repo.yaml` sont ignorés silencieusement.

### UC-3 — Parsing récursif et clonage automatique des dépendances

À partir du repo root, Polenta lit `polenta-repo.yaml` (s'il existe) et pour chaque dépendance :
- **Même URL, même pin, déjà cloné** → skip, instance partagée.
- **Même URL, même pin, absent** → clone une seule fois sous le nom déclaré.
- **Même URL, pins différents** → deux instances indépendantes obligatoires (UC-4).
- **URL inconnue** → clone à partir de `url` au commit `pin` dans `<workspace>/<name>/`.
- Après le clone, parsing récursif du `polenta-repo.yaml` de la dépendance (DFS).
- Écriture de `tree.cache.yaml` à la fin.

**Règle d'arrêt :** un repo sans `polenta-repo.yaml` est une feuille, le parsing s'arrête.

### UC-4 — Même repo, pins différents

Deux composants dépendent de `iface-can-bus` à des pins différents. Ce sont deux instances indépendantes — elles ne peuvent pas partager le même répertoire. Polenta interrompt le parsing et demande à l'utilisateur de déclarer deux noms de montage distincts dans `.polenta/workspace.yaml` :

```yaml
# .polenta/workspace.yaml
mount-overrides:
  - url: git@github.com:org/iface-can-bus.git
    pin: b7d2e90
    mount-as: can-bus-next      # nom métier choisi par l'utilisateur
  - url: git@github.com:org/iface-can-bus.git
    pin: 3a1d007
    mount-as: can-bus-legacy    # nom métier choisi par l'utilisateur
```

Les noms sont libres — l'utilisateur peut choisir sa terminologie projet. Après saisie, Polenta relance le parsing et clone les deux instances sous leurs noms respectifs.

### UC-5 — Mettre à jour le pin d'une dépendance

L'utilisateur sélectionne un composant dans l'arbre du workspace et choisit un nouveau pin (commit SHA ou tag). Polenta :
1. Met à jour le `polenta-repo.yaml` du repo parent concerné.
2. Si un autre composant partageait l'ancienne version et n'a pas changé → le clone existant reste intact (il est maintenant orphelin de la référence mise à jour).
3. Clone la nouvelle version si absente du workspace.
4. Marque les liens vers des objets de la dépendance comme `needsRevalidation` (analyse d'impact identique à §4.4 de SPEC-FORKS-BRANCHES-BASELINES.md).
5. Régénère `tree.cache.yaml`.

### UC-6 — Interface

Une interface est un repo Polenta ordinaire côté structure (mêmes exigences, mêmes tests, même arbre de versions). Il déclare ses rôles dans son propre `schema.yaml` — c'est l'interface qui est souveraine sur sa terminologie (producer/consumer, master/slave, controller/device, server/client, etc.) :

```yaml
# iface-can-bus/.polenta/schema.yaml
roles:
  - name: controller
    label: Contrôleur CAN
  - name: device
    label: Périphérique CAN
```

Les exigences de l'interface sont taguées par rôle dans leur frontmatter :

```yaml
# iface-can-bus/requirements/REQ-CAN-001.md
---
id: CAN-001
fields:
  roles: [controller]   # seul le contrôleur doit couvrir cette exigence
  statement: |
    WHEN the controller initiates a transfer
    THE controller SHALL send a START condition within 1 µs
---
```

Un composant implémenteur déclare dans son `schema.yaml` quelle version de l'interface il implémente et quels rôles il joue. Un composant peut jouer plusieurs rôles simultanément :

```yaml
# comp-motor-control/.polenta/schema.yaml
implements:
  - interface: iface-can-bus
    version: "2.1"
    roles: [device]          # motor-control est uniquement périphérique

# comp-bms/.polenta/schema.yaml
implements:
  - interface: iface-can-bus
    version: "2.1"
    roles: [controller, device]   # bms est à la fois maître et nœud
```

Cette déclaration active trois comportements dans Polenta :

**1. Vérification de couverture par rôle**

Polenta filtre les exigences `approved` de l'interface par les rôles déclarés par le composant. Seules les exigences dont le champ `roles` intersecte les rôles déclarés sont exigées. Toute exigence applicable sans lien `implements-interface` entrant depuis ce composant est signalée comme non couverte.

**2. Matrice de conformité**

Une vue dédiée affiche, pour chaque repo interface du workspace :
- Lignes : exigences `approved` de l'interface (groupées par rôle)
- Colonnes : composants implémenteurs avec leurs rôles déclarés
- Cellules : `covered` / `missing` / `validated` — grisée si le rôle de l'exigence ne s'applique pas au composant

**3. Notification de changement**

Quand une exigence d'un repo interface passe en `approved` ou est modifiée après approbation, Polenta identifie tous les composants du workspace dont les rôles déclarés intersectent le champ `roles` de l'exigence modifiée, et marque leurs liens `implements-interface` concernés comme `needsRevalidation`. Le mécanisme est identique à §4.4 de SPEC-FORKS-BRANCHES-BASELINES.md.

## Critères d'acceptation

### CA-1 — Marqueur workspace

- [ ] Un répertoire contenant `.polenta/workspace.yaml` est reconnu comme workspace à l'ouverture.
- [ ] Un répertoire sans `.polenta/workspace.yaml` n'est pas reconnu comme workspace (message explicite).
- [ ] La création d'un nouveau workspace écrit `.polenta/workspace.yaml` (même vide `{}`) sans modifier aucun repo git.

### CA-2 — Parsing récursif et clonage

- [ ] Ouvrir un repo root avec 3 dépendances directes (dont une partagée par deux chemins) clone exactement N repos distincts dans le workspace (N = nombre de repos uniques, pas de doublons pour les pins identiques).
- [ ] Un repo déjà présent au bon pin n'est pas re-cloné (vérification par chemin + HEAD commit SHA).
- [ ] `tree.cache.yaml` est écrit dans `.polenta/` après chaque parsing réussi.
- [ ] `tree.cache.yaml` est invalidé (supprimé ou recalculé) si le HEAD du repo root a changé depuis le dernier cache.

### CA-3 — Détection de conflit diamond

- [ ] Quand deux chemins de dépendance aboutissent au même `url` avec des `pin` différents, Polenta affiche une notification de conflit **avant** de cloner quoi que ce soit pour la version en conflit.
- [ ] La notification identifie les deux chemins et les deux pins.
- [ ] L'utilisateur peut choisir Option A ou Option B sans quitter l'app.

### CA-4 — Coexistence (Option B)

- [ ] Après configuration de `mount-overrides`, les deux versions sont présentes dans le workspace sous les noms configurés par l'utilisateur.
- [ ] Les objets liés à la version `can-bus-legacy` restent résolvables depuis la version `can-bus-next`.
- [ ] `tree.cache.yaml` reflète les deux montages distincts.

### CA-5 — Suppression de `schema.nodes[].url`

- [ ] Le type `SystemNode` dans `packages/types/src/schema.ts` ne comporte plus les champs `url` et `branch`.
- [ ] `SchemaService.syncSubmodules()`, `buildGitmodules()`, `cloneSubmodule()`, `removeSubmodule()`, `writeGitmodules()` sont supprimés.
- [ ] La vue "Modèle de données" (`renderer/routes/schema.tsx`) ne propose plus de champ URL/branche sur les nœuds.
- [ ] Les projets existants utilisant `nodes[].url` sont migrés par l'outil de migration (Phase 5) sans perte de données.

### CA-6 — Aucune régression sur les projets mono-repo (sans dépendances)

- [ ] Un repo sans `polenta-repo.yaml` s'ouvre normalement dans un workspace.
- [ ] Les fonctionnalités existantes (exigences, tests, branches, baselines) fonctionnent à l'identique.
- [ ] Le `WorkspaceService` (`workspace.json` dans userData) continue de fonctionner pour la liste des projets récents pendant la transition.

### CA-7 — Interface : déclaration des rôles

- [ ] Un repo interface peut déclarer N rôles dans son `schema.yaml` (sans limite de nombre).
- [ ] Une exigence de l'interface peut être taguée avec un ou plusieurs rôles via le champ `roles` dans son frontmatter.
- [ ] Une exigence sans champ `roles` s'applique à tous les rôles (exigence commune).
- [ ] Un composant implémenteur peut déclarer plusieurs rôles simultanément (`roles: [controller, device]`).
- [ ] Un repo déclarant `implements` est affiché avec un badge visuel distinct dans l'arbre workspace.
- [ ] Le `linkType` `implements-interface` est proposé dans l'éditeur de liens du repo implémenteur.

### CA-8 — Vérification de couverture par rôle

- [ ] Polenta ne signale comme manquante que les exigences dont le champ `roles` intersecte les rôles déclarés par le composant.
- [ ] Un composant jouant le rôle `device` n'est pas signalé en défaut sur une exigence taguée `[controller]` uniquement.
- [ ] Un composant jouant `[controller, device]` est vérifié sur l'union des exigences des deux rôles.
- [ ] Le signal de non-couverture est visible depuis la vue du composant implémenteur.
- [ ] Une exigence en statut `draft` ou `obsolete` n'est pas exigée dans la vérification.

### CA-9 — Matrice de conformité

- [ ] Une vue "Conformité interfaces" est accessible depuis le workspace.
- [ ] Les lignes sont groupées par rôle ; les cellules hors-rôle d'un composant sont grisées (non applicables).
- [ ] Chaque cellule indique `covered`, `missing` ou `validated`.

### CA-10 — Notification de changement d'interface

- [ ] Quand une exigence d'interface est modifiée ou passe en `approved`, seuls les composants dont les rôles déclarés intersectent le champ `roles` de cette exigence reçoivent un `needsRevalidation`.
- [ ] La notification est visible dans la vue d'analyse d'impact (T46) et dans la matrice de conformité (CA-9).

## Cas limites à gérer

| Cas | Comportement attendu |
|-----|---------------------|
| Dépendance circulaire (A → B → A) | Détection de cycle pendant le parsing, arrêt avec erreur explicite listant le cycle |
| Repo cloné mais corrompu (pas de HEAD valide) | Avertissement non bloquant ; le repo est ignoré dans l'arbre mais reste sur disque |
| `polenta-repo.yaml` mal formé (YAML invalide) | Erreur de parsing signalée pour ce repo ; les autres branches de l'arbre continuent |
| Pin introuvable sur le remote (SHA inconnu) | Erreur de clone signalée ; l'utilisateur peut corriger le pin ou ignorer la dépendance |
| Deux repos déclarant le même `name` dans des `polenta-repo.yaml` différents mais URL différentes | Conflit de nom (pas de version) → Polenta demande à l'utilisateur de renommer l'un des deux via `mount-overrides` |
| Workspace ouvert sur une machine sans accès réseau | Les repos déjà clonés fonctionnent en offline ; les dépendances manquantes sont signalées comme non disponibles sans bloquer l'app |
| Migration d'un projet existant avec `nodes[].url` | L'outil de migration génère un `polenta-repo.yaml` à partir des nœuds avec URL et supprime les champs `url`/`branch` du `schema.yaml` |
| Profondeur d'arbre > 5 niveaux | Pas de limite technique imposée ; une dépendance circulaire est déjà couverte par la détection de cycle |

## UI — Points ouverts (à spécifier avant implémentation)

Les UCs suivants introduisent des interactions nouvelles qui n'ont pas d'équivalent dans l'UI actuelle. Ils devront être maquettés avant la phase d'implémentation correspondante.

### UI-1 — Wizard création de workspace (UC-1)

Interaction en deux étapes aujourd'hui absente de l'app :
1. Sélection du répertoire de workspace (file picker système).
2. Saisie de l'URL (ou chemin local) du repo root + lancement du clone.

Points à décider : modal ou page dédiée ? Progression du clonage visible ? Gestion des erreurs réseau inline ?

### UI-2 — Prompt nommage lors d'un conflit de pins (UC-4)

Quand deux deps aboutissent au même repo à des pins différents, Polenta doit interrompre le parsing et demander deux noms de montage. Interaction bloquante nouvelle.

Points à décider : notification + formulaire inline dans l'arbre workspace, ou modale séparée ? Prévisualisation des deux répertoires qui seront créés ?

## Hors scope (ce ticket ne fait PAS)

- **Interface graphique complète de gestion du workspace** : l'UC est textuel/YAML pour cette phase ; une vue dédiée peut venir plus tard.
- **Synchronisation automatique des dépendances en arrière-plan** : le clonage/checkout ne se déclenche qu'à l'ouverture ou à la demande explicite de l'utilisateur.
- **Contrôle d'accès par composant** : les permissions restent gérées au niveau du repo git (PAT/SSH), pas par Polenta.
- **Résolution automatique des conflits diamond** : Polenta notifie et propose des options, mais ne choisit jamais automatiquement.
- **Support de submodules git natifs** : on abandonne les submodules git ; aucun effort de compatibilité n'est requis pour `.gitmodules`.
- **CI/CD multi-repo** : la configuration CI pour cloner le workspace complet est hors scope (mentionnée dans "Impact sur l'existant" mais non implémentée ici).
- **Partage de workspace entre utilisateurs** : le répertoire workspace est local à chaque utilisateur ; aucune synchronisation du répertoire workspace lui-même n'est prévue.
- **Gestion des conflits de merge inter-repos** : les conflits de merge restent dans le scope de SPEC-FORKS-BRANCHES-BASELINES.md §2.4 et ne sont pas modifiés par ce ticket.
- **Upgrade assisté des dépendances** (analyse d'impact) : déjà spécifié dans SPEC-FORKS-BRANCHES-BASELINES.md §4.4 ; ce ticket pose uniquement l'infrastructure workspace, l'UI d'upgrade reste à planifier.
