# T70 — Refonte Modèle de données : arbre de structure (composants & interfaces)

## Contexte

Depuis T69, un composant ou une interface n'est plus une entrée `schema.nodes[].url` du schéma produit : c'est un repo git indépendant, cloné à plat dans le workspace, déclaré comme dépendance dans `polenta-repo.yaml` et découvert au runtime via l'arbre workspace (`.polenta/tree.cache.yaml`, route `/workspace`).

La page **Modèle de données** (`routes/schema.tsx`) n'a pas suivi ce changement : son onglet **Composants** ne fait qu'éditer des `SystemNode` locaux (name/label/description, sans repo réel) et son onglet **Éléments** configure les types d'objets (`ObjectTypeDefinition`) de ces nœuds locaux. Le lien entre "modèle de données" et "structure réelle du workspace" (route `/workspace`) n'existe pas : ce sont deux vues séparées, et il n'existe aujourd'hui **aucune UI** pour ajouter une dépendance (composant ou interface) au workspace — seul `polenta-repo:save` (écriture brute du manifeste) existe côté IPC.

Ce ticket unifie les deux : un unique arbre de structure, qui montre les repos réels du workspace et permet d'y ajouter des dépendances et des types d'éléments.

## Décisions

- **Ajout d'un composant = clone réel.** Ajouter un composant depuis l'arbre écrit une entrée dans `polenta-repo.yaml` du repo parent (`{ name: label, url: repo, pin: branche }`) et déclenche le clone dans le workspace, comme le fait déjà `WorkspaceTreeService.buildTree` pour les dépendances existantes. Le champ « branche » saisi par l'utilisateur est stocké tel quel dans `pin` (un `pin` n'est pas obligatoirement un SHA — cf. `repoExistsAtPin`).
- **Ajout d'une interface = clone + `implements`.** Le formulaire (repo, nom, rôle(s), version) fait deux choses en une action : (1) ajoute la dépendance comme un composant (repo → `polenta-repo.yaml`, nom → nom de montage), (2) écrit une entrée dans `implements:` du `schema.yaml` du repo **courant** (celui depuis lequel on ajoute) avec `{ interface: nom, version, roles }`.
- **Édition cross-repo.** Les types d'éléments (exigence/test/campagne) sont éditables pour n'importe quel repo de l'arbre (le repo courant et toutes ses dépendances clonées dans le workspace), pas seulement le repo racine. Éditer un repo dépendance modifie le `schema.yaml` de ce repo, physiquement présent sur disque dans le workspace.
- **`/workspace` est remplacée.** L'arbre de structure du nouvel onglet devient le seul endroit pour consulter/faire évoluer la structure du workspace. La route `/workspace` (et son usage éventuel depuis la page d'accueil) est retirée au profit de ce nouvel onglet.
- **Popup au lieu de carte inline.** L'édition d'un type d'élément (`ObjectTypeDefinition`) — aujourd'hui une carte dépliable inline dans l'onglet Éléments (`ObjectTypeCard`) — devient une popup modale. Le contenu (nom, label, préfixe, couleur, catégorie fixée à la création, tableau des champs, tableau des statuts) est repris à l'identique.
- **Suppression des nœuds locaux "hors repo".** L'onglet Composants actuel permet de créer des `SystemNode` locaux additionnels sans repo git réel (regroupements purement locaux). Cette possibilité disparaît : un repo dans l'arbre correspond toujours à un repo git réel (le repo courant ou une dépendance clonée). Le nœud local `root` du repo courant reste le point d'ancrage unique pour les types d'éléments propres à ce repo.

## Description fonctionnelle détaillée

### UC-1 — Consulter l'arbre de structure

L'onglet **Structure** (remplace les onglets Composants + Éléments) affiche l'arbre du workspace, ancré sur le repo courant :

```
▼ produit-aspirateur (racine)
  ├ 📄 SYS — Exigence Système       (élément)
  ├ 📄 SYS-TST — Test système       (élément)
  ▼ comp-motor-control              (composant)
    ├ 📄 MC-REQ — Exigence FW       (élément)
  ▼ iface-can-bus                   (interface)
    ├ 📄 CAN-001 — Exigence interface (élément)
```

- Chaque repo (racine, composant, interface) est un nœud dépliable ; ses enfants directs sont : les repos dont il dépend (`polenta-repo.yaml`) **et** ses propres types d'éléments (`ObjectTypeDefinition` de son `schema.yaml`).
- Badge visuel distinct pour un repo interface (repris de `/workspace` : badge violet "Interface").
- Si aucun workspace n'est actif (projet mono-repo simple, jamais initialisé en workspace plat), l'arbre affiche uniquement le repo courant avec ses types d'éléments — pas de section dépendances, pas d'action "Ajouter composant/interface" tant que le workspace n'est pas initialisé (cf. cas limite dédié).
- Cliquer sur un repo (racine, composant ou interface) déplie/replie ses enfants. Cliquer sur un élément (type d'objet) ouvre la popup de configuration (UC-5).

### UC-2 — Ajouter un composant

Action "+ Ajouter un composant", disponible sur n'importe quel repo de l'arbre (racine ou dépendance).

**Formulaire :** repo (URL git), label (nom de montage / affichage), branche.

**Comportement :**
1. Validation : nom de montage non vide, pas déjà utilisé par un autre mount name du workspace avec une URL différente (cas limite conflit de nom, cf. T69 cas limites).
2. Écrit une entrée `{ name: label, url: repo, pin: branche }` dans `polenta-repo.yaml` du repo sur lequel l'action a été lancée.
3. Déclenche un rebuild de l'arbre workspace (clone si absent, comme `workspace:rebuild-tree`).
4. Le nouveau repo apparaît dans l'arbre, déplié, avec ses éventuels types d'éléments déjà définis dans son propre `schema.yaml` (repo existant) ou vide (nouveau repo).
5. Si le clone échoue (URL invalide, branche introuvable, réseau) : message d'erreur inline, le `polenta-repo.yaml` n'est pas modifié (opération atomique).

### UC-3 — Ajouter une interface

Action "+ Ajouter une interface", disponible sur n'importe quel repo de l'arbre.

**Formulaire :** repo (URL git), nom (nom de montage), rôle(s) joués par le repo courant, version implémentée.

**Comportement :**
1. Mêmes étapes 1–3 que UC-2 (le repo interface est cloné comme une dépendance ordinaire).
2. En plus : ajoute une entrée `{ interface: nom, version, roles }` dans `implements:` du `schema.yaml` du repo **sur lequel l'action a été lancée** (pas celui de l'interface).
3. Si le repo interface est déjà présent dans le workspace (ajouté par un autre composant) : pas de nouveau clone, seule l'entrée `implements` est ajoutée/complétée.
4. Le nouveau repo apparaît dans l'arbre avec le badge "Interface".

### UC-4 — Ajouter un élément (type d'objet)

Action "+ Ajouter un élément" (exigence / test / campagne), disponible sur n'importe quel repo de l'arbre — reprend le menu déroulant existant de l'onglet Éléments actuel.

**Comportement :**
1. Crée un `ObjectTypeDefinition` vide (mêmes valeurs par défaut qu'aujourd'hui : statuts par défaut selon la catégorie) dans le `schema.yaml` du repo choisi.
2. Ouvre immédiatement la popup de configuration (UC-5) sur ce nouvel élément.
3. Validation à l'enregistrement : le `prefix` doit être unique sur l'ensemble du workspace (tous repos confondus, pas seulement le repo édité) — cf. règle CLAUDE.md #10, étendue au périmètre multi-repo.

### UC-5 — Configurer un élément (popup)

Cliquer sur un élément existant dans l'arbre, ou juste après sa création (UC-4), ouvre une popup modale contenant exactement les champs de l'`ObjectTypeCard` actuel :
- Nom (identifiant), Label affiché, Préfixe ID, Couleur
- Tableau des champs (`FieldsTable`)
- Tableau des statuts (`StatusesTable`), absent pour la catégorie `campaign`
- Note d'aide spécifique aux tests (étapes Action/Résultat) reprise à l'identique

**Comportement :**
- Bouton Enregistrer (actif si modifications), bouton Annuler / Echap (confirmation si modifications en attente — même pattern que `CancelConfirmModal`).
- Enregistrer écrit dans le `schema.yaml` du repo auquel appartient l'élément (peut être un repo dépendance, cf. décision "Édition cross-repo").
- Bouton Supprimer (confirmation), repris de `ConfirmDelete`.

### UC-6 — Retrait de la route `/workspace`

- La route `/workspace` est supprimée. Le bouton "Conformité interfaces" et la logique de résolution de conflit diamond (`DiamondConflictModal`) sont déplacés/accessibles depuis le nouvel onglet Structure.
- Un conflit diamond détecté lors d'un rebuild (déclenché par UC-2/UC-3, ou à l'ouverture du projet) affiche la même modale bloquante qu'aujourd'hui, dans le contexte de l'onglet Structure.

## Critères d'acceptation

### CA-1 — Arbre de structure
- [ ] L'onglet Structure remplace les onglets Composants et Éléments dans `routes/schema.tsx`.
- [ ] L'arbre affiche le repo courant, ses dépendances (composants/interfaces, récursif) et les types d'éléments de chaque repo.
- [ ] Un repo interface affiche le badge visuel distinct (violet).
- [ ] Un projet mono-repo sans workspace actif affiche uniquement le repo courant et ses éléments, sans erreur.

### CA-2 — Ajout composant
- [ ] Ajouter un composant avec repo/label/branche valides écrit une entrée dans `polenta-repo.yaml` et cache un repo cloné apparaissant dans l'arbre.
- [ ] Un nom de montage déjà utilisé par une URL différente est rejeté avec un message explicite avant toute écriture.
- [ ] Un échec de clone (réseau, branche introuvable) n'altère pas `polenta-repo.yaml` et affiche une erreur inline.

### CA-3 — Ajout interface
- [ ] Ajouter une interface clone le repo (si absent) ET ajoute une entrée dans `implements:` du repo courant avec `{ interface, version, roles }`.
- [ ] Ajouter une interface déjà présente dans le workspace (via un autre composant) n'effectue pas de second clone.
- [ ] Le repo ajouté affiche le badge "Interface" dans l'arbre.

### CA-4 — Ajout et configuration d'un élément
- [ ] Ajouter un élément sur n'importe quel repo de l'arbre crée un `ObjectTypeDefinition` dans le `schema.yaml` de ce repo et ouvre la popup de configuration.
- [ ] La popup reprend à l'identique les champs de l'`ObjectTypeCard` actuel (nom, label, préfixe, couleur, champs, statuts).
- [ ] Un `prefix` déjà utilisé ailleurs dans le workspace (tous repos confondus) est rejeté à l'enregistrement avec un message explicite.
- [ ] Cliquer sur un élément existant dans l'arbre rouvre la popup pré-remplie.

### CA-5 — Édition cross-repo
- [ ] Un élément appartenant à un repo dépendance (pas le repo courant) est éditable et enregistrable depuis cette même popup, en écrivant dans le `schema.yaml` du repo concerné.

### CA-6 — Retrait de `/workspace`
- [ ] La route `/workspace` n'est plus accessible ; toute navigation existante vers elle est redirigée vers l'onglet Structure du projet concerné.
- [ ] La résolution de conflit diamond et la matrice de conformité restent accessibles depuis le nouvel onglet.

### CA-7 — Aucune régression
- [ ] Les onglets Liens et Interfaces de `routes/schema.tsx` fonctionnent à l'identique (aucune modification de comportement).
- [ ] Les projets existants avec plusieurs `SystemNode` locaux sans repo (créés avant ce ticket) restent lisibles : ils sont affichés en lecture seule dans l'arbre avec une indication qu'ils doivent être migrés (pas de suppression silencieuse de données).

## Cas limites à gérer

| Cas | Comportement attendu |
|-----|---------------------|
| Ajout composant/interface sur un projet jamais initialisé en workspace plat | Proposer l'initialisation du workspace (réutilise le flux `workspace:init` existant) avant de poursuivre l'ajout |
| Conflit diamond déclenché par un ajout (même URL, pin différent d'une dépendance déjà présente ailleurs) | Modale bloquante identique à celle de `/workspace` avant de finaliser le clone |
| `prefix` dupliqué entre deux repos du workspace | Erreur à l'enregistrement de la popup élément, aucun des deux repos n'est modifié |
| Suppression d'un élément utilisé par des instances existantes (exigences/tests créés avec ce type) | Confirmation explicite ; les instances existantes ne sont pas supprimées, elles deviennent orphelines (comportement identique à l'existant, non traité par ce ticket) |
| Repo dépendance marqué `readonly` | La popup d'édition reste accessible en lecture seule ou masque le bouton Enregistrer — à trancher en Design |
| Nom de montage identique à un repo déjà présent mais URL différente | Conflit de nom (pas de version) → rejeté, message invitant à choisir un autre nom (cohérent avec le cas limite T69 équivalent) |
| Ancien projet avec `SystemNode` locaux multiples sans repo (pré-T70) | Affichés en lecture seule dans l'arbre, non éditables via ce nouvel onglet tant qu'ils n'ont pas été migrés vers de vrais repos dépendance (hors scope : outil de migration automatique) |

---

## Hors scope (ce ticket ne fait PAS)

- **Mise à jour du pin / branche d'une dépendance existante** et **suppression d'une dépendance** : non demandées par ce ticket, restent à spécifier séparément (UC-5 de T69 mentionnait déjà cette fonctionnalité comme non implémentée).
- **Migration automatique** des anciens `SystemNode` locaux sans repo vers de vrais repos dépendance.
- **Modification des onglets Liens et Interfaces** : comportement inchangé.
- **Renommage d'un repo dans l'arbre** (mount name) après ajout.
- **Résolution automatique de conflit diamond** : reprise telle quelle de T69 (notification + choix utilisateur, jamais automatique).
