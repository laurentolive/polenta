# T71 — Version d'interface implémentée dérivée du pin git

## Contexte

Un composant déclare, dans son `schema.yaml`, qu'il implémente une interface :

```yaml
implements:
  - interface: iface-can-bus   # nom de montage dans le workspace
    version: "2.1"              # saisi à la main — AUCUN lien avec le pin réel
    roles: [device]
```

Le champ `version` est une chaîne libre saisie par l'utilisateur (dans `AddDependencyModal.tsx` au moment du clonage, et dans l'onglet Interfaces de `schema.tsx` en édition directe). Il n'a aucun lien vérifié avec le `pin` (SHA/tag/branche) réellement épinglé pour le repo interface dans le workspace (`WorkspaceTreeNode.pin`, résolu via `polenta-repo.yaml`). Rien n'empêche cette valeur de diverger silencieusement de l'état git réel.

## Décision

La "version implémentée" n'est plus une donnée déclarée : c'est une donnée **dérivée** du pin git réel du repo interface tel que résolu dans l'arbre du workspace courant.

- Le champ `version` disparaît de `ImplementsDeclaration` (`packages/types/src/schema.ts`) et de `schema.yaml` (`implements: [{interface, roles}]`, sans `version`).
- Partout où la version implémentée est affichée, elle est calculée à la volée : on cherche le `WorkspaceTreeNode` dont le `name` correspond à `implements[i].interface`, et on affiche son `pin` brut (SHA court / tag / branche, tel que déclaré — pas de résolution vers un tag le plus proche).
- Si le mount n'est pas résolu dans l'arbre courant (interface non clonée / composant consulté hors workspace), afficher un état "non résolu" plutôt qu'une valeur périmée.

## Composants legacy / versions divergentes

Deux composants du même workspace peuvent légitimement implémenter des versions différentes de la même interface (ex: un composant legacy sur l'interface v1.0, un composant récent sur la v2.1 rétrocompatible). Ce cas est **déjà couvert** par le mécanisme existant de diamond-conflict + `MountOverride` :

- Si deux repos déclarent des pins différents pour la même URL d'interface, Polenta le signale déjà comme un conflit à résoudre (`DiamondConflictModal.tsx`).
- La résolution par l'utilisateur (monter le repo interface deux fois sous deux noms distincts via `MountOverride`) **est** l'acte d'acceptation explicite de la coexistence des deux versions — pas de nouveau mécanisme de calcul de rétrocompatibilité à construire.
- Chaque composant pointe simplement `implements[i].interface` vers le nom de mount correspondant à la version qu'il implémente réellement.

T71 ne modifie donc pas la logique de détection de diamond-conflict ni `MountOverride` — il ne fait que retirer la déclaration manuelle de version et la remplacer par une lecture du pin résolu.

## Hors scope

- La revalidation automatique (`needsRevalidation`) quand le pin de l'interface change (upgrade) : la logique de conformité (`interface-compliance.service.ts`) reste inchangée. Un futur ticket pourra étudier le déclenchement d'une revalidation quand le pin d'une interface bouge.
- Toute évolution de la détection de diamond-conflict ou de `MountOverride`.
- L'onglet Interfaces / Liens au sens large — seul le champ `version` de la déclaration `implements` est concerné.

## Comportement attendu

1. **Création d'une interface** (`AddDependencyModal.tsx`, flux "+ Interface" de l'onglet Structure) : le champ "version implémentée" est retiré du formulaire. Seuls repo / nom / branche (pin de clonage) / rôles restent. Le clonage + l'entrée `implements` (sans `version`) sont créés comme aujourd'hui.
2. **Édition d'une déclaration `implements`** (onglet Interfaces, `schema.tsx`) : le champ de saisie libre `version` est retiré. La version affichée pour chaque déclaration est en lecture seule, dérivée du pin du mount correspondant.
3. **Arbre Structure** : le badge/affichage de version sur un nœud composant implémentant une interface montre le pin résolu (lecture seule), pas de champ éditable.
4. **Matrice de conformité** : l'en-tête ou la légende affichant la version de l'interface implémentée par un composant montre le pin résolu.
5. **Composant avec interface non résolue** (mount absent de l'arbre courant, ex. interface pas encore clonée) : affichage explicite "non résolu" — pas de valeur en cache, pas de crash.
6. **Deux composants du même workspace implémentant des pins différents de la même URL d'interface** : fonctionne déjà via le flux diamond-conflict/MountOverride existant, chacun affiche le pin de son propre mount.

## Critères d'acceptation

- [x] `ImplementsDeclaration` n'a plus de champ `version` (type + schéma YAML)
- [x] `AddDependencyModal.tsx` (flux interface) ne demande plus de version implémentée
- [x] L'onglet Interfaces (`schema.tsx`) n'a plus de champ de saisie libre pour la version ; affiche le pin résolu en lecture seule
- [x] La version affichée dans l'arbre Structure et dans la matrice de conformité correspond au pin résolu du mount de l'interface, pas à une valeur saisie — **sans objet** : ni l'arbre Structure ni la matrice de conformité n'affichaient de version avant T71 (vérifié en sprint1), rien à faire évoluer à ces deux endroits
- [x] Une interface non résolue dans l'arbre courant affiche un état explicite "non résolu" (pas de crash, pas de valeur périmée)
- [x] Deux composants du workspace pinnant des versions différentes de la même interface passent par le flux diamond-conflict/MountOverride existant sans régression
- [x] Aucune régression sur `interface-compliance.service.ts` (logique de conformité par rôles/liens inchangée)

## Hors scope explicite (rappel)

- Revalidation automatique sur changement de pin d'interface
- Détection/calcul de rétrocompatibilité entre versions d'interface
- Modification de la logique de diamond-conflict / MountOverride
