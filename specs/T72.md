# T72 — Vue système : parcourir et éditer n'importe quel repo du workspace depuis le projet racine

## Contexte

Depuis T69 (workspace plat), un projet est composé du repo racine ouvert + des dépendances
déclarées dans `polenta-repo.yaml` (composants et interfaces), résolues récursivement par
`WorkspaceTreeService` et exposées à plat dans `WorkspaceTree.nodes`.

L'onglet **Structure** (T70) sait déjà parcourir tout cet arbre : il liste chaque repo du
workspace et, sous chacun, ses types d'éléments (`ObjectTypeDefinition`) comme feuilles.

La **vue Système** (`SystemViewContext.tsx`), elle, n'a pas été mise à jour pour ce modèle :

```ts
const { data: project } = useQuery({
  queryFn: () => api.workspace.resolve(decodeProjectId(currentProjectId)),
})
const repoPath = project?.localPath ?? ''       // toujours la racine
const { data: schema } = useProjectSchema(repoPath)
const nodes = schema?.nodes ?? []               // toujours schema.nodes de la racine
```

`repoPath` est figé sur la racine du projet ouvert. Le combobox **Composant** (`SystemPanel.tsx`)
liste `nodes`, c'est-à-dire uniquement les `SystemNode` locaux du repo racine (typiquement un
seul nœud `root`). Les dépendances du workspace (ex. `iface-bus-uart`, `comp-controller`,
`comp-sensor`, `HMI`, `BMS`) n'y apparaissent jamais — impossible d'y créer, lister ou éditer
une exigence/test/campagne sans ouvrir ce repo comme projet Polenta indépendant.

`SPEC-SYSTEM-VIEW.md` documente encore l'ancien modèle ("Combobox Composant — Liste les
composants (SystemNodes) du projet") : à mettre à jour en sprint final.

La route `/components` (`?component=`) existe mais réutilise le même `SystemViewContext` sans
resélectionner de `repoPath` — c'est un reliquat pré-T69 ("kept for backwards compat but no
longer used" dans le code), pas un mécanisme cross-repo fonctionnel.

## Décision

Le combobox **Composant** de la vue Système liste désormais les **repos du workspace** (racine
+ toutes les dépendances récursives, à plat — même liste que l'arbre Structure), pas seulement
les `SystemNode` locaux du repo racine. Sélectionner un repo dans ce combobox recharge tout le
contexte (schéma, arbre, index requirements/tests, liens) sur **son propre** `repoPath`.

## Comportement attendu

### 1. Combobox Composant

- Liste à plat tous les repos de `WorkspaceTree.nodes` (racine comprise), dans l'ordre du DFS
  déjà produit par `WorkspaceTreeService.buildWorkspaceTree`.
- Libellé de chaque entrée : `<mount name>` + le `label` du premier `SystemNode` de son propre
  schema.yaml si présent (ex. `comp-controller — Contrôleur (maître bus UART)`), sinon le mount
  name seul.
- En mode mono-repo (pas de workspace, `workspace.detect` → `'repo'`) : liste réduite à un seul
  élément (le repo courant), comportement inchangé par rapport à aujourd'hui.
- Un repo sans `.polenta/schema.yaml` (ex. `BMS` dans le cas actuel) utilise le schéma par
  défaut (`DEFAULT_SCHEMA`, un nœud `root` sans objectTypes) → combobox Élément affiche
  `Aucun élément configuré`, comme le prévoit déjà l'état vide documenté dans
  `SPEC-SYSTEM-VIEW.md`. Aucun traitement spécial requis.

### 2. Résolution du `repoPath` effectif

- `repoPath` n'est plus systématiquement `project.localPath` : il devient
  `selectedRepoNode.repoPath`, résolu depuis `WorkspaceTree.nodes` par mount name.
- Tout ce qui dépend actuellement de `repoPath` dans `SystemViewContext` (schéma, arbre
  `TypeTree`, index requirements/tests, création/édition d'objets, liens) continue de
  fonctionner sans changement d'API — seul l'input `repoPath` change de source.
- `RequirementsIndexService` / `TestsIndexService` sont déjà keyés par `repoPath` (Map interne)
  → aucun changement requis côté cache, le changement de repo sélectionné recharge naturellement
  le bon index.

### 3. Persistance de la sélection (URL)

- Un nouveau paramètre d'URL (ex. `repoName`) est ajouté à côté de `componentId`/`typeId`
  existants, pour retenir **quel repo du workspace** est sélectionné (distinct du `SystemNode`
  local sélectionné à l'intérieur de ce repo).
- Absent de l'URL → défaut sur le repo racine (rétro-compatible avec les liens existants qui ne
  connaissent pas ce paramètre).
- Changement de repo sélectionné → réinitialise la sélection Élément au premier type disponible
  dans ce repo (même règle que le changement de Composant aujourd'hui).

### 4. Droits d'édition selon le pin

- Un repo dont le `pin` (dans `polenta-repo.yaml`) résout vers une **branche locale existante**
  (vérifiée via `git.listBranches`, pas seulement le pattern regex SHA) reste éditable.
- Un repo dont le `pin` résout vers un **tag** ou un **SHA** (pas de branche locale
  correspondante) passe en **lecture seule** dans la vue Système : création/édition/suppression
  désactivées, action visible mais désactivée avec message explicite (ex. "Ce composant est figé
  sur une baseline — passez sur une branche pour l'éditer").
- Le repo racine du projet ouvert reste toujours éditable (jamais concerné par un `pin`).
- C'est à la charge de l'utilisateur de configurer le `pin` d'un composant sur une branche s'il
  veut pouvoir l'éditer depuis cette vue — aucune UI de changement de pin n'est ajoutée par ce
  ticket (existe déjà via l'onglet Structure / `AddDependencyModal`).

### 5. Liens vers un autre repo

- Une exigence/test peut continuer de porter un lien (`ObjectLink`) dont la cible vit dans un
  autre repo du workspace (ex. `implements-interface` de `comp-controller` vers
  `iface-bus-uart`) — ce mécanisme existe déjà et n'est pas modifié.
- **Hors périmètre** (voir ci-dessous) : résoudre et afficher le **titre** de l'objet cible
  quand il vit dans un autre repo. La section Liens de `EditView` affiche l'ID brut de la cible
  distante (ex. `ITF-005`) sans résolution de titre cross-repo, comme c'est déjà implicitement
  le cas aujourd'hui pour un ID inconnu du repo courant.

## Critères d'acceptation

- [ ] Depuis `polenta-prj2` ouvert comme projet, le combobox Composant liste `polenta-prj2`,
      `HMI`, `BMS`, `iface-bus-uart`, `comp-controller`, `comp-sensor` (tous les repos du
      workspace, à plat).
- [ ] Sélectionner `comp-controller` recharge le combobox Élément avec ses propres types
      (`exigence-fw` / `test-fw`), affiche l'arbre de ses propres exigences (`CTRL-001`…),
      et permet de créer/éditer un objet qui s'écrit dans `comp-controller/requirements/`
      (pas dans le repo racine).
- [ ] Ouvrir `CTRL-001` dans la vue Édition affiche sa section Liens avec le lien
      `implements-interface → ITF-005` existant (ID brut, pas de titre résolu).
- [ ] Naviguer avec l'URL retenant `repoName=comp-controller&componentId=root&typeId=exigence-fw`
      rouvre le bon repo/composant/type après rechargement de l'app.
- [ ] Un lien vers un projet ouvert AVANT ce ticket (sans `repoName` dans l'URL) continue de
      fonctionner et affiche le repo racine par défaut.
- [ ] Un repo mono-repo (pas de workspace) affiche un combobox Composant à une seule entrée,
      comportement inchangé.
- [ ] Un composant dont le `pin` est un tag/SHA (ex. test avec `comp-controller` pinné sur un
      tag) affiche la vue Système en lecture seule pour ce repo (pas de bouton création/édition
      actif) ; repinné sur une branche, l'édition redevient possible sans redémarrage de l'app
      (après rebuild de l'arbre workspace).
- [ ] `BMS` (repo sans `.polenta/schema.yaml`) sélectionné dans le combobox affiche
      `Aucun élément configuré` sans erreur.

## Hors scope explicite

- Résolution et affichage du **titre** d'un objet cible d'un lien quand il vit dans un autre
  repo (reste un ID brut). Nécessiterait un index global ID → repo sur tout le workspace ;
  ticket futur si besoin.
- Autocomplete cross-repo dans `LinkCombobox` pour **créer** un nouveau lien vers un objet d'un
  autre repo (les candidats restent scopés au repo courant, comme aujourd'hui).
- Changement de `pin` (branche/tag/SHA) depuis la vue Système — reste gérable uniquement via
  l'onglet Structure / `AddDependencyModal`, inchangé par ce ticket.
- Drag & drop entre composants (déjà explicitement hors scope dans `SPEC-SYSTEM-VIEW.md`).
- Mise à jour de la route `/components` en tant que telle : ce ticket unifie la sélection de repo
  dans `SystemViewContext`, ce qui rend `/components` et `/product` équivalents pour la
  sélection de repo ; la suppression éventuelle de la route dupliquée est laissée à un ticket de
  nettoyage séparé pour ne pas mélanger renommage de routes et nouvelle fonctionnalité.
