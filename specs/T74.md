# T74 — Éditer / retirer un composant ou une interface existant dans l'arbre Structure

## Contexte

`StructureTab.tsx` (T70) permet aujourd'hui, pour chaque repo de l'arbre workspace :
- de renommer/décrire son `SystemNode` local (`NodeEditModal` — label + description uniquement,
  ne touche pas à `polenta-repo.yaml`) ;
- d'y **ajouter** un composant ou une interface enfant (`AddDependencyModal` → `addDependency`
  / `addInterfaceImplementation` dans `lib/workspaceActions.ts`).

Il n'existe **aucune UI pour modifier ou retirer une dépendance déjà déclarée**. Concrètement,
pour un repo de l'arbre autre que la racine (un `WorkspaceTreeNode` avec un `url` non vide), on
ne peut aujourd'hui :
- ni changer son `pin` (branche/tag/SHA) une fois ajouté,
- ni changer les rôles qu'un composant déclare jouer pour une interface,
- ni le retirer de l'arbre,
- ni renommer son mount name.

Fait notable découvert en explorant le code existant : `addDependency()` (déjà écrite, T70) gère
**déjà** le cas "entrée existante avec le même `name`+`url` mais un `pin` différent" — elle
corrige l'entrée en place au lieu d'en ajouter une seconde (`lib/workspaceActions.ts:52-53`,
commentaire *"correcting an existing entry's pin"*). Éditer la branche d'une dépendance
existante est donc déjà supporté **côté logique** ; il ne manque que l'UI pour y accéder en mode
édition (pré-remplie) plutôt qu'en mode création (vide).

## Décisions (validées avec l'utilisateur)

1. **Retrait du disque** : optionnel, via case à cocher explicite dans la confirmation de
   retrait. Par défaut, seule la référence dans `polenta-repo.yaml` est retirée — le dossier
   cloné reste sur disque, non référencé par l'arbre. Cocher "supprimer aussi le dossier local"
   déclenche en plus une suppression physique du répertoire.
2. **Renommage du mount name** : autorisé, avec mise à jour en cascade de tous les
   `implements[].interface` du workspace qui référencent l'ancien nom, plus renommage physique
   du répertoire cloné et mise à jour de l'entrée `name` chez le(s) parent(s) qui la déclarent.
3. **Retrait d'une interface** : retire automatiquement la déclaration `implements` correspondante
   du composant parent qui l'avait ajoutée (évite une référence pendante vers un mount qui
   n'existe plus).

## Comportement attendu

### 1. Édition (branche / rôles / renommage)

- Nouvelle action sur chaque `RepoRow` non-racine (icône crayon à côté du nom du repo, distincte
  de celle qui édite déjà le `SystemNode` local) : ouvre une modale d'édition pré-remplie avec
  les valeurs actuelles (`url` en lecture seule — changer l'URL d'une dépendance existante n'est
  pas un "edit", c'en est une nouvelle ; `name`, `branch`, et pour une interface `roles`).
- Modifier la branche uniquement : réutilise `addDependency()` telle quelle (déjà idempotente sur
  "même name+url, pin différent" → corrige en place).
- Modifier les rôles (interface) : met à jour l'entrée `implements[].roles` correspondante dans
  le schéma du parent (nouvelle logique, symétrique à l'ajout dans `addInterfaceImplementation`
  mais en `update` plutôt qu'en `push`).
- Renommer le mount name : voir §3 (sprint séparé, cf. Découpage).

### 2. Retrait

- Nouvelle action sur chaque `RepoRow` non-racine : bouton de suppression (réutilise le pattern
  `ConfirmDelete` déjà utilisé pour les nœuds orphelins), avec case à cocher "Supprimer aussi le
  dossier local" dans la confirmation.
- Retire l'entrée de `polenta-repo.yaml → dependencies[]` du **parent direct** uniquement (pas de
  cascade vers d'éventuels sous-repos — un sous-repo qui n'est plus atteignable depuis la racine
  disparaît naturellement de l'arbre reconstruit, sans action spécifique).
- Si le repo retiré est une interface : retire aussi l'entrée correspondante de
  `implements[]` dans le schéma du parent qui l'avait ajoutée.
- Si la case "supprimer le dossier local" est cochée : supprime physiquement le répertoire après
  succès de la mise à jour du manifeste (jamais avant, pour ne pas perdre le dossier si l'écriture
  du manifeste échoue).
- Rebuild de l'arbre après retrait (même mécanisme que l'ajout).

### 3. Renommage du mount avec cascade (découpage en sprint séparé — voir plus bas)

- Renomme physiquement le répertoire cloné (`fs.rename`).
- Met à jour `name` dans l'entrée `polenta-repo.yaml → dependencies[]` du parent direct.
- Parcourt tous les repos de l'arbre workspace et, pour chacun dont le schéma déclare
  `implements: [{interface: <ancien nom>, ...}]`, réécrit `interface` avec le nouveau nom.
- Cas non géré (documenté en hors-scope, pas bloquant) : un même repo (même URL+pin) monté sous
  deux noms différents via `MountOverride` (diamond conflict résolu) — renommer l'un des deux
  montages ne doit affecter que les références à CE montage précis, pas l'autre. Le mécanisme de
  cascade doit filtrer par mount name exact, jamais par URL seule.

## Critères d'acceptation

- [x] Éditer la branche d'un composant existant (ex. `main` → `v2.1`) sans le retirer/rajouter ;
      l'arbre se recharge avec le nouveau pin résolu.
- [x] **(Ajouté en sprint 1, découvert en vérification live)** Éditer vers une branche/tag
      invalide n'efface jamais le clone local existant — le repo n'est jamais recloné par-dessus
      lui-même, seulement `fetch()` puis `checkout()`. Voir S2ter de `T74-tests.md`.
- [ ] Éditer les rôles déclarés par un composant pour une interface ; la matrice de conformité
      reflète les nouveaux rôles après rebuild.
- [ ] Retirer un composant sans cocher "supprimer le dossier" : disparaît de l'arbre, le dossier
      cloné reste présent sur disque.
- [ ] Retirer un composant avec la case cochée : disparaît de l'arbre ET le dossier est supprimé
      du disque, mais seulement si le retrait de la référence a réussi.
- [ ] Retirer une interface : la déclaration `implements` correspondante disparaît du schéma du
      parent qui l'avait ajoutée.
- [ ] Renommer un mount (sprint 2) : le dossier est physiquement renommé, toutes les déclarations
      `implements[].interface` du workspace pointant vers l'ancien nom sont mises à jour, l'arbre
      se recharge correctement sous le nouveau nom.
- [ ] Renommer un mount partagé sous deux noms différents (diamond + `MountOverride`) ne modifie
      que les références au montage renommé, pas à l'autre montage de la même URL.

## Hors scope explicite

- Détection/prévention de la casse de liens (`ObjectLink`) inter-repos dont la cible vivrait dans
  un repo retiré — un lien `implements-interface` pointant vers un ID d'un repo retiré reste tel
  quel (déjà le comportement actuel pour un ID inconnu, cf. T72 §Hors scope résolution de titre
  cross-repo).
- Changer l'URL git d'une dépendance existante (équivaut à une nouvelle dépendance — retirer puis
  rajouter).
- Cascade de retrait vers les sous-dépendances d'un repo retiré (elles disparaissent simplement de
  l'arbre reconstruit si plus aucun chemin ne les atteint depuis la racine).
- Renommage automatique de fichiers/dossiers référençant l'ancien mount name en dehors de
  `polenta-repo.yaml` et `schema.yaml → implements[]` (ex. liens ObjectLink stockés par ID
  d'objet, pas par mount name — non concernés).
- **(Découvert pendant le sprint 1)** Éditer les rôles déclarés par un composant pour une
  interface qui n'est **pas son parent direct dans l'arbre** — ex. un composant dont
  `implements[].interface` pointe vers une interface montée ailleurs dans le workspace (cas
  possible du modèle de données, illustré par `polenta-prj2` où `comp-controller`/`comp-sensor`
  déclarent leurs rôles pour `iface-bus-uart` sans que celle-ci soit leur enfant direct). Le champ
  Rôles de la modale d'édition n'agit que sur la relation "le parent direct déclare implémenter
  cet enfant interface", symétrique à ce que fait déjà "+ Interface" à l'ajout. Éditer un
  `implements[]` "libre" (déclaré indépendamment de la position dans l'arbre) nécessiterait de
  choisir parmi potentiellement plusieurs relations — hors périmètre, ticket futur si besoin.

## Découpage en sprints

**Sprint 1 — Édition (branche/rôles) + retrait, sans renommage**
Réutilise `addDependency()` existante pour la branche ; nouvelle logique minimale pour éditer
`implements[].roles` et pour retirer une entrée de `dependencies[]` (+ suppression disque
optionnelle, + nettoyage `implements` pour une interface retirée). Aucun nouveau canal IPC pour
la branche/rôles (déjà couvert par `polentaRepo.save`/`schema.save`) ; un nouveau canal
`fs:remove-dir` (ou équivalent) est nécessaire pour la suppression physique optionnelle.

**Sprint 2 — Renommage du mount avec cascade**
Nécessite un nouveau canal IPC pour le renommage physique de répertoire, plus la logique de
parcours de l'arbre pour réécrire les références `implements[].interface`. Isolé en sprint séparé
car c'est la partie la plus risquée (opération disque non triviale, cas diamond/MountOverride à
ne pas casser) — sprint 1 doit rester livrable et utile indépendamment.
