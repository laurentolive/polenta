# T76 — Stocker les images de richtext comme fichiers référencés (comme les diagrammes draw.io)

## Contexte

`T47` a établi (décision D4 de `CONTEXT.md`) que les diagrammes draw.io insérés
dans un champ `richtext` sont des **références à un fichier `.drawio` du repo**
(`diagrams/`, chemin relatif + `nodeId` optionnel), jamais du XML embarqué inline.

Les images, elles, utilisent l'extension standard `@tiptap/extension-image`
(`ResizableImageExtension.ts`) et sont stockées en **base64 inline** dans le
Markdown :
- Collage presse-papiers (`RichTextField.tsx`, `handlePaste`) :
  `FileReader.readAsDataURL(blob)` → insertion directe d'un `data:...;base64,...`
- Bouton toolbar "Insérer une image" (`handleInsertImage` + IPC
  `dialog:pick-image-file`) : le fichier choisi est lu sur disque et renvoyé en
  base64 (`{ mimeType, base64 }`), jamais conservé comme chemin de fichier.
- `T75` a ajouté un bloc fenced ```` ```image ```` (JSON `{src, width, height,
  crop}`) pour porter les métadonnées de redimensionnement/rognage, mais `src`
  y reste un data URI base64.

Cette divergence cause un gonflement du repo Git (données binaires dupliquées
à chaque édition) et diffère du modèle documentaire déjà annoncé dans
`SPEC-REQ-requirements.md` §3.2 ("images via URL") et dans `CLAUDE.md`. Ce
ticket aligne le stockage des images sur le modèle fichier déjà en place pour
les diagrammes draw.io.

## Décisions (validées avec l'humain avant rédaction de cette spec)

1. **Dossier de stockage** : un nouveau dossier `images/` à la racine du repo
   (produit ou composant), miroir exact de `diagrams/` pour les `.drawio`. Une
   image collée ou choisie via le sélecteur de fichier y est copiée si elle ne
   s'y trouve pas déjà (même logique que `api.drawio.pickFile`, qui copie un
   fichier externe dans `diagrams/`).
2. **Pas de migration du contenu existant** : les images déjà stockées en
   base64 inline (avant ce ticket, y compris les blocs ```` ```image ```` de
   T75 avec crop) ne sont pas converties automatiquement. Décision explicite de
   l'humain : leur perte est acceptable. Aucun script de migration, aucune
   conversion silencieuse à l'ouverture/sauvegarde n'est demandé par ce ticket.
3. **Sérialisation** : le bloc ```` ```image ```` introduit par T75 garde
   exactement son schéma JSON actuel (`src`/`width`/`height`/`crop`) — seule la
   sémantique de `src` change : un chemin relatif (ex. `images/photo-01.png`)
   au lieu d'un data URI. La syntaxe Markdown standard `![alt](src)` reste
   utilisée tant qu'aucun `width`/`height`/`crop` n'est défini (règle déjà
   posée par T75, désormais `src` y est aussi un chemin relatif).

## Comportement attendu

### Insertion (édition, `RichTextField.tsx`)

1. Coller une image depuis le presse-papiers : au lieu d'encoder en base64,
   les octets de l'image sont écrits dans un nouveau fichier sous `images/` du
   repo courant. Nom généré (pas de nom de fichier source disponible pour un
   clipboard paste) : horodatage + extension déduite du type MIME
   (`png`/`jpg`/`gif`/`webp`). Le nœud `image` inséré référence ce chemin
   relatif comme `src`.
2. Bouton toolbar "Insérer une image" : le fichier sélectionné via le picker
   est copié dans `images/` du repo courant s'il ne s'y trouve pas déjà (même
   logique que `api.drawio.pickFile` pour les `.drawio`), en conservant son nom
   d'origine. En cas de collision de nom avec un fichier déjà présent dans
   `images/`, un suffixe garantit l'unicité (ex. `photo-01-2.png`).
3. Nouvelle méthode IPC (remplace ou complète `dialog:pick-image-file`) qui
   copie le fichier choisi dans `<repo>/images/` et retourne le chemin relatif,
   au lieu de lire et encoder le fichier en base64.

### Rendu (lecture et édition)

4. `RichTextViewer.tsx` et `RichTextField.tsx` affichent une image référencée
   en la lisant depuis le disque via IPC (même principe que `api.drawio.read`
   pour l'aperçu des diagrammes), et non plus en décodant un data URI stocké
   inline.
5. Fichier image référencé introuvable (chemin invalide, fichier supprimé,
   submodule non résolu) → état d'erreur explicite inline, cohérent avec le
   comportement déjà défini pour un diagramme draw.io introuvable (`T47`) —
   jamais de rendu vide silencieux ni de crash de l'éditeur.

### Remplacement de fichier (menu contextuel, `T75`)

6. L'action "Remplacer le fichier" du menu contextuel copie le nouveau fichier
   choisi dans `images/` (même logique de collision qu'au point 2) et met à
   jour `src` avec le nouveau chemin relatif, en conservant position,
   dimensions et crop du bloc. L'ancien fichier référencé n'est pas supprimé
   automatiquement du disque (cohérent avec le comportement drawio existant).

## Cas limites

- Deux insertions successives du même fichier externe (même image choisie
  deux fois depuis le picker) : dédupliquer (réutiliser la copie déjà
  présente dans `images/`) ou créer une nouvelle copie à chaque insertion —
  détail technique laissé à `T76-design.md`.
- Nom de fichier collé/copié en conflit avec un fichier `images/` existant →
  suffixe garantissant l'unicité (cf. point 2), jamais d'écrasement silencieux.
- Fichier référencé situé hors du repo courant (chemin absolu, ou submodule
  non cloné dans le workspace) → état "introuvable", cohérent avec le point 5.
- Copier-coller d'un bloc image entre champs richtext (même repo ou repo
  différent) → la référence de fichier est copiée telle quelle (même fichier
  partagé), pas de duplication — même comportement que pour un bloc drawio
  copié (`T47`).
- Aucun repo/dossier de travail ouvert au moment du collage/insertion → même
  comportement de repli que celui déjà existant pour l'insertion d'un diagramme
  draw.io dans ce cas (à reprendre tel quel, pas de nouveau cas à inventer).

## Hors scope explicite

- Migration ou script de conversion des images déjà stockées en base64 (cf.
  Décision 2) — perte acceptée, aucune action de ce ticket dessus.
- Nouveau type de champ standalone `image` (comme le champ `drawio` autonome
  existant) — ce ticket ne touche que l'embed richtext (`ResizableImage` /
  bloc ```` ```image ````), pas le modèle de données `SchemaField`.
- Compression, redimensionnement automatique ou limite de taille du fichier
  source à l'insertion — non demandé.
- Suppression automatique du fichier physique dans `images/` lors de l'action
  "Supprimer" le bloc (menu contextuel `T75`) ou lors d'un remplacement d'image
  — cohérent avec le comportement drawio existant (le fichier référencé n'est
  jamais supprimé automatiquement du disque).
- Export Word/Excel (`T43`) tenant compte du changement de stockage — aucun
  changement attendu côté export (il consomme déjà le rendu, pas le stockage
  brut).

## Critères d'acceptation

- [ ] Coller une image depuis le presse-papiers dans un richtext crée un
      fichier dans `images/` du repo courant ; le document stocké ne contient
      pas de data URI base64 pour cette insertion
- [ ] Le bouton toolbar "Insérer une image" copie le fichier sélectionné dans
      `images/` (s'il n'y est pas déjà) et insère une référence par chemin
- [ ] Le bloc ```` ```image ```` conserve son schéma JSON existant
      (`src`/`width`/`height`/`crop`) ; `src` contient désormais un chemin
      relatif
- [ ] La syntaxe `![alt](chemin)` est utilisée quand aucun `width`/`height`/
      `crop` n'est défini (cohérent avec la règle posée par `T75`)
- [ ] `RichTextViewer.tsx` et `RichTextField.tsx` affichent l'image en lisant
      le fichier référencé sur disque, pour tout contenu nouvellement inséré
- [ ] Un fichier image référencé introuvable affiche un état d'erreur inline
      explicite, sans crash de l'éditeur
- [ ] "Remplacer le fichier" (menu contextuel `T75`) copie le nouveau fichier
      dans `images/` et met à jour la référence en conservant position,
      dimensions et crop
- [ ] Deux fichiers copiés/collés avec un nom identique dans `images/` ne
      s'écrasent pas (suffixe garantissant l'unicité)
- [ ] Aucune migration automatique n'est appliquée aux images déjà stockées en
      base64 avant ce ticket (comportement non garanti pour ce contenu ancien,
      décision assumée)
