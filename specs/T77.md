# T77 — Dashboards personnalisables par requêtes façon SQL

**Statut** : specifying
**Branche** : T77
**Worktree** : `../polenta-T77/`

---

## Description fonctionnelle

Ajouter un système de **dashboards personnalisables** : l'utilisateur construit une requête sur les champs des objets du projet (exigences, tests, campagnes...) — via un query builder guidé par `schema.yaml`, ou en SQL avancé pour les cas non couverts par le builder — et choisit un type de représentation (widget/chart) pour le résultat. Un dashboard est une collection de ces widgets.

Trois cas d'usage sont prioritaires pour ce ticket :
1. **Couverture de test** — quelles exigences sont couvertes par des tests, à quel niveau (`CoverageStatus` existant : `pass` / `fail` / `blocked` / `not_run` / `needs_revalidation`).
2. **Avancement** — répartition des exigences/tests par statut (`draft`/`review`/`approved`/...), par domaine, dans le temps.
3. **Maturité des définitions** — proportion d'exigences respectant les règles de cohérence du projet (voir § Critères de maturité).

Remplace l'actuel "Tableau de bord" de la page Projet (`project.$id.tsx` : StatCards, répartitions domaine/statut/priorité, récemment modifiées), qui est **retiré sans reprise** — aucune migration automatique de son contenu vers les nouveaux widgets.

## Moteur de requête

- **AlaSQL** (ou équivalent : SQL exécuté directement sur des tableaux JS, sans moteur de stockage). Pas de SQLite, pas de base applicative — cohérent avec `CONTEXT.md` décision D1 ("pas de base de données applicative") et `SPEC.md` §5 ("Index en mémoire reconstruit depuis le working tree").
- Les requêtes s'exécutent sur l'**index en mémoire** déjà reconstruit depuis les fichiers du working tree (frontmatters + `tree.yaml`) — jamais persisté sur disque, jamais commité.
- **Périmètre des données** : repo courant **+ composants submodules agrégés** (arbre complet représenté par `tree.yaml`), pour permettre des dashboards transverses (ex : couverture de test cross-composant, avancement produit global).
- Deux modes d'accès :
  - **Query builder guidé** : sélection de type d'objet (`objectTypeRef`), champs, opérateurs, valeurs, combinables en ET/OU — présente uniquement les champs valides pour le(s) type(s) choisi(s) selon `schema.yaml`.
  - **Mode SQL avancé** : zone de texte SQL libre pour les requêtes non couvertes par le builder (jointures multiples, sous-requêtes...). Lecture seule sur l'index — aucun risque d'intégrité, aucune mutation possible via ce mode.

---

## Vue "Requêtes"

- Éditeur de requête avec bascule entre les deux modes (builder / SQL avancé).
- Zone de résultat : table du résultat de la requête courante.
- Bouton **Exporter en Excel** sur le résultat courant (réutilise l'infrastructure d'export existante, cf. `SPEC.md` §2.4 / T43).
- Bouton **Sauvegarder** la requête courante (titre + portée privée/partagée au moment de la sauvegarde).
- Liste **"Requêtes sauvegardées"** : filtrable dynamiquement par texte (titre + contenu de la requête), indique la portée (icône privé/partagé) de chaque entrée.
- Liste **"Historique"** : chaque exécution de requête (builder ou SQL) y est enregistrée automatiquement.
  - Toujours **privé** — jamais partageable, même si la requête source est une requête partagée.
  - Filtrable dynamiquement par texte, comme la liste des sauvegardées.
  - Purge automatique des entrées devenues invalides (référencent un champ/type supprimé du schéma depuis) — pas de plafond numérique arbitraire, l'auto-nettoyage plus le filtre texte suffisent à garder la liste utilisable.
  - Suppression manuelle unitaire via une petite croix sur chaque entrée.
- Cliquer sur une entrée (sauvegardée ou historique) recharge la requête dans l'éditeur (builder ou SQL selon son mode d'origine), pour voir le résultat actuel ou l'ajuster.
- Une requête sauvegardée peut ensuite être utilisée comme source d'un widget dans la vue Dashboard.

---

## Vue "Dashboard"

- Grille de widgets à **tailles prédéfinies** (ex. petit / moyen / large), réordonnable par drag & drop (même pattern que l'`ElementTree` de la vue Système). Pas de redimensionnement libre en pixels (cf. Hors scope).
- Bouton **"Ajouter un widget"** → popup de configuration :
  - Titre du widget
  - Sélecteur de requête : si le dashboard courant est **privé**, propose toutes les requêtes de l'utilisateur (privées + partagées) ; si le dashboard est **partagé**, ne propose **que les requêtes déjà partagées** (filtre proactif — jamais de validation d'erreur après coup).
  - Type de widget (barres, camembert, courbe, tuile KPI, table…) — **choix libre, non contraint par la forme du résultat de la requête**. L'utilisateur reste juge de la pertinence du type choisi.
  - Mapping des champs du résultat vers les rôles attendus par le widget (catégorie/mesure/série pour un chart, colonnes affichées pour une table, champ unique pour une tuile KPI…).
  - **Aperçu live** du chart pendant la configuration, avec le résultat réel de la requête sélectionnée — permet à l'utilisateur de voir immédiatement si la combinaison type/données est lisible et d'ajuster lui-même, sans contrainte imposée par l'outil.
- Chaque widget est sauvegardé (portée héritée du dashboard parent, cf. § Visibilité ci-dessous).
- Le dashboard lui-même est sauvegardable avec un titre et une portée privée/partagée.

---

## Visibilité : privé / partagé

Trois types d'entités concernées, chacune privée ou partagée : **Requête**, **Widget**, **Dashboard**.

- Un **Widget** ne peut être partagé que si sa **Requête** source est partagée.
- Un **Dashboard** ne peut être partagé que si **tous** ses widgets sont partagés (et donc, par transitivité, toutes leurs requêtes).
- **Promotion** privé → partagé : libre à tout moment pour une Requête ; pour un Widget, nécessite que sa requête soit déjà partagée (sinon le flux propose de partager la requête d'abord) ; pour un Dashboard, nécessite que tous ses widgets soient déjà partagés.
- **Rétrogradation** partagé → privé : **bloquée** si l'objet a des dépendants partagés (ex. une Requête partagée utilisée par un Widget partagé ne peut pas repasser privée). Le blocage affiche la liste des dépendants à traiter d'abord (même logique que pour la suppression, ci-dessous).
- **Suppression** d'une Requête utilisée par au moins un Widget : **bloquée**, avec la liste des Widgets/Dashboards dépendants affichée, pour permettre à l'utilisateur de lever les dépendances avant de supprimer.
- **Stockage** :
  - Partagé → fichier(s) YAML versionnés dans le repo (ex. `dashboards/*.yaml`, `queries/*.yaml` — un fichier par objet, même logique anti-conflit que les reviews).
  - Privé → préférence locale utilisateur (même mécanisme que la visibilité des colonnes, `api.pref`), jamais committé.
  - L'historique de requêtes est toujours dans le stockage privé, sans exception.

## Panneau latéral

- Deux sections séparées : **"Dashboards"** et **"Requêtes"** (pas d'arbre mixte — actions différentes selon le type d'objet).
- Chaque section : liste réorganisable par drag & drop (même pattern que l'`ElementTree` de la vue Système), avec un bouton d'ajout dédié.
- Clic sur un dashboard → ouvre la vue Dashboard correspondante. Clic sur une requête → ouvre la vue Requêtes avec cette requête chargée dans l'éditeur.

## Critères de maturité (dashboard "maturité des définitions")

Basé sur les règles de cohérence de `CLAUDE.md` déjà en vigueur dans le projet. Une exigence est considérée "mature" si :
- Tous les champs `required: true` de son type sont remplis
- Le champ `statement` respecte la syntaxe EARS
- Au moins un critère d'acceptance mesurable est présent
- Si `status: approved` → au moins un lien `verification` vers un test
- Aucun lien la concernant n'a `needsRevalidation: true`

Le dashboard doit permettre de voir : taux de maturité global, par domaine, et la liste des exigences non conformes avec le(s) critère(s) manquant(s).

*(Le détail exact du calcul — champ par champ, requête AlaSQL correspondante — sera précisé en phase Design.)*

## Critères d'acceptation

- [ ] Un utilisateur peut créer une requête via le query builder guidé (type d'objet, champs, opérateurs, combinaison ET/OU) sans écrire de SQL
- [ ] Un utilisateur peut basculer en mode SQL avancé et écrire une requête SQL exécutée sur l'index en mémoire
- [ ] Le résultat de la requête courante peut être exporté en Excel
- [ ] Une requête peut être sauvegardée (titre + portée privée/partagée)
- [ ] La liste des requêtes sauvegardées et la liste d'historique sont filtrables dynamiquement par texte
- [ ] L'historique est toujours privé, ses entrées invalides sont purgées automatiquement, et chaque entrée est supprimable individuellement via une croix
- [ ] Cliquer sur une requête sauvegardée ou une entrée d'historique recharge la requête dans l'éditeur adapté à son mode d'origine
- [ ] Un widget peut être ajouté à un dashboard via une popup (titre, requête, type de widget libre, mapping des champs) avec aperçu live du chart
- [ ] Le type de widget n'est jamais restreint par la forme du résultat de la requête
- [ ] Ajouter un widget à un dashboard partagé ne propose, dans le sélecteur de requête, que des requêtes déjà partagées
- [ ] Partager un widget est impossible si sa requête est privée ; partager un dashboard est impossible si un seul de ses widgets est privé
- [ ] Repasser en privé une requête ou un widget partagé est bloqué s'il a des dépendants partagés, avec la liste des dépendants affichée
- [ ] Supprimer une requête utilisée par au moins un widget est bloqué, avec la liste des widgets/dashboards dépendants affichée
- [ ] Un dashboard "couverture de test" pré-configuré est fourni en exemple/template, basé sur `CoverageStatus`
- [ ] Un dashboard "avancement" pré-configuré montre la répartition par statut et par domaine
- [ ] Un dashboard "maturité" montre un taux global + liste des exigences non conformes avec critère manquant
- [ ] Les requêtes portent sur le repo courant ET les composants submodules agrégés (`tree.yaml`)
- [ ] Le panneau latéral présente deux sections séparées (Dashboards / Requêtes), chacune réorganisable par drag & drop
- [ ] Les widgets sont disposés en grille à tailles prédéfinies, réordonnable ; pas de redimensionnement libre en pixels
- [ ] Le nouvel onglet latéral apparaît dans l'`ActivityBar`
- [ ] Le "Tableau de bord" actuel de `project.$id.tsx` est retiré, sans widget de reprise automatique
- [ ] Aucune requête (builder ou SQL avancé) ne peut muter les données — lecture seule sur l'index

## Hors scope T77

- Redimensionnement libre des widgets en pixels (`react-grid-layout` ou équivalent) — grille à tailles prédéfinies seulement pour ce ticket
- Partage/duplication d'un widget entre plusieurs dashboards — un widget appartient au dashboard dans lequel il est créé
- Export des dashboards complets (PDF/Excel) — cf. logique d'export existante (`SPEC.md` §2.4), à traiter dans un ticket dédié si besoin
- Alertes / notifications basées sur seuils de dashboard
- Requêtes planifiées / rafraîchissement automatique en tâche de fond
- Historique/versioning des résultats de dashboard dans le temps (snapshots)
- Promotion automatique en cascade (ex. partager un dashboard ne partage pas automatiquement ses widgets/requêtes privés à sa place — l'utilisateur doit le faire explicitement au préalable)
