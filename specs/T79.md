# T79 — Baseline multi-composant

## Contexte

`baseline.tsx` crée aujourd'hui une baseline en posant un tag git sur le seul repo root
(`api.baseline.create(repoPath, { tag: mainTag, components: [] })`) : le champ `components` est
systématiquement envoyé vide, et `workspaceDir` n'est jamais transmis à l'appel.

Côté main process, le chaînon est en réalité **à moitié câblé** (T69 sprint 3,
`ipc/index.ts` `baseline:create`) :

```ts
ipcMain.handle('baseline:create', async (_e, repoPath, dto, workspaceDir?) => {
  await c.sync.createTag(repoPath, dto.tag)
  if (workspaceDir) {
    const tree = await c.workspaceTree.readCache(workspaceDir)
    if (tree) {
      for (const node of tree.nodes) {
        if (node.repoPath === repoPath) continue
        await c.sync.createTag(node.repoPath, dto.tag)   // même nom de tag que le root
      }
    }
  }
  const record = { tag: dto.tag, createdAt: ..., components: dto.components.map(...) }
  return c.baseline.create(repoPath, record)
})
```

Ce handler sait déjà taguer tous les repos du workspace **si on lui passe `workspaceDir`** — mais
`baseline.tsx` ne le fait jamais, donc en pratique seul le root est tagué et
`BaselineRecord.components` reste toujours `[]`. C'est ce chaînon qu'il faut fermer.

**Précision sur le type mentionné dans le ticket** : le ticket cite `BaselineComponentSnapshot`
(`packages/types/src/baseline.ts`). Ce type — et tout le fichier `baseline.ts` de
`packages/types` qui l'entoure (`Baseline`, `BaselineStats`, `BaselineDiff`...) — est **mort** :
réexporté depuis `packages/types/src/index.ts` mais jamais importé nulle part ailleurs dans le
code. Le type réellement utilisé par le flux vivant (`baseline.service.ts`,
`packages/api-client/src/types.ts`) est `BaselineComponentRecord` / `CreateBaselineComponentDto` /
`BaselineRecord` — beaucoup plus simple (juste `name`/`tag`, pas de `commitSha`/stats). C'est ce
second type qu'il faut alimenter ; l'agent Design ne doit pas chercher à faire vivre
`BaselineComponentSnapshot`.

**Dépendance T78** (mergé) : le panneau Version liste déjà tous les repos du workspace via
`useWorkspaceStructure(workspaceDir, repoPath)` → `flatNodes` (root + composants + interfaces, à
plat, dédupliqué) et interroge déjà `api.sync.status(repoPath)` par repo (branche courante,
fichiers stagés/non stagés). T79 réutilise ce même hook et cette même query dans `baseline.tsx`,
qui n'a aujourd'hui aucune notion du workspace multi-repo.

**Branche d'intégration par repo** : chaque repo du workspace (root ou composant) est un projet
Polenta autonome (cf. `CLAUDE.md`) avec son propre `config/project.yaml` et son propre champ
`integrationBranch` (cf. `ActionService.readIntegrationBranch`, `repoPath`-scoped, fallback
`'main'` si absent). **Aucun endpoint renderer n'expose ce champ aujourd'hui** — seul le main
process (`ActionService`) le lit, pour son propre usage interne. Un nouvel endpoint est
nécessaire pour que l'UI puisse construire, avant tentative de création, la liste des repos qui
ne sont pas sur leur branche d'intégration.

## Description fonctionnelle

### Validation bloquante avant création

Avant d'autoriser la création d'une baseline, résoudre pour **chaque repo du workspace**
(`flatNodes` de `useWorkspaceStructure`, root inclus) :

- son `integrationBranch` configuré (nouvel endpoint, lecture `config/project.yaml` du repo)
- son état git courant via `api.sync.status(repoPath)` (déjà exposé) : `branch`, `staged`,
  `unstaged`

Un repo est **en défaut** si `status.branch !== integrationBranch` OU
`staged.length + unstaged.length > 0`.

S'il existe au moins un repo en défaut :
- le bouton "Créer la baseline" est désactivé
- la liste des repos en défaut est affichée, avec la raison pour chacun (mauvaise branche
  courante avec la branche attendue vs actuelle, ou modifications en attente) — reprend le
  pattern d'avertissement déjà présent dans `baseline.tsx` (messages rouge/ambre sous le champ de
  tag)

Cas mono-repo (pas de composant, `flatNodes` ne contient que le root) : comportement inchangé,
seul le root est vérifié.

### Contenu créé

Un tag de **même nom** (celui saisi pour le root, ex. `v1.2.0`) est posé sur chaque repo du
workspace, chacun à sa propre HEAD (`sync.createTag(repoPath, tag)` sans `commitSha` résout déjà
HEAD du repo ciblé — aucun changement requis côté `sync.service.ts`).

`baseline.tsx` doit :
1. Charger l'arbre workspace via `useWorkspaceStructure(workspaceDir, repoPath)`, comme le fait
   déjà `VersionPanel`
2. Construire `dto.components` à partir des nœuds hors-root :
   `{ name: node.name, tag: mainTag, createTag: true }` pour chacun
3. Appeler `api.baseline.create(repoPath, dto, workspaceDir)` — le troisième paramètre
   `workspaceDir` existe déjà dans la signature du handler main process mais n'est aujourd'hui
   jamais transmis par l'appelant

### Vérification d'unicité du tag étendue à tout le workspace

Aujourd'hui, `baseline.tsx` vérifie que le tag choisi n'existe pas déjà **sur le root uniquement**
(`mainTags.includes(mainTag)` via `api.sync.tags(repoPath)` du root, et
`baselines.some(b => b.tag === mainTag)`). Cette vérification doit être étendue : le tag choisi ne
doit exister sur **aucun** repo du workspace avant de permettre la création — avertissement
listant le(s) repo(s) où le tag existe déjà si c'est le cas.

### Affichage

`BaselineItem` dans `baseline.tsx` affiche déjà le détail par composant d'une baseline dépliée
(nom + tag, cf. lignes 55–70 actuelles) — aucun changement requis ici, il cessera simplement de
recevoir une liste toujours vide.

## Hors scope

- Comparaison de baselines multi-composant (diff) — reste scopé au root, non traité ici
- Consultation en lecture seule d'une baseline (naviguer "dans" une baseline comme dans l'état du
  projet à ce moment) — hors scope, non implémenté à ce jour, indépendant de T79
- Pruning des tags orphelins sur les repos composants — `BaselineService.list()` ne vérifie
  aujourd'hui l'existence du tag que sur le root (`tagExists(repoPath, b.tag)`) ; laisser tel
  quel, ne pas étendre le pruning aux composants dans ce ticket
- Renommage de nomenclature de branches `prj-`/`tck-` → `int-`/`dev-` — déjà fait (T81, archivé)
- Propagation de pin, workflow "Publier" (T82, T83) — indépendants de la création de baseline

## Critères d'acceptation

1. Dans un workspace avec au moins un composant, la page Baseline liste tous les repos du
   workspace et leur état (branche courante vs branche d'intégration configurée, propre/en
   attente) avant toute tentative de création
2. Si un ou plusieurs repos ne sont pas sur leur branche d'intégration configurée, ou ont des
   modifications en attente (stagées ou non), la création est bloquée et ces repos sont listés
   avec la raison
3. Une fois tous les repos conformes, créer une baseline pose un tag de même nom sur le root et
   sur chaque composant/interface du workspace, chacun à sa propre HEAD
4. La baseline créée est listée avec `components` non vide (nom + tag par composant), visible en
   dépliant l'élément dans la colonne "Baselines existantes"
5. La vérification d'unicité du tag choisi couvre tous les repos du workspace, pas seulement le
   root
6. Cas mono-repo (pas de composant) : comportement inchangé (aucune régression), un seul repo
   vérifié et tagué
7. Si un composant échoue à être tagué après que la validation bloquante a pourtant validé son
   état (cas rare, ex. modification concurrente hors app pendant la création) — comportement
   actuel du handler conservé : log + continue, la baseline est quand même créée avec le composant
   en échec absent de `components` (à documenter clairement dans l'UI en phase Design plutôt que
   de faire échouer toute la création)
