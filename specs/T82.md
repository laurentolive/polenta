# T82 — Le checkout/commit d'un composant réécrit le pin en cascade dans les `polenta-repo.yaml` amont

## Contexte

Le panneau Version (T78) permet de changer la branche/tag courant(e) d'un composant ou
d'une interface directement depuis l'arbre multi-repo, via le `BranchCombobox` de
[VersionRepoFolder.tsx](../apps/desktop/src/renderer/components/sidebar/version/VersionRepoFolder.tsx)
(`checkoutMutation` → `api.sync.checkoutBranch(repoPath, name)`). Ce checkout n'agit
aujourd'hui que sur le repo du composant lui-même : il change ce qui est physiquement
coché sur disque, mais ne touche jamais le `pin` déclaré pour ce composant dans le
`polenta-repo.yaml` du repo parent qui le référence comme dépendance
(`dependencies: [{ name, url, pin }]`). Le `pin` du parent reste donc périmé — le
prochain rebuild de l'arbre workspace (`WorkspaceTreeService.buildTree`) le détecterait
comme désynchronisé (`repoExistsAtPin` renverrait `false`) et tenterait de re-checkouter
le composant sur son ancien pin, annulant silencieusement le choix de l'utilisateur.

T78 avait explicitement exclu ce sujet de son périmètre :
> « Écriture du pin dans `polenta-repo.yaml` du parent lors d'un checkout de composant
> (T82) » — [T78.md](T78.md) §Hors scope.

Le mécanisme d'écriture existe déjà côté renderer : `addDependency()` dans
[workspaceActions.ts](../apps/desktop/src/renderer/lib/workspaceActions.ts) sait déjà
« corriger le pin d'une entrée existante » (cas utilisé aujourd'hui par le flux d'ajout
de composant/interface, T70) et rebuild l'arbre ensuite. T82 réutilise ce mécanisme
existant, à deux déclencheurs différents détaillés ci-dessous.

**Élargissement de périmètre (validé après la première version de cette spec)** : le
ticket initial ne couvrait que la mise à jour du pin dans le parent **direct**, et
n'ajoutait pas de checkout par commit. Les deux sont désormais en scope :
1. le panneau Version gagne un moyen de checkouter un composant/interface sur un commit
   (SHA) arbitraire, pas seulement une branche/tag ;
2. la mise à jour du pin se propage en cascade au-delà du parent direct, vers les
   grands-parents et au-delà, jusqu'à la racine — voir §Déclencheur 2.

## Description fonctionnelle

### Déclencheur 1 — Checkout d'un composant (branche, tag, ou commit)

Le `BranchCombobox` de `VersionRepoFolder` gagne une option **"Checkout un commit…"**
(à côté de "Nouvelle branche…", dans le pied fixe de la liste déroulante) : un champ de
saisie d'un SHA, validé côté client par `api.sync.resolveRefs(repoPath)` ou un simple
format hexadécimal, qui appelle `api.sync.checkoutCommit(repoPath, sha)` — déjà exposé et
utilisé par la vue Historique (root-only) mais jamais câblé pour un composant. Ce nouveau
chemin suit les mêmes règles de confirmation que le checkout de branche/tag existant
(garde de modifications en attente → `checkoutConfirm`).

Après un checkout **réussi** (branche, tag, **ou commit** désormais) d'un nœud de l'arbre
Version : le `pin` de l'entrée correspondante (`dependencies[].name` == nom de montage du
nœud) est réécrit, avec la référence tout juste checkoutée (nom de branche, nom de tag, ou
SHA complet pour un commit), dans le `polenta-repo.yaml` de **chaque repo du workspace qui
déclare ce nœud comme dépendance** — dans l'immense majorité des cas un seul repo (son
parent direct dans l'arbre affiché), mais potentiellement plusieurs pour une dépendance
partagée (ex. une interface requise par deux composants). C'est le même mécanisme de
recherche que celui du déclencheur 2 (cascade) ci-dessous, appliqué une seule fois avec la
réf checkoutée comme valeur. Le repo **root** n'est déclaré comme dépendance nulle part —
son checkout ne trouve donc jamais de repo à mettre à jour, sans cas particulier à coder.

- Si la référence checkoutée est identique au `pin` déjà déclaré dans un repo dépendant,
  aucune écriture n'a lieu pour celui-ci (pas de modification fantôme dans
  Stage/Modifications).
- L'écriture se fait par une simple modification du fichier `polenta-repo.yaml`, déjà
  suivi par git dans le(s) repo(s) dépendant(s) — **aucun stage ni commit automatique**.
  La modification apparaît dans les sections Stagés/Modifications de ce(s) dossier(s)
  dans le panneau Version, exactement comme une modification de fichier manuelle
  (l'utilisateur reste maître de la stager/committer/annuler).
- Annuler cette modification (bouton "Annuler" sur `polenta-repo.yaml` dans les
  Modifications du parent) restaure l'ancien pin — comportement natif de `discard`, rien
  à coder spécifiquement.

### Déclencheur 2 — Commit d'un repo qui a lui-même un ou plusieurs parents (cascade)

Le déclencheur 1 met à jour le pin du parent direct au moment du checkout, sans qu'un
commit soit nécessaire (le HEAD du composant checkouté existe déjà, c'est un commit
existant). Mais **cette écriture elle-même** rend le parent direct "sale" : tant qu'il
n'est pas committé, son propre HEAD ne change pas, donc son grand-parent éventuel n'a
rien de valide à pointer. La cascade vers les grands-parents ne peut donc se déclencher
qu'au moment où ce parent est lui-même **committé** — peu importe si ce commit contient
la mise à jour de pin du déclencheur 1 ou toute autre modification.

Règle générale, appliquée à **tout commit réussi** dans **tout repo de l'arbre
workspace** (bouton "Committer" existant dans `VersionRepoFolder`, quel que soit son
contenu) :

- Si le repo tout juste committé est déclaré comme dépendance (`dependencies[]`, matché
  par `name` + `url`) dans le `polenta-repo.yaml` d'un ou plusieurs **autres repos** du
  workspace courant (pas seulement son unique parent visuel dans l'arbre rendu — une
  interface partagée peut être dépendance de plusieurs composants), le nouveau HEAD SHA
  du repo committé est proposé comme `pin` dans le(s) `polenta-repo.yaml` de **chacun**
  de ces repos.
- Cette proposition suit exactement les mêmes règles que le déclencheur 1 : simple
  écriture de fichier (pending modification, jamais de stage/commit automatique), no-op
  si le pin est déjà à jour, erreur distincte si l'écriture échoue (le commit source, lui,
  a réussi), rollback + avertissement si un diamond-conflict est détecté au rebuild.
- **Récursivité** : si l'un de ces repos "ancêtres" est ensuite committé à son tour (à
  tout moment, indépendamment, par une action utilisateur distincte), le même mécanisme
  se redéclenche pour SES propres parents dans l'arbre, et ainsi de suite jusqu'à la
  racine. Chaque niveau de la cascade est une modification en attente indépendante :
  l'utilisateur peut committer le niveau 1 aujourd'hui et laisser le niveau 2 en attente
  indéfiniment — aucune obligation de "tout committer d'un coup".
- Committer le repo **root** ne déclenche aucune cascade (aucun repo du workspace ne le
  référence comme dépendance).
- Si le repo committé n'est référencé par aucun autre `polenta-repo.yaml` du workspace
  (cas courant — la plupart des commits sont des modifications d'exigences/tests sans
  rapport avec un pin), rien ne se passe : ce n'est pas un commit qui déclenche
  systématiquement une écriture, seulement un commit dans un repo qui a un ou des
  parents connus dans l'arbre actuellement ouvert.

### Échec de l'écriture du pin

Le checkout git (déclencheur 1) ou le commit (déclencheur 2) a déjà réussi quand
l'écriture du pin est tentée. Si cette écriture échoue (ex: `polenta-repo.yaml` du
parent verrouillé/illisible), c'est signalé à l'utilisateur comme une erreur **distincte**
de celle du checkout/commit (qui, lui, a réussi) — ne pas afficher un échec sur l'action
qui a en réalité abouti.

### Diamond conflict potentiel

`addDependency()` rebuild l'arbre après avoir écrit le pin et, si le rebuild remonte un
`diamond-conflict` (un autre repo du workspace référence la même URL avec un pin
différent), **annule (rollback) l'écriture** — comportement déjà existant, réutilisé tel
quel, aux deux déclencheurs. Dans ce cas, l'action source (checkout ou commit) reste
valide sur disque, mais le `pin` du repo amont concerné n'a pas changé : l'utilisateur en
est averti (pas d'échec silencieux) et invité à résoudre le conflit de montage (mécanisme
existant, `DiamondConflictModal`) avant que l'état ne redevienne cohérent. T82 ne modifie
pas la résolution de diamond conflict elle-même.

## Hors scope

- Stage ou commit automatique d'un `polenta-repo.yaml` modifié, à **quelque niveau que ce
  soit** de la cascade — reste toujours une action manuelle de l'utilisateur, à chaque
  niveau indépendamment
- Déclenchement de la cascade spécifiquement depuis le flux "Publier" (T83,
  dev-\*/Publier) avec un réglage de granularité configurable dans la vue Projet (option
  globale vs par lien parent/enfant, approbation manuelle d'intégrateur) — c'est le sujet
  propre de **T85**, qui dépend désormais aussi de T82 : T85 ajoutera une couche de
  configuration par-dessus le mécanisme de cascade "au commit" fourni ici (par ex.
  désactiver la proposition automatique pour certains liens, ou exiger une validation
  explicite avant même qu'elle apparaisse comme modification en attente)
- Résolution de diamond conflict — mécanisme existant (`DiamondConflictModal`),
  simplement respecté (rollback) si déclenché par ces écritures
- Changement de comportement de `WorkspaceTreeService`/`addDependency` — réutilisés tels
  quels
- Adaptation de la vue Historique (`graph.tsx`) au multi-repo — le nouveau checkout par
  commit vit dans le panneau Version (`BranchCombobox`), pas dans `graph.tsx`

## Critères d'acceptation

1. Checkout d'une branche sur un composant (nœud non-root) dans le panneau Version →
   le `pin` de son entrée dans `dependencies[]` du `polenta-repo.yaml` du parent direct
   est mis à jour avec le nom de la branche
2. Checkout d'un tag sur un composant → même comportement, `pin` = nom du tag
3. Le `BranchCombobox` d'un composant/interface (non-root) propose une option "Checkout
   un commit…" ; un SHA valide saisi et checouté avec succès met à jour le `pin` du
   parent direct avec ce SHA, au même titre qu'une branche/tag
4. Après un checkout (1/2/3), `polenta-repo.yaml` du parent apparaît dans Modifications
   (non stagé) du dossier parent — pas de commit automatique, pas de stage automatique
5. Checkout vers la réf déjà pinnée (no-op fonctionnel) → aucune écriture, aucune entrée
   nouvelle dans Modifications
6. Checkout du repo root → aucune écriture de pin (pas de parent)
7. Committer des modifications stagées dans un repo qui est référencé comme dépendance
   par un ou plusieurs autres repos du workspace propose, pour chacun d'eux, la mise à
   jour de son `pin` vers le nouveau HEAD SHA du repo committé — en Modifications non
   stagées, jamais committée automatiquement
8. Cette cascade est récursive : committer ensuite l'un de ces repos "ancêtres" propose à
   son tour la mise à jour dans SES propres parents, jusqu'à la racine
9. Committer le repo root, ou un repo qu'aucun autre repo du workspace ne référence, ne
   déclenche aucune proposition de pin (comportement inchangé, pas de bruit)
10. "Annuler" une modification de pin proposée (à n'importe quel niveau) restaure
    l'ancien pin (`discard` standard, non spécifique à T82)
11. Si une écriture de pin échoue après un checkout/commit réussi, un message d'erreur
    distinct de celui du checkout/commit est affiché ; l'action source reste effective
12. Si une écriture de pin déclenche un diamond-conflict, le pin visé n'est pas modifié
    (rollback existant) et l'utilisateur est averti que l'action source a réussi mais que
    le pin n'a pas pu être mis à jour

## Note technique pour la phase Design

Les deux déclencheurs partagent le **même mécanisme de recherche** : retrouver, parmi
`flatNodes` (tous les repos du workspace courant, cf. `useWorkspaceStructure`), ceux dont
le `polenta-repo.yaml` déclare une dépendance `{ name, url }` correspondant au repo
concerné (checkouté ou committé), puis y réécrire le `pin`. `WorkspaceTree.logicalTree` /
`nodes[].children` ne suffisent **pas** pour ça : la construction de l'arbre (dédup via un
`visited` global dans `WorkspaceTreeService.buildWorkspaceTree`) n'attache chaque nœud qu'à
un seul parent visuel, même si plusieurs repos le déclarent réellement comme dépendance —
il faut donc lire chaque manifest (`api.polentaRepo.get`) plutôt que de s'appuyer sur la
forme déjà construite de l'arbre. Un seul balayage suffit dans les deux cas (pas de vraie
récursion à coder) : la « cascade » vers les grands-parents n'est pas un algorithme
récursif exécuté en une passe, elle émerge simplement du fait que le même hook se
redéclenche naturellement le jour où l'un des repos mis à jour est à son tour committé.

Ne pas câbler ce mécanisme sur `createBranch`/`createBranchAt` (crée et checkoute une
nouvelle branche sans changement de contenu) : le flux "Faire une modification" de T83
crée une branche `dev-*` à chaque déclenchement, et proposer un pin vers cette branche
éphémère (supprimée après "Publier") serait du bruit pur. Se limiter aux checkouts
explicites vers une réf existante (branche, tag, commit) via le panneau Version, et aux
commits qui font réellement avancer le contenu.
