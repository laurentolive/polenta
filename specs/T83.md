# T83 — Workflow simplifié de modification ("faire une modification" / "Publier")

## Contexte

Aujourd'hui, modifier une exigence impose à l'utilisateur standard de naviguer manuellement dans
le panneau Version (`VersionRepoFolder.tsx`) pour créer une branche, la checkout, puis revenir
éditer, puis re-naviguer pour stager et committer — aucune de ces étapes n'est reliée, et il
n'existe aucun bouton de merge dans l'UI vivante. `SystemViewContext`/`VersioningContext`
bloquent déjà l'édition tant que la branche courante est en lecture seule
(`isReadonly = branch.startsWith('int-')`, `VersioningContext.tsx:46`), mais rien ne guide
l'utilisateur vers l'action "créer une branche pour pouvoir éditer".

**Primitives déjà disponibles côté `SyncService`** (`apps/desktop/src/main/services/sync.service.ts`),
il n'y a pas de `BranchService`/`MergeService` séparé comme le décrit encore
`SPEC-FORKS-BRANCHES-BASELINES.md` §2 (fichier obsolète sur ce point, cf. Refs SPEC) :
- `createBranch(repoPath, name)` — crée + checkout (`sync.service.ts:466`)
- `stageAll(repoPath)` — équivalent `git add -A` (`sync.service.ts:203`)
- `commit(repoPath, message, author?)` — commit l'index courant, ne stage rien lui-même (`sync.service.ts:169`)
- `mergeInto(repoPath, fromBranch, intoBranch)` — merge sans checkout préalable de `intoBranch`,
  **déjà exposé en IPC (`sync:merge-into`) et déjà utilisé côté renderer** (`graph.tsx`, merge manuel
  entre branches arbitraires) mais jamais depuis un flux automatisé. C'est la primitive que
  "Publier" doit utiliser.
- `listBranches(repoPath)` classe déjà les branches par préfixe `int-`/`dev-` (T81).

**Mise à jour (T79 mergé depuis la rédaction initiale de ce spec) :** la lecture de "la" branche
d'intégration configurée d'un repo est désormais réellement câblée, pas seulement planifiée.
`GitService.getIntegrationBranch(repoPath)` existe (`git.service.ts:47-54`, lit
`config/project.yaml` → `integrationBranch`, fallback `'main'`), exposé en IPC
(`baseline:get-integration-branch`, `ipc/index.ts:341`) et côté renderer
(`api.baseline.getIntegrationBranch(repoPath)`, `packages/api-client/src/types.ts:333`).
`ActionService.readIntegrationBranch` délègue déjà à cette même méthode. **T83 réutilise cet
endpoint tel quel pour la lecture** — aucune deuxième implémentation à créer. Ce qui manque encore :
l'**écriture** (rien ne persiste jamais ce champ aujourd'hui) et la désignation, côté vue Projet,
de laquelle des branches `int-*` existantes est "la" branche configurée
(`IntBranchSelector`, `project.$id.tsx:54-150`, permet de créer/checkout des branches `int-*` mais
n'en désigne aucune comme cible canonique).

**Flux "Action" orphelin à supprimer.** Un flux quasi équivalent existe déjà dans le code
(`ActionService`, routes `/action/new` et `/action/$actionId`) : titre → branche → édition →
review → merge. Il n'est référencé par aucun lien de navigation dans l'app (routes mortes), utilise
un nommage de branche incompatible (`user/<login>/ACT-XXXX`, pas `dev-*`), et impose une review
approuvée avant merge — à l'opposé du "commit + merge automatique" demandé ici. Décision actée
avec l'utilisateur : **ce flux est supprimé dans le cadre de T83**, pas conservé ni adapté.

## Description fonctionnelle

### Élément d'UI contextuel "mode vue / mode édition"

Un élément persistant (bouton + indicateur de mode), placé dans le chrome de l'application
(à ancrer précisément en phase Design — candidat naturel : `AppLayout.tsx`, pour rester visible
quel que soit le panneau actif, contrairement à `SyncBar` qui n'est montée que sur la page
Projet). Il reflète l'état git du **repo concerné** :
- repo root par défaut (`VersioningContext`, déjà monté dès qu'un projet est ouvert) ;
- repo actuellement parcouru dans la vue Système/Produit quand cette vue est active
  (`SystemViewContext.repoPath`, déjà la source de vérité du "repo concerné" pour l'édition —
  aucune résolution nouvelle à construire, cf. le repoPath déjà propagé à `EditView`).

Deux états, déterminés en comparant la branche courante du repo concerné (`sync:status`) à sa
branche d'intégration configurée (nouvel endpoint de lecture, partagé avec T79) :

| État | Condition | Affichage |
|------|-----------|-----------|
| **Vue** (intégration) | branche courante === branche d'intégration configurée du repo | Bouton unique **"Faire une modification"** |
| **Édition** | branche courante commence par `dev-` | Boutons **"Publier"** + **"Annuler"**, indicateur de mode "Édition" |
| Autre (branche arbitraire, HEAD détaché, config absente) | — | Élément neutre/masqué — hors scope, pas un état que T83 doit gérer |

Un indicateur de mode (pastille/texte "Lecture" / "Édition") reste visible en permanence à côté du
bouton pour que l'utilisateur sache toujours dans quel mode il se trouve.

### Popup "Faire une modification"

1. Clic sur le bouton → popup avec un unique champ **Titre** (obligatoire, pas de description ni
   de champ optionnel — le ticket ne demande que le titre, à la différence du flux Action
   supprimé qui en demandait plus).
2. Validation :
   - dérive un nom de branche `dev-<slug-du-titre>` (algorithme de slug + gestion de collision —
     ex. suffixe numérique si le nom existe déjà — à détailler en phase Design)
   - `sync.createBranch(repoPath, nomBranche)` — crée et checkout depuis la branche d'intégration
     courante
   - ferme la popup ; l'élément d'UI bascule immédiatement en mode Édition
3. Le titre saisi est conservé (en mémoire, scope session) pour servir de message de commit par
   défaut à la publication — comportement de repli si le titre n'est plus disponible (ex. redémarrage
   de l'app en cours d'édition) à définir en phase Design (T83 n'introduit pas de fichier YAML de
   suivi de "modification" comme le faisait `ActionService` — chaque branche `dev-*` est sa propre
   trace via `git log`, pas de persistance applicative supplémentaire).

### Bouton "Publier"

1. `sync.stageAll(repoPath)`
2. Si rien à publier (aucun fichier stagé/modifié ET aucun commit d'avance sur la branche
   d'intégration) → bouton désactivé, pas d'action possible tant que l'utilisateur n'a rien changé
3. `sync.commit(repoPath, message)` — message par défaut = titre de la modification
4. `sync.mergeInto(repoPath, brancheDevCourante, brancheIntégrationConfigurée)`
5. **Succès** : checkout de la branche d'intégration, suppression de la branche `dev-*` locale
   (nettoyage, même logique que l'actuel `ActionService.merge` avant suppression), retour au mode
   Vue, rafraîchissement de l'état git affiché
6. **Échec (conflit)** : l'utilisateur reste sur sa branche `dev-*` (aucune perte de travail),
   notification simple ("quelqu'un a modifié les mêmes informations") avec un lien vers la vue
   Version en mode avancé pour résolution manuelle — T83 détecte et notifie, il n'implémente
   **aucune** résolution de conflit ni diff champ par champ (scope de T84). La détection de
   conflit elle-même reste aujourd'hui superficielle côté `SyncService` (`mergeInto` retourne
   `conflicts: []` sans détail sur `MergeConflictError`, cf. `sync.service.ts:518-521`) — suffisant
   pour un succès/échec binaire, pas pour le détail que T84 devra construire.

### Bouton "Annuler"

Action destructive : demande confirmation (reprend le pattern déjà utilisé pour l'abandon dans
l'ancien flux Action / la confirmation de checkout avec modifications en attente de
`VersionRepoFolder.tsx`). Une fois confirmé : rejette les modifications en attente, checkout de la
branche d'intégration configurée, suppression de la branche `dev-*` locale, retour au mode Vue.

### Configuration de la branche d'intégration (vue Projet)

Étend `IntBranchSelector` (`project.$id.tsx`) ou ajoute un contrôle adjacent : sélectionner/valider
une branche `int-*` persiste ce choix comme `integrationBranch` du repo dans son
`config/project.yaml` via un nouvel endpoint d'écriture (`GitService.setIntegrationBranch`,
symétrique du `getIntegrationBranch` déjà câblé par T79). Lecture via l'endpoint existant
(`api.baseline.getIntegrationBranch`) ; repli sur `'main'` si non configuré.

### Suppression du flux "Action"

Retrait complet, code mort et non atteignable depuis la navigation :
- `apps/desktop/src/main/services/action.service.ts`
- routes `action.new.tsx`, `action.$actionId.tsx` (+ entrée `routeTree.gen.ts` régénérée)
- handlers IPC `actions:*` (`ipc/index.ts`)
- types `Action`/`ActionStatus`/`CreateActionDto` (`packages/types`) s'ils ne sont pas utilisés
  ailleurs
- wiring dans `container.ts`

À vérifier en phase Design avant suppression : `action.$actionId.tsx` appelle
`api.reviews.getByAction(repoPath, actionId)` — si cette capacité de review-par-action est utilisée
ailleurs dans le code des Reviews, ne retirer que la partie flux Action/branche, pas
l'infrastructure Review générique.

## Hors scope

- Résolution de conflit de merge (T84) — T83 ne fait que détecter l'échec et notifier
- Propagation du pin vers les repos parents après Publier (T85)
- Push automatique vers le remote après Publier — reste une action manuelle séparée (bouton
  "Pousser" existant dans `SyncBar`)
- Une "modification" = un repo = une branche `dev-*` ; éditer simultanément plusieurs repos dans
  une seule modification n'est pas traité
- Historique/traçabilité applicative des modifications passées (pas de fichier YAML de suivi
  comme le faisait `ActionService` — l'historique git de la branche `dev-*` en tenait lieu avant
  suppression du commit de merge)
- Nettoyage exhaustif de `SPEC-FORKS-BRANCHES-BASELINES.md` au-delà des sections directement
  concernées par ce ticket (le fichier documente encore un modèle `BranchService`/`MergeService`
  jamais construit — correction ciblée en dernier sprint, pas une réécriture complète)
- Ancrage exact de l'élément d'UI dans le cas multi-repo avancé (plusieurs repos ouverts,
  changement de repo concerné pendant une édition en cours) au-delà du comportement décrit
  ci-dessus — affiné si besoin en phase Design

## Critères d'acceptation

1. Sur un repo dont la branche courante est la branche d'intégration configurée, un bouton
   "Faire une modification" est visible ; sur toute autre branche non `dev-*`, aucun bouton de ce
   flux n'apparaît
2. Cliquer sur "Faire une modification" ouvre une popup demandant uniquement un titre ; valider
   crée et checkout une branche `dev-<slug>` depuis la branche d'intégration courante, sans
   navigation supplémentaire requise de la part de l'utilisateur
3. Une fois la branche `dev-*` checkoutée, le bouton devient "Publier" + "Annuler", avec un
   indicateur visible du mode Édition
4. L'édition (création/modification d'exigences, tests…) est possible sur la branche `dev-*`,
   comme c'est déjà le cas aujourd'hui pour toute branche non-`int-*` (aucune régression sur
   `isReadonly`)
5. "Publier" sans aucune modification en attente est désactivé (rien à committer/merger)
6. "Publier" avec des modifications en attente : stage, commit (message = titre de la
   modification), merge automatique dans la branche d'intégration configurée, retour en mode Vue,
   branche `dev-*` locale supprimée
7. "Publier" en cas de conflit de merge : notification claire, aucune perte des modifications de
   l'utilisateur (reste sur `dev-*`), lien vers la vue Version en mode avancé
8. "Annuler" (après confirmation) : abandonne les modifications en attente, revient sur la branche
   d'intégration configurée, supprime la branche `dev-*` locale
9. La vue Projet permet de désigner, parmi les branches `int-*` existantes, laquelle est "la"
   branche d'intégration du repo ; ce choix est persisté dans `config/project.yaml` et relu à la
   prochaine ouverture du projet
10. Aucune trace résiduelle du flux Action orphelin (routes, service, handlers IPC, types) sauf
    l'infrastructure Review générique si elle est partagée ailleurs
11. TypeScript / lint : zéro nouvelle erreur
