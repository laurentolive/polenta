# T84 — Résolution de conflit au "Publier" : liste des fichiers en conflit + lien contextualisé vers la vue Version

## Contexte

T83 a déjà livré, en effet de bord de la gestion d'échec du bouton "Publier"
(`ModificationControl.tsx:121-123`), une notification générique ("Quelqu'un a modifié les mêmes
informations — résolution manuelle nécessaire.") et un bouton "Résolution manuelle (Version)" qui
navigue vers `/graph` sans paramètre de repo. Le ticket T84 tel que formulé dans `TICKETS.md`
("notifier simplement... et renvoyer vers la vue Version en mode avancé... pas de mergetool
simplifié dans ce périmètre") décrit donc, littéralement, un comportement déjà en place.

L'exploration du code pour ce spec a mis en évidence trois trous concrets derrière cette
notification, qui sont le véritable objet de T84 :

1. **`conflicts` n'est jamais peuplé.** `SyncService.merge`/`mergeInto` (`sync.service.ts:506-529`)
   attrapent `MergeConflictError` d'isomorphic-git et renvoient systématiquement
   `{ success: false, conflicts: [] }`, alors que l'erreur porte réellement
   `err.data.filepaths`/`bothModified`/`deleteByUs`/`deleteByTheirs`
   (`node_modules/isomorphic-git/index.js:3745-3757`). L'utilisateur n'a aujourd'hui aucune
   indication de **quels fichiers** sont en conflit.
2. **Le même bug existe dans le merge manuel de `graph.tsx`** (`graph.tsx:325,338` —
   `` `Conflits de merge : ${result.conflicts.join(', ')}` ``, qui affiche donc toujours "Conflits
   de merge : " suivi de rien), pour la même raison côté service.
3. **Le lien "Résolution manuelle (Version)" pointe vers `/graph`, qui est câblé en dur sur le repo
   root** (`graph.tsx:743` — `repoPath = project?.localPath ?? ''`, aucun paramètre `repo` dans
   `validateSearch`). Or "Publier" (T83) peut être déclenché sur un repo composant via `?repo=`
   (`useModificationMode`) — si le conflit survient sur un composant, ce lien renvoie
   silencieusement vers le graphe du root, pas du repo réellement en conflit. La vue qui, elle,
   accepte déjà un `repoPath`/`ref1`/`ref2` arbitraires est `/version-diff`
   (`version-diff.tsx:13-18`), pas `/graph`.

Point structurel à noter (contraint la suite, ne change pas le périmètre) : **isomorphic-git
n'écrit aucun marqueur de conflit sur disque** en cas d'échec de `git.merge()` — contrairement à
git natif, aucun fichier n'est laissé dans un état "conflicted" à éditer. Le seul chemin de
résolution manuelle réellement disponible avec les primitives existantes est : consulter la liste
des fichiers en conflit, comparer les deux versions via le diff de branche déjà existant
(`/version-diff`), éditer le fichier sur la branche `dev-*` pour réconcilier son contenu, committer,
relancer "Publier".

Ce spec a été validé avec l'utilisateur sur 3 points de périmètre (cf. Critères d'acceptation) :
lister les fichiers en conflit dans la notification, contextualiser le lien vers la vue Version
(repo + diff pré-sélectionnés plutôt qu'une navigation générique), et corriger au passage le même
bug de `conflicts` vide côté merge manuel de `graph.tsx`.

## Description fonctionnelle

### 1. Peuplement réel de `MergeResult.conflicts`

`SyncService.merge`/`mergeInto` extraient la liste des fichiers en conflit depuis
`MergeConflictError.data` (isomorphic-git) au lieu de retourner `conflicts: []`. Le type
`YamlConflict` existant (`base`/`ours`/`theirs`) n'est **pas** à peupler — il porte la vision
"mergetool champ par champ" hors périmètre de ce ticket (cf. Hors scope) ; le détail exact de la
représentation (liste de chemins, éventuellement distinguant modification/suppression) est laissé
à la phase Design, mais elle doit a minima porter le chemin relatif de chaque fichier en conflit.

### 2. Notification de `ModificationControl` : liste des fichiers

La popup "Publication impossible" (`ModificationControl.tsx:257-278`) affiche, sous le message
générique actuel, la liste des chemins de fichiers en conflit renvoyée par "Publier". Reste
générique si la liste est vide pour une raison quelconque (ne doit jamais bloquer l'affichage de la
notification elle-même).

### 3. Lien de résolution manuelle contextualisé

Le bouton "Résolution manuelle (Version)" navigue vers une vue Version **scopée au repo réellement
concerné** (celui résolu par `useModificationMode` — root ou composant via `?repo=`), pas
systématiquement le root. Candidat naturel identifié en exploration : `/version-diff` avec
`repoPath` = repo concerné, `ref1` = branche `dev-*` courante, `ref2` = branche d'intégration
configurée — ouvre directement le diff entre les deux branches en conflit, sans re-sélection
manuelle par l'utilisateur. Le choix exact de la route/des paramètres est affiné en phase Design si
`/version-diff` s'avère avoir ses propres limitations pour ce cas d'usage (ex. nécessite que le
repo composant soit déjà connu de `useWorkspaceStructure` au moment de la navigation).

### 4. Correctif partagé pour le merge manuel de `graph.tsx`

Le bouton de merge manuel existant (branches arbitraires, `graph.tsx:321-343`) consomme le même
`SyncService.merge`/`mergeInto` — il bénéficie automatiquement du correctif du point 1. Son message
d'erreur (`Conflits de merge : ${result.conflicts.join(', ')}`) affiche désormais la vraie liste au
lieu d'une liste vide ; pas de changement de comportement au-delà de cette correction.

## Hors scope

- **Mergetool champ par champ** (base/ours/theirs par champ YAML, choix de valeur, UI de
  résolution) — exclu explicitement par le libellé du ticket ("pas de mergetool simplifié dans ce
  périmètre"). Le type `YamlConflict` reste déclaré mais non peuplé ; sa suppression/simplification
  n'est pas non plus demandée (limiter le diff à ce qui sert ce ticket).
- **Écriture de marqueurs de conflit sur disque** ou toute autre assistance de résolution
  au-delà de lister les fichiers et faciliter l'accès au diff existant — isomorphic-git ne le
  permet pas nativement, et ce n'est pas la vision retenue pour T84 (contrairement à
  `SPEC-TECH-stack.md` §6 / `SPEC-FORKS-BRANCHES-BASELINES.md` §2.4, à corriger, cf. Refs SPEC).
- **Distinction fine des types de conflit** (modification des deux côtés vs suppression d'un côté
  `deleteByUs`/`deleteByTheirs`) dans l'UI — la liste de fichiers suffit pour ce périmètre ; le
  service peut capturer ces catégories mais l'UI n'a pas à les traiter différemment.
- **"Publier" multi-repo simultané** — toujours hors scope (repris de T83).
- **Nettoyage exhaustif des sections SPEC** au-delà de `SPEC-TECH-stack.md` §6 et
  `SPEC-FORKS-BRANCHES-BASELINES.md` §2.4, qui décrivent toutes deux la vision field-by-field comme
  "cible T84" — à corriger pour refléter le périmètre réellement livré (liste de fichiers + lien
  contextualisé), pas une réécriture plus large de ces fichiers.

## Critères d'acceptation

1. En cas d'échec de "Publier" (conflit de merge), `SyncService.merge`/`mergeInto` renvoient un
   `conflicts` non vide contenant le chemin relatif de chaque fichier réellement en conflit (plus
   jamais `conflicts: []` sur un échec de type `MergeConflictError`).
2. La notification affichée par `ModificationControl` après un "Publier" en échec liste ces chemins
   de fichiers, en plus du message générique existant.
3. Le bouton de résolution manuelle navigue vers une vue Version qui affiche effectivement le repo
   concerné (root ou composant, selon celui sur lequel "Publier" a échoué) — pas systématiquement
   le root — avec le diff entre la branche `dev-*` et la branche d'intégration déjà ouvert.
4. Le merge manuel de `graph.tsx` (branches arbitraires) affiche la même liste réelle de fichiers en
   conflit en cas d'échec, au lieu du message vide actuel.
5. Aucune UI de résolution champ par champ (choix de valeur base/ours/theirs) n'est introduite.
6. TypeScript / lint : zéro nouvelle erreur.
