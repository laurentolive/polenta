# T87 — Édition directe sur la branche d'intégration, retrait de "Faire une modification" / "Annuler"

## Contexte

Le workflow T83 impose aujourd'hui un aller-retour en 2 temps avant de pouvoir éditer quoi que ce
soit sur un repo dont la branche courante est la branche d'intégration configurée (`int-*`) :

1. Cliquer **"Faire une modification"** → popup titre → crée et checkout `dev-<slug>`
2. Éditer (l'édition n'est possible qu'une fois sur `dev-*` — tant qu'on est sur `int-*`,
   `SystemViewContext.readOnly` bloque toute sauvegarde)
3. Cliquer **"Publier"** → stage + commit + merge dans l'intégration + checkout intégration +
   suppression de `dev-*`

Pour un utilisateur non technique (ex. testeur exécutant une campagne), le concept de branche doit
disparaître de son parcours normal. Ce ticket inverse l'ordre : on édite d'abord, directement sur
la branche courante (y compris `int-*`), et la branche `dev-*` n'est créée qu'au moment de
publier — après coup, de façon transparente.

## Description fonctionnelle

### Ce qui disparaît

- **Le read-only lié à la convention `int-*`** (`VersioningContext.isReadonly` :
  `branch === '' || branch.startsWith('int-')`, et sa propagation dans
  `SystemViewContext.readOnly` via `isBranchReadonly`). Être checkouté sur la branche
  d'intégration n'empêche plus d'éditer.
- **Le bouton "Faire une modification"** (`ModificationControl`, mode `'view'`) — plus besoin de
  créer `dev-*` avant d'éditer.
- **Le bouton "Annuler"** (mode `'edit'`, avec sa popup de confirmation) — le discard de
  modifications en attente reste possible, mais uniquement via le panneau Version (action déjà
  existante, volontairement moins accessible pour limiter les pertes de travail accidentelles).
- **Le badge d'état** ("Lecture" / "Édition") affiché en permanence par `ModificationControl`. Il
  n'est pas remplacé par un autre indicateur — aucune notion de lecture-seule ne subsiste sur les
  branches.

### Ce qui reste bloqué

- **Detached HEAD** (repo checkouté sur un commit ou un tag — typiquement une baseline — sans
  branche courante). C'est la seule condition de blocage de **l'édition** elle-même, techniquement
  déjà portée par `SystemViewContext.isRepoReadonly` (`branch === ''`) et par l'équivalent racine
  dans `VersioningContext.isReadonly` (même test). Une baseline reste un snapshot figé : pour
  éditer, il faut d'abord checkout une branche (n'importe laquelle — `int-*`, `dev-*`, ou une
  branche créée manuellement depuis le panneau Version).
- **Publication interdite** (mais édition autorisée) quand la branche courante est une branche
  `int-*` **différente** de la branche d'intégration configurée du repo. Nouveau cas introduit par
  ce ticket, distinct du detached HEAD : l'utilisateur peut toujours éditer sur cette branche, mais
  "Publier" ne merge que vers la branche d'intégration configurée — merger depuis une autre
  branche `int-*` n'a pas de sens (deux branches d'intégration qui divergeraient) donc l'action est
  bloquée plutôt que silencieusement redirigée.
- Rien d'autre. Il n'y a plus de composant "en lecture seule" par nature — la notion de composant
  importé en lecture seule (SPEC-FORKS-BRANCHES-BASELINES.md §4.3, modèle `components.yaml` +
  `sourceRef` pointant une baseline) ne correspond à aucune implémentation actuelle (architecture
  réelle = submodules git plats, cf. T30) et n'a pas de traduction dans le code aujourd'hui — ce
  paragraphe de la spec est caduc et sera mis à jour par le sprint final de ce ticket.

### Ce qui change dans "Publier"

Chaque repo (root, composant ou interface) a sa propre branche d'intégration **configurée**
(`config/project.yaml` → `integrationBranch`, résolue via `useIntegrationBranch(repoPath)` —
mécanisme déjà existant, T79/T83). "Publier" merge **toujours** vers cette branche configurée du
repo concerné, jamais vers une autre. La résolution du comportement au clic sur "Publier" dépend de
la relation entre la branche courante et cette branche configurée — **et s'applique repo par repo**
(un workspace multi-repo peut avoir chaque repo sur une branche différente, chacun évalué
indépendamment) :

| Branche courante du repo | Comportement de "Publier" |
|---|---|
| `branch === integrationBranch` (cas nominal) | Popup titre → création de `dev-<slug>` **depuis la position courante** (le titre sert de slug + message de commit par défaut) → stage + commit sur `dev-<slug>` → merge vers `integrationBranch` → checkout `integrationBranch` → suppression de `dev-<slug>` (branche éphémère créée par ce flux) → push de `integrationBranch` vers `origin`. |
| `branch !== integrationBranch` et `branch` ne commence pas par `int-` (branche `dev-*` ou branche libre créée manuellement — usage avancé, utilisateur git) | Popup titre (sert de message de commit) → stage + commit **directement sur `branch`** (aucune branche intermédiaire créée) → merge de `branch` vers `integrationBranch` → push de `integrationBranch` vers `origin`. Le repo **reste checkouté sur `branch`** après publication — pas de checkout forcé vers l'intégration, pas de suppression de `branch` (elle a été créée par l'utilisateur, il en reste responsable). |
| `branch` commence par `int-` mais `branch !== integrationBranch` (une autre branche d'intégration que celle configurée pour ce repo) | **Publication interdite.** "Publier" n'est pas actionnable pour ce repo dans cet état (édition elle-même reste possible — seule la publication est bloquée, cf. §"Ce qui reste bloqué"). |
| Detached HEAD (`branch === ''`) | Édition bloquée (cf. §"Ce qui reste bloqué") — "Publier" non pertinent. |

Dans les deux premiers cas (publication autorisée), en cas de conflit de merge : comportement
inchangé (§2.4 SPEC-FORKS-BRANCHES-BASELINES.md) — l'utilisateur reste sur la branche de travail
(`dev-<slug>` ou `branch`), notification + lien vers résolution manuelle dans `/version-diff`, pas
de push tenté.

**Push automatique :** une fois le merge local réussi (les deux premiers cas), "Publier" pousse la
branche d'intégration vers `origin` (`sync:push-branch`, ciblée sur `integrationBranch` par son nom
— indépendant de la branche effectivement checkoutée après le merge). Sans ce push, un utilisateur
qui ne touche jamais au panneau Version n'aurait aucun moyen de partager son travail avec l'équipe.
Si le push échoue (remote divergé, réseau, authentification) : le merge local n'est **pas** annulé
(déjà acquis), une erreur non bloquante signale l'échec du push, l'utilisateur reste dans l'état
post-merge (checkouté sur `integrationBranch` dans le cas nominal, ou sur sa branche dans le cas
avancé) — à lui de résoudre depuis le panneau Version (pull puis push manuel, par exemple).

Le popup de titre s'affiche donc désormais **au moment de Publier**, plus au moment de commencer à
éditer.

## Comportements attendus par cas d'usage

| Cas | Comportement |
|-----|--------------|
| Repo checkouté sur sa branche d'intégration configurée, aucune modification en attente | Édition possible immédiatement (pas de popup, pas de branche créée). Bouton "Publier" visible mais désactivé. |
| Édition d'un champ, puis navigation vers un autre élément/repo sans publier | Modification sauvegardée localement (fichier écrit sur disque, non commitée) — persiste tant que l'utilisateur ne la publie pas ni ne la discard depuis le panneau Version. Comportement de sauvegarde locale inchangé par ailleurs (debounce existant de `SystemViewContext`). |
| Clic "Publier" avec des modifications en attente, sur la branche d'intégration | Popup titre → à la validation, séquence complète (création `dev-*`, stage, commit, merge, checkout intégration, suppression `dev-*`, push) sans étape intermédiaire visible pour l'utilisateur. |
| Clic "Publier" depuis une branche `dev-*` ou une branche libre (usage avancé) | Popup titre (message de commit) → stage + commit directement sur la branche courante → merge vers l'intégration configurée → push. Le repo reste sur cette branche après coup ; la branche n'est jamais supprimée automatiquement. |
| Repo checkouté sur une branche `int-*` différente de la branche d'intégration configurée | Édition autorisée, "Publier" non actionnable pour ce repo (cf. §"Ce qui reste bloqué"). |
| Checkout d'une autre branche/commit sur le même repo (panneau Version) alors qu'il y a des modifications en attente | Pas de blocage applicatif ajouté par ce ticket — comportement natif d'isomorphic-git : succès si aucun conflit de fichier (les modifications suivent alors sur la nouvelle cible), erreur native affichée telle quelle sinon. |
| Repo en detached HEAD (baseline ou commit arbitraire checkouté) | Édition bloquée, comme aujourd'hui (`isRepoReadonly` / `isReadonly` racine). L'utilisateur doit d'abord checkout une branche. |
| Push automatique en échec après un merge réussi | Le merge local n'est pas annulé ; une erreur non bloquante signale l'échec du push ; l'utilisateur reste dans l'état post-merge (checkout déjà effectué le cas échéant). |
| Création de baseline (T79) alors que des modifications sont en attente sur la branche d'intégration | Blocage inchangé — condition non contournable existante (SPEC-FORKS-BRANCHES-BASELINES.md §5.2). L'utilisateur doit Publier avant de pouvoir créer la baseline. |
| Panneau Version — indicateur "Lecture seule" (`VersionPanel.tsx`, basé sur `useVersioning().isReadonly`) | Doit refléter uniquement le detached HEAD désormais (plus jamais `int-*` seul) — cohérent avec le retrait du read-only sur les branches. |
| Workspace multi-repo, repos sur des branches différentes | Chaque repo est évalué indépendamment (branche courante vs sa propre branche d'intégration configurée) — pas de mode global unique pour le workspace. |

## Critères d'acceptation

1. Éditer un champ d'exigence/test alors que le repo (root ou composant) est checkouté sur sa
   branche d'intégration configurée sauvegarde localement sans erreur, sans créer de branche.
2. `ModificationControl` n'affiche plus que "Publier" (aucun bouton "Faire une modification",
   aucun bouton "Annuler", aucun badge Lecture/Édition).
3. "Publier" est désactivé tant que `pendingChangesCount === 0`, quelle que soit la branche
   courante (dès lors que ce n'est pas un detached HEAD).
4. Publier depuis la branche d'intégration avec des modifications en attente aboutit à : une
   branche `dev-*` éphémère créée puis supprimée, un commit sur cette branche avec le titre saisi
   comme message, un merge réussi dans la branche d'intégration configurée du repo, le repo
   re-checkouté sur cette branche d'intégration, et un push de cette branche vers `origin` — sans
   étape intermédiaire visible par l'utilisateur.
5. Publier depuis une branche `dev-*` ou une branche libre (pas la branche d'intégration, pas une
   autre branche `int-*`) aboutit à : un commit directement sur cette branche, un merge réussi vers
   l'intégration configurée, un push de l'intégration vers `origin`, et le repo reste checkouté sur
   la branche de départ (non supprimée).
6. "Publier" n'est pas actionnable quand la branche courante est une branche `int-*` différente de
   la branche d'intégration configurée du repo — l'édition reste possible dans cet état.
7. Un échec du push après un merge réussi n'annule pas le merge local ; une erreur non bloquante
   est affichée.
8. Éditer alors que le repo est en detached HEAD (baseline ou commit) reste bloqué, avec le même
   comportement qu'aujourd'hui.
9. La création de baseline reste bloquée si des modifications sont en attente sur la branche
   d'intégration du repo (aucune régression sur T79 §5.2).
10. Un conflit lors du merge de "Publier" laisse l'utilisateur sur la branche de travail (`dev-*`
    ou la branche courante selon le cas) avec ses modifications commitées intactes, affiche la
    liste des fichiers en conflit, et ne tente aucun push (comportement T84 inchangé pour la partie
    conflit).

## Hors scope explicite

- Toute UI de résolution de conflit champ par champ (déjà hors scope avant ce ticket, §2.4).
- Le blocage/déblocage de checkout quand des modifications sont en attente : on laisse le
  comportement natif de git, pas de garde applicative ajoutée (décision explicite de ce ticket).
- Le retrait de la notion de composant en lecture seule décrite dans
  SPEC-FORKS-BRANCHES-BASELINES.md §4.3 est *constaté* (spec caduque, sans traduction dans le code
  actuel) mais la mise à jour de cette section du fichier spec se fait au sprint final, pas ici.
- Le fichier de travail actuellement présent dans le repo principal mais non committé
  (`IntegrationBranchSelector.tsx` supprimé, `StructureTab.tsx`, `VersionRepoFolder.tsx`,
  `useBranchCheckout.ts` modifiés) est un chantier préexistant sans lien avec ce ticket — à ne pas
  toucher ni écraser ; à clarifier avec l'humain séparément si besoin avant de démarrer le sprint
  de dev.
