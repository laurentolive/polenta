# T88 — bug : l'arbre d'historique (Version) ignore le repo sélectionné

## Root cause

`GraphPage` (`apps/desktop/src/renderer/routes/graph.tsx`, route `/graph`, ouverte
depuis l'icône Historique du panneau Version) résolvait son `repoPath` via
`api.workspace.resolve(projectId)`, c'est-à-dire toujours la racine du workspace —
indépendamment du repo effectivement sélectionné dans l'arbre du panneau latéral.

Le panneau Version dispose pourtant déjà d'un mécanisme de sélection partagé,
`SelectedRepoContext` (T80) : cliquer sur un repo dans `VersionRepoFolder` appelle
`selectRepo(repoPath)`, et `/version-diff` lit déjà ce contexte pour suivre la
sélection en direct. `graph.tsx` n'avait simplement jamais été branché dessus — un
commentaire explicite dans le code l'anticipait :

> "Always the workspace root today — this view (Historique) has no per-repo
> selector. […] If this route is ever adapted to a non-root repo, wire
> propagatePinToDependents into checkoutBranchMut/checkoutCommitMut/the commit
> mutation below."

Ce commentaire pointait un second problème latent : les actions de checkout de
cette page (bouton ⎇ sur une ligne de commit, et le menu contextuel — checkout
branche/commit) appellent directement `api.sync.checkoutBranch`/`checkoutCommit`
sans propager le nouveau pin aux repos dépendants (`propagatePinToDependents`,
T82). Tant que `repoPath` était forcément la racine — que rien ne dépend — ce
n'était pas un bug. Une fois la page branchée sur le repo sélectionné, un checkout
depuis cette vue sur un repo composant aurait laissé les pins des repos
dépendants incohérents, exactement le problème que T82 avait corrigé ailleurs
(`VersionRepoFolder` / `useBranchCheckout`).

## Correctif appliqué

`apps/desktop/src/renderer/routes/graph.tsx` :

1. Remplacé la requête `api.workspace.resolve` (racine uniquement) par
   `useSelectedRepo()` (`SelectedRepoContext`, T80) — `repoPath` suit désormais
   en direct le repo sélectionné dans le panneau Version, avec la racine comme
   valeur par défaut (comportement inchangé tant qu'aucun repo n'est sélectionné
   explicitement).
2. Ajouté `useWorkspaceStructure(workspaceDir, rootRepoPath)` pour résoudre
   `flatNodes` et le nœud du repo sélectionné (`{ name, url }`), nécessaires à la
   propagation de pin.
3. Titre de la page : affiche le nom du repo sélectionné (`Arbre de versions —
   <nom>`) quand ce n'est pas la racine, pour lever toute ambiguïté sur ce qui est
   affiché.
4. Branché `propagatePinToDependents` (T82) sur les trois mutations de checkout
   de cette page : le bouton ⎇ de la ligne de commit (`checkoutMutation`), et
   `checkoutBranchMut`/`checkoutCommitMut` du menu contextuel — même mécanique
   que `useBranchCheckout`. Un avertissement (`PinPropagationWarning`, déjà utilisé
   ailleurs) s'affiche sous l'en-tête en cas de conflit/échec de propagation.
   No-op silencieux quand le repo sélectionné est la racine (rien n'en dépend).
   Les autres actions du menu contextuel (merge, rebase, push, delete, création
   de branche/tag) ne changent pas de HEAD sur un ref existant de la même façon
   qu'un checkout et restent hors du périmètre de la propagation de pin, comme
   dans `useBranchCheckout` (`createBranch` n'y est pas non plus branché).

Aucun autre fichier modifié. `pnpm typecheck` (apps/desktop) : 0 erreur.

## Comment vérifier

1. Ouvrir un workspace avec au moins un repo composant sous la racine.
2. Dans le panneau Version, cliquer sur un repo composant (pas la racine) pour le
   sélectionner.
3. Cliquer sur l'icône Historique (⏱) : l'arbre affiché doit être celui du repo
   composant sélectionné (commits, branches, tags spécifiques à ce repo), avec le
   nom du repo dans le titre.
4. Revenir au panneau Version, sélectionner un autre repo (ou la racine) sans
   renaviguer manuellement vers `/graph` — si la page Historique est encore
   montée/ré-ouverte, elle doit suivre la nouvelle sélection.
5. Si le repo sélectionné est déclaré comme dépendance ailleurs dans le workspace
   (cas diamant / interface partagée) : faire un checkout de branche ou de commit
   depuis cette page et vérifier que le pin est proposé aux repos dépendants
   (mêmes effets qu'un checkout fait depuis le panneau Version lui-même), avec un
   avertissement affiché en cas de conflit.
6. Vérifier que le comportement historique (repo racine par défaut, aucune
   sélection explicite) est inchangé.

Non testé interactivement (pas d'Electron attachable dans cette session) — attend
validation manuelle humaine avant archivage/merge.
