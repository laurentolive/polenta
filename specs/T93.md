# T93 — Query Builder : les types des composants submodule n'apparaissent jamais

## Contexte

Signalé par l'utilisateur : « dans le dashboard req builder on ne voit que les
elements du repo root ». Le "Query Builder" (page `/query`, mode Builder) sert
aussi à créer les requêtes utilisées par les widgets du Dashboard — le symptôme
touche donc les deux.

---

## Root cause

**Fichiers** :
- `apps/desktop/src/renderer/components/dashboard/QueryBuilder.tsx` (`getQueryableTypes`)
- `apps/desktop/src/renderer/routes/query.tsx`
- `apps/desktop/src/main/services/query-engine.service.ts` (`resolveTableInfo`, `buildSql`)

Le sélecteur "Type d'objet" du builder était alimenté par `useProjectSchema(repoPath)`,
qui ne lit que le `schema.yaml` du repo **root** (produit). Un nœud submodule ne
déclare pas ses `objectTypes` localement dans le schéma du produit — « le schéma du
composant fait foi » (CLAUDE.md) — donc `getQueryableTypes(schema)` ne pouvait
jamais lister un type appartenant à un composant.

Résultat : impossible de sélectionner un type de composant dans le builder, donc
impossible de filtrer/afficher ses exigences — alors que le moteur de requête
(`buildDataset()`) agrège **déjà** requirements/tests de tous les composants du
workspace (repo courant + submodules, via `tree.cache.yaml`). Le picker de type
n'était simplement pas branché sur la même source multi-composant que les
données qu'il est censé filtrer.

Le mécanisme correct existait déjà ailleurs dans le code
(`useWorkspaceStructure` → `schemasByRepoPath`, utilisé par `StructureTab.tsx` /
`SystemViewContext.tsx`) mais n'était pas réutilisé par le Query Builder.

### Complication : `objectTypeRef` n'est pas unique entre composants

Chaque repo composant est autonome et nomme systématiquement son propre nœud
schéma local `root` (CLAUDE.md, règle 7). Deux composants différents peuvent
donc tous les deux déclarer un type `root::exigence-fw` — `objectTypeRef` seul
ne suffit pas à identifier sans ambiguïté "de quel composant" une fois agrégé
dans un même dataset. Le dataset agrégé (`flattenRequirement`/`flattenTestCase`)
tague déjà chaque ligne avec un champ `component` (nom du mount workspace) —
c'est ce tag qui lève l'ambiguïté, mais rien ne le propageait jusqu'au filtre
`WHERE [objectTypeRef] = ...` généré par `buildSql()`, ni jusqu'au calcul des
champs autorisés (`resolveTableInfo()`, qui ne résolvait `objectTypeRef` que
contre le schéma du repo root).

---

## Correctif appliqué

**`packages/types/src/dashboard.ts`** — `BuilderConfig` gagne un champ optionnel
`component?: string` (mount name du composant propriétaire du type sélectionné ;
absent = repo courant/racine, comportement historique inchangé).

**Frontend** (`QueryBuilder.tsx` + `query.tsx`) :
- `getQueryableTypes` prend maintenant `flatNodes` + `schemasByRepoPath` (déjà
  exposés par `useWorkspaceStructure`, remplace `useProjectSchema(repoPath)`
  dans `query.tsx`) et liste les types de **tous** les composants du workspace,
  qualifiés par leur mount name.
- Chaque option du `<select>` encode `{component, objectTypeRef}` (`ref` seul
  n'étant pas unique entre composants) ; `onChange` décode la paire et la pose
  sur `BuilderConfig`.
- `switchToSql()` passe désormais `workspaceDir` à `api.queries.builderToSql`.

**Backend** (`query-engine.service.ts`) :
- `resolveTableInfo(repoPath, objectTypeRef, component, workspaceDir)` résout
  désormais le schéma contre le repo du **composant réellement propriétaire du
  type** (résolu via le cache `tree.cache.yaml`, nouvelle méthode privée
  `resolveComponentPath`) quand `component` est fourni, au lieu de toujours lire
  le schéma du repo root — cohérent avec le commentaire déjà présent dans
  `buildDataset()` ("objectTypeRef n'est significatif que contre le schéma LOCAL
  de son propre composant").
- `buildSql()` ajoute `AND [component] = '<mount name>'` à la clause de scope
  quand `config.component` est renseigné, en plus de `[objectTypeRef] = ...`.
- `builderToSql()` et `execute()` propagent `workspaceDir`/`config.component`
  jusqu'à `resolveTableInfo`.

**IPC / api-client** : `queries:builder-to-sql` (handler, `ipc-client.ts`,
`types.ts`) prend un paramètre `workspaceDir` optionnel supplémentaire, sur le
modèle de `queries:execute` qui l'avait déjà.

### Pourquoi pas de filtre `component` pour le repo root

Les nœuds de `tree.cache.yaml` nomment le repo root d'après le nom de son
dossier (`path.basename(rootRepoPath)`), alors que son propre `schema.yaml`
nomme son nœud local `root` — deux vocabulaires différents qui ne coïncident
pas. Comme il n'y a aucune ambiguïté possible sur les types du repo root
(un seul repo root par workspace), le correctif ne pose `component` que pour
les types appartenant à un composant **autre** que le repo courant
(`node.repoPath !== selfRepoPath` dans `QueryBuilder.tsx`) — comportement du
repo root strictement inchangé, y compris pour les projets mono-repo sans
composants (aucune régression : `useWorkspaceStructure` retourne alors un seul
nœud `flatNodes = [{name: 'root', repoPath}]`, identique à `selfRepoPath`, donc
toujours sans tag `component`).

## Comment vérifier

### Cas de test manuel

Prérequis : un workspace produit avec au moins un composant submodule ayant son
propre `schema.yaml` déclarant un type `requirement` ou `test`, et au moins une
exigence créée dans ce composant.

1. Ouvrir `/query` sur le workspace produit.
2. Ouvrir le sélecteur "Type d'objet" du builder.

   **Avant le fix** : seuls les types du repo root apparaissent.
   **Après le fix** : les types de chaque composant apparaissent aussi, préfixés
   par le label du composant (ex. "Contrôle moteur / Exigence FW").
3. Sélectionner un type d'un composant, exécuter sans condition : les lignes du
   composant apparaissent dans le résultat (colonne `component` = mount name du
   composant).
4. Ajouter une condition sur un champ custom propre à ce type (pas un champ
   système) : la liste de champs proposée correspond au schéma du composant, et
   le filtre fonctionne (pas d'erreur "Champ inconnu pour ce type d'objet").
5. Régression : sélectionner un type du repo root, vérifier que le résultat est
   identique à avant le fix (pas de filtre `component` ajouté, toutes les
   exigences root visibles).
6. Régression mono-repo (projet sans composants) : le picker se comporte à
   l'identique d'avant (un seul groupe de types, sans préfixe de composant).

Non testé interactivement dans cette session (pas d'Electron attachable) —
`pnpm typecheck` passe sans erreur nouvelle sur `@polenta/desktop`,
`@polenta/api-client` et `@polenta/types` (l'unique échec de `pnpm typecheck`
