# T94 — Préférence projet : propagation automatique du pin

## Contexte

Décision actée le 2026-07-14 (voir CLAUDE.md, section « Modèle de données ») : le comportement de
propagation du `pin` d'un sous-repo (submodule) vers le manifeste de son repo parent, lorsque ce
sous-repo reçoit un commit, doit être piloté par une **option au niveau du projet** (auto vs
approbation manuelle par l'intégrateur), et non codé en dur.

Ce ticket ne couvre **que** l'ajout du support de cette préférence dans le modèle de données et son
point d'édition dans l'UI. La logique de propagation elle-même (déclenchement au commit, écriture du
pin dans `polenta-repo.yaml` du parent, etc.) dépend de la refonte multi-repo de la vue Version, qui
n'est pas encore implémentée — elle est hors scope ici.

## Description fonctionnelle

- `ProjectSchema` gagne un champ racine optionnel `preferences`, indépendant de `nodes` /
  `objectTypes` / `linkTypes` (options d'outil, pas de modèle métier).
- Première préférence : `preferences.autoPropagatePin: boolean` (défaut `false` si absent —
  comportement actuel inchangé tant que rien n'est coché).
- Dans la page **Modèle de données** (`/schema`), un nouvel onglet **Préférences** est ajouté à côté
  de Structure / Liens / Interfaces. Il contient une case à cocher :
  « Propager automatiquement le pin des sous-repos vers le repo parent lors d'un commit reçu sur le
  sous-repo », suit le même flux de brouillon + bouton Enregistrer que l'onglet Liens (pas
  d'écriture immédiate).
- Cette préférence est un réglage **par repo** (chaque `schema.yaml` a la sienne), au même titre que
  le reste du schéma — pas un réglage global à tous les projets ouverts.

## Comportements attendus

1. Un repo sans `preferences` dans son `schema.yaml` (schéma existant avant ce ticket) charge sans
   erreur ; la case Préférences apparaît décochée.
2. Cocher la case, Enregistrer → `preferences: { autoPropagatePin: true }` écrit dans
   `.polenta/schema.yaml`.
3. Décocher puis Enregistrer alors que c'était `true` → la clé repasse à `false` (pas de suppression
   de la clé, cohérent avec le reste du schéma qui garde ses clés à valeur par défaut explicite
   quand elles ont déjà été écrites une fois).
4. Annuler (Échap / bouton Annuler) sur l'onglet Préférences revient à l'état sauvegardé, comme les
   autres onglets.

## Critères d'acceptance

- [ ] `ProjectSchema.preferences?.autoPropagatePin` typé dans `packages/types/src/schema.ts`
- [ ] `SchemaService` (lecture/écriture disque) round-trip la clé sans la perdre ni la forcer
- [ ] Onglet « Préférences » visible et fonctionnel dans `/schema`, suit le flux dirty/save/cancel
      existant (comme l'onglet Liens)
- [ ] Aucune régression TypeScript (`npm run typecheck` ou équivalent, zéro nouvelle erreur)
- [ ] Un schéma existant sans `preferences` continue de se charger normalement (rétrocompatibilité)

## Hors scope

- Logique effective de propagation du pin au commit (dépend de la refonte Version multi-repo, non
  codée à ce jour — voir mémoire projet « Refonte vue Version multi-repo »)
- Granularité fine par lien parent/enfant (tranché : option globale au projet, cf. CLAUDE.md)
- Toute UI en dehors de la page Modèle de données
