# T97 — Paramètres de test, saisie des valeurs à l'ajout en campagne

## Contexte

Un cas de test (`TestCase`) est aujourd'hui un texte fixe : `preconditions`,
`postconditions` et chaque étape (`action`/`expectedResult`/`notes`) sont des champs
`RICHTEXT` figés à la rédaction du test (SPEC-TESTS.md §2.2–2.4). Pour un test qui varie
seulement par une valeur numérique ou un réglage (ex. « appliquer {voltage} pendant
{duration} secondes »), il faut aujourd'hui dupliquer le test entier pour chaque valeur
testée — pas de mécanisme de variable/paramètre dans le modèle actuel (aucune notion de
paramètre, template ou placeholder n'existe dans le code, confirmé par recherche
transverse `parameter`/`template`/`placeholder`/`{{`).

Ticket original : « Ajouter la possibilité d'ajouter des paramètres à un test. Dans les
champs du test, chaque paramètre est référencé par son label entre {} (exemple
{voltage}). Lors de l'ajout du test à la campagne l'utilisateur doit spécifier les
paramètres s'il y en a de le test ajouté. »

**Décisions de conception tranchées avec l'utilisateur avant rédaction** (cf. §"Ce qui a
été tranché") :
1. Pas de liste de paramètres déclarée séparément — un paramètre est détecté
   automatiquement par scan du texte, la référence `{label}` **est** la déclaration.
2. Le scan porte sur les champs système `preconditions`, `postconditions` et les 3 champs
   de chaque étape (`action`/`expectedResult`/`notes`) — pas sur les champs personnalisés
   du template (`fields: {}`).
3. Les valeurs saisies à l'ajout en campagne sont **substituées** dans le texte affiché à
   l'exécution du test dans cette campagne (pas juste stockées à part).

Important : `addTests()` (`campaigns.service.ts`) référence aujourd'hui le test par
`testCaseId` **sans copie de contenu** (T49, qui introduirait une copie figée à l'ajout,
n'est pas implémenté). L'exécution (`campaign.$campaignId.execute.$testId.tsx`) relit
donc le test **en direct** (`api.tests.get`) à chaque affichage. Ce ticket ne dépend pas
de T49 : les valeurs de paramètres sont stockées séparément, au niveau de l'entrée
`CampaignTestRun` de la campagne, et combinées avec le contenu du test relu en direct au
moment de l'affichage (voir §"Cas limite : test modifié après ajout").

## Description fonctionnelle

### 1. Détection des paramètres d'un test

Un paramètre est une sous-chaîne `{label}` trouvée dans le texte HTML de l'un des 5
champs scannés : `TestCase.preconditions`, `TestCase.postconditions`, et pour chaque
`TestStep` : `action`, `expectedResult`, `notes`.

- Motif reconnu : `{` suivi d'un ou plusieurs caractères alphanumériques/`_`/`-` (pas
  d'espace, pas d'accolade imbriquée), suivi de `}` — ex. `{voltage}`, `{max_current}`,
  `{temp-ambiante}`. Un texte contenant `{2 mesures}` (espace) n'est **pas** reconnu comme
  paramètre.
- La liste des paramètres d'un test = labels uniques trouvés (un même label répété
  plusieurs fois dans le texte = un seul paramètre, une seule valeur pour toutes ses
  occurrences), dans l'ordre de première apparition : `preconditions` → étapes dans
  l'ordre (`action` puis `expectedResult` puis `notes` de chaque étape) → `postconditions`.
- Calcul côté client à partir du contenu déjà chargé du test (pas de nouvel endpoint
  backend nécessaire a priori — à confirmer en Design) : une fonction utilitaire
  `extractTestParameters(testCase) → string[]`.
- Un test sans aucun `{label}` reconnu a une liste de paramètres vide — comportement
  actuel inchangé pour ces tests (aucune saisie supplémentaire demandée à l'ajout).

### 2. Saisie des valeurs à l'ajout en campagne

Dans le panneau "+ Ajouter des tests" de `campaign.$campaignId.tsx` (liste à cocher
existante, §agent exploration : state `addingTests`/`selectedToAdd`, mutation
`api.campaigns.addTests`) : pour chaque test coché qui a au moins un paramètre détecté,
un formulaire inline apparaît (sous la ligne du test, ou dans une étape de confirmation
dédiée — détail laissé au Design) avec un champ texte libre par paramètre, libellé par
son label (`{voltage}` → champ "voltage").

- Valeur : texte libre, une ligne, obligatoire (pas de valeur vide) — cohérent avec le
  pattern déjà en place pour `EquipmentUsed.identification` (« champ libre »,
  SPEC-TESTS.md §3.2).
- Le bouton de confirmation d'ajout est désactivé tant qu'un paramètre détecté d'un test
  sélectionné n'a pas de valeur saisie.
- Tests sans paramètre parmi la sélection : ajoutés sans formulaire, comportement actuel
  inchangé.
- Les valeurs sont propres à **cette entrée du test dans cette campagne** — si le même
  test est ajouté séparément à deux campagnes (ou deux fois indirectement, ce qui n'est
  pas possible aujourd'hui, `addTests` dédoublonne), chaque instance a ses propres
  valeurs.

### 3. Stockage

`CampaignTestRun` (`packages/types/src/campaign.ts`) gagne un champ optionnel
`paramValues?: Record<string, string>` (label → valeur), rempli à l'ajout, absent/`{}` si
le test n'a pas de paramètre. `addTests()` (backend) doit accepter, pour chaque
`testCaseId` ajouté, les valeurs de paramètres associées (signature exacte — tableau
d'objets `{testCaseId, paramValues?}` plutôt que `string[]` — à trancher en Design).

### 4. Substitution à l'exécution

Sur les pages qui affichent le contenu du test dans le contexte d'une campagne —
`campaign.$campaignId.execute.$testId.tsx` (exécution) et
`campaign.$campaignId.run.$testId.tsx` (lecture seule d'un run terminé) — avant le rendu
(`dangerouslySetInnerHTML`) de `preconditions`, `postconditions` et de chaque
`action`/`expectedResult`/`notes` d'étape, chaque occurrence de `{label}` présente dans le
texte est remplacée par la valeur stockée dans `CampaignTestRun.paramValues[label]` pour
ce test dans cette campagne, **si elle existe**.

- **Sécurité** : la valeur saisie par l'utilisateur est un texte libre injecté dans du
  HTML pré-existant affiché via `dangerouslySetInnerHTML` — elle doit être échappée
  (échappement HTML des caractères `< > & " '`) avant substitution, pour ne pas ouvrir de
  vecteur d'injection HTML/script via un paramètre malicieusement rempli (ex. valeur
  `<script>...</script>`).
- Hors du contexte d'une campagne (fiche de définition du test `test.$testId.tsx`,
  panneau "+ Ajouter des tests" avant confirmation) : aucune valeur n'existe encore, le
  texte continue d'afficher `{label}` littéralement, sans mise en forme spéciale (pas de
  surlignage — voir Hors scope).

### Cas limite : test modifié après ajout

Comme l'ajout référence le test en direct (pas de copie, T49 non fait), le contenu relu à
l'exécution peut différer de celui qui existait au moment de l'ajout :

- Un paramètre présent dans le texte actuel mais absent de `paramValues` (nouveau
  `{label}` apparu depuis l'ajout, ex. nouvelle version approuvée du test) : affiché
  littéralement (`{label}`, non substitué) à l'exécution — pas d'erreur, pas de blocage.
- Une valeur présente dans `paramValues` dont le `{label}` n'apparaît plus dans le texte
  actuel (paramètre supprimé du test depuis) : simplement ignorée.

### Édition des valeurs après ajout

Une fois le test ajouté à la campagne, ses valeurs de paramètres restent modifiables
(erreur de saisie possible) — affordance d'édition sur la ligne du test dans la liste des
tests de la campagne (`campaign.$campaignId.tsx`), UI exacte laissée au Design. Sans
cette possibilité, une faute de frappe obligerait à retirer puis ré-ajouter le test.

## Comportements attendus par cas d'usage

| Cas | Comportement attendu |
|---|---|
| Test sans aucun `{label}` dans ses champs scannés, ajout à une campagne | Comportement actuel inchangé — aucune saisie demandée. |
| Test avec `{voltage}` dans une étape, sélectionné pour ajout à une campagne | Un champ de saisie "voltage" apparaît avant confirmation ; l'ajout est bloqué tant qu'il est vide. |
| Test avec `{voltage}` répété dans 3 champs différents (précondition + 2 étapes) | Un seul champ de saisie "voltage" — la valeur saisie s'applique aux 3 occurrences à l'exécution. |
| Ajout groupé de 3 tests dont 2 ont des paramètres | Formulaire de saisie affiché uniquement pour les 2 tests concernés ; le 3e s'ajoute sans saisie. |
| Ouverture de la page d'exécution d'un test ajouté avec `voltage=24V` | Le texte affiché remplace `{voltage}` par `24V` partout où il apparaît dans preconditions/steps/postconditions. |
| Valeur de paramètre saisie contenant des caractères `<`/`>`/`&` | Affichée telle quelle en texte à l'exécution, sans être interprétée comme du HTML. |
| Le test est modifié (nouvelle version) après avoir été ajouté à une campagne avec un paramètre en moins | Le nouveau `{label}` s'affiche littéralement à l'exécution (non substitué), sans erreur. |
| Consultation de la fiche de définition du test (hors campagne) | `{label}` s'affiche tel quel, comme aujourd'hui — aucune substitution, aucun style particulier. |
| Faute de frappe détectée après ajout | L'utilisateur modifie la valeur depuis la liste des tests de la campagne, sans retirer/ré-ajouter le test. |
| Lecture d'un run terminé (`run.$testId.tsx`) | Mêmes valeurs substituées qu'à l'exécution — cohérence entre exécution en cours et relecture a posteriori. |

## Critères d'acceptation

1. `extractTestParameters` (ou équivalent) détecte tous les `{label}` uniques d'un test
   dans `preconditions`, `postconditions`, `action`/`expectedResult`/`notes` de chaque
   étape — pas dans les champs personnalisés (`fields`) ni dans `equipment`.
2. Le panneau d'ajout de test à une campagne demande une valeur par paramètre détecté,
   pour chaque test sélectionné qui en a, et bloque la confirmation tant qu'une valeur
   requise est vide.
3. `CampaignTestRun` persiste les valeurs saisies (`paramValues`), par test et par
   campagne (deux campagnes différentes avec le même test = valeurs indépendantes).
4. `campaign.$campaignId.execute.$testId.tsx` et
   `campaign.$campaignId.run.$testId.tsx` affichent le texte du test avec chaque
   `{label}` remplacé par sa valeur stockée, échappée pour ne pas être interprétée comme
   du HTML.
5. Un `{label}` sans valeur stockée (test modifié depuis l'ajout) s'affiche littéralement
   à l'exécution sans provoquer d'erreur ni bloquer l'affichage.
6. Les valeurs d'un test déjà ajouté à une campagne sont modifiables depuis la liste des
   tests de la campagne.
7. Un test sans `{label}` détecté ne change pas de comportement (aucune saisie
   supplémentaire, aucun impact sur `addTests()`).

## Hors scope explicite

- **Surlignage visuel des `{label}`** dans l'éditeur (`RichTextField`) ou le visionneur
  (`RichTextViewer`) richtext, en dehors du contexte d'exécution d'une campagne — ces
  composants sont partagés avec les exigences et d'autres types d'objets ; ce ticket ne
  les modifie pas. Le token reste un texte brut comme un autre.
- **Typage des valeurs de paramètre** (nombre, enum, unité…) — toute valeur est un texte
  libre, sans validation de format, comme `EquipmentUsed.identification`.
- **Dépendance à T49** (copie du test à l'ajout en campagne) — non nécessaire pour ce
  ticket, les deux tickets restent indépendants et peuvent être livrés dans n'importe
  quel ordre.
- **Exécution de test hors campagne** (run isolé, `campaignRunId: null` dans
  SPEC-TESTS.md §3.2) — aucune route de ce type n'existe actuellement dans le code
  (seules les routes sous `campaign.$campaignId.*` exécutent un test) ; si une telle route
  est ajoutée plus tard, elle n'a par construction aucune valeur de paramètre à substituer
  (la saisie n'a lieu qu'à l'ajout en campagne).
- **Import de résultats automatisés** (JUnit XML, SPEC-TESTS.md §3.5) — pas concerné par
  les paramètres, aucun changement.
- **Génération automatique de campagne** depuis une sélection d'exigences
  (SPEC-TRACEABILITY.md) — si les tests générés ont des paramètres, ils suivront le même
  écran d'ajout ; pas de pré-remplissage automatique de valeurs dans ce ticket.

## Addendum sprint 2 — instances multiples d'un même test paramétré

Retour utilisateur après le sprint 1 : « on doit pouvoir ajouter plusieurs fois le même
test dans une campagne s'il y a des paramètres, et la liste des tests de la campagne
doivent faire apparaître les paramètres s'il y en a. »

Deux ajouts au périmètre initial :
1. **Instances multiples** — un test avec au moins un paramètre `{label}` peut être inclus
   plusieurs fois dans la même campagne (ex. `{voltage}` testé à 12V et 24V dans deux
   exécutions distinctes de la même campagne). Un test **sans** paramètre reste limité à
   une seule inclusion (comportement du sprint 1 inchangé pour ce cas).
2. **Affichage des valeurs dans la liste** — la liste des tests d'une campagne affiche
   désormais les valeurs de paramètres d'une instance directement sous son titre (pas
   seulement accessible via l'édition).

Voir `T97-design.md` §9 pour la conception (identifiant `entryId`) et `T97-sprint2.md`
pour l'implémentation.
