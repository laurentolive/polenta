# T98 — Connexion GitHub simplifiée (OAuth Device Flow)

## Contexte

L'écran de connexion actuel (`login.tsx` / `AccountPanel.tsx` / `auth.service.ts`) n'accepte qu'un
Personal Access Token (PAT) collé manuellement. GitHub a désactivé l'authentification Git/API par
identifiant + mot de passe brut depuis 2021 — un champ « login / mot de passe » générique ne
fonctionnerait donc pas contre github.com. Générer un PAT (Settings → Developer settings →
Personal access tokens, choix des scopes) est une manipulation trop technique pour un utilisateur
non-initié, qui ne connaît que son login/mot de passe GitHub habituel.

Décision actée avec l'humain (2026-07-15) : ajouter le **GitHub OAuth Device Flow** comme second
mode de connexion, **en plus** du formulaire PAT existant (pas de remplacement, pas de statut
« avancé/caché » — les deux options ont la même visibilité). Ce flow est celui utilisé par
`gh auth login`, VS Code, Docker CLI : l'utilisateur clique « Se connecter avec GitHub », l'appli
affiche un code court et ouvre `github.com/login/device` dans le navigateur système : il s'y
connecte avec son compte GitHub habituel (login/mot de passe + 2FA le cas échéant) et valide.
Polenta récupère le token automatiquement par polling, sans jamais afficher ni demander de PAT.

Le Device Flow est spécifique à un provider OAuth (GitHub, GitLab.com, Gitea≥1.17 l'implémentent
chacun avec leurs propres endpoints) — ce ticket ne couvre que **GitHub** (`github.com`), cohérent
avec son titre. GitLab/Gitea self-hosted restent sur le formulaire PAT existant.

## Description fonctionnelle

- Sur l'écran `/login`, quand le remote sélectionné est `https://github.com`, un second bloc
  apparaît au-dessus ou à côté du formulaire PAT : bouton **« Se connecter avec GitHub »**.
- Au clic :
  1. Polenta demande un `device_code` / `user_code` à GitHub (`POST
     https://github.com/login/device/code`, scope `repo`).
  2. L'appli affiche le `user_code` en gros caractères (+ bouton copier) et ouvre
     `https://github.com/login/device` dans le navigateur par défaut de l'utilisateur.
  3. Pendant que l'utilisateur valide dans le navigateur, l'appli poll
     `POST https://github.com/login/oauth/access_token` à l'intervalle recommandé par GitHub
     (`interval`, ≥5s) et affiche un état « En attente de validation dans le navigateur… ».
  4. À la validation, le token OAuth obtenu est traité **exactement comme un PAT** dans le reste du
     système : résolution d'identité (`resolveGithubIdentity`, déjà existant), stockage via
     `keytar`/`auth.json` (`setup()` existant), author git, credentials HTTPS pour
     `isomorphic-git` (`onAuth`) — aucune nouvelle voie de stockage de token à créer.
  5. L'utilisateur est redirigé vers `/` comme après une connexion par PAT réussie.
- Bouton **Annuler** pendant l'attente : arrête le polling, revient à l'état initial de l'écran.
- Le formulaire PAT reste affiché et pleinement fonctionnel en parallèle (aucune régression), pour
  GitHub comme pour les autres remotes.

## Comportements attendus par cas d'usage

1. **Connexion nominale** : clic « Se connecter avec GitHub » → code affiché → validation dans le
   navigateur → l'appli détecte le succès au polling suivant → redirection `/` avec identité
   résolue (nom, email, avatar si disponible), token stocké au même endroit qu'un PAT classique.
2. **Utilisateur ferme le navigateur sans valider** : au bout de `expires_in` (typiquement 900s
   côté GitHub), le polling reçoit `expired_token` → message d'erreur « Code expiré, réessayez » →
   retour à l'état initial (pas de boucle infinie).
3. **Utilisateur clique Annuler pendant l'attente** : le polling s'arrête immédiatement, aucun
   token n'est demandé une fois annulé, retour à l'état initial.
4. **Utilisateur refuse l'autorisation côté GitHub** : réponse `access_denied` → message d'erreur
   explicite, retour à l'état initial.
5. **Rythme de polling trop rapide** (`slow_down`) : l'appli augmente l'intervalle de polling en
   conséquence plutôt que d'échouer.
6. **Remote ≠ github.com** (GitLab, Gitea, custom) : le bouton Device Flow n'apparaît pas, seul le
   formulaire PAT est visible (comportement actuel inchangé).
7. **Pas de réseau / GitHub indisponible** pendant la demande de code ou le polling : message
   d'erreur, pas de crash, possibilité de réessayer.
8. **Après connexion réussie**, `AccountPanel` / `account.tsx` affichent l'identité résolue de la
   même manière qu'après une connexion PAT — aucune UI spécifique « connecté via Device Flow » à
   distinguer visuellement.

## Critères d'acceptance

- [ ] Bouton « Se connecter avec GitHub » visible sur `/login` uniquement quand le remote effectif
      est `https://github.com`
- [ ] Flow complet fonctionnel : code affiché, navigateur ouvert automatiquement, polling, succès →
      identité résolue + redirection `/`
- [ ] Cas expiration (`expired_token`), refus (`access_denied`) et ralentissement (`slow_down`)
      gérés sans crash et avec message compréhensible
- [ ] Annulation manuelle stoppe le polling sans effet de bord
- [ ] Token obtenu par Device Flow stocké et consommé via le même mécanisme que le PAT
      (`keytar`, `auth.json`, `getHttpsCredentials`) — pas de nouveau chemin de stockage
- [ ] Formulaire PAT existant non régressé (toujours visible et fonctionnel, GitHub compris)
- [ ] Aucune régression TypeScript / lint (zéro nouvelle erreur)

## Hors scope

- GitLab.com / Gitea / GitHub Enterprise Server (Device Flow potentiellement supporté par ces
  plateformes mais non traité ici — restent sur PAT)
- Suppression ou masquage du formulaire PAT (décision actée : les deux options coexistent à égalité)
- Rafraîchissement automatique du token (GitHub OAuth Apps classiques n'expirent pas les tokens
  Device Flow par défaut ; pas de refresh token à gérer)
- Détection/migration des comptes déjà connectés par PAT vers OAuth

## Point ouvert à trancher avant la phase Dev

Le Device Flow nécessite un **`client_id` d'une OAuth App GitHub** enregistrée par le mainteneur du
projet (Settings → Developer settings → OAuth Apps → New OAuth App ; aucun *client secret* requis
côté client pour ce flow, donc safe à embarquer dans l'appli distribuée). **Ce `client_id` doit être
fourni avant le sprint de dev** — proposition : variable d'environnement / config build
`GITHUB_OAUTH_CLIENT_ID` (cohérent avec le pattern `process.env` déjà utilisé dans
`apps/desktop/src/main/index.ts`). À valider en review de spec.
